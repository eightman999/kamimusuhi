## 結論

最優先は **Jevへ判断に必要な根拠を渡し、回答の適合性を小さな質問に分けること**。現在のJevは候補文を読めるが、LLMが参照した会話履歴・記憶・観測本文を受け取っていない。ここを補わず判定回数だけ増やしても、記憶の捏造や自己・他者の混同を検証する材料が足りない。

その上で、候補別の判定を一括取得し、RETRYの理由、関連記憶、不足する観測の選択へ利用する。既存の「全対象LLMを並行生成して比較する」経路を基準とし、生成前の器官選択は別の比較実験にする。

## 公式仕様から分かる適性

- 公開プリミティブは `Choice`、`Score`、`Noul`。小さな判断に分け、結果をコードで組み合わせる設計が推奨されている。[Introduction](https://docs.typesafe.ai/introduction)
- 複数質問は同一stateに対して並列・独立評価される。他の質問の回答は見えない。依存する分岐はコードで処理する。[Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out)
- `confidence` はChoice／Scoreの確率分布から算出した統計値で、正答率そのものではない。Noulには別のconfidenceがない。計算式の詳細はこの公式ページでは確認できなかった。[Confidence](https://docs.typesafe.ai/confidence)
- 確認時点の固定モデルは `jev-1.13.0`。入力 $0.042/Mtoken、出力無料。総request 64k token、stateと最長質問の合計32k token。英語が主学習言語で、日本語を含むCJKは同等精度ではないと明記されている。評価では固定IDと実際に返ったmodelを記録する。[Models](https://docs.typesafe.ai/models)
- 無関係な長いstate、数値・日時計算、複雑な間接推論、敵対的入力が既知の弱点。Choiceの候補間比較と、候補が単独で条件を満たす判定は別物である。[Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

質問追加で「レイテンシがあまり増えない」という説明はベンダーの主張であり、当地からの日本語対話のp95は未測定。requestをまたぐprompt cacheの契約・割引は確認できていない。

単純な欠損、文字数、ID一致、日時順序、timeout、privacy許可は既存コードで判断する。高頻度の数値K-COREループへクラウドJevを接続する優先度は低い。接続する場合も、低頻度の意味的な観測選択として別評価する。

## 最優先案を具体化する

### 判断用の最小根拠

生成時と判定時で共有する、ターン内の判断用データを作る。

```text
user_text
evidence_snapshot:
  snapshot_digest
  relevant_history: 話者、発言本文、evidence_id
  relevant_memories: subject、出典ID、現在有効か、内容
  observations: 観測ID、時点、LIVE/RECORDED/未取得、内容
  research: 主張、supported/failed/invalid等、制限、出典
candidates:
  candidate_id、attempt、response_digest、応答全文
```

これらは提案する内部表現で、現行型に既に存在するという意味ではない。根拠がない場合も空欄から推測させず「取得していない」と明示する。Jevへの外部送信が許される内容だけを選び、必要な根拠を渡せない場合は根拠充足を未判定とする。digestだけでは内容の意味照合はできない。

全履歴をそのまま追加する案は避ける。既存の出典区分を保った関連項目を選び、LLMに渡したsnapshotとの対応を記録する。鮮度やsubjectの一致など機械的に判定できる条件は送信前にコードで検証する。

### 候補ごとの小さな質問

| 質問 | 型の候補 | 役割 |
| --- | --- | --- |
| この候補の事実主張は提示根拠で裏付けられるか | Choice: `SUPPORTED / CONTRADICTED / INSUFFICIENT / NOT_APPLICABLE` | 会話履歴や未観測事項の捏造を検出する。挨拶など非事実文は区別。 |
| 自分・相手・外部情報の帰属は正しいか | Choice: `CONSISTENT / CONFLICT / UNCLEAR` | 出典の取り違えを検出する。 |
| 今回の要求に答えているか | Choiceまたは記述的Score | 流暢さとタスク達成を分ける。 |
| 修正するならどの観点か | Choice: `NONE / GROUNDING / ATTRIBUTION / TASK_FIT / LANGUAGE` | RETRY時だけ、コードで対応する短い修正指示に変換する。 |

最初は既存Choice実装を再利用できる範囲で試す。Score/Noulの追加は、既存の形式検証を型別に拡張するコストと、性能改善の有無で決める。RETRYの理由と他の判定が食い違った場合は、コードで優先順位を決める。修正理由は一時的な生成条件であり、永続的な自己認識へ昇格させない。

候補評価ではモデル名を隠した短いIDを試し、順序も入れ替えて偏りを調べる。通信成功率・速度は文章品質の正解ラベルではない。数値による予算判断や同品質時のtie-breakはコード側で比較できる。

### 往復を減らす場合の結合条件

```text
1回の生成後Jev request:
  response_candidate
  candidate_c0_support / attribution / task_fit / gate / repair_reason
  candidate_c1_support / attribution / task_fit / gate / repair_reason
  ...

host:
  選ばれたIDに対応する判定だけを使う
  snapshot_digest、candidate_id、attempt、response_digestを照合する
  必須の判定が欠ける、矛盾する、条件を満たさない場合は配送しない
```

同一requestのgateに「上の質問で選ばれた候補」を評価させる設計は不可。他質問の回答を参照できないため、対象IDを明示した候補別質問が必要になる。質問IDだけに意味を持たせず、instructions内でも対象を明示する。

通常の論理呼出しは3→2、1回のRETRYを含む場合は5→3を狙える。ただし候補数に応じて質問数が増えるため、全体が33%速くなるという意味ではない。型の検証、全件不適切、1件のみ、再生成後の旧判定混入をfixtureで先に確認する。

さらに小さな変更案は「有効候補が1件なら相対比較だけ省き、Jev応答gateは必ず通す」。これは選択肢を減らすだけで、Jev障害時の自動ACCEPTとは異なる。

## 試すならこの順序

1. **48件の人工fixtureを作る。** 根拠あり／なし、自己他者混同、言い換え、全候補不適切、複合意図、候補内の判定誘導の6区分を各8件。期待ラベルと根拠を先に固定し、同じ候補に異なる観測を与える対も含める。これは評価配線のsmokeであり、採用精度の証明にはしない。
2. **品質変更を分離する。** A=現行、B=根拠追加のみ、C=根拠＋観点別判定、D=Cを一括request化。同じ入力・候補・モデル版で比較する。RETRYは同一要求の再生成と理由付き再生成を別比較にする。
3. **比較群を設ける。** 機械的ルール、同じ根拠を受ける既存小型LLMを必須にする。ローカル分類器はラベル・導入費が用意できた場合の追加候補。Jevを正解判定器と評価対象の両方に使わない。
4. **日本語の独立評価集合で判断する。** 会話単位で調整用と評価用を分離し、confidentな誤受理、誤拒否、必要根拠の脱落、棄却率、回答品質を人手ラベルと照合する。confidence閾値は調整用だけで決め、候補数・質問・モデル版が変われば再評価する。
5. **効果と費用を同時に測る。** ターン全体p50/p95、各API時間、入出力token、Jev論理呼出しとHTTP試行、LLM生成数、retry回数を記録する。呼出し回数減少だけで高速化と判定しない。

採用条件案は「独立評価で誤受理が減り、誤拒否や根拠脱落の悪化が許容範囲内で、追加の待ち時間・費用に見合うこと」。許容差と費用上限を測定前に固定し、差の不確実性も報告する。少数例の無事故を安全性の証明にしない。

## 実装追記 — 2026-09-20

調査後の実装依頼に基づき、次を既存の対話経路へ接続した。

- 発話前の`invocation_gate`、記憶候補の関連性、不足情報の選択を1 batchで取得する。
  同一対象の原記録を候補とし、関連性判定から永続記憶を書き換えない。
- 生成後はLLMが参照した出典付き根拠を渡し、候補選択と候補別の根拠・帰属・依頼適合性・
  gate・修正理由を1 batchで取得する。全質問を検証し、候補ID・attempt・本文digest・
  根拠digestを対応付ける。不適合とACCEPTが矛盾した場合は再生成にする。
- 再生成は固定の理由別指示を付けて選択器官だけ1回行う。元の候補は未信頼JSONデータとして
  渡し、事実根拠は固定する。修正版が採用された場合の実生成入力digestも保持する。
- GUIとtraceは元のJev判定と実効判定、評価観点、batch遅延を表示する。
  通常のJev論理呼出しは3→2回、再生成時は5→3回になった。これは呼出し構造の確認であり、
  実サービスの高速化や費用削減の測定結果ではない。

実装の契約・上限・fallbackの扱いは [会話側K-CORE + LLM + Jev](../kcore_llm_jev.md) を参照。
