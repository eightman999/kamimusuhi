### 3.1 A+ — Reflection agent audit: system prompt にある人格・社会規則は、検査しやすいものだけ守られやすい

**Primary**

- Subigya K. Nepal et al., *Faithful Where It Can Be Checked: Auditing a Reflection Agent Against Its System Prompt in a Randomized Trial*, arXiv:2609.19635, submitted 2026-09-17  
  https://arxiv.org/abs/2609.19635

career reflection agent の randomized trial から 17,930 turns を監査した研究。reply-length cap のように容易に検査できる規則は守られた一方、`do not flatter` や `challenge gently` のような interactional disposition は大きく崩れた。論文 abstract では、agent 条件の参加者が career commitment / exploration の複数指標で悪化し career doubt が増えたこと、また transcript 内で「決めるよう繰り返し迫る」行動が強い参加者ほど doubt が大きい関連が報告される。ただし、個別行動とアウトカムの関連をそのまま因果効果と解釈してはならない。

1. **実証済み**: 17,930 turns の coding により、容易に機械監査可能な規則と、非迎合・gentle challenge のような曖昧な規則で遵守率が大きく異なることが示された。randomized trial 全体として agent 条件と複数 outcome の差も観測された。
2. **提案・推測段階**: 「検査可能性そのもの」が遵守差の唯一の因果要因だとは未証明。特定 transcript behavior と downstream outcome の相関も、各 behavior の因果効果を直接証明しない。
3. **関連 subsystem**: Persona Core、social cognition、relationship model、Global Workspace、HCI、longitudinal persona evaluation。
4. **借りられる設計・実装アイデア**: persona / social rule を prose のままにせず、可能な範囲で transcript-level measurable contract へ落とす。例: `decision-demand count`、refusal respect、praise/flattery rate、gentle disagreement rate、uncertainty acknowledgment。定期的に behavior audit を行う。
5. **Kamimusuhiとの差分**: Kamimusuhi は Persona Core + durable self state を持つ設計だが、その構造化だけで「実際の対話行動が persona に忠実」とは保証されない。identity continuity と behavioral disposition fidelity は別物である。
6. **次に検証すべきこと**: `BehavioralDispositionAuditBench-v0`。同一 self-state / relationship-state でモデル・prompt rendering・memory load を変え、非迎合、gentle challenge、refusal respect、過剰な意思決定要求などを machine-checkable metric と human rating の両方で測る。長期 repeated sessions でも drift を追う。
7. **重要度**: **A+**

**設計要約**: `persona rule written != persona behavior realized`。

### 3.2 A — Hermes #115437: in-flight work の durable marker は timeout 時ではなく submit 成功時に作る

**Primary implementation record**

- NousResearch/hermes-agent PR #115437, opened 2026-09-18  
  https://github.com/NousResearch/hermes-agent/pull/115437

Hermes group-chat では、remote member の turn が実行中に Desktop が終了・crash・renderer restartすると、turn 自体は remote gateway で継続できる。しかし既存の `stranded` marker は timeout path でしか書かれなかったため、**timeout 前に caller が消えた turn は durable に「回収すべき in-flight work」と記録されなかった**。再起動後、完了 reply が silent prior context になり、さらに同 member を re-drive して live session を割り込む可能性があった。

提案 fix は `prompt.submit` が acknowledge された直後に `{before, thread, turn}` marker を durable room state へ書き、次 boundary / restart から late reply を harvest する。現在 process の poll が所有中の marker は token で判別して二重回収を防ぎ、session が本当に消滅した場合と一時到達不能も区別する。PR は open で、real two-machine run ではなく scripted gateway test である。

1. **実証済み**: origin/main で failing となる regression fixture と、修正後の submit→poll→restart-like harvest sequence が提示されている。既存 plugin test 群 669 tests も通過と報告。
2. **提案・推測段階**: PR は未merge。actual two-machine crash / network partition 実験は未実施。すべての execution surface に同じ意味論が適用済みではない。
3. **関連 subsystem**: distributed execution、K-Edge/K-Core handoff、turn lifecycle、result delivery、Continuity Kernel の liveness/provenance 辺界、multi-agent orchestration。
4. **借りられる設計・実装アイデア**: `dispatch acknowledged` の直後、caller survival に依存しない durable `InFlightObligation` を作る。`execution_owner` と `result_collector` を分離し、collector が死んでも restart 後に exactly-once 相当で harvest できるようにする。`gone` と `temporarily unreachable` を別 terminal/nonterminal state にする。
5. **Kamimusuhiとの差分**: Kamimusuhi は conversation turn だけでなく tool call、background cognition、remote model、robot action、sleep job まで持つため、marker は chat-specific map ではなく typed execution obligation として一般化する必要がある。
6. **次に検証すべきこと**: `InFlightObligationDurabilityBench-v0`。submit ACK の直後、streaming中、tool subcall中、completion直前に caller/node を kill し、remote execution を継続。restart後に result が1回だけ回収され、同一 task が re-drive されず、session gone / network unreachable が区別されることを要求する。
7. **重要度**: **A**

**設計要約**: `dispatch accepted != caller remains alive to collect result`。

### 3.3 A — FINSKILLOPS: self-improving skill は targeted success だけでなく protected regressions と negative-control false activation を通過して昇格する

**Primary**

- Yanzhang Ma et al., *FINSKILLOPS: A Self-Evolving Multi-Agent System for SEC Filing QA*, arXiv:2609.19680, submitted 2026-09-17  
  https://arxiv.org/abs/2609.19680

post-deployment failure から typed diagnosis を作り、scoped skill patch を提案し、targeted validation、protected-case regression checks、negative controls、versioned replacement / retirement を通してから frozen skill registry に昇格する。12-round operational study では **33候補中6 skillのみ promotion**、monitoring non-correct rate は20.0%から12.5%へ低下。enhanced benchmark では evolved skills の correctness が3.70から4.55へ上がったと報告する。

既収載の SkillAA と「局所 update + validation」という方向は重なるが、今回の差分は **negative controls による scope leakage / false activation の明示検査**と、低い promotion rate 自体を正常な運用結果として扱う点である。

1. **実証済み**: 6 benchmarks と12-round study で、scoped skill lifecycle を用いた system の改善を報告。candidate の大部分を昇格させない controlled admission が実際に運用されている。
2. **提案・推測段階**: SEC filing QA 以外の open-world procedure、robot skill、social behavior、Persona mutation に同じ成績で一般化することは未実証。
3. **関連 subsystem**: procedural memory、self-improvement、tool skill registry、Mutation/Activation Gate、evaluation lineage。
4. **借りられる設計・実装アイデア**: candidate skill ごとに `target failures / protected positives / negative activation cases / supersedes / retirement receipt` を持たせる。改善したことだけでなく、「適用すべきでない場面で発火しない」を promotion 条件にする。
5. **Kamimusuhiとの差分**: Kamimusuhiでは procedural skill と self/persona/value mutation を分離しているため、この aggressive な self-evolution をまず procedural lane に限定する。Persona Core への一般化は不可。
6. **次に検証すべきこと**: `SkillScopeNegativeControlBench-v0`。既知 failure を直す skill patch を生成し、近接だが非適用の task、矛盾する user policy、異なる owner/profile、旧 version task を negative controls にする。target gain、protected regression、false activation、retirement behavior を同時評価。
7. **重要度**: **A**

**設計要約**: `fixing the target != being safe outside the target`。

### 3.4 A — Agent resource dynamics: Cognitive Budget は task-sensitive runtime profile でなければならない

**Primary**

- Wonmi Choi et al., *Not All AI Agents Are Equal: Characterizing Resource and Performance Dynamics*, arXiv:2609.19947, submitted 2026-09-17  
  https://arxiv.org/abs/2609.19947

RAG QA、web search、software coding の agent workloads を対象に、remote LLM latency と local tool/container の CPU・disk I/O・memory を計測。task により bottleneck が大きく異なり、**faster LLM response や CPU core 増加が常に agent latency を改善するわけではない**と報告する。task-aware optimization では CPU-sensitive task の latency を約5.4倍改善し、mixed tasks の average latency を約32%削減した。

1. **実証済み**: 代表的3 workloadで、同一agent stackでもresource sensitivityがtask-dependentであること、staticな「CPUを増やす」最適化が一貫して効かないことを測定。CPU-aware admission / allocation の改善を実測。
2. **提案・推測段階**: 3 workloadの結果を multimodal robotics、local-only Persona Core、Apple Silicon、GPU inferenceへそのまま一般化できない。
3. **関連 subsystem**: Cognitive Budget、Cognitive Action Router、K-Edge/K-Core/K-Deep placement、tool orchestration、resource health / digital interoception。
4. **借りられる設計・実装アイデア**: resource profile を node-level capacity だけでなく action/task-level empirical sensitivity として持つ。例: `remote_wait_fraction`, `cpu_sensitivity`, `disk_io_sensitivity`, `memory_peak`, `concurrency_curve`, `TTFT`, `energy`。router は task class と live pressure から admission / placement を変える。
5. **Kamimusuhiとの差分**: 現行 architecture の Cognitive Budget は利用可能資源を明示するが、資源を増やしたときの **marginal performance curve** までは中心概念としていない。ここを測定可能な body capability model にできる。
6. **次に検証すべきこと**: `ResourceSensitivityRoutingBench-v0`。検索、code、memory recall、local LLM、remote LLM、multimodal perception を2/4/6/12 CPU thread、異なる network latency、concurrencyで測定し、static allocation と task-aware routing を比較。p50/p95 latency、energy、cost、successを同時記録する。
7. **重要度**: **A**

**設計要約**: `more compute != lower cognitive latency`。

### 3.5 B+ — Agile-WAM: tactile と vision を同一時間スケールで予測しない multimodal control

**Primary**

- Hanchu Zhou et al., *Agile-WAM: An Agile Tactile World Action Model for Contact-Rich Robot Control*, arXiv:2609.20761  
  https://arxiv.org/abs/2609.20761

vision と tactile を shared latent へ入れ、action chunks と future latent を同時生成する World Action Model。設計上の重要点は、vision は隣接frame間で緩やかに変化しやすい一方、tactile は接触で急変するため、**visual latent は長めの temporal offset、tactile latent は next-frame の短 horizon**を予測する multi-horizon supervision を使うこと。9 simulation + 5 real-world contact-rich tasks で strongest baseline より success rate を改善し、real-world 5実験で overall success の relative gain 29.4%、inference latency 11.9 ms を報告する。

1. **実証済み**: simulation/real robot で multi-horizon tactile WAM の性能と low-latency inference を報告。
2. **提案・推測段階**: multi-horizon choice が Kamimusuhi の汎用 sensory event bus 全体に最適とは未証明。world model latencyとsensor→actuator total loop latencyも同一ではない。
3. **関連 subsystem**: K-Nerve/K-Edge、multimodal perception、robotics、temporal control、artificial nervous system。
4. **借りられる設計・実装アイデア**: modalityごとに固定共通tickへresampleする前提を避け、`modality-specific horizon / freshness / interrupt priority` を持つ。接触・collision signalは短 horizon、visual scene contextは長 horizonという非対称処理を比較する。
5. **Kamimusuhiとの差分**: Kamimusuhiは単一robot policyではなくdistributed sensory bodyを想定するため、latent WAMをidentity-bearing memoryにせず、K-Edgeのephemeral predictive control stateとして扱うべき。
6. **次に検証すべきこと**: `MultiRateTactilePredictionBench-v0`。同一horizon、tactile-short/vision-long、event-trigger tactile の3方式を比較し、contact detection latency、task success、false interrupt、compute/energyを測る。
7. **重要度**: **B+**

**設計要約**: `same scene != same temporal horizon across modalities`。

### 3.6 B — Hermes #115426: retrieval score の数値衝突は semantic relevance を保証しない

**Primary implementation record**

- NousResearch/hermes-agent PR #115426, opened 2026-09-18  
  https://github.com/NousResearch/hermes-agent/pull/115426

`gbrain recall_fast` で、実用 query と junk recall が同じ 0.152 付近のscoreを返し、単一thresholdでは signal と noise を分離できなかったという運用例。提案fixは低score floorを維持しつつ prompt と memory hit の content-word overlap を追加する。

1. **実証済み**: PR内の具体 fixture では relevant / irrelevant hit が同score帯に重なり、score-only filterが両者を分離できない。追加filterで4 regression testsがpassする。
2. **提案・推測段階**: lexical overlap 自体が一般解ではない。paraphrase、cross-lingual recall、entity aliasでは false negative を増やし得る。PRも未merge。
3. **関連 subsystem**: episodic/semantic memory retrieval、Global Workspace admission、background memory activation。
4. **借りられる設計・実装アイデア**: retrieval backend の raw score を universal confidence と扱わず、score calibration + semantic/typed admission + provenance/freshness を分離する。
5. **Kamimusuhiとの差分**: Kamimusuhiは複数 memory domain を持つため、generic lexical overlapより `memory_type / owner / time / source / query intent` を使った admission が必要。
6. **次に検証すべきこと**: `RecallScoreCollisionBench-v0`。同scoreの関連/無関連、paraphrase、zero lexical-overlap synonym、cross-language、stale memory、wrong-person memoryを作り、threshold-only / lexical / reranker / typed gateを比較する。
7. **重要度**: **B**

**設計要約**: `retrieval score != semantic relevance`。
