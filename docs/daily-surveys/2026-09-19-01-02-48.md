### A+ — Hermes Agent #115175: canonical session への書込みは session ID ではなく live owner lease に従う

**Source**

- https://github.com/NousResearch/hermes-agent/pull/115175

Hermes の `peer run` transport は canonical Bot Chat の `session_id` を正しく解決していたが、Desktop がそのchatのlive leaseを保持しているか確認せず、自プロセスで別agentを起動して同じ transcript に追記していた。結果として、Desktop側からはrequest/answerが見えないまま、**同一sessionへ二つのwriterが並行して書く**状態が成立していた。提案fixではlive ownerのmailboxへhandoffし、ownerが返すreceiptをrunの最終状態へ変換する。ただしPR自身が `/chat/stream` と「API turn実行中にDesktopが開く」逆向きraceは未解決と明記している。

1. **実証済み**: open PRのregression fixtureで、live ownerが存在するBot Chatへ `peer run` した際に旧実装がsecond writerを作ること、修正案でownerのreply / failure / queued cancelをreceipt経由で扱えることが示されている。
2. **提案・推測段階**: 全transportに対してsingle-writerが保証されたわけではない。PR記載通り `/chat/stream` とmid-turn lease acquisitionは残る。
3. **関連subsystem**: Continuity Kernel、canonical event log、distributed execution、Global Workspace ingress、external-action/result receipts。
4. **借りられる設計**: `session_id` だけで書込み先を決めず、`continuation_id + live_owner_generation + lease/authority receipt` をwrite admissionへ要求する。非owner transportはmailbox/handoffへ変換する。
5. **Kamimusuhiとの差分**: KamimusuhiはHermesより強くcanonical identity lineageを分離しているため、conversationだけでなく self/relationship/episodic/procedural mutation に同じ規則を広げる必要がある。
6. **次に検証**: `CanonicalSessionSingleWriterBench-v0`。interactive、background、peer、RPC、restart、handoff、late-open、network partitionを交差させ、同一canonical continuationへ同時writerが生じないこと、stale writerがfail-closedになることを検証する。
7. **重要度**: **A+**

**設計要約**: `same canonical id != current write authority`。

### A+ — Hermes Agent #115162: `local` のような相対aliasは owner namespace を失うと別個体へ誤配送される

**Source**

- https://github.com/NousResearch/hermes-agent/pull/115162

複数Desktopが一つのgatewayを共有したとき、各Desktopは自分のmachineを `local` と呼ぶ。同じ文字列でも意味するendpointは異なるのに、gatewayが単一roster / outboxへ統合してowner provenanceを保持していなかったため、後からsyncしたDesktopが前のfleetを消し、`hermes@local` 宛てenvelopeを別Desktopが先にclaimして**送信者自身のMacで実行する**誤配送が起こり得た。修正案はDesktop identityをscoped ownerとしてroster/envelopeへ保持し、曖昧なaliasは推測せずrefuseする。

1. **実証済み**: 2 Desktop / 1 gateway fixtureで roster overwrite、wrong drain、alias collisionが再現され、per-owner rosterとclaim filterで分離される。
2. **提案・推測段階**: `local` が複数ownerに存在する場合の明示的なqualified target grammarは未設計。今回のfixは安全側に拒否するところまで。
3. **関連subsystem**: distributed embodiment、K-Edge/K-Core routing、identity continuity、tool/model endpoint registry、peer messaging。
4. **借りられる設計**: human-friendly aliasをcanonical endpoint identityにしない。`endpoint_id = owner_principal / device_or_runtime_id / local_alias / generation` とし、aggregation後もowner namespaceを失わない。
5. **Kamimusuhiとの差分**: Kamimusuhiは複数deviceを「同じ個体の身体」として束ねるため、ownerは人/installationだけでなく `identity lineage + body-node identity` を含める必要がある。
6. **次に検証**: `RelativeEndpointNamespaceBench-v0`。複数deviceが全て `local`, `gpu`, `camera`, `home` の同名aliasを持つ状態で、aggregate view、offline/reconnect、rename、handoff、stale rosterを含め誤配送0を要求する。
7. **重要度**: **A+**

**設計要約**: `same alias string != same endpoint identity`。

### A — MAGMA-GEN: failureを学習信号にする前に matched counterfactual re-execution で原因帰属を検証する

**Sources**

  https://arxiv.org/abs/2609.20056
- Official project organization  
  https://github.com/MAGMA-rob

長期robot manipulationの失敗は、high-level decisionが悪かったのか、観測が不完全だったのか、decisionは妥当だがphysical executionが失敗したのか曖昧である。MAGMA-GENはprivileged coachが早期のdecision errorと局所修正を仮説化するが、その診断をそのまま教師データにせず、**同じstate・matched conditionsから再実行してdownstream progressが改善した候補だけをsupervisionとして保持**する。

1. **実証済み**: 論文はsimulationとreal-robot executionのinteractive long-horizon manipulationで、distillation / trajectory-repair baselinesに対するtask success / recovery改善を報告している。
2. **提案・推測段階**: counterfactual validationが任意のopen-world failureや社会的・言語的失敗へそのまま一般化することは未実証。
3. **関連subsystem**: K-Edge / robotics、procedural memory、self-improvement、reflection、failure attribution。
4. **借りられる設計**: `observed failure -> blame` を禁止し、`failure hypothesis -> localized intervention -> matched replay/re-execution -> improvement evidence -> update admission` にする。
5. **Kamimusuhiとの差分**: Kamimusuhiではpolicy updateだけでなく、self-modelやnarrativeが「自分はXが苦手」と結論する場合も誤帰属があり得る。canonical historyは保持し、原因仮説はderived stateとして別管理する必要がある。
6. **次に検証**: `CounterfactualFailureAttributionBench-v0`。同一の失敗表面を、plan error / stale perception / actuator fault / tool timeout / external service faultで生成し、re-execution evidenceなしの原因固定をrejectできるか測る。
7. **重要度**: **A**

**設計要約**: `failure observed != failure cause identified`。

### A — Hermes Agent #115158: security flagが存在しても実redirect seamに結線されていなければcredential boundaryは存在しない

**Source**

- https://github.com/NousResearch/hermes-agent/pull/115158

Hermes MCPの `strict_redirect_headers` は、httpx response hookで `response.next_request` を読んでいたが、その値はhook実行後に作られるため、real redirectでは実質early-returnし続けていた。さらにcontent-type preflightは別clientでredirectを追い、strict flagも渡されず、cross-origin 302へ `X-API-Key` が到達するlive reproductionが得られた。修正案はredirect requestを実際に構築するseamへstripperを移し、preflightにも同じpolicyを通す。

1. **実証済み**: httpx/httpx2のlive 302でstrict policyが効いていなかったこと、preflight経由のconfigured header leakage、修正後のsame-origin / cross-origin / multi-hop testsが報告されている。
2. **提案・推測段階**: PRはopenでありupstream mainへ採用済みではない。すべてのHTTP stackやOAuth flowを一般に保証するものではない。
3. **関連subsystem**: tool/MCP orchestration、credential boundary、preflight/readiness probe、external-resource acquisition。
4. **借りられる設計**: security policyは「設定値がある」ことではなく、actual transport seamでenforcedされることをlive adversarial testする。probe/preflightも本実行と同じcredential egress policyへ束ねる。
5. **Kamimusuhiとの差分**: Kamimusuhiでは外部model/API/toolが多数のcognitive extensionになるため、redirectだけでなくdelegate/subprocess/browser/connectorごとにauthority-taintのegress boundaryが必要。
6. **次に検証**: `CredentialRedirectBoundaryBench-v0`。same-origin、cross-origin、multi-hop、preflight、OAuth authorization server、custom header、proxyを含むreal network fixtureでsecret到達集合を測る。

## 7. 実装 / 実験候補

優先順位:

1. **P0 `CanonicalSessionSingleWriterBench-v0`**  
   全ingress transportについてcanonical continuation owner/leaseを検査し、second writer / late owner acquisition / restart raceを再現する。

2. **P0 `RelativeEndpointNamespaceBench-v0`**  
   同名aliasを持つ複数body node / gateway / profileを同時接続し、owner-qualified identityなしのrouteをfail-closedにする。

3. **P0 `CounterfactualFailureAttributionBench-v0`**  
   同一failure surfaceへ異なるcausal mechanismを割り当て、matched re-executionなしのskill/self-model mutationをrejectする。

4. **P0 `DistillationBehavioralContaminationBench-v0`**  
   synthetic consolidation datasetを用いてsemantic inspectionだけでは見えないtrait transferを測る。candidate modelはcanonical activation前にheld-out behavioral batteryを必須化する。

5. **P1 `CredentialRedirectBoundaryBench-v0`**  
   real redirect server fixtureでMCP/preflight/OAuth/custom headerのegress boundaryを試験する。

6. **P1 `HarnessMechanismTransferBench-v0`**  
   SoL-Pi型4機構をKamimusuhi workloadへ移植せず、まず外部比較benchでfactorial ablationする。

7. **P1 `DormantCapabilityReadinessBench-v0`**  
   「今使わないので壊れていても気付かない」body/cognitive-resource failureをactive probeで検出する。

8. **P2 `RelationshipVisibilityBiasBench-v0`**  
   user-model inferenceがexternal visibilityの高いeventだけを過大評価しないか測る。
