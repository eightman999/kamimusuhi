## 3. 要約

今回の主題は、**「開始・許可・成功・記録」のどこか一つが成立したことを、他の境界まで成立した証拠にしない**である。

特に強い境界は以下。

~~~text
turn handoff accepted != sibling effects settled
worker spawned != worker lifecycle durably owned
text persisted as assistant history != text user actually received
environment recommendation != user objective
route allowed != configured/intended fallback
worker status ok != subject verdict pass
verifier ran != verifier covered what mattered
recent latency slack != static compute budget
typed output != order-invariant/calibrated decision
short-term reflection benefit != long-term human skill preservation
~~~

Kamimusuhi では既に thought / speech / execution / delivery、canonical evidence / derived view、models-as-organs / continuity-owner を分けている。今回の新規 evidence は、その分離を **turn batch、worker spawn、streaming utterance、model routing、verification record、Cognitive Budget** まで具体化する。

## A — OpenClaw #157364: turn handoff が sibling tool effect を無言で失わせる

**Source**

- OpenClaw issue #157364
- https://github.com/openclaw/openclaw/issues/157364
- Created: 2026-09-24 15:29 UTC
- issue-level source reproduction / fixは未確定

### (1) 何が実証済みか

同じ assistant message が sessions_yield と別の effectful tool call を同時にdispatchしたとき、yieldが受理されると turn handoff の abort が sibling tool にも伝播し、tool implementationへ入る前のpreflightで死ぬ経路が報告された。

実運用例では、channel post が **333 ms** でpreflight abortされ、同じcommandを単独turnで実行すると **574 ms / exitCode 0** で完了した。run自体は success としてsettleし、失われたside effectを明示するterminal recordがない。

issueは published 2026.9.1 bundleの source pathまで追跡し、yield自身にはhandoff exemptionがあるが siblingには渡っていないことを示している。

### (2) 何が提案・推測段階か

- maintainer fixはまだ normative ではない。
- 全toolをhandoff後も最後まで走らせるのが正解とは限らない。外部副作用では cancellation policy が必要。
- issue提案の bounded grace も、別abortを見落とす弱点がある。

### (3) Kamimusuhi 関連 subsystem

- Cognitive Action Router
- tool execution state machine
- delegation / sessions_yield相当のhandoff
- outbox / effect receipt
- result integration / delivery

### (4) 借りられる設計・実装アイデア

turn lifecycle と tool-attempt lifecycle を別ownerにする。

各 effectful dispatch は少なくとも以下を持つ。

~~~text
intent_id
turn_id
tool_attempt_id
authority_receipt
dispatch_state
effect_state
delivery_state
terminal_reason
~~~

turn handoffは新しい認知turnのownerを移せても、既dispatch intentを無言で成功扱いして消してはいけない。siblingは settle、明示cancel、UNKNOWN/reconcile のいずれかへ必ず閉じる。

### (5) Kamimusuhiとの差分

Kamimusuhi は既に side-effect を REQUESTED / AUTHORIZED / QUEUED / EXECUTING / SUCCEEDED|FAILED|UNKNOWN / RESULT_DELIVERED と分ける方針を持つ。今回のissueは、**そのstate machineをturn単位ではなく sibling tool attempt単位に持つ必要がある**ことを具体化する。

### (6) 次に検証すべきこと

**TurnHandoffSiblingEffectSettlementBench-v0**

- yield + file write / HTTP / channel post / durable memory proposalを同一batchでdispatch。
- yield先行、effect先行、同時、crash、timeoutをsystematicに差し替える。
- 全intentがterminal stateへ閉じることを検査。
- successだがeffect未実行、effect実行済みなのにretry、duplicate effectを別metricにする。

## A — Hermes #121556: spawn と durable worker registration の隙間で二重実行

**Source**

- NousResearch/hermes-agent issue #121556
- https://github.com/NousResearch/hermes-agent/issues/121556
- Created: 2026-09-24 13:08 UTC
- CI failure + deterministic local reproduction

### (1) 何が実証済みか

dispatcherが worker process をspawnした直後、worker_pid を task runへ記録する前にSIGKILLされると、workerは実際には生きているが schedulerから見えない。

報告ではCIでも二重実行を観測し、local deterministic reproは **4/4 red**。event sequenceも claimed → heartbeat(worker_pid null) → reclaimed → claimed → spawned → completed と示されている。

### (2) 何が提案・推測段階か

- worker self-registrationが全platform / process modelで十分かは要検証。
- exactly-once execution自体は一般には難しく、external effectにはidempotency/fencingも必要。
- PIDはprocess incarnation identityとして完全ではない。

### (3) Kamimusuhi 関連 subsystem

- K-Deep worker dispatch
- distributed organ lifecycle
- Continuity Kernel周辺のlease / fencing
- background jobs
- effect execution / idempotency
- recovery / stale-claim reconciliation

### (4) 借りられる設計・実装アイデア

**side effectより先に durable attempt identity を確立する**。

workerをspawnする前後で最低限、

~~~text
task_id
attempt_id
lease_epoch
worker_incarnation
owner
fencing_token
registered_at
~~~

をdurable storeへ置き、worker自身も最初のexternal/model callより前に self-register / compare-and-set する。

### (5) Kamimusuhiとの差分

KamimusuhiではPIDをidentityにせず、process incarnation / node identity / authority leaseを分けられる。さらに外部effectには attempt_id / idempotency key を繋げられるため、単なるscheduler bugではなく **distributed cognitive organのownership invariant** にできる。

- PID / UUID / fencing-token方式を比較。

## A — CAVEAT: 利害を持つ環境は delegated agent の user objective を大幅に曲げる

### (1) 何が実証済みか

- https://github.com/nokia-applied-research/AnyJev
- Apache-2.0, v0.0.2（survey時点のrepo記載）

### (1) 何が実証済みか

AnyJevは任意のnext-token-logprob対応LLMから choice / noul(Yes/No) / score のtyped decisionを作るreadout layerを公開している。

L0は cyclic-shift marginalization と label-prior correction、L1は100–500 labelsを使うtemperature scalingを重ねる。

repoの再現可能benchmarkでは Qwen3-8B / BANKING77 20-way / n=300で、

- option reversal flip: raw **0.230** → L0 **0.073**
- accuracy: **0.747** → **0.803**
- ECE: raw **0.240** → L1 **0.095**

と報告する。

repo自身がlimitationsも明記している。L0が逆効果になるtask、batch priorのclass-imbalance dependence、modelが問題自体を解けない場合はcalibrationで救えないこと、L1がdistribution shiftへ耐えないこと、現状benchmarkが主にQwen familyであることなど。

### (2) 何が提案・推測段階か

- Jev/Kev専用modelと同じlatency classになるとは限らない。
- K-option choiceのL0はK回prefillを必要とし、低latency organではcompute costが増える。
- option-order invarianceがsemantic label-renaming invarianceまで保証するわけではない。
- finance/medical等への一般的安全利用はdiscovery記事の推奨であり、このrepo benchmarkからは証明されない。

### (3) Kamimusuhi 関連 subsystem

- K-Nerve / typed microdecision
- routing / classifier
- uncertainty / abstention
- local model reuse
- provider-neutral System-One interface

### (4) 借りられる設計・実装アイデア

decision receiptへ raw probabilityだけでなく **calibration level / readout method / option-order audit** を持たせる。

~~~text
decision
distribution

calibration_artifact_id
option_set_hash
permutation_count

~~~

### (5) Kamimusuhiとの差分

Kamimusuhiはdecision organ自体をidentity ownerにしない。AnyJevはgeneral LLMをre-useできる点が強いが、dedicated Jev/Kev/Diffusion系よりlatency/energyが大きい可能性がある。従って「精度が上がる」だけでなく K-Nerve に置く価値を end-to-end budgetで比較する必要がある。

### (6) 次に検証すべきこと

**TypedDecisionReadoutBiasMitigationBench-v0**

- Jev / Kev / AnyJev raw / L0 / L1を同じ日本語decision setで比較。
- option reorder、label semantic rename、OOD、class imbalance、adversarial wordingを入れる。
- accuracy / ECE / abstention quality / TTFT / joule proxy / costを測る。
- L1 calibration-set drift後のfailureを別metricにする。

## C — Scenario-Driven Neuroevolution: branch coverageより「望むbehavior scenario」をevolution targetにする

**Source**

- van Cuyck et al., *Scenario-Driven Neuroevolution: Using Models to Guide Test Generation for Games*
- arXiv:2609.28130
- https://arxiv.org/abs/2609.28130
- Accepted at ICTSS 2026

### (1) 何が実証済みか

従来Neatestがuncovered statement / branchごとにneural test agentを進化させるためscaleしにくく、またbranch coverageが意図したgameplayと一致しない問題に対して、abstract game modelからdesired scenarioを与え、そのbehaviorを再現するagentへneuroevolutionを誘導する。

13 Scratch gamesで、scenario behaviorを再現しつつ traditional code-guided Neatest比で branch coverageを **7%** 上げたと報告する。

### (2) 何が提案・推測段階か

- open-ended evolutionそのものの研究ではなくsoftware testing寄り。
- Kamimusuhiのself-improvementへ直接一般化はできない。
- scenario specificationが人間由来であり、goal generation自体のopen-endednessは扱わない。

### (3) Kamimusuhi 関連 subsystem

- self-improvement sandbox
- evolutionary test generation
- Mutation Gate evaluation
- behavior-driven regression generation

### (4) 借りられる設計・実装アイデア

coverage最大化だけでなく、**semantic scenario / invariant / relationship behavior** をtest-generation fitnessへ入れる。たとえば「再起動後も同じrelationship ownerを参照する」「interrupt後に未配信発話を共有記憶へ入れない」など。

### (5) Kamimusuhiとの差分

Kamimusuhiのevolution targetは code branchではなく continuity / authority / social behavior / resource policy等のmulti-objective。scenarioは mutation fitnessの一部に限定する。

### (6) 次に検証すべきこと

**ScenarioGuidedContinuityTestEvolutionBench-v0**

- continuity invariantを抽象scenarioへする。
- coverage-only fuzzing / property-based test / scenario-guided evolutionを比較。
- discovered regression countとfalse-positive costを測る。

### (7) 重要度

# 6. 既存 docs への追記候補

## architecture.md 候補

### 6.1 Tool attempt lifecycleをturn lifecycleから分離

同一assistant turn内でhandoff/cancelが起きても、既dispatch tool intentは独立したattempt ownerを持ち、settle / explicit cancel / UNKNOWNへ閉じる。

**根拠:** OpenClaw #157364。

### 6.2 Distributed workerはside effect前にdurable self-registration

spawn済みprocessをschedulerが見失うwindowを許さず、attempt_id / fencing token / incarnationをexternal workより先にdurable化する。

**根拠:** Hermes #121556。

### 6.3 Communicated utteranceをgenerated/persisted textと分離

streaming outputでは canonical common-ground updateを surface delivery coverageに基づける。

**根拠:** Hermes #121594。

### 6.4 Route policyとcatalog enumerationを分離

catalog orderはpolicyでない。override invalidation後は primary/fallback policyを再評価し、selection reasonをreceipt化する。

**根拠:** OpenClaw #157377。

## spec.md 候補

すぐにnormative invariantへ昇格させる前にbenchを通すべきだが、次の候補は強い。

- **Effect Closure Invariant:** accepted turn handoffは既dispatch effect attemptを暗黙success/cancelへしない。
- **Worker Registration Invariant:** effectful workerはdurable attempt ownership/fencing前にexternal effectへ入らない。
- **Communicated-History Invariant:** relationship/common-groundへ昇格するassistant utteranceはuser-visible/delivered coverageを越えない。
- **Routing Intent Invariant:** policy-invalidated overrideのreplacementはcatalog enumeration orderではなくexplicit routing policyから決まる。
- **Verification Evidence Invariant:** validator execution successとsubject verdict/coverageは別fieldである。

## docs/research-foundations.md 候補

CAVEATを「delegated agentにおけるuser objective fidelity」の新しいempirical evidenceとして候補化。特に external environment が cooperativeであるという暗黙仮定を置かない点が重要。

## 11. 今回の短い結論

今回もっともKamimusuhiに効くのは、runtimeやagentの「成功」という一語をさらに分解することである。

> **handoffが成功してもeffectは消え得る。workerがspawnしてもowner登録は済んでいない。DBに残った発話でもuserへ届いたとは限らない。allowed modelでも意図したfallbackとは限らない。validatorが正常でも対象が正しい・十分に見たとは限らない。**

したがって、次の実装優先順位は **effect closure → worker registration/fencing → communicated-utterance coverage → routing-policy receipt → verification coverage** の順で試す価値が高い。CAVEATはその上位層として、外部環境やplatform自身がKamimusuhiのuser-objectiveを曲げる前提を正式にbenchへ入れる根拠になる。
