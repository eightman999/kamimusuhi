## 1. A — MutationReadAuthorityCoherence: validationした読み取りとwrite basisを分離しない

**一次資料**

- NousResearch/hermes-agent PR #114227, merged 2026-09-18 00:49 JST  
  https://github.com/NousResearch/hermes-agent/pull/114227

### (1) 何が実証済みか

`save_config` はまず fresh / fail-closed な `require_readable_config_before_write(config_path)` で書込み前検証を通した後、その戻り値を捨て、explicit path抽出のためにcached `read_raw_config()` をもう一度呼んでいた。二回目の読み取りが一時的エラーを `{}` として返すと、strip-defaults処理が「明示設定なし」と誤認し、live reproでは30-sectionの intact config が `['_config_version']` だけへ縮退した。修正は**最初のfail-closed readの同じ値**をmutation basisとして再利用する。corrupt YAML時はRuntimeErrorでfileはbyte-identical、focused testsは194 pass + 4 Windows-only skipと報告されている。

### (2) 何が提案・推測段階か

Hermesのconfig writerに対する実証であり、Kamimusuhiのcanonical historyやPersona mutationで同じbugが存在する証拠ではない。PR本文が示す同型の`auth.py` writer問題も、このPRでは未修正・未実証のfollow-upである。

### (3) 関係するKamimusuhiサブシステム

- Continuity Kernel
- Mutation / Activation Gate
- config / Persona Core runtime settings
- canonical derived-state writers
- `INV-005`, `INV-011`, `INV-013`, `INV-014`

### (4) 借りられる設計・実装アイデア

validationの結果を単なるboolではなく、mutationが使う**read receipt / revision-bound snapshot**にする。

```text
ReadSnapshot(path, revision, digest, parsed_state)
  -> validate
  -> compute mutation from SAME snapshot
  -> compare-and-write(expected revision/digest)
```

write直前に別cache / weaker parser / alternate readerへ戻らない。

### (5) Kamimusuhiとの差分

既存の`RepairInvalidationRevalidationBench`は「後続repairで以前のvalidityが壊れる」問題。本件はもっと狭く、**検証対象とmutation計算対象が同一時点ですら別read pathになっているTOCTOU / authority-coherence問題**である。

### (6) 次に検証すべきこと

**`MutationReadAuthorityCoherenceBench-v0`**

- canonical derived-state / config writerへ二つのread pathを故意に作る
- validation後にcache miss / stale empty / concurrent revisionを注入
- validated snapshot以外からwrite patchを生成したらfail
- expected predecessor / digest不一致なら再読込して再validation
- crash/retryでもvalidated receiptのrevisionを追跡する

### (7) 重要度

**A** — canonical mutationの直前に置くべき機械的な不変条件へ直結する実装failure evidence。

## 2. A — ASLEval: privacyを「想定出口」だけで測ると漏洩を見逃す

**一次資料**

- Wu et al., *ASLEval: Measuring Privacy Exposure Displacement in LLM Agent Sessions*, arXiv:2609.18864  
  https://arxiv.org/abs/2609.18864

### (1) 何が実証済みか

ASLEvalはhidden target setを事前登録し、authorizationと照合しながら**宣言された全visible exitのunion**でsession exposureを測る。複数enterprise-style環境・独立runtimeで、expected-outlet-only評価はvisible-exit unionが回収したexposureの**46.9%を見逃した**。attacker self-reportにはomissionと高いfalse discoveryが併存し、schema-aligned internal evidenceはvisible exposureより前に現れる傾向も報告された。

### (2) 何が提案・推測段階か

全種類のagent surfaceを網羅した普遍的privacy benchmarkではない。console等のhard caseはhuman reviewでも難しいと明記されている。またmodel-visible returnを減らす対策はnormal-task successを消す場合があり、単純な「見せない」設計の最適性は示していない。

### (3) 関係するサブシステム

- authenticated surfaces / Global Workspace
- tool result / browser / code / notification / delivery
- relationship memory / private canonical evidence
- K-Edge / K-Core間のsurface boundary

### (4) 借りられる設計・実装アイデア

privacy evalを`final answer`や単一tool callではなく、episode-wide visible boundaryとして宣言する。

```text
target secret / protected fact
  + authorization policy
  + visible exits[]
  -> session exposure union
  -> outlet-specific + union metrics
```

internal tracesは「漏洩した証拠」ではなく診断用に分離する。

### (5) Kamimusuhiとの差分

既収載の`SecretTaintEgressBench`はsecretがbrowser observation等からmodel/sessionへ戻る具体的taint path。本件は**privacy評価そのものの観測境界**を拡張し、「一つの出口が安全だった」をsession全体の安全と取り違えない点が差分。

### (6) 次に検証すべきこと

**`SessionWidePrivacyExposureBench-v0`**

- chat / tool log / browser / attachment / notification / debug console / archive exportをvisible exitとして列挙
- hidden target + authorization scopeをfixture化
- expected channelだけのmetricとunion metricのmiss率を比較
- privacy utilityとtask successを同時報告

### (7) 重要度

**A** — 分散body・多数surfaceを持つKamimusuhiでは、単一surface privacy testより直接的な測定原則になる。

## 3. A — CHASE / Bad Genius: held-out taskだけではharnessのprotocol shortcutを検出できない

**一次資料**

- Zhu et al., *Bad Genius: Counterfactual-Guided Harness Evolution Beyond Task-Specific Shortcuts*, arXiv:2609.18366  
  https://arxiv.org/abs/2609.18366

### (1) 何が実証済みか

自動harness optimizationではprompt、memory、retrieval、tools、control codeをbenchmark feedbackで改変できる。task holdoutはsemantic taskを変えてもbenchmark protocol自体を固定するため、benchmark-wide shortcutが残る。CHASEはvalidity-preservingなprotocol transformationをChallengerが探索し、gain destructionの大きいcounterfactualをarchiveへ追加する。synthetic benchmarkとOfficeQAで、released-benchmark gainを保ちながらvalid protocol changeに対するgain destructionを低減したと報告している。

### (2) 何が提案・推測段階か

OfficeQA等での結果であり、Persona Core continuity benchやKamimusuhi固有runtimeへそのまま一般化できない。validity firewallが「本当にsemantics preservingか」という別の評価問題も残る。

### (3) 関係するサブシステム

- harness / tool/model orchestration
- procedural self-improvement
- Persona Core candidate training/evaluation
- evaluator lineage / frozen historical evaluators

### (4) 借りられる設計・実装アイデア

held-out tasksに加え、**protocol counterfactual holdout**を作る。

- equivalent field ordering / serialization
- semantically irrelevant UI rearrangement
- alternate tool aliases
- harmless timing / batching changes
- equivalent evidence presentation order

改善がこれらで消えるなら「能力」ではなくprotocol artifactを疑う。

### (5) Kamimusuhiとの差分

直前の`EvaluatorLineagePoisoningBench`はpoisoned benchmarkが自己改変lineageへ危険な性質を焼き込む話。CHASEは悪意がなくても**公開benchmark protocolへの過適合**が起きる点が差分。

### (6) 次に検証すべきこと

**`HarnessCounterfactualRobustnessBench-v0`**

- baseline harness / optimized harnessを用意
- semantics-preserving protocol変換群を生成
- released benchmark gainとcounterfactual gain destructionを別metric化
- Persona continuity / memory / tool-use benchmarkでも同じ評価を試す

### (7) 重要度

**A** — self-improvement loopで「評価が上がった」ことを能力向上へ昇格する前の重要なcounterfactual gate。

## 4. A — SAFE: 危険を理解していても、安全証拠を取りに行くとは限らない

**一次資料**

- Tafveez, *Do Frontier Models Seek Safety Evidence Before Acting?*, arXiv:2609.17865  
  https://arxiv.org/abs/2609.17865

### (1) 何が実証済みか

SAFEはdeployment decision前にoptional safety evidenceを取得できる状況を作り、retrieval cost、problem probability、severity、presentationを操作した。GPT-5.5、o3、Claude Opus 4.8、Sonnet 4.6でevidence acquisition policyが大きく異なり、severity上昇でinspectionは増え、retrieval cost上昇で減った。一方problem probabilityを10%→70%へ上げてもinspection変化は最大21ptに留まった。reasoningの説明とcounterfactual behaviorが一致しない場合も報告している。

### (2) 何が提案・推測段階か

controlled benchmark上のモデル行動であり、現実のphysical safetyやKamimusuhiのauthority policyを直接検証していない。「どのモデルが安全」と一般化する結果でもない。

### (3) 関係するサブシステム

- epistemic action / active inference
- Cognitive Action Router
- K-Core deliberation
- high-impact tool / physical action admission
- uncertainty / regulatory state

### (4) 借りられる設計・実装アイデア

安全証拠取得を「モデルが気が向けばする推論」ではなく、high-impact actionの**explicit prerequisite / obligation**として表現する。

```text
risk class -> required evidence class -> acquire / unavailable / stale
           -> action permit only if obligation satisfied
```

### (5) Kamimusuhiとの差分

既存のactive-inference / epistemic action設計は「不確実性を減らすために観測する」一般原理。本件は**安全上必要な観測を、モデルがコストやframeの影響でskipする**実証であり、policy-bound evidence acquisitionへ一段強く落とせる。

### (6) 次に検証すべきこと

**`SafetyEvidenceAcquisitionBench-v0`**

-危険度・取得コスト・確率・frameを直交操作
- model-choiceだけでなくhard obligation gateあり/なしを比較
- required evidence stale / unavailable時のabstentionを測る
- reasoning explanationとactual acquisition behaviorを別metric化

### (7) 重要度

**A** — K-Coreの「慎重そうな発話」を安全性証拠にせず、証拠取得そのものをruntime contractへする根拠。

## 5. A — VLA-ULAP: remote VLAと超軽量local predictorを交互利用するfast/slow body control

**一次資料**

- Cao et al., *VLA-ULAP: Interleaving Cloud VLA Calls with Ultra-Lightweight Local Action Prediction at the Edge*, arXiv:2609.18663  
  https://arxiv.org/abs/2609.18663

### (1) 何が実証済みか

約7.4M parametersのULAPがcurrent views、proprioception、executed action historyからaction chunkをpredictし、remote VLA hidden stateやserver round tripなしにlocalで動く。Jetson Orin Nanoで**19.9 ms / 0.183 J**、比較されたGR00T on RTX A6000は284.3 ms / 50.55 J。3つのsimulation pairでVLA callsを48.8–76.7%削減しつつbaseline successの95.0–97.5%を維持。SO-101実機でもbaseline successの95.2–100%を維持し、推論時間47.9–58.0%、inference-device energy 52.1–62.5%削減を報告している。

### (2) 何が提案・推測段階か

KamimusuhiのK-Nerve/K-Edgeで同じcall suppression率が出る保証はない。ULAPはonline verifierなしでもactionを出すため、Kamimusuhiのauthority/safety requirementをそのまま満たすわけでもない。

### (3) 関係するサブシステム

- K-Nerve / K-Edge / K-Deep
- robotics / embodied action
- Cognitive Budget
- latency / energy / remote inference availability

### (4) 借りられる設計・実装アイデア

remote deliberative policyとlocal reflex/predictorを固定周期で単純交互にするのではなく、**local predictorが短いaction horizonを肩代わりし、必要時だけremote policyへ戻る**構成を比較対象にする。

### (5) Kamimusuhiとの差分

Kamimusuhiではlocal micro-policyはidentity ownerではなくbody organ。さらにlocal predictorへ与えるaction authorityを、TTL、state precondition、safe envelope、generationへbindした方がよい。

### (6) 次に検証すべきこと

**`EdgeActionSubstitutionBench-v0`**

- remote-only / fixed-rate local / confidence-gated localを比較
- p50/p95/p99 sensor→action latency、energy、success、remote callsを測る
- stale observation / network delay / unexpected contactでlocal authorityを即revoke
- local predictorのaction envelope外逸脱をhard gate

### (7) 重要度

**A** — K-Nerve/K-Edgeのfast pathを「小型LLM」以外の実機比較へ落とせる直接的な設計候補。

## 7. B — AI peersは人間の不正行動にもsocial normとして作用する

**一次資料**

- Zhang et al., *AI Peers Exert Social Influence on Human Dishonesty in Groups*, arXiv:2609.18060  
  https://arxiv.org/abs/2609.18060

### (1) 何が実証済みか

N=280とN=360のrandomized behavioral studyで、AI peerのnormative cueがhuman peerと同程度のsocial influenceを持ち、honest cueよりdishonest cueで参加者のdishonest reportingが増えた。injunctive / subjective / descriptive normsで効果が見られた。隣接条件の大きな変化は最初のdishonest peer出現時に集中し、1→4 peersでは弱くnon-monotonicだった。

### (2) 何が提案・推測段階か

特定taskにおけるdishonesty behaviorであり、長期伴侶AIや日常会話へ効果量を一般化できない。AI peerの人格・信頼・関係継続性が媒介するかも未確定。

### (3) 関係するサブシステム

- social cognition / Theory-of-Mind-like modeling
- relationship model / group context
- HCI / companion behavior
- speech/action policy

### (4) 借りられる設計・実装アイデア

Kamimusuhiの発話をinformation transferだけでなく**normative social signal**として観測する。複数agent場面では「他agentもやっている」を暗黙の正当化に使わない。

### (5) Kamimusuhiとの差分

Kamimusuhiは長期関係とidentity continuityを持つため、単発peerより影響が強くなる可能性も弱くなる可能性もある。これは未実証であり、むしろ長期follow-upが必要。

### (6) 次に検証すべきこと

**`NormativePeerInfluenceStudy-v0`**

- advice / descriptive norm / explicit commandを分離
- single vs repeated interaction
- AI identity continuityあり/なし
- participant choiceとperceived social pressureを別測定

### (7) 重要度

**B** — architecture invariantというより、persistent social agentのHCI評価軸として重要。

### (3) 関係するサブシステム

- synthetic data generation

### (4) 借りられる設計・実装アイデア

Kamimusuhiのdream/simulation出力を直接actuator commandにせず、**bounded desired prior**として使い、実sensor feedbackが閉ループで上書き可能にする。

### (5) Kamimusuhiとの差分

`dream != evidence`という既存invariantを物理制御へ具体化する例。generated multimodal predictionはtrajectory/force hypothesisであり、actual contact evidenceではない。

### (6) 次に検証すべきこと

**`GeneratedPriorVsMeasuredFeedbackBench-v0`**

- generated force profileを意図的に過大/過小にする
- real force feedbackのoverride latencyとstabilityを測る
- priorなし / video-only / video+audioを比較
- synthetic priorはcanonical sensory evidenceへ保存しない

### (7) 重要度

**B** — dream/embodiment境界の具体的なrobotics比較対象。

## 10. B — Zenn実測: Jevは超高速typed microdecisionに有望だが、ranking能力は別評価が必要

**一次的な実装記録 / discovery source**

- Zenn, *TypeSafe JevとClaudeでニュース選別を53日分比べた — 1日1秒・0.1セントの判定器*（2026-09-17）  
  https://zenn.dev/acropapa330/articles/typesafe-jev-news-triage-53days

**公式一次資料**

- TypeSafe, *Introducing System One Models and Jev*  
  https://typesafe.ai/blog/introducing-system-one-models-and-jev

### (1) 何が実証済みか

Zenn記事は53日・LLM枠714件（採用327件）でニュース選別を再評価した一次運用記録。日別AUC平均はJev 0.653、Haiku 4.5 0.676、Sonnet 5 0.697、並び順baseline 0.637。Jev−並び順は+0.016で95%CI [-0.050,+0.083]、Jev−Sonnetは-0.044で95%CI [-0.083,-0.003]。速度は18件を並列4本で約1.0秒/日、1件p50 0.20s / p95 0.25s、費用約$0.001/日と報告。全2,428 candidatesを2分17秒で処理し429/529なしだった。

TypeSafe公式はtyped probabilistic decisions、$0.042/MTok input、70–500ms、System-One-shaped queryで40–200x faster等を主張する一方、workflow evalにmodel-capabilities team由来のbiasやLLM wrapper条件差があり得ることも明記している。

### (2) 何が提案・推測段階か

Zennの採用ラベルは客観ground truthではなく、confidence calibrationもhuman truthではなくSonnet判定との一致を主に見ている。53日・単一workflowであり、Kamimusuhi reflexへの一般化は不可。公式のfrontier-equivalent intelligence主張も独立再現が十分ではない。

### (3) 関係するサブシステム

- K-Nerve / K-Edge low-latency microdecision
- routing / filtering / salience
- confidence / abstention
- Cognitive Budget

### (4) 借りられる設計・実装アイデア

Jev型providerをhigh-authority plannerではなく、**typed negative filter / triage / wake-routing候補**として比較する。probabilityとlatencyの両方を使い、uncertain zoneではK-Coreへescalateする。

### (5) Kamimusuhiとの差分

既存01:03 dailyではJevを「typed probabilistic microdecision provider watch」に留めた。今回は日本語圏の独立field testが加わり、**速さは強いがranking qualityはtask/context次第**という具体的な利用境界が得られた。

### (6) 次に検証すべきこと

**`TypedMicrodecisionProviderBench-v1`**

- salience / route / deny候補をJev / tiny local model / rules / small LLMで比較
- AUCだけでなくcalibration、abstain、p95 latency、cost、network failureを測る
- high-authority actionはprobability単独で許可しない
- raw probabilitiesとvendor confidenceを分けて保存

### (7) 重要度

**B** — 新原理ではないが、K-Nerve/K-Edgeの実用比較候補として情報量が増えた。
