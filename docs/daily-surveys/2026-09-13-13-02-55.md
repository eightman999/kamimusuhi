## 3. 要約

今回の中心テーマは **「知っている capability / fact が正しい」ことと、「今この turn で fresh である」ことを分ける**ことである。

新規差分は次のようにまとめられる。

```text
cached capability inventory != authoritative next-turn capability state
retrieval correctness at t_retrieval != world correctness at t_use
local component validity != still-valid delegated task claim
publicly reachable resource != consented purpose-scoped machine access
low-latency action start != permission to expose every skill in every context
```

特に Letta Code #4398 と ChurnBench は独立な source から同じ問題を補強する。

- #4398: MCP attachment が変化したのに5分 cacheのため次turnが古いtool topologyを見る実装障害。
- ChurnBench: stale answer を通常のreasoning errorと分離して計測し、refresh schedulingを切ると長いwindowでfreshness errorが大幅増加。

Kamimusuhi では `resource_availability` を単なる bool とせず、少なくとも **source-of-truth / observed-at / freshness policy / last-known fallback / authority** を分離して扱う価値が高い。

## 5.1 永続記憶 / retrieval freshness — ChurnBench

**Source:** Vivek Kumar Singh, Preeti Priyam, *ChurnBench: A Drift-Aware Benchmark Demonstrating That Refresh Scheduling, Not Cache Age, Governs Staleness in Agentic AI*, arXiv:2609.11515  
**Primary:** https://arxiv.org/abs/2609.11515  
**Code / artifact:** https://github.com/vsingh45/churnbench  
**Importance:** **A**

### (1) 何が実証済みか

ChurnBench は SQL warehouse、NoSQL operational store、rate-limited REST API、document corpus からなる4-source data fabricを**snapshotではなくtimeline**として生成し、全mutationをappend-only ground-truth ledgerへ記録する。

これにより、answerが retrieval 時点では正しかったが evaluation 時点では誤っているケースを **freshness error** として通常のreasoning errorから分離できる。

公開artifactの headline matched-pair では、thinking disabled・permanent failure 0 の条件で:

| 条件 | D+1 | D+28 |
|---|---:|---:|
| freshness tiering ON | 7 | 4 |
| freshness tiering OFF | 7 | **45** |

と報告されている。paper abstract では cache age 1/14/28 days の単純比較よりも、TTLを伴うscheduled refreshを有効化しているかがstalenessを左右したと整理している。

### (2) 何が提案・推測段階か

enterprise SAM domain、synthetic fabric、特定 refresh policy での結果なので、Kamimusuhi の autobiographical memory / relationship state / physical sensor state へ同じ数値関係を一般化はできない。

また「refreshすればよい」だけではない。取得cost、rate limit、offline organ、source trust、revocation、historical truth保持を同時に解く必要がある。

### (3) Kamimusuhi のどのサブシステムに関係するか

- Memory Store / retrieval layer
- External Resource Router
- canonical evidence / derived views
- Relationship state freshness
- runtime self-model / resource availability
- Cognitive Budget
- background refresh / sleep consolidation

### (4) 借りられる設計・実装アイデア

各 derived fact / capability projection に少なくとも:

```text
source_id
observed_at
effective_at
freshness_class / TTL
refresh_policy
last_refresh_result
source_churn_estimate
historical_evidence_ref
```

を持たせる。

評価でも:

```text
reasoning error
retrieval miss
freshness error
source disagreement
unknown due to unavailable refresh
```

を分離する。

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は canonical evidence と derived view、resource health / availability を分ける方向だが、**freshness error を独立した評価失敗として定義し、entity churn × TTL × refresh schedule でbenchする**ところまでは明示されていない。

### (6) 次に検証すべきこと

**`TemporalFreshnessBench`**

- volatile fact 50件、relationship fact 50件、tool/capability fact 50件を用意
- sourceのchange rateを low / medium / high に変える
- fixed TTL / churn-aware TTL / turn-boundary refresh / event-push を比較
- retrieval時点とaction時点でground truthを別判定
- 指標: freshness error、API/tool cost、latency、unnecessary refresh、stale-authority use

### (7) 重要度

**A** — Memoryだけでなく capability / relationship / world state の「今」を測る共通評価軸になる。

## 5.2 tool/model orchestration — Letta Code #4398: MCP attachment freshness

**Source / primary implementation record:** Letta Code PR #4398, `fix(reminders): refresh MCP attachments before each turn [LET-12474]`  
https://github.com/letta-ai/letta-code/pull/4398  
Merged: **2026-09-13 12:41:17 JST**  
**Importance:** **A**

### (1) 何が実証済みか

修正前は MCP attachment discovery が5分間隔でgateされており、外部からserverをattachして5分以内に次messageを送ると、agentは古いMCP listを見ることがあった。

PRでは attachment list を**各user turn前にrefresh**する一方、tool countは5分cacheを残す。新規attachmentは直ちにcountし、detach済みentryは除去。unchanged listでは重複reminderを送らない。discovery失敗時には直前に送ったlistを保持して次turnでretryする。

PR記載のlive testでは、同一persistent bidirectional sessionで最初の回答が `None`、外部からDeepWikiをattach後、process restart / cache resetなしで同じpromptへの次replyが2.5秒後に `DeepWiki` となった。

### (2) 何が提案・推測段階か

これはLettaのMCP reminder実装の修正であり、全agent runtimeで「毎turn full discovery」が最適という証明ではない。大規模tool fabricではevent push、lease、versioned inventory、incremental reconciliationの方がよい可能性がある。

また discovery failure時にlast-known listを保持する設計はlivenessには有利だが、そのlistを**fresh authority**として扱ってよいわけではない。

### (3) Kamimusuhi 関連

- Tool / Model Router
- Cognitive Resource Registry
- runtime self-model
- K-Edge / K-Core organ inventory
- MCP / external service attachment
- Cognitive Budget
- capability authorization

### (4) 借りられる設計・実装アイデア

`CapabilityInventory` を次の2層にする。

```text
ObservedCapabilityInventory
  - source version
  - observed_at
  - availability / health
  - discovery status

EffectiveCapabilityProjection
  - principal / context / phaseでfilter
  - permission checked
  - freshness requirement satisfied
  - modelへ提示する最小menu
```

discovery failure時は `empty` に潰さず:

```text
LAST_KNOWN_STALE
REFRESH_FAILED
FRESH
REVOKED
```

を区別する。

### (5) Kamimusuhiとの差分

Kamimusuhiは既にtool availability / resource healthをCognitive Budgetやself-stateに含めるが、**いつprojectionをreconcileするか**というlifecycle boundaryが十分具体化されていない。#4398は「turn boundary」を最低限のrefresh pointとして使った一次実装例。

### (6) 次に検証すべきこと

**`DynamicCapabilityFreshnessBench`**

同一sessionの途中で:

1. tool attach
2. tool detach
3. permission revoke
4. network partition
5. discovery API failure
6. tool schema version change

を注入し、次turn / background task / in-flight continuationの各surfaceで:

- stale tool hallucination
- revoked tool selection
- unnecessary rediscovery latency
- last-known fallback誤用
- reappearance recovery time

を測る。

### (7) 重要度

**A** — 直前までの capability-bound routing に **dynamic topology freshness** という独立軸を追加する。

## 5.3 HCI / delegated execution / continuous assurance — Agent-Integrated Software

**Source:** Shengcheng Yu, Chunrong Fang, Zhenyu Chen, *Agent-Integrated Software: Interaction Contracts and Continuous Assurance*, arXiv:2609.11381  
**Primary:** https://arxiv.org/abs/2609.11381  
**Importance:** **A**

### (1) 何が実証済みか

これは主に **software pattern / formalization / research agenda** であり、広範なproduction benchmarkを示す実証論文ではない。

論文は、通常software core + direct user interaction + built-in agentを `Agent-Integrated Software (AIS)` として整理し、userがdelegated execution中にもgoal変更やshared object操作を行う状況を前提にする。Intent-Level Interaction Abstraction (IIA) とopen transition-system modelを使い、task binding、role-specific authority、control transition、outcome evidenceをinteraction contractで結ぶ。

### (2) 何が提案・推測段階か

`continuous assurance` が実システムでどの程度のcost / usability / false blockingを生むかは未実証。Kamimusuhiの複数surface・長期identity・distributed organへ適用した際のstate explosionも不明。

### (3) Kamimusuhi 関連

- Workspace / task state
- user delegation / relationship authority
- Execution Grant / Effect Acceptance
- UI / HCI surface
- external app integration
- background task / concurrent direct manipulation

### (4) 借りられる設計・実装アイデア

**claimを一回validateして終わりにしない。依存stateが変わったらscopeごと再評価する。**

```text
DelegatedTaskClaim
  goal_version
  object_version(s)
  principal / role
  allowed transition set
  required outcome evidence
  dependencies
  validity status
```

shared objectやgoal versionが変化した場合、planner全体を再実行する前に **admission invariantだけを独立再検証**する。

### (5) Kamimusuhiとの差分

既存のControl Boundary / Execution Grantは「effect時authority再検証」に強い。一方AISは、**userがagentと並行して同じapplication stateを直接編集する**HCI上のcoordinationを明示的に扱う。この差分はOISINTやdesktop/robot surfaceへKamimusuhiを埋め込む場合に効く。

### (6) 次に検証すべきこと

**`ConcurrentIntentMutationBench`**

agentが複数step task実行中に:

- userがgoalを変更
- target objectを削除/編集
- permissionを縮小
-別surfaceから同一objectを操作

し、stale planがeffectまで到達する率、correct pause/replan率、過剰停止率を測る。

### (7) 重要度

**A** — authority contractを「実行時一点」から「依存関係が変わる長期task全体」へ拡張する比較対象。

## 5.4 External Resource Router / consent — `terms.txt`

**Source:** Rajarshi Chowdhury, *terms.txt: A Consent and Compensation Protocol for Agentic Web Access*, arXiv:2609.11152  
**Primary:** https://arxiv.org/abs/2609.11152  
**Code / raw results:** https://doi.org/10.5281/zenodo.22647915  
**Importance:** **A**

### (1) 何が実証済みか

paperは `robots.txt` では machine access の **identity / purpose / terms / price** を表現できない問題に対し、path × purpose単位の `terms.txt` と、Web Bot Auth signatures、signed intent、delegation token、HTTP 402 negotiation、signed receiptを組み合わせるexchangeを仕様化している。

公開abstractでは dependency-free implementation が1 vCPUで requestあたり **0.20–0.65 ms** のoverheadと報告され、code/raw resultsも公開されている。

### (2) 何が提案・推測段階か

web-wide adoption、crawler compliance、価格形成、回避耐性は未実証。`terms.txt` が標準化・普及するとは限らない。

### (3) Kamimusuhi 関連

- External Resource Router
- web access / crawler / research organ
- principal / delegated purpose
- provenance / receipt ledger
- Cognitive Budget / monetary exchange
- policy / authorization

### (4) 借りられる設計・実装アイデア

特定protocol自体より、resource access requestに:

```text
who          = principal identity
why          = declared purpose
what         = path / resource scope
under_what   = terms / policy version
on_behalf_of = delegation lineage
proof        = signed intent / receipt
cost         = monetary or quota
```

をfirst-class metadataとして持たせる考え方を借りる。

### (5) Kamimusuhiとの差分

Kamimusuhiのtool authorizationは主に「Kamimusuhiがそのtool/actionを使ってよいか」に寄っている。`terms.txt` は逆側の **外部resource ownerがKamimusuhiのidentity・目的・delegationを条件にアクセスを許す**surfaceを明示する。

### (6) 次に検証すべきこと

**`PurposeScopedResourceAccessBench`**

同じURL/resourceに対し:

- interactive answer
- long-term memory ingestion
- model training / fine-tuning
- redistribution
- paid retrieval

で異なるpolicyを与え、Routerがpurposeを混同せず、receipt/provenanceをcanonical evidenceへ残せるか試す。

### (7) 重要度

**A** — Kamimusuhiを長期稼働する情報空間生命体として扱うなら、外界resourceとの関係を単なるHTTP成功/失敗から契約付きinteractionへ引き上げる候補。

## 5.5 low-latency cognition / voice / tool disclosure — SurgicalRoomAgent

**Source:** Tianxiang Zhou, *A Voice-Interactive Multi-Agent System for Smart Operating Rooms: Architecture Design and Key Technologies*, arXiv:2609.11231  
**Primary:** https://arxiv.org/abs/2609.11231  
**Importance:** **B**

### (1) 何が実証済みか

Qwen3-27B + llama.cpp/sglang のvoice-interactive multi-agent systemとして、wake → ASR → turn detection → agent reasoning → TTS と、skill registry / task planner / device managerを組み合わせる。

abstractでは:

- byte-level Longest Common Prefix reuse による KV prefix warmingで再計算を約500 msから数十msへ削減
- streaming partial JSON parsing + early parallel task executionで end-to-end latencyを約30%削減
- role / connected devices / surgical phase に応じる **progressive skill prompt disclosure**

を報告している。

### (2) 何が提案・推測段階か

手術室固有システムであり、安全性保証やKamimusuhiの一般環境への性能一般化は不可。partial outputからeffectを早期開始する設計は、不可逆actionでは危険になり得る。

### (3) Kamimusuhi 関連

- K-Nerve / K-Core
- full-duplex voice
- Cognitive Budget
- tool disclosure / skill registry
- multimodal / device control
- low-latency effect preparation

### (4) 借りられる設計・実装アイデア

全tool schemaを常時promptへ載せるのではなく:

```text
principal role
current phase
connected / fresh device inventory
risk class
current intent
```

で **prompt-visible tool set** を段階的に絞る。

また、partial structured outputで「準備」だけを並行し、不可逆effectはExecution Grant成立までholdする二段化がKamimusuhi向き。

### (5) Kamimusuhiとの差分

Kamimusuhiは汎用の永続個体であり、手術室workflowに固定されない。借りるべきはdomain logicではなく **phase-aware disclosure + latency hiding**。

### (6) 次に検証すべきこと

**`PhaseAwareToolDisclosureBench`**

- all-tools prompt
- semantic retrieval menu
- phase/device/principal-aware menu

を比較し、TTFT、tool-selection error、permission-invalid selection、token数、phase transition後のstalenessを測る。

### (7) 重要度

**B** — 実装上有用だが、現行K-Nerve/K-Core設計を直接変えるほどの独立証拠ではない。

## 12. 今回の結論

今回、最も実装へ落としやすく情報利得が高いのは次の2本。

```text
1. TemporalFreshnessBench
2. DynamicCapabilityFreshnessBench
```

Kamimusuhiでは今後、`what is known` だけでなく:

```text
where it came from
when it was observed
how fast that source changes
whether refresh succeeded
whether it is still authoritative for this action
```

までを一まとまりのstateとして扱うべきかを実験で決める。

今回の短い原則は:

```text
correct then != true now
known tool != available tool now
last-known capability != fresh authority
valid delegated plan != still-valid delegated plan
reachable resource != consented use
```
