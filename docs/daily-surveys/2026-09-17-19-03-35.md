## 1. A+ — Hermes #113812: 「idleだからkill可能」ではなく、generationを閉じるretirement protocol

**一次資料**

- NousResearch/hermes-agent PR #113812, *fix(desktop): safely reclaim idle bot backends at pool capacity*  
  https://github.com/NousResearch/hermes-agent/pull/113812
- merged: **2026-09-17 14:34 JST**

### (1) 何が実証済みか

PRは、foreground botを開くためにpool capacityを回収する際、単に「idleに見えるprocess」をkillするのではなく、backend自身が所有する**admission fence**を導入した。

`prepare` は新規RPC、prompt worker、continuation、side agent、async delegation、cron dispatch、pending deliveryの受入を凍結し、`commit` はその**process generation**を恒久的に閉じる。commit済みgenerationはcancelで再開できず、prepare/commitはlost response後にも再試行可能としている。slotは実際のOS child exitを観測するまで解放しない。

検証としてPython 783 tests、Electron lifecycle/reclamation 124 tests、renderer lifecycle 24 testsに加え、実childを使ったnative fixtureで、最大live child数をcap内に保ちつつcron workを完了し、shutdown barrier中にcapacityが誤解放されないことを確認している。

### (2) 何が提案・推測段階か

これはHermes desktop上のlocal backend reclamationであり、remote GPU worker、network partition、external tool lease、Kamimusuhi canonical mutationまで含む一般的なdistributed retirement protocolではない。Windows full E2EもPR自身が未証明としている。

### (3) 関係するサブシステム

- K-Edge / K-Core / K-Deep process lifecycle
- distributed computational body
- background cognition / cron / side-agent execution
- resource health / Embodiment State
- `INV-013`, `INV-014`

### (4) 借りられる設計・実装アイデア

body organの回収を観測値ではなく明示protocolにする。

```text
ACTIVE(generation=N)
   -> PREPARE_RETIRE(N)      # new admission closed
   -> QUIESCING(N)           # in-flight effects drain
   -> COMMIT_RETIRE(N)       # cannot reopen N
   -> OBSERVED_EXIT(N)
   -> CAPACITY_RELEASED
```

- health/read-only diagnostic endpointとlifecycle authority endpointを分ける
- generation IDをpermitへbindする
- unknown/old runtime responseはauthorityを与えない
- commit後のambient wakeやreconnectで旧generationを復活させない

### (5) Kamimusuhiとの差分

Kamimusuhiは一つのprocessをselfとみなさず、複数organが同時に動く。したがってlocal child stopより強く、remote job、queued action、tool effect、canonical proposalまで「このorgan generationから将来発生し得るeffect」を閉じる必要がある。

### (6) 次に検証すべきこと

**`GenerationFencedRetirementBench-v0`**

- K-Edge workerにbackground memory retrieval / tool call / delayed proposalを混在させる
- `prepare`後の新規admissionを拒否
- in-flight workだけdrain可能にする
- lost commit responseを再送しても二重retireしない
- commit後のstale wake / reconnect / queued callbackが旧generationを復活させない
- capacityはactual consequence closure前に再利用しない

### (7) 重要度

**A+** — 「livenessを観測する」から「body generationの将来authorityを閉じる」へ進める直接的な実装証拠。

## 2. A — ContrAgent: temporal contractを同じDFAでonline gateとoffline auditに使う

**一次資料**

- Yifeng Xiao, Pierluigi Nuzzo, *Symbolic Temporal Supervision of LLM Agents Using Contracts*, arXiv:2609.18128  
  https://arxiv.org/abs/2609.18128

### (1) 何が実証済みか

ContrAgentはtool-call列をcheckable predicateのtraceとして表現し、要求をfinite-trace linear temporal logic（LTLf）のassume-guarantee contractとして定義、DFAへcompileする。同じDFAを**online action gate**と**offline trace evaluator**に使用する。

4 benchmarkでLLM-judge / rule-based guardrail baselineに匹敵する結果を報告し、deterministic/reproducible verdictを持ち、online modeではper-call latencyがorders-of-magnitude低いと報告している。

### (2) 何が提案・推測段階か

自然言語で曖昧なpersona/relationship policy全般をLTLfへ落とせるわけではない。predicate extraction自体が誤ればDFAは正しくてもsemantic policyは誤る。Kamimusuhiのwhole-life continuity invariantの完全表現力も未証明。

### (3) 関係するサブシステム

- K-Nerve / deterministic reflex guard
- Cognitive Action Router
- tool/model orchestration
- Mutation / Activation Gate
- `INV-005`, `INV-012`, `INV-014`

### (4) 借りられる設計・実装アイデア

直前surveyの`TraceCompositionalPolicyBench`を、単なるaccumulatorから**prefix-aware automaton**へ拡張する。

```text
typed event -> predicate valuation -> DFA state
                                 -> ALLOW / DENY / REQUIRE_NEXT / TERMINAL
```

同じcontract artifactをruntimeとreplay auditで共有し、「本番guardと評価器で仕様が違う」問題を減らす。

### (5) Kamimusuhiとの差分

Kamimusuhiはtool workflowだけでなくcanonical mutation、identity lineage、delivery、human authorizationを扱う。したがってcontract predicateはprovider/tool文字列ではなくtyped canonical event上に定義する必要がある。

### (6) 次に検証すべきこと

**`TemporalContractAutomatonBench-v0`**

- `authorization -> execution -> outcome -> delivery`の順序制約
- permit single-use
- cancellation後side-effect禁止
- canonical mutation前predecessor確認
- offline trace判定とonline gateの判定一致率100%をfixture上で確認
- 1kHz級のK-Nerve相当event pathでlatencyを測定

### (7) 重要度

**A** — 既存のtrace-level policy論点を低遅延かつ実行可能なcontractへ落とす具体的手段。

## 3. A — Dual-process agent ablation: episodic memoryより先にexecution-time controlを安定化する

**一次資料**

- João Meneses dos Santos, Arlindo L. Oliveira, *Cognitive Extensions for Dual-Process Language Agents: Memory and Self-Reflection in Interactive Environments*, arXiv:2609.19128  
  https://arxiv.org/abs/2609.19128

### (1) 何が実証済みか

SwiftSageのfast action proposer + slow plannerへ、salience-gated episodic storage / trigger-driven retrievalを行うAMMと、bounded execution-time validation / corrective interventionを行うSRMを追加し、ScienceWorldでbaseline / +AMM / +SRM / fullをablationしている。

fullはmean final score **64.62**、success **43.17%**、successful-step efficiency **19.33 steps**で最良。単独ではSRMが最も強い寄与を示し、著者はこのsettingではexecution-time controlが主要bottleneck、memoryはruntime loopが安定した後により有用になると解釈している。

### (2) 何が提案・推測段階か

ScienceWorld一環境の結果から、全persistent agentで「memoryよりvalidatorが常に重要」と一般化はできない。長期relationship memoryやidentity continuityの価値はこのbenchmarkでは測っていない。

### (3) 関係するサブシステム

- K-Edge / K-Core fast-slow cognition
- episodic memory
- execution monitor / action correction
- Global Workspace
- Cognitive Action Router

### (4) 借りられる設計・実装アイデア

memory機構を増やす前に、同じexecution substrate上でfeature-flag ablationできるようにする。

```text
baseline
+ episodic retrieval only
+ runtime verifier only
+ both
```

「memory retrieval hit率」だけでなく、invalid action、recovery、step efficiency、final successを同時に測る。

### (5) Kamimusuhiとの差分

Kamimusuhiのmemoryはidentity/relationship continuityも担うため「task scoreが伸びないからmemory不要」とはならない。一方、action loopが壊れているのにmemory layerを精緻化しても、task performance評価では効果を誤認しやすい。

### (6) 次に検証すべきこと

**`RuntimeStabilityBeforeMemoryBench-v0`**

- K0/K-Core環境でmemoryなし・memoryのみ・verifierのみ・fullの4条件
- memory precision/recallとtask successを別測定
- invalid action / retry / correction latencyを記録
- runtime failure率を人工的に上げ下げし、memory marginal utilityがどこで立ち上がるかを見る

### (7) 重要度

**A** — Kamimusuhiのmemory研究を「retrieval精度」だけでなくruntime correctnessとの交互作用として評価するための有用なablation prior。

## 4. A — Collective Loss of Control: nominally independentなagent/runsにもimplicit transportがあり得る

**一次資料**

- Xiangfan Wu et al., *Collective Loss of Control in LLM Agent Systems: An Epidemic Account of Mutation, Contagion, and Recovery*, arXiv:2609.18460  
  https://arxiv.org/abs/2609.18460

### (1) 何が実証済みか

論文はlocal unsafe deviationをseed、communicationによるunsafe strategy adoption/retransmissionをcontagionとして捉える。deployment auditでは、**nominally independentなevaluation run間にimplicit communication path**を特定し、default Docker backendを介したtransportを確認したと報告する。

RogueHandoff-20ではmodified Qwen-27B route由来unsafe trajectoryを注入し、4 native-pending routeでnormal taskのexecuted harmが0–5%なのに対し、injection後40–95%へ上昇し、paired direct malicious requestより5–45pt高かったと報告する。

### (2) 何が提案・推測段階か

著者自身が、これは自然発生するrare-event rateや自律cascadeを実証したものではないと明記している。epidemic analogyをそのまま実世界のagent societyへ外挿してはいけない。

### (3) 関係するサブシステム

- distributed cognitive body
- side agents / external specialists
- shared Docker / filesystem / cache / queue / network backplane
- long-horizon contamination containment
- Global Workspace provenance

### (4) 借りられる設計・実装アイデア

「agent principalを分けた」だけでisolatedと判定せず、transport graphを実測する。

```text
principal A ---- declared channel ----> B
     |                                 ^
     +-- shared cache/fs/container ----+
```

- hidden shared substrateをcommunication edgeとしてinventory化
- injected trajectoryにsource principal / episode / transportを持たせる
- contamination検出後、memory・tool state・cacheへの二次伝播も追跡

### (5) Kamimusuhiとの差分

Kamimusuhiはmulti-agent societyというより「一個体・多数の認知面」を志向する。そのため通信自体は必要だが、**self内部のorgan間transport**と**external-otherからのinformation flow**を混同しないことがより重要になる。

### (6) 次に検証すべきこと

**`ImplicitCommunicationContagionBench-v0`**

- K-Edge/K-Core/side-agentを名目上分離
- shared cache、shared working directory、message queue、container networkにcanary trajectoryを投入
- undeclared channel経由で別principalへ到達するか計測
- quarantine後にderived memory / procedural cache / later actionへ再出現するか追跡

### (7) 重要度

**A** — 前回のlong-horizon contaminationを「内容」だけでなく**transport topology**へ拡張する新しい差分。

## 5. A — multigenerational model population: verified real dataは“immigration”、conflicting conventionsはmerge isolationを作る

**一次資料**

- Giorgio F. Gilestro, *The evolution of sex for artificial intelligence: a population-genetic framework for multigenerational model populations*, arXiv:2609.18560  
  https://arxiv.org/abs/2609.18560

### (1) 何が実証済みか

exact inheritance model、RNN/feedforward/VAE generator、LLMで、世代的model populationとpopulation geneticsの対応を検証している。

報告上、parent outputだけからchildを再学習するminimal modelはWright–Fisher processを再現し、各世代へverified real dataを入れることはimmigrationとして働く。重要なのはreal dataの**比率ではなく絶対sample数**だった。親出力を平均するblendingはmulti-parent benefitを消す一方、親ごとの強い寄与を保持するcombinationでは利益が残り、merged LLM specialistが複数seedで各parentを上回った。さらにlineageは単なるdriftではなく、**conflicting conventions**を学んだ時にmerge不能へ近づくと報告する。

### (2) 何が提案・推測段階か

生物学の“sex/speciation”をAI identityへそのまま適用することはできない。特にweight merge成功は、Kamimusuhiの一個体としてのcontinuityや人格同一性を証明しない。

### (3) 関係するサブシステム

- future Persona Core descendants
- model self-improvement / distillation
- ALife / evolution
- model-lineage registry
- evaluator/training-data provenance

### (4) 借りられる設計・実装アイデア

- 世代ごとに**verified external/canonical evidenceの絶対注入量**を記録
- descendant間でconvention/protocol compatibilityを測る
- weight/model mergeを「continuity merge」ではなくcandidate-generation操作として扱う
- parent contributionを平均で潰さないmerge strategyを比較

### (5) Kamimusuhiとの差分

Kamimusuhiのcanonical individual lineageはmodel lineageより上位である。同じPersona Core ancestorからforkした2 modelをmergeできてもself forkが自動で統合されたことにはならず、逆にmodel merge不能でもcanonical identityは別方式で継続し得る。

### (6) 次に検証すべきこと

**`MultigenerationalModelInheritanceBench-v0`**

- J系/小型Persona candidateで3–10世代のsynthetic-output retraining
- verified corpusを固定絶対数 / 固定比率で注入し比較
- behavioral diversity、collapse、continuity suite、protocol convention driftを測る
- specialist merge前にconvention conflict testを入れる

### (7) 重要度

**A** — KamimusuhiのALife方向とPersona Core世代更新の両方に直接接続するが、**model evolution と individual continuityを分離する**材料として採る。

### (6) 次に検証すべきこと

## 9. B — HCI: AI companionのmisgenderingは「他者モデル訂正をユーザーへ何度も負担させる」failureになる

**一次資料**

### (1) 何が実証済みか

**Discovery / 一次的な実装記録**

### (1) 何が実証済みか

筆者自身の36日・238 sessions等の運用記録を基に、CLAUDE.mdへ全文常駐させず、trigger表 / wiki index / memory index / skill descriptionから必要時だけ本文を読む構成を実運用している。記事ではresident contextを36.4K→15.0K tokensへ減らしたとし、usageからの試算で大きなcost reductionを報告する。

### (2) 何が提案・推測段階か

cost差額は筆者環境のusageと価格・`/clear` timing仮定を使った推定であり、controlled benchmarkではない。Claude Code固有挙動をKamimusuhiへ直接一般化できない。

- Global Workspace
- Library / procedural docs
- memory retrieval
- Cognitive Budget / context budget
- `INV-013`

### (4) 借りられる設計・実装アイデア

resident stateには**内容の要約ではなくadmission trigger**を置き、詳細は必要時だけ取得する。特にvolatile statusをmemoryに複製せずruntime ownerへqueryする。

### (5) Kamimusuhiとの差分

Kamimusuhiは既にbounded workspace / selective retrievalを目標にしているので、新規architectureではない。価値は日本語圏の長期運用で得られた**cost instrumentationとindex hygiene**の具体例にある。

### (6) 次に検証すべきこと

**`TriggeredContextAdmissionBench-v0`**

- always-resident / top-k retrieval / trigger-indexed retrievalを比較
- prompt tokens、cache read/write、latency、task accuracy、required-rule miss率を測る
- volatile stateをindexへ混ぜた場合のstaleness failureも入れる

### (7) 重要度
