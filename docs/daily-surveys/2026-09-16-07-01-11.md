## 要約

今回の重要差分は5本に圧縮できる。

1. **state migration は file rename ではなく authority migration である。** Letta #3232 は、現行 state が空であっても現行ファイルを authoritative とし、壊れた current state から stale legacy state へ黙って fallback しない。古い state の「復活」を防ぐことが、migration の correctness に含まれる。
2. **remote execution と observer process の生存は分離する。** Letta #4466 は、enqueue 後に client process を切り離し、status read failure を execution failure とみなさず、入力を再送しない。completion signal も goal success certificate ではない。
3. **diagnostic / readiness path は実 execution path と同じ意味論を使う必要がある。** Hermes #112236 は、実 session は fallback provider で起動できるのに readiness probe は primary provider だけを見て false negative を出す不整合を修正した。ただし「特定 provider を明示確認」する probe では fallback で失敗を隠さない。
4. **physical self-improvement は failure recovery / reset / collection / policy learning / supervisor learning を閉ループ化できるが、更新対象を分離すべきである。** REVOLVE は4つの実機 manipulation task で5 iteration の closed-loop evolution を評価し、policy success と agent judgment の改善、human effort の大幅削減を報告した。
5. **human-AI cognition は利用量だけでは記述できない。** 9月15日更新の HCI 理論論文は execution locus / cognitive governance / representational reorganization / process organization / reachable cognitive space の5軸を提案した。Kamimusuhi では「外部知能を使ったか」より **誰が認知的主導権を持ち、何が内部化・外部化されたか**を記録する語彙として有用だが、現時点では理論提案である。

今回の設計圧縮:

```text
legacy state exists != legacy state may resurrect
observer died != remote execution failed
remote run completed != requested goal succeeded
probe result != runtime truth unless probe shares execution semantics
fallback is valid for execution != fallback may mask an explicitly tested dependency
self-improvement loop != unrestricted self/persona mutation
AI use intensity != cognitive organization
```

### A — Letta #3232: durable-state migration は「古い state を復活させない」まで含めて設計する

**出典**: letta-ai/letta-code PR #3232, *fix(channels): rename routing.yaml to routing.json with legacy migration*  
merged: **2026-09-16 05:34 JST**  
https://github.com/letta-ai/letta-code/pull/3232

1. **何が実証済みか**: JSON形式の channel routing state が誤って `routing.yaml` と名付けられていた migration で、new writesを`routing.json`へ移しつつ、direct read/cache load/teleport guardの全 readerがlegacy stateを扱えるようにした。migrationは内容をvalidate後、hard linkで新名をatomic publicationし、成功後にのみ旧名を削除する。両ファイルが存在する場合は **`routing.json` が authoritative で、空route tableも有効な最新状態** とする。現行ファイルがcorrupt/unreadableでも stale legacy へfallbackしない。saveはunique tempへwrite+flush後renameし、失敗時は旧snapshotを保持する。23-case disk suiteを含む73 focused tests、実filesystem smoke testを報告している。power-loss simulationとWindows実機は未実施。
2. **何が提案・推測段階か**: このmigration patternだけでDB schema、distributed replica、canonical self-state、cryptographic key rotationまで安全に一般化できるとは未実証。hard-link不可filesystem、network filesystem、multi-node concurrent writer、power lossの扱いは別途必要。
3. **関係する Kamimusuhi subsystem**: Continuity Kernel、canonical evidence/self history、routing state、relationship/index schema migration、K-Edge/K-Core persistent cache、activation metadata。
4. **借りられる設計・実装アイデア**: migrationを `read old -> transform/validate -> publish new authority -> verify -> retire old` の明示state machineにする。**current authority が一度成立したら、legacy は recovery candidate ではあっても silent fallback source にしない**。空状態・revoked状態を「欠損」と誤認しない。migration receiptにsource generation / target generation / publication status / cleanup statusを残す。
5. **Kamimusuhiとの差分**: Kamimusuhiは既にcanonical head/predecessor/lineageを持つ設計だが、schema/file format migration時の「legacy read compatibility」と「authority precedence」を具体化していない。特に stale branch / deleted relationship / revoked route が旧形式から復活すると `INV-006/011/014` を破る。
6. **次に検証すべきこと**: **`AuthoritativeStateMigrationBench`**。旧形式A→新形式Bのmigration中に crash、concurrent save、permission failure、corrupt current、empty current、legacy-only read、cleanup failureを注入し、(a)最新stateが巻き戻らない、(b)空/削除が復活しない、(c)reader間でauthorityが分裂しない、(d)再起動後に同じheadへ収束することを測る。
7. **重要度**: **A**。identity continuityそのものではないが、canonical stateを将来何度も進化させるKamimusuhiでは長期寿命に直結する。

### A — Letta #4466: remote execution の存続・観測・goal success を三分する

**出典**: letta-ai/letta-code PR #4466, *fix(agent): notify remote completion from existing Cloud status*  
merged: **2026-09-16 03:34 JST**  
https://github.com/letta-ai/letta-code/pull/4466

1. **何が実証済みか**: 以前はremote Agent launch後、submitter CLI processがlistener completionまで接続を保持し、1時間上限やread failureで「失敗」と報告し得た一方、remote execution自体は継続していた。修正後は`--no-wait`でenqueue receiptを返してsubmitterを終了し、parent harnessが既存Cloud Super Run statusを監視する。status readの一時失敗はbackoff/retryし、**inputを再送しない**。新しいsendがlatestを追い越しても古いtaskのoutcomeとして採用しない。reply textを取得できなくてもcompletionを通知し、再launchせずconversation readを案内する。PR自身が「completionはCloud activity signalであり、requested goal accomplishmentの証明ではない」と明記する。deterministic testsとlive smoke checkあり。
2. **何が提案・推測段階か**: Cloud status feed自体のexactly-once semantics、長時間partition、status retention期限、remote side effectのtransactional correctness、goal-level verifierはこのPRでは保証されない。
3. **関係する Kamimusuhi subsystem**: K-Deep/background work、remote model/tool orchestration、Execution Grant、Action/Effect Ledger、result delivery、continuation/recovery、multi-device cognition。
4. **借りられる設計・実装アイデア**: `accepted/enqueued`, `executing`, `terminal runtime state`, `reply collectible`, `goal verified`, `result delivered` を別stateにする。observerのdisconnect/restartをremote work cancellationと同一視しない。receipt/run IDで観測を再接続し、**unknown outcomeで同じ input を自動再送しない**。
5. **Kamimusuhiとの差分**: `INV-012/014` ですでにexecution/delivery/unknownを分けるが、K-Deepや外部agentを長時間走らせる場合、observer process lifecycleをexecution lifecycleから切り離す具体的実装証拠になる。さらに「terminal runtime status != semantic goal success」を明示する必要がある。
6. **次に検証すべきこと**: **`DetachedRemoteExecutionObservationBench`**。enqueue直後のclient kill、observer restart、status read failure、newer run overtaking、reply loss、remote success/failure/unknownをfault injectionし、duplicate execution率、false-failure率、false-success率、reconciliation latency、goal verifierとの一致率を測る。
7. **重要度**: **A**。K-Deep / background cognitionを非同期化する際の誤再実行・誤完了を直接防ぐ。

### A- — Hermes #112236: readiness / diagnostic は実行経路と同じ resolver を使い、明示probeではfallbackを禁止する

**出典**: NousResearch/hermes-agent PR #112236, *fix(gateway): Desktop readiness probe no longer shows onboarding on a multiplexed backend or when a fallback provider serves the session*  
merged: **2026-09-16 06:24 JST**  
https://github.com/NousResearch/hermes-agent/pull/112236

1. **何が実証済みか**: multiplex backendでlaunch profileのreadiness probeだけsecret scopeをbindしておらずfalse failureになり、さらに実session creationはfallback-aware resolverを使うのにprobeはstrict primary resolverを使っていたため、**sessionは起動できるがUIはonboarding/errorを出す**不整合があった。修正後、default readinessはsession creationと同じfallback-aware resolverを使い、selected provider/modelを返す。一方、ユーザーが明示的に`provider=anthropic`等を確認した場合はstrict checkを維持し、別provider fallbackで失敗を隠さない。新testsはbaseで赤/headで緑、gateway suite 1,962 passと報告。
2. **何が提案・推測段階か**: readinessとexecutionを同じcode pathに寄せれば全health checkが正しくなるわけではない。external providerのrate limit、latency、model capability、partial tool availability等は別health dimension。
3. **関係する Kamimusuhi subsystem**: Computational Embodiment State、resource health、Cognitive Action Router、K-Edge/K-Core/K-Deep provider routing、operator UI、fallback policy。
4. **借りられる設計・実装アイデア**: runtime statusは「別実装の診断推測」ではなく **実 execution resolver のdry-run / inspect mode** から導出する。`can_run_current_policy` と `is_specific_resource_healthy(resource_id)` を分ける。前者は許可されたfallbackを含み得るが、後者はfallbackでmaskしない。
5. **Kamimusuhiとの差分**: `INV-013` はpresent stateをreal ownerから導出するが、今回の差分は **status computation semantics自体がreal execution semanticsと一致すること**。fallback-capableな分散身体では「身体全体として活動可能」と「特定器官が健全」を別metricにする必要がある。
6. **次に検証すべきこと**: **`DiagnosticRuntimeParityBench`**。primary/fallback/local/remote provider、credential scope、offline node、degraded capabilityを交差させ、diagnosticが実execution可否と食い違う率を測る。明示器官probeではfallbackがfalse positiveを作らないことも検証する。
7. **重要度**: **A-**。新しいidentity invariantではないが、computational embodimentの自己認識を現実に接地するため重要。

### A- — REVOLVE: 実機 failure-correction loop を policy と supervisor の二重学習へ戻す

**出典**: Hanyu Liu et al., *REVOLVE: An Automated Closed-Loop Framework for Evolving Robot Manipulation with Minimal Human Intervention*, arXiv:2609.14633, submitted 2026-09-13 / updated 2026-09-15  
https://arxiv.org/abs/2609.14633

1. **何が実証済みか**: preprintは、data collection、policy training/deployment、failure recovery、continual learningを一つの実機loopへ統合するREVOLVEを提案・評価した。Automated Reset and Collection (ARC)でfailure後のreset/correction dataを収集し、Dual-Loop Evolution (DLE)でmanipulation policyとagent judgmentの双方を更新する。4 real-world manipulation tasks、5 iterationsで、平均policy success **+18.5 points**、agent judgment accuracy **+8.5 points**、human effortをdata collectionで **94.4%**、deployment testingで **95.1%**削減したと報告する。
2. **何が提案・推測段階か**: 長期運用でのcatastrophic drift、安全性、open-ended taskへの一般化、hardware wear、failure distribution shift、identity/persona continuityは未実証。agent judgment改善が「自己モデルの改善」を意味するわけでもない。
3. **関係する Kamimusuhi subsystem**: embodied K-Edge/K-Nerve、procedural memory、self-improvement、failure attribution、world/action model、robotics/MOVI接続、offline consolidation。
4. **借りられる設計・実装アイデア**: physical trialを `attempt -> observation -> failure classification -> recovery/reset -> correction trajectory -> verified outcome -> policy update candidate / supervisor update candidate` と二経路に分ける。execution failureをpersona/selfへ直接学習させず、**motor/procedural policy と evaluator/supervisor memoryを別update channel**にする。
5. **Kamimusuhiとの差分**: REVOLVEの中心はtask performanceとautomationであり、canonical identityやauthority lineageは扱わない。Kamimusuhiでは実機学習の改善がPersona Core/value/relationship stateへ横滑りしないMutation Gateが必要。
6. **次に検証すべきこと**: **`EmbodiedFailureCorrectionLoopBench`**。簡単なrobot/simulator taskで、(a)policy only、(b)supervisor memory only、(c)dual-loop、(d)naive all-state learningを比較し、success improvement、repeat-failure率、unsafe recovery率、cross-task regression、canonical self-state非回帰を測る。
7. **重要度**: **A-**。Kamimusuhiの「経験から発達する身体」を実験可能なclosed-loopに落とす比較対象として有用。

### B — Sustained Human-AI Cognition: 「AIをどれだけ使ったか」ではなく認知の組織化を記述する

**出典**: Zijian Ru, *The Dynamic Organization of Sustained Human-AI Cognition: From Construct-Level Change to Relational Structure*, arXiv:2609.14942, submitted 2026-09-14 / updated 2026-09-15  
https://arxiv.org/abs/2609.14942  
Zenodo v2: https://doi.org/10.5281/zenodo.22678803

1. **何が実証済みか**: 本稿は主として理論・分析frameworkであり、実験で効果量を実証した研究ではない。論文は sustained AI participation を5つのrelational dimension — **execution locus, cognitive governance, representational reorganization, process organization, reachable cognitive space** — で記述し、同じAI利用量や同じ短期outcomeでも異なる認知組織があり得るというtestable propositionsを提示する。
2. **何が提案・推測段階か**: 5軸の測定妥当性、相互独立性、長期能力変化との因果関係、具体的HCI介入の有効性は未実証。Kamimusuhiへそのまま「心理モデル」として実装する根拠はない。
3. **関係する Kamimusuhi subsystem**: Cognitive Action Router、external-model delegation、self-model/capability model、human-AI co-regulation、HCI、cognitive budget、K-Core/K-Deep orchestration。
4. **借りられる設計・実装アイデア**: delegation traceに単なる`provider/model/cost`だけでなく、`execution_locus`, `decision_owner`, `representation_changed?`, `process_role`, `reachable_space_delta`のような**認知組織メタデータ**を実験的に付ける。特に「外部モデルを呼んだ」ことと「判断権を外部モデルへ渡した」ことを区別する。
5. **Kamimusuhiとの差分**: 論文は人間-AI関係の分析framework。Kamimusuhiは人工個体自身のcognitive extension / organ / otherを区別するため、同じ語彙を**自己の外部認知依存度・governanceの測定**へ翻案する。人間の認知発達についての結論をAI個体へ類推しない。
6. **次に検証すべきこと**: **`CognitiveOrganizationTraceStudy`**。同じtaskをlocal-only、external-model-as-advisor、external-model-as-decider、tool-heavy、human-guidedの条件で解き、最終accuracyだけでなくdecision ownership、internal representation update、future unaided performance、external dependencyを追跡する。
7. **重要度**: **B**。規範要件ではなく、extended cognitionを「利用回数」以上に測る観測語彙として有用。
