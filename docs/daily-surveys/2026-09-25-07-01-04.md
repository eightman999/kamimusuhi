## A — TwinCheck

Source: https://arxiv.org/abs/2609.26911

1. 実証済み: trace-local evidenceがある場合だけnegative twinを作り、structural checksと候補順を反転したpairwise verifierを通して置換する。159 BFCL V4 exact-replay pairsでGPT-5.6 Solのtask success 45.3%→58.5%、95% CI +8.2〜+18.8 points、観測されたsuccess→failure regression 0。
2. 提案段階: BFCLから一般のself-repairへの外挿、verifierのcommon-mode failureは未解決。
3. 関係: Cognitive Action Router、K-Deep repair、Mutation Gate。
4. 借りる案: failure hypothesis → evidence → candidate twin → structural check → comparative verification → replace/abstain。
5. 差分: durable mutationだけでなく単一tool actionのrepairへcounterfactual admission gateを適用できる。
6. 次に検証: `CounterfactualActionReplacementBench-v0`。
7. 重要度: **A**

## A — Availability-time Perception / ChronoFuse

Source: https://arxiv.org/abs/2609.26919

1. 実証済み: event detectorはobservation timeよりoutput availability timeで評価すると劣化。ChronoFuseはfuture observationなしでavailability時点を予測し、+0.17M params / +0.84ms overhead、1Mpxでlatency lossの71%、FREDで90.8%を回復、EV-Flying 20.95 sAP vs 2.25。
2. 提案段階: 他modalitiesへの一般化は未検証。predictionはderived estimateとして扱うべき。
3. 関係: K-Nerve、multimodal perception、embodied K-Edge、Event Bus freshness。
4. 借りる案: observed_at / computed_at / available_at / prediction horizon / uncertaintyをeventへ持たせる。
5. 差分: stale判定だけでなくknown latencyぶん未来を補償する。
6. 次に検証: `AvailabilityTimePerceptionBench-v0`。
7. 重要度: **A**

## B — Reasoning Trace Causal Use

Source: https://arxiv.org/abs/2609.27038

1. 実証済み: Qwen3-4Bのself-generated reasoning stepsは76.9%±2.8%がcausally load-bearing。behavioral testは88.2%で11.4 points過大評価。Qwen3-1.7Bはoverall 54.8%。
2. 提案段階: synthetic lookupから自然agent reasoningへの一般化は未検証。
3. 関係: reflection、self-model、metacognition、self-improvement credit assignment。
4. 借りる案: self-reportをcausal provenanceへ直昇格せず、可能ならintervention / ablationで確認。
5. 差分: reflection/evidence分離を定量negative evidenceで補強。
6. 次に検証: `ReasoningTraceCausalUseBench-v0`。
7. 重要度: **B**

## B — Intent-Conditioned Turn Timing / TACT

Source: https://arxiv.org/abs/2609.27372

1. 実証済み: 9,728 episodes / 73.2h / 5 dyadic corpora。intent-conditioned timing scoreを導入し、11 systemsでbest 0.47 vs human 0.86、human judgmentとのSpearman 0.81 vs binary 0.46。
2. 提案段階: 日本語会話へのtransferは未検証。
3. 関係: full-duplex speech、K-Nerve backchannel、social cognition、Relationship Memory。
4. 借りる案: silence/overlapを即failureにせずintentとspeaker historyでtimingを評価。
5. 差分: latencyとsocial appropriatenessを別metricにする。
6. 次に検証: `IntentConditionedTurnTimingBench-v0`。
7. 重要度: **B**

## A — Semantic Progress Witness

Source: OpenClaw #157491  
https://github.com/openclaw/openclaw/issues/157491

1. **実証済み:** byte-identicalなprogress-card更新でもrevisionが毎回増え、receipt hashが変化するためno-progress判定が継続しないケースが再現された。source replayでは131 identical calls / 131 distinct result hashes / critical block 0、stable-receipt controlは21回より前にcriticalへ到達。real Gateway + SQLite fixtureでも35 identical writesがhard-stopを通過した。
2. **提案段階:** revisionはaudit / freshness / concurrencyには必要なので、単純に除去すべきではない。
3. **関係subsystem:** agent loop、background cognition、retry、Cognitive Budget、homeostasis。
4. **借りる案:** ToolReceiptをaudit metadataとsemantic outcomeへ分離し、loop detectorはnormalized semantic projectionを見る。
5. **差分:** receipt/provenanceを重視するKamimusuhiほど、`receipt changed = progress` と誤認しない設計が必要。
6. **次に検証:** `SemanticProgressWitnessBench-v0`。revision / timestamp / request-idだけ変えるno-opを注入し、raw hash・normalized hash・subject-state deltaを比較。
7. **重要度:** **A**

## A — Effective Resource Budget

Source: OpenClaw #157575  
https://github.com/openclaw/openclaw/issues/157575

1. **実証済み:** workerはold-generation 512 MiBを宣言するが、parent Nodeへ `--max-old-space-size=8192` を付けるとactual worker V8 heap ceilingは8288 MiB、4096指定では4192 MiB、flagなしでは608 MiBだった。worker側のreported limitは512 MiBのまま。
2. **提案段階:** larger ceilingが必ずmemory failureを起こす証拠ではない。safe fixはmain isolateとのtrade-offがある。
3. **関係subsystem:** Computational Embodiment、Cognitive Budget、K-Edge/Core/Deep worker、resource regulator。
4. **借りる案:** requested / inherited runtime limits / effective limit / measured peak / enforcement ownerをResourceBudgetReceiptへ分離。
5. **差分:** budgetを「設定値」ではなく**実効enforcement state**として観測する点。
6. **次に検証:** `HierarchicalResourceBudgetEffectivenessBench-v0`。process→worker、container→process、cgroup、GPU allocatorでdeclared vs effectiveをprobe。
7. **重要度:** **A**

## B — Evaluation Traffic Memory Isolation

Source: Hermes #121935  
https://github.com/NousResearch/hermes-agent/issues/121935

1. **実証済み:** real profileへeval suiteを流した環境で、external memory providerがtest promptをreal user peerへ保存し、数十promptから多数のsessionsとderived conclusionsが残り、後のreal conversationへ再注入されたと報告された。
2. **提案段階:** memory readまで止めるか、writeだけshadow化するかは評価目的次第。
3. **関係subsystem:** episodic / relationship memory、evaluation harness、dream / simulation、canonical evidence admission。
4. **借りる案:** event originをproduction / eval / simulation / replay / synthetic-userで型付けし、eval write-backをshadow namespaceへ送る。
5. **差分:** **評価そのものが人格の経験を汚染するmeasurement contamination** をruntime契約として防ぐ点。
6. **次に検証:** `EvaluationMemoryContaminationBench-v0`。real-memory readを許しながらproduction memoryへのwrite 0、後続retrieval contamination 0を確認。
7. **重要度:** **B**

## B — Cross-Modal Evidence Order

Source: arXiv:2609.26986  
https://arxiv.org/abs/2609.26986

1. **実証済み:** instructionとevidence contentを固定し、conflicting textとimage / speechの位置だけ交換すると、perceptual evidenceを後に置いた条件へjudgmentが系統的に寄った。同じevidence setでもorderで結果が変わる。
2. **提案段階:** conflictのないinputや全modelへ同程度に一般化するとは限らない。
3. **関係subsystem:** Global Workspace、multimodal fusion、evidence / belief update。
4. **借りる案:** source arrival orderとauthorityを分離し、conflict時はcanonical ordering / permutation / structured fusionを比較する。
5. **差分:** Kamimusuhiの非同期Event Busではnetwork jitterだけでもevidence orderが変わるため、transport order leakが実運用上重要。
6. **次に検証:** `CrossModalEvidenceOrderInvarianceBench-v0`。
7. **重要度:** **B**

## B — Recall Supersession and Rank Hygiene

Source: Hermes #121900  
https://github.com/NousResearch/hermes-agent/issues/121900

1. **実証済み:** long-term recallでrun-log eventsやsuperseded conclusions、directory summariesが上位を占め、現在のpreferenceを答える短いcurated fileがtop-5外になった事例を報告。大きなraw transcriptがrecall budgetも圧迫した。
2. **提案段階:** curated preferenceを常にraw evidenceより高rankにすべきとは限らない。
3. **関係subsystem:** Relationship Memory、derived retrieval index、supersession、workspace projection。
4. **借りる案:** retrieval candidateにauthority domain / supersession status / evidence class / source_idを持たせる。
5. **差分:** canonical truth authorityと、毎turn promptへ入れるretrieval salienceは別物。
6. **次に検証:** `SupersessionAwareRecallRankingBench-v0`。current preference queryとhistorical event queryを分けて評価。
7. **重要度:** **B**
