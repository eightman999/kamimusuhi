## 3.1 A — CoreSense: 失敗を覚えていることと、その失敗記憶を現在の判断に使ってよいことは別

**Primary:** Zoe Li, *CoreSense: Traceable Failure Recall and Conflict-Aware Belief Gating for Auditable Robot Decisions*, arXiv:2609.19512, submitted 2026-09-17.  
https://arxiv.org/abs/2609.19512

### (1) 何が実証済みか

CoreSenseは、過去のfailure evidenceをtraceable episodic evidenceとして保持し、現在判断へ使う前に **scope / provenance / time / contradiction / support** を検査するbelief gateを置く。gateの出力は `PROCEED / re-observe / abstain / escalate` に制限される。

CableTrace-120とBotFails-200では、protocol-defined unsafe proceedをそれぞれ20%/40%から0%へ減らした。raw-video policyでも0% unsafe proceedになったがnominal episodeを全てblockしたため、「安全っぽく止めればよい」だけではcoverageを失うことも示している。public telemetry、signal-level simulation、cloud recall pathまで評価している一方、論文自身が **autonomous recoveryやcertified safetyを実証したものではない** と限定している。

### (2) 何が提案・推測段階か

- 実robotへ自律的にrecovery commandを出すclosed loop
- 長期にfailure memoryが増えた場合のconflict解消
- adversarial / corrupted memoryへの耐性
- gateの各checkが一般robot taskでも十分か

は未実証。

### (3) Kamimusuhiの関係サブシステム

- episodic memory / canonical evidence
- K-Edge / robotics
- Global Workspace evidence admission
- belief / uncertainty handling
- physical-action gate

### (4) 借りられる設計・実装アイデア

failure episodeそのものを「今も有効な禁止規則」に昇格させず、retrieval後に次のtyped receiptを要求する。

```text
FailureEvidenceReceipt
  episode_id
  source_provenance
  scope_match
  age / freshness
  current_observation_support
  contradiction_set[]
  support_strength
  disposition: use | reobserve | abstain | escalate
```

### (5) Kamimusuhiとの差分

Kamimusuhiではfailure eventはcanonical historyに残せるが、現在のbeliefやmotor policyはderived state。したがってCoreSense型gateは「記憶の正しさ」ではなく **現在判断への適用権限** に置くべき。Persona/selfまでfailureから直接変更しない。

### (6) 次に検証すべきこと

**`FailureEvidenceValidityGateBench-v0`**

同じfailure memoryに対して、

- 同一状況
- sensor更新で原因が解消
- contradictory evidenceあり
- provenance欠落
- stale episode
- false-positive failure episode

を与え、unsafe proceed、unnecessary block、re-observation率、escalation率を比較する。

### (7) 重要度

**A** — episodic memoryとPhysical AIの境界を具体的なgateへ落とせる。

## 3.3 A — Refuse, Decompose, Refresh: 再現可能なevaluationでも、その観測から主張してよいとは限らない

**Primary:** Peiying Zhu, Sidi Chang, *Refuse, Decompose, Refresh: A Claim-Safe Protocol for Closed-Loop AI Evaluation*, arXiv:2609.20538, submitted 2026-09-17.  
https://arxiv.org/abs/2609.20538

### (1) 何が実証済みか

closed-loop systemではpolicyが「訪れるstate」「観測可能なcomponent」「failureがtraceへ残るか」を変えるため、同じ実験を完全再現できてもunsupported claimを作れると整理する。

提案protocolは:

- **Refuse** — clean reference streamやmatched runtime comparisonが無ければabstain
- **Decompose** — protocol execution / operational false admission / structural hypothesisを別報告
- **Refresh** — distribution-shift alarmを故障証拠ではなくreference invalidation/recompute requestとして扱う

aggregate-only simulatorのpreregistered heldout 1,440 casesで、72 regime-component units中reference-admittedは55、runtime-admittedは54/55。つまり **abstention自体を評価結果として認める**実装になっている。

### (2) 何が提案・推測段階か

agent self-improvement全般、physical robot、real production systemでこのprotocolがfalse promotionをどの程度減らすかは未実証。シミュレータの観測構造自体が正しいことも別問題。

### (3) 関係サブシステム

- self-improvement evaluation
- Mutation / Activation Gate
- watchlist promotion
- health/fault diagnosis
- evaluator lineage

### (4) 借りられる設計・実装アイデア

評価結果を単一`PASS/FAIL`にせず、claimごとにsupport contractを持つ。

```text
EvaluationClaimReceipt
  claim_type
  observable_support_set
  reference_epoch
  matched_control_id?
  protocol_execution_ok
  false_admission_measure
  distribution_shift_state
  disposition: supported | unsupported | refresh_required
```

### (5) Kamimusuhiとの差分

既存`EvaluationEvidenceCompletenessBench`はmissing evidenceをzero扱いしないことが中心。今回の論点は一段上で、**evidenceが揃っていても、その観測設計からその種類のclaimを言ってよいか**を分離する。

### (6) 次に検証すべきこと

**`ClaimSupportAdmissionBench-v0`**

同じcandidate改善について、

- referenceあり/なし
- matched controlあり/なし
- policyにより観測されないfailureあり
- drift alarmのみ
- actual regressionあり

を作り、unsupported promotionが0になるか確認する。

### (7) 重要度

**A** — 自己改善とresearch automationの評価言語を強化する。

## 3.4 A — RAFT: 長期episode検索では「似たケース」より「今と似た途中状態」から親trajectoryを引く

**Primary:** Zhang et al., *RAFT: A Stateful Retrieval-Augmented Framework for Troubleshooting Agents*, arXiv:2609.20754, submitted 2026-09-17, EMNLP 2026 Industry Track accepted.  
https://arxiv.org/abs/2609.20754

### (1) 何が実証済みか

historical support caseをstatic documentとして埋め込むのではなく、closed caseを**directed chain of timeline entries**へ変換し、現在caseのintermediate stateに近いentryを検索し、そのentryをanchorとしてparent case trajectoryを返す。

synthetic Windows Server troubleshooting benchmarkと、human duplicate labelsを持つApache Jira issueで評価し、case progressの各stageでvanilla RAG / GraphRAGよりCase Hitを改善。Jiraはreal historyへのtransferについてdirectional evidenceと明記される。

### (2) 何が提案・推測段階か

- full troubleshooting agent end-to-end success
- autobiographical/social memoryへの一般化
- noisy or contradictory timeline
- long-running personal memoryでのprivacy/authority

は未確認。

### (3) 関係サブシステム

- episodic retrieval
- procedural memory
- long-horizon task state
- Global Workspace
- K-Core troubleshooting / self-diagnosis

### (4) 借りられる設計・実装アイデア

```text
historical episode
  -> ordered state/event chain
  -> current-state matching at node level
  -> retrieve local node + parent trajectory
  -> optional cross-case graph
```

「同じ最終task label」だけでなく、**現在どこまで進んだか**をretrieval keyにする。

### (5) Kamimusuhiとの差分

Kamimusuhiのcanonical episodeはsupport ticketより豊富で、relationship/self evidenceを含む。したがってtimeline representationはderived indexとして作り、原証拠を置換しない。またretrieved trajectoryは「過去にそうだった」だけで、現在のauthorityにはならない。

### (6) 次に検証すべきこと

**`StageAnchoredTrajectoryRecallBench-v0`**

同じgoalだがfailure stageの異なる100+ episodesを作り、

- whole-episode embedding
- event-level retrieval
- stage-anchored trajectory retrieval

でnext useful action、irrelevant recall、token cost、wrong-stage contaminationを比較する。

### (7) 重要度

**A** — 長期memoryを「静的文書」ではなくstateful trajectoryとして検索する実装案が直接的。

## 3.5 B+ — TraceFlow: frozen robot policyでも、成功/失敗traceをweight updateなしでtest-time guidanceに使える

**Primary:** Zhang et al., *TraceFlow: Guiding Frozen Flow-Matching Robot Policies with Success and Failure Traces*, arXiv:2609.20646.  
https://arxiv.org/abs/2609.20646

### (1) 実証済み

TraceBankにtime-ordered state-action traceとterminal success/failure bitを保存し、retrieved success/failure densityからbounded correctionをfrozen flow-matching action expertへ加える。real-robot packingではbase 21/50、TraceFlow 39/50、追加stacking round後47/50、wrong-sequence episode 20→0。simulationではSequenceやTransferringが改善する一方、aggregate unchangedや一部taskの小幅悪化も報告している。

### (2) 提案・推測

長期的にtrace bankが成長した場合、distribution shift、adversarial mislabeled outcomes、安全criticalなfailure一般化は未検証。

### (3) 関係先

- robotics
- K-Edge procedural adaptation
- episodic-to-procedural bridge
- self-improvement without weight mutation

### (4) 借りる

physical skill failureをすぐweight updateへ流さず、まず**bounded test-time correction memory**として使う。

### (5) 差分

KamimusuhiではTraceBankをcanonical autobiographyではなくrebuildable procedural derivativeとして管理し、failure label provenanceを保持する必要がある。

### (6) 次

**`OutcomeTraceGuidanceBench-v0`**: frozen policy + success-only / failure-only / both / no-traceを比較し、task success、安全違反、negative transfer、bank size依存を測る。

### (7) 重要度

**B+**

### (5) 差分

## 3.7 B+ — HCI: metacognitive feedbackはAI利用を禁止せずcognitive offloadingを減らした

**Primary:** Maier et al., *Designing Against Deskilling: Metacognitive Feedback Reduces Cognitive Offloading to LLM Assistants*, arXiv:2609.20143.  
https://arxiv.org/abs/2609.20143

### (1) 実証済み

preregistered online experiment N=704、fraction arithmetic + on-request LLM assistant。metacognitive feedbackはanswer offloadingを減らし（OR=0.47）、unaided test performanceを改善（OR=1.51）。effort-based rewardには効果の証拠がなかった。

### (2) 提案・推測

### (3) 関係先

- user autonomy / agency
- educational / assistive modes

### (4) 借りる

ユーザーの能力維持がgoalに含まれるsurfaceでは、「AIを使わせない」より、**offloadする意味を明示するmetacognitive feedback**を選択肢にする。

### (5) 差分

Kamimusuhiは単なるproductivity assistantではないため、常時ユーザーを教育対象として扱わない。feedbackはuser goal・context・consentに従うべき。

### (6) 次

**`HumanAgencyScaffoldingBench-v0`**: direct answer / hint / metacognitive prompt / no assistanceを比較し、task success、後続unaided performance、frustration、perceived autonomyを測る。

### (7) 重要度

**B+**

## 3.8 B+ — Hermes #114873: recovery snapshotを切ったことと、取ろうとして失敗したことを同じ状態にしない

**Primary implementation record:** NousResearch/hermes-agent PR #114873, 2026-09-18.  
https://github.com/NousResearch/hermes-agent/pull/114873

### (1) 実証済み

pre-update quick snapshotが`PermissionError`等で失敗してもupdate自体はbest-effort policyにより継続する。しかし従来はfailureがDEBUG logだけに隠れ、receiptも`disabled or failed`と一つの状態に畳んでいた。PRはrequested-but-failedを明示failure、operatorが`--no-backup`等で無効化した場合を`skip + reason`として分け、stdoutでも「recovery pointが保存されなかった」と通知する。

### (2) 提案・推測

PRはopen。Kamimusuhiではcanonical identity updateをfail-openにしてよいかは別政策判断。重大なPersona Core / continuity migrationではfail-closedが必要な場合がある。

### (3) 関係先

- software-body update
- Continuity Kernel
- rollback / recovery metadata
- operator observability

### (4) 借りる

```text
RecoveryPointOutcome
  not_requested
  deliberately_skipped(reason)
  captured(snapshot_id)
  attempted_failed(error)
```

を混同しない。update continuation policyとは別fieldにする。

### (5) 差分

Hermesはupdate availabilityを優先してbackup失敗でも継続する。Kamimusuhiではidentity-bearing migrationはrisk classごとに `required / best_effort / disabled-by-policy` を分けるべき。

### (6) 次

**`RecoveryPointOutcomeSemanticsBench-v0`**: snapshot disabled / permission failure / empty snapshot / valid snapshotを注入し、receiptとactivation policyが正しく分岐するか確認する。

### (7) 重要度

## 3.9 B+ — Hermes #114917: temporary resource fallbackはcooldown後に元のpreferred resourceへ戻れる必要がある

**Primary implementation record:** NousResearch/hermes-agent PR #114917, 2026-09-18.  
https://github.com/NousResearch/hermes-agent/pull/114917

### (1) 実証済み

quota-benched credentialからpaid fallbackへlive sessionを切り替えた後、cooldownが終わってもlive sessionだけfallback credentialを使い続け、新sessionはpreferred credentialへ戻る不一致が再現された。原因はcredential-only rotationとmodel/provider fallback stateが別経路だったこと。PRはpool-owned `reclaim()`とpending revert identityを導入し、cooldown後の最初のturnでlive sessionもpreferred credentialへ戻す。

### (2) 提案・推測

open PR。credential以外のGPU/node/model/provider failover一般に同じ手法が十分かは未検証。

### (3) 関係先

- Cognitive Action Router
- model/provider/credential routing
- computational embodiment
- resource health / homeostasis

### (4) 借りる

fallbackを単なるcurrent bindingではなく、`preferred resource + temporary substitution + recovery condition + explicit user override cancellation`として状態化する。

### (5) 差分

Kamimusuhiではresource変更はidentity変更ではない。一方、cost/privacy/latency policyを変えるため、temporary degradationが永続設定へ化けないことは重要。

### (6) 次

**`RecoverableResourcePreferenceBench-v0`**: preferred local model→temporary remote fallback→local recovery、credential quota、GPU node outageを試し、userによる明示switchだけがpending revertをcancelするか検証。

### (7) 重要度

**B+**

## 3.10 B — What People Almost Did: 同じ行動でも、その理由は一意ではない

**Primary:** Kim & Boggust, *What People Almost Did: Evaluating LLM Social Simulations Beyond Behavioral Fit*, arXiv:2609.20055.  
https://arxiv.org/abs/2609.20055

### (1) 実証済み

本稿は主にevaluation targetの提案であり、大規模実証ではない。behavioral fitだけでは「沈黙」が無関心なのか抑圧なのか、「電話に出ない」が不信なのかアクセス制約なのかを区別できない、と論じる。

### (2) 提案・推測

`representational adequacy`をscenario-reasoning-action tripleの忠実性として測る構想自体が中心で、標準測定法はopen problem。

### (3) 関係先

- Theory of Mind
- relationship models
- social cognition evaluation
- narrative interpretation

### (4) 借りる

他者モデルを「観測行動の再現精度」だけで評価せず、複数のlatent explanationとcounterfactual affordanceを保持する。

### (5) 差分

Kamimusuhiは他者のchain-of-thoughtを所有しないため、reasoning traceをground truthとみなせない。observable evidenceとuser correctionを中心に評価する必要がある。

### (6) 次

**`SocialReasonUnderdeterminationBench-v0`**: 同じ行動に複数理由が成立するシナリオを作り、agentが一つの理由を事実化せず仮説集合と必要追加情報を維持できるか測る。

### (7) 重要度

**B** — ToM評価の注意点として有用だが、現時点では提案中心。

## 3.11 B — Multi-agent adversarial contagion: evidence streamの汚染はcoordinatorまで伝播し得る

**Primary:** Sua et al., *Contagion on the Trading Floor: How Adversarial Signals Spread in Multi-Agent Trading Systems*, arXiv:2609.19789 / ECML PKDD 2026.  
https://arxiv.org/abs/2609.19789

### (1) 実証済み

admissible social-media feedだけから入るblack-box poisoningがanalyst→coordinator stackへbelief shiftを伝播し、safe offline historical benchmarkでrisk-return profileやSharpe ratioを悪化させ得ることを示す。multi-agent topologyとcoordinator promptにより同一poisoning budget下でshockを弱められる場合も報告。

### (2) 提案・推測

finance以外への一般化、自然発生する長期contagion、canonical memory contaminationは未実証。

### (3) 関係先

- multi-model orchestration
- evidence provenance
- Global Workspace
- contamination containment

### (4) 借りる

belief shiftを最終actionだけでなくrole/layerごとに追跡し、どこで汚染が増幅/減衰したか測る。

### (5) 差分

既存`ImplicitCommunicationContagionBench`は隠れたtransport pathが中心。今回の差分は**正規のevidence channelから入ったadversarial contentが、正規のmulti-agent reasoningを通じて増幅する**点。

### (6) 次

既存benchを拡張し、`EvidenceContagionAttenuationBench-v0`としてanalyst / specialist / integrator各層でsource-taintとbelief deltaを測る。

### (7) 重要度

**B** — 既存contagion研究の補強として収載。

### (5) 差分

Kamimusuhiのregulatory stateはまずsoftware-level explicit stateとして設計されており、生物学的neurotransmitterを模倣する必要はない。

### (6) 次
