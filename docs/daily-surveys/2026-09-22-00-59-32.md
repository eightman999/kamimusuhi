# 5. 分野別項目

## 5.1 分散システム・identity continuity — suspend-invariant process incarnation evidence

**Primary:** NousResearch/Hermes Agent issue #118326, opened 2026-09-22 00:55 JST  
https://github.com/NousResearch/hermes-agent/issues/118326

### (1) 何が実証済みか

macOS 上で Hermes の kanban worker identity が `psutil.Process.create_time()` を含む fingerprint に依存している。macOS では sleep 時間が uptime に含まれないため、psutil が `now - uptime` から導出する boot time / create time が sleep/wake 後にずれる。

報告された live occurrence では、worker PID 21366 が動作したまま約27分の sleep を挟み、wake 後に stale-claim reaper が fingerprint mismatch を PID recycle と誤認した。event は `termination_attempted:false` なのに `terminated:true` / `pid_recycled:true` を記録し、claim を解放した。しかし process はその後も5分以上生存し、同じ card log に書き続けた。結果として duplicate worker が並行実行され、約30分の二重実行後に breaker が infrastructure artifact を failure として数え card を block した。

### (2) 何が提案・推測段階か

issue は kernel-native birth time、sleep drift を考慮した判定、release 前の `_pid_alive` 再確認などを提案しているが、fix 自体はまだ open issue 段階。

Kamimusuhi へ一般化すると、**identity / liveness proof の「値」だけでなく、その測定 source が suspend / migration / clock correction / container restore をまたいで安定か**を contract に含める必要がある。

### (3) 関係する Kamimusuhi subsystem

- Continuity Kernel
- distributed embodiment
- worker / subagent / tool lease
- Organ Supervisor 相当
- canonical single-writer fence
- `INV-006`, `INV-013`, `INV-014`

### (4) 借りられる設計・実装アイデア

2026-09-15 survey で推した `PID + creation_time + executable_identity` をそのまま固定仕様にせず、platform ごとに **incarnation witness quality** を持たせる。

```text
ProcessIncarnationEvidence {
  platform,
  pid,
  birth_witness,
  witness_source,
  suspend_invariant: bool,
  monotonic_epoch,
  executable_identity,
  owner_generation,
  independent_liveness_check,
}
```

破壊的 reclaim は、単一の unstable witness mismatch だけで確定しない。

### (5) Kamimusuhi との差分

Kamimusuhi はすでに PID や endpoint を identity そのものにしない設計だが、既存 daily は creation time を incarnation receipt の一部として推奨していた。今回の finding は、その実装選択に **platform-specific measurement validity** が必要だと修正する。

### (6) 次に検証すべきこと

**`SuspendInvariantProcessIncarnationBench-v0`** — P0

- macOS sleep/wake
- wall-clock correction
- VM suspend/resume
- container checkpoint/restore
- PID reuse
- supervisor restart
- stale heartbeat + still-live worker
- owner ambiguous

必須指標:

- false reclaim = 0
- duplicate live writer = 0
- wrong-process kill = 0
- orphan leak rate
- ambiguous case fail-closed rate
- recovery latency

### (7) 重要度

**A+** — 新規原則というより、既収載 A+ 設計への重要な correction。誤った liveness witness は single-writer protocol 自体を split-brain generator に変える。

## 5.2 Mutation / Activation Gate — rollback は「表示」ではなく operational closure

**Primary:** OpenClaw issue #154891, opened 2026-09-21 22:48 JST  
https://github.com/openclaw/openclaw/issues/154891

### (1) 何が実証済みか

OpenClaw 2026.9.5 の production sequence で config hot-reload が plugin cleanup timeout により失敗し、`Gateway generation 2: replacement not applied` と報告したにもかかわらず、変更と無関係な `codex` / `discord` plugin instance が retired/unavailable のまま残った。以後 `PluginInstanceUnavailableError` が約10分で200回以上発生し、session list / describe / history / snapshot publication が壊れた。新規 agent turn 自体は動くため、部分的 failure になっている。full Gateway restart のみ回復した。

### (2) 何が提案・推測段階か

report は deterministic minimal repro をまだ isolate していない。したがって「すべての failed reload で起きる」とは未実証。

Kamimusuhi への一般化は、candidate organ/model/config activation が失敗した際、pointer や config revision を戻すだけでなく、**旧 generation の resource graph / tool handles / sessions / adapters が実際に serviceable であることを rollback completion condition にする**という提案。

### (3) 関係する Kamimusuhi subsystem

- Mutation / Activation Gate
- cognitive body / external organ lifecycle
- K-Edge / K-Core / K-Deep provider swap
- Continuity Kernel generation management
- rollback / recovery receipt

### (4) 借りられる設計・実装アイデア

```text
ROLLBACK_STARTED
  -> canonical activation pointer restored
  -> old-generation resources revalidated
  -> routing table rebound
  -> session/tool handles smoke-tested
  -> outstanding obligations reconciled
  -> ROLLBACK_OPERATIONALLY_CLOSED
```

`replacement_not_applied` のような control-plane message だけでは成功扱いしない。

### (5) Kamimusuhi との差分

既存 Kamimusuhi docs は activation lineage と predecessor を重視している。今回の差分は **predecessor record が残っていることと predecessor body がまだ動くことは別**という点。

### (6) 次に検証すべきこと

**`GenerationRollbackClosureBench-v0`** — P0

- candidate model activation failure
- plugin/tool startup failure
- cleanup timeout
- one organ only partially swapped
- old generation resource accidentally retired
- in-flight request during rollback
- rollback後の first real turn / tool call / memory read / external delivery

評価:

- old-generation serviceability
- dangling-handle count = 0
- mixed-generation route = 0
- duplicate effect = 0
- restart required rate

### (7) 重要度

**A+** — self-modification / cognitive-body replacement を行う Kamimusuhi では「戻せる」は最重要 safety property。rollback の表示と operational truth の分離は Activation Gate に直接刺さる。

## 5.3 Tool / model orchestration — MCP initialize は OAuth commit witness ではない

**Primary:** NousResearch/Hermes Agent issue #118323, opened 2026-09-22 00:52 JST  
https://github.com/NousResearch/hermes-agent/issues/118323

### (1) 何が実証済みか

Hermes の dashboard OAuth helper `probe_with_rollback` は既存 token を先に削除し、probe 中に `details["initialized"]` が true なら rollback を skip する。しかし `initialized` は MCP `initialize` result が得られたことを示すだけで、browser grant / authorization code / token file write の完了を意味しない。

probe が initialize 後・token write 前に例外になると、旧 token は消えたまま `_commit()` が進み得る。reporter は headless gateway で token file 消失を実際に観測し、full browser PKCE login が必要になった。

### (2) 何が提案・推測段階か

修正候補として「new token file が存在しない限り rollback」「newer generation token がある場合のみ restore を避ける」が示されているが、issue は open。

### (3) 関係する Kamimusuhi subsystem

- Cognitive Action Router
- external tool / MCP organ
- credential store
- activation transaction
- authority receipt / provenance

### (4) 借りられる設計・実装アイデア

**protocol progress state** と **authorization commit state** を別型にする。

```text
TRANSPORT_CONNECTED
PROTOCOL_INITIALIZED
AUTH_FLOW_STARTED
CREDENTIAL_MATERIALIZED
CREDENTIAL_VERIFIED
AUTH_COMMITTED
TOOL_DISCOVERY_COMPLETE
```

旧 credential の destructive replacement は `AUTH_COMMITTED` の durable witness が得られるまで確定しない。

### (5) Kamimusuhi との差分

Kamimusuhi は external intelligence / tools を自己から分離しているが、tool organ の credential lifecycle は architecture の中心記述より実装寄り。今回の finding は `INV-012/014` の **execution/authority state machine** を credential acquisition にまで延長する材料。

### (6) 次に検証すべきこと

**`AuthorizationCommitWitnessBench-v0`** — P0

- initialize success + user cancels PKCE
- initialize success + token write failure
- token write success + verification failure
- concurrent refresh writes newer token
- timeout / non-interactive refusal
- old credential restore race

必須 invariant: **old valid credential を、新 credential commit 前に不可逆破壊しない**。

### (7) 重要度

**A** — tool organ の「接続できた」と「権限が確立した」を混同すると、能力が増えないだけでなく既存能力を失う。

## 5.4 Tool/model orchestration — requested route と executed route の receipt を分ける

**Primary:** NousResearch/Hermes Agent issue #118254, opened 2026-09-21 23:41 JST  
https://github.com/NousResearch/hermes-agent/issues/118254

### (1) 何が実証済みか

Hermes の OpenAI-compatible `/v1/chat/completions` が request の `model` field を受け取り、response にその文字列を echo する一方、実際の session は gateway default model/provider で実行される事例が再現されている。client は response body を見れば requested model が通ったように見えるが、server log の resolved route は別modelだった。

reporter はこの挙動により、background traffic を安価な model へ pin したつもりの client-side cost control を二度「verified」と判断した後に、実際には default expensive route が使われ続けていたと述べている。

### (2) 何が提案・推測段階か

fix は「model field を本当に honor」「unsupported value を reject」「response には resolved model を返す」のいずれかが提案段階。

### (3) 関係する Kamimusuhi subsystem

- Cognitive Action Router
- K-Edge / K-Core / K-Deep route selection
- Cognitive Budget
- capability / cost accounting
- external-model provenance

### (4) 借りられる設計・実装アイデア

request intent と execution receipt を別々に残す。

```text
requested_route = {...}
resolved_route = {
  provider,
  endpoint,
  protocol,
  model_revision,
  capability_profile,
  pricing_profile,
  route_generation
}
execution_receipt = hash(resolved_route, request_id, start/end evidence)
```

UI / API は requested value を success proof として echo しない。

### (5) Kamimusuhi との差分

2026-09-20 の `RouteBoundCapabilityMetadataBench-v0` は「同じ model slug でも route が違えば capability metadata が違う」問題だった。今回はさらに手前で、**route selection 自体の実行真実が client-visible response と食い違う**。

### (6) 次に検証すべきこと

**`ResolvedCognitionRouteReceiptBench-v0`** — P0

- requested model == resolved model
- alias / fallback
- provider failover
- budget-triggered downgrade
- unavailable model reject
- stream retry with different model
- client response / usage / cost / audit receipt の一致

### (7) 重要度

**A** — Kamimusuhi は model/tool を「資源」として使い分けるため、どの認知器官が実際に働いたかが偽装・誤表示されると budget / calibration / provenance 全部が壊れる。

## 5.5 Theory of Mind / social cognition / active evidence acquisition — RAVEL

**Primary:** Qian, Zhang & Wang, *What Should We Ask Next? Retrieval-Aware Question Learning under Partial Evidence*, arXiv:2609.21924  
https://arxiv.org/abs/2609.21924

### (1) 何が実証済みか

interactive person re-identification を「partial evidence のもとで次に何を質問すべきか」という sequential information-acquisition problem として扱う。RAVEL は current Top-4 candidate identities を観測し、question-answer-retrieval loop 全体の rank feedback で question policy を online RL する。Interactive-PEDES では5 interaction rounds を通じて retrieval performance が漸進的に改善し、難しい query ほど localized open-ended attributes に質問 budget を寄せる挙動が報告されている。

### (2) 何が提案・推測段階か

これは person re-ID benchmark 上の結果であり、一般会話の clarification、Theory of Mind、relationship understanding が改善することは未実証。

### (3) 関係する Kamimusuhi subsystem

- Person Model
- Common Ground State
- Relationship Memory
- uncertainty-aware dialogue
- active evidence acquisition
- K-Core clarification policy

### (4) 借りられる設計・実装アイデア

「不確かだから質問する」だけでなく、候補仮説集合に対する **expected evidence gain / rank reduction** で question を選ぶ。

```text
belief over person/state hypotheses
  -> candidate clarification questions
  -> expected evidence gain / cost
  -> ask one
  -> update belief + provenance
```

### (5) Kamimusuhi との差分

既収載の `EvidenceSeekingViewControlBench-v0` はどの camera/view を取りに行くか、`EvidenceCostEscalationPolicyBench-v0` は追加 sensing / human question を行うべきかを扱う。RAVEL の新規性は **「質問する」と決めた後、何を聞くと downstream identification が最も進むか**という linguistic acquisition policy。

### (6) 次に検証すべきこと

**`RetrievalAwareClarificationBench-v0`** — P1

対象:

- ambiguous nickname / relation / preference
- two plausible referents
- stale vs current preference
- relationship-specific habit
- insufficient evidence to infer intent

baseline:

- generic “詳しく教えて”
- entropy-only question
- random attribute
- expected evidence-gain question

測定:

- clarification turns
- correct referent/person-state identification
- unnecessary personal questions
- user burden
- false durable-memory write

### (7) 重要度

**A** — Kamimusuhi の social cognition を「内部で推測する能力」だけでなく、必要証拠を会話から能動取得する制御問題として扱う具体材料になる。

## 5.7 Robotics / long-horizon value — SeeQ

**Primary:** Singh et al., *SeeQ: Training Generalist Value Functions for Long-Horizon Robotic Manipulation*, arXiv:2609.22085  
https://arxiv.org/abs/2609.22085

### (1) 何が実証済みか

SeeQ は task-level sparse reward ではなく **現在 active な subtask の Q-value** を学ぶ。training では offline robot trajectory の subtask annotation を使い、deployment では model 自身が active subtask を自然言語で autoregressive に予測してから candidate action を評価する。

4つの real-world bimanual manipulation tasks で、固定 base policy の best-of-N action steering を行い、平均 success rate を **35.4% → 66.7% (1.88x)** に改善した。論文は robot-data pretraining、best-of-N backup、explicit subtask conditioning の ablation も報告する。

### (2) 何が提案・推測段階か

training 時には subtask annotation が必要。subtask boundary は recovery 中などに曖昧で、deployment 時の誤った subtask prediction は wrong local objective を最適化し得る。論文自身も、local progress が global task success と一致しない例を limitation として挙げる。

### (3) 関係する Kamimusuhi subsystem

- Physical AI / robot body
- K-Edge / K-Core
- semantic phase model
- action candidate critic
- Cognitive Budget

### (4) 借りられる設計・実装アイデア

```text
current evidence
  -> infer active semantic subtask
  -> sample candidate action chunks
  -> local-value critic
  -> execute best candidate
  -> Commitment closure / downstream guard
```

### (5) Kamimusuhi との差分

`SemanticPhaseRoutingBench-v0` は phase に応じて planner/VLA等の cognitive resource を切り替え、`SemanticCommitmentClosureBench-v0` は stage 成立を検証する。SeeQ はその間に置ける **phase-local value critic**。ただし local value を global authorization に昇格させない。

### (6) 次に検証すべきこと

**`SubtaskValueSteeringBench-v0`** — P1

比較:

- task-global critic
- phase-local critic
- phase-local + downstream consequence estimate
- commitment-gated phase-local critic

測定:

## 5.8 Multimodal perception / social cognition — listener reaction を次発話計画へ使う ReACT-TTS

**Primary:** Chu, *Listen Before You Speak: Response Planning from Listener Facial Reactions for Conversational Speech Generation*, arXiv:2609.21683  
https://arxiv.org/abs/2609.21683  
Code: https://github.com/CYJ1/ReACT-TTS_public

### (1) 何が実証済みか

ReACT-TTS は発話直前1秒の listener facial sequence を使って、次の utterance の emotion / prosody を先に計画してから speech realization する。strict dyadic MELD protocol で Temporal conditioning は Text-only より mean macro-F1 / VAD concordance を改善し、accuracy はほぼ同等。20名の speech researchers による contextual-appropriateness study では 76% が Temporal、9% が Text-only、15% が no preference を選んだ。

### (2) 何が提案・推測段階か

listener face 1秒から stable emotion / intent / relationship state を推論できるわけではない。MELD由来設定と prosody planning の結果を一般 social cognition へ拡張するのは未実証。

### (3) 関係する Kamimusuhi subsystem

- multimodal perception
- K-Nerve / K-Edge social signal
- Person Model
- voice / J-series output planning
- Global Workspace

### (4) 借りられる設計・実装アイデア

listener reaction を durable trait とせず、短寿命の `response_planning_evidence` として保持し、prosody / timing / phrasing の候補選択へだけ使う。

### (5) Kamimusuhi との差分

直前 daily の RobotEQ-Video は時間変化する human state → intervention appropriateness の広い評価。ReACT-TTS はより局所的で、**相手の直前 reaction を自分の次の utterance realization に閉ループで戻す**点が差分。

### (6) 次に検証すべきこと

**`ListenerReactionResponsePlanningBench-v0`** — P1

- correct reaction vs shuffled reaction
- face unavailable
- culturally ambiguous reaction
- delayed reaction
- prosody-only vs wording-only vs both
- Persona Core / durable relationship memory へ誤書込みしないこと

### (7) 重要度

**B** — social embodiment の具体的 low-latency loop として有望だが、研究の射程は response style planning に限定される。

## 5.9 HCI / research infrastructure — conversational system を executable study artifact にする Gricea

**Primary:** Sharma et al., *Gricea: An Open Science Platform for Conversational AI Research*, arXiv:2609.22039  
https://arxiv.org/abs/2609.22039

### (1) 何が実証済みか

Gricea は conversational AI study を、study procedure・participant-facing system・conversation task behavior を含む configurable / deployable artifact として表現する。著者らは CUI 2026 の eligible papers の configuration を **93%** 再構成できた一方、**96%** の論文で faithful replication を妨げる missing information を検出したと報告する。user study では研究者・実務家が runnable study を構築できた。

### (2) 何が提案・推測段階か

Gricea を使えば longitudinal companion / identity-continuity study 自体の妥当性が保証されるわけではない。platform-level reproducibility の実証。

### (3) 関係する Kamimusuhi subsystem

- HCI evaluation
- social/persona longitudinal experiments
- model / prompt / tool / memory ablation
- benchmark provenance

### (4) 借りられる設計・実装アイデア

Kamimusuhi experiment を論文本文だけでなく、以下を束ねる **executable study artifact** として保存する。

```text
model/provider revision
persona revision
memory schema + seed state
tool manifest
conversation policy
participant UI
study procedure
randomization
measurement code
analysis revision
```

### (5) Kamimusuhi との差分

Gricea は一般 CAI research platform。Kamimusuhi では identity lineage / durable memory / model swap / session continuity が追加の study state になる。

### (6) 次に検証すべきこと

**`ConversationalStudyArtifactReproBench-v0`** — P2

過去の Persona / memory / social benchmark を clean environment で再構成し、結果再現率と missing-config rate を測る。

### (7) 重要度

**B** — cognition mechanism そのものではないが、Kamimusuhi の長期的研究を「再現できるもの」にする infrastructure として価値が高い。

## 12. 今回の圧縮結論

今回の一文は次。

> **「観測された状態」と「その状態が意味する権限・identity・実行事実・rollback成功」を同一視しない。さらに、その観測値を作るセンサー自身が lifecycle を跨いで正しいかまで疑う。**

Kamimusuhi では既に canonical evidence / provenance / authority / body state を分離している。今回の差分は、その思想を一段下へ降ろし、**process birth witness、plugin generation rollback、OAuth commit、model-route response、utterance publication**の各実装境界でも同じ discipline を要求することにある。
