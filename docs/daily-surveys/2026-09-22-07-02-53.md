# 5. 分野別項目

## 5.1 Tool/model orchestration・自己改善 — verified progress がある時だけ communication がsearchを“合成”できる

**Primary:** Park et al., *Scaling Discovery through Test-Time Communication*, arXiv:2609.21032  
https://arxiv.org/abs/2609.21032

### (1) 何が実証済みか

複数LLM agentがpredefined roleなしでshared directoryを介して成果物を共有する test-time communication を評価した。ARC-AGI-3では、`k` communicating agents の `team@k` が **4k independent agents** に相当するsuccess rateを示し、advantageはkとともに増えた。研究型taskにも転移し、polyomino packingでは既知bestを更新、MNIST classifier compressionでは4 agentsが **1,957-byte / 99.4% accuracy** のclassifierを作ったと報告している。

重要なのはnegative conditionも示していること。**computeが小さい場合、またはclear progress measureがない場合は independent agents がcommunicationを上回り得る**。

### (2) 何が提案・推測段階か

この結果を「multi-agentはsingle/independentより常に強い」と一般化できない。paperの利点は、途中成果がtransferableで、比較可能なprogress signalがあり、coordination taxを払えるcomputeがあるtaskに依存する。

Kamimusuhiでは、agent数を増やすruleではなく、次をrouting featureにする仮説が妥当。

```text
progress_verifiability
artifact_transferability
branch_independence
coordination_cost
remaining_compute
shared_state_corruption_risk
```

### (3) 関係する Kamimusuhi subsystem

- K-Deep research / planning
- Cognitive Action Router
- Global Workspace / shared artifact space
- Cognitive Budget
- background research workers
- self-improvement experiment generation

### (4) 借りられる設計・実装アイデア

- intermediate artifactを共有するだけでなく、**progress verifier付きartifact**としてpublishする。
- verifierのないtaskはまず independent best-of-k をbaselineにする。
- shared workspaceへのwriteはsource agent、evidence、score/versionを保持する。
- communication topology選択もCognitive Budgetの一部にする。

### (5) Kamimusuhiとの差分

Kamimusuhiは複数独立人格のteamを作ることが主目的ではなく、一個体のK-Deep/background cognitionを並列化する。したがってshared directoryを「他者の会話空間」ではなく、**attributed/rebuildable cognitive workspace**として扱い、canonical self-stateへ直接昇格させない必要がある。

また2026-09-20 dailyの「dense sequential workflowではmulti-agentが不利」というfindingと矛盾しない。今回の差分は、**長い探索で再利用可能なbreakthroughをobjective verifierが拾える時にはcommunicationのcompound gainが出る**という追加条件。

### (6) 次に検証すべきこと

**`VerifiedProgressCommunicationBench-v0`** — P1

同一total computeで以下を比較する。

1. independent best-of-k
2. shared-directory team
3. verifier-gated shared-directory team
4. noisy-verifier team

Kamimusuhi向けtask:

- repo issue diagnosis
- long-horizon literature synthesis
- novllm experiment design
- code optimization

指標:

- final success / quality
- unique useful intermediate artifacts
- coordination tokens
- corrupted/incorrect shared artifacts adopted率
- wall time / cost
- verifier false-positive時のherding増幅

### (7) 重要度

**A** — K-Deepの「いつ並列agentを会話させるべきか」に、task dependencyだけでなく **progress verifiability** を追加する実証的根拠。

## 5.2 Distributed cognition — semantic sparse communication graph

**Primary:** Tambwekar et al., *Proxifield: Decentralized Multi-Agent Communication through Semantic Proximity*, arXiv:2609.20889  
https://arxiv.org/abs/2609.20889

### (1) 何が実証済みか

Proxifieldはtrainingやcentral plannerなしで、各roundに以下4 signalからsparse communication graphを作る。

- direct address
- information needs
- plan alignment
- information complementarity

Drone Search and Rescue と HiddenBenchでStar / Shared Contextと比較し、最大model scaleでは両domainでbaselineを上回った。team size増大時、Starに対するtask reward advantageは **N=5で5.4% → N=25で53.0% → N=50で59.5%**。permanent agent failureの最重条件でもno-failure rewardの73.6%を保持し、Shared Context 58.3%、Star 38.8%と報告している。

### (2) 何が提案・推測段階か

「semantic routingならKamimusuhiでも同じgain」という保証はない。評価はmulti-agent benchmarkであり、一個体内部のcognitive organ間routing、異種model、privacy/authority制約は別問題。

### (3) 関係する Kamimusuhi subsystem

- Cognitive Action Router
- Global Workspace
- K-Core / K-Deep parallel cognition
- background processors
- distributed embodiment
- delegated cognition observability

### (4) 借りられる設計・実装アイデア

全subagentへ全contextをbroadcastせず、workspace item / requestごとに以下のrouting scoreを持つ。

```text
needs_this_information
can_answer_this_need
plan_overlap
novel_complementarity
latency_cost
privacy_boundary
authority_class
```

semantic proximityだけでなくKamimusuhi固有の**provenance / privacy / authority**をhard constraintとして上に置く。

### (5) Kamimusuhiとの差分

Proxifieldのnodeは比較的対等なagents。KamimusuhiではPersona Core、memory service、Jev-class semantic telemetry、specialist local model、frontier modelは同格ではない。**semantic relevanceが高いことはauthorityを得ることではない**。

### (6) 次に検証すべきこと

**`SemanticSparseCognitionRoutingBench-v0`** — P1

- all-to-all broadcast
- central router
- Proxifield-like semantic sparse graph
- semantic + provenance/authority constrained sparse graph

を10/25/50 worker相当で比較する。

指標:

- useful result recall
- redundant context/token transfer
- latency
- one worker failure時performance
- cross-domain information leak = 0
- wrong-authority adoption = 0

### (7) 重要度

**A** — Kamimusuhiの「分散しているが一個体」という構成で、Global Workspaceを巨大broadcast busにしない具体的比較対象になる。

## 5.3 Cognitive Budget / scheduler — quotaの意味スコープはqueue partitionを跨ぐ

**Primary:** NousResearch/Hermes Agent issue #118499, opened 2026-09-22 05:23 JST  
https://github.com/NousResearch/hermes-agent/issues/118499

### (1) 何が実証済みか

`kanban.max_in_progress_per_profile` が「profile単位の上限」という意味なのに、dispatcherは現在board内のrunning countだけで判定していた。cap=3、board Aにprofile `alice` のrunning 3件がある状態でも、board Bの4件目がspawnするreproが提示されている。N boardsならprofileは理論上 `N * cap` を持て、shared global capを一profileが食い潰し他boardをstarveさせ得る。

### (2) 何が提案・推測段階か

提案fixは全boardの`running_by_assignee()`を合算すること。Kamimusuhiへ一般化すると、quota/rate/cognitive budgetは「どのtable/queueで実装したか」ではなく、**budget ownerのsemantic scope**でaggregateすべきという設計仮説になる。

### (3) 関係する Kamimusuhi subsystem

- Cognitive Budget
- K-Deep/background worker scheduler
- per-person / per-task fairness
- digital interoception / resource pressure
- multi-surface distributed body

### (4) 借りられる設計・実装アイデア

```text
BudgetLease {
  owner_principal,
  budget_class,
  amount,
  scope_generation,
  active_across_partitions,
  expires_at,
}
```

queueごとに独立countせず、budget ownerが同じならcross-queue / cross-board / cross-surfaceでaggregateする。

### (5) Kamimusuhiとの差分

KamimusuhiはCognitive Budgetをarchitecture上明示しているが、実装時にK-Core queue、K-Deep queue、sleep queueなど別storageへ分割すると同じbugを作れる。既収載のcgroup measurement-scope問題はresource sensorのscope mismatch、今回は**logical principal fairnessのscope mismatch**である。

### (6) 次に検証すべきこと

**`PrincipalWideCognitiveBudgetBench-v0`** — P1

- 1/2/8 queues
- 1 profileが全queueへjob投入
- critical vs best-effort class
- queue restart / lease expiration
- K-Core→K-Deep migration

成功条件:

- principal cap超過 = 0
- unrelated principal starvation = 0
- critical class preemption correctness
- aggregate usageとphysical usageの誤差bounded

### (7) 重要度

**B** — 原則自体は分散resource managementの定石だが、KamimusuhiのCognitive Budgetをmulti-queue化する際の具体的fallacyとして価値が高い。

## 5.4 Multimodal perception / K-Nerve — readiness flagではなくend-to-end sensory progressを監視する

**Primary:** NousResearch/Hermes Agent issue #118552, opened 2026-09-22 06:29 JST  
https://github.com/NousResearch/hermes-agent/issues/118552

### (1) 何が実証済みか

Windows DirectSound inputで`sounddevice.InputStream.read_available`が音声入力中でも0のままになる環境が報告された。Hermesのwake-word captureは`read_available >= frame_length`までpollしてから`stream.read()`するため、UI/logは`listening`になっているのに実際にはframeがwake-word engineへ1つも届かず、無期限待ちになる。same physical deviceのWASAPI pathでは`read_available`が正常に増え、client capture pathへ切り替えるとwake-word detectionが復活した。

### (2) 何が提案・推測段階か

DirectSound全般が常に壊れるとは未実証。Kamimusuhiへの一般化は、driver/APIのready/available値を単独health witnessにせず、**raw event → preprocess → classifierまでのprogress**を観測すること。

### (3) 関係する Kamimusuhi subsystem

- K-Nerve
- audio / wake-word / sensory event bus
- K-Edge
- multimodal health monitoring
- reflex / interrupt path

### (4) 借りられる設計・実装アイデア

sensor healthを複数段に分ける。

```text
DEVICE_OPEN
STREAM_STARTED
RAW_FRAME_ADVANCING
PREPROCESS_ADVANCING
DETECTOR_ADVANCING
SEMANTIC_EVENT_ADVANCING
```

一定時間`RAW_FRAME_ADVANCING`が止まったらwarning / fallback route / sensor degradationを出す。`LISTENING`表示は最終progress witnessから導出する。

### (5) Kamimusuhiとの差分

Kamimusuhi specはmechanically observable present stateをruntime ownerから導出するが、**runtime owner自身のstatus bitが真でもdataflowが進んでいない**場合を別に扱う必要がある。前回のprocess create-time driftと同様、sensor自体のmeasurement validityを監査する話だが、今回はperception pipelineのend-to-end liveness。

### (6) 次に検証すべきこと

**`SensorProgressWitnessBench-v0`** — P1

- microphone open but zero frames
- frames arrive but preprocessing wedged
- classifier alive but timestamps frozen
- camera/LiDAR equivalent
- platform API reports stale readiness
- fallback sensor switch

指標:

- silent dead-sensor detection latency
- false alarm rate
- fallback recovery time
- stale-frame acceptance = 0

### (7) 重要度

**B** — always-on K-Nerve/Edgeでは「センサーがopenだから身体が見えている」という誤認を避ける基本fixtureになる。

## 5.5 Persistent memory / HCI — canonical resultの存在とactive projectionへの結合は別

**Primary:** NousResearch/Hermes Agent issue #118481, opened 2026-09-22 04:54 JST  
https://github.com/NousResearch/hermes-agent/issues/118481

### (1) 何が実証済みか

長期sessionでDesktopが多数のtool rowを`Result unavailable`と表示する一方、`state.db`では314 tool-call IDs中313にresult rowが存在し、empty/NULL resultは0だった。compaction carryによりtool rowsは合計1,385（約4.4 carriers/id）、28 IDsは2つのdistinct payloadを持っていた。UI placeholderはsealed partにresultがattachedされていない時に発火するため、**data lossではなくprojection/attachment gap**が強く示唆されている。

root causeはrenderer dumpがなく未確定で、result eventがfront-end partへ届かないか、paged-out transcript外のcarrierをre-resolveできていない可能性が残る。

### (2) 何が提案・推測段階か

Kamimusuhiでは`unavailable`を一状態に潰さず、少なくとも以下を分けるべきという提案。

```text
NO_CANONICAL_RESULT
CANONICAL_RESULT_PRESENT_NOT_PROJECTED
PROJECTION_AMBIGUOUS
PROJECTED
```

### (3) 関係する Kamimusuhi subsystem

- canonical evidence
- Global Workspace
- session/history compaction
- tool-result provenance
- UI / HCI
- replay / recovery

### (4) 借りられる設計・実装アイデア

- UI/workspace rowはcanonical result idへstable referenceを持つ。
- compactionでcarrierが複製されてもcanonical result identityは1つ。
- projection miss時は「結果なし」と断定せずcanonical storeをre-resolveする。
- distinct payloadが複数ある場合は自動first-matchせずambiguityを出す。

### (5) Kamimusuhiとの差分

Kamimusuhiは既に`canonical evidence > derived view`を規範化しているため、新しい哲学ではない。今回の価値は **long session + compaction + UI sealing** という具体fixtureと、canonical existence / projection attachment / ambiguityを別metricにできる点。

### (6) 次に検証すべきこと

**`CanonicalResultProjectionBench-v0`** — P2

- 10k+ turn history
- repeated compaction
- paged-out tool carriers
- late result arrival
- same call id with duplicate identical carriers
- same id with conflicting payloads
- restart / rehydrate

成功条件:

- canonical presentを`missing`表示しない
- ambiguousを誤って1件へ確定しない
- UI projection再構築がcanonical recordを書き換えない

### (7) 重要度

**B** — invariantの新規追加ではないが、Kamimusuhiのderived-view philosophyを長期UIへ落とす良い実障害fixture。

## 5.6 Persona Core / social cognition — personality SFTを“人格獲得”とみなさないnegative evidence

**Primary:** Krabbe & Shi, *Do Personality-Tuned LLMs Make Better Social Agents?*, arXiv:2609.21857  
https://arxiv.org/abs/2609.21857

### (1) 何が実証済みか

Qwen2.5-7B-InstructとMinistral-8B-Instructを、personality-labelled social-media posts + dialoguesでfine-tuneし、複数social interaction scenariosを3 independent LLM judgesで評価した。著者らは、**fine-tuned modelsが各baselineよりdifferent personalitiesのrole-playに優れなかった**と報告する。Qwenではlinguistic diversity改善が見られたが、personality fidelity全体の優位には繋がらなかった。

同時にinter-rater agreementが低く、結果解釈のconfidence自体が限定されると明記されている。

### (2) 何が提案・推測段階か

「persona fine-tuningは無意味」とは言えない。training data quality/domain alignment、trait representation、評価器の信頼性、longitudinal consistencyが未解決。

Kamimusuhiへの教訓は、Persona Coreをpersonality-labelled SFTしただけで**durable personality / identity continuityを獲得したと見なさない**こと。

### (3) 関係する Kamimusuhi subsystem

- Persona Core training
- model migration continuity suite
- social cognition
- self-model expression
- relationship behavior

### (4) 借りられる設計・実装アイデア

Persona Core experimentでは、単発judge scoreだけでなく以下を分離する。

```text
trait controllability
cross-scenario consistency
longitudinal consistency
relationship-specific behavior
linguistic style diversity
value/decision consistency
judge agreement
```

### (5) Kamimusuhiとの差分

このpaperはrole-playing/social simulationのpersonalityを扱う。Kamimusuhiのpersonaは**weights + persistent self state + autobiography + relationship history + current regulatory state**で成立するため、trait imitationの上手さだけをidentity qualityにしない。

### (6) 次に検証すべきこと

**`PersonaWeightingVsStateBench-v0`** — P1

同一base modelで:

1. prompt/persona-state only
2. personality SFT only
3. SFT + persistent self state
4. SFT + self/relationship memory

をmulti-session scenarioで比較する。

指標:

- trait fidelity
- value drift
- autobiographical interpretation consistency
- relationship-specific adaptation
- judge agreement + deterministic behavioral probes

### (7) 重要度

**B** — J-series/Persona Core学習を進めるKamimusuhiに対し、「人格データでSFTした = 人格が強くなる」という素朴仮説への有用なnegative evidence。

## 5.7 Multimodal embodiment / HCI — daily recalibrationなしのsilent-speech sensor

**Primary:** Xu et al., *AESSI: An Around-Ear Silent Speech Interface for Cross-Day Online Reuse without Test-Day Calibration*, arXiv:2609.21436  
https://arxiv.org/abs/2609.21436

### (1) 何が実証済みか

around-ear electrophysiological silent-speech interfaceで、masked-context representation pretrainingを用いて日跨ぎのsensor repositioning / physiological variabilityへのrobustnessを狙う。24 participants・44 recordings・25 Mandarin everyday sentencesで評価し、complete final recordingsをheld-outした6 participantsで **92.24% mean accuracy without test-day calibration**。最後のrecordingから少なくとも21日後の5 participants × 50 randomized online testsでも **98.0% overall accuracy**、CPU replayのmedian preprocessing + inferenceは31.70 msと報告している。

### (2) 何が提案・推測段階か

closed sentence set、participant数、特定sensor placementでの結果であり、open-vocabulary thought decodingや一般的なsilent communicationを示すものではない。Kamimusuhiの常用interfaceとしてのcomfort/privacy/long-term driftも未実証。

### (3) 関係する Kamimusuhi subsystem

- K-Edge sensory input
- multimodal perception
- private/quiet human interface
- sensor calibration / body capability model
- low-latency interaction

### (4) 借りられる設計・実装アイデア

- sensor modelを日々fine-tuneする代わりに、**cross-day invarianceをrepresentation pretrainingで作る**。
- capability receiptに`last_calibrated_at`だけでなく`cross-day validated envelope`を持つ。
- privacy-sensitive inputはlocal K-Edge inferenceを優先する。

### (5) Kamimusuhiとの差分

AESSIは人間→AIの入力器官であり、Kamimusuhi自身のidentity/memoryではない。採用しても**trusted sensor organ**であってself authorityは持たない。またsilent speech recognition結果はuser intentのcanonical confirmationと同一ではない。

### (6) 次に検証すべきこと

# 6. Fresh corroboration / 重複のため独立promotionしないが重要なもの

## 6.1 Loopjacking (`2609.21081`) — Review–Execution Artifact Identity の外部実証強化

Primary: https://arxiv.org/abs/2609.21081

paperは、人間がAを承認したのに実装がmaterially differentなBを実行できるfailureを **Loopjacking** と命名し、representation mismatchとpost-approval state substitutionを分ける。post-approval substitutionをAgno AgentOSの7 releases（3.0.9まで）とconditional in-memory LangGraph Agent Server compositionの12 versions（0.14.0まで）で再現し、OpenClaw 2026.2.23でrepresentation mismatchを再現。OpenClaw 2026.2.24ではreject、OpenAI Agents SDK 0.22.0/0.22.2はserialized continuationによりmutated operationを拒否するnegative controlになった。

Kamimusuhiでは既に2026-09-21 13:01 blind-spotで **`reviewed rendering != executable identity`** をA+収載済み。したがって新規原則にはしない。ただしbench fixtureへAgno/LangGraph/OpenAI Agents SDK型のcross-frameworkケースを追加する価値が高い。

## 6.2 Hermes #118538 — ambient profile scope消失によるtool policy全拒否

Primary: https://github.com/NousResearch/hermes-agent/issues/118538

multiplex gatewayでOMH `pre_tool_call`がtool-dispatch path上のactive profile scopeを失い、全toolをfail-closedで拒否し、pure LLM responseだけが残るrepro。これは2026-09-16 dailyの **principal/profile propagation across subprocess/thread/RPC** のfresh corroboration。

追加fixtureとしては、policy hookをambient `contextvar`だけへ依存させず、owner/profile scopeをexplicit argument/capabilityとして渡すこと、そして`UNKNOWN_SCOPE`と`POLICY_DENIED`を別状態にすることが有用。

## 6.3 OpenClaw #155227 — enabled / configured / applied / ready は別状態

Primary: https://github.com/openclaw/openclaw/issues/155227

外部pluginのhook permissionがupgrade後にblockedでもgateway/plugin自体はhealthyに見える観測を背景に、host-owned structured diagnosticと`enabled / blocked / saved / applying / applied / failed`の区別を提案している。issue自身が**exploratory PRD / no implementation commitment**と明記しているため、新規実装実証としては数えない。

既存 Kamimusuhi の readiness/diagnostic parity、authorization commit witness、tri-state capability evidenceを補強するwatch item。
