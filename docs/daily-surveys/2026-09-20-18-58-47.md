### 2.1 A+ — 非同期 recovery 完了と foreground ownership を分離する

**Primary fresh evidence:** NousResearch/hermes-agent PR #117131  
https://github.com/NousResearch/hermes-agent/pull/117131  
created: 2026-09-20 18:38 JST 頃 / survey時点 open

**(1) 何が実証済みか**  
Desktopのchat Bから correction/steer を送り、runtimeが stale で `session not found` になった後に `session.resume(B)` を待たせ、その間にユーザーが chat Aへ移動するreproductionが作られている。baseではBのrecovery完了時に画面がBへ戻り、次の明示sendもBへ保存された。candidateではforegroundはAのまま、Bのbackground correctionはBに帰属したまま継続する。PRは32 recovery cases、renderer UI 8,413 tests / 912 files、native E2Eでsidebar・RPC destination・SQLite ownerまで検査したと報告している。

**(2) 何が提案・推測段階か**  
PRは未merge。renderer中心の修正で、Python backendやmacOS/Windows native全面検証は未実施。Kamimusuhiのmulti-device / robot / remote-model topologyで同じ競合が存在するかは未検証。

**(3) 関係するKamimusuhiサブシステム**  
Continuity Kernel、Global Workspace、surface/session routing、K-Edge↔K-Core distributed execution、background cognition、relationship/chat episode ownership。

**(4) 借りられる設計・実装アイデア**  
非同期操作を開始する前に `source_principal / surface / session / episode / runtime / route / generation` をcaptureし、await後のrecovery resultはそのowner scopeへだけ帰属させる。foregroundへruntime/viewをpublishしてよいのは、完了時にもcurrent foregroundがcaptured ownerと一致する場合だけにする。background work自体は不必要にcancelしない。

**(5) Kamimusuhiとの差分**  
HermesはDesktop chat routingの問題。Kamimusuhiでは同一原則を、voice stream、robot body、remote tool、distributed sensor、external LLM、sleep/background taskにも一般化する必要がある。特に「計算結果をどこへ返すか」と「現在の自己/身体のforeground ownerを誰が変更できるか」は別authorityにする。

**(6) 次に検証すべきこと**  
**`AsyncRecoveryOwnerBindingBench-v0`**: Bのrecoveryを開始→Aへforeground切替→B完了、を基本fixtureにし、network partition、restart、hidden steer、lineage alias、remote-model retryを加える。Bのeffect/resultはBへ届くが、Aのforeground/runtime/next-write ownerは変わらないことを検証する。

**(7) 重要度:** **A+**

**Kamimusuhi invariant候補:** `accepted background operation != authority to capture foreground after await`。

### 2.2 A — sender名ではなく structured author provenance を end-to-end に持つ

**Primary fresh evidence:** NousResearch/hermes-agent PR #117132  
https://github.com/NousResearch/hermes-agent/pull/117132  
created: 2026-09-20 18:39 JST 頃 / survey時点 open

**(1) 実証済み**  
PRはper-turn sender identityとして `id / name / is_bot / platform` をgateway turn、API proxy、Hindsight memoryまでstructured fieldとして運ぶ変更を実装し、325 focused tests passedと報告している。背景にはshared sessionで複数senderが存在すると、display-name prefixをprompt textから再parseする方式ではproxyやmemory retentionで誤帰属し得る問題がある。

**(2) 提案・推測段階**  
PRは未mergeで、open時点ではfull repository suiteはまだ完了していない。Kamimusuhiで必要な「人」「アカウント」「端末」「bot」「delegated agent」「speaker」と「authorization principal」の全分離まではこのPRのscope外。

**(3) 関係サブシステム**  
Relationship Memory、Theory of Mind/common ground、social cognition、Continuity Kernel provenance、multi-user / multi-bot surfaces、memory extraction。

**(4) 借りられる設計**  
message/eventに `AuthorRef` を持たせ、rendered prefixや自然言語署名からidentityを復元しない。少なくとも `principal_id`, `actor_id`, `actor_kind`, `platform`, `source_message_id`, `surface/session` をtyped metadataとして運び、memory writeにも同じprovenanceを残す。

**(5) Kamimusuhiとの差分**  
Kamimusuhiでは「誰が発話したか」と「誰の権限でactionが許可されたか」と「誰についてのrelationship memoryか」を別fieldにする必要がある。botがuserの代行をしている場合など、author=principalとは限らない。

**(6) 次に検証**  
**`StructuredAuthorProvenanceBench-v0`**: 同名の人/bot、表示名変更、shared group chat、proxy relay、bot代理発話、replay、memory extractionを混ぜ、どの経路でも誤ったperson/relationshipへ記憶が入らないことを検証する。

**(7) 重要度:** **A**

**Invariant候補:** `rendered sender label != authoritative author identity`。

### 2.3 A — approval UI は summary ではなく exact semantic mutation を見せる

**Primary fresh evidence:** NousResearch/hermes-agent PR #117134  
https://github.com/NousResearch/hermes-agent/pull/117134  
created: 2026-09-20 18:40 JST 頃 / survey時点 open

**(1) 実証済み**  
長いmemory replacementがpending summaryでは旧文中心に短縮され、意味のあるnew tailが見えない問題に対し、`/memory diff <id>` でcurrent saved entriesからread-only projectionを生成し、実際にmatchしたentry、projected content、advisory sizeを確認できる実装が提示された。stale/malformed proposalでは誤解を招くpartial diffではなくerrorとcomplete original payloadを表示する。focused regressionはbase RED、branch 7 pass。隣接runは76 pass、Windowsの既知permission failure 2件、1 skipと報告。

**(2) 提案・推測段階**  
未merge。live messaging transportの実証はなく、PR自身も「projectionがapproval check通過を保証するものではない」と明記している。

**(3) 関係サブシステム**  
Mutation/Activation Gate、Persistent Self State、Relationship Memory、procedural memory、human review HCI、proposal receipts。

**(4) 借りられる設計**  
review receiptを短いsummaryだけにbindせず、`candidate payload + predecessor/base state + expanded semantic effect/diff`へhash-bindする。previewは便宜表示、approval authorityはfull candidate/effectに対して発行する。stale base時は「再計算された別effect」を自動承認扱いしない。

**(5) Kamimusuhiとの差分**  
Hermesはnative memory proposal中心。Kamimusuhiではpersona、relationship、tool policy、body capability、canonical self-stateなど複数domainにまたがるmutationがあり、semantic diffの型がもっと多い。

**(6) 次に検証**  
**`ProposalReviewCompletenessBench-v0`**: long-tail hiding、substring selector拡張、stale predecessor、multi-op reorder、cross-domain proposalを作り、「reviewした表示」と「実際にactivateされるeffect」がbit/semanticに一致しない限りactivationを拒否する。

**(7) 重要度:** **A**

**Invariant候補:** `reviewed summary != reviewed mutation`。

### 2.4 A — partial observabilityでは「記憶」と「現在belief」を分ける

**Primary paper:** Kumar et al., *Towards a Belief-Based World Model for LLM Agents*, arXiv:2609.00455  
https://arxiv.org/abs/2609.00455  
code: https://github.com/skumar-ml/belief-world-models

**(1) 実証済み**  
論文はsimulation-only world modelとは別に、現在のlatent stateに対するbeliefを直接queryできるinterfaceを提案。ALFWorldでLlama-3.1-8B ReActはSR@1 29.9→Belief 43.3→Belief+simulation(BB-WM) 62.9、Qwen3-14B ReActは76.1→90.3→91.0。memory-only ablationよりbelief版が上回るケースも示す。ScienceWorldでもLlama/Qwenでperformance・efficiency改善が報告される。

**(2) 提案・推測段階**  
著者は意図的にscalable learned belief modelの問題を解いておらず、text environmentでstate space・prior/updateをhand-specifyしてbelief access自体の価値を分離検証している。Sonnetでは性能差が小さい。実世界センサのuncertaintyやopen-world belief learningは未実証。

**(3) 関係サブシステム**  
Global Workspace、world/self model、K-Core/K-Deep planning、active perception、multimodal evidence integration、episodic memory。

**(4) 借りられる設計**  
canonical evidenceとは別に、rebuildableな `BeliefState` を持つ。`known / unknown / probability / last-evidence / contradiction`をqueryできるinterfaceを作り、future simulationとcurrent uncertaintyのqueryを別APIにする。情報獲得目的のepistemic actionをfirst-classにする。

**(5) Kamimusuhiとの差分**  
Kamimusuhiは既にcanonical evidenceとcurrent interpretationを分ける方針を持つため、beliefは新しい「真実store」ではなくderived projectionとして実装すべき。relationship/self-modelでも同様に、推測をautobiographical factへ昇格させない。

**(6) 次に検証**  
**`BeliefStateInterfaceBench-v0`**: history-only / deterministic state summary / belief-only / simulation-only / belief+simulationを比較し、task successだけでなく不要探索、epistemic action efficiency、false confidence、stale-belief recovery、sensor contradictionを測る。

**(7) 重要度:** **A**

**Invariant候補:** `remembered observations != represented uncertainty about current state`。

### 2.5 B+ — selective persistent memoryはfull historyより良い場合がある

**Primary source:** Apple Machine Learning Research, *Shared Selective Persistent Memory for Agentic LLM Systems* (EMNLP 2026)  
https://machinelearning.apple.com/research/shared-selective-persistent-memory

**(1) 実証済み**  
Appleはtask specifications、data schemas、tool configurations、output constraints等の再利用可能contextを選択保存し、session-specific reasoning tracesは残さないshared selective memoryを、git-versioned collaborative workspaceで評価している。公式研究ページは3 enterprise deployment scenariosでtask completion 96%、no-memory 79%、full-history 71%を報告し、4 public datasetsでもreplicationを行ったとしている。full-history persistenceがstale reasoningに引かれて性能を落とす例も報告する。

**(2) 提案・推測段階**  
enterprise artifact-generation settingの結果であり、人格・relationship continuityやopen-world autonomous agentの長期記憶へそのまま一般化できない。何を「discardable reasoning」とみなせるかはKamimusuhiではより慎重に決める必要がある。

**(3) 関係サブシステム**  
Persistent Memory、procedural/tool configuration memory、Global Workspace、team/shared memory、access control。

**(4) 借りられる設計**  
canonical raw evidenceを別系統に保持しつつ、workspaceには再利用価値の高いtyped selective memoryだけを投影する。shared memoryはRBAC付きで、session reasoning traceはcanonical relationship/autobiographical factへ自動昇格させない。

**(5) Kamimusuhiとの差分**  
Appleのshared workspace memoryはcollaborative productivityが目的。Kamimusuhiのcontinuity-bearing autobiographical stateは単なるworkspace optimizationではないため、削除・共有・移譲のauthorityをさらに強く分離する必要がある。

**(6) 次に検証**  
**`SelectivePersistentMemoryBench-v0`**: no-memory / full transcript / selective typed memory / selective+raw-evidence fallbackを長期taskで比較し、task quality、token、stale-trace contamination、critical-memory miss、cross-user leakageを測る。

**(7) 重要度:** **B+**

### 2.6 B+ — real-world VLA online RLでは absolute value よりreference-anchored improvementを使う

**Primary paper:** Su et al., *VLA-Precision: Asymmetric Co-Bootstrapping for Efficient Real-World Online RL of Vision-Language-Action Models*, arXiv:2609.04355  
https://arxiv.org/abs/2609.04355

**(1) 実証済み**  
ACoBはearly intervention-guided behavioral learning、global return propagation、local preference rankingを組み合わせ、frozen/reference actionに対するrelative advantageでpolicy driftを抑える。9 high-precision chemistry tasks / 4 robot embodimentsで平均98.3% success、平均45.8 min/taskのonline training、27.6 s episodeを報告。ACoB-Streamはup to 10.9× throughput/computational efficiencyを報告する。

**(2) 提案・推測段階**  
同一研究系のprecision chemistry tasks中心で、Kamimusuhi/MOVIのopen-world mobilityや長期nonstationary environmentへの一般化は未実証。candidate policyの改善と安全なactivationは別問題。

**(3) 関係サブシステム**  
Physical AI、K-Edge/K-Core、robot policy adaptation、self-improvement、Mutation/Activation Gate。

**(4) 借りられる設計**  
online adaptationではunreliableなabsolute criticを直接最大化せず、frozen reference against relative improvement、human intervention、preference rankingを利用する。重いVLA prefixのinvariant-state reuse/streamingもruntime optimization候補になる。

**(5) Kamimusuhiとの差分**  
Kamimusuhiではlearned candidateの生成・評価・activation authorityを分ける。ACoBのreference regularizationはcandidate trainingのstability priorにはなるが、canonical body controllerへの昇格許可にはしない。

**(6) 次に検証**  
**`ReferenceAnchoredEmbodiedAdaptationBench-v0`**: nonstationary manipulation/mobility taskでabsolute-value RL、reference-relative update、intervention-gated updateを比較し、success、policy drift、rollback rate、safety violation、independent validation通過率を測る。

**(7) 重要度:** **B+**

### 2.7 B — Agent Plugins 1.0: portabilityとauthority portabilityは別

**Primary source:** GitHub Docs, *About GitHub Copilot plugins*  
https://docs.github.com/en/copilot/concepts/agents/about-plugins

**Japanese discovery source:** note 2026-09-20記事を入口に確認  
https://note.com/sane_design2026/n/nd6ecbe3ecd2b

**(1) 実証/仕様として確認済み**  
GitHub DocsではAgent Plugins 1.0をportable formatとして扱い、共通部分は `skills/` のSKILL.md群とroot `mcp.json`。agents、hooks、commands、rules、LSPなどはclient-specificで、Copilot固有要素は `com.github.copilot` 配下に置かれる。すなわち現行仕様上も「plugin全体がどのclientでも同じ意味で動く」わけではない。

**(2) 提案・推測段階**  
異なるagent runtime間でpermission、credential custody、sandbox、tool side effect、name resolutionまで意味論的にportableであることは仕様ページからは保証されない。日本語紹介記事の「Google/Amazon/Microsoft/OpenAIが共通仕様として公開」等の広い業界主張は、今回GitHub公式一次資料だけでは全面検証していないため採用しない。

**(3) 関係サブシステム**  
Tool/model orchestration、procedural skill packaging、MCP、capability registry、external cognitive extensions。

**(4) 借りられる設計**  
portable artifact (`skill semantics / MCP config`) と host-local admission (`principal / capability grant / credential / sandbox / egress policy`) を分離する。plugin importでauthorityを暗黙継承しない。

**(5) Kamimusuhiとの差分**  
Kamimusuhiではexternal tools/modelsは自己そのものではなくattributed cognitive extension。skill packageの移植性が上がっても、identity・credential・activation authorityはhost/individualごとに再bindすべき。

**(6) 次に検証**  
**`PortablePluginAuthorityTranslationBench-v0`**: 同一pluginを2つのruntimeへ導入し、異なるgrant/sandbox/secret scope/name collision下で、semantic capabilityは移植できても権限はlocal policyから再認証されることを確認する。

**(7) 重要度:** **B**

### 2.8 B — silent runtime recoveryはbody faultを消したことにはならない

**Primary fresh evidence:** NousResearch/hermes-agent PR #117140  
https://github.com/NousResearch/hermes-agent/pull/117140  
created: 2026-09-20 18:55 JST 頃 / survey時点 open

**(1) 実証済み**  
OS/Chromiumにlive rendererを外部killされた場合、従来はdesktop.logに残るだけでユーザーにはlossが見えなかった。PRはexternal `killed`をrecovery pageで明示し、ordinary crashはreload、destroyed window teardownはsilentという3-arm invariantをtestsで分けている。Electron unit tests 31 pass、macOSでmanual testを報告。

**(2) 提案・推測段階**  
Linux/Windows native検証は未実施。UI fault presentationがKamimusuhiのdistributed body health表示にそのまま適用できるわけではない。

**(3) 関係サブシステム**  
K-Edge/K-Core body health、HCI、Continuity Kernel recovery receipts、operator observability。

**(4) 借りられる設計**  
auto-recoveryしても「外部kill / OOM / expected handoff / ordinary crash」をtyped body-fault eventとして区別する。continuityが保たれた場合でもbody discontinuityは観測可能にする。

**(5) Kamimusuhiとの差分**  
Kamimusuhiは複数body/nodeを持ち得るため、faultはUI popupではなくowner-qualified health eventとして記録し、canonical identity failureとは分離する。

**(6) 次に検証**  
**`SilentBodyFaultVisibilityBench-v0`**: node process kill、OOM、network loss、planned handoffをinjectし、identity continuityは維持しつつbody-health history/diagnosticが正しく区別されるか測る。

**(7) 重要度:** **B**

## 9. 今日の結論

今回の最も重要な差分は、**非同期作業を開始したownerと、その完了時に現在foregroundを所有している対象を混同しないこと**だった。Kamimusuhiが複数身体・複数surface・background cognitionを持つほど、この境界はchat UIのbugではなくidentity continuityの基本契約になる。

同時に、社会記憶では **表示名ではなくstructured author provenance**、自己改変では **summaryではなく実際のmutation effectへのapproval**、world modelでは **記憶とbelief uncertaintyの分離** が必要になる。

圧縮すると今回は、**「終わった仕事が現在の自分を奪わない」「名前ではなく由来を持つ」「要約を承認しただけで本体を承認したことにしない」「覚えていることと、今の世界をどれだけ確信しているかを分ける」**という回である。
