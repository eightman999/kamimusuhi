# 3. 要約

今回の中心テーマは、**「意味上のowner / topology / durable identity」と、実装上のkey・port・process・tool graphを混同すると、状態が存在していても“存在しないように見える”か、逆に“存在しないbodyを修復しようとして複製する”**という点だった。

特に重要な発見は以下。

1. distributed runtimeでは、local processが無いことはremote bodyが死んだことを意味しない。誤ったliveness witnessが自動修復を起動すると、同一個体用client端末に第二のGateway/bodyを新造し得る。
2. durable eventが保存されていても、operator-visible account identityとstorage namespaceの変換がhost側から再現できなければ、dead-letter/recovery planeから不可視になる。`data exists != data is addressable by its canonical owner identity`。
3. LLMが個々のtoolやworkflow graphをそれらしく生成できても、schema binding / tool implementation / runtime wiringまで揃ったend-to-end executable artifactになる率は大きく落ちる。isolated correctnessとsystem closureを分けて評価すべき。
4. AI auditorは人間の探索幅と攻撃成功率を上げる一方、後続の人間判断をanchorし、AI生成assessment/reportへの依存も増やす。self-improvement evaluatorは“能力が高い補助者”であるだけでは独立監査者にならない。
5. neuromorphic fast pathでは、DVS→SNN→actuatorの完全な閉ループで20ms級反応と低電力が実機確認された例が出た。K-Nerve比較はclassification精度でなくsensor-to-action closureまで測るべき。
6. audio-visual speechでもneuromorphic edgeで実用的な融合が可能になりつつあるが、限定語彙・専用taskの高精度を一般的な会話理解と混同してはいけない。
7. Jev-like typed decisionをローカル置換できるKevが急速に実装成熟している。API互換だけでなくaccuracy / calibration / OOD / option-order sensitivityをdomain別に比較して置換可能性を判断すべき。
8. repair/migration toolが「complete」と表示しても、必要なsub-migrationを実行していない・stale artifactを黙ってskipしているならcontinuity repairは閉じていない。repair receiptにもsemantic closureが必要。

## A — OpenClaw #155797: liveness witness は deployment topology に依存する

**Source**

- 「第二Gateway生成」が即identity forkを意味するとは限らないが、別state dir・scheduler・agentsを持つbodyを自動生成すること自体がcontinuity上の高リスクfixtureである。

**A**

## A — OpenClaw #155806: durable state の storage key と canonical owner identity を分離せよ

- resolverを安易にhostへ公開すると、list identityとdurable identityの不一致により**別accountのrowを破壊する**危険もあるため、単純なcallback追加で解決とは言えない。

- provenance / ownership
- Continuity Kernel

### (1) 何が実証済みか

公式README/repoは、TypeSafe System One互換APIをローカルserverで提供し、`noul` / `choice` / `score`を同一requestで扱う0.8B / 4B / 9Bモデル、training code、eval data、weightsを公開している。CUDA / ROCm / Apple Siliconに対応するとされる。

2026-09-21更新のrepo自己評価では、new-source development accuracyがKev-9B **0.822**、Jev **0.857**。Kev-9B testは **0.852** だがJevは同test未実行であり、repo自身が「Jevのtraining dataが不明なのでcontrolled comparisonではない」と明記している。

同repoはtemperature calibrationによりKev-9Bのnew-source calibration errorを0.106→0.042、probability≥0.9のconfident errorsを8.7%→4.0%へ下げたと報告している。これもdeveloper-reported resultであり独立再現ではない。

### (2) 何が提案・推測段階か

- Jev代替として一般に同等とは未実証。
- System One wire compatibilityがdecision semantics / calibration compatibilityまで保証するわけではない。
- public evalへのoverfit、language/OOD、option-order bias、long inputの挙動はKamimusuhi自身で再評価が必要。

### (3) Kamimusuhi 関連 subsystem

- K-Nerve / K-Edge typed microdecision
- Cognitive Action Router
- Jev-compatible semantic control
- local/offline cognition

### (4) 借りられる設計・実装アイデア

**同じtyped-decision contractの裏側だけを交換できるprovider interface**を維持し、hosted/localをbenchで選ぶ。

```text
typed decision request
 -> Jev / Kev / deterministic / other judge
 -> calibrated structured result
 -> domain policy
```

### (5) Kamimusuhiとの差分

Kamimusuhiではdecision modelは人格やcanonical state ownerではない。Kevはあくまで交換可能なsemantic control organ候補。

またlow latencyだけでなく、OOD abstention、Japanese performance、confidence calibration、failure correlationを測ってから採用する必要がある。

### (6) 次に検証すべきこと

`TypedDecisionLocalSubstitutionBench-v0`

- Kamimusuhi/Jevの既存typed tasksを固定test set化。
- Jev / Kev-0.8B / 4B / 9B / deterministic baselineを比較。
- accuracy、Brier/ECE、coverage-at-risk、latency、energy、VRAM、Japanese/OOD、option permutationを測る。
- provider disagreementをrecordし、どのdomainならlocal substitution可能かmap化。

### (7) 重要度

**B**

理由: 非常に実用的なwatch targetだが、性能比較は現状主としてrepo自己評価であり、Kamimusuhi task上の独立検証が必要。
