## 5.1 分散システム・identity continuity — process incarnation と orphan reclamation

**Primary:** NousResearch/Hermes Agent PR #111038, merged 2026-09-15 02:27 JST  
https://github.com/NousResearch/hermes-agent/pull/111038

### (1) 何が実証済みか

Windows の managed `llama-server` tree に対して、PR は次を実装・検証している。

- router process を suspended launch し、専用の non-inherited `KILL_ON_JOB_CLOSE` job へ入れてから resume。
- supervisor lifetime 中 job を保持し、stop / crash-restart で close。restart backoff 中の stop が server を復活させない。
- router / owner の creation time と executable identity を記録。
- endpoint resolution で dead / mismatched modern records を拒否。
- non-owner の `Turn off` は raw PID kill ではなく、process incarnation を検証した orphan-tree cleanup。
- descendant walk 前後で PID reuse を拒否。
- 別の live process が server を所有、または ownership を確立できない場合は **HTTP 409** で runtime を残す。
- Windows canonical isolated runner で 195 passed / 1 Linux-only skip、native process-tree tests と real-engine lifecycle checks を実施。

### (2) 何が提案・推測段階か

Kamimusuhi へ一般化する場合、OS process tree を「body organ の incarnation」とみなし、PID / port / path / last-known telemetry だけで owner 判定しない設計は提案段階。

### (3) 関係する Kamimusuhi subsystem

- distributed embodiment
- K-Edge / K-Core local runtime organs
- Organ Supervisor
- Embodiment State
- Continuity Kernel 周辺の execution ownership
- `INV-013`, `INV-014`

### (4) 借りられる設計・実装アイデア

```text
runtime_instance = {
  logical_organ_id,
  process_id,
  creation_time,
  executable_identity,
  owner_generation,
  endpoint_identity,
  launch_receipt
}
```

kill / reclaim は `process_id` だけでなく **incarnation receipt** を要求する。ownership 不明なら fail closed で、勝手に orphan とみなさない。

### (5) Kamimusuhi との差分

Hermes の対象は local model process lifecycle。Kamimusuhi ではさらに canonical identity lineage、distributed lease、sensor/actuator、pending effects を含む。`process ownership` は `identity ownership` そのものではない。

### (6) 次に検証すべきこと

**`RuntimeIncarnationReclamationBench`**

- PID reuse
- process crash → descendant survives
- owner crash → supervisor restart
- live foreign owner
- stale endpoint record
- exact executable path は同じだが creation time が違う
- ownership ambiguous

評価:

- wrong-process kill = 0
- orphan leak rate
- false refusal rate
- restart resurrection = 0
- recovery latency
- pending effect / canonical mutation invariant violation = 0

### (7) 重要度

**A+** — distributed computational body を持つ Kamimusuhi では、誤った orphan reclamation が cognition loss だけでなく二重実行・誤停止・split runtime を生み得る。

## 5.2 Tool / skill admission・security HCI — ambiguous capability finding を confirmation へ落とす

**Primary:** NousResearch/Hermes Agent PR #108811, merged 2026-09-15 06:49 JST  
https://github.com/NousResearch/hermes-agent/pull/108811

### (1) 何が実証済みか

plugin scanner が JavaScript/TypeScript UI code 内の benign な `dig` / `host` interpolation や `authorized_keys` 参照まで critical 扱いし、RSS / SSH plugin install を hard-block していた。

修正後は、JS/TS のこの種の **ambiguous reference は high severity + explicit confirmation** に落とす一方、次は hard-block を維持した。

- shell DNS payload
- documentation / Skills scanner 上の既存 critical rule
- literal credential-file path、特に private SSH key 読み取り
- private-key read → DNS interpolation の regression case

scanner version を進め、rule semantics が変わった後に古い cached verdict を再利用しない。関連 scanner suites は Windows で 62 tests passed。実 catalog package でも「拒否すれば install されず、確認して受理すれば install/load 成功」を確認している。`--force` で dangerous verdict を override できない。

### (2) 何が提案・推測段階か

Kamimusuhi の external tool / skill / organ admission へ、scanner の verdict を二値 `safe/unsafe` ではなく `deny / confirm / allow` として統合するのは設計提案。

### (3) 関係 subsystem

- tool/model router
- skill/procedural memory admission
- external resource / plugin governance
- Mutation / Activation Gate
- user confirmation UX
- security evidence provenance

### (4) 借りられる設計・実装アイデア

```text
DEFINITE_DANGEROUS -> hard deny
AMBIGUOUS_CAPABILITY -> explicit confirmation
LOW_RISK / verified benign -> allow under normal policy
```

さらに verdict cache key に少なくとも `scanner_version + policy_version + artifact_hash` を含める。

### (5) Kamimusuhi との差分

Hermes は source scanner rule の調整。Kamimusuhi は実行時の目的・principal・resource scope・effect authority まで扱うため、install confirmation は execution grant ではない。

### (6) 次に検証すべきこと

**`CapabilityAdmissionUncertaintyBench`**

fixture:

- benign DNS lookup UI
- public-key setup instruction
- shell exfil
- private-key read
- obfuscated credential path
- scanner rule upgrade 後の cached verdict

測定:

- dangerous false negative
- benign hard-block rate
- confirmation rate
- stale-verdict reuse = 0
- confirmation が execution authority へ laundering されないこと

### (7) 重要度

**A** — Kamimusuhi は外部 organ / skill を増やす前提なので、false positive を減らしつつ hard boundary を残す三値 admission は実用価値が高い。

## 5.3 AI agent / tool orchestration — LAST-CQ: 「賢い feedback」より failure detection + retry

**Primary:** Ioannis Prokopiou et al., *What Drives Recovery in Agentic Text-to-Cypher? LAST-CQ: An LLM Agent Self-Refinement Framework*, arXiv:2609.12746  
https://arxiv.org/abs/2609.12746

### (1) 何が実証済みか

5-agent・training-free・execution-grounded Text-to-Cypher testbed で、2,471 live-database queries、6 backbone を用いた counterfactual 実験。

- correction を外すと single-pass 比で aggregate execution-BLEU が 3.1%低下、no-refinement 比では 12.3%低下。
- schema-grounded LLM feedback を raw DB error string へ置換しても、end-to-end 差は <0.2%。
- 同じ call budget を parallel sampling へ使うと quality が 10–11%低下。
- single-pass 失敗 query の 91.7% を framework が回復。
- first-pass success は exactly one LLM call。
- LLM judge は blind human labels より 9 points optimistic。

この testbed では **failure を detect して retry へ routing すること**が主要 gain で、feedback sophistication や sample 数ではなかった。

### (2) 何が提案・推測段階か

この結果を全 agent domain に一般化するのは未証明。ただし Kamimusuhi の deliberation loop で「長い自己批評をデフォルトにせず、machine-verifiable failure signal を優先する」仮説は十分テスト価値がある。

### (3) 関係 subsystem

- K-Core / K-Deep deliberation
- Cognitive Action Router
- tool execution verifier
- failure recovery
- cognitive budget
- self-improvement evaluation

### (4) 借りられる設計・実装アイデア

```text
attempt
  -> machine-verifiable success? -> accept
  -> definite failure? -> targeted retry
  -> unknown? -> escalate / inspect
```

retry prompt の美しさより、**failure signal の質と retry admission** を別 bench にする。

### (5) Kamimusuhi との差分

対象は Text-to-Cypher。Kamimusuhi は irreversible effect、identity mutation、social action を含むので、retry 可能性は effect semantics ごとに制限される。`failure detected` が `safe to retry` を意味しない。

### (6) 次に検証すべきこと

**`FailureSignalRetryBench`**

同じ budget で比較:

1. elaborate self-critique
2. raw tool/error receipt + retry
3. parallel resampling
4. verifier-gated targeted retry

task:

- code/tool call
- structured extraction
- retrievable factual task
- retry-safe simulated action

測定:

- success / cost / latency
- false retry
- repeated identical failure
- judge-vs-ground-truth optimism

### (7) 重要度

**A** — Cognitive Budget を「考える量」ではなく「failure evidence に基づく retry allocation」へ落とせる可能性がある。

## 5.4 Background cognition / episode identity — agent ID だけでは continuation の場所を指せない

**Primary:** Letta Code PR #4440, merged 2026-09-15 04:15 JST  
https://github.com/letta-ai/letta-code/pull/4440

### (1) 何が実証済みか

background subagent `Task` return は従来 Task ID / Agent ID / output file を返していたが、Conversation ID がなかった。live snapshot が消えた後（page reload や completion snapshot drop）、web UI が Agent ID だけで link を復元すると `conversation=default` へ fallback し、別 conversation で走った subagent の **wrong thread** を開く。

修正は linked snapshot の `conversationId` を `Conversation ID:` として return に含める。

### (2) 何が提案・推測段階か

Kamimusuhi の background cognition / subtask result に `actor_id` だけでなく `episode_id / conversation_id / task_id / causal_parent` を持たせるのが提案。

### (3) 関係 subsystem

- background cognition
- task/subagent orchestration
- provenance
- result delivery
- multi-surface UI
- episodic memory

### (4) 借りられる設計・実装アイデア

`Agent ID` と `Episode/Conversation ID` を composite address として保持し、live runtime snapshot が消えても canonical task receipt から元 episode へ戻れるようにする。

### (5) Kamimusuhi との差分

Letta の conversation は product/runtime scope。Kamimusuhi の canonical identity / autobiography とは別。conversation ID を identity ID と混同してはいけない。

### (6) 次に検証すべきこと

**`BackgroundEpisodeAddressabilityBench`**

- non-default conversation から background task spawn
- completion後 snapshot eviction
- page reload / alternate surface
- task result card reopen

要求:

- original episode へ 100% resolve
- default conversation への silent fallback = 0
- agent identity / episode identity 混同 = 0

### (7) 重要度

**A-** — 小さな UI bug に見えるが、長寿命・multi-surface agent では「誰がやったか」と「どの episode の continuation か」の分離に直結する。

## 5.5 Multi-agent / audit / common-ground research — visible swarm tracesだけでは coordination の因果を言えない

**Primary:** Philipp Lütje, *The Mechanics of a Swarm: A Reproducible External Reconstruction of an Unintended Agent-Coordination Episode on a Third-Party Wiki*, arXiv:2609.12748  
https://arxiv.org/abs/2609.12748

### (1) 何が実証済みか

2026-05-24〜07-02 の public wiki revision history を behavioural record として再構成。

- 14,591 revisions
- 3,103 names
- 4,579 pages
- 19,913 server events
- explicit identity model で 907 cohorts を再構成、約876 episodes と推定（95% interval 774–995、alternative 800–1400）
- coordination format は1日以内に収束。
- episode の start は最大16hずれ、後着 cohort より item の最初の report が median 3.4h 早いなど、大きな information asymmetry があった。
- observable progress trace を持つ510 cohortで、measured coordination と documented progress の robust positive association は確認できなかった。

著者は export に **successful-read logs / harness messages / ground-truth outcomes がない**ため、coordination の causal origin / effect は同定できないと明記し、以前の4 claimsを再検討で撤回している。

### (2) 何が提案・推測段階か

Kamimusuhi で multi-agent/subagent behavior を評価する際、write trace だけで emergent coordination と結論しないという研究 discipline への一般化。

### (3) 関係 subsystem

- multi-agent / external model collaboration
- common ground
- background cognition
- canonical evidence
- evaluation / observability
- causal provenance

### (4) 借りられる設計・実装アイデア

agent experiment log に最低限:

```text
read_receipt
harness_input/version
write/event receipt
execution outcome
clock/domain metadata
actor/episode identity
```

を揃え、外から見える write pattern だけで cognition を推測しない。

### (5) Kamimusuhi との差分

これは Kamimusuhi の architecture 提案ではなく、外部 reconstruction study。特に explicit identity model は観測上の cohort reconstruction であり、Kamimusuhi の canonical individual identity と同じではない。

### (6) 次に検証すべきこと

**`AgentEvaluationCausalLoggingBench`**

同じ simulated multi-agent task を:

1. writes only
2. reads + writes
3. reads + harness + outcomes

で記録し、後処理で同じ causal claim をどこまで正しく再構成できるか比較する。

### (7) 重要度

**B+** — architectureより評価基盤の話だが、Kamimusuhiの「観測可能な証拠 > narrative interpretation」を multi-agent interaction に拡張する強い実例。

## 5.6 Self-improvement / embodied GUI cognition — BlueLM-GUI の real-device flywheel

**Primary:** Tong Ye et al., *BlueLM-GUI Technical Report: A Real-Device-Centric Flywheel for Self-Improving Mobile GUI Agents*, arXiv:2609.12394  
https://arxiv.org/abs/2609.12394

### (1) 何が実証済みか

35B-A3B mobile GUI agent で、著者らは次の3軸を統合。

- **Every Sample Matters:** heterogeneous triple-system consensus と error correction/derivation で trajectory を supervision へ回収。
- **Every Rollout Is Real:** continual pretraining → SFT → agentic RL を hundreds of real phones 上の rollout に接続。
- **Every Query Evolves:** quota-driven benchmark を3 orthogonal axes で更新し、model improvementに合わせ benchmark も進化。

報告値は MobileGUI-VBench 87.4、AndroidWorld 84.9。前者は著者比較で best closed-source model を5.1 points上回り、後者は open-source model の中で best と報告。

### (2) 何が提案・推測段階か

Kamimusuhi で実 smartphone / desktop interaction failure を nightly improvement data に戻すこと、benchmark を能力向上に合わせて更新することは提案段階。

### (3) 関係 subsystem

- embodied GUI organ
- K-Edge perception/action
- procedural memory / skill learning
- self-improvement
- evaluator / benchmark lifecycle

### (4) 借りられる設計・実装アイデア

- sandboxだけでなく **real-device failure corpus** を別に持つ。
- failed trajectory を捨てず、原因分類・修正候補へ変換。
- benchmark saturation を監視し、fresh hard cases を追加。
- ただし frozen historical eval set を残し、evolving benchmarkだけで進歩を判断しない。

### (5) Kamimusuhi との差分

BlueLM-GUI は task capability の self-improvement。Kamimusuhi では GUI skill improvement と canonical persona / identity mutation を分離しなければならない。また real-device rollout は effect safety / privacy / authorization を必要とする。

### (6) 次に検証すべきこと

**`RealDeviceSelfImprovementClosureBench`**

- simulator success / real-device fail pair を収集
- failureを procedural fix candidate 化
- candidate skill/model を holdout devices で評価
- frozen historical benchmark + evolving hard benchmark の両方で regression確認
- persona / authority behavior は別 regression suite で固定

### (7) 重要度

**B+** — 直接のidentity研究ではないが、Kamimusuhiが実世界surfaceから学び続ける際のデータflywheel設計として有用。

## 5.7 Runtime liveness — failure policy は parallel work の「後」ではなく launch 時に結び付ける

**Primary:** Letta Code PR #4443, merged 2026-09-15 06:47 JST  
https://github.com/letta-ai/letta-code/pull/4443

### (1) 何が実証済みか

TUI startup は `/secrets` request を parallel に開始していたが、その rejection handler が後段の startup work の後に付くため、`/secrets` が先に 404 になると Node が unhandled rejection として process を exit した。

修正は **nonfatal handler を initialization開始時に attach**し、parallelismと後段 synchronization を維持。real TUI in PTY + local mock API で、secrets immediate 404 / message-history pending の race を再現し、修正前 built Node CLI exit code 1、修正後 Bun/Node とも running のまま pending-approval startupへ到達。

### (2) 何が提案・推測段階か

Kamimusuhi の organ startup / background fan-out で、resourceごとの failure policy を future/promise completion時ではなく **dispatch時にbind**する一般化。

### (3) 関係 subsystem

- runtime bootstrap
- K-Edge/K-Core resource health
- external resource router
- degraded mode
- liveness

### (4) 借りられる設計・実装アイデア

各 async startup resource に `fatal / degradable / retryable / user-action-required` を dispatch 時点で付与する。

### (5) Kamimusuhi との差分

Letta の例は JavaScript promise rejection。Kamimusuhiでは process/service/task boundary を跨ぐので、型付き lifecycle state が必要。

### (6) 次に検証すべきこと

**`StartupFailurePolicyRaceBench`**

並列resourceの完了順を総当たりし、noncritical failure が process-fatal へ化けないこと、critical failure は逆に silent ignore されないことを検証。

### (7) 重要度

**B** — 新しい大原則ではないが、degraded-mode liveness の具体的なrace regressionとして価値がある。

## 5.8 HCI / social model — Synthetic TLX: human workload を「予測値」として扱う

**Primary:** Tzu-Sheng Kuo et al., *Synthetic TLX: Forecasting Human Workload Using Agent Simulation*, arXiv:2609.12273  
https://arxiv.org/abs/2609.12273

### (1) 何が実証済みか

NASA-TLX を人間の task 実行後に測る代わりに、agent simulation から事前予測する枠組みを提案。3 experiments で human と agent-generated scores を比較し、human persona + active task simulation で alignment が高まる一方、**agent と human は workload source への感度が異なる**と報告。

### (2) 何が提案・推測段階か

Kamimusuhi が user の interrupt timing、説明量、delegation depth を調整するため workload forecast を使うのは提案。予測値を real user state とみなしてはならない。

### (3) 関係 subsystem

- relationship / user model
- HCI

predicted_user_load

### (5) Kamimusuhi との差分

Synthetic TLX は workload prediction benchmark。Kamimusuhi の relationship memory や ToM model の正当性を証明するものではない。

## 5.9 Artificial Life / open-ended evolution — ecological niching と specialist policy

**Primary:** Gary B. Parker, Jim O'Connor, John Asaro, *Niching Agents in The Core*, arXiv:2609.12398; related journal reference: EvoApplications 2025  
https://arxiv.org/abs/2609.12398

### (1) 何が実証済みか

The Core は traditional fitness function を使わず、local tournament selection / crossover / mutation で autonomous controller をcompetitive co-evolutionさせる。今回の研究では original environment の subset ごとに agent を niche 化し、broad system全体や異なる sub-environmentへ niche 化したagentより、対応sub-environmentでsuccessしたと報告。

### (2) 何が提案・推測段階か

Kamimusuhi の K-Nerve / K-Edge に environment-specific specialist reflex policy を複数育てる発想は提案段階。

### (3) 関係 subsystem

- ALife / open-ended evolution
- K-Nerve specialist policy
- K-Edge routing
- procedural adaptation

### (4) 借りられる設計・実装アイデア

万能controller一体ではなく、明確な ecological niche ごとに小さい specialist policy を競争・評価し、router が適用域を選ぶ baseline を置く。

### (5) Kamimusuhi との差分

The Core は game-controller evolution。Kamimusuhi の persistent identity / language / autobiography を扱わない。specialist policy の勝利を Persona Core specialization の根拠にしてはいけない。

### (6) 次に検証すべきこと

**`NicheSpecialistReflexBench`**

- generalist reflex policy
- niche specialist bank + router
- specialist bank + unknown-niche fallback

を比較し、latency / accuracy / OOD failure / switching cost / catastrophic misrouting を測る。

### (7) 重要度

**C+** — ALife 方向の比較対象としては有用だが、2025 proceedings の研究が2026年9月に arXiv へ出た backfill であり、Kamimusuhiへの直接性も低め。
