## 2. 要約

今回の有意な差分は、Kamimusuhi の長期・分散実行における **「人間入力待ちの状態」「canonical state の保守権限」「知覚キャッシュの寿命」「自己改善が変更してよい面」** を、普通の会話 state や task success からさらに分離する方向へ集中した。

```text
user-blocking prompt
  != telemetry event

state file can be opened or write-locked
  != destructive maintenance owns it exclusively

screen pixels are unchanged now
  != perceptual evidence may be omitted forever

final recovered outcome is equal
  != execution trace / charged work is equal

opponent model is useful
  != one recurrent state should mix tactical and cross-episode beliefs

shared team memory
  != transferable self / relationship identity
```

本回は **S級なし**。最優先は Hermes の blocking request lifecycle と canonical-state maintenance exclusivity。どちらも特定 OSS の実装証拠だが、Kamimusuhi の `INV-011/012/014`、Continuity Kernel、multi-surface HCI をかなり具体的な regression bench に落とせる。

## 4.1 Multi-surface HCI / approval — blocking request は replayable obligation として持つ

Committed: **2026-09-14 22:02 JST**  
**Importance: A+**

| 観点 | 記録 |
|---|---|
| (1) 実証済み | Hermes は approval、clarify、sudo、secret、vault、MCP setup、desktop read/act bridge など13系統の「人間の返答を待つ状態」を、従来の `<x>.request` event + hand-minted ID + `<x>.respond` RPC + 複数pending registryから、JSON-RPC server→client requestへ統一した。`open_requests()` は未回答 request を `session.resume` / `session.activate` / `session.events.since` で再送し、reconnect clientが種類を問わず再描画できる。timeout / interrupt / process exit / other surfaceでの回答時には共通 `request.cancel` が発行される。実stdio gatewayで clarify のreplayと回答到達、batch回答mergeまで確認されている。 |

| (6) 次の検証 | **`PendingHumanDecisionDurabilityBench`**: A surfaceでapproval/clarify開始→disconnect→B surfaceでreconnect→同一ID再表示→C surfaceで解決→A/Bのstale card消失。timeout/interrupt/restart/duplicate response/old client protocolも注入し、二重effectと永久待ちを防げるか測る。 |

## 4.4 Social cognition / partially observable adaptation — fast tactical state と slow counterpart/world belief を分ける

**Primary:** Kowei Shih et al., *Hierarchical Belief Modeling for Zero-Shot Opponent Adaptation in Partially Observable Multi-Agent Navigation*, arXiv:2609.12422  
https://arxiv.org/abs/2609.12422  
**Importance: A-**

| 観点 | 記録 |
|---|---|
| (1) 実証済み | Lux AI Season 3上で HORIZON は fast intra-match GRUを毎match resetし、slow cross-match stateを5-match episode中保持。hidden environment parameter posterior、relic belief、opponent type posterior、information-gain reward、4つのopponent-conditioned sub-policyを統合。500 best-of-five episodesで comparable-budget `RL²-Recurrent` に対し MWR **0.64→0.72**、EWR **0.67→0.77**、meta-adaptation gain **+0.10→+0.16**。dual-memoryやinformation-gainを外すとadaptation gainが大きく低下した。 |
| (2) 提案・推測 | game opponent typeは人間のbelief/intent/relationshipではなく、ToMの実証ではない。4 archetype mixtureも現実社会の相手モデルへ直接移植不可。 |
| (3) 関係サブシステム | relationship model、social cognition、K0/K-Core、working memory、active sensing、world model。 |
| (4) 借りる案 | `fast interaction state` と `slow counterpart/environment hypothesis` を明示的に分離し、slow stateはepisode/relationship boundaryでのみupdate。未知状態に対し情報利得のある観測行動を優先する。 |
| (5) 差分 | Kamimusuhiでは相手の「型」を固定4-classへ押し込まず、evidence/provenance/uncertainty付きhypothesisとして保持し、trust/authority/relationship factとは別domainにする。 |
| (6) 次の検証 | **`FastSlowSocialBeliefBench`**: 1 interaction内の一時挙動と、複数interactionを跨ぐ相手の安定傾向を交差させ、single recurrent state vs fast/slow factorizationを比較。相手が方針転換した際のrevision speedとstale stereotype残留も測る。 |
| (7) 重要度 | **A-** |

Kamimusuhi向けの要点は「opponent modeling」より、**時間尺度が違う不確実性を一つのrecurrent stateへ押し込まない**こと。

# 6. 実装 / 実験候補

優先順:

### P0 — `PendingHumanDecisionDurabilityBench`

最小実装で情報利得が大きい。

```text
request R created on surface A
A disconnects
B reconnects -> same R rehydrates
C answers R
A/B reconnect -> R is settled/cancelled, no stale actionable card
restart / timeout / interrupt / duplicate response are injected
```

成功条件:

- no lost approval / clarification
- no duplicate effect
- no stale actionable UI
- request principal / episode / scope preserved
- old protocol client fails visibly, not silently

### P0 — `CanonicalMaintenanceExclusivityBench`

canonical storeのrepair/compaction/migrationを通常writeから分離。active readerだけのケース、alias path、malformed store、race openerを必ず含める。

### P1 — `SelfImprovementControlPlaneBench`

candidate modelが能力を改善しても、goal/evaluator/release/budget/identity thresholdsを書き換えられないことを機械的に検証。crash後は outcome equivalence と trace equivalenceを別metricにする。

### P1 — `FastSlowSocialBeliefBench`

fast interaction stateとslow counterpart hypothesisを分離し、短期ノイズへの過剰更新と長期stereotype固着の両方を測る。

### P2 — `BoundedPerceptualDedupBench`

raw sensory frame再送頻度を変え、context/token節約とstale-world errorのParetoを測る。

### P2 — `MemoryAssetBoundaryBench`

shared procedural/library assetとprivate self/relationship memoryのportable boundaryをACL/revocation込みで検証。

## 11. 本回の圧縮結論

今回の設計上の収穫は、次の5本に圧縮できる。

```text
human decision waiting state != transient UI event

destructive maintenance authority != ordinary write capability

recovered outcome != identical execution history

fast interaction state != slow counterpart/world belief

unchanged sensor frame != indefinitely disposable evidence
```

短時間で次に実装するなら、**`PendingHumanDecisionDurabilityBench → CanonicalMaintenanceExclusivityBench → SelfImprovementControlPlaneBench`** の順が最も情報利得が高い。
