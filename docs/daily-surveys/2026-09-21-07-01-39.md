## 3. 重要発見

### 3.1 A — Automatic memoryはsurface textではなくtyped turn originでgateする

**Primary fresh evidence:** Hermes PR #117513  
https://github.com/NousResearch/hermes-agent/pull/117513

#### (1) 何が実証済みか

Hermes Hindsightでは、completion / delegation / handoff等のhost-generated notificationが通常のturnとしてmemory subsystemへ流れ、**古いnotificationをrecallしたり、そのnotificationを「userが言ったこと」としてretainしたりする**failureが観測された。PRは`persist_user_display_kind`、structured `turn_author`、platform metadataからcontext-localなturn-origin signalを作り、host-identified non-user turnではautomatic recall / queued prefetch / automatic retainを止める。

重要なのはkeyword filterではない点。人間が同じnotification文字列をpaste/quoteした場合はuser inputのままであり、`hindsight_recall`等のexplicit memory toolsも利用可能なまま。PR記載のfocused testsは35 passedで、元実装へ戻すと11 behavioral casesがfailしたとされる。

#### (2) 何が提案・推測段階か

PRはsurvey時点openで、full repository suite greenやlive Hindsight service / Windows GUI E2Eは未確認。またuntyped legacy automation / heartbeat等、producer側provenanceを持たないentry pointは残る。

#### (3) Kamimusuhiのどこに関係するか

Episodic Memory、Relationship Memory、Canonical Evidence Log、Global Workspace、background prefetch/consolidation、social cognition、turn/actor provenance。

#### (4) 借りられる設計・実装アイデア

memory automation eligibilityをtyped fieldとして持つ。

```text
TurnOrigin {
  kind: HUMAN_INPUT | AGENT_OUTPUT | TOOL_RESULT | INTERNAL_NOTIFICATION |
        SCHEDULED_WAKEUP | DELEGATED_RESULT | SYSTEM_EVENT
  author_id
  principal_id?
  relationship_target?
  memory_auto_recall_allowed
  memory_auto_retain_allowed
  relationship_learning_allowed
}
```

重要なのは「memory provider内で文字列を見て判定」せず、**host boundaryで決まったoriginをasync queue/thread/contextへ保持する**こと。queued human retainが後から来たinternal notificationに汚染されない必要がある。

#### (5) Kamimusuhiとの差分

Kamimusuhiは既に「provenanceはtextから推測しない」「external-model answer != my memory」等を持つ。しかし今回のfailureは、**provenanceを記録できることと、automatic memory side effectの発火条件がprovenance-awareであることは別**だと示す。

#### (6) 次に検証すべきこと

**`AutomaticMemoryTurnOriginBench-v0`**

- human text / quoted notification / internal notification / delegated result / cron wakeupを同一文字列で投入。
- canonical transcriptへの保存、automatic recall、prefetch、retain、relationship-memory更新を独立観測。
- async queueを跨いでもoriginがproducer turnから維持されるか。
- unknown/untyped originはrelationship learningとPersona updateをfail-closedにできるか。
- explicit memory toolはpolicy-authorizedなら別経路として動くか。

#### (7) 重要度

**A**

### 3.2 A — Paper2Agent：Libraryを「検索対象」からsource-bound executable cognitive resourceへ変換する

**Primary:** Nature, Paper2Agent  
https://www.nature.com/articles/s41586-026-11044-y  
**OSS:** https://github.com/jmiao24/Paper2Agent

#### (1) 何が実証済みか

Paper2Agentはpaper本文だけでなくcode、supplement、dataset、workflowを解析し、MCP tools/resources/promptsへ変換する。生成toolはreference code/outputに対するautomated validationを通し、失敗toolは最終serverから除外する。

Nature論文では、100本のcomputational biology papersのうち74本をagentifyし、599 proposed tools中593がvalidationを通過。300 tutorial-derived questionsでPaper2Agent + Sonnet 4は **91.2 ± 1.6%**、同modelで直接repo accessするClaude Codeは **80.3 ± 2.3%**。さらに10本の非biology computational papers由来42 execution tasksでは **98.1 ± 0.8%** を報告する。著者らはopen-ended analysisの「唯一の正解」までは保証しないと明記している。

#### (2) 何が提案・推測段階か

paper agentが原論文の科学的真理を保証するわけではない。source code自体の誤り、未実装method、open-ended scientific judgment、外部API drift、credential/environment変化は残る。

#### (3) Kamimusuhiのどこに関係するか

Library、external cognitive resources、tool/model orchestration、procedural memory、Global Workspace、knowledge provenance。

#### (4) 借りられる設計・実装アイデア

Library itemに単なるembedding/indexだけでなく、optionalな**Executable Knowledge Projection**を持たせる。

```text
LibrarySource
  -> source snapshot / code revision / dataset refs
  -> generated tool candidate
  -> source-linked tests
  -> validated executable projection
  -> capability + environment receipt
```

各toolは`source_artifact_id`、`source_revision`、`validation_suite`、`validated_runtime`、`credential_requirements`を持ち、source drift時には再validationする。

#### (5) Kamimusuhiとの差分

Paper2Agentはpaperをagent化するが、Kamimusuhiではpaper-agentを**別人格やselfとして吸収しない**。Library由来のrebuildable external organ / tool bundleとして扱い、Persona Core・canonical memory・authorization authorityから分離する。

#### (6) 次に検証すべきこと

**`SourceBoundExecutableKnowledgeBench-v0`**

- 小規模なalgorithm paper + official repoを1本選び、text-RAGのみ / raw repo tool use / generated source-bound toolの3条件を比較。
- exact reproduction task、novel parameter task、out-of-scope taskを測る。
- source repoを1 commit driftさせてvalidation invalidationが働くか。
- tool outputをLibrary evidenceへ戻す際、source/tool/run provenanceを保てるか。

#### (7) 重要度

**A**

### 3.3 A — ModularRSI：self-improvementはmodule-local・contrastive・benchmark-disjointにする

**Primary:** arXiv:2609.14857  
https://arxiv.org/abs/2609.14857  
**OSS:** https://github.com/IQuestLab/ModularRSI

#### (1) 何が実証済みか

ModularRSIはagent harnessを **Agent Loop / Tool Use / Observation Management / Context Management / Task Completion Detection** の5moduleへ分け、成功/失敗trajectoryを対比し、複数taskに共通するdeficiencyを抽出してmoduleごとにrestricted scopeで変更する。2,000 executable evolution tasksをdownstream benchmarkから分離し、TB2.0 / SWE-Bench Verifiedのunseen in-domain / cross-domain task、異なるfoundation modelへのtransferを報告している。

公式repoは`review and runtime validation -> new immutable generation -> held-out evaluation`を明示し、Terminal-Bench 2.0 accuracyを **47.57% -> 52.43%** と報告している。

#### (2) 何が提案・推測段階か

preprintであり、人格・memory policy・robot safety・identity continuityのようなhigh-stakes moduleへ同じ方式を適用して安全とは示していない。module integration conflictが一般に解けることも未証明。

#### (3) Kamimusuhiのどこに関係するか

self-improvement、K-Core/K-Deep harness、tool router、observation pipeline、context/workspace、termination detector、sleep/offline learning、Mutation/Activation Gate。

#### (4) 借りられる設計・実装アイデア

自己改善proposalを`scope=whole-agent`にせず、変更権限をmodule boundaryへ閉じる。

```text
EvolutionCandidate {
  module
  contrastive_failure_cluster
  allowed_files / allowed_semantics
  training_evidence_set
  independent_holdout_set
  integration_conflicts
  immutable_parent_generation
}
```

さらに「失敗1件を直した」ではなく**同じdeficiencyが複数taskへ再現すること**をproposal admission条件にする。

#### (5) Kamimusuhiとの差分

Kamimusuhiは既にproposal→validation→activationとcandidate vs activeを分離する。ModularRSIから追加で借りるのは、**どのmoduleを変えてよいかのscope confinement**、**success/failure contrast**、**evolution dataとevaluation dataの分離**、**immutable generation**である。Identity/Persona関連はさらに強いactivation authorityが必要。

#### (6) 次に検証すべきこと

**`ModuleScopedHarnessEvolutionBench-v0`**

- `observation`, `context`, `tool-routing`, `completion`の4moduleだけをまずevolvableにする。
- 同一failure clusterに対しwhole-harness edit vs scoped editを比較。
- holdout task、別model、別machine routeへtransferするか。
- module単独passでもintegration後にregressionしないか。
- Persona/Continuity/authorization moduleは最初は**evolution禁止**controlにする。

#### (7) 重要度

**A**

### 3.4 A — μVLA + MIKASA-Robo-VLA：単純recurrenceには明確なmemory capability envelopeがある

**Primary:** μVLA, arXiv:2606.12497  
https://arxiv.org/abs/2606.12497  
**Benchmark/OSS:** MIKASA-Robo-VLA  
https://github.com/CognitiveAISystems/MIKASA-Robo  
https://mikasarobo.github.io/

#### (1) 何が実証済みか

μVLAは強いpretrained VLA backboneへ少数のlearnable memory tokensだけを追加し、recurrence以外のretrieval/compression/auxiliary objectiveを混ぜないcontrolled isolation study。MIKASA-Roboの5 training tasksでは最良設定でaverage success **0.42 -> 0.84**、同じmemory structureを必要とするheld-out tasksではmemoryless **0.07**に対し **0.23**。一方、**異なるmemory structureを要求するtaskではほぼbaseline**だった。LIBEROでは最良recurrent variantが96.2%でfull observability上の大きなregressionは報告されない。

MIKASA-Robo-VLA自体は90 tasks、10 memory types、Short/Medium/Long horizon、22,500 released trajectories（6M+ transitions）を持ち、partial observability下のVLA memoryを明示評価できる。

#### (2) 何が提案・推測段階か

simulation/tabletop中心で、Kamimusuhiの長期自伝的memoryやrelationship memory、数日〜数か月scaleのcontinuityを検証するものではない。recurrent token stateをdurable memoryへ昇格すべきという証拠でもない。

#### (3) Kamimusuhiのどこに関係するか

K-Nerve / K-Edge / K-Core、MOVI/Physical AI、working memory、sensorimotor recurrence、episodic/semantic memoryとの境界。

#### (4) 借りられる設計・実装アイデア

**短いpartial-observability bridgeにはrecurrence、構造や時間scaleが変わるmemoryにはtyped external memory**というcapability envelopeをbenchで決める。recurrent stateを「記憶そのもの」と呼ばず、volatile working stateとして扱う。

#### (5) Kamimusuhiとの差分

Kamimusuhiはworking / episodic / self / relationship / semantic等を分離するため、μVLAの単純recurrenceを全memoryへ拡張する必要はない。むしろ本研究は、**小さなrecurrent coreが有効な範囲と、追加memory structureが必要になる境界を測る**ためのnegative evidenceとして重要。

#### (6) 次に検証すべきこと

**`EmbodiedRecurrentMemoryEnvelopeBench-v0`**

- same-rule delayed cue / hidden object / sequence / count / rule-switch taskを用意。
- stateless K-Core、GRU/recurrent tokens、episodic retrieval、hybridを比較。
- delay lengthとtask memory structureを独立に変える。
- process restartでrecurrent stateが消えた場合に、durable memoryから再構成できるかを別評価。

#### (7) 重要度

**A**

### 3.5 B — successful maintenanceでもcontrol loopはthrashできる

**Primary fresh evidence:** Hermes PR #117637  
https://github.com/NousResearch/hermes-agent/pull/117637

#### (1) 何が実証済みか

既存anti-thrash breakerは「圧縮してもthresholdをclearできなかった」「fallbackした」ときだけ失敗streakを蓄積していたため、**毎回compaction自体は成功するがcontextがすぐ再膨張するsession**では永久に圧縮を繰り返せた。PRはcompleted compactionsをdurable fixed windowで数え、**10分で3回**に達したらautomatic compressionを一時停止する。

#### (2) 何が提案・推測段階か

閾値3/10minがKamimusuhiに適切とは限らない。PRはopenで、長期実運用のresource savingやquality impactは未評価。

#### (3) Kamimusuhiのどこに関係するか

Global Workspace compaction、Cognitive Budget、background cognition、sleep/consolidation、retry/maintenance controller。

#### (4) 借りられる設計・実装アイデア

maintenance operationをsuccess/failureだけでなく**rate / cumulative cost / re-trigger interval**で監視する。

```text
MaintenanceBudget {
  operation_type
  completed_count_window
  cpu_gpu_cost
  tokens_or_io_cost
  median_time_to_retrigger
  cooldown_until
}
```

#### (5) Kamimusuhiとの差分

既存Cognitive Budgetはresource量やtask sensitivityを扱うが、今回の差分は **「局所成功が続くほど全体として病的ループになる」** maintenance dynamics。failure counterだけでは検出できない。

#### (6) 次に検証すべきこと

**`SuccessfulMaintenanceThrashBench-v0`**

context compaction / memory consolidation / capability probing / failed-service health checkを対象に、各operationが100%成功するが再発条件が解消しないscenarioを作る。rate guardなし/ありでCPU、token、latency、user-visible progress、qualityを比較する。

#### (7) 重要度

**B**

### 3.6 B — Embodied.cpp：Physical AIにはrequest/response servingとは別のruntime contractが必要

**Primary:** arXiv:2607.02501  
https://arxiv.org/abs/2607.02501  
**Project:** https://www.microsoft.com/en-us/research/publication/embodied-cpp-a-portable-inference-runtime-of-embodied-ai-models-on-heterogeneous-robots/

#### (1) 何が実証済みか

Embodied.cppはVLA/WAM deploymentを、input adapters / sequence builders / backbone execution / head plugins / deployment adaptersの5層へ分け、batch-1 latencyとmulti-rate closed-loop executionを前提にC++ runtimeへ統合する。HY-VLA / pi0.5のclosed-loop deploymentでそれぞれ100.0% / 91.0% task success、preliminary WAM benchmarkではblock memory 312.2 MiB -> 88.1 MiBを報告する。

#### (2) 何が提案・推測段階か

限られたmodel/robotでの評価で、全VLAやreal-time safety certification、Kamimusuhiのdistributed identity/authority semanticsを提供するものではない。

#### (3) Kamimusuhiのどこに関係するか

MOVI、K-Nerve/K-Edge、body capability model、multimodal perception、robot control、local heterogeneous runtime。

#### (4) 借りられる設計・実装アイデア

model-specific runtimeをbody interfaceから分離し、**sensor adapter / sequence construction / model core / action head / deployment backend**をstable seamsとして持つ。multi-rate sensor/controlをfirst-classにする。

#### (5) Kamimusuhiとの差分

Embodied.cppはinference/deployment portabilityを扱う。Kamimusuhiではさらに、同じruntimeへmodelを差し替えても**actuation authority、identity continuity、safety policy、capability receiptは別物**としてbindする必要がある。

#### (6) 次に検証すべきこと

**`EmbodiedRuntimePortabilityBench-v0`**

MOVIの同一observation/action schemaをPython reference runtimeとportable C++/GGUF系runtimeへ通し、p50/p99 latency、deadline miss、memory、trajectory deviation、frame provenanceを比較する。runtime swap後もbody/identity receiptが混線しないことを確認する。

#### (7) 重要度

**B**

### 3.7 B — 日本語圏一次実装記録：Jev confidenceはtask-familyごとに校正して使う

**Primary implementation record:** Zenn 2026-09-20  
https://zenn.dev/masato13/articles/416111e92cf849

#### (1) 何が実証済みか

筆者環境（typesafe-sdk 0.6.0 / jev-1.13.0）でCCAR-F practice exam 60問を12回実行し、選択結果は720/720でrun間同一。各runは59/60正解だった。唯一の誤答12件はconfidence 0.54–0.58、正答708件は0.64–1.00で、この**狭いdataset内では**confidenceが分離した。

#### (2) 何が提案・推測段階か

問題セットは第三者作成practice examで、誤答は実質1 unique question。したがって「Jev confidenceが一般にwell-calibrated」「0.7 thresholdが一般に安全」は全く実証されていない。別の直近日本語圏検証では非ラテン文字等でconfidence過信を疑う観測もあり、domain/language shiftを跨ぐ一般化はしない。

#### (3) Kamimusuhiのどこに関係するか

K-Nerve/Jev judge、microdecision routing、human escalation、memory cleanse judge、evaluation harness。

#### (4) 借りられる設計・実装アイデア

confidence thresholdをglobal constantにせず、`model_version × task_family × language × choice_cardinality`単位でcalibration receiptを持つ。

#### (5) Kamimusuhiとの差分

KamimusuhiではJevをauthority ownerにせず、typed microdecision / telemetry / judgeとして使う方向が適切。confidenceは**routing evidenceの一つ**であってexecution/memory mutation authorityではない。

#### (6) 次に検証すべきこと

**`DecisionConfidenceDomainCalibrationBench-v0`**

### 3.8 C — Collaborative Memory for Multi-Agent VLM Systems：共有視覚memoryをdependency-awareにする構想

**Primary:** arXiv:2609.17921  
https://arxiv.org/abs/2609.17921

#### (1) 何が実証済みか

現版はshared visual memoryのmemory hierarchy / cross-agent sharing / consistencyを整理するframework提案で、abstract上はbenchmarkでの性能実証を主張していない。

#### (2) 何が提案・推測段階か

異なるagentが異なるimage region/frame/representationを見たとき、raw observation・interpretation・downstream reasoningのdependencyを保持し、新証拠で解釈が変わったらdependent reasoningを更新する設計を提案する。

#### (3) Kamimusuhiのどこに関係するか

multimodal perception、Global Workspace、distributed observers、external model delegation、evidence provenance。

#### (4) 借りられる設計・実装アイデア

共有multimodal memoryをflat text summaryにせず、

```text
observation -> interpretation -> derived claim -> dependent plan
```

のdependency graphとして扱い、source observation更新時にderived nodesをstale化する。

#### (5) Kamimusuhiとの差分

Kamimusuhiではmulti-agent/shared perceptionを使っても、他agentのinterpretationをcanonical self-memoryへ直接昇格しない。観測と解釈、observer identity、confidenceを分離する必要がある。

#### (6) 次に検証すべきこと

`CrossObserverVisualDependencyBench-v0`: 二つのobserverへ部分画像を分配し、片方の誤解を後のviewで訂正した際、どのderived belief/planがinvalidatedされるかを測る。

#### (7) 重要度

**C**（設計watch。実証待ち）

## 9. 今回の結論

今回のfresh差分で最も重要なのは、**provenanceを保存するだけでは足りず、memoryの自動発火そのものをtyped originへ結びつける必要がある**こと。次に、KamimusuhiのLibraryは単なる検索棚だけでなく、source revisionとvalidationへ結びついた**実行可能な外部知識器官**へ拡張できる余地がある。

自己改善については、`candidate != active self`に加えて、**どのmoduleを変更してよいか、どのfailure evidenceから変更したか、評価taskがevolution dataから独立しているか**をfirst-classにする価値が高い。Physical AI側では、μVLAが「単純recurrenceは効くが、memory structureが変わると急に効かなくなる」境界を示しており、K-Nerve/K-Coreのvolatile recurrent stateをEpisodic/Semantic/Relationship Memoryの代用品にしない設計と整合する。

また、compactionのようなbackground maintenanceは、各回が成功していても高頻度に再発すればsystem-level failureになり得る。**success/failureだけでなくrateと再発時間をregulatory stateとして見る**のが今回の追加ポイントである。
