## 5.1 Distributed continuity / recovery — Letta Code #4431

**Primary implementation:** Letta Code PR #4431, *only the execution owner resumes an interrupted turn on sync*  
https://github.com/letta-ai/letta-code/pull/4431  
Merged: **2026-09-14 14:44:06 JST**  
**Importance: A+**

| 観点 | 記録 |
|---|---|
| (1) 実証済み | `sync` が browser observer、prewarm/idle sandbox probe、実際の owner relaunch など複数 origin から届く環境で、以前は fresh listener が pending approval を復元して stale tool call を deny し、そのまま competing continuation を開始し得た。修正は `recover_approvals` と `resume_interrupted_turn` を分離し、observer は approval を調べ/park できても immediate continuation を開始しない。focused tests で owner/observer/`recover_approvals=false` の差を確認。 |
| (2) 提案・推測 | production relaunch path は merge 時点で cloud-api が `resume_interrupted_turn` をまだ送っておらず、本番 E2E は未完。一般的な distributed-agent protocol にそのまま適用できるかは未実証。 |
| (3) 関係サブシステム | Continuity Kernel、migration/recovery、K-Edge/K-Core handoff、Effect Acceptance、episode lease。 |
| (4) 借りる案 | recovery API を `DISCOVER_OR_RECONSTRUCT_STATE` と `RESUME_EXECUTION` に型分離する。前者は observer/read-only runtime でも可能、後者は current execution owner + fresh lease/fence + handoff state を要求。 |
| (5) 差分 | Kamimusuhi は canonical identity lineage と effect authority を Letta より強く分離する。したがって resume bit 一つではなく `episode_id / owner_ref / lease_epoch / expected predecessor / pending effect state` と結びつける必要がある。 |
| (6) 次の検証 | **`ObserverSafeRecoveryBench`**: owner A が tool await 中、observer B/C が sync/recovery discovery、owner crash/relaunch、handoff、stale approval を競合。observer が evidence を復元できても execution/effect を開始しないこと、owner が liveness を回復することを検証。 |
| (7) 重要度 | **A+** |

今回の核心:

```text
recoverable / inspectable state
!=
authority to continue the episode
```

これは既存 `INV-006` と `INV-014` を強化する regression evidence であり、新 invariant を増やすよりテスト化が適切。

## 5.2 Tool/model orchestration — Competence-Gated Pooling

**Primary:** Aditi Tiwari, Aashrith Bandaru, Heng Ji, *Competence-Gated Pooling of Language Models and Priors for Event Forecasting*, arXiv:2609.12101  
https://arxiv.org/abs/2609.12101  
**Importance: A**

| 観点 | 記録 |
|---|---|
| (1) 実証済み | 2,357件のresolved binary question・5 LMsで、domain別source weightを過去 outcome から推定し、不確実ならglobal weightへ縮約する gate を評価。main external baselineのBrierを **0.0771→0.0732** に改善。ForecastBench market subsetでは有意改善せず、gateは市場予測へほぼdefer。4 Qwenモデルでは verbal confidence が「外部予測より役立つ場面」を安定して識別できなかった。 |
| (2) 提案・推測 | forecasting以外のtool/model routing、長期agent task、non-stationary expert poolに同じ推定法が有効かは未実証。domain labelsが粗い/変化する場合も要検証。 |
| (3) 関係サブシステム | Cognitive Action Router、K-Core/K-Deep escalation、external model integration、capability model、Cognitive Budget。 |
| (4) 借りる案 | provider/modelの自己申告confidenceやglobal benchmark rankだけでなく、**現在利用可能な他resourceに対する条件付きmarginal value** を履歴から学ぶ。gainが見込めないときは明示的にdefer/skip。 |
| (5) 差分 | Kamimusuhiのrouterはaccuracyだけでなく privacy / latency / cost / authority / freshness / data boundary を同時制約に持つ。competence gateはそのうち epistemic utility の一項。 |
| (6) 次の検証 | **`MarginalUtilityRoutingBench`**: local model、frontier model、search、code、cached answerを組み合わせ、各source単体accuracyと「既存sourceに追加したときのincremental gain」を分離。verbal confidence routing、historical outcome gate、oracle gateを比較し、cost/latency込みutilityを測る。 |
| (7) 重要度 | **A** |

設計上の短い教訓:

```text
high standalone capability
!=
useful additional cognition right now
```

## 5.3 Multi-stage reasoning / semantic continuity — Deictic Ambiguity

**Primary:** Obinna I. Ekekezie, *Can LLMs in Draft-Verify-Revise Pipelines Resolve Deictic Ambiguity?*, arXiv:2609.12162  
https://arxiv.org/abs/2609.12162  
Code/data link is provided from the arXiv page.  
**Importance: A**

| 観点 | 記録 |
|---|---|
| (1) 実証済み | draft→verify→revise の cascade で `previous` のような文脈依存語が stage ごとに違う対象を指す **deictic shift** を synthetic benchmark で評価。10 base examples×3 conditions、6 models、21 reasoning-effort configurations。balanced accuracyは0.156〜near-perfect。GPT-5.2は reasoningなし0.156→最高effort0.942、Gemini 3 Proは全levelで0.94超。誤判定時はoperational reasoningよりsurface cue依存が目立った。 |
| (2) 提案・推測 | synthetic 10-base-example familyから実world multi-agent workflow全般への一般化は未確定。高effortで多くが直るが、それを「referent identityが保証された」とは言えない。 |
| (3) 関係サブシステム | K-Deep research/review pipeline、Global Workspace、tool/model orchestration、evidence graph、narrative/summary handoff。 |
| (4) 借りる案 | stage間で自然言語だけを渡さず、entity/event/artifactへ stable ID を与え、`ReferentBinding {surface_text, target_id, scope, introduced_at}` を持たせる。grader feedbackも「previous result」ではなくID参照に正規化。 |
| (5) 差分 | Kamimusuhiには canonical evidence ID / episode ID / lineage reference を持てるため、単なるprompt engineeringより構造化しやすい。一方、relationship/person pronoun等の会話的曖昧性まで全てID化するのは不自然なので、critical pathのみ型付けする。 |
| (6) 次の検証 | **`CrossStageReferentStabilityBench`**: draft/reviewer/reviser/summary/tool stageを5〜8段重ね、`previous/it/that user/the result` と stable-ID条件を比較。最終正解だけでなく各stageのreferent一致率を測る。 |
| (7) 重要度 | **A** |

これは continuity を「identity」だけでなく **semantic object continuity** まで広げる実装上の論点。

# 12. 今回の結論

今回の最も強い追加は、**recoveryを「状態が見える/復元できる」ことと「実行を再開してよい」ことへ分割する**実装証拠だった。

次に、model/tool orchestrationでは

```text
confidence != marginal utility
```

multi-stage reasoningでは

```text
surface reference != stable referent
```

multi-rate embodied cognitionでは

```text
connected modules != explicit temporal semantics
```

を、それぞれ独立した評価軸にする価値が高い。

**次の実験優先度は `ObserverSafeRecoveryBench → MarginalUtilityRoutingBench → CrossStageReferentStabilityBench → MultiRateTemporalGraphBench`。**
