# 分野別項目

## 1. A — Principal Credential Isolation: credential fallback を authority inheritance にしない

**一次資料**

- NousResearch/hermes-agent PR #113425 — *fix(auth): named profiles no longer inherit the root profile's credentials*  
  merged 2026-09-17 06:34:59 JST  
  https://github.com/NousResearch/hermes-agent/pull/113425

### (1) 何が実証済みか

Hermes の named profile が自分のcredentialを持たないとき、root profile の `auth.json` / credential poolへ暗黙fallbackし、root所有者としてproviderを利用できていた。さらにprofile側でOAuth tokenをrefresh/saveするとroot storeへwrite-throughし、root tokenを回転させ得た。

修正後はread/writeともactive profile storeだけを見る。PRのlive probeでは、修正前はprofile BでrootのxAI OAuth tokenとpool keyが見え、Bからtoken saveするとroot tokenまで更新された。修正後はBではcredential無しとして明示的に失敗し、root storeは不変。A→B→AのmultiplexでもBはA/rootのproviderを借りず、Aは前後で正常に自分のproviderを解決した。4つの新規 invariant test はbaseでred、修正後green、focused runは1337 tests passと報告されている。

### (2) 何が提案・推測段階か

Kamimusuhiで「各process/deviceが必ず別credentialを持つべき」とまでは言えない。同一個体の複数organが同一providerを共同利用することはあり得る。

一般化すべきなのは、**grantが見つからないことを、親namespace/root/default principalのgrantを使ってよい根拠にしない**こと。共有が必要なら明示的なdelegation/lease/capabilityとして表現する。

### (3) Kamimusuhiのどのサブシステムに関係するか

- Cognitive Action Router / tool-model routing
- external cognitive extensions
- distributed K-Edge / K-Core / K-Deep organs
- credential / capability store
- Continuity Kernel周辺のprincipal ownership
- `INV-006` distributed execution
- `INV-007` external intelligence attribution
- `INV-014` authority/provenance/liveness boundary

### (4) 借りられる設計・実装アイデア

```text
credential lookup(principal, provider)
  -> exact-principal grant
  -> explicit delegated grant / lease
  -> otherwise fail closed
```

- implicit root/global fallbackを持たない
- API keyの「copy」とOAuth/session grantの「delegation」を分ける
- refresh/rotationはgrant ownerのstoreにしかwriteしない
- copied secretにはorigin / copied_at / owner / revocation relationを残す
- single-use OAuthやrefresh tokenはcloneではなくper-principal sign-inを基本にする
- missing grant時は「どのprincipalが何を持たないか」をoperatorへ明示する

### (5) Kamimusuhiとの差分

Hermesのprofileはほぼsecurity namespaceだが、Kamimusuhiではdevice/process/organは必ずしも別個体ではない。そのため「全部credential分離」ではなく、**same self と same authority を同義にしない**設計が必要。個体内organであっても、そのorganに付与されていない外部権限をdefault rootから拾わせない。

### (6) 次に検証すべきこと

**`PrincipalCredentialIsolationBench-v0`**

- principal/organ Aはprovider PのAPI key + rotating OAuthを持つ
- Bはgrant無し
- Bからread / invoke / refresh / revoke / write-backを試す
- root/default/env fallback経由でもAのcredentialへ到達しないこと
- explicit delegated grantを発行した場合だけBが利用できること
- delegated grant revocation後、warm cache/background worker経由でも再利用できないこと
- A/Bが同一canonical selfに属する場合と別selfの場合の両方を試す

### (7) 重要度

**A** — multi-organ個体のauthority分離に直接刺さる。新しい大原則より、`INV-006/014` をcredential lookup/writebackまで貫通させるconformance testとして価値が高い。

## 2. A — Descendant Consequence Closure: parentを止めただけではagentを止めたことにならない

**一次資料**

- letta-ai/letta-code PR #4497 — *fix(subagents): terminate stopped agent process trees*  
  merged 2026-09-17 04:25:48 JST  
  https://github.com/letta-ai/letta-code/pull/4497

### (1) 何が実証済みか

従来の`TaskStop`はbackground controllerとheadless subagent processだけを止め、すぐ`killed: true`を返していた。active tool subprocessが存在すると、OSがそのtool processをreparentし、subagent headが終了した後もresource消費・実行を継続できた。

修正ではlocal subagentごとに専用process groupを作り、まずgroupへ`SIGINT`、2秒後も残るprocessをgroup単位でforce-killする。Windowsでは`taskkill /T /F`を利用し、`TaskStop`はexecutionがsettleしてから`killed: true`を返す。descendantがSIGINTを無視する実process testで、Linux 20/20、macOS 10/10でsurvivor無しと報告されている。

### (2) 何が提案・推測段階か

これはlocal OS process treeのclosureを実証したもので、HTTP request、queued job、remote GPU process、MCP side effectなど**すでに外へ出たeffect**までcancelできる証拠ではない。

Kamimusuhiではprocess-tree cancellationを必要条件の一つとして採りつつ、remote/distributed effectはlease/fence/idempotency/effect receiptで別に閉じる必要がある。

### (3) Kamimusuhiのどのサブシステムに関係するか

- Background / Deliberation / K-Deep subprocesses
- tool execution runtime
- distributed computational body
- external-effect tracking
- `INV-012` thought/utterance/execution/delivery distinction
- `INV-014` authority/liveness transition

### (4) 借りられる設計・実装アイデア

停止をsemantic lifecycleとして扱う。

```text
stop requested
 -> revoke execution lease
 -> graceful interrupt descendants
 -> bounded wait
 -> force local descendants
 -> fence remote/queued effects
 -> verify no remaining effect-capable owner
 -> STOPPED receipt
```

localではprocess group/cgroup/job objectを利用し、child/grandchildへexecution epochを伝播する。`stopped=true`はcontroller object消滅ではなく、**effect-capable descendantsのclosure確認後**に発行する。

### (5) Kamimusuhiとの差分

Kamimusuhiはネットワークnativeなbodyを想定するため、process groupだけでは不十分。K-Edge deviceやremote model/tool callは親processが死んでも継続し得る。そのためOS treeは「local body subtree」、Continuity Kernelのexecution leaseは「distributed causal subtree」を閉じる役割に分ける。

### (6) 次に検証すべきこと

**`DescendantConsequenceClosureBench-v0`**

- subagent → tool child → grandchildをspawn
- child/grandchildの一部はgraceful signalを無視
-同時にqueued jobとremote side effectを1件ずつ発行
- stop後、local descendant 0を確認
- remote側はfencing token失効または結果を`unknown/abandoned`としてauthority無しにする
- STOPPED receiptより後にcanonical state mutationが起きないこと
- crash/restart中のstopでも同じclosureを再構成できること

### (7) 重要度

**A** — 「cancelled result returned != future effect authority revoked」という既存論点を、実process-tree failureで強く裏付ける。local/remote両方を含むconsequence closure benchへ昇格させる価値が高い。

## 3. A — Replay Adapter Semantic Invariance: provider-wire shimを偽の履歴イベントにしない

**一次資料**

- NousResearch/hermes-agent PR #113419 — *fix(responses): replayed reasoning+tool rounds no longer carry a blank assistant item*  
  merged 2026-09-17 06:23:21 JST  
  https://github.com/NousResearch/hermes-agent/pull/113419

### (1) 何が実証済みか

HermesのResponses API adapterは、reasoning itemには後続assistant itemが必要だというfallbackを、実際には`function_call`がすでに後続している場合にも発火させていた。その結果、canonicalなturnに存在しない空のassistant messageがreasoningとtool callの間へ挿入され、以後のtool roundごとにmodelへ再提示されていた。

live failing-turn fixtureでは修正前に3つのblank carrier、5つの`reasoning -> function_call` adjacency破壊が生じ、修正後はblank 0、broken adjacency 0、5つのcall/output pairを維持した。別の実モデル再現ではblankあり4/4でdegenerate final、blankなし4/4 cleanという観測がある一方、20-rep/armの別A/Bではnullだったため、PR自身も**唯一の原因とは主張していない**。

### (2) 何が提案・推測段階か

Kamimusuhiで同じprovider adapter bugがあるとは未検証。ただし、model/providerごとにreasoning/tool schemaへ変換する際、transport上必要なshimが次turnで「本当にagentが発話したhistory」として再読される危険は一般的。

### (3) Kamimusuhiのどのサブシステムに関係するか

- Canonical Self History / Evidence
- model/tool orchestration adapters
- Global Workspaceからexternal modelへのrendering
- tool-call history / replay
- `INV-008` internal generation != fact
- `INV-011` canonical evidence > derived representation
- `INV-012` thought / utterance / tool effect distinction

### (4) 借りられる設計・実装アイデア

canonical events と provider wire items を別型にする。

```text
CanonicalEvent
  -> ProviderRenderer
  -> WireItem[]
```

- wire-only carrierには`synthetic_transport=true`を付ける
- synthetic itemをcanonical event logへwrite-backしない
- next-turn replayはcanonical eventから毎回再renderする
- reasoning / tool_call / tool_result adjacencyをsemantic invariantとしてtestする
- provider互換のためのplaceholderが必要でも、発話者やbelief provenanceを持たせない

### (5) Kamimusuhiとの差分

Kamimusuhiはcanonical evidenceとderived viewを原則上分離している。今回の価値は、**prompt rendering / provider compatibility層もderived viewであり、そこで生成されたartifactがcanonical historyへ逆流してはいけない**という具体化にある。

### (6) 次に検証すべきこと

**`ReplayAdapterSemanticInvarianceBench-v0`**

同一canonical episodeを複数backend（chat-completions / Responses / local OpenAI-compatible等）へrenderし、

- event count / speaker / control-vs-data type
- reasoning→tool_call→tool_result causal adjacency
- call ID / effect receipt binding
- synthetic carrierのcanonical非混入
- repeated replay後もevent graphが増殖しないこと

を比較する。可能なら実モデルでshim有無のA/Bを十分なrep数で行う。

### (7) 重要度

**A** — model交換可能なKamimusuhiではprovider adapterが常設境界になる。canonical historyを守るための小さく強い回帰テストに向く。

## 4. A — Hidden Body Fault Residual: nominal policyを保存したまま、観測履歴から身体故障を補償する

**一次資料**

- Linan Deng et al., *Residual Fault Adaptation for Dexterous In-Hand Manipulation Under Runtime Joint Faults*, arXiv:2609.17404  
  submitted 2026-09-15  
  https://arxiv.org/abs/2609.17404

### (1) 何が実証済みか

16-DoF LEAP Handのin-hand manipulationで、healthy teacherを凍結したnominal action pathwayとして残し、recurrent residual policyがproprioceptionとcommand-response historyからbounded correctionを出すRFAを提案している。

trainingではjoint locking / range restriction / intermittent dropout / reduced gain / command delay / command biasの6種類について、対象joint、severity、onsetをrandomizeし、弱いfault conditionをより多くsampleするadaptive samplingも使う。deployment時のcontrollerにはfault label、affected joint、controller-switch signalを与えない。

simulationではmixed runtime fault下でhealthy policyより改善を報告し、real robotでもsoftware-injected faultに対するzero-shot deploymentを示す。重要な限定として、論文のreal-robot faultは**物理的なアクチュエータ破損ではなくtarget-level command anomalyのsoftware injection**であり、multi-joint simultaneous faultもreported training distribution外。

### (2) 何が提案・推測段階か

このresidual構造をKamimusuhiの全homeostasisへ一般化できる証拠はない。特にsensor断線、network partition、VRAM pressure、model degradationはrobot joint faultとは異なる。

ただし「正常系controllerを壊して作り直すのではなく、まずnominal pathwayを保ち、history-conditioned bounded residualで適応する」比較baselineとして有用。

### (3) Kamimusuhiのどのサブシステムに関係するか

- K-Nerve / K-Edge low-latency control
- embodiment state / body calibration
- digital interoception / homeostatic regulation
- robotics / mobility/manipulation organ
- failure-adaptation memory

### (4) 借りられる設計・実装アイデア

```text
nominal controller (frozen / trusted)
       +
history-conditioned bounded residual
       -> actuator command
```

- fault diagnosisを必須にしないpassive adaptation baseline
- `commanded` と `realized/observed` を別streamで保持
- onsetがepisode途中でも適応できるrecurrent state
- residual magnitudeを安全envelopeでclamp
- adaptation trainingでfailure modeを均等にせず、失敗が多いmodeを再sample

### (5) Kamimusuhiとの差分

KamimusuhiのK-Nerveはidentity ownerではなく、reflex/fast control organ。したがってresidual policyが学習してもPersona Coreやcanonical selfを変える必要はない。またphysical fault adaptationは「self-improvement」より**body-organ calibration / compensation**として分離した方がよい。

### (6) 次に検証すべきこと

**`HiddenBodyFaultResidualBench-v0`**

まずsoftware bodyで小さく行う。

- nominal sensor→action policyを固定
- latency増大 / packet dropout / biased sensor / actuator gain低下 / delayed commandを途中から注入
- explicit fault classifier + switch、robust single policy、bounded recurrent residualを比較
- recovery latency、healthy-regime regression、tail latency、unsafe action rate、residual magnitudeを測る
- fault解除後にnominal regimeへ戻れるかも測る

### (7) 重要度

**A** — K-Nerve/K-Edgeに具体的な故障適応baselineを与える。生物学的homeostasisの証拠ではなく、工学的body compensationとして扱う。

## 5. B — Checkpoint lineage must migrate with identity rename

**一次資料**

- NousResearch/hermes-agent PR #113363 — *renamed profile keeps rollback history ...*  
  merged 2026-09-17 06:34:23 JST  
  https://github.com/NousResearch/hermes-agent/pull/113363

### (1) 何が実証済みか

Hermesのcheckpoint project identityがabsolute workdir hashに依存していたため、`profiles/old -> profiles/new`のrename後、refs/meta/ledgerが旧identity側に残り、rollback historyが見えなくなった。

### (3) 関係するサブシステム

- Continuity Kernel
- checkpoint / rollback / self-update
- software-body lineage
- identity migration

### (4) 借りられるアイデア

- rename/migrate対象をcanonical IDで列挙
- checkpoint/ref/ledger/recovery journalを同一migration transactionへ含める
- retryはidempotentではなく**ancestry-aware**にする
- target側がdivergeしたらoverwriteせずexplicit reconciliationへ送る

### (5) Kamimusuhiとの差分

前回dailyでprofile rename/tombstone自体は既に収載済み。今回の差分は、**active identity namespaceだけでなくrecovery lineageもmigration setへ含める**実証が加わった点。

### (6) 次に検証すべきこと

rename途中でcrashさせ、old/new両方に部分stateがある状態からretry。new側に新checkpointが増えているケースも含め、rewind/data loss無しで収束するかを確認。

### (7) 重要度

**B** — 新原則というより既存identity-migration設計のcoverage拡張。

## 7. B — Advisory cognitionは同じpersistent agentでも別execution laneへ隔離できる

**一次資料**

- letta-ai/letta-code PR #4501 — *feat(ci): add expert escalation after code review*  
  merged 2026-09-17 06:11:37 JST  
  https://github.com/letta-ai/letta-code/pull/4501

### (1) 何が実証済みか

通常のcode review後、同じAmelia agentが個人memoryのrouting ruleを読み、必要なら1人のdomain expertへ1問だけescalateするadvisory passが追加された。初期実装はcompleted review conversationをCloud経由でresumeしたが、live runでactive Amelia workと競合してtimeoutし得たため、fresh local `--new` conversationへ変更され、PR contextだけを取得する設計になった。

### (2) 何が提案・推測段階か

このworkflowから一般的な「subagentは全部new conversationにすべき」とは言えない。長期memoryを共有したいケース、同一episode continuityが必要なケースもある。

- background cognition / critic / verifier
- expert/model routing
- persistent agent identity vs episode identity
- resource scheduling

### (4) 借りられるアイデア

- same persona/agent memoryを使っても、advisory execution laneは別conversationにできる
- expert routing knowledgeとactive task contextを分離
- advisory failureをmain workflowのsuccess/failureと分離
- escalatorは「一人・一問」などbounded output contractを持つ

### (5) Kamimusuhiとの差分

Kamimusuhiでは既に`agent identity != episode identity`を強く扱っているため新規性は低い。今回は**同じpersistent selfのbackground criticがprimary episodeをresumeしなくてもよい**実運用例として見る。

### (6) 次に検証すべきこと

`AdvisoryLaneInterferenceBench`:
main conversationが長時間tool call中にcritic/verifierを起動し、shared memoryは読めてもactive continuation authorityやin-flight contextを奪わず、CPU/model quota競合もboundedであることを確認。

### (7) 重要度

**B** — episode identity分離の実装prior artとして有用だが、既存Kamimusuhi論点の補強。

# 既存docsへの追記候補

## `architecture.md` / `spec.md`

今すぐ新しいnormative invariantを増やすより、既存`INV-006/011/012/014`のテスト項目として次を候補にする。

1. **Credential non-inheritance**  
   grant absenceはancestor/root/default grantの暗黙継承を意味しない。
2. **Cancellation consequence closure**  
   parent/controller停止をSTOPPEDと記録する前に、local descendantとdistributed effect authorityを閉じる。
3. **Replay renderer purity**  
   provider-specific synthetic transport itemはcanonical historyへ昇格しない。
4. **Recovery lineage migration coverage**  
   principal/path renameのmigration setへcheckpoint/ref/ledger/recovery metadataを含める。
