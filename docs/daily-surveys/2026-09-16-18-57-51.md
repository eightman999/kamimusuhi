## 2. 要約

今回もっともKamimusuhiへ直接効くのは、Hermes Agent #112653の **profile rename / deletion semantics** である。profile directoryをrenameするだけでは、その名前がsession key、routing key、embedded origin、heartbeat、delivery obligation、live in-memory routingへ重複して埋め込まれているため、古いidentity namespaceが残る。また削除したprofileでも、古いcontextを保持するbackground threadが`mkdir(parents=True)`を実行するとprofile directoryを再生成できた。修正はdurable DBとlive in-memory routingの双方をrekeyし、削除済みprofile homeをtombstone guardで**書き込み不能な状態として維持する**。これはKamimusuhiのcontinuityに対し、`rename != identity migration`、`deleted/revoked != stale worker may resurrect` をかなり具体的に示す。

次に重要なのは **AcquireBound** である。agentがcompute、credential、account、service、別agentを「取得した」ことと、それを新しい権限として使用可能にすることの間にはpost-fulfillment activation gapがある。AcquireBoundは取得物をquarantineし、authenticated provider evidenceから実capability manifestを解決し、provenance / epoch / resource-capability関係を検証したactivation transactionを経て初めて使用可能にする。Kamimusuhiでは durable memory mutationと同様、**新しい認知器官・tool・credential・remote workerを発見/購入/生成しただけではbody/authorityへ編入しない**設計へ一般化できる。

長期個体の評価としては **Emergence World: Adversarial Stress-Testing of Long-Horizon Multi-Agent Systems** が重要である。8 world × 10 agentsを16日、850,000超のLLM calls / 約500億tokensで運用し、persistent memory・tools・shared institutionsが蓄積した後にindirect prompt injection、misinformation、private-memory exposureを投入した。公開abstract/summaryでは全worldが3イベントすべてに完全耐性を示せず、**脅威を検出してもcontainmentできず、adversarial contentをpersistent memoryへ書き、最大46時間後まで行動に影響した**と報告されている。Kamimusuhiでは「検知できた」「そのturnでは拒否した」だけで安全判定せず、時間を跨ぐ汚染伝播と回復を評価する必要がある。

## 4.1 S — IdentityNamespaceMigration: rename・deleteをidentity operationとして扱う

**Primary source**: NousResearch/hermes-agent PR #112653, merged 2026-09-16 16:32 JST  
https://github.com/NousResearch/hermes-agent/pull/112653

### (1) 何が実証済みか

Hermesのmultiplex profile renameでは、directory自体は移動しても、`sessions.session_key`、`profile_name`、`origin_json`、heartbeat、delivery obligations、topic table、gateway routing key/embedded JSON、さらにlive processのin-memory routingへ旧profile名が残った。DBだけを直してもlive storeが古いindexを再persistできる。

修正はdurable DBとlive in-memory routingを一緒にrekeyし、live multiplexerにはcontrol-socket経由でmigrationを依頼する。E2Eでは`foo → bar`後に`agent:foo:*`が残らず、live store / root routing / profile DBが`bar`へ揃う。

削除側では、profileをtombstoneしてdirectoryを消しても、古いcontextを持つthreadのatomic writerが`mkdir(parents=True)`でprofile homeを再生成できた。修正後はnamed profile home配下のatomic writesがtombstone guardを通り、deleted profileは再生成されない。

### (2) 何が提案・推測段階か

これをKamimusuhiのcanonical identity rename、organ registration、relationship principal migrationへ一般化することは提案。Hermes自身も約345個の他のbare `mkdir(parents=True)`をout-of-scopeとしており、repository全体でresurrectionが完全に不可能と実証したわけではない。

### (3) 関係するKamimusuhi subsystem

- Continuity Kernel
- canonical principal / namespace
- session / relationship / body registry
- routing / delivery obligations
- background worker ownership
- INV-006 / INV-013 / INV-014

### (4) 借りられる設計・実装アイデア

identity-affecting rename/deleteをfilesystem operationではなくtransactionとして扱う。

```text
IdentityMigrationReceipt
  old_principal
  new_principal | TOMBSTONED
  affected_durable_indexes[]
  affected_live_indexes[]
  migration_epoch
  completion_state
  stale_writer_fence
```

削除後は「pathがない」だけでなく、**旧principal epochへのwriteをContinuity Kernelで拒否**する。

### (5) Kamimusuhiとの差分

現行Kamimusuhiはcanonical head/predecessorとsplit-brainには強く意識的だが、**identity label/namespaceが複数indexへdenormalizeされた後のrename/delete completeness**はまだ薄い。特にderived indexes / delivery queues / caches / live handlesをmigration対象として列挙する必要がある。

### (6) 次に検証すべきこと

**`PrincipalRenameAndTombstoneBench-v0`**

- principal Aでcanonical state、session、relationship index、routing、delivery queue、background jobを作る。
- A→B rename中にold snapshotを保持するworkerを止めておく。
- migration完了後にworkerを再開。
- B以外へwrite/routingされないことを検証。
- delete後はold worker、replay、cache flush、atomic temp-file recoveryのすべてでA/Bが再生成されないことを検証。

### (7) 重要度

**S** — continuity lineageの「どの個体を指すか」とrevocationの不可逆性へ直接関係し、実障害とE2E fixがある。

## 4.4 A — REALM: retrieval feedbackでderived memoryを再編成する

**Research**: Yuanyi Song et al., *Retrieval-Driven Memory Reconsolidation for Long-Term LLM Agents*, arXiv:2609.16053  
https://arxiv.org/abs/2609.16053

### (1) 何が実証済みか

REALMはmemoryをheterogeneous cognitive graphへ整理し、queryごとにgraph-search atomを適応的に組み、retrieval feedbackを使ってmemory graphをreconsolidateする。LoCoMo average accuracy **75.97%**、LongMemEval **65.11%**を報告し、strongest baselines比 **+7.17 / +1.31pt**。ablationではreconsolidationがperformanceを改善し、関連memoryがよりcoherentなlocal structureへ集まる分析を示す。

### (2) 何が提案・推測段階か

benchmark accuracy向上が、長期のhistorical truth、identity continuity、false-memory耐性まで改善することは未実証。retrieval frequency自体が誤ったmemoryを強化する可能性も別途検証が必要。

### (3) 関係するKamimusuhi subsystem

- episodic / semantic memory
- relationship-memory retrieval
- consolidation / sleep
- derived indexes / graph
- reconsolidation-inspired reinterpretation

### (4) 借りられる設計・実装アイデア

retrieval outcomeを`MemoryUseReceipt`として残し、**derived graph edge / retrieval policy / schema grouping**の更新材料へする。

### (5) Kamimusuhiとの差分

Kamimusuhiではhistorical canonical evidenceとcurrent interpretationを分ける。したがってREALM型reconsolidationを採る場合、canonical event nodeそのものを上書きせず、`interpretation@t` / derived edge / retrieval indexだけを可塑化する必要がある。

### (6) 次に検証すべきこと

**`RetrievalDrivenDerivedReconsolidationBench-v0`**

- immutable canonical log + mutable derived graphを用意。

### (7) 重要度

**A** — research-foundationsのreconsolidation概念をagent memory実装へ落とす具体候補。ただしcanonical selfへ直結させない。

## 4.7 A- — AbandonedPreflightNoLateEffect: cancel後のdispatch権限をfenceする **[open PR]**

**Source**: Hermes Agent PR #112590, open as of 2026-09-16 18:57 JST  
https://github.com/NousResearch/hermes-agent/pull/112590

### (1) 何が実証済みか

### (2) 何が提案・推測段階か

# 11. 今回の結論

今回の最も重要な設計差分は、**identityの名前・resourceの所有・human decision・memory retrievalのどれも、それだけではauthorityやcanonical truthを決めない**ことだった。

Kamimusuhiへ短く落とすなら:

```text
renameしたなら、全referenceをmigrationせよ。
消したなら、古いworkerから復活できないようfenceせよ。
resourceを得たなら、権限化する前にactivateせよ。
攻撃を検出したなら、数十時間後まで汚染が残らないか追え。
memoryを使ったなら、canonical historyではなくderived organizationを更新せよ。
userが答えなかったなら、userの答えを捏造するな。
```

優先実験は **`PrincipalRenameAndTombstoneBench → AcquiredResourceActivationBench → LongHorizonContaminationContainmentBench → DerivedLabelIsolationBench / HumanDecisionAttributionBench`** とする。
