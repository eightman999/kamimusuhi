# 分野別項目

## 1. A — TranscriptEventIdentityDecoration: transport metadataの差を「別の記憶」と誤認しない

**一次資料**

- NousResearch/hermes-agent PR #114423, created 2026-09-18 06:11 JSTごろ, 調査時点 open / unmerged  
  https://github.com/NousResearch/hermes-agent/pull/114423

### (1) 何が実証済みか

`/v1/responses` の multi-turn chainingで、stored transcriptが `3 -> 8 -> 21 -> 61 -> 121 -> 258 -> 517 -> 1040 -> 2077 -> 4178` rowsと増えるreproが報告されている。原因は、過去履歴prefixかどうかをwhole-dict equalityで判定していた一方、production rowには後から `timestamp`、`_db_persisted`、`_row_id`、`platform_message_id` 等のtransport/storage metadataが追加され、同じ`role/content`でもdictとして一致しなくなったことだった。その結果、既にpriorを含むfull transcriptへ再度`prior + current_user`をprependし、重複がcompaction後のsession DB/UIへも残る。

PRはprefix判定をsemantic fieldsへ限定するregression testを追加している。ただし**未merge**なので、upstreamの確定仕様ではなく、再現付きfailure evidenceとして扱う。

### (2) 何が提案・推測段階か

PRの修正はHermesの特定adapterで`(role, content)`比較へ戻すもの。これはKamimusuhiのcanonical event identityとして十分ではない。同じ人が同じ文を二度発話することは合法なので、canonical historyで`role/content`一致をdedupe keyにすると逆方向のlossが起きる。

### (3) 関係するKamimusuhiサブシステム

- canonical episode / autobiographical event log
- Global Workspace → episode ingestion
- model/provider replay adapter
- compaction / summary / derived view rebuild
- `INV-009`, `INV-011`, `INV-012`, `INV-013`

### (4) 借りられる設計・実装アイデア

**cognitive event identity** と **transport envelope identity** を分ける。

```text
CanonicalEvent
  event_id
  producer_principal
  episode_id
  semantic_payload
  event_time
  predecessor / causal refs

TransportEnvelope
  row_id
  provider_message_id
  timestamp/cache flags
  delivery metadata
  -> canonical_event_id
```

adapterが「full transcriptかturn-onlyか」を判断する場合は、既存event id / canonical referenceを優先し、semantic equivalenceは限定的なcompatibility fallbackに留める。

### (5) Kamimusuhiとの差分

Kamimusuhiは既にcanonical evidenceとderived viewを分離しているが、**同じsemantic eventへtransport metadataが積み増された時のidentity contract**は独立benchとして明示されていない。既存の`ReplayAdapterSemanticInvarianceBench`はprovider shimが偽のassistant eventを作る問題で、本件は**同じeventを別recordと誤認して複製する問題**。

### (6) 次に検証すべきこと

**`TranscriptEventIdentityDecorationBench-v0`**

- 同じcanonical eventへtransport metadataを0/1/5種類付加
- full-history / turn-only / compacted-historyの3形態でreplay
- event countとevent_id setが不変であること
- 同文の正当な反復発話2件はdedupeされないこと
- adapter metadata変更後もcanonical episode digestが不変であること

### (7) 重要度

**A** — autobiographical historyの増殖・人格/関係記憶の誤学習へ直接つながるため高優先。

## 2. A — TurnTerminalStateClosure: turnが終わる時、全tool callを意味のあるterminal stateへ閉じる

**一次資料**

- NousResearch/hermes-agent PR #114442, created 2026-09-18 06:48 JSTごろ, 調査時点 open / unmerged  
  https://github.com/NousResearch/hermes-agent/pull/114442

### (1) 何が実証済みか

ACP clientでfinished turnのtool callが永久に`in_progress`表示になるfailureが報告されている。通常成功callは`tool.completed`で閉じられるが、blocked/denied callはcompletion event自体を生成しないためopen mapに残る。PRはturn-end sweepで未閉鎖callを`failed`へ移し、同一tool名の複数callを二重closeしないguardを追加。focused suite 177 pass、実Paseo 0.8.0で`read/edit: running`が`read: completed / edit: failed`へ変わったと報告している。

興味深い副作用として、downstream continuationがtool statusをwork evidenceとして利用しており、terminalization後にsuperseded agentを正しくretireできたとされる。

### (2) 何が提案・推測段階か

`failed`がdenied/blocked/cancelled/abandonedすべての最終semanticとして最適とは限らない。Kamimusuhiでは`DENIED_BY_USER`、`POLICY_BLOCKED`、`CANCELLED_BEFORE_EFFECT`、`UNKNOWN_EXTERNAL_OUTCOME`等を分ける必要がある。

### (3) 関係するサブシステム

- Action Router / tool execution ledger
- human authorization
- continuation / handoff / retirement
- notification / delivery
- `INV-012`, `INV-014`

### (4) 借りられる設計・実装アイデア

turn/episode境界に**open-effect audit**を置く。

```text
for call in calls_started_this_turn:
    require call.status in TERMINAL_OR_EXPLICITLY_DETACHED
```

terminalは単なるUI状態ではなく、後続agentが「何が起きたか」を判断するevidenceにする。

### (5) Kamimusuhiとの差分

Kamimusuhi specはthought / utterance / confirmation / execution started / success / deliveryを区別している。本件はその状態機械に**turn終了時のclosure invariant**を加える実装証拠。外部jobが意図的にdetached executionへ移る場合だけ例外とし、ownership receiptを要求すべき。

### (6) 次に検証すべきこと

**`TurnTerminalStateClosureBench-v0`**

- success / denied / policy-block / timeout / cancel / executor crash / detached remote run
- turn終了直後にopen stateが残らないこと
- detachedはremote owner + observation handleを持つこと
- 同名tool call複数件でFIFO/ID誤closeがないこと
- terminal statusだけから「成功」を推測しないこと

### (7) 重要度

**A** — INV-012/014を実行時に閉じるための直接的failure evidence。

## 3. A — EvaluationEvidenceCompleteness: missing traceを0点・無害・無コスト扱いしない

**一次資料**

- NousResearch/hermes-agent PR #114436, created 2026-09-18 06:40 JSTごろ, 調査時点 open / unmerged  
  https://github.com/NousResearch/hermes-agent/pull/114436

### (1) 何が実証済みか

既存analysisが、missing trace dataをzero-valued evidenceとして扱い、unrecorded cellをdenominatorから落とし、さらにarm間を同じ`run_id`でpairせず比較できるという構造的問題をsynthetic fixtureで再現した。PRはlocal/offlineのfail-closed evaluatorを追加し、cell completeness、run_id pairing、task-clustered seeded bootstrap、guardrail、battery identityを記録する。新規13 testsとeval suite 16 testsがpassしたと報告している。

### (2) 何が提案・推測段階か

このPRは**live batteryを実行していない**。したがって新evaluatorが実運用でpromotion qualityを改善した証拠ではなく、evaluation semanticsのhardening proposalである。また自動promotionやschedulerは含まれない。

### (3) 関係するKamimusuhiサブシステム

- Persona Core / router / memory candidate self-improvement
- A/B eval / regression gate
- evaluator lineage / benchmark provenance
- Cognitive Budget optimization

### (4) 借りられる設計・実装アイデア

promotion reportをscoreだけでなく**evidence completeness contract**にする。

```text
EvalVerdict:
  battery_id
  candidate_revision
  baseline_revision
  paired_run_ids
  expected_cells
  observed_cells
  missing_cells
  CI / guardrails
  verdict = PASS | FAIL | INCOMPLETE
```

`INCOMPLETE`を0点へ暗黙変換しない。

### (5) Kamimusuhiとの差分

既存`EvaluatorLineagePoisoningBench`は評価器そのものの汚染、`HarnessCounterfactualRobustnessBench`はprotocol shortcut。本件はより下層の**measurement completeness / pairing integrity**であり、善意のbenchmarkでも欠測処理だけでpromotion判断が歪む。

### (6) 次に検証すべきこと

**`EvaluationEvidenceCompletenessBench-v0`**

- candidate/base 20 paired seeds
- 1, 5, 20%のtrace/cell欠損を故意注入
- naive zero-fill / drop-missing / fail-closedのpromotion率比較
- run pairingを崩した時のfalse promotion率を測定
- report自体のbattery/version digestを固定

### (7) 重要度

**A** — self-improvementを安全に回す前提条件。欠測を性能として数えないことはモデル非依存。

## 4. A — CERA-MoA: specialistが学習するならrouterも能力変化へ追随する

**一次資料**

- Jiang et al., *CERA-MoA: Co-Evolving Routing Mechanisms with Continually Learning LLM Agents*, arXiv:2609.18779, submitted 2026-09-16  
  https://arxiv.org/abs/2609.18779

### (1) 何が実証済みか

CERA-MoAは、agent policy更新とrouter更新を同じclosed loopへ入れる。router側は共有backboneのmid-layer hidden statesからpredictive familiarityを推定し、固定top-kではなくcumulative thresholdで最小agent subsetを選ぶ。training中はexploration bonusを入れ、query allocation自体がspecializationを形成する。

論文表ではQwen3-4B系の平均がbase 49.6、RouteMoA 53.1、AT-GRPO 61.0に対しCERA-MoA 63.2、Llama-3.2-3B系ではbase 33.6、RouteMoA 43.3に対しCERA-MoA 47.9と報告されている。複数domainでstatic/fixed-workflow系baselineを上回るという主張には実験表とablationが付く。

### (2) 何が提案・推測段階か

hidden-state familiarityがKamimusuhiのheterogeneous provider/API群で同様に機能するとは未証明。closed-source APIではmid-layer stateを取れない。またcompetence scoreが安全性・authority・privacyまで表すわけではない。

### (3) 関係するKamimusuhiサブシステム

- Cognitive Action Router
- external model/tool specialist pool
- K-Core / K-Deep resource selection
- model capability registry
- Cognitive Budget

### (4) 借りられる設計・実装アイデア

specialistのversion/model/skillが変わったらrouter calibrationを**別epochとして再評価**する。

```text
SpecialistCapabilityReceipt:
  specialist_id
  version/model_id
  eval_epoch
  domains + confidence
  cost/latency

RouterPolicy:
  calibrated_against = {receipt digests}
```

agent更新後に古いrouter scoreを永久利用しない。

### (5) Kamimusuhiとの差分

CERA-MoAは複数LLM policyを共同学習するMoAであり、Kamimusuhiでは外部modelは**identity-neutralなcognitive resources**。routerとspecialistのco-adaptationは借りても、外部agentのweight変化をPersona identity mutationへ直結させない。

### (6) 次に検証すべきこと

**`RouterCapabilityCoEvolutionBench-v0`**

- 3 specialistのうち1つだけ能力分布を意図的にfine-tune/replace
- frozen router vs periodic recalibration vs online banditを比較
- accuracy / cost / latency / misroute率 / safety policy breachを測定
- provider version change後のstale capability receiptを拒否できるか確認

### (7) 重要度

**A** — Kamimusuhiのmodel/tool orchestrationが長期間変化する前提なら、router driftを第一級に扱う必要がある。

## 5. A — Evolutionary Ensemble Search: 子個体は親の成功証拠を相続せず、自分で検証する

**一次資料**

- Madrigal-Cianci & Chordia, *Evolutionary Ensemble Search: Council-Guided Program Evolution with Persistent Memory*, arXiv:2609.17590  
  https://arxiv.org/abs/2609.17590

### (1) 何が実証済みか

EESはrole-specialized council、orchestrator、evolutionary engine、persistent session/problem memoryを組み合わせ、code mutation / pipeline edit / crossoverでcandidateを生成する。重要なのは**each child must execute and acquire its own validation evidence**と明示している点。公開MLE-bench Lite development ledgerでは22 tasks中19でmedal-threshold artifact、best outcomesは11 gold / 5 silver / 3 bronzeと報告する。

同時に著者は、grade feedback between runs、external-source routes、mixed confirmationが入っているため、このaggregateを**blind autonomous-agent success rateではない**と明記している。

### (2) 何が提案・推測段階か

cross-modal development campaignの実績であり、open-ended artificial lifeやPersona Coreの安全な自己改変を証明していない。persistent lessonsが長期に汚染されないことや、crossover後のsemantic regressionを完全検出できることも未証明。

### (3) 関係するKamimusuhiサブシステム

- procedural skill evolution
- harness / workflow candidate search
- self-improvement evaluator
- derived skill/library memory
- lineage-aware candidate archive

### (4) 借りられる設計・実装アイデア

**validation receiptはcandidate-local**にする。

```text
Candidate B = mutate(Candidate A)
A.validated == true
DOES NOT imply
B.validated == true

B must own:
  artifact digest
  execution trace
  environment/battery identity
  validation receipt
```

archiveはbest一本だけでなく、異なるfailure profileを持つalternativeを保持する。

### (5) Kamimusuhiとの差分

Kamimusuhiではcanonical self/identity mutationはさらに強いauthority gateを必要とする。EESの考え方はまず**procedural/harness candidate lane**へ限定して借りるべきで、successful childをそのままPersona Coreへ焼き込まない。

### (6) 次に検証すべきこと

**`DescendantIndependentEvidenceBench-v0`**

- validated parentから100 descendantsをmutation/crossover生成
- parent receiptを誤ってinheritするnaive systemと比較
- descendant自身を再実行しないfalse promotion率を測定
- environment/version変化後のreceipt invalidationも追加

### (7) 重要度

**A** — self-improvement lineageで「血統」と「証拠」を分離する明快な実装原則。

## 6. B — Structured unpredictabilityは「内面」やpath dependenceの証明ではない

**一次資料**

- Cochinescu, *Entropy in Conversational AI: Structured Unpredictability as Inferrable Interiority*, arXiv:2609.19044  
  https://arxiv.org/abs/2609.19044

### (1) 何が実証済みか

persistent low-dimensional style/attention stateを持つwrapperが複数responseからnovelty/state affinityで選択する仕組みを実装。real-model grid（Qwen2.5-1.5B-Instruct-4bit, 56 sequences/arm）ではlexical noveltyはcontrolより上がった一方、事前登録されたjoint novelty-consistency criterionは**失敗**。twin separationも成立せず、著者自身が「path dependenceを支持しない」「perceived mind / consciousnessはtestしていない」と限定している。

### (2) 何が提案・推測段階か

「観察者が推論できるinteriority」というdesign target自体は概念提案。今回の結果はむしろ主要criterionのnegative resultであり、persistent hidden stateが人格的内面を作ることを示していない。

### (3) 関係するKamimusuhiサブシステム

- Persona Core / regulatory style state
- persistent hidden state
- self-model / narrative identity evaluation
- HCI / perceived continuity
- `INV-010`

### (4) 借りられる設計・実装アイデア

**memory-reset ablation / twin separation**をKamimusuhi自身のpersistent state評価へ借りる。見かけの一貫性ではなく、同一初期条件から異なる経験を与えたtwinsが後に因果的に分離するかを測る。

### (5) Kamimusuhiとの差分

Kamimusuhiのidentityはstyle variabilityで定義しない。canonical history、relationship lineage、authority continuity等が主であり、behavioral path dependenceはその一部の検証結果にすぎない。

### (6) 次に検証すべきこと

**`PersistentStateBehavioralCausalityBench-v0`**

- twin A/Bへ異なる長期episodeを与える
- transcript-visible contextを揃えたprobeを後で実施
- persistent stateあり / reset / shuffled historyを比較
- divergenceだけでなくsource-attributable causalityを測る

### (7) 重要度

**B** — 「自然な揺らぎ」を人格証拠にしないための良いnegative-control研究。

## 7. B — Ghost writer: taskをforgetしてもwriter registryが残れば偽の同時実行が生き続ける

**一次資料**

- NousResearch/hermes-agent PR #114448, created 2026-09-18 06:57 JSTごろ, 調査時点 open / unmerged  
  https://github.com/NousResearch/hermes-agent/pull/114448

### (1) 何が実証済みか

`forget_task()`がread stampは解放する一方、owned `_last_writer` entriesを残し、終了済みtaskを「concurrent sibling」として報告し続けるreproがある。PRはforget時purgeと、read時に1時間超entryをevictするfallbackを追加し、exact reproがquietになることとfocused registry testsを報告している。

### (2) 何が提案・推測段階か

1時間TTLはHermesのoperational heuristicであり、Kamimusuhiのauthority semanticsへそのまま持ち込むべきではない。長時間jobではalive writerを誤expireし得るし、canonical authorityの失効をwall clockだけで決めるのは危険。

### (3) 関係するKamimusuhiサブシステム

- distributed workspace / file mutation
- worker/task ownership
- concurrency diagnostics
- lease / generation fencing

### (4) 借りられる設計・実装アイデア

writer ownershipを`task_id`だけでなく`owner_generation + lease/retirement receipt`へbindし、task retirementと同じtransactionでregistry ownershipも閉じる。

### (5) Kamimusuhiとの差分

既存のgeneration-fenced retirementはbackend/sessionの退役。本件は**resource-specific writer shadow state**が退役に追随しない問題で、より細粒度。

### (6) 次に検証すべきこと

**`GhostWriterLeaseRetirementBench-v0`**

- normal completion / crash / retry / owner generation replacement
- retired writerがconflict警告へ残らないこと
- live long-running writerはTTLだけで消えないこと
- recovery後はowner-generation proofでrebindすること

### (7) 重要度

**B** — distributed bodyでのfalse conflict/liveness低下を防ぐ補助invariant。

## 8. B — 日本語圏一次運用記録: 「multi-agent化」が11件の障害原因を1件も解かなかったケース

**discovery / primary implementation record**

- Qiita, 田前秀樹, 「複数のエージェントを協調させる」という発表が同じ週に重なった日、自分の障害記録11本を数え直したら、それで防げたものはゼロだった, 2026-09-11  
  https://qiita.com/Hideki_Tamae/items/ca8dbed6a5cd5eba0147

### (1) 何が実証済みか

## 9. B — Route-neutral execution receipts: fallback/model routeとaudit lineageを分離する案

**一次資料**

- NousResearch/hermes-agent PR #114447, 調査時点 **draft / unmerged**  
  https://github.com/NousResearch/hermes-agent/pull/114447

### (1) 何が実証済みか

## 今回の圧縮結論

```text
metadataが増えた
!=
記憶が増えた

turnが終わった
!=
全effectの意味が確定した

記録が無い
!=
ゼロだった

専門家が学習した
!=
昔のrouterが今も正しい

親が通った
!=
子も通った

振る舞いが少し揺らいだ
!=
内面や個体史が実証された
```

Kamimusuhiに最も直接的なのは、**canonical event identityをtransport metadataから切り離すこと**、**effect stateをturn境界で閉じること**、**self-improvement評価の欠測をfail-closedにすること**の3点。これらはモデル性能ではなく、長寿命個体の履歴・権限・検証の整合性を守るruntime contractである。
