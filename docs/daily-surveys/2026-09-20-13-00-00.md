## 4.1 A+ — ContinuationWakeupOwnership: 「続ける」と決めても、自分で次turnを起こせなければ長期自律ではない

**Primary source:** Hermes PR #116619  
https://github.com/NousResearch/hermes-agent/pull/116619

### (1) 何が実証済みか

Hermes の `/goal` session では goal judge が `should_continue=true` を返し、ユーザーにも「continuing」と通知しているのに、次のagent turnが**無関係な新規 inbound message が来るまで開始されない** failure が再現された。

root cause は post-turn hook が continuation event を per-session FIFO へ enqueue する時点が、通常の turn-end drain より後だったこと。もう一つの orphan rescue path は新しい inbound message が来たときしか走らないため、idle session では永久に continuation が眠る。

修正は、enqueue 後に session が idle であり、FIFO slot がまだ未claimなら、通常の inbound と同じ `handle_message(...)` entry pointへactive drainする。targeted 6 tests、goal/loop/busy 周辺 125 tests pass（1 skip）を報告し、baseへ戻すと元症状を再現する red-proof も記載している。調査時点では open PR。

### (2) 提案・推測段階

Kamimusuhi の default cognition / sleep scheduler / unresolved-goal loop に同じ bug が存在することは未実証。また continuation の自動起動は runaway loop と表裏なので、単に wakeup を増やせばよいわけではない。

### (3) 関係サブシステム

- default cognition / background cognition
- Global Workspace episode lifecycle
- Cognitive Action Router
- K-Core / K-Deep long-horizon task
- scheduler / durable obligation / liveness

### (4) 借りられる設計・実装アイデア

「次へ進む」という認知判断と「誰が次のturnを起動するか」を別stateにする。continuation receipt に少なくとも `continuation_id / due-or-immediate / wakeup_owner / predecessor_turn / budget / cancellation authority` を持たせ、**外部event非依存のwake path**を要求する。

### (5) Kamimusuhiとの差分

Hermes は gateway session 内の goal continuation。Kamimusuhi では default cognition、sleep/replay、remote tool result、robot observation、unfinished commitment など、複数の internal trigger source がある。一方、canonical mutationやphysical actuationの自動連鎖はより強い admission/budget gate を必要とする。

### (6) 次に検証すべきこと

**`ContinuationWakeupOwnershipBench-v0`**

- 外部messageを完全に止めた状態で multi-turn internal goal が最後まで進むか
- turn completion → next wakeup の p50/p99 latency
- restartを跨いでcontinuation obligationが失われないか
- cancel / budget exhaustion / stale goal で確実に停止するか
- duplicate wakeup が二重turnを作らないか
- auto-continuation が canonical write / actuation authority を自動拡張しないか

### (7) 重要度

**A+** — 「requestが来た時だけ賢いwrapper」から内部起動性を持つ人工個体へ進む上で、livenessの根幹。

## 4.2 A — DependencyStructureOrchestration: multi-agentの価値は人数ではなくtask dependency graphで決まる

**Primary source:** Yuan et al., *Rethinking Multi-Agent Collaboration: When More Is Less*, arXiv:2609.19759  
https://arxiv.org/abs/2609.19759

### (1) 何が実証済みか

論文は single-agent harness と multi-agent collaboration を系統比較し、**long-horizon かつ依存関係が疎なtaskではmulti-agentが有利になりやすい一方、tightに逐次依存するworkflowではsingle-agent harnessが優位**と報告する。提案する SAIGE はagentをon-demand spawnし、semantic dependencyをgraph edgeとして扱う。agent poolを増やす、recursionを深くするといった単純scale-upは一貫して改善しない。

### (2) 提案・推測段階

この境界がKamimusuhiの研究・memory maintenance・robotics taskへそのまま転移することは未実証。benchmarkのtask decomposition品質にも依存する。

### (3) 関係サブシステム

- Cognitive Action Router
- K-Deep research / planning
- subagent / external model orchestration
- Cognitive Budget
- Global Workspace integration

### (4) 借りられる設計・実装アイデア

agent数を固定policyにせず、task graph の `dependency density / sequential critical path / parallelizable branches / cross-branch context volume` を routing feature にする。

### (5) Kamimusuhiとの差分

Kamimusuhiではsubagentは「別個体」ではなく認知資源/workerとして扱うケースが多く、さらにprovenance、identity、write authorityを統合する必要がある。単なるtask score以外に、merge cost、audit cost、evidence duplication、authority surfaceも評価対象にする。

### (6) 次に検証すべきこと

**`DependencyStructureOrchestrationBench-v0`**

同一taskを dependency graph の疎密だけ変え、single-agent / fixed multi-agent / adaptive spawn を比較する。

- success / correctness
- token・cost・wall time
- duplicated context traffic
- merge conflicts
- provenance completeness
- false consensus / correlated failure

### (7) 重要度

**A** — 「複数agentを使うか」をモデルサイズや流行ではなく、task構造とCognitive Budgetへ落とせる。

## 4.3 A — RoleScopedFailureMemory: failure lessonは失敗種別と責務へbindする

**Primary source:** Ghaffari et al., *LearnActCoder: Role-Aware Error Memory for Adaptive Clinical Coding Agents*, arXiv:2609.19721  
https://arxiv.org/abs/2609.19721

### (1) 何が実証済みか

LearnActCoder は少量の labeled LEARN batch から structured MistakeKDB を作り、**false-negative lessonをrecall-oriented Coder、false-positive lessonをprecision-oriented Judge**へ振り分ける。150 matched MIMIC-III notes で structured MistakeKDB は CPT F1 を +5.9pt 改善し、raw examples / reflection-style memory は no-memory baseline 近傍だった。ICD-9 improvement は有意でなく、MIMIC-IVではprecision↑ / recall↓で F1 は統計的に不変。1,000 held-out MIMIC-IIIではoperating pointの安定性を報告する。著者は retrospective evaluation であり absolute CPT performance が低いことも明記する。

### (2) 提案・推測段階

臨床codingのCoder/Judge分業が一般agent architectureへ直接一般化できるとは限らない。改善はtask/label体系依存。

### (3) 関係サブシステム

- procedural memory
- reflection / failure analysis
- verifier
- Cognitive Action Router
- self-improvement / skill update

### (4) 借りられる設計・実装アイデア

`FailureLesson`に `failure_type / responsible_role / anti-pattern / positive repair / applicability / evidence / expiry` を持たせ、全componentのpromptへglobal注入しない。

### (5) Kamimusuhiとの差分

Kamimusuhiはidentity/persona/relationship/canonical memoryも持つため、failure lessonをself-beliefへ昇格させない。まずprocedural/role-local derived memoryとして扱い、繰り返し検証されたものだけをstable skillへpromotionする。

### (6) 次に検証すべきこと

**`RoleScopedFailureMemoryBench-v0`**

同じfailure corpusから、(a) global reflection memory、(b) role-scoped memory、(c) no memory を作り、false positive / false negative / latency / cross-role regression / irrelevant-trigger rateを比較する。

### (7) 重要度

**A** — memory量より「誰がそのlessonを読む権利・必要があるか」を設計する材料。

## 4.4 A — CognitiveTurnIdentity: session identityだけでは一回の認知episodeを監査できない

**Primary source:** Hermes PR #116615  
https://github.com/NousResearch/hermes-agent/pull/116615

### (1) 何が実証済みか

Desktop plugin には `busy`、`focusedSessionId`、累積usageがあったが、queued prompt、goal continuation、loop tick、auto-continueがbusy/idle transition付近で始まると「今どのturnか」を識別できず、per-turn usage baselineを安全に持てなかった。

PRはfresh in-flight turnごとにmonotonic `turn_id`を発行し、in-place steer/redirectでは同じIDを維持する。backend JSON、desktop state、plugin SDKへthreadし、Python targeted testsとTypeScript testsで fresh turnが別ID、steerが同一IDになることを検証。調査時点open PR。

### (2) 提案・推測段階

monotonic turn IDだけでdistributed episode identityを解けるわけではない。restart、cross-device handoff、branch、background child、replayにはより強いnamespaceが必要。

### (3) 関係サブシステム

Global Workspace、observability、Cognitive Budget、tool/model receipt、background task、continuity diagnostics。

### (4) 借りられる設計・実装アイデア

`session_id`とは別に `episode/turn_id` をfirst-classにし、usage、retrieval、tool calls、external model calls、interrupt、continuation、workspace renderingを同じturnへbindする。

### (5) Kamimusuhiとの差分

Kamimusuhiではturnより長い cognitive episode、speech interruption、sensor-driven subepisode、offline reflectionもあるため、単一counterではなく `episode_id -> child_activity_id` の階層が適切。

### (6) 次に検証すべきこと

**`CognitiveTurnIdentityBench-v0`**: queued continuation、steer、interrupt+resume、subagent、restart、voice backchannelを混ぜ、cost/receipt/evidenceが誤ったturnへ帰属しないことを検証。

### (7) 重要度

**A** — distributed cognitionの監査単位をsessionより細かく切るための実装上の重要差分。

## 4.5 B+ — jev-ultrafast: 動的に列挙した合法action spaceへ判断を縮約する低遅延browser control

**Discovery source (日本語):** からまげ, Zenn, 2026-09-19公開 / 09-20更新  
https://zenn.dev/karamage/articles/8ff31cccd3d223

**Primary implementation:** Browser Use, `browser-use/jev-ultrafast`  
https://github.com/browser-use/jev-ultrafast

### (1) 何が実証済みか

一次repoは各browser observationからvisible controlsをindex化し、Jevに `CLICK / TYPE_TEXT / SELECT / SCROLL / WAIT / DONE / BLOCKED` とcompatible targetの選択だけをさせる。自由生成textが必要な `TYPE_TEXT` のときだけ小型LLMへ委譲する。model outputはselector/coordinate/JS/shellへ直接ならず、executorがobserved node、freshness、occlusionを再検証する。

公開測定では Google Flights の同一task・同一model設定の6 alternating runsで両version 3/3 pass、median **9.450s → 7.092s（25%減）**、browser protocol calls **1,092 → 101**。ただし著者自身が「one task / one browser profile / 3 repeatsずつでgeneral reliability benchmarkではない」と限定している。単一recordingは7,073ms。

### (2) 提案・推測段階

任意web操作、frames/shadow DOM/canvas/upload/pop-up/nested scrollなどへの一般化は未実証。Jev自体の安全性・校正もこのrepo単独では証明しない。

### (3) 関係サブシステム

K-Edge、browser organ、low-latency cognition、Cognitive Action Router、action ABI、HCI/tool use。

### (4) 借りられる設計・実装アイデア

「次actionを自然言語で生成」せず、**現在観測から機械的に生成した合法action集合から選択**させる。自由生成は値生成など必要箇所だけに限定し、execution直前にfreshness/geometry/authorityを再確認する。

### (5) Kamimusuhiとの差分

KamimusuhiではJev固定ではなく、FSM/tiny classifier/SNN/small LLM等を同じtyped action contractで比較したい。またbrowser actionはidentity-bearing mutationではないため、Canonical Self State更新と同じauthorityを持たせない。

### (6) 次に検証すべきこと

**`IndexedActionSpaceLatencyBench-v0`**

- free-form LLM action vs indexed choice vs deterministic rule
- p50/p99 decision latency、protocol calls、task success
- stale snapshot rejection
- unsupported/ambiguous action abstention
- malicious page textがaction schemaを拡張できないこと

### (7) 重要度

**B+** — K-Nerve/K-Edgeの「低semantic-cost decision」を実システムでどう狭いaction spaceへ落とすかの良い比較対象。

## 4.6 B — TypedArtifactIdentity: digestだけでなくartifactの型とcanonical解決先をlineageへbindする

**Primary source:** Hermes PR #116618  
https://github.com/NousResearch/hermes-agent/pull/116618

### (1) 何が実証済みか

40桁hexとしてvalidなcatalog pinでも、それがGit annotated tag objectのSHAならcommit SHAではない。checkoutはtagをcommitへ解決するため、旧guardは正しいcheckoutを `actual commit != requested tag-object SHA` として拒否した。PRは `^{commit}` へpeelしてから比較し、wrong commit guardは維持。targeted 34 tests passを報告。

### (2) 提案・推測段階

このGit固有failureがKamimusuhi model lineageへ現れるとは限らない。

### (3) 関係サブシステム

Continuity Kernel、Persona Core model lineage、plugin/tool body、artifact provenance、rollback。

### (4) 借りられる設計・実装アイデア

receiptに `identifier + object_type + resolver + resolved_digest` を持たせる。`sha256:...`の文字列一致だけで model manifest / weight shard / container / commit / tag / dataset snapshotを同一視しない。

### (5) Kamimusuhiとの差分

canonical identity lineageはartifact lineageより上位であり、model/plugin artifactが一致しても「同一個体」を意味しない。

### (6) 次に検証すべきこと

**`TypedArtifactIdentityBench-v0`**: tag→commit、manifest→blob、model alias→immutable revision、symlinked checkpoint等で、validation対象とactivation対象が同じsemantic artifactへresolveされるか確認。

### (7) 重要度

**B**。

## 4.7 B — GoalRepresentationSemantics: commitmentの意味と実行用goal表現を分離する

**Primary source:** Abel & Ho, *The syntax and semantics of goals*, arXiv:2609.19448  
https://arxiv.org/abs/2609.19448

### (1) 何が実証済みか

これは実装benchmarkではなく、goalをworld knowledgeと合成されるrepresentationとして捉え、goal languageのexpressivity、equivalence、efficiency、形式と意味の区別を整理する理論的synthesis。異なるgoal表現が同じ行動意味を持つか、そもそも必要なbehaviorを表現できるか、というdesign spaceを示す。

### (2) 提案・推測段階

Kamimusuhiへの実装効果は未実証。performance claimはない。

### (3) 関係サブシステム

commitments、planner、default cognition、scheduler、self-model、long-horizon task state。

### (4) 借りられる設計・実装アイデア

canonical commitmentの**semantic intent**と、その時点のplannerが使う実行表現（自然文、task graph、predicate、temporal constraint等）を分離する。

### (5) Kamimusuhiとの差分

Kamimusuhiではgoalは単なるtask objectiveだけでなく、relationship commitmentやself-maintenance obligationも含む。representation migrationをidentity/commitment mutationと同一視しないことが重要。

### (6) 次に検証すべきこと

**`GoalRepresentationEquivalenceBench-v0`**: 同じcommitmentを自然文 / DAG / predicate / temporal formへ変換し、allowed/forbidden behavior、completion判定、restart recoveryが一致するか測る。

### (7) 重要度

**B** — foundationalだが現時点では設計概念。

## 4.8 B — Noema v0.21.8: memory prefetch/searchをcount・time・charsでboundedにする

**Primary source:** Noema v0.21.8 release, 2026-09-20  
https://github.com/Fail-Safe/Noema/releases/tag/v0.21.8

### (1) 何が実証済みか

v0.21.8 は Hermes integration 向けに `bounded_search` と `bounded_prefetch` を追加。release noteでは bounded search は最大3 active trace bodiesをprovenance/truncation marker付きで `recall_context`へ返し、bounded prefetchはlocal CLIへ2秒timeout・6,000-character context limitを設け、startup preferencesを除外しsession-log headerを含むpacketをdiscardする。

### (2) 提案・推測段階

この境界設定が recall quality、longitudinal identity、latencyへどの程度効くかの独立benchmarkは確認できない。Noema自体をcanonical memory backendへ採用する根拠にはまだ弱い。

### (3) 関係サブシステム

memory retrieval、Global Workspace、context engineering、Hermes-compatible organ、latency budget。

### (4) 借りられる設計・実装アイデア

pre-LLM memory hookには、少なくとも `max_items / max_chars-or-tokens / max_latency / allowed memory lanes / truncation receipt` を必須にする。

### (5) Kamimusuhiとの差分

Kamimusuhiはcanonical evidenceを別に保持するため、bounded recallはあくまで再生成可能なworkspace projection。切り捨てがcanonical forgettingを意味してはならない。

### (6) 次に検証すべきこと

**`BoundedRecallProjectionBench-v0`**: memory corpusを固定し、count/token/time budgetを変えながら task utility、critical-memory miss、latency、provenance retentionを比較する。

### (7) 重要度

**B** — fresh OSS implementation watch。watchlist候補だがnormative promotionは時期尚早。
