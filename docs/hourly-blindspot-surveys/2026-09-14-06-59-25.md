通常の agent / memory / distributed-systems survey では、restart、migration、schema migration、working memory は別々に扱われがちである。しかし長寿命で分散身体を持つ Kamimusuhi では、次の境界が identity continuity を直接壊し得る。

# 5. 候補ごとの評価

## 5.1 A+ — Recovery Intent / Expected Continuation Barrier

### (1) 何が実証済みか

Letta Code #4404 が restart 後の interrupted turn を自動 recovery するようになった後、conversation teleport の destination で新しい race が顕在化した。

source computer から destination へ handoff する正常系は概略:

```text
cloud -> destination: runtime_start
source -> cloud -> destination: teleport_continue(tool results, teleport_id)
```

しかし destination の startup replay が source 側から残った pending/replay-unsafe approval を見つけると、通常の restart recovery として stale denial continuation を先に開始し、turn lease を取ってしまう。その数百ms後に正規の `teleport_continue` が届くと、destination は `already processing` として拒否し、handoff が失敗した。

#4408 は `runtime_start(recover_approvals:false)` のように **setup call 単位**で recovery を抑止しようとした。ところが #4413 の再現では、別経路の status `sync` が teleport 完了前に到着すると、そこから recovery が起動できた。そのため #4408 は exact revert された。

replacement の #4410 は、`runtime_start` が `teleport_id` を受け取った時点で **「この destination は authoritative continuation を待っている」**ことを runtime state に記録する。以後の独立 `sync` も recovery turn を開始せず、`teleport_continue` 到着で expectation を clear する。continuation が来ない場合は60秒で expiration し、通常 recovery に戻る。

つまり実装差分が示したのは、単なる lock や retry の問題ではない。

```text
same persisted pending state
+ different recovery context
=> different legal next action
```

### (2) 何が提案・推測段階か

- Letta の `teleport_id` / 60秒 timeout を Kamimusuhi にそのまま採用すべき、という主張ではない。
- migration 中にどの state を transfer し、どの approval/effect authority を再検証するかは Kamimusuhi の Effect Acceptance / Continuity Kernel contract に依存する。
- handoff source 自体が死んだ場合、expected continuation をいつ abandon するかは failure detector / lease / fencing と組み合わせる必要がある。
- 「continuation が期待される」ことは、その continuation の effect authority が fresh であることを意味しない。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- Continuity Kernel
- migration checkpoint / body handoff
- K-Edge ↔ K-Core / device-to-device continuation
- background job / long-running cognitive episode
- Effect Acceptance / pending approval / unknown external outcome
- turn / episode lease
- crash recovery / deterministic replay
- computational embodiment

### (4) 借りられる設計・実装アイデア

restart reason / migration reason を implicit call path にしない。

候補 state:

```text
ContinuationExpectation
  expectation_id
  episode_id
  source_generation
  destination_generation
  reason: MIGRATION | HANDOFF | REMOTE_RESUME | OTHER
  expected_sender / authority_context
  created_at_monotonic
  expires_at_monotonic
  state: EXPECTED | ARRIVED | VERIFIED | EXPIRED | CANCELLED
  blocks_recovery_domains[]
  provenance
```

重要な規則:

```text
recoverable persisted state
  does not imply
permission to autonomously start recovery

while a verified continuation is expected,
all ingress paths must honor the same recovery barrier
```

per-call `recover=false` のような局所 flag ではなく、**operation-wide / episode-wide state** として持つ。

さらに到着後は:

```text
continuation identity verified
!= continuation authority fresh
```

なので、effect authority / capability / freshness は別途再検証する。

### (5) Kamimusuhiとの差分

Kamimusuhi は既に:

- deterministic replay
- in-flight continuation liveness
- async causal principal
- migration checkpoints
- leases/fencing
- stale authorization を fresh grant とみなさない原則

を持つ。

不足しているのは、**recovery engine 自身を抑止・許可する causal state**。既存の `cognition_resume_state` は「何を再開するか」に寄るが、今回の問題は **「別の正規 continuation が来るため、今は自律 recovery を始めてはいけない」**という negative authority である。

### (6) 次に検証すべきこと

**`HandoffRecoveryRaceBench`** を追加する。

最小構成:

- source runtime A
- destination runtime B
- pending non-interactive approval
- migration/continuation ID
- ingress 4系統:
  - `runtime_start`
  - status `sync`
  - background recovery tick
  - authoritative continuation

順序を property-based / randomized に入れ替える。

検証 invariants:

1. continuation expectation 中に competing recovery turn が開始しない。
2. continuation が duplicate delivery されても二重 episode を作らない。
3. continuation が期限内に来なければ eventually recovery へ戻れる。
4. destination restart 後も expectation が必要範囲で再構築できる。
5. source generation が stale/fenced なら continuation を reject/quarantine できる。
6. continuation受理と external effect authority を同一視しない。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

これは AI agent、distributed systems、migration のどれか一分野の「新技術」ではなく、**restart recovery と live handoff が同じ persisted state を異なる意味で読む時の composition bug** である。しかも latest daily / blind-spot 後の数時間で修正→revert→replacement が merge されており、日次のカテゴリ検索では取りこぼしやすい。

### (8) 重要度

**A+**。Kamimusuhi の multi-device embodiment / migration を実装する前に bench 化する価値が高い。

## 5.2 A+ — Historical Semantic Interpretation Contract / Upcaster Lineage

### (1) 何が実証済みか

Overeem et al. は 19 の event-sourced systems、25人の engineers への調査から、schema evolution を実務上の主要 challenge の一つとして抽出し、少なくとも以下の tactics を整理した。

- versioned events
- weak schema
- upcasting
- in-place transformation
- copy-and-transform

論文は、初期には versioned events / weak schema を使い、必要に応じて upcasting や copy-and-transform へ進むという実務知を報告する。

EventSourcingDB の現行 best-practice docs も、old events を immutable / long-lived として扱い、breaking structural/semantic change には new event type/version を用いる方向を示す。また 2026-08-10 の解説は、**payload shape の変更は schema evolution、event content 自体が誤っていた場合は別問題**と明示している。

Kamimusuhi の `spec.md` には既に NFR-004 として:

```text
durable state は provenance/history を失わず version/migrate 可能
```

という generic requirement がある。今回の差分は migration の可否ではなく、**migration 後の interpretation が history の意味を silently 書き換えないこと**である。

### (2) 何が提案・推測段階か

- Kamimusuhi が完全な event-sourced architecture を採用すべき、という主張ではない。
- すべての field rename / representation change に重い cryptographic receipt が必要とは限らない。
- 「意味が同じ」の自動判定は一般には困難であり、domain-specific invariants と golden examples が必要になる。
- current decoder の bugfix によって過去解釈が改善されること自体を禁止するのではなく、**解釈変更が不可視であること**を問題にする。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- Canonical Evidence / Self History
- autobiographical / relationship reconstruction
- schema evolution / storage migration
- deterministic replay
- migration / backup / restore
- derived view rebuild
- audit / provenance
- long-term Persona Core evaluation dataset

### (4) 借りられる設計・実装アイデア

raw evidence と normalized/current view の間を first-class にする。

候補:

```text
HistoricalInterpretationReceipt
  evidence_id
  raw_payload_hash
  original_event_type
  original_schema_version
  decoder_version
  upcaster_chain[]
  normalized_schema_version
  normalized_payload_hash
  transformation_class:
    STRUCTURAL_ONLY | SEMANTIC_REINTERPRETATION | CORRECTION_REFERENCE
  interpretation_policy_version
  generated_at
```

設計規則候補:

```text
STRUCTURAL_ONLY upcaster:
  - deterministic
  - side-effect free
  - no current-world lookup
  - no current persona/value/policy lookup
  - must not invent a historical fact

historical factual correction:
  - MUST be represented as new evidence / correction / supersession
  - MUST NOT be hidden inside an upcaster
```

危険例:

```text
v1: relationship_trust = null

bad upcast:
  if null, fill with current default trust=0.7

=> old event now appears to assert something it never asserted
```

安全側:

```text
v1 null
 -> v2 { trust: UNKNOWN, source: LEGACY_ABSENT }
```

### (5) Kamimusuhiとの差分

既存 NFR-004 は **version/migrate 可能性**を要求するが、変換器の semantic discipline までは定義していない。

既存 deterministic replay は主に:

```text
same history + compatible code
=> same control result
```

を狙う。

今回の問題は:

```text
same raw history
+ intentionally changed schema/decoder
=> what historical claims are allowed to change?
```

であり別軸。

canonical evidence を「原記録」として強く扱う Kamimusuhi ほど、**raw bytes が不変でも current interpretation が drift する**問題を監査できる必要がある。

### (6) 次に検証すべきこと

**`HistoricalUpcastEquivalenceBench`**。

fixture:

- 3世代以上の event/schema
- rename / optional field / enum split / unit change / missing default / nested structure化
- factual correction event
- privacy redaction marker

比較:

1. v1 runtime での historical interpretation
2. v1→v2→v3 incremental migration
3. raw v1 history を v3 runtime で direct replay

測定:

- historical proposition equivalence
- unknown→known の勝手な増加率
- correction event を無視した再構築率
- derived autobiography / relationship state の drift
- upcaster chain reproducibility

必須 negative test:

- current user profile
- current timezone
- current policy
- external API
- current model output

を upcaster が参照すると fail させる。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

schema evolution は storage / backend の「保守作業」に見えやすく、通常の AI agent / memory survey では cognitive identity の問題として分類されにくい。Kamimusuhi では canonical history が identity の根拠なので、**decoder の変更が autobiographical past を変える**という特殊な重要性を持つ。

### (8) 重要度

**A+**。即 spec 追記より、まず NFR-004 の conformance bench として実装し、実際の schema migration fixture で falsify するのがよい。

## 5.3 B+ — Motor Working State / Motor Working Memory

### (1) 何が実証済みか

McDougle & Hillman の Trends in Cognitive Sciences review は、一般的な working-memory 研究で motor content が比較的見落とされてきたと指摘し、人間の脳が motor content を:

- **prospective**: これから行う voluntary movement の planning / imagining / manipulation
- **retrospective**: 直前に実行した movement の短期保持

の双方で保持する証拠を整理している。

レビューの working model では、motor plan、somatosensory state estimate、visuospatial state estimate 等を短時間統合し、rapid movement refinement と skill learning に使う可能性を論じる。

これは「独立した一個の神経モジュールが確定した」という主張ではなく、**motor-specific content を working-memory 的に保持する機能的区別が有用**という review-level evidence である。

### (2) 何が提案・推測段階か

- Kamimusuhi に生物学的 MWM を模倣した network を作るべき、という意味ではない。
- PNL の generic recurrent state より dedicated motor buffer が必ず優れるとは未検証。
- digital-only action や API tool use にまで motor analogy を広げるべきではない。
- motor buffer を長期記憶や autobiography に昇格させる必要は通常ない。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- Peripheral Neural Layer / K-Nerve
- K-Edge fast cognition
- robot / actuator control
- gaze / head orientation
- speech motor system / interruption / backchannel timing
- sensorimotor adaptation
- skill learning / calibration
- distributed embodiment handoff

### (4) 借りられる設計・実装アイデア

`Global Workspace` と `procedural memory` の間に、非常に短命な **Action Working State** を比較候補として置く。

```text
ActionWorkingState
  action_episode_id
  intended_primitive / sequence
  commanded_actuator_state
  expected_sensory_consequence
  recent_executed_primitive
  observed_sensory_consequence
  residual_error
  body_calibration_revision
  expiry / refractory state
```

原則:

```text
short-lived motor state
  != autobiographical event
  != procedural skill definition
  != semantic workspace item by default
```

必要なものだけ attributed `ReflexEvent` / `SensoryEvent` として上位へ promote する。

### (5) Kamimusuhiとの差分

`docs/peripheral-neural-layer.md` には既に:

- stateful low-latency controller
- compact temporal state
- motor primitives
- local stabilization
- gaze/orientation primitive

がある。

したがって今回の提案は「PNL を stateful にする」ではない。

差分は、**prospective intent と retrospective executed-action / sensory consequence を同じ action episode に束ねて、rapid correction 用の一時状態として明示するか**である。

これは将来、単純 reflex と K-Edge semantic planning の間を埋める可能性がある。

### (6) 次に検証すべきこと

**`MotorWorkingStateBench`**。

最初は実ロボット不要で、2D simulated actuator / gaze target でよい。

条件:

1. stateless reflex
2. generic PNL recurrent state
3. structured ActionWorkingState

perturbation:

- actuator latency jitter
- gain drift
- target movement
- transient sensor dropout
- command duplication
- short handoff between two simulated body controllers

metrics:

- correction latency
- overshoot / oscillation
- action completion rate
- perturbation後の recovery steps
- state size / update cost
- stale motor state の誤適用率
- upper workspace への不要 promotion 数

さらに speech/gaze へ移植した時に同じ abstraction が成立するかを見る。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

これは working memory、motor control、skill learning の境界にあり、普通の neuroscience survey では cognition、robotics survey では controller、agent survey では action history と別名で現れる。**「短期 motor content の保持」自体が設計単位**として抜けやすい。

### (8) 重要度

**B+**。中心 continuity invariant ではないが、Physical AI / distributed embodiment が進むと効いてくる。PNL へ規範追加する前に simulation bench で dedicated structure の価値を確認する。

## 10. 今回の判断

今回の strongest finding は **Recovery Intent / Expected Continuation Barrier**。

Kamimusuhi は既に crash recovery、deterministic replay、effect replay safety、fencing をかなり強く持つ。しかし今回の Letta regression chain は、さらに一段外側の条件を示した。

```text
「復旧できる」
  と
「今、復旧を開始してよい」
  は別
```

特に multi-device embodiment では、destination が古い pending state を見て自律 recovery を始める瞬間に、source から正規の continuation が飛んでいる可能性がある。これは split-brain の canonical head だけでは防げず、**episode-level recovery intent / continuation expectation** が必要になり得る。

次点の historical semantic interpretation は、Kamimusuhi が長寿命化するほど重要度が上がる。raw history の hash が不変でも、10回の schema migration を経て「昔何が起きたと読まれているか」が変われば、実質的には autobiographical past が変質している。

Motor Working State は中心 continuity invariant ではないが、PNL/K-Nerve が physical embodiment を担う段階で、reflex と semantic cognition の間を埋める比較価値の高い仮説である。
