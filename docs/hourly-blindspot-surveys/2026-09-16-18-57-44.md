# 4. 候補ごとの評価

## 4.1 A+ — Pre-Commit Handoff Abortability: prepare reservation と ownership transfer を分ける

**Primary source**

- Letta Code #4299 — `fix(teleport): unblock source input after disconnect before handoff [LET-12212]`  
  merged 2026-09-16 13:19 JST  
  https://github.com/letta-ai/letta-code/pull/4299

### (1) 何が実証済みか

Letta Code の teleport では、source connection が readiness 前に閉じる / 消えると、source は `teleport_ready` を送っておらず turn も yield していないのに pending teleport request を保持していた。その結果、reconnect後の通常入力が「handoff中」として拒否され続けた。

修正では **まだ送信されていない teleport request だけ**を除去し、以下を保持する。

- active source turn
- すでにaccept済みの input queue
- saved tool results / saved record bytes
- request OTID
- active lease

6個の deterministic boundary case（idle / active turn / accepted queue drain の各境界）では修正前は6/6で後続入力が拒否され、修正後は admission される。追加caseでは production input dispatcher を通し、`turn_finished` / `end_turn` と backend reload 後の persisted assistant reply まで確認している。

一方、write exception、open socketへ送信した後のdelivery loss、sourceがすでにyieldした後のdisconnectはこのpatchの範囲外である。Cloud側の teleport record がpendingのままexpiryまで残る問題も別と明記されている。

### (2) 何が提案・推測段階か

Kamimusuhi の device / K-tier migrationへ、teleportの実装詳細をそのまま移植すべきだとは証明されていない。

提案するのはより一般的な境界である。

```text
transition intent / reservation
!=
source authority yield
!=
target activation
```

pre-commit failure時には「migration recovery」を起動するより先に、**成立していない transition reservation を局所的にabortできる**べき、という一般化は設計提案段階。

### (3) Kamimusuhi のどこに関係するか

- Continuity Kernel
- K-Edge ↔ K-Core ↔ K-Deep のexecution handoff
- multi-device embodiment
- conversation / cognitive episode relocation
- Expected Continuation Barrier
- RecoveryJournal
- execution-owner lease / generation fencing

### (4) 借りられる設計・実装アイデア

handoffを最低でも以下に分ける。

```text
HandoffState
  NONE
  REQUESTED          # provisional reservation only
  SOURCE_READY       # source can hand off
  SOURCE_YIELDED     # source authority relinquished
  TARGET_ACCEPTED    # target owns continuation
  COMMITTED
  ABORTED_PRECOMMIT
```

`REQUESTED` / `SOURCE_READY` の段階では、canonical owner / execution ownerを移さない。

`HandoffReservation` 候補:

```text
reservation_id
source_owner_epoch
source_connection_generation
requested_target
accepted_input_watermark
created_at
expires_at
state
abort_reason
```

原則:

```text
pre-commit transport failure
=> abort provisional reservation
=> preserve active/accepted work
=> do not fabricate a recovery episode
```

### (5) Kamimusuhiとの差分

既出 Expected Continuation Barrier は、**handoffが成立し正規 continuation が来るはずのとき、autonomous recoveryを競合させない**境界だった。RecoveryJournal は restart後に再利用できる未完了workのevidenceを残す。

今回の差分はその前段で、**sourceがまだyieldしていないのに prepare/reservationだけが残る**場合である。ここで recovery を始めるとむしろ二重化する。必要なのは recovery ではなく **pre-commit abort**。

### (6) 次に検証すべきこと

**`PreCommitHandoffAbortBench-v0`**

phaseごとに source connection kill / reconnect / timeout を注入する。

- before request durable
- after `REQUESTED`
- after `SOURCE_READY`
- immediately before yield
- immediately after yield
- target accept前後

成功条件:

- yield前のfailureでは source owner epoch が変わらない。
- active turn / accepted queue / saved results が欠落しない。
- provisional reservationだけがabortされる。
- 後続入力が永久blockしない。
- yield後のfailureだけが既存 Expected Continuation / recovery pathへ移る。
- stale reservation cleanup が新しいhandshakeを消さない（reservation generation fencing）。

### (7) 既存dailyではなぜ拾いにくいか

agent handoff は通常「migration / recovery / continuation」と一括される。今回の問題は distributed transaction の **prepare-before-commit residue** に近く、LLM agent / memory / identity のキーワードだけでは位相差が見えにくい。

### (8) 重要度

**A+** — distributed embodiment を実装すると高確率で踏む境界で、既存 recovery contract の手前を埋める。

## 4.2 A+ — Runtime Reclaim vs Semantic Interaction Closure: activation lifetime と会話thread lifetimeを分ける

**Primary source**

- Hermes Agent #112659 — `Desktop: a reclaimed chat keeps its durable row through the full teardown`  
  merged 2026-09-16 15:43 JST  
  https://github.com/NousResearch/hermes-agent/pull/112659

**Cross-domain supporting source**

- Microsoft Orleans — Grain lifecycle / activation collection / persistence  
  https://learn.microsoft.com/en-us/dotnet/orleans/host/configuration-guide/activation-collection  
  https://learn.microsoft.com/en-us/dotnet/orleans/overview

### (1) 何が実証済みか

Hermesでは以下の automatic Desktop cleanup が durable session row を終了させていた。

- `ws_orphan_reap`
- `idle_timeout`
- `lru_evict`
- `tui_shutdown` / `ws_disconnect` もautomatic側として扱う

修正後は、これらで runtime attachment が回収されても durable chat row は open のままで、sidebarから再開できる。明示的 `session.close` / `tui_close` は引き続き終了させる。

重要なのは root cause が **teardown writer の二重化**だった点である。lifecycle chokepoint側で `db.end_session()` をskipしても、直後の `agent.close()` が別handleから同じrowを `agent_close` として終了させた。修正は「rowをspareした」という決定を downstream close path まで伝播させる。

real `SessionDB` を使う teardown tests と live WebSocket E2E では、socket drop→reclaim後も `ended_at=None`, `end_reason=None` を確認している。一方、TTL後の startup orphan sweep は残り、phantom active rowを永久に残さない。

Actor-model側でも、Microsoft Orleans は idle / memory pressure を理由に in-memory grain activationを回収できる一方、stable grain identity と persistent state によって後で再activationできる。これは Kamimusuhi への直接証明ではないが、**runtime activation と logical persistent entity lifecycle を分離する成熟した設計例**である。

### (2) 何が提案・推測段階か

Kamimusuhiで全conversationを無期限openにすべき、という意味ではない。semantic close / archive / expiry policy は必要。

また Orleans grain identity は conversation relation や autobiographical episode ではないため、actor lifecycleを人格継続へ直接同一視してはならない。借りるのは lifecycle decomposition だけである。

### (3) Kamimusuhi のどこに関係するか

- `session` / current interaction state
- K-Edge surface disconnect / reconnect
- multi-device presence
- resource-pressure eviction
- Continuity Kernel の runtime owner metadata
- user-visible conversation / relationship continuity
- background task / result delivery
- observability（phantom active / falsely closed の両方）

### (4) 借りられる設計・実装アイデア

`session` を一つのboolean `active/closed` にせず、少なくとも二軸へ分ける。

```text
RuntimeAttachment
  ATTACHED
  IDLE
  RECLAIMING
  RECLAIMED
  REATTACHING

InteractionThreadLifecycle
  OPEN
  RESUMABLE
  CLOSE_REQUESTED
  CLOSED
  ARCHIVED
  EXPIRED
```

lower-level runtime は `RuntimeAttachment` を回収してよいが、`InteractionThreadLifecycle` を直接 `CLOSED` にしない。

semantic terminalization は `InteractionCloseReceipt` を持つ候補:

```text
thread_id
close_kind: explicit | archive | policy_expiry | irrecoverable_corruption
requested_by / policy_id
requested_at
finalizers / pending-delivery state
closed_at
close_reason
```

`runtime disconnect` や `memory pressure` は close reason ではなく attachment event とする。

### (5) Kamimusuhiとの差分

既出 Completion Publication Barrier は「active workが0でも未publish completion等が残るなら episode完了ではない」という **work quiescence** の境界。

今回の差分は、すべてのworkが終わり process/socket が回収可能でも、**user-facing interaction thread / resumable conversational continuity をsemanticに閉じてよいとは限らない**こと。

また actor-native identity finding は `identity != runtime instance` だったが、今回は identityそのものではなく **interaction lifecycle authority** の話である。

### (6) 次に検証すべきこと

**`RuntimeReclaimSemanticContinuityBench-v0`**

同一 durable interaction thread に対して以下を注入する。

- WebSocket disconnect
- K-Edge process restart
- idle timeout
- LRU / memory-pressure eviction
- graceful app quit
- explicit user close
- explicit archive
- policy TTL expiry

成功条件:

- resource reclaimでは process/socket/lease が解放される。
- durable threadは `RESUMABLE` のままで history / pending presentation state を失わない。
- explicit close/archiveのみ所定のterminal stateへ進む。
- dual teardown writersが、上流のspare decisionを後から上書きできない。
- stale `active` rowも永続しない（TTL / orphan reconciliationが別契約として働く）。

### (7) 既存dailyではなぜ拾いにくいか

agent surveyは session persistence を「DBに保存できるか」と捉えがちで、OS / actor runtimeは activation collectionを「resource management」と捉える。今回の盲点は **resource lifecycle と conversational/social lifecycle の境界**にある。

### (8) 重要度

**A+** — Kamimusuhi が複数device・常時稼働・resource-adaptive executionへ進むほど重要になる。

## 4.3 A — Live-Postcondition Migration Completion: migration successをartifact存在ではなくlive stateで判定する

**Primary source**

- Hermes Agent #112651 — `gateway migrate --multiplex resumes from live state, rolls back the whole destructive phase, and hermes update refuses an unknown default User=`  
  merged 2026-09-16 16:33 JST  
  https://github.com/NousResearch/hermes-agent/pull/112651

### (1) 何が実証済みか

Hermesのgateway fleet migrationでは、`systemd_install` が unit file を書いた後、実際の `start` 前/途中でprocessが止まると、旧判定は `has_gateway=true` を unit file の存在だけで満たし「already multiplexed」と誤認した。そのため live gateway が0でも recovery が走らなかった。

修正後は migrationが待っている postcondition を live state から再導出し、**default gatewayが実際にrecordしている `served_profiles` が migration manifest の全profileをcoverすること**を要求する。

同時に destructive phase 全体を一つの compensation boundary に入れた。flag write、secondary stop/uninstall、default bring-up のどこで失敗しても manifestを使って rollbackする。preflightで判明できる principal / filesystem failure は、working gatewayを止める前に拒否する。

real unit generator / installer / uninstaller + recording `systemctl` shim のreproでは、baseは unit書込み後のinterruptを `already=True` と誤認し、secondary stop失敗時にfleetを欠損させた。修正後は interruptedとしてresumeでき、destructive-step failureでは旧fleetを復元した。新 invariant tests 7件は base red / head green。

### (2) 何が提案・推測段階か

このPRは gateway migration であり、Persona Core / Continuity Kernel migrationの安全性を直接証明するものではない。

Kamimusuhiへ借りるのは以下の一般則。

```text
migration marker exists
!= target postcondition holds

configuration installed
!= software body is live and serving intended scope
```

### (3) Kamimusuhi のどこに関係するか

- software-body / runtime migration
- K-Edge / K-Core service consolidation
- Persona Core backend replacement
- model server upgrade
- Continuity Kernel replica / endpoint relocation
- owned compute / Embodiment State
- self-update / autonomic maintenance

### (4) 借りられる設計・実装アイデア

`MigrationPostconditionReceipt` 候補:

```text
migration_id
source_generation
target_generation
expected_live_capabilities
expected_served_scopes
observed_live_capabilities
observed_served_scopes
observed_owner_principal
health_probe_receipts
migration_manifest_digest
compensation_state
completed_at
```

migration engineの原則:

1. knowable failureをpreflightする。
2. 最初のdestructive stepより前にrollback manifestをdurableにする。
3. **全destructive phase** を compensation boundary に含める。
4. successは config/file/flag ではなく live postcondition で判定する。
5. rollback不完全時は「成功」にせず、manifestを残してoperator/recoveryへ渡す。

### (5) Kamimusuhiとの差分

最新 daily の software-body lineage finding は、restart/updateで **どの executable / install lineage を起動するか**を mechanically grounded にする話だった。

今回の差分は、その正しいtargetを選んだあとでも、**migrationが実際に完了して intended service set を提供しているか**を live postcondition で検証すること。

INV-013 の具体化ではあるが、destructive migrationに必要な compensation boundary と completion receipt はまだ薄い。

### (6) 次に検証すべきこと

**`DestructiveMigrationBoundaryBench-v0`**

旧 K-Core service set A/B/C → 新 consolidated service D への migration fixtureを作り、各stepでkill/failure injectionする。

- manifest durable化前後
- config flag write
- A/B/C stop
- uninstall / unregister
- D install
- D process start
- health readiness
- capability registration
- final postcondition commit

成功条件:

- preflightで分かる失敗は destructive action 0件で拒否。
- failure後は old set fully restored、または明示 `ROLLBACK_INCOMPLETE`。
- installed-but-dead targetを success扱いしない。
- success receipt は live capability / principal / generation を含む。
- stale migration resumeが新generationを上書きしない。

### (7) 既存dailyではなぜ拾いにくいか

これは AI agent というより configuration management / transactional upgrade / autonomic computing のfailure modeである。model upgradeを「モデルをロードできたか」で評価すると、service topology の部分移行・誤complete判定が見えない。

### (8) 重要度

**A** — 近い将来のK-tier/runtime統合・自動updateに直接効くが、現時点ではidentity canonical commitそのものとは一段外側。

## 4.4 A- — Directional Derived-Memory Portability: 同じmemory storeでも後継modelで同じ記憶とは限らない

**Primary source (backfill)**

- Ankit Goyal, Jaideep Ray, *Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory Portability*, arXiv:2609.05339, 2026-09-04  
  https://arxiv.org/abs/2609.05339

### (1) 何が実証済みか

48 synthetic histories、2つのopen-weight sub-10B modelを使い、同じhistoryを4形式で保持してwriter/reader model migrationを比較した。

- `LC-RAW`: verbatim history
- `RAG`: chunk + embedding retrieval
- `NOTES`: model-generated compressed natural-language notes
- `KG-fixed`: fixed-schema knowledge graph

報告値:

- `KG-fixed` は writer swap 後のaccuracy変化が **+0.0004 ± 0.0020** とほぼ不変。
- `NOTES` は migration direction により **+9.91pp / -13.28pp** と非対称に変化。
- RAG の50/50 mixed embedding migrationは **+4.96pp** 改善に留まり、full re-embeddingの **+11.90pp** の大半を取り逃した。
- NOTES deficitの80%は construction時の情報損失に帰属。
- RAG deficitの81%は retrieval failure に帰属。
- NOTESのstore-only repairは48/48で90% recovery targetを満たせず、raw source historyを残した場合は一方向で34/48成功。

### (2) 何が提案・推測段階か

- synthetic histories / 2 model の結果なので、Kamimusuhi Persona Coreの長期自伝・関係memoryへ同じ数値を一般化できない。
- fixed-schema KGが万能という証拠ではない。
- larger model / multilingual / multimodal / years-long history でのportabilityは未実証。

### (3) Kamimusuhi のどこに関係するか

- Persona Core migration
- episodic / relationship / semantic derived memory
- retrieval index
- embedding service migration
- Library / memory vector store
- canonical evidence → derived view rebuild
- continuity regression suite

### (4) 借りられる設計・実装アイデア

Kamimusuhiはすでに canonical evidence をderived summary/indexより上位に置くため、その方針を維持する。

追加で derived memory に epoch / construction provenance を持たせる候補:

```text
DerivedMemoryEpoch
  representation_type
  source_evidence_ids
  writer_model_id
  writer_model_revision
  schema_version
  embedding_model_id
  embedding_revision
  embedding_dimension
  index_build_id
  constructed_at
```

migration原則候補:

- model A→B と B→A を同じ「upgrade score」に平均化しない。
- embedding model/revision変更時は原則 full re-embed を baseline にする。
- 異なる embedding space を暗黙に一つのindexへ混在させない。
- raw/canonical sourceを残し、store-only repair に依存しない。
- memory representationごとに migration test を別に持つ。

### (5) Kamimusuhiとの差分

Kamimusuhi の README/spec はすでに「summary/indexはderivedで、canonical evidenceから再構築可能であるべき」としている。したがって **raw source retention自体は新規提案ではない**。

今回の差分は、モデル交換時に **derived representationが writer-model-coupled / embedding-space-coupled になり得ることを定量的に試験する**点。特に mixed embedding epoch は、storage migrationが終わっていても retrieval semantics が中途半端な状態を作る。

### (6) 次に検証すべきこと

**`MemoryPortabilityAcrossPersonaMigrationBench-v0`**

Kamimusuhiの同一 canonical historyから以下を作る。

- raw evidence replay
- episodic summary
- relationship synthesis
- free-form model-written notes
- fixed-schema self/relationship facts
- vector index

Persona Core / embedding backendを A→B / B→A で交換し、以下を測る。

- identity / relationship fact accuracy
- historical vs current interpretation distinction
- correction / supersession retrieval
- retrieval recall
- unsupported trait contamination
- repairability from canonical evidence

embeddingは `old-only / 50-50 mixed / full re-embed` を比較する。

### (7) 既存dailyではなぜ拾いにくいか

memory surveyは通常 retrieval quality を固定model内で測り、model migration surveyは Persona behavior を見る。今回の問題は **memory representationを作ったmodelと、それを後で読むmodelのcross-version coupling** にあるため、両分野の境界で落ちやすい。

### (8) 重要度

**A-** — 現行 canonical-evidence方針を強く支持する実証差分。新アーキテクチャより migration benchmark / metadata強化として採るのが妥当。

## 10. 今回の設計圧縮

今回のfindingを最小限の契約へ落とすと次の4本になる。

```text
PREPARE != COMMIT
handoff reservationを持っただけでは、sourceはまだ自分である。

DEACTIVATED != CLOSED
計算資源を回収しても、会話・関係・継続threadを勝手に終わらせない。

INSTALLED != LIVE
migration完了はfile/flagの存在ではなく、live postconditionで判定する。

STORED != PORTABLE
同じmemory storeが残っても、model/embedding epochが変われば同じ記憶として機能するとは限らない。
```

短期の優先順位は **Pre-Commit Handoff Abortability → Runtime Reclaim / Semantic Closure Separation → Live-Postcondition Migration → Memory Portability Bench**。とくに最初の2つは、現在の continuity runtimeを本格的にmulti-device化する前にfixtureとして固定しておく価値が高い。
