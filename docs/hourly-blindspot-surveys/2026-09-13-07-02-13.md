# 6. 候補ごとの評価

## 6.1 S — CALM / Coordination Criterion: 「同期するか」を state の意味論から決める

**Primary:**
- Hellerstein, *The Coordination Criterion* — https://arxiv.org/abs/2602.09435
- Hellerstein & Alvaro, *Keeping CALM* — https://arxiv.org/abs/1901.01930

### (1) 何が実証済みか

CALM は、monotone な computation が consistent な coordination-free distributed implementation と対応する、という設計原理を与える。2026年の *The Coordination Criterion* はこれを特定言語から離し、asynchronous message-passing の Lamport history と observable outcome 上で、**specification が history extension に対して monotone であることと coordination-free implementability の境界**として定式化している。

これは Kamimusuhi の正しさを証明したものではないが、「coordination を protocol の好みではなく、spec の意味論から要求できる」という理論基盤は確立された systems result である。

### (2) 何が提案・推測段階か

Kamimusuhi の各 operation が本当に monotone / non-monotone かの分類はまだ行っていない。特に append-only event store が monotone でも、そこから計算する `current authoritative head` や `現在有効な capability` は非単調になり得る。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Continuity Kernel
- canonical evidence replication
- K-Edge / K-Core / multi-device proposal exchange
- relationship / sensory event aggregation
- capability revocation
- authoritative head / singleton ownership
- forgetting / delete / supersede
- Effect Acceptance

### (4) 借りられる設計・実装アイデア

`CoordinationNecessityMatrix` を作り、state transition / query を次のように分類する。

```text
coordination-free candidate
  append immutable evidence
  add provenance edge
  add independent observation/proposal
  accumulate positive telemetry
  replicate immutable artifact

coordination-required candidate
  choose one authoritative head
  revoke / delete / supersede
  claim "no pending work exists"
  assign exclusive actuator ownership
  redeem single-use authority
  decide irreversible effect exactly once
  garbage-collect evidence whose absence is semantically meaningful
```

重要なのは、**Continuity Kernel を弱めることではなく、Kernel が本当に直列化すべき surface を狭く・説明可能にすること**である。

### (5) Kamimusuhiとの差分

現行設計は canonical head / atomic activation / split-brain prevention を強く定義している一方、どの情報まで同じ強度の coordination を必要とするかを operation semantics から分類する文書は確認できなかった。

### (6) 次に検証すべきこと

**`CoordinationNecessityAudit`**

- 現在の durable state mutation / query を列挙。
- history extension で過去の observable conclusion を撤回する必要があるかを分類。
- 2〜3 device partition を inject。
- monotone candidate は local progress を許し、merge 後に convergence するか確認。
- non-monotone candidate は fencing / consensus / canonical activation を要求。
- 指標: unnecessary-coordination latency、split-brain、lost valid progress、incorrect convergence、coordination surface size。

### (7) 既存 daily ではなぜ拾いにくいか

CRDT / distributed systems として検索すると data structure や consistency mechanism に寄りやすく、**coordination の必要性を specification semantics から決める database theory / logic の視点**は agent/identity survey から外れやすい。

### (8) 重要度

**S** — Continuity Kernel の責務境界そのものを、より小さく formalizable にできる可能性がある。ただし採用前に Kamimusuhi operations の monotonicity audit が必須。

## 6.3 A — Accrual failure detector: `silent != dead`

**Primary:** Hayashibara et al., *The φ accrual failure detector*  
https://dspace.jaist.ac.jp/dspace/handle/10119/4784

### (1) 何が実証済みか

φ accrual failure detector は process を `trusted / suspected` の Boolean だけで返さず、連続的な **suspicion level** を出す。application 側が要求に応じた threshold を選べるため、低 threshold の速いが誤りやすい検出と、高 threshold の遅いが慎重な検出を同じ観測基盤の上で使い分けられる。報告では network condition に応じて scale を適応させ、長距離通信上で既存 adaptive detector と比較評価している。

### (2) 何が提案・推測段階か

Kamimusuhi の organ liveness に φ をそのまま採用すべきとは限らない。phone sleep、Wi-Fi roaming、GPU OOM、process hang、sensor disconnect、credential expiry は異なる failure mode を持つ。また failure detector は Byzantine integrity や「正しい出力をしているか」を判定しない。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- distributed embodiment
- K-Edge / K-Core organ registry
- leases / fencing
- degraded mode
- actuator handoff
- sensor health
- model/provider failover
- continuity migration

### (4) 借りられる設計・実装アイデア

liveness を epistemic state として持つ。

```text
OrganLivenessEvidence
  organ_id
  generation
  last_observed_at
  suspicion_score
  evidence_sources
  network_partition_hint
  clock_quality
  last_successful_effect
```

policy は用途別に threshold を変える。

```text
low suspicion     -> latency routing を他 organ へ寄せる
medium suspicion  -> 新しい effect assignment を止める
high suspicion    -> corroboration 後に generation fencing
terminal decision -> durable evidence / operator-policy を要求
```

つまり `route away`, `fence`, `declare failed`, `declare identity dead` を一つの timeout に結びつけない。

### (5) Kamimusuhiとの差分

現行は health、freshness、leases/fencing、degraded mode を持つが、**観測不能を binary failure claim に変換する前の suspicion/evidence layer** は明示的には収載されていない。

### (6) 次に検証すべきこと

**`OrganFailureSuspicionBench`**

- latency spike
- packet loss / partition
- laptop sleep / phone background suspension
- process crash
- hung process
- actual hardware disappearance

を注入し、固定 timeout と adaptive suspicion を比較する。指標は false-death rate、failover latency、dual-active duration、unnecessary fencing、rejoin success、effect loss。

### (7) 既存 daily ではなぜ拾いにくいか

distributed identity survey は split-brain / consensus / fencing に寄りやすく、**その前段の「そもそも相手は死んだのか」という failure-detection epistemology** は古典分散システムの別文脈に埋もれやすい。

### (8) 重要度

**A** — multi-device embodiment で network silence を「死亡」や lineage break へ直結させる事故を減らせる。特に mobile / intermittent organ を持つ設計では重要。

## 6.4 A — Supervision tree + microreboot: recovery domain を identity domain から切る

**Primary:**
- Erlang/OTP supervisor — https://www.erlang.org/doc/apps/stdlib/supervisor.html
- Candea et al., *Microreboot—A Technique for Cheap Recovery* — https://www.usenix.org/conference/osdi-04/microreboot%E2%80%94-technique-cheap-recovery

### (1) 何が実証済みか

Erlang/OTP supervisor は child process を監視し、`one_for_one`, `one_for_all`, `rest_for_one` 等の restart strategy と restart intensity/period を持つ。依存関係に応じて recovery blast radius を明示でき、restart storm 時には上位 supervisor へ failure を伝播できる。

Microreboot 研究は、process recovery と data recovery を分離し、Internet auction system の component-level recovery で多くの同一 failure を full reboot より一桁程度速く、lost work も一桁程度少なく回復できることを報告した。

### (2) 何が提案・推測段階か

Kamimusuhi の cognition graph が Erlang process tree のような単純 tree になるとは限らず、memory cache、sensor fusion、tool session には DAG 的 dependency がある。LLM call 自体を restart すれば意味的に同一になる保証もないので、non-deterministic cognition は直前 survey の replay contract と併用が必要。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- K-Nerve workers
- K-Edge sensory/peripheral pipeline
- memory index / derived views
- tool adapters
- speech pipeline
- K-Deep jobs
- observability / maintenance agent
- Continuity Kernel の failure containment

### (4) 借りられる設計・実装アイデア

`CognitiveSupervisionGraph` を明示する。

```text
organ/process
  state_class: durable | ephemeral | rebuildable | external
  restart_policy: one | dependent-subtree | grouped | never-auto
  max_restart_intensity
  upstream_dependencies
  generation
  escalation_target
  replay_requirement
```

例:

- sensor decoder crash → decoder だけ microrestart
- retrieval indexer crash → indexer + dependent cache を再構築
- local LLM server crash → model organ restart、canonical self は触らない
- Continuity Kernel corruption suspicion → auto-restart ではなく safe/read-only recovery path

`restart storm` は「頑張って再起動し続ける」のではなく、quarantine / degraded mode / human-visible incident へ escalation する。

### (5) Kamimusuhiとの差分

現行には deterministic replay、degraded mode、watchdog、organ generation/fencing がある。しかし **どの failure がどの dependency subtree を restart し、canonical identity state を何があっても巻き添えにしないか**という supervision topology は独立の設計問題として未整理。

### (6) 次に検証すべきこと

**`MicrorebootIsolationBench`**

- sensor decoder / retrieval cache / local model server / tool bridge / speech worker に fault injection。
- full process restart と component restart を比較。
- canonical head / evidence hash が不変か確認。
- stale handle / generation crossing を同時注入。
- restart storm を起こし、上位 escalation が働くか確認。
- 指標: MTTR、collateral restart count、lost work、canonical mutation count、stale-handle action、restart-loop duration。

### (7) 既存 daily ではなぜ拾いにくいか

agent reliability は checkpoint / retry / replay に寄りがちだが、これは **OS/telecom 系の fault-containment / supervision topology** の問題である。`どう復元するか` だけでなく `何を巻き込んで復元するか` を扱うため通常の memory/continuity 分類から落ちやすい。

### (8) 重要度

**A** — Kamimusuhi が「一個体だが一processではない」以上、故障時に identity 全体を再起動する設計は不自然。実装コストも比較的低く、早期に導入可能。

### (1) 何が実証済みか

### (2) 何が提案・推測段階か

Letta listener の ownership model が Kamimusuhi の organ ownership にそのまま対応するわけではない。また PR 自身も stalled-network の全ケースを live outage で再試験したわけではないと明記する。

### (5) Kamimusuhiとの差分

`spec.md` INV-013 は machine-observable current state を runtime owner から導出する原則をすでに持つ。今回の差分は **execution path そのものを owner へ寄せ、calling wrapper が別 loop で policy/computer ownership を迂回しない**という実装パターン。

### (6) 次に検証すべきこと

**`ExecutionOwnerBindingBench`**

- caller が古い runtime policy / model setting を持つ条件を作る。
- owner organ だけが current computer capability を持つようにする。
- direct-local loop と owner-routed execution を比較。
- 指標: policy bypass、wrong computer generation、usage/accounting loss、cancellation mismatch。

tool orchestration として見ると単なる routing refactor に見えるが、distributed cognition では **body/resource ownership をどの process が代表するか**という embodiment boundary に相当する。

## 12. 今回の結論

今回の核心は、Kamimusuhi の distributed continuity を **「全ノードを強く同期する」問題だけとして見ない**ことにある。

```text
何が coordination を本当に必要とするか        -> monotonicity / semantic audit
その organ は本当に死んだのか                -> suspicion / failure evidence
どこまで再起動すべきか                        -> supervision / microreboot
遅れて戻る event は誰の処理に由来するか       -> causal principal
その由来は今の実行権限を意味するか             -> no; authority revalidation
実際に body/resource を所有して実行するのは誰か -> execution owner
```

次に一本だけ回すなら **`AsyncCausalPrincipalBench`**。その次に、コード変更なしでも始められる **`CoordinationNecessityAudit`** を行う価値が高い。
