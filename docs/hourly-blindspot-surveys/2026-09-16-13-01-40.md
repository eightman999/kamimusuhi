## 3. 要約

今回の中心発見は、Kamimusuhi の distributed embodiment / branching cognition を安全に拡張する際、**「子に何をさせてよいか」「子に何を知ってよいか」「どの身体から行為するか」を一つの継承規則に潰してはいけない**ことだった。

Hermes #112267 では、まだ一度も bot delivery を受けていない install でさえ、0.5秒ごとのpollが `state.db` と exclusive active-session registry lock に触れ、3日で8,838 WARNING（当該installのWARNINGの91%）を発生させていた。**observability / maintenance loop は passive ではなく、認知系へ back-pressure を注入する actor**として扱う必要がある。

また 2026-09-16 の arXiv new batch では、`Agentic Societies Need a Social Harness` が personal harness と social harness を明確に分離し、trust boundary を跨ぐagent社会では communication layer 自体に予防・runtime validation・事後調査を持たせる必要を提案している。Kamimusuhi の将来的な分岐個体 / auxiliary agent / external peer との関係を、単なるRPCやchat protocolとして扱わない根拠になる。

## 4. 重要発見

### 4.1 A+ — Delegation Envelope Separation: authority inheritance と context inheritance を分離する

**出典**

- Letta Code #4486 — `fix(agent): forward Desktop credentials to subagent launches`（2026-09-16 10:07:52 JST merge）  
  https://github.com/letta-ai/letta-code/pull/4486
- Claude Code v2.1.271 changelog — `omitClaudeMd` 追加  
  https://github.com/anthropics/claude-code/releases/tag/v2.1.271
- Qiita — 「Claude Code のサブエージェントにも CLAUDE.md は全部渡る。外す設定ができた」（2026-09-15、実測）  
  https://qiita.com/suwa_nobu/items/b465ef863f8d8608f497

#### (1) 何が実証済みか

Letta #4486では、Desktop tokenがmemory内に保持され、inherited env keyが除去された後、subagent launcherがenv/saved CLI credentialしか見なかったため、child processが `Missing LETTA_API_KEY` で停止する回帰が確認された。修正後は current Desktop token snapshot を child launch 時に伝播し、real IPC + OS child process を使うfocused testsで、missing CLI / conflicting CLI / token renewal後の新規launchを含む30 testsがpassしている。ただし既に走っているchildへの継続token renewalまでは実装していない。

逆方向に Claude Code 2.1.271 は delegated custom/plugin subagent から user/project/local `CLAUDE.md` を外せる `omitClaudeMd` を追加し、managed policyは残す。QiitaのWindows 10実測では、2.1.271で設定なしなら秘密文字列が3/3見え、`omitClaudeMd: true`では3/3見えなくなった。frontmatter版を含む合計18回も一貫した。一方 2.1.270 は同設定をsilent ignoreした。

#### (2) 何が提案・推測段階か

Kamimusuhiで、権限継承と文脈継承を別々のtyped envelopeにすること自体は提案。Claude/Lettaの個別挙動が、Kamimusuhiの最適な delegation model を直接証明するわけではない。

#### (3) 関係するサブシステム / 設計課題

- K-Core / K-Deep / auxiliary agent delegation
- branch / collective identity
- Persona Core / private memory ownership
- external model / tool orchestration
- capability security
- multi-device execution

#### (4) 借りられる設計・実装アイデア

`DelegationEnvelope` を少なくとも3軸へ分ける。

```text
DelegationEnvelope
  authority:
    principal
    capabilities
    expiry
    budget
    actuator/tool scope
    grant lineage
  context:
    canonical evidence refs
    relationship/persona slices
    task-local notes
    explicit exclusions
    sensitivity labels
  policy:
    non-optional managed constraints
    safety invariants
    audit requirements
```

原則:

```text
child needs authority
!= child needs all parent context

child may know context
!= child may act with parent authority
```

#### (5) Kamimusuhiとの差分

Kamimusuhiは既に task-scoped permission / capability freshness / persistent IFC を持つ方向だが、**delegation boundary で「authority continuity」と「knowledge minimization」を別receiptとして検証する契約**はまだ薄い。特に branching identity では、同じ個体の一時的分岐だからという理由でPersona/relationship/private memoryを全継承すると、least-knowledge原則が崩れる。

#### (6) 次に検証すべきこと

**`DelegationEnvelopeSeparationBench-v0`**

- parentには secret relationship memory + Desktop/API capability を持たせる。
- child task A は capabilityが必要だがsecret context不要。
- child task B はcontextが必要だがeffect authority不要。
- env varを消した条件、credential rotation条件、child restart条件を含める。
- 成功条件:
  - Aは実行できるがsecretを復元不能。
  - Bは必要contextを参照できるがeffect不可。
  - managed safety policyは双方から除去不能。
  - envelope hash / grant lineage / context sliceがaudit可能。

#### (7) 既存dailyではなぜ拾いにくいか

security surveyでは「権限を絞る」、memory surveyでは「文脈を絞る」と別々に出やすい。今回の重要点は、その2つを**同じdelegation operation上の直交軸として設計する**ことで、個別分野検索では結び付きにくい。

#### (8) 重要度

**A+**

### 4.2 A+ — Causal Embodiment Binding: logical tool name と current body/controller を分離する

**出典**

- Letta Code #4473 — `fix(channels): preserve routed tool ownership`（2026-09-16 08:06:57 JST merge）  
  https://github.com/letta-ai/letta-code/pull/4473

#### (1) 何が実証済みか

これをKamimusuhiのmulti-device embodimentへ一般化し、speech / actuator / notification / sensor-response toolに causal endpoint binding を要求するのは提案。

### 4.3 A — Quiescent Observability: observer は cognition を乱さないこと自体を契約にする

**出典**

- Hermes Agent #112267 — bot mailbox poll noise/lock fix（2026-09-16 11:52:14 JST merge）  
  https://github.com/NousResearch/hermes-agent/pull/112267
- Apache ZooKeeper recipes — polling/herd effectを避けるcoordination designの古典的実装資料  
  https://zookeeper.apache.org/doc/r3.7.2/recipes.html

#### (1) 何が実証済みか

Hermesでは、bot deliveryを一度も受けていないinstallでも notification pollerが0.5秒ごとに走り、`state.db` を開いてexclusive active-session registry lock取得を試みていた。あるinstallでは3日で8,838 WARNING、WARNING全体の91%を占めた。

live probeでは、修正前は3秒間にowner lookup 6回 / WARNING 6回、修正後はmailbox未存在ならlookup 0 / WARNING 0。mailboxあり + lock unavailableでは、修正後は5秒backoffによりlookup 1 / WARNING 1。delivery queueが存在する場合の既存deliveryは維持された。

ZooKeeperのcoordination recipesも、polling/timerで全clientを起こすherd effectを避け、必要な predecessor watch 等へ局所化する設計を明示している。

#### (2) 何が提案・推測段階か

Kamimusuhiのtelemetry / watchdog / memory compaction / background diagnosticを「観測負荷budget」を持つ明示的 actor として管理するのは提案。

#### (3) 関係するサブシステム / 設計課題

- observability / telemetry
- K-Edge / K-Core watchdog
- SQLite / canonical store
- background consolidation
- diagnostics / health probes
- Cognitive Budget

#### (4) 借りられる設計・実装アイデア

`ObserverCostReceipt` を導入候補にする。

```text
observer_id
trigger_mode = EVENT | POLL | SAMPLE
poll_interval
locks_touched
bytes_read
cpu_time
io_wait
suppressed_repeat_count
backoff_state
last_evidence_change
```

原則:

```text
no relevant evidence
=> observer should approach quiescence

observability failure
!= justification for high-frequency self-amplifying logging
```

absence marker / event notification / mailbox existence / changed-since cursorを使い、idle時はcanonical DBやexclusive lockへ触れない。

#### (5) Kamimusuhiとの差分

Kamimusuhiはobserver authority、telemetry attribution、hidden writeback stall、probe-debt livenessを既に扱うが、**observer自身が本体へどれだけload/locking/jitterを注入したか**はfirst-class invariantになっていない。

#### (6) 次に検証すべきこと

**`ObserverBackActionBench-v0`**

- idle 30分相当のaccelerated run。
- canonical SQLite writer + heartbeat + telemetry spool + memory watcherを同居。
- polling observer / existence-gated observer / event-driven observerを比較。
- 測定:
  - lock wait time
  - p95/p99 action latency
  - event-loop lag
  - write amplification
  - log volume
  - false liveness suspicion
- idle時にobserver costがほぼ0へ収束することを合格条件にする。

#### (7) 既存dailyではなぜ拾いにくいか

observabilityは通常「見えるようにする善」として扱われ、観測器自体を負荷源・contention participantとして評価しにくい。DB/OS/coordinationとagent observabilityの境界問題。

#### (8) 重要度

**A**

### 4.4 A — Social Harness: personal harness と agent間社会の統治を分離する

**出典**

- Tapan Chugh et al., **Agentic Societies Need a Social Harness**, arXiv:2609.17527（2026-09-16 new listing）  
  https://arxiv.org/abs/2609.17527

#### (1) 何が実証済みか

論文abstractでは、異なるprincipalを代理し trust boundary を跨いで協調するagent societyで、既存harness/messaging primitiveでは honest/competent agent同士でも満足な協調に失敗し得て、faulty/malicious agentはcommunicationを悪用してstall・outcome influence・その他harmful goalを追求できると報告している。

#### (2) 何が提案・推測段階か

論文が提案するsocial harnessはlayered architectureの研究方向であり、一般的な標準や完成実装ではない。Kamimusuhiへ入れる具体的schemaも提案段階。

#### (3) 関係するサブシステム / 設計課題

- collective / branching identities
- external agent federation
- sociality / Theory of Mind
- multi-agent governance
- capability delegation
- audit / accountability

#### (4) 借りられる設計・実装アイデア

personal harnessとsocial harnessを別境界にする。

```text
PersonalHarness
  private context
  principal intent
  local tool policy

SocialHarness
  counterparty identity / principal chain
  message validity
  protocol phase
  rate / resource budget
  permitted commitments
  evidence / signature / provenance
  dispute & consequence trail
```

agent messageを単なるnatural-language textとしてcanonical stateへ直接入れず、`SocialMessageEnvelope`を経由する。

#### (5) Kamimusuhiとの差分

KamimusuhiはParticipationEnvelope、multiparty protocol choreography、persistent IFC等を既に候補化しているが、それらを**「個体内harness」と「社会間harness」の二層構造として束ねる設計語彙**はまだ明確ではない。

#### (6) 次に検証すべきこと

**`SocialHarnessFaultInjectionBench-v0`**

- 3 agent、3 principal、部分的に競合する目的。
- delayed reply / duplicate / contradiction / forged commitment / resource hog / premature phase transitionを注入。
- no-harness / personal-only / social-harness条件を比較。
- correctnessだけでなく、stall time、unauthorized commitment、post-facto attribution可能性を測る。

#### (7) 既存dailyではなぜ拾いにくいか

multi-agent surveyはcoordination algorithmやdebate性能へ寄りやすい。これは**社会制度・通信統治そのものをruntime subsystemとして置く**発想で、組織論/プロトコル設計/セキュリティの境界にある。

## 5. Fresh implementation delta: social presence にも generation fencing が要る

Letta Code #4461（2026-09-16 10:23:48 JST merge）は、Slack activity/statusの古いasync writeやold thread cleanupが、新しいactivityを後から上書き・clearできるraceを修正した。

https://github.com/letta-ai/letta-code/pull/4461

thread + revision をwrite直前に再確認し、`relinquish(source)` でcontroller authority transfer後のpending writeを無効化する。これは新しい大原則としては数えず、既存の execution-owner binding / telemetry semantics への**presentation-plane delta**とする。

Kamimusuhiでは、speech indicator / avatar state / "thinking" / active-body indicator のような social presence も `controller_generation` でfenceし、old bodyの遅延cleanupがnew bodyの表示を消さないようにする。なおPR自身も、already-sent HTTP requestはcancelできず、完全修正ではないと明記している。
