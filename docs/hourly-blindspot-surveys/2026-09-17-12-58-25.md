## 1. 今回狙った盲点

1. **Negative mutation semantics / absence vs deletion**  
   patch / merge / desired-state APIで「キーがない」ことが、削除・未変更・不明のどれを意味するかが曖昧になっていないか。

   software-body update中にcron/sleep/consolidation/watchdogをdispatchし、半更新runtimeで走らせたり、失敗したのにscheduleだけ進めたりしていないか。

   stop対象をexact session keyで引くため、同一interactionの別projection（channel/thread/rolling DM等）から停止できない経路がないか。

   monitor/watch/subscriptionを開始できる権限と、それを無期限に存続させる権限が暗黙に同一になっていないか。

## 3. 要約

今回もっとも重要なのは、長寿命agentでは **「変化させること」だけでなく「消すこと」「待つこと」「止めること」に独立した意味論が必要**だという点である。

Hermes #113734 は、UIが残すべきpresetだけをPUTして「消したつもり」になっても、backendのdeep-mergeが omitted key を「変更なし」と解釈して旧presetを復元し、しかもAPIは成功を返すという典型的なnegative mutation bugだった。これは設定UIに見えるが、Kamimusuhiのmemory forgetting、capability revocation、relationship consent撤回でも同型が起きる。**absenceをdeletionとして推測してはいけない。delete/tombstone/replaceはfirst-class operationにする必要がある。**

#113735 は別種の時間的バグを示す。update lock中にcron jobをdispatchしscheduleだけ進めると、jobはhalf-replaced code treeで走るか失敗し、時間slotは消費済みになる。長寿命agentにとってsleep/consolidation、memory compaction、credential rotation、health scan、relationship maintenanceは単なるbest-effort cronではなく「一度は実行されるべきtemporal obligation」になり得る。maintenance中はdispatchを止めるだけでなく、**due obligationを未消費のまま持ち越す**必要がある。

#113738 は直前回の cancellation closure と対になる。前回は「正しいtaskを止めた後、そのdescendant effectorまで本当に止まったか」だった。今回はもっと手前で、同じchat/turnが複数の正規化session keyで表現されると、exact-key lookupだけでは正しいtaskを**見つけられない**。従って cancellation safety は `resolve target → authorize scope → cancel owner → prove effectors quiescent` の4段に分けるべきである。

Letta #4507 はobserverの寿命を問い直す。PR自体はClaude CodeのMonitor contractへ追随するdraftであり、本番障害の実証ではない。しかし `persistent: true` を外し、5分default / 30分maxに揃える設計は、Kamimusuhiのobserver/monitor/subscriptionを **leased authority** として扱う良い圧力になる。観測は受動ではなく、I/O、privacy exposure、scheduler work、notification、memory injectionを引き起こす可能性があるため、開始権限だけで永久watchを許さない方がよい。

#113730 は既出の software-body epoch findingへの明確な実装差分である。remote backend updateが `ok && restoreOk` でも、renderer側socketはreplaced backendの旧connection incarnationにbindされたままになり得る。**body restored != attachments rebound**。これは新原則ではなく、既存 `MixedSoftwareBodyEpochBench` に connection-incarnation check を追加すべき証拠である。

最後にMemVaultは、Kamimusuhiが既に持つforgetting/erasure原則への具体的実装候補を示す。fact content用のkeyを破棄して内容を不可読にしつつ、hash-chained ledgerには「このfactが存在し、忘却された」という監査可能な出来事を残す。これは有望だが、embedding/index/cache/backup/replicaにplaintext相当情報が残らないことまで実証されて初めてKamimusuhi向けの強いerase primitiveになる。

## 5.1 A+ — Explicit Negative Mutation Semantics: 「存在しない」と「消せ」を分ける

**Primary source**

- NousResearch/hermes-agent PR #113734 — *fix(desktop): persist MoA preset deletions from the settings pane*  
  https://github.com/NousResearch/hermes-agent/pull/113734  
  調査時点: **open / mergeable / 未merge**

### (1) 何が実証済みか

PRの再現では、Desktopがpreset deletion後に「残っているpreset集合」をPUTしても、backendが `merge_existing=True` のdeep mergeを使うため、payloadから消えたkeyがdisk側から再導入された。UIはoptimisticに削除成功を表示しrouteも `ok: true` を返すが、次readで削除presetが復活する。

PRではbase上で新しい2 invariant testが失敗し、提案patch後は通ると報告。関連config/model suiteも265 passとしている。ただし調査時点でPRは未mergeであり、upstream contractとして確定したわけではない。

### (2) 何が提案・推測段階か

Kamimusuhiで同一バグが既に存在することは未実証。一般化した提案は、persistent state mutationで次を明示的に分けること。

```text
NO_CHANGE
SET(value)
DELETE
REPLACE_SUBTREE(value)
REVOKE_AUTHORITY
FORGET_CONTENT
```

特に `missing`, `null`, empty collectionをDELETEの暗黙sentinelとして使わない。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Memory / Self / Relationship mutation
- consent withdrawal / memory ownership
- capability / credential / tool revocation
- Continuity Kernel / Mutation Gate
- derived viewの再構築
- `INV-005` durable mutation
- `INV-014` authority/provenance/livenessをexplicit state化

### (4) 借りられる設計・実装アイデア

**`MutationOp` をalgebraic type化**する。

```text
MutationOp =
  Set(path, value, expected_revision)
  | Delete(path, expected_revision, reason)
  | ReplaceSubtree(path, value, expected_revision)
  | Revoke(capability_id, expected_epoch)
  | Forget(memory_id, erasure_policy)
```

さらに deletion receipt に:

```text
requester_principal
reason / consent_basis
predecessor_revision
removed_object_id
residue_policy
replica_targets
completion_state
```

を持たせる。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでに distributed erasure、derived-belief retraction、consent-bound memory promotionを検討している。しかしそれらは主に **「削除を決めた後、どこまで消すか」** の問題だった。

今回の新規境界はその前段、**「削除の意思がpatch/merge境界で消えていないか」**。erase protocolが完璧でも、DELETE intentがbackendへ届かなければ何も消えない。

### (6) 次に検証すべきこと

**`ExplicitNegativeMutationBench-v0`**

- self/relationship/library/configで同名nested keyを用意
- `missing`, `null`, `{}`, `[]`, explicit `DELETE`, subtree replaceを投げる
- patch/merge/CRDT/event-sourcing adapterを跨いでも意味が変わらないこと
- optimistic UI / API successだけで削除成功扱いしないこと
- replica/offline nodeがold valueを復活させないこと
- DELETEとFORGETを分離し、audit residue policyを検証

### (7) 既存デイリーサーベイではなぜ拾いにくいか

一見すると「設定UIの削除バグ」であり、agent memory / identity研究のkeyword検索では出にくい。しかし本質は **negative informationをpatch protocolでどう表現するか**というdistributed state / CRDT / API semanticsの問題で、memory ownershipとprivacyに直結する。

### (8) 重要度

**A+** — 忘却、revocation、consent withdrawalを持つ長寿命個体では「削除要求が成功したように見えて実際には残る」ことは重大。実装コストも低く、型とconformance testで早期に固定できる。

## 5.2 A+ — Due-Work Conservation Across Maintenance: maintenanceは時間的義務を食べない

**Primary source**

- NousResearch/hermes-agent PR #113735 — *fix(cron): defer tick dispatch while an update holds the lock*  
  https://github.com/NousResearch/hermes-agent/pull/113735  
  調査時点: **open / mergeable / 未merge**

### (1) 何が実証済みか

PRは、live update markerが存在する状態でcron tickを通常dispatchすると、updaterがcode treeをswapしている最中のjobを起動しうるうえ、scheduleをadvanceしてしまうため、そのslotを消費した扱いになる問題を対象にしている。

提案patchはupdate marker中にdispatchを0件にし、due jobをpost-update tickへ残す。focused regression testが追加されgreenと報告されている。ただしPRは未mergeで、production incidentの定量評価はない。

### (2) 何が提案・推測段階か

Kamimusuhiで全scheduled jobをexactly-onceにすべき、という意味ではない。obligation classによって semantics を分ける必要がある。

```text
BEST_EFFORT
LATEST_ONLY
AT_LEAST_ONCE_DUE
MUST_NOT_RUN_DURING_MAINTENANCE
RECOMPUTE_AFTER_MAINTENANCE
```

推測段階なのは、どのoffline cognitionがどのclassに属するか。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Sleep / Dream scheduler
- consolidation / memory compaction / index refresh
- continuity checkpoint / backup
- credential rotation / capability refresh
- health/self-model maintenance
- software-body update
- K-Core long-lived orchestration

### (4) 借りられる設計・実装アイデア

scheduled taskを時刻だけでなく **durable obligation** として表す。

```text
TemporalObligation {
  obligation_id
  due_at
  semantic_class
  required_runtime_epoch?
  state: DUE | HELD_MAINTENANCE | DISPATCHED | COMPLETED | SUPERSEDED
  attempt_epoch
  completion_receipt?
}
```

maintenance barrier中は `DUE -> HELD_MAINTENANCE` とし、schedule cursorを成功扱いで進めない。

### (5) Kamimusuhiとの差分

既出の software-body epoch は **「どのversionの身体で走ったか」** を守る。Expected Continuation / Completion Publication Barrierは **「開始済みworkをどう終わらせるか」** を守る。

今回の差分は、まだdispatchしていない **時間的義務そのものをmaintenanceで失わない** こと。

### (6) 次に検証すべきこと

**`MaintenanceDeferredObligationBench-v0`**

- due直前にsoftware update開始
- update中にtickを複数回発火
- schedule cursorだけ進んでjobが消えないこと
- update成功後に1回だけdispatchされること
- update rollback / crash / rebootでもobligationが残ること
- `LATEST_ONLY` jobは複数missを1件へcoalesceできること
- staleで無意味なsensor-derived jobは逆にdropできること

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent orchestrationではretry/recoveryに焦点が当たりやすいが、これはcron schedulerとsoftware updaterの交差点にある。**「未実行の仕事が消える」**ため通常のfailure logにも現れにくい。

### (8) 重要度

**A+** — Kamimusuhiのsleep/consolidation/default cognitionはscheduled background workを多用する予定で、maintenance頻度も高い。slot消失は静かに長期人格・memory hygieneを劣化させるため早期fixture化価値が高い。

## 5.3 A — Causal Cancellation Scope Across Key Projections: stop対象はstorage keyではなくinteraction scope

**Primary source**

- NousResearch/hermes-agent PR #113738 — *fix(gateway): /stop falls back to any running turn in the same chat*  
  https://github.com/NousResearch/hermes-agent/pull/113738  
  調査時点: **open / mergeable / 未merge**

### (1) 何が実証済みか

PRは、running turnと`/stop`が同じlogical chatに属していても、normalization後のsession keyが異なると「no active task to stop」になり、turnが走り続ける2条件を再現している。

- top-level channel turnは `chat_type=channel` だがreply-thread側のstopは `chat_type=thread`
- rolling-DM configではrunning sessionがthread slotなし、stop側はthread付き

新しい4 invariant testはbaseで2条件がred、提案patch後green。authz gateとcross-chat isolationもpinし、focused `stop/slash/busy` suiteは376 passと報告されている。

### (2) 何が提案・推測段階か

Kamimusuhiで「同じchatなら全部止める」を一般化してはいけない。multi-principal / multi-agent / branchを含むため、stop scopeは少なくとも principal、surface、conversation/episode、run generationを組み合わせる必要がある。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- interruption / emergency stop
- K-Edge / K-Core handoff
- multi-surface conversation
- speech cancellation
- subagent/tool cancellation
- Social Harness
- distributed embodiment

### (4) 借りられる設計・実装アイデア

`CancellationTarget` をraw keyから分離する。

```text
CancellationTarget {
  principal_id
  interaction_id
  causal_run_id
  run_generation
  accepted_key_projections[]
  scope_boundary
}
```

resolve手順:

```text
surface input
 -> canonical interaction scope resolve
 -> authority check
 -> active owner/generation resolve
 -> cancellation dispatch
 -> descendant effect closure check
```

### (5) Kamimusuhiとの差分

直前回の `CancellationClosureBench-v0` は **正しいparent taskを止めた後に孫process/tool subprocessが残らないか**を扱った。

今回の新規差分はその前段:

```text
can resolve the intended running turn?
        ↓
can stop its owner?
        ↓
are all effectors quiescent?
```

この3段を別testにする。

### (6) 次に検証すべきこと

**`CancellationTargetProjectionBench-v0`**

- same interactionをDM / thread / top-level / voice surface / device handoffで複数projection
-各surfaceからSTOP
- canonical interactionに属するactive generationだけ止まること
- sibling chat / different principal / intentionally forked branchへ越境しないこと
- stale surfaceの古いrun generationが新runを止めないこと
- target resolve成功後は既存`CancellationClosureBench`へ接続

### (7) 既存デイリーサーベイではなぜ拾いにくいか

停止機構は通常「signalがprocess treeへ届くか」で評価されるが、この問題はchat normalization / routing key / UI threading semantics側に潜る。HCIとdistributed identityの境界にあるため、一般agent safety検索では見落としやすい。

### (8) 重要度

**A** — emergency stop / user interruptionで「停止要求は届いたのに別keyなので何も止まらない」は危険。既存 cancellation closure と組み合わせるとend-to-end stop contractになる。

## 5.4 B+ — Bounded Observer Leases: watch権限を永続capabilityにしない

**Primary source**

- letta-ai/letta-code PR #4507 — *fix(tools): require Monitor deadlines*  
  https://github.com/letta-ai/letta-code/pull/4507  
  調査時点: **draft / open / human verification pending**

### (1) 何が実証済みか

PRはClaude Code側のMonitor contract変更へ追随し、Letta Codeが保持していた `persistent: true` と最大1時間deadlineを削除する提案。command / WebSocket monitorはdeadline必須、default 5分・max 30分へ寄せ、`TaskStop`による早期cancelは維持する。

focused monitor/interrupt tests 38件とcheck 12/12が通ると報告されている。ただしPR自身が **自動生成draftでhuman verification pending** と明記しており、本番failureの証拠としては扱わない。

### (2) 何が提案・推測段階か

Kamimusuhiの全observerを30分以下にする根拠はない。借りるべきなのは数値ではなく、**observerはleaseを持ち、継続観測にはrenewalが必要**という構造。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- resource health monitor
- external service / file / stream watcher
- sensory subscriptions
- background cognition
- telemetry / observability
- privacy-sensitive context monitoring
- proactive agent triggers

### (4) 借りられる設計・実装アイデア

```text
ObservationLease {
  observer_id
  principal_id
  source_scope
  purpose
  expires_at
  max_event_rate
  privacy_class
  renewal_capability
  cancellation_owner
}
```

lease expiry時はsilent detachではなく、必要に応じてdurable `observer_expired` eventを残す。renewalは元のprincipal/purpose/fresh policyで再評価する。

### (5) Kamimusuhiとの差分

既出の **Observer Back-Action** はpollingがlock/I/O/jitterを生むこと、**observer sync vs execution authority** はobserverがstateを見てもturnを再開してよいとは限らないことを扱った。

今回は第三軸として **観測の時間的authority** を追加する。

```text
may observe now
!=
may observe forever
```

### (6) 次に検証すべきこと

**`ObserverLeaseExpiryBench-v0`**

- file/websocket/process/sensor monitorを異なるleaseで開始
- expiry後にevent injectionが止まること
- renewalなしでreboot後に復活しないこと
- privacy policy変更時はrenewal拒否できること
- observer expiryが監視対象processを誤停止しないこと
- `TaskStop` / episode close / owner migrationとの優先順位を検証

### (7) 既存デイリーサーベイではなぜ拾いにくいか

monitorは「read-only utility」と扱われやすく、capability lifetimeやprivacy retentionの議論から漏れやすい。実際にはwatchは継続的なデータ取得権限であり、long-lived AIでは大きなprivacy surfaceになる。

### (8) 重要度

**B+** — 構造は有望だが、今回の一次evidenceはdraft PRとupstream contract追随で、事故削減の実証ではない。watchlist / fixture先行が妥当。

## 5.5 A- delta — Attachment Incarnation Rebind after Body Replacement

**Primary source**

- NousResearch/hermes-agent PR #113730 — *fix(desktop): reconnect SSH sockets after managed updates*  
  https://github.com/NousResearch/hermes-agent/pull/113730  
  調査時点: **open / mergeable / 未merge**

### (1) 何が実証済みか

managed SSH updateが成功しremote backendがrestoreされても、Desktopのsecondary gateway socketがreplaced Linux backendへbindされた古いconnectionを保持し、GUIが通信不能になり得る。提案patchは `ok && restoreOk` のとき既存secondary socketを強制reconnectし、focused testは修正前0 call / 修正後1 callをpinする。partial/failed transactionではreconnectしない。

### (2) 何が提案・推測段階か

Kamimusuhiの全connectionをupdate後無条件reconnectすべきとは限らない。connectionがincarnation-awareでlive migration可能なら維持できる。必要なのは attachment と body incarnation の整合確認。

### (3) 関係サブシステム

- K-Edge / K-Core remote attachment
- device/surface connection
- model server replacement
- software-body epoch
- distributed embodiment

### (4) 借りる案

既存 `MixedSoftwareBodyEpochBench-v0` に:

```text
body_incarnation_id
attachment_bound_incarnation
post_update_rebind_required
rebind_receipt
```

を追加する。

### (5) Kamimusuhiとの差分

これは独立新原則ではなく、9月17日01:02の **software-body namespace epoch coherence** をconnection layerへ延長する実証差分。

### (6) 次に検証すべきこと

- backend process replacement
- old socket half-open / stale route / reconnect
- update success後に全required attachmentがnew incarnationへbind
- failed updateではcurrent working attachmentを破壊しない
- multi-deviceで一部だけold incarnationの状態を検出

### (7) なぜ拾いにくいか

software update研究はartifact/process versionに寄りやすく、GUI/socketが「正常終了したupdate後も古い身体へ繋がる」client-side residual stateは見落とされやすい。

### (8) 重要度

**A- delta** — distributed embodimentでは重要だが、既存software-body epoch findingへの具体化として吸収すべき。

## 5.6 B+ watch — Audit-Preserving Cryptographic Forgetting

**Primary implementation source**

- swap-mitra/memvault  
  https://github.com/swap-mitra/memvault  
  README: https://github.com/swap-mitra/memvault/blob/main/README.md

### (1) 何が実証済みか

公開READMEと実装は、MemVaultが:

- append-only hash-chained ledger
- retrievalごとの `retrieval_id` とcandidate/outcome記録
- bitemporal query
- `memory_forget` によるcryptographic erase

を提供すると説明している。設計上はfact contentの暗号鍵を破棄し、ledger record自体は残すため、chain integrityと「忘却された」というhistoryは保持する。

今回この場で独立security auditや全残留surfaceの実測は行っていないため、**provable forgettingという強い表現をKamimusuhiでそのまま採用はしない**。

### (2) 何が提案・推測段階か

Kamimusuhiで有用なのは次の分離。

```text
content confidentiality / recoverability
!=
audit provenance of the erase event
```

ただし vector embedding、BM25 index、cache、backup、replica、log、derived summariesに内容を推測できる情報が残れば、key destructionだけでは個体全体のforgettingにならない。

### (3) 関係サブシステム

- privacy-preserving memory
- user-owned memory / consent
- distributed erasure
- bitemporal canonical evidence
- retrieval provenance

### (4) 借りる案

fact単位/segment単位のDEKを持ち、forget時に:

```text
DestroyContentKey
InvalidateIndexes
PurgeCaches
PropagateReplicaErase
RecordMinimalForgetReceipt
```

を分離。ledgerにはcontentそのものではなく、object id、time、authority、erase completion、residue policyのみ残す。

### (5) Kamimusuhiとの差分

Kamimusuhiは既に distributed erasure completion と storage-vs-use forgetting を持つ。MemVaultはその一部を実装した **reference pattern** であり、新規原則ではない。

### (6) 次に検証すべきこと

**`CryptoForgetResidueBench-v0`**

- fact contentにcanary秘密を入れる
- write → retrieve → index/cache/backup作成 → forget
- raw DB / index / embedding / ledger / backup / replicaからcanary回収可能性を測る
- forget receipt自体から内容が過度に推測できないか確認
- key backup / process memory / crash直前snapshotも対象

### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory研究はretrieval accuracyやcompressionが中心で、privacy系は「削除APIがあるか」で終わりやすい。一方これは暗号鍵生命周期、tamper-evident logging、bitemporal provenanceの交点にある。

### (8) 重要度

**B+ watch** — 方向はKamimusuhiと非常に相性が良いが、全residue surfaceの監査前に強いerase保証として採用すべきではない。

### 最小state model案

```text

  SET | DELETE | REVOKE | FORGET | REPLACE_SUBTREE

  DUE -> HELD_MAINTENANCE -> DISPATCHED -> COMPLETED

Cancellation
  TARGET_RESOLVED -> AUTHORIZED -> OWNER_CANCELLED -> EFFECTORS_QUIESCENT

Observation
  ACTIVE_LEASE -> RENEWED | EXPIRED | REVOKED

Attachment
  BOUND(epoch=n) -> BODY_REPLACED(n+1) -> REBIND_REQUIRED -> BOUND(n+1)
```

## 11. 最終判断

今回の中心は、**long-lived cognitionでは「何かをする」positive pathだけでなく、「消す・延期する・止める・期限切れにする」negative / temporal operationsをfirst-class contractにする必要がある**、という点にある。

最も早くKamimusuhiへ効くのは次の2本。

```text
omission is not deletion
maintenance is not completion
```

その上で cancellation を:

```text
target resolution
→ authority
→ owner cancellation
→ effect closure
```

へ分解し、observerはlease、distributed body attachmentはincarnation-awareにする。

**推奨着手順:** `ExplicitNegativeMutationBench-v0` → `MaintenanceDeferredObligationBench-v0` → `CancellationTargetProjectionBench-v0` → 既存software-body epoch fixture拡張 → observer lease → crypto-forget residue audit。
