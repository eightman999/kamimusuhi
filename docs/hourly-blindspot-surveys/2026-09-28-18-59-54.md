## 3. 候補ごとの評価

### 3.1 A update — Recovery-Plane Failure-Domain Independence

Fresh: OpenClaw #160267  
https://github.com/openclaw/openclaw/issues/160267

1. **実証済み**: gateway restart が restart intent を state DB に書いてから serving process をsignalする設計で、実運用のmain-thread wedge時に対象process自身がstate-lifecycle coordinatorを保持し続け、CLI restartがintent writeを拒否した。約7時間37分の停止中、復旧にはOS service-manager側の操作が必要だった。
2. **提案・推測**: 常にstate DBを無視した強制restartを行うべき、という主張ではない。normal laneが成立しない時だけ使うout-of-band recovery authorityを別failure domainに置く案。
3. **関係subsystem**: Continuity Kernel、Software Body、watchdog、K-Core/K-Edge supervisor、restart / migration / degraded mode。
4. **借用案**: normal maintenance lane と emergency recovery lane を分離。emergency laneはtarget runtimeのevent loop / state coordinator / plugin graphへ依存しない。復旧後にemergency recovery receiptをcanonical storeへreconcileする。
5. **Kamimusuhiとの差分**: control-plane isolation / microrebootは既出。fresh差分は **repair actuatorそのものが故障targetのowned coordinatorに依存し、最悪時だけ使えない**長時間field evidence。
6. **次の検証**: **RecoveryPlaneIndependenceBench-v0 — P0**。event-loop spin、state-lock永久保持、DB writer wedge、plugin hangを注入し、normal restart failure後も独立supervisorがbounded timeでretire/restartできるか、stale writer fencingとpost-recovery receiptを確認。
7. **拾いにくい理由**: continuity研究はrestartの正しさを見るが、restart契約を実行する機構自体の生存性はOS/SREへ落ちやすい。
8. **重要度**: **A update**

更新原則: **recovery actuator should not share the exact failure dependency it must recover.**

### 3.2 A update — Observer-Plane Workload Budget & Serving Isolation

Fresh: OpenClaw #160337  
https://github.com/openclaw/openclaw/issues/160337

1. **実証済み**: 約4.3 GB、2,782 sessions、183k transcript_eventsのstoreでheavy dashboard/webchat use中にgateway main threadが100% CPUとなり、HTTP/WebSocket servingが停止してwatchdog restartになった。storeはretention cap内。bootではsync SQLite hold、wedge sampleではJS deserialization/allocation/GC/string conversionがhotだった。
2. **提案・推測**: 全readを別processへ移す必要はない。small stateはin-processで十分。必要なのはread/projectionにもbounded work budgetを持たせること。
3. **関係subsystem**: Observability、DialogueSession history、Canonical Evidence reader、operator UI、event loop、homeostasis。
4. **借用案**: observer queryにpage/row/bytes/CPU-time budgetを持たせ、large projectionはworkerへ移す。critical serving pathにはmax synchronous work slice / max event-loop lagを設ける。
5. **Kamimusuhiとの差分**: 既出observer back-actionはpolling/lock contention中心。今回は **正常にboundedなstoreでも正当なhistory readのworking setがserving cognitionをstarve** する。
6. **次の検証**: **ObserverPlaneWorkBudgetBench-v1 — P0**。100 MB / 1 GB / 5 GB相当stateでhistory/search/dashboardを並行し、p99 loop lag、turn latency、health latency、RSS/GCを測る。
7. **拾いにくい理由**: observabilityは「見るだけ」に見えるが、実装上はDB read・projection・serialization・GCを生むactive workload。
8. **重要度**: **A update**

更新原則: **bounded storage does not imply bounded observation work.**

### 3.3 A update — Causal Freshness of Operational Verdicts

Fresh: Hermes Agent #126190  
https://github.com/NousResearch/hermes-agent/issues/126190

1. **実証済み**: 過去のrate-limit時のlast_failure_errorが、後のdependency wait→ready遷移後も残り、respawn guardが古いtextをcurrent auth blockerと解釈した。4 tasksが約27時間readyのまま、各task 1,400回超のguard eventを出し続け、credential問題という誤診断も提示した。
2. **提案・推測**: historical errorを削除すべきではない。audit evidenceとして残しつつ、current guard authorityと分離すべき。
3. **関係subsystem**: scheduler、standing duties、retry/respawn、health diagnosis、self-maintenance。
4. **借用案**: operational verdictへattempt_id / state_generation / valid_until / superseded_byを持たせる。human-readable error textをcontrol predicateへ再parseしない。
5. **Kamimusuhiとの差分**: causally superseded verdict / generation-aware diagnostic suppressionは既出。fresh差分は **stale diagnosisがfuture work admissionを永久拒否するcontrol authorityへ昇格** した点。
6. **次の検証**: **OperationalVerdictFreshnessBench-v1 — P0/P1**。rate-limit→dependency→ready、auth failure→repair、resource pressure→recovery、manual unblock、restartを交差し、historical evidenceを残しつつfalse block=0を要求。
7. **拾いにくい理由**: observabilityでは古いerrorを保持したいが、schedulerでは有効期限とcausal scopeが必要。
8. **重要度**: **A update**

更新原則: **historical diagnostic evidence is not current control authority.**

### 3.4 A update — Secondary Telemetry Copy Governance

Fresh: OpenClaw #160361  
https://github.com/openclaw/openclaw/issues/160361

1. **実証済み**: delivery pathがagent reply全文をstdout/systemd journalへ1行ずつ記録し、nested laneではsession/run/channelとrecipient識別子も含む。報告環境で24時間に約1.1k nested recordsと約63k reply/continuation records、peak 71k records/hour。会話本文とrouting identifierがtranscriptとは別retention/readersのjournalへ複製された。
2. **提案・推測**: diagnostic modeでのcontent samplingまで禁止するものではない。explicit opt-in / bounded retention / reader scope / redactionがあれば正当化できる場合がある。
3. **関係subsystem**: Observability、privacy-preserving memory、relationship memory、logging、backup/export、incident forensics。
4. **借用案**: service logはmetadata default。payloadはdefault-off。content captureは別policy domainとし、retention/reader/export scopeを明示。recipient IDにもsensitivity labelを持たせる。
5. **Kamimusuhiとの差分**: privacy-before-capture / live-only sensitive context custodyは既出。fresh差分は **通常会話replyがdelivery loggerにより別policyのOS journalへ大規模自動複製されるshadow memory** のfield evidence。
6. **次の検証**: **TelemetryShadowCopyGovernanceBench-v1 — P0/P1**。user/assistant/tool/private-derived output、recipient IDs、failure/retryを流し、journal/OTLP/error log/exportをscan。default raw payload duplicate=0を要求。
7. **拾いにくい理由**: memory/privacyはcanonical storeを見て、SRE loggingはdebug convenienceを見る。長寿命agentではjournalも実質的な第二の記憶。
8. **重要度**: **A update**

更新原則: **diagnostic duplication creates a separate memory domain and must be governed as one.**

### 3.5 B update — Bound Tool Contract Parity

Fresh: OpenClaw #160272  
https://github.com/openclaw/openclaw/issues/160272

1. **実証済み**: code-mode sessionのlive exec toolはJavaScript実行contractなのに、同sessionからAPI.readで得るtools/exec.d.tsとcatalog.searchはshell execのcommand/workdir/pty等という別contractを返す。同一identifierがlive bindingとstatic introspectionで互換性のないschema/semanticsを指す。
2. **提案・推測**: 全tool名を長いnamespaceへ変更する必要はない。session-scoped resolutionやcontract digestでもよい。
3. **関係subsystem**: Cognitive Resource Registry、tool/model orchestration、code execution、action safety。
4. **借用案**: ToolRefをnameだけでなくnamespace/provider + schema digest + bound generationで識別する。catalog/docsはcurrent bound contractを返すかambiguous candidatesを返す。
5. **Kamimusuhiとの差分**: ClosedWorldToolResolutionBench-v0はcollision/schema epoch mismatchを既に含む。fresh差分は **runtime bindingは正しいが、agentが参照するstatic documentation planeだけが別semanticsを返す** contract-parity failure。
6. **次の検証**: **BoundToolContractParityBench-v1 — P1**。同名異schema、hot reload、code/shell/local/remote variants、catalog cache、reconnectを作り、live schema digest == introspected digestを要求。
7. **拾いにくい理由**: registryとdocs/typesは別subsystemだが、agentは両方をtool knowledgeとして使う。
8. **重要度**: **B update**

### 3.6 B update — Meta-Memory Usage Evidence Integrity

Fresh: Hermes Agent #126181  
https://github.com/NousResearch/hermes-agent/issues/126181

1. **実証済み**: holographic memory schemaにはretrieval_countが存在しqueryでもselectされるが、issueおよびsource searchではincrement pathがなく0のまま。現在rankingは主にtrust_scoreを使うため、直ちにretrieval orderingを壊す証拠はない。
2. **提案・推測**: retrieval_countをforgettingやsalienceへ使うべきという主張ではない。単純countはhelpfulnessとも異なる。
3. **関係subsystem**: episodic/semantic memory、graceful forgetting、memory self-observation、experience-driven consolidation。
4. **借用案**: retrieval attempt / prompt injected / cited-used / helpful feedbackを分離。counter writer、transaction、read-only process、batch flush、crash semanticsを明示。
5. **Kamimusuhiとの差分**: memory recall/salience/feedbackは既出だが、**meta-memory featureがschemaにあるだけでproducerが存在しないsilent-zero failure**はself-calibration入力品質として独立にtest価値がある。
6. **次の検証**: **MemoryUseEvidenceIntegrityBench-v0 — P1**。retrieve-only、injected、cited、helpful/unhelpful、concurrent readers、read-only、crash-before-flushでusage telemetryの正確性を測る。
7. **拾いにくい理由**: memory benchmarkは回答精度/recallを見るが、memory systemが自分の使用履歴を正しく観測するかはmetacognition/telemetry/database境界。
8. **重要度**: **B update**

## 7. 既存docsへの追記候補

### architecture.md

- self-recovery supervisorへ failure-domain independence を追加
- observability/history readerへ CPU / bytes / rows / event-loop work budget
- operational verdictをstate generation / attemptへbind

### spec.md 候補

1. recovery mechanismは、recover対象runtimeが所有するscheduler/lock/coordinatorだけに依存してはならない。
2. observability/history workloadはlatency-critical cognitionとhealth pathをstarveできないようboundedでなければならない。

4. raw conversational payloadを別retention/reader scopeのtelemetry/log domainへ暗黙複製してはならない。
5. effectful tool identityはeffective live contractへbindし、static catalogとの不一致をsilentに許可してはならない。
6. ranking/forgetting/self-calibrationへ使うmeta-memory counterはproducer coverageとfailure semanticsをtestしなければならない。

## 11. 今回の結論

今回、独立新規原則を無理に増やすより価値が高かったのは、既存の control-plane / observability / provenance 原則を **長時間・大規模運用で実際に壊れる境界まで具体化すること**だった。

最優先は:

1. **回復機構を壊れた本体と同じfailure domainへ閉じ込めない。**
2. **観測・履歴閲覧にもwork budgetを持たせ、認知servingをstarveさせない。**
3. **過去のdiagnosticを現在のcontrol authorityとして使わない。**

> **maintenance / observability / diagnostics are not outside the cognitive system; they are resource-consuming, authority-bearing organs and must be governed accordingly.**
