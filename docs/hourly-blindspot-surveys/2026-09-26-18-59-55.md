## 3. 候補ごとの評価

### 3.1 A — Monotonic / Non-Replayable State Restore Closure

**Fresh source:** OpenClaw #158784, 2026-09-26  
https://github.com/openclaw/openclaw/issues/158784

**Supporting specifications:**
- Matrix Olm: https://spec.matrix.org/unstable/olm-megolm/olm/
- Signal Double Ratchet: https://signal.org/docs/specifications/doubleratchet/
- GlobalPlatform TEE System Architecture v1.3: https://globalplatform.org/wp-content/uploads/2022/05/GPD_SPE_009-GPD_TEE_SystemArchitecture_v1.3_PublicRelease_signed.pdf

1. **実証済み:** unclean shutdown後にvalidだが古いMatrix crypto snapshotをrestoreすると、Olm ratchet stateが後退し、outboundだけが継続的にdecrypt不能になる事例が報告された。device identity等は一見healthyで、古いsession stateを捨てて再handshakeすると回復した。
2. **提案・推測:** Kamimusuhiに同じE2EE実装はない。全monotonic stateへhardware counterを要求する主張でもない。
3. **関係箇所:** distributed embodiment、authenticated surfaces、migration、backup/restore、relationship channel、Continuity Kernel。
4. **借用案:** snapshot対象を `REPLAYABLE / MONOTONIC_ADVANCE / RENEGOTIABLE_EPHEMERAL / ONE_SHOT` で型分けし、rollback-sensitive stateを通常snapshotと同じrestore contractへ置かない。
5. **差分:** 既存rollback / last-surviving-copyは「どのcopyへ戻るか」を扱う。本件は**古いcopyが真正でも、戻すこと自体がprotocol correctnessを壊す**。
6. **次の検証:** `MonotonicStateRestoreBench-v0`。counter/ratchet generationを進め、古いsnapshotからの再activationを拒否し、renegotiable stateはdiscard→re-establishする。
7. **拾いにくい理由:** secure messaging / trusted storage / crash consistencyとagent continuityの境界。
8. **重要度:** **A**。

### 3.2 A — Durable Parent-Prerequisite Revalidation

**Fresh source:** Hermes Agent #123583, 2026-09-26  
https://github.com/NousResearch/hermes-agent/issues/123583

1. **実証済み:** live agentが「session rowは作成済み」というprocess-local flagを信じ続け、外部delete/prune/store replacement後も再検証しないため、その後のmessage appendが毎回失敗し、visible conversationだけ進んでdurable transcriptが無音で停止するreproが報告された。
2. **提案・推測:** KamimusuhiのDB schemaが同型とは限らず、missing parentを自動再作成することも常に正しいとは限らない。
3. **関係箇所:** DialogueSession、Canonical Evidence、Self History、Continuity Kernel、prune/migration/repair。
4. **借用案:** durable parent referenceへ `store_generation / object_generation / lifecycle_state` を持たせ、child append時にcurrentnessを検証。write失敗はcached prerequisiteを即invalidateする。
5. **差分:** Corruption-Preserving Publicationは unreadable vs absent、Authoritative Lifecycle Resolverはprojection由来の存在誤判定。本件は**一度成立した前提が長寿命process中に失効する**問題。
6. **次の検証:** `DurableParentPrerequisiteBench-v0`。active session下でparent delete/store replaceを注入し、silent durable lossを禁止する。
7. **拾いにくい理由:** DB referential integrity、cache invalidation、canonical evidenceの交差点。
8. **重要度:** **A**。

### 3.3 A update — Cancelled-Intent Replay Exclusion

**Fresh sources:**
- Hermes #123532: https://github.com/NousResearch/hermes-agent/issues/123532
- Hermes #123533: https://github.com/NousResearch/hermes-agent/pull/123533

1. **実証済み:** queued user inputをaccept時にtranscriptへ保存した後、Stop/reset/dedup pathがqueueだけをdiscardするとrowがactiveのまま残り、resume時にcancel済みinputが過去のuser messageへ結合されmodelへ再提示される問題が再現された。fixはrowを削除せずinactive化する。
2. **提案・推測:** audit上はcancelled inputを保持してよい。存在そのものの削除とfuture cognitionへの利用停止は別。
3. **関係箇所:** DialogueSession、queue、canonical interaction evidence、memory derivation、deterministic replay、user intent。
4. **借用案:** `ACCEPTED / QUEUED / DISPATCHED / CANCELLED_BEFORE_DISPATCH / INTERRUPTED_AFTER_DISPATCH / COMPLETED` と `ACTIVE / AUDIT_ONLY / SUPERSEDED` を分離。
5. **差分:** cancellation consequence closureはfuture effect authority中心。本件は**user-originの本物の入力でもcancel後はfuture cognitionのactive replay資格を失う**。
6. **次の検証:** `CancelledIntentReplayBench-v0`。restart/compaction/replay/memory extraction後もcancel済みinputがactive prompt・preference・commitmentへ昇格しないことを確認。
7. **拾いにくい理由:** UI queue bugに見えるが、speech-act validity / event sourcing / replay semanticsの問題。
8. **重要度:** **A update**。

### 3.4 B — Effectful Gesture Single-Consumer Closure

**Fresh source:** Hermes #123755, 2026-09-26  
https://github.com/NousResearch/hermes-agent/issues/123755

1. **実証済み:** 同じkeyboard gestureをfocused composerの編集操作とglobal queue-dispatch handlerが同時に処理し、1入力で編集とmessage dispatchの両方が起こるケースが再現された。
2. **提案・推測:** keyboard固有のbugであり、Kamimusuhi全surfaceに同型collisionがある証拠ではない。
3. **関係箇所:** HCI、desktop/TUI/mobile、K-Edge reflex、DialogueSession、Action Router、hardware button。
4. **借用案:** gestureへ `surface_id / focus_owner / interaction_mode / gesture_id / generation` を持たせ、まずsingle semantic actionへresolveしてからeffect admissionする。
5. **差分:** UI-control-plane vs conversational agencyより前段の、**同一physical inputのsemantic ownership**。
6. **次の検証:** `GestureEffectConsumptionBench-v0`。focus/modeをcross-product化し、1 gestureが複数effectful actionへresolveしないことをfuzz。
7. **拾いにくい理由:** GUI event propagation / mode error / human factors側に見える。
8. **重要度:** **B**。

### 3.5 B update — Perception-to-Turn Delivery Acknowledgement

**Fresh source:** Hermes #123357, 2026-09-26  
https://github.com/NousResearch/hermes-agent/issues/123357

1. **実証済み:** voice barge-inでspeech detection、playback interruption、recording、STTまで成功しても、stale callback stateによりturn admission前にsilent dropする事例が報告された。
2. **提案・推測:** issue時点のroot-cause analysisであり、全voice pathでのfix完了は未確認。
3. **関係箇所:** auditory perception、turn-taking、K-Edge→DialogueSession、Global Workspace ingress。
4. **借用案:** `CAPTURED -> TRANSCRIBED -> INTENT_CLASSIFIED -> TURN_ACCEPTED/REJECTED -> WORKSPACE_DISPATCHED` をcorrelation ID付きで追う。silent returnは禁止。
5. **差分:** 09/25 Cognitive Payload Deliveryはskill/evidence→model request。本件は**sensor perception→conversation ingress**方向へのextension。
6. **次の検証:** `PerceptionTurnDeliveryBench-v0`。barge-in、busy→idle transition、reconnect、STT latency、double interruptをfault-injectionする。
7. **拾いにくい理由:** multimodal benchmarkは認識精度を測りがちで、認識後のevent deliveryはHCI/runtime側へ落ちる。
8. **重要度:** **B update**。
