## 3. 要約

今回もっとも重要なのは、**「継承」と「停止」をそれぞれ一枚のboolとして扱わない**ことだった。

Hermes #113425 は、named profile が自分のcredentialを持たないとき、root profileの `auth.json` を読むだけでなく、token refresh時にroot storeを**書き換える**設計になっていた。便利なfallbackだったが、profile isolationの観点では「設定を共有しているから権限も借りてよい」というambient authorityになっていた。修正後は各profileがcredentialを所有し、明示的なclone/mirrorだけがAPI keyを複製する。OAuthのsingle-use grantは明示再loginを要求する。

一方 Letta #4497 は、`TaskStop` がsubagent processを止めた時点で `killed:true` を返しても、そのagentが起動したtool subprocessがOSにreparentされて生存し得ることを実証した。長寿命agentでは「taskが止まった」という高レベル状態と「effectを起こし得る全descendantが静止した」という低レベル状態を分ける必要がある。

Hermes #113419 は、protocol adapterが内部historyをResponses wireへ変換するとき、reasoning itemの後にすでにfunction_callが存在するのにblank assistant messageを合成し、それを毎turn replayしていた。これは単なるserialization bugではなく、**canonical historyに存在しないsemantic eventをadapterが発明した**という provenance 問題である。Kamimusuhiでは provider compatibility shim をcanonical evidence producerにしてはいけない。

Letta #4483 は逆方向のauth gapを示す。既知IDへのA2A messageはacting human senderで送れるのに、shared-agent listingはsandbox API keyだけで評価していたため、「知っていれば話せるが、その人として発見できない」状態になった。discovery / enumerate / searchはread-onlyだから軽い、ではなく、**そのprincipalに見えてよい存在集合を決める認可操作**である。

さらに Hermes #113432 は、max-output-token exhaustionでvisible textがない場合でもResponses経路だけ同じbudget / reasoning effortを3回再送していた。retry counterは進んでも、failure conditionは一切変わっていなかった。retryには「回数」だけでなく、**前回失敗に対して何を変え、どのprogress signalを期待するか**が必要である。

最後に、9月16日公開のliquid state machine研究は、低消費電力SNN/reservoir系で瞬間spike stateだけをreadoutする設計の弱点を示す。recent reservoir statesを明示的なwindowとしてreadoutへ渡すだけで、NARMA5のridge readout median test NRMSEが2.106→0.317、transformer readoutが0.807→0.179へ改善した。K-Nerve候補では「内部reservoirを大型化する」前に、**短いtemporal evidence bufferをreadoutへ露出する**単純な比較が必要そうである。

# 5. 候補ごとの評価

## 5.1 A+ — Credential Non-Inheritance: configuration lineage と authority lineage を分ける

**Primary source**

- NousResearch/hermes-agent PR #113425 — *named profiles no longer inherit the root profile's credentials*  
  merged **2026-09-17 06:34:59 JST**  
  https://github.com/NousResearch/hermes-agent/pull/113425

**Supporting review**

- Surapani et al., *Authorization Architectures for Tool-Using AI Agents*, arXiv:2609.15906  
  https://arxiv.org/abs/2609.15906

### (1) 何が実証済みか

Hermesのnamed profileは、profile側にcredentialがない場合rootのcredential storeへfallbackしていた。しかもreadだけではなくOAuth/token refreshがroot storeへwrite-throughし、profileがroot ownerのtokenを更新できた。

修正後はread/writeともactive profile storeだけを見る。rootがcredentialを持ちprofileが空の場合、profileは `no_provider_configured` でfail closedし、明示的なprofile login/configを要求する。PRの実probeでは、修正前にprofile BがA/rootのOpenRouter keyを解決していた条件で、修正後はBが明示errorとなりAは前後とも正常。focused runは1337 tests pass。

### (2) 何が提案・推測段階か

Kamimusuhiで全credentialを各deviceへ物理複製すべき、という意味ではない。共有vaultを使ってもよい。必要なのは**credential利用権限がprincipal / embodiment / delegated taskに明示的にbindされ、設定fallbackや親namespaceの存在だけで権限が発生しないこと**。

### (3) 関係するサブシステム / 設計課題

- Cognitive Action Router
- local/frontier model credentials
- MCP / tool providers
- K-Edge / K-Core / K-Deep間のprincipal isolation
- distributed embodiment
- Delegation Envelope / Social Harness
- `INV-006`, `INV-007`, `INV-013`, `INV-014`

### (4) 借りられる設計・実装アイデア

`CredentialBinding` をconfig inheritanceから独立させる。

```text
CredentialBinding {
  principal_id
  provider_id
  credential_ref
  allowed_scope
  valid_from / expires_at
  delegation_receipt?
  embodiment_constraint?
}
```

原則:

- parent/default/root fallbackはcredential selectorとして使わない
- clone時のcredential copyは独立したexplicit operation
- OAuth refresh/writebackも同じprincipal boundaryを維持
- UIの「設定を複製」と「credentialを複製」を別操作にする
- credential欠如は別principalへfallbackせず、degraded modeまたはexplicit delegationへ落とす

### (5) Kamimusuhiとの差分

既存の Delegation Envelope Separation は「子へcontext/authorityを何を渡すか」、executor context transport は「thread境界でprincipal/policyを失わないか」を扱う。今回はそれ以前の、**何も委譲していないのにnamespace fallbackだけでcredentialが生えるambient inheritance**が差分。

### (6) 次に検証すべきこと

**`CredentialInheritanceIsolationBench-v0`**

- principal A/rootはprovider credentialあり、Bはなし
- Bからmodel call / tool call / token refresh / revoke / cooldown resetを試す
- BがA credentialをread/writeできないこと
- explicit delegation receipt付きでは必要scopeだけ利用可能なこと
- clone configのみ / clone API key / OAuth再loginを別caseにする
- restart・migration・profile rename後もbindingが変化しないこと

### (7) 既存dailyではなぜ拾いにくいか

agent authorization一般論では「least privilege」「delegation」を検索するが、これは**profile設定の便利なfallbackがcredential ownerを越境する実装障害**で、auth論文よりmulti-profile lifecycle bugとして現れる。

### (8) 重要度

**A+** — distributed embodiment / multi-principal環境で、ambient authorityを直接発生させる境界。実装可能でfixture化も容易。

## 5.2 A+ — Cancellation Closure: logical stop は effect-bearing descendants の静止まで完了しない

**Primary source**

- letta-ai/letta-code PR #4497 — *terminate stopped agent process trees*  
  merged **2026-09-17 04:25:48 JST**  
  https://github.com/letta-ai/letta-code/pull/4497

### (1) 何が実証済みか

`TaskStop` は以前、headless subagent processだけへsignalを送り即座に `killed:true` を返していた。active tool subprocessは親process終了後にOSへreparentされ、生き残ってresource消費やeffectを継続できた。

修正では各subagentを専用process groupへ入れ、groupへSIGINT、2秒後にも残るprocessはgroupごと強制kill、Windowsでは `taskkill /T /F` を使用する。`TaskStop` はexecution settlementを待ってから成功を返す。real launcher + SIGINT無視descendantによるregression testで、Linux 20/20、macOS 10/10で生存descendantなし。

### (2) 何が提案・推測段階か

OS process groupだけでKamimusuhiのeffect closureが完全になるわけではない。remote job、HTTP request、GPU kernel、queued message、robot actuator commandはprocess tree外に存在し得る。

一般化すべきなのは **cancellation domain がeffect-bearing descendantsを追跡し、stop completionがそのquiescence evidenceを要求する**こと。

### (3) 関係するサブシステム / 設計課題

- K-Deep research worker
- child/subagent orchestration
- Code / shell / tool execution
- external model streaming
- robotics / actuator dispatch
- pre-commit handoff / recovery
- side-effect safety / observability

### (4) 借りられる設計・実装アイデア

```text
CancellationDomain {
  root_execution_id
  local_process_group
  remote_job_ids[]
  outstanding_effect_receipts[]
  pending_deliveries[]
  state: ACTIVE | CANCELLING | QUIESCING | QUIESCENT | UNKNOWN
}
```

`STOPPED` を単なるcontroller stateにせず、少なくとも:

1. new dispatch fence
2. graceful cancel broadcast
3. descendant/effect reconciliation
4. bounded force termination
5. residual unknown effectsのquarantine
6. `QUIESCENT` receipt

までを分ける。

### (5) Kamimusuhiとの差分

既出の cancellation後future-dispatch fence は「cancel後に**新しい**tool callを出さない」、pre-commit handoff abortabilityはauthority yield前のreservation cleanup。今回は、**既にspawn/dispatch済みのeffectorsが親終了後も生き残る**下位runtime問題である。

### (6) 次に検証すべきこと

**`CancellationClosureBench-v0`**

- child → grandchild → tool subprocessを作る
- grandchildはgraceful signalを無視
- parentだけ停止するnaive実装とgroup/domain cancellationを比較
- stop return後にfile/network/CPU side effectが発生しないこと
- remote mock job / queued effect / actuator mockも追加
- cleanup不能なら `QUIESCENCE_UNKNOWN` とし、`killed:true` を返さないこと

### (7) 既存dailyではなぜ拾いにくいか

agent-level surveyはtask cancellation APIやworkflow stateを見るが、**OS reparenting / process-group semantics**はsystems/runtimeの下層へ落ちるため見落としやすい。

### (8) 重要度

**A+** — stop/revokeを安全境界として使うなら、effect closureがなければ虚偽の停止状態になる。local fixtureですぐ再現可能。

## 5.3 A — Semantic Transcoding Integrity: provider adapter は架空の履歴を作らない

**Primary source**

- NousResearch/hermes-agent PR #113419 — *replayed reasoning+tool rounds no longer carry a blank assistant item*  
  merged **2026-09-17 06:23:21 JST**  
  https://github.com/NousResearch/hermes-agent/pull/113419

### (1) 何が実証済みか

Responses adapterがreasoning itemには必ずfollowing itemを置こうとし、同じmessageにfunction_callが既にある場合でも空のassistant itemを挿入していた。その結果、replayed historyは本来の

```text
reasoning -> function_call -> function_call_output
```

ではなく、途中にcanonical historyに存在しないblank assistant eventを含んだ。

real failing-turn fixtureでは修正前3 blank carriers / 5 broken reasoning followers、修正後0 / 0で、5 call/output pairsを保持。報告者のlive A/Bではblank carrierありで4/4 degenerate final、なしで4/4 cleanだった。ただしPR自身が「唯一の原因とは証明していない」と明記している。

### (2) 何が提案・推測段階か

blank eventがKamimusuhiの全providerで同様のbehavior driftを起こすとは限らない。提案する一般則は、**wire compatibilityのためのsynthetic carrierをcanonical semantic eventへ昇格させない**こと。

### (3) 関係するサブシステム / 設計課題

- provider-neutral model adapter
- canonical session evidence
- deterministic replay
- tool call/result pairing
- model migration / backend portability
- provenance / audit

### (4) 借りられる設計・実装アイデア

二層に分ける。

```text
CanonicalTurnGraph
  user / thought-class / utterance / tool_call / tool_result / delivery

ProviderWireProjection
  provider-required carrier / wrapper / compatibility item
```

wire-only itemには `synthetic=true`, `projection_reason`, `provider_schema_version` を持たせ、canonical append禁止。reverse importでもsynthetic carrierをsemantic utteranceと誤認しない。

### (5) Kamimusuhiとの差分

既出 deterministic replay はsoftware/versionを跨いで同じeffect historyを再現する問題、historical semantic upcastingは旧schemaを新schemaへ読む問題。今回は**現在のhistoryをprovider wireへ投影するだけで存在しない発話を作ってしまうprojection impurity**。

### (6) 次に検証すべきこと

**`SemanticTranscodingNoPhantomEventBench-v0`**

- canonical fixture: reasoning/tool call/result/text/no-text混在
- OpenAI Responses / chat-completions / Anthropic / local adaptersへprojection
- canonical semantic graphとround-trip semantic graphが同型であること
- synthetic wire carrier数は許容するがcanonical event countへ混ざらないこと
- call-id / causality edge / tool-result pairingが保持されること

### (7) 既存dailyではなぜ拾いにくいか

provider adapter bugは通常「API互換」「streaming」分類に入り、identity/memory surveyから外れる。しかしlong-lived agentではreplay bytesが将来のbehaviorとmemory interpretationへ影響するため、履歴provenance問題になる。

### (8) 重要度

**A** — provider-neutral architectureを掲げるKamimusuhiで、backend交換時のsemantic history汚染を防ぐ直接的契約。

## 5.4 A — Discovery–Action Principal Parity: listing/searchも認可面である

**Primary source**

- letta-ai/letta-code PR #4483 — *discover agents as the current sender*  
  merged **2026-09-17 03:42:42 JST**  
  https://github.com/letta-ai/letta-code/pull/4483

### (1) 何が実証済みか

Cloud sandboxはA2A message送信時にcurrent human senderを使っていたが、`agents list --shared` はsandbox API keyだけでshared agentをdiscoverしていた。結果、agentはtarget IDを知っていればmessageできる一方、自分が代理するhuman principalとしてそのtargetを列挙できなかった。

### (2) 何が提案・推測段階か

discoveryとactionの権限集合が常に同一であるべき、とは限らない。存在を見せずにknown IDだけ許可する設計や、その逆もあり得る。

重要なのは、**両方が意図したprincipalとpolicyで評価され、ambient service identityへ落ちないこと**。

### (3) 関係するサブシステム / 設計課題

- Social Harness / A2A
- agent / peer registry
- tool/model discovery
- multi-user relationship graph
- shared memory/library discovery
- privacy / existence confidentiality

### (4) 借りられる設計・実装アイデア

`DiscoveryQuery` にprincipalを第一級に持たせる。

```text
DiscoveryQuery {
  acting_principal
  delegated_by?
  namespace
  purpose
  capability
  visibility_policy_epoch
}
```

`list/search/resolve` と `message/invoke/mutate` の各decision receiptを比較可能にする。

### (5) Kamimusuhiとの差分

executor context transportはthread/executor境界でprincipalを失わない話。今回は**同じruntime内でも discovery code path だけ別credential/principalで動く policy-plane divergence**である。

### (6) 次に検証すべきこと

**`DiscoveryActionPrincipalParityBench-v0`**

- human A/Bが異なるshared peer集合を持つ
- same sandbox/service identityからA/Bを代理
- list/search/resolve/messageを実行
- discoveryとactionがそれぞれintended principalで評価されること
- service credential単独でcross-user existence leakageしないこと
- deliberately asymmetric policyも正しく表現できること

### (7) 既存dailyではなぜ拾いにくいか

security surveyはwrite/side effect authorizationを優先しやすく、**listingやsearchを「read-only metadata」として軽視**しがち。A2Aではexistence/relationship topology自体がprivate informationになり得る。

### (8) 重要度

**A** — sociality / multi-principal systemで、発見可能性そのものをprincipal-bound capabilityにする必要を具体化する。

## 5.5 B+ — Progress-Sensitive Retry: retryはfailure conditionを変えた証拠を持つ

### (1) 何が実証済みか

Responses routeでreasoningが`max_output_tokens`を使い切りvisible textが空でも、continuationが同じ2000 token / high reasoning条件を最大3回再送し、同じfailure classから出られなかった。修正後は次attemptでreasoning設定を弱め、output capを2000→4000→8000と変える。fake SSE live reproでは、修正前は同一条件3回、修正後は各attemptでbudgetが変化した。focused mirrors 102 tests pass。

### (2) 何が提案・推測段階か

budgetを倍増すれば必ず成功するわけではない。一般化するのは倍増ruleではなく、**retry policyが前回failure causeに対するinterventionとprogress evidenceを持つこと**。

### (3) 関係するサブシステム / 設計課題

- K-Core / K-Deep model routing
- Cognitive Budget
- degraded mode
- external model recovery
- cost/latency control
- long-horizon orchestration

### (4) 借りられる設計・実装アイデア

```text
RetryAttempt {
  failure_class
  changed_dimensions[]
  expected_progress_signal
  budget_delta
  attempt_deadline
  stop_reason
}
```

同一failure fingerprint + changed_dimensions空なら、blind retryせずdegrade / reroute / surface failureへ進む。

### (5) Kamimusuhiとの差分

既出 hydration retry taxonomy は503等をtransient/permanentに分類する。今回は**retryableと判断した後、同じ条件を再送するだけでは収束しない**というprogress contract。

### (6) 次に検証すべきこと

**`RetryProgressInvariantBench-v0`**

- token exhaustion / rate limit / timeout / malformed response / tool busyを注入
- naive identical retryとcause-aware retryを比較
- attemptごとにfailure fingerprintとinterventionを記録
- cost増大だけでprogressしない場合のstop条件を検証

### (7) 既存dailyではなぜ拾いにくいか

retryは通常SDK/runtime実装詳細として扱われるが、長寿命agentでは同一failure loopがresource depletionやself-triggered outageになる。

### (8) 重要度

**B+** — identity coreではないが、Cognitive Budget / degraded-modeの実装規律として有用。

## 5.6 B+ — Temporal Evidence Window for Reservoir Reflexes

**Primary source**

- Wu et al., *Sliding-window training on readout layer enhances liquid state machines for temporal prediction*, npj Unconventional Computing 3, Article 52, **published 2026-09-16**  
  https://www.nature.com/articles/s44335-026-00093-1

### (1) 何が実証済みか

固定されたliquid state machine/reservoirのreadoutへ、現在stateだけでなく直近の複数spike-stateをwindowとして渡す方法を評価した。

NARMA5でmedian test NRMSEは:

- ridge readout: **2.106 → 0.317**（約85% reduction）
- transformer readout: **0.807 → 0.179**（約78% reduction）

NARMA10 / Mackey–Glassでも同じ定性的傾向。入力historyだけを同じwindowで与えるmatched baselineも改善するが、reservoir-based readoutの方が一貫して低errorであり、reservoirのnonlinear transformationが単なるdelay line以上の寄与を持つことを示した。

### (2) 何が提案・推測段階か

NARMA/Mackey–Glassでのtemporal prediction改善が、そのままKamimusuhiのsalience / interrupt / sensor routingへ移るとは未実証。transformer readoutをK-Nerveへ入れるとlow-latency/energy利点を失う可能性もある。

### (3) 関係するサブシステム / 設計課題

- K-Nerve
- sensory temporal filtering
- event-camera / audio / telemetry reflex
- low-latency anomaly detection
- reservoir / SNN / neuromorphic hardware候補

### (4) 借りられる設計・実装アイデア

reservoir自体を複雑化する前に、readoutへbounded temporal windowを追加する。

```text
spike/event stream
   -> fixed small reservoir
   -> last N reservoir states ring buffer
   -> cheap linear/readout classifier
   -> WAKE / IGNORE / INTERRUPT / ROUTE
```

比較軸は `window length × reservoir size × readout complexity × latency × power × accuracy`。

### (5) Kamimusuhiとの差分

K-Nerve現設計はLIF/SNN/LUT/FSM等を比較するが、temporal memoryを「reservoir内部だけの責務」とみなす必要はない。**短いexplicit temporal bufferをreadout側へ持つ**ことで、小さいreservoirのまま性能を上げられる可能性がある。

### (6) 次に検証すべきこと

**`K-NerveTemporalWindowBench-v0`**

- current-state readout vs 4/8/16/32-step window
- GRU / LIF reservoir / simple event accumulatorを比較
- synthetic temporal pattern + MOVI sensor jitter/anomaly traceの双方で評価
- macro-F1 / detection latency / false interrupt / CPU/GPU power / memory footprintを計測
- transformer readoutはupper bound、linear/ridgeをdeployment候補として比較

### (7) 既存dailyではなぜ拾いにくいか

neuromorphic surveyはdevice / neuron / SNN trainingへ寄りやすく、**readout側の短期temporal context設計**は地味でagent architecture分類にも入りにくい。

### (8) 重要度

**B+** — identity continuityからは遠いが、K-Nerveの実験設計を低コストで改善できるfreshな実証差分。
