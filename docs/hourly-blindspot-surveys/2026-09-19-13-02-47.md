## 1. 今回狙った盲点

1. **lossy compaction が会話内容だけでなく「継続中の仕事を再び操作できる能力」を壊す問題**  
   summary が意味的に自然でも、subagent handle、agent identity、pending verification、cross-agent message provenance が失われれば continuity は壊れる。

2. **migration / restore と branching / clone の意味論の混同**  
   state を複製できても、destination 側の provider identity、OAuth、recovery ownership、local secret source をそのまま複製してよいとは限らない。

3. **memory scope が primary recall には効くが derived operation で消える問題**  
   recall / reflect / prefetch / consolidation / dream の一部だけが owner/tag/purpose scope を無視すると、memory domain separation は実装上無効になる。

4. **human-agent handoff 中の embodiment が agent-idle と判定される問題**  
   activity clock が静かでも、人間が control lease を握って使用中なら resource は live である。activity と possession/control を分離して扱えるか。

5. **Theory of Mind を自然言語の人物像としてだけ持つ問題**  
   nested belief、knowledge、want、unknown、common ground の型と推論境界を programming-language 的に表現できるか。

6. **proposal を検証していても proposer-computed post-state を信用してしまう問題**  
   distributed systems の Byzantine client 検証から、high-impact self-mutation / shared state transition に independent execution validation を借りられるか。

補助探索として、context compaction、profile cloning / rebirth、memory scope propagation、human-in-the-loop embodiment、programming languages for social cognition、Byzantine transaction validation、Zenn / Qiita / note の当日実装記録を走査した。

## 5.1 A — Compaction Continuation Closure

**Primary:** Letta Code PR #4559  
https://github.com/letta-ai/letta-code/pull/4559  
**Support:** *The Compaction Cliff in Long-Running AI Agent Memory*  
https://arxiv.org/abs/2608.22752

### (1) 何が実証済みか

Letta の実装記録では、subagent-heavy conversation を2回 compact した際、3/6 task notifications が summary 上 `failed` になった一方、worker は実際には継続し後から結果を返した。さらに agent ID truncation、worker-reported artifact の attribution 消失、local/cloud compaction prompt の task-state parity 欠如が確認された。PR は open だが regression motivation と test changes は具体的である。

別研究の Compaction Cliff は、type-blind compaction による safety-rule retention の急落と、typed retention policy による改善を benchmark で実証している。

### (2) 何が提案・推測段階か

Letta #4559 の word-limit 増加そのものが長期的解決とは未証明。active work state を natural-language summary に含めるだけで arbitrary nesting / crash / cross-device resume を保証できるわけではない。Kamimusuhiではむしろ continuation-critical state を summary から分離する必要がある。

### (3) Kamimusuhiの関連 subsystem / design issue

K-Deep、Global Workspace、Delegation/Orchestration、Expected Continuation、Continuity Kernel、background cognition、sleep/dream、external model/tool handle。

### (4) 借りられる設計・実装アイデア

`ContinuationRegister` を derived summary とは別の typed state として持つ。

```text
ContinuationRegisterEntry {
  obligation_id
  owner_agent_id
  execution_handle
  causal_parent
  status
  last_verified_artifact
  verification_state
  pending_inbound_refs
  authority_scope
  created_epoch
}
```

自然言語 summary はこの register の stable ID を参照するだけにし、active obligation / handle / authority / verification provenance は lossy compaction 対象から外す。

### (5) Kamimusuhiとの差分

Kamimusuhiは canonical evidence と derived views を既に分離するが、「継続中の delegated work を操作可能なまま保持する continuation-critical state lane」はまだ明示契約として弱い。canonical evidence が残っていても、handle と owner mapping を失えば operability は戻らない。

### (6) 次に検証すべきこと

**`CompactionContinuationClosureBench-v0`**

- 6以上の background/subagent/tool jobs を起動
- nested delegation + cross-agent messages + partial verification を混在
- 2〜5回 compaction
- compaction後に各 handle を status/steer/cancel/harvest 可能であること
- running worker を `failed` に誤分類しないこと
- worker-reported SHA/path は verification 済みになるまで attributed claim のままであること
- agent/conversation/task ID を省略・短縮して canonical identity を壊さないこと

### (7) 既存 daily survey ではなぜ拾いにくいか

「memory compression / summarization quality」に見えるが、実際の問題は **control-plane state serialization と resumability**。memory benchmark だけでは、summary 後に task を steer/cancel/reap できるかは測られない。

### (8) 重要度

**A**

**設計要約:** `remembering what was happening != retaining the handles needed to continue it`。

## 5.2 A — Memory Scope-Propagation Closure

**Primary:** Hermes PR #115629  
https://github.com/NousResearch/hermes-agent/pull/115629

### (1) 何が実証済みか

同じ Hindsight provider 内で `_recall()` は tag filter を forward する一方、`_reflect()` は supported `tags` / `tags_match` を落としていた。その結果、direct reflection と reflect-based prefetch が bank-wide retrieval になり得た。修正では default wire behavior を変えず opt-in scope を伝播し、96 tests passed / 2 skipped が報告される。

### (2) 何が提案・推測段階か

PR は open。tag filtering が Kamimusuhi の owner/consent/purpose semantics を十分表現できるとは限らない。また downstream synthesis が scope 内 evidence だけから生成されたことを end-to-end に証明する仕組みは別途必要。

### (3) Kamimusuhiの関連 subsystem / design issue

Persona / relationship / autobiographical memory / Library / social cognition / dream-reflection / consent / privacy-preserving memory / K-Deep。

### (4) 借りられる設計・実装アイデア

memory query に primitive tag list ではなく typed `MemoryEvidenceScope` を持たせ、derived operators すべてに伝播する。

```text
MemoryEvidenceScope {
  owner
  memory_domains
  relationship_scope
  purpose
  consent_epoch
  max_sensitivity
  allowed_derivations
}
```

`recall / reflect / prefetch / consolidate / dream / summarize / export` は scope を明示的に受け取り、未対応 operator は global fallback せず fail closed または conservative scope にする。trace には `scope_requested`, `scope_effective`, `scope_narrowed_by`, `scope_expansion_authority` を残す。

### (5) Kamimusuhiとの差分

Kamimusuhiは memory domain separation を強く持つが、architecture 上の分離と adapter/runtime path の scope propagation は別問題。primary retrieval が正しくても reflect/dream/consolidation が global evidence を読むと境界は破れる。

### (6) 次に検証すべきこと

**`MemoryScopePropagationBench-v0`**

同一 semantic fact を owner A/B、relationship X/Y、private/library、consent epoch old/new に重複配置し、全 memory operator を traverse。出力 context、derived memory、summary、dream artifact に scope 外 evidence が混入しないことを lineage で検証する。特に「scope 未指定 = global」を privacy-sensitive domain では禁止する variant を比較する。

### (7) 既存 daily survey ではなぜ拾いにくいか

memory algorithm / retrieval quality ではなく、**adapter の引数 propagation と derived-operation graph の closure**という実装継ぎ目の問題。普通の memory survey は recall 精度を測っても reflect path の filter 欠落まで見ない。

### (8) 重要度

**A**

**設計要約:** `a scoped memory store is not scoped if one derived operator can silently widen the evidence set`。

## 5.3 A — Branching Identity Clone Semantics / Clone Publication Barrier

**Primary:** Hermes PR #115632  
https://github.com/NousResearch/hermes-agent/pull/115632

### (1) 何が実証済みか

Hermes profile clone では、provider selection をコピーして package/native config を欠落させる path と、逆に provider identity / OAuth state を複製し得る path が同居していた。draft fix は destination publish 前の provider preparation、generation-pinned snapshot、destination-specific AI peer/session prefix、non-transferable credential の reauthentication、offline ownership inspection を導入し、targeted tests/fixtures を報告している。

### (2) 何が提案・推測段階か

PR は draft。native Windows/Linux full suite と live provider authentication は未実施。clone ownership manifest も authenticated provenance ではない。Kamimusuhiで人格・自己モデル・関係・身体まで含む identity branch に一般化できるかは未検証。

### (3) Kamimusuhiの関連 subsystem / design issue

identity continuity、branching identities、death/rebirth、migration/backup/restore、multi-device embodiment、Memory、Persona Core、Continuity Kernel、credential/capability ownership。

### (4) 借りられる設計・実装アイデア

migration と clone を別 operation type にし、各 state item に clone policy を要求する。

```text
ClonePolicy =
  SHARE_BY_REFERENCE
  | COPY_WITH_NEW_OWNERSHIP
  | REGENERATE_DESTINATION_ID
  | REAUTHENTICATE
  | DROP
  | REQUIRE_HUMAN_DECISION
```

新 branch は `ClonePublicationBarrier` を通過するまで discoverable/active にしない。barrier は provider/plugin readiness、new principal IDs、credential status、external references、recovery ownership、lineage parent、unresolved items を検査する。

### (5) Kamimusuhiとの差分

既存の State-Transfer Closure と Credential Non-Inheritance は transfer category を扱うが、**branch を作る行為は「同じ個体を別hostへ移す」ことではない**。どの relation/memory/resource identity を共有し、どれを新生個体用に再発行するかという individuation contract が別途必要。

### (6) 次に検証すべきこと

**`BranchingIdentityCloneSemanticsBench-v0`**

- shared remote Library
- local autobiographical store
- source-private filesystem refs
- OAuth credential
- external peer/agent identity
- device lease
- plugin binary + config

を持つ source individual を branch。意図した shared reference のみ共有され、OAuth/secret はコピーされず、destination peer ID と recovery ownership は新規、half-prepared clone は publish されないことを要求する。repeat clone と abort/rollback も含める。

### (7) 既存 daily survey ではなぜ拾いにくいか

backup/restore・identity continuity・credentials を個別に検索すると出るが、**branching identity の「何を同一のまま共有し、何を個体化するか」**という birth semantics は filesystem/profile clone の実装事故から初めて見えやすい。

### (8) 重要度

**A**

**設計要約:** `clone is a birth/branch operation, not merely a restore to another directory`。

## 5.4 A — Control-Lease-Qualified Resource Lifetime

**Primary:** Hermes PR #115633  
https://github.com/NousResearch/hermes-agent/pull/115633

### (1) 何が実証済みか

human takeover 中は agent interaction が止まるため idle timer が進み、従来 janitor が shared headed browser を human login 中に reap できた。fix は human-held lease + shared-browser provenance を resource liveness evidence として扱い、hand-back 後に通常 reaping を復元する regression を追加。関連 suite 846 passed と報告される。

### (2) 何が提案・推測段階か

PR は open。browser/Bot Screen 以外の robot, wearable, BCI, camera, motor controller, remote desktop で同じ design が十分かは未検証。lease leak による永続保持も別リスク。

### (3) Kamimusuhiの関連 subsystem / design issue

K-Edge、multi-device embodiment、HCI/human-computer integration、shared control、robotics、resource GC、liveness、authority handoff。

### (4) 借りられる設計・実装アイデア

resource lifetime を `last_agent_activity` だけに依存させず、control possession を独立 state にする。

```text
EmbodimentControlLease {
  resource_id
  controller_kind: AGENT | HUMAN | SHARED | EXTERNAL
  principal
  acquired_at
  expiry
  handoff_epoch
  release_receipt
}
```

GC/reaper は `semantic activity`, `pending effect`, `control lease`, `maintenance hold` を別 evidence として評価する。human takeover は agent idle を自然に引き起こすため、idle はむしろ expected state とみなす。

### (5) Kamimusuhiとの差分

既出 Activity-Qualified Destructive GC は「message がなくても task progress/heartbeat があれば消さない」を扱う。今回の差分は、**activity がゼロでも control possession 自体が resource liveness を構成する**こと。multi-device embodiment では不可欠。

### (6) 次に検証すべきこと

**`ControlLeaseQualifiedReapingBench-v0`**

human が browser/device を takeover → agent activity=0 のまま timeout を越える → resource survives → human releases → normal timeoutでreap。さらに agent process crash、human lease expiry、network partition、stale lease、shared mode を注入し、resource leak と premature reap の両方を測る。

### (7) 既存 daily survey ではなぜ拾いにくいか

robotics/HCI survey は takeover usability を、systems survey は idle reaping を別々に扱いやすい。**human-agent control handoff と GC/liveness の seam** は双方の分類から落ちやすい。

### (8) 重要度

**A**

**設計要約:** `no agent activity can be the expected signature of successful human control`。

## 5.5 B — Typed Theory-of-Mind DSL

**Primary:** Chandra et al., arXiv:2609.19598  
https://arxiv.org/abs/2609.19598

### (1) 何が実証済みか

論文は `memo` という実プログラミング言語を用い、`knows`, `wants`, `thinks` のような domain-specific constructs で ToM を表現する worked examples を示す。unbounded structural variation、domain specialization、world knowledge/intuitive physicsとのinterface、child/adult theory の差を同じ formal view で説明できることを例示する。

### (2) 何が提案・推測段階か

agent benchmark で prose/JSON social model より精度・safety・generalization が高いことは未実証。人間の ToM が literal DSL として実装されていることを示す研究でもない。現段階は理論的/formal proposal と見るべき。

### (3) Kamimusuhiの関連 subsystem / design issue

Social Cognition Engine、Relationship Model、common ground、nested beliefs、developmental learning、self/other distinction、Theory of Mind。

### (4) 借りられる設計・実装アイデア

canonical fact と mental-state attribution を型で分離する research-layer DSL を試す。

```text
Observed(p, evidence)
Believes(agent, p, evidence, confidence)
Knows(agent, p, justification)
Wants(agent, goal, strength)
Believes(agentA, Believes(agentB, p))
Unknown(agent, p)
CommonGround(group, p, evidence)
```

inferred belief を world fact へ promote するには別 gate を要求する。development experiment では nested depth / available operators / inference rules を段階的に増やせる。

### (5) Kamimusuhiとの差分

Kamimusuhiは social cognition / relationship state を持つ方針だが、representation が prose/embedding/structure のどこまで formal であるべきかは未固定。DSL は Persona/Relationship の canonical storage そのものではなく、**social hypothesis / query / inference layer** として試すのが安全。

### (6) 次に検証すべきこと

**`SocialTheoryDSLBench-v0`**

Sally-Anne型 false belief、nested belief、common ground、deception、uncertain observation、speaker-specific knowledge を用意し、free-form prose/JSON vs typed DSL で contradiction rate、unsupported fact promotion、provenance retention、nested reasoning accuracy、token/latency を比較する。

### (7) 既存 daily survey ではなぜ拾いにくいか

内容は ToM だが primary category は programming languages / language-of-thought formalization。通常の social cognition / psychology survey では「mental-state model を DSL/compiler として設計する」という実装示唆が落ちやすい。

### (8) 重要度

**B**

**設計要約:** `representing what another agent may believe should not silently turn that belief into a world fact`。

## 5.6 B — Independent Transition Validation from Sintr

**Primary paper:**  
https://arxiv.org/abs/2608.27091  
**Fresh seminar:**  
https://www.cs.cornell.edu/events/systems-research-seminar/sintr-safe-interactive-transactions-presence-byzantine-clients

### (1) 何が実証済みか

Sintr は client-centric BFT systems において、serializable ordering があっても Byzantine client が不正な transaction output を提出できる integrity gap を対象とする。redundant execution + heterogeneous per-object integrity policy で既存 systems を harden し、評価では throughput 3–16%、latency 3–21% の overhead を報告する。2026-09-18 Cornell Systems Seminar でも発表された。

### (2) 何が提案・推測段階か

database transaction validity を AI self-modification / memory mutation へ直接一般化した研究ではない。LLM proposer failure が Byzantine adversary と同じ分布を持つわけでもない。

### (3) Kamimusuhiの関連 subsystem / design issue

Mutation Gate、Continuity Kernel、self-improvement、shared state、distributed cognition、high-impact memory/persona/policy update。

### (4) 借りられる設計・実装アイデア

高影響 mutation では proposal に完成済み post-state を提出させてそのまま commit するのではなく、kernel-owned deterministic transition または independent validator が proposal intent から post-state を再構成する。critical object だけ redundant execution / heterogeneous invariant checks を要求する。

### (5) Kamimusuhiとの差分

Kamimusuhi は proposal → validation/policy → activation を既に中心契約とする。追加差分は **「validator が proposal の主張を読む」だけでなく、transition computation 自体を trusted/independent path で再実行する**こと。したがって新原則ではなく validation depth の watchlist 候補。

### (6) 次に検証すべきこと

**`IndependentTransitionValidationBench-v0`**

proposer に、合法な predecessor/version を使いつつ hidden invariant を壊す post-state、計算ミスした derived field、権限外 object を混ぜた patch を生成させる。syntax/policy-only validator、single re-execution、heterogeneous dual validator を比較し、false accept、latency、compute overhead を測る。

### (7) 既存 daily survey ではなぜ拾いにくいか

BFT/database literature の「ordering safety と application execution validity は別」という区別は、AI agent survey では通常 fault tolerance / consensus の話に埋もれ、Mutation Gate の validator design へ接続されにくい。

### (8) 重要度

**B**

**設計要約:** `a well-ordered state transition can still be the wrong computation`。

## 10. 今回の結論

今回の最も重要な blind spot は、**continuity を「情報が残っていること」と同一視しないこと**である。

1. compaction 後に「何をしていたか」を説明できても、live task の handle / owner / verification state を失えば行為の continuity はない。
2. memory store が scope-aware でも、reflect/dream/consolidate のどこかが scope を落とせば epistemic/privacy boundary は閉じていない。
3. clone に state が揃っていても、credential / external principal / recovery ownership を個体化しなければ新 branch の identity は成立しない。
4. agent が idle でも、人間が同じ body/resource を握っているなら embodied continuity は生きている。

したがって次の設計焦点は **「summary の品質」より `continuation closure`、「memory tag」より `scope-propagation closure`、「backup/restore」より `branch individuation`、「idle timer」より `control lease`** に置く価値が高い。
