### 3.1 A — Application-Semantic Backup Attestation

Fresh evidence:
- OpenClaw #159228: https://github.com/openclaw/openclaw/issues/159228
- Hermes #124564: https://github.com/NousResearch/hermes-agent/issues/124564

1. **実証済み**  
   OpenClaw #159228 は `backup sqlite create --agent` が success / verification pass を返す一方、Gateway が実際に使う DB ではなく隣の空 DB path をsnapshotしたというfield report。報告上、backupは約670KB・56 tables・主要row 0件、live storeは50〜250MBで例として transcript events 21,515件。hash / SQLite integrity / owner verificationは通った。ただし issue は live repro 要確認ラベル付きなので独立再現済みとはしない。  
   Hermes #124564 は controlled reproduction。300,000-byte file をZIPへ書く途中120,000 bytes時点でsource read errorを注入すると、upstreamはarchiveを返し、そのmemberはtruncatedだがCRC-valid / archive-readableになった。

2. **提案・推測**  
   全backupでfull restore rehearsalを毎回行う必要があるとは限らない。重要なのは低層integrityを捨てることではなく、semantic correctnessの十分条件にしないこと。

3. **関係subsystem**  
   Continuity Kernel、Canonical Self History/Evidence、episodic/relationship/self memory、backup/restore/migration、software-body rollback、recovery evidence。

4. **借りる案**  
   `BackupAttestation` に `authoritative_source_id / source_generation / canonical_head / schema_version / snapshot_boundary / completeness / required_semantic_witnesses / restore_probe_result` を持つ。hash/CRC/integrityに加え、current authoritative storeとのbinding、required event classes、canonical head、partial salvage statusを検証。partial artifactはlast-known-good generationをpruneしない。

5. **Kamimusuhiとの差分**  
   Last-Surviving-Copyは最後の有効copyを消さない話、Corruption-Preserving Publicationは読めない状態をabsent扱いしない話。今回は **正常に読め、検証も通るartifactが、意味的にはwrong/incomplete** という別方向。

6. **次に検証**  
   **`SemanticBackupAttestationBench-v0` — P0**。wrong-but-valid DB、empty schema-compatible DB、mid-member failure、readable partial archive、WAL boundary、snapshot中generation change、memory store一部欠落を注入し、`COMPLETE` false positive=0、last-good preservation、sandbox restoreのsemantic witnessを確認。

7. **拾いにくい理由**  
   backup研究はarchive/crash consistency、agent memory研究はretrieval/persistenceへ寄る。「正しく保存したfileが、正しい個体状態なのか」は境界に落ちる。

8. **重要度**: **A**

**Invariant候補:** `container integrity != semantic backup correctness`

### 3.2 A update — Branch-Lineage Receipt Parity Across Entrypoints

Fresh evidence: Hermes #124540  
https://github.com/NousResearch/hermes-agent/issues/124540

1. **実証済み**  
   ACP `session/fork` はhistoryをdeep-copyし新UUIDを作るが `parent_session_id` も `_branched_from` も記録しない。一方CLI `/branch`、Gateway `/branch`、HTTP API forkはlineage markerを記録する。ACP forkは後からbranchと識別できず、sourceをrestore不能な場合にempty `sessionId` を返す経路も報告。

2. **提案・推測**  
   parentを必ずfork時に終了させるかはproduct semantics依存。exploratory branch / migration / true identity forkを同一lifecycleへ潰すべきではない。

3. **関係subsystem**  
   Continuity Kernel、split-brain/fork、ACP/A2A/API/UI adapter、workspace/session projection、canonical provenance。

4. **借りる案**  
   adapterごとにfork logicを持たず共通 `ContinuityFork` へ収束。`ForkReceipt {child_lineage_id,parent_lineage_id,fork_point,parent_generation,operation_kind,authority_receipt,source_surface}` を全成功pathで発行。

5. **差分**  
   Kamimusuhiはfork semantics自体を既に強く持つ。fresh差分は **規範が正しくても一protocol adapterだけreceiptを書かないとidentity graphが欠落する**というconformance failure。

6. **次に検証**  
   **`BranchLineageEntrypointParityBench-v0` — P0**。CLI/REST/ACP/A2A/local UI/remote UI、source active/closed/missing、retry/duplicate requestをcross-product化し、全成功pathで同型receipt、source解決不能はtyped errorを要求。

7. **拾いにくい理由**  
   identity surveyはfork理論、adapter差はAPI実装として別扱いされる。だがlineage metadataのないbranchは後から正しく隔離・継続判断できない。

8. **重要度**: **A update**

**更新原則:** `branch semantics SHALL be invariant across interaction protocols`

### 3.3 A update — Failure-Domain-Scoped Circuit Breaker + Upgrade Cohort Gate

Fresh evidence: OpenClaw #159342  
https://github.com/openclaw/openclaw/issues/159342

Classical reference: Microsoft Azure Bulkhead pattern  
https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead

1. **実証済み**  
   operational reportではcore upgrade後、一つのWhatsApp pluginが新SDKと互換でなくboot crash。5分内3回unclean bootでgateway-wide crash-loop breakerが発火し、そのpluginだけでなく全channel autostartが抑制されSlack等も停止。update側はconfigured pluginにtarget releaseがなくてもwarningでcore updateを続けるため、次bootのincompatible cohortを作れると報告。issueはmaintainer/product review中で独立再現済みとは扱わない。

2. **提案・推測**  
   pluginを常にquarantineして残りを起動すればよいわけではない。continuity-critical organやsafety gateは全体fail-closedが正しい場合がある。必要なのは **failure domain + criticalityでbreaker scopeを決めること**。

3. **関係subsystem**  
   Organ Supervisor、K-Edge/modal adapters、plugin runtime、self-update/software-body lineage、graceful degradation、standing duties、Cognitive Resource Registry。

4. **借りる案**  
   organ/pluginに `failure_domain / criticality / compatibility_range / required_by / breaker_scope / degraded_mode` を持たせる。update preflightで target core + enabled organ cohort のcompatibility closureを取り、optional incompatibilityならexplicit degraded plan、critical incompatibilityならupdate block。

5. **差分**  
   Extension Termination-Class Containmentはcallbackのhost termination、NFR-005はgraceful degradation、既存failure-domain findingはcorrelated dependencies。今回は **breaker scopeとupgrade compatibility preflightが共通domain modelを持たないと局所故障をsystemic outageへ増幅する**差分。

6. **次に検証**  
   **`FailureDomainCircuitBreakerBench-v0` — P0/P1**。optional organ crash×3、critical store adapter failure、target plugin missing、shared dependency crash、restart stormを注入。unaffected surface availability、blast radius、unsafe degraded rate、preflight false allow/blockを測る。

7. **拾いにくい理由**  
   package management、SRE breaker、graceful degradationが別分野に分かれる。長寿命個体ではsoftware-bodyの局所損傷を全身停止へ変えるhomeostatic問題。

8. **重要度**: **A update**

**更新原則:** `component failure SHALL NOT expand beyond its declared failure domain without an explicit criticality rule`

### 3.4 B — Migration Sanitizer Non-Interference

Fresh evidence: Hermes #124523  
https://github.com/NousResearch/hermes-agent/issues/124523

1. **実証済み**  
   field reportでは `profile export` がarchive内file contentへsecret redactionを適用し、literal secretだけでなく `$TOKEN`、env placeholder、code、prose、skill referencesまで書換えた。archiveはimportできるがscript 401、syntax error、MCP header破損、bundled skill hash不一致が起きたと報告。8 profiles / 約430 files / 1,500 lines規模との報告だが、issueは `needs-repro` なので独立確認済みとはしない。

2. **提案・推測**  
   export時redactionを全面禁止すべきとは限らない。literal secretsをportable packageに含めない要件は正当。問題はsecret exclusion/substitutionとarbitrary text rewritingの混同。

3. **関係subsystem**  
   migration/backup/restore、software-body portability、skill/tool code、credential refs、privacy-preserving export、reproducibility/artifact hash。

4. **借りる案**  
   artifact-type-aware transformationにする。`ExportItem {artifact_type,sensitivity_class,transformation,semantic_hash_before,semantic_validation_after,transform_receipt}`。secret本体はomit/reference-only、env referencesは保持、code/skillはsemantic-preserving copyを基本にし、変更file/fieldを列挙。

5. **差分**  
   secret-taint egressは漏洩防止、trajectory redaction compatibilityは公開trace中心。今回は **privacy transformがidentity-bearing software bodyを壊す migration non-interference**。

6. **次に検証**  
   **`MigrationSanitizerNonInterferenceBench-v0` — P1**。code、skill manifest、prompt/rule、config env ref、relationship/self memory、literal secret field、binaryをexport→importし、syntax/reference resolution/origin hash/canonical digest/secret non-disclosureを同時検証。

7. **拾いにくい理由**  
   privacyは「何をredact」、migrationは「何をcopy」と分かれる。ここではredaction operator自体がstate mutation。

8. **重要度**: **B**

**原則候補:** `privacy transformation SHALL NOT silently mutate unrelated semantics`

### 3.5 B update — Projection-Repair Source-Coverage Preservation

Fresh evidence: Hermes #124731  
https://github.com/NousResearch/hermes-agent/issues/124731

1. **実証済み**  
   crash/restart後にunanswered user row Rが残り、新user message Uが来るとalternation repairが R+U を一つのmerged live rowへする。その後current-turn indexがmerged rowへre-anchorされ、finalize時persist overrideがmerged row全体をUだけで置換し、Rをlive message listから落とす経路が報告。Gateway reload後にはpersistent rowsから再mergeされ得るため、turn中にpluginが見たrowとfinalize後live rowが食い違う。

2. **提案・推測**  
   merged prefixを保存してoverride appendするか、overrideをmerged rowへre-anchorしないかは実装依存。

3. **関係subsystem**  
   canonical transcript/evidence、history normalization、DialogueSession、crash recovery、context-engine plugins、projection→writeback authority。

4. **借りる案**  
   複数source eventを一rendered rowへ融合する場合 `ProjectionCoverage {rendered_id,source_event_ids,transform_kind,writable_extent}` を保持。current-turn overrideはこのturnが追加したextentだけ変更可能にする。

5. **差分**  
   2026-09-19 surveyではfailed unanswered turn後のmergeがundo/retryをwedgeする事例をProjectionMapの必要性としてwatch済み。今回のfresh差分は **writebackでsource contentが実際に消えるmechanism** まで進んだこと。lossy-projection non-writebackの具体fixture更新。

6. **次に検証**  
   **`ProjectionRepairCoverageBench-v1` — P1**。unanswered R+new U、tool/user repair、compaction carrier、multimodal row、crash/reloadを跨ぎ、source coverage conservation、current-turn writable extent、old-content loss=0を確認。

7. **拾いにくい理由**  
   conversation repair、DB persistence、plugin contextが別レイヤー。表示compatibilityのためmergeしたrowをmutation targetにしてよいかが層間に落ちる。

8. **重要度**: **B update**

### End-to-End Arguments in System Design

Saltzer, Reed, Clark, 1984  
https://web.mit.edu/saltzer/www/publications/endtoend/endtoend.pdf

低層のerror detection/recoveryだけではapplicationの最終correctnessを完全には保証できず、endpoint/application-level checkが必要という古典的systems principle。今回のbackup findingには、

```text
CRC/hash/SQLite integrity
  = storage/container evidence

authoritative source identity
+ semantic completeness
+ lineage/generation binding
+ restore witness
  = continuity-grade backup evidence
```

という分離を与える。Kamimusuhi固有の正しさをこの古典が証明するわけではない。

### Bulkhead / fault containment

Microsoft Azure Architecture Center  
https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead

一つのservice/resource poolのfailureを他領域へ波及させないfault-isolation pattern。Kamimusuhiでは単なるmicroservice分割ではなく、`failure_domain + criticality + degraded_mode` をOrgan Supervisor / update gateの共通語彙にする候補。

## 11. 結論

最重要は backup を **「読めるartifactを作ったか」から「continuity-bearing stateを意味的に復元できるartifactを作ったか」へ格上げすること**。

```text
physical/container validity
+ authoritative-source binding
+ semantic completeness
+ lineage/generation binding
+ restore witness
= continuity-grade backup
```

次点は、branch/fork lineage receiptを全adapterで同一contractへ閉じることと、optional cognitive organのfailureをwhole-individual outageへ増幅しないfailure-domain model。

Kamimusuhiは既に canonical evidence / lineage / graceful degradation を持つため、今回のfindingは大きな新subsystem追加ではなく、backup・fork・update・export・history repairという周辺実装にも既存continuity disciplineを最後まで通す補強になる。
