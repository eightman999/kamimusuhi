# 5. 候補ごとの評価

## 5.1 A+ — State-Transfer Closure: portable stateをfilesystem recursive copyで定義しない

**一次資料:** Hermes #114440

### (1) 何が実証済みか

PRが扱うincidentでは、remote home tree内のlive Unix socket `~/.hermes/gateway.sock` をGNU tarがarchiveできず `socket ignored` + non-zero exitとなり、sync-backが失敗した。失敗時の3回retryはfull treeを再downloadし、hard kill時にはprocess内`finally` cleanupが走らずmulti-GB temp archiveが残り得た。issue reporter環境では2時間で約45GBのtemp tar残留が報告されている。PRはsocketをarchive対象から除外し、stale-temp sweepを6h→30minへ短縮し、2GiB capをoverride可能にする。focused testsは38 pass + 1 skipと報告。

### (2) 何が提案・推測段階か

Kamimusuhiのstate treeに同じsocket/tar failureがある証拠ではない。また`*.sock`除外が一般的なmigration state分類の解答というわけではない。socket以外にもlock、FIFO、device node、temporary cache、open DB WAL、model cache、credential materialなど別classがある。

### (3) 関係するサブシステム/設計課題

- Continuity Kernel migration / checkpoint
- multi-device embodiment
- backup / restore / death-rebirth
- K-Edge/K-Core state handoff
- canonical evidence / derived indexes / runtime attachments

### (4) 借りられる設計・実装アイデア

recursive directory archiveではなく **`StateTransferManifest`** を作る。

```text
artifact -> durability_class
  CANONICAL_DURABLE
  DERIVED_REBUILDABLE
  RUNTIME_EPHEMERAL
  SECRET_NONTRANSFERABLE
  EXTERNAL_REFERENCE

+ type / size / digest / owner / generation
+ transfer method
+ restore validator
+ cleanup lease for staging artifacts
```

socket / lock / PID / tmp archiveは原則`RUNTIME_EPHEMERAL`。大容量cacheは`DERIVED_REBUILDABLE`として必要時のみ転送。kill-safe cleanupはin-process `finally`だけでなく、lease/age based external sweeperも持つ。

### (5) Kamimusuhiとの差分

既存のmigration/recovery findingは「どのcontinuationを再開するか」「attachmentを新incarnationへbindしたか」を強く扱う。一方、**migration payloadの集合そのものをfilesystem namespaceから直接推定しない**というstate-closure contractは未収載だった。

### (6) 次に検証すべきこと

**`StateTransferClosureBench-v0`**

- fixture treeへUnix socket / FIFO / lock / stale PID / SQLite WAL / 5GB rebuildable cache / secret / canonical logを混在
- manifestなしrecursive copyとmanifest-driven transferを比較
- mid-transfer SIGKILL / network disconnect / destination ENOSPCを注入
- canonical state loss、ephemeral artifact resurrection、temp leak、restore latencyを測る
- restore後にruntime artifactが**再生成**され、転送由来で復活しないことを確認

### (7) 既存dailyではなぜ拾いにくいか

AI memory / agent recoveryではなく、Unix filesystem特殊file・tar exit semantics・temp resource lifecycleというbackup/OS運用の境界に出るため。

### (8) 重要度

**A+** — identity migration / backupが「正常完了したつもりで一部stateだけ欠落・runtime artifactだけ復活」する事故を防ぐ基盤契約になる。

## 5.3 A — Concurrency Evidence Lifecycle: owner/writer metadataもleaseを持つ

**一次資料:** Hermes #114448

### (1) 何が実証済みか

`forget_task()`がread stampは解放しても`_last_writer`を残したため、既に終了したtaskがconcurrent siblingとして報告され続けた。修正はそのtaskが所有するwriter entryを終了時に消し、さらに1時間より古いentryをread時にevictする。exact reproはforget直後・TTL expiry後ともquietになり、registry suite 12 greenと報告。

### (2) 何が提案・推測段階か

Kamimusuhiのcanonical writer registryに同じleakがある証拠ではない。またTTL 1hはHermes固有heuristicであり、continuity authorityの一般値として借りるべきではない。

### (3) 関係するサブシステム/設計課題

- Continuity Kernel predecessor/conflict checks
- mutation gate
- background worker ownership
- distributed body writer fencing
- observability / false conflict alarms

### (4) 借りられる設計・実装アイデア

concurrency evidenceを永久metadataにしない。

```text
WriterClaim(
  actor_id,
  generation,
  resource,
  acquired_at,
  lease_until,
  release_receipt,
  observed_liveness
)
```

`historical last writer`と`currently holds write authority`を別fieldにする。cleanup failure時でもgeneration/fencing tokenとlease expiryでlive authorityへ昇格しない。

### (5) Kamimusuhiとの差分

既存のcapability freshness / observer lease / probe-debt livenessに近いが、今回は**競合検知のevidence自体のlifecycle**が対象。stale metadataが安全側のfalse blockを作り、長寿命系では永続的な「ghost writer」になり得る。

### (6) 次に検証すべきこと

**`ConcurrencyEvidenceLeaseBench-v0`**

- writer acquire後にnormal finish / crash / kill -9 / network partition / worker replacementを注入
- stale writer claimが新generationを永久blockしないこと
- 同時にlive split-brain writerはTTLだけで勝手に消えないこと
- historical provenanceは残しつつlive authority indexから外れること

### (7) 既存dailyではなぜ拾いにくいか

distributed identity研究は「本物の並行writer」を重視する一方、**競合検出器が作る幽霊writer**はlock registry / concurrency bookkeepingの実装細部に見えるため。

### (8) 重要度

**A** — conservative kernelがstale evidenceで永続停止するのを避けつつ、actual split brain検知を弱めないための契約。

## 5.6 B+ — Telemetry Policy Epoch: 「観測条件が変わった」ことをtraceに残す

**一次資料 / 公式提案:** OpenTelemetry OTEP Telemetry Policies  
**補助実装記事:** Elastic Observability Labs, 2026-09-17

### (1) 何が実証済みか

OpenTelemetry specification repositoryのOTEPは、typed・implementation-agnostic・standalone・dynamicな`Telemetry Policy`を提案している。policy providerとapplier間はasynchronous updateを許し、out-of-date policyをsystem failureにしないことを志向する。Elasticは2026-09-17に、Java SDK/agentでsampling等をruntime変更するexperimental implementationを紹介した。

### (2) 何が提案・推測段階か

OTEPは確定標準ではなくschemaも変更可能。Kamimusuhiでdynamic telemetry policyが必要か、どのpolicyをlocal/central ownerが持つべきかは未決定。runtime sampling変更が認知品質を直接改善することも示されていない。

### (3) 関係するサブシステム/設計課題

- long-lived observability / telemetry
- evaluator / experiment reproducibility
- privacy-aware tracing
- resource pressure / degraded mode
- distributed K-Edge/K-Core monitoring

### (4) 借りられる設計・実装アイデア

既存OpenTelemetry trace projectionへ `telemetry_policy_epoch` を追加する候補。

```text
TelemetryPolicyReceipt:
  policy_id
  revision/epoch
  effective_from
  target_signal
  sampling/filter summary
  issuer / authority
  previous_epoch
```

重要なのは、policy change eventを**そのpolicy自身でdropできない別のmeta-audit channel**へ残すこと。長期metric比較時はepoch跨ぎを明示する。

### (5) Kamimusuhiとの差分

2026-09-10のOpenTelemetry findingはsemantic conventions/trace exportが中心。本件は**何を観測するか自体がruntimeで変更可能なcontrol state**になった時のlineageと比較可能性という差分。

### (6) 次に検証すべきこと

**`TelemetryPolicyEpochBench-v0`**

- 100%→1% sampling、secret-attribute filter、trace-disableをruntime変更
- policy change前後のself/ops metricsにepochが付くこと
- policy propagation lag中のmixed-node状態を識別できること
- policy change audit eventだけはsamplingで消えないこと
- observability overhead削減とdiagnostic recallのtrade-offを測る

### (7) 既存dailyではなぜ拾いにくいか

observabilityは通常「agentをどう見るか」で扱われるが、**観測器の設定自体もdistributed mutable stateである**というcontrol-plane問題はOpenTelemetry標準化/運用基盤側に出る。

### (8) 重要度

**B+** — 既存OpenTelemetry採用候補への実質的な新delta。標準化進展をwatchし、確定前にspecへ固定しない。
