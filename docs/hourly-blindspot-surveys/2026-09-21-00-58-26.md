## 1. 今回狙った盲点

1. **Intentional ownership transfer / cross-device handover**  
   「同一sessionはsingle writer」という安全条件を崩さず、同じ人が別deviceへ明示的に継続を引き渡すには何が必要か。`rebind`、`takeover`、`fork`、`concurrent writer`を混同しない。

2. **Pre-start cancellation / lifecycle-phase cleanup ownership**  
   task/workerが開始後なら`finally`でcleanupできるが、queue上でcancelされて一度もworker codeへ入らない場合、そのcleanupは誰の責務か。

3. **Failure-atomic destructive lifecycle**  
   uninstall / checkpoint clear / replacement / rollbackのように複数artifactを削除する操作が途中でI/O failureを起こしたとき、`active`でも`removed`でもないghost stateを残さないか。

4. **Public social activity signals**  
   typing / speaking / listening / thinking等の表示が、内部taskのlivenessではなく利用者が観測できるinteraction milestoneと整合しているか。

5. **Extension termination channels**  
   plugin callbackの通常例外を隔離していても、`SystemExit`等のprocess-control系exceptionが境界を飛び越え、host全体のdispatchを停止できないか。

固定リスト外では、structured concurrency、conversation chronemics / read-receipt HCI、destructive lifecycle repairability、termination-class exception taxonomyを追加探索した。

### 4.1 A — Atomic Continuity Lease Transfer：cross-device継続は「lock解除」ではなくsingle-writer handoverにする

**Primary fresh evidence:** Hermes PR #117321  
https://github.com/NousResearch/hermes-agent/pull/117321

#### (1) 何が実証済みか

Hermesではstored sessionに最大1つのlive ownerを持たせているため、desktopが保持中のchatを**同じ利用者のphone**から継続しようとしても拒否される。PRは`allow_session_takeover`をdefault falseで追加し、有効時のみ第二surfaceが既存leaseを**置換**する。atomic lock+prune block内でownership replacementを行い、takeover後もleaseはexactly oneのまま。registry不明時はfail closed、capacity limitは別契約として維持する。PR記載では新規7 casesを含む44 tests pass。

#### (2) 何が提案・推測段階か

PRはsurvey時点open。Hermesのsession UI/runtime向けで、複数deviceが同一Kamimusuhi individualのbody/sensor/actuatorを持つ状況、network partition、late writes、本人認証とsurface trustの分離までは未検証。

#### (3) Kamimusuhiのどこに関係するか

Continuity Kernel、multi-device embodiment、session/workspace owner、voice/chat surface、K-Edge↔K-Core routing、relationship episode continuity、distributed action authority。

#### (4) 借りられる設計・実装アイデア

`ContinuityLeaseHandover`をfirst-class operationにする。

```text
session_or_episode_id
from_lease_id / from_surface
new_surface / new_runtime
principal_id
old_generation -> new_generation
handover_nonce
capability_digest
reason / operator_intent
authorized_at
```

handoverはCAS/atomic commitで**旧leaseをrevokeし新leaseをactivateする一操作**とし、旧surfaceから到着するlate mutation/actionはold generationでfenceする。`TAKEOVER`、`RECONNECT`、`FORK`、`READ_ONLY_MIRROR`を別operation typeにする。client UIにはeffective takeover capabilityをadvertiseし、serverのpolicyとUI affordanceがずれないようにする。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `DurableDelegationOwnerRebind`はephemeral session ID rotation後もtask ownerを追う話。
- `AsyncRecoveryOwnerBinding`はawait後のlate recoveryが別foregroundを奪わない話。
- `ControlLeaseQualifiedResourceLifetime`はhuman/agent control中のbodyをGCしない話。

今回は逆方向で、**本人の明示intentによってlive ownerを正当に別surfaceへ移す**ための契約。continuityのためにlockを消すのではなく、lock ownershipを原子的に移す。

#### (6) 次に検証すべきこと

**`AtomicContinuityLeaseTransferBench-v0`**

- Desktop Aがlease保持 → Phone Bがtakeover → Aのlate writeは拒否、Bのみcommit可能。
- A/B/Cが同時takeoverを試みても最終live ownerは1。
- registry unreadable / network partition時に「ownerなし」と推測しない。
- same principal / different principal / shared accountを区別。
- takeover直前のin-flight tool/actionを誰が所有するかを明示。
- read-only mirrorはwriter leaseを奪わない。
- takeover capabilityがserver/client双方で一致する。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

multi-device continuityは通常「同期」「reconnect」「distributed identity」として検索され、**安全なsingle-writer性を保ったまま意図的にownerを移すhandover protocol**はUI/session coordinationの小機能に見えやすい。identity continuityとconcurrency controlの境界にある。

#### (8) 重要度

**A**

**Invariant候補:** `cross-device continuity != concurrent write authority`。  
**Contract候補:** `intentional handover SHALL atomically revoke the old writer lease before activating the new writer lease`。

### 4.2 A — Lifecycle-Phase Cleanup Ownership：開始前cancelではworkerの`finally`を期待しない

**Primary fresh evidence:** Hermes PR #117320  
https://github.com/NousResearch/hermes-agent/pull/117320

**Backfill:** Python asyncio cancellation / structured concurrency  
https://docs.python.org/3/library/asyncio-task.html  
https://peps.python.org/pep-0789/

#### (1) 何が実証済みか

Hermesではparent interruptがqueued delegate futureをworker開始前にcancelすると、prebuilt child objectは既にparentへattach済みなのに、workerは一度もchild-run cleanup pathへ入らず、childがattached/unclosedのまま残る。修正は`future.cancel()`が成功した場合だけdispatcher側がdetach+closeし、既にrunningなfutureは従来通りworker側cleanupへ委ねる。PR記載ではfocused 3 tests、adjacent 18 tests pass。Python公式docsも、TaskGroup shutdownがtask開始前ならcoroutine body自体が一度も実行されないケースを明示する。

#### (2) 何が提案・推測段階か

PRはdraft。Kamimusuhiでdelegate childがどのresourceをpreallocateするかは未定で、GPU reservation、memory transaction、tool capability、remote worker slot等へ同じfailureがどう写るかは要実験。

#### (3) 関係サブシステム

K-Deep delegation、Background Cognition、tool/model orchestration、parallel research workers、cancellation closure、resource budgeting、subagent observability。

#### (4) 借りられる設計・実装アイデア

task lifecycleを最低限以下に分け、cleanup responsibilityをphaseで決める。

```text
ALLOCATED -> QUEUED -> STARTING -> RUNNING -> TERMINAL
     |          |          |          |
 parent       parent     handoff     worker
 owns         owns       point       owns
 cleanup      cleanup                cleanup
```

child resourceのownership transferを「futureを作った時」ではなく、**workerがstart/acceptした証拠**にbindする。pre-start cancel成功ならcreator/dispatcherがcleanup、runningへ遷移済みならworkerがcleanupする。二重cleanupを避けるため`CleanupOwnerToken`またはidempotent close receiptを持つ。

#### (5) Kamimusuhiとの差分

既存`Cancellation Closure over Effectors`は開始済みeffectやsubtaskへcancelを閉包させる発想。今回は**effect/subtaskが開始されなかったため、その主体自身がcleanupできない**。つまり cancellation propagation ではなく lifecycle-phase dependent ownership の問題。

#### (6) 次に検証すべきこと

**`LifecyclePhaseCleanupOwnershipBench-v0`**

- child allocate直後 / queue中 / start race / running後の各phaseでparent cancel。
- `cancel()==true`ならparent cleanup、`false`ならworker cleanup、というownershipが二重化/空白化しない。
- parent crash直前、worker accept直後のhandoff crash windowをfault injection。
- GPU slot、DB transaction、remote session、capability lease、temporary memory branchでresource leak 0を検査。

#### (7) 既存デイリーではなぜ拾いにくいか

通常は「cancelが届くか」「taskが止まるか」を見るため、**cancel対象のcoroutineが一度も始まっていない**ケースは見落とされやすい。これはagent研究よりruntime / structured-concurrency implementationに埋もれる。

#### (8) 重要度

**A**

**Invariant候補:** `resource allocated for a task != cleanup responsibility has transferred to that task`。

### 4.3 A — Failure-Atomic Lifecycle Teardown：削除途中failureをghost stateにしない

**Primary fresh evidence:** Hermes PR #117318  
https://github.com/NousResearch/hermes-agent/pull/117318

#### (1) 何が実証済みか

WindowsのGit objectやPOSIX package treeにはread-only file/parent directoryがあり、bare `shutil.rmtree`が途中のunlink failureで停止し得る。Hermesではこれにより:

- checkpoint clearがstoreを**半分だけ削除**して失敗、
- MCP uninstallがconfigを先に消した後clone削除で止まり、**unmanaged cloneが残って再installも阻害**、
- plugin rollback/removal/staging cleanupもpartial stateを残し得る、

という複数lifecycle pathが影響していた。PRはPermissionErrorに限定してwrite bit/parentを修復してretryするshared removerを導入し、他errorは従来通りpropagateする。Windows上で再現されたcheckpoint testが修正後passしたと報告。

#### (2) 何が提案・推測段階か

この修正は特定のpermission failureを減らすもので、電源断、disk full、remote object deletion、partial credential revoke等に対してlifecycle操作全体をtransactionalにするものではない。Kamimusuhiのcanonical storageやdistributed body unregisterに一般化する部分は提案段階。

#### (3) 関係サブシステム

Continuity Kernel、migration/restore、plugin/skill lifecycle、body registration、checkpoint/archive、graceful forgetting、model/cache replacement、maintenance worker。

#### (4) 借りられる設計・実装アイデア

非transactional resourceに対するdestructive lifecycleを、単一`delete()`ではなくrepairable protocolにする。

```text
ACTIVE
  -> TEARDOWN_INTENT (durable receipt)
  -> external/artifact cleanup steps
  -> verify postconditions
  -> FINALIZED_REMOVED

途中失敗
  -> TEARDOWN_INCOMPLETE
  -> exact remaining artifacts + retry/rollback plan
```

registry/configを先に消す場合は、artifactを孤児化しないdurable tombstone/referenceを残す。逆にartifactを先に消す場合は、canonical pointerがdead targetをactive扱いしない。各stepをidempotentにし、`TeardownReceipt`へ対象、attempt、remaining set、error class、authorityを記録する。

#### (5) Kamimusuhiとの差分

- `Explicit Destructive Scope`は「何を消してよいか」。
- `RetentionPolicyDomainSafety`は「削除selectionを壊れたpolicyが最大化しないか」。
- `Provenance-Preserving Rollback`はmutation rollbackの由来保持。

今回は **正しい対象を正しく削除し始めても、non-transactional I/Oが途中で失敗した後のpost-stateをどう閉じるか**。delete authorityではなくdestructive operationのfailure atomicity / repairabilityである。

#### (6) 次に検証すべきこと

**`FailureAtomicLifecycleTeardownBench-v0`**

- N個のartifact削除で1..N番目すべてにfault injection。
- crash / permission / disk-full / remote timeout / partial revokeを注入。
- failure後は`ACTIVE`に戻せるか、`TEARDOWN_INCOMPLETE`として機械的に残作業を列挙できること。
- configだけ消えたghost、artifactだけ残ったunmanaged resource、silent partial checkpointを禁止。
- retry N回で収束し、二重削除が新しいside effectを作らないこと。

#### (7) 既存デイリーではなぜ拾いにくいか

「Windows read-only fileが消せない」というplatform bugに見え、agent identityやmemory研究の検索語からは出ない。しかし長寿命agentではuninstall、checkpoint rotation、migration cleanup、forgettingが必ず積み重なるため、**partial teardownは時間とともにidentity/state ambiguityを増やす**。

#### (8) 重要度

**A**

**Invariant候補:** `destructive lifecycle failure SHALL NOT silently erase the information needed to determine or repair the remaining state`。

### 4.5 B — Extension Termination-Class Containment：plugin isolationは`Exception`だけでは閉じない

**Primary fresh evidence:** Hermes PR #117315  
https://github.com/NousResearch/hermes-agent/pull/117315

#### (1) 何が実証済みか

caller-thread plugin hookが`Exception`だけをcatchしていたため、dependency/callbackが`sys.exit()`を呼ぶと`SystemExit`がdispatchを終了させ、後続callbackもskipした。timeout-bounded workerではprocess exit自体は避けられてもfailure reportingが失われた。修正は`SystemExit`をper-callback failureとして隔離・reportしつつ、operatorの`KeyboardInterrupt`はpropagateする。PR記載では85 tests pass。

Python公式docsでも`CancelledError`が`BaseException`直系であることが明示されており、「`except Exception`でextension boundaryを閉じた」と考えるのは一般に危険である。

#### (2) 何が提案・推測段階か

in-processで捕捉すべきtermination classは言語/runtime依存。OOM、segfault、native extension crash、process killはPython exception policyだけではcontainできない。Kamimusuhiでpluginをどこまでout-of-process化するかは別設計課題。

#### (3) 関係サブシステム

Plugin/Skill runtime、extension security、K-Edge adapters、sensor/tool drivers、Global Workspace hooks、observability、supervision tree。

#### (4) 借りられる設計・実装アイデア

extension callback failureを少なくとも:

```text
NORMAL_FAILURE
TERMINATION_REQUEST (e.g. SystemExit)
CANCELLATION
OPERATOR_INTERRUPT
PROCESS_CRASH
RESOURCE_EXHAUSTION
```

へ分け、host policyがどれをcontain / propagate / restartするか明示する。第三者extensionは可能ならprocess boundary + supervisorへ移し、in-process hookはtermination capabilityを持たない前提にする。

#### (5) Kamimusuhiとの差分

直前の`PortablePluginTrustProjection`は「portable package conformance ≠ trust/authority」。今回は**既にロードしたextensionがhost control-flowを終了させるtermination channel**の隔離で、capability permissionとは別のblast-radius問題。

#### (6) 次に検証すべきこと

**`ExtensionTerminationContainmentBench-v0`**

- callbackが`SystemExit` / normal exception / cancellation / `KeyboardInterrupt`を発生。
-後続callback継続、failure receipt、operator interrupt伝播を期待値別に検査。
- subprocess pluginではexit code / signal / OOMをsupervisorがextension failureへ変換し、Continuity Kernelや他surfaceを落とさないこと。

#### (7) 既存デイリーではなぜ拾いにくいか

plugin securityはpermission、sandbox、secret accessへ寄りがちで、**language runtimeのexception hierarchyそのものがauthority channelになる**点はimplementation detailとして埋もれやすい。

#### (8) 重要度

**B**

**Invariant候補:** `extension callback failure SHALL NOT acquire process-termination authority merely by choosing a different exception class`。

## 10. 今回の結論

今回のblind spotは「ownership / cleanup / presence」を**開始時だけでなく移行点で定義する**ことに集約できる。

Kamimusuhiの長寿命・分散個体では、ownerを固定し続けるだけではmulti-device continuityにならない。一方で自由にownerを切り替えるとsingle-writer性が壊れるため、**handover自体をatomic continuity operation**にする必要がある。同様に、taskをcancel可能にするだけでは足りず、workerが一度も起動しないphaseではcreatorがresourceを回収しなければならない。削除も「呼んだ/失敗した」の二値ではなく、途中failureから残存状態を機械的に再構築できなければならない。

そしてsocial agentでは、typingやspeakingのような表示も単なるUIではない。相手が「今この個体は何をしている」と推測する材料であり、内部transportのstallをそのまま社会的signalとして漏らさない契約が必要になる。
