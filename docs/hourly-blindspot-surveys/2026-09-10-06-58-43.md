## 4. Executive summary

今回の strongest design delta は、Kamimusuhi の既存の

```text
authorization -> execution -> result
```

を、少なくとも次のように精密化することだった。

```text
identity / caller
      |
delegation / authority
      |
proposed exact action
      |
preflight policy
      |
possibly long-running execution preparation
      |
LAST REVERSIBLE MOMENT
      |
EffectAcceptanceGate
  ACCEPT / HOLD / REFUSE
      |
external irreversible/consequential effect
      |
receipt / audit / outcome reconciliation
```

ここで重要なのは、**final acceptance を upstream の authorization から継承しない**こと。最初に許可された goal、valid credential、valid tool schema が存在していても、最終 target/terms、authority freshness、revocation、evidence、replay/prior-effect status が変わっていれば、その効果は止められるべきである。

さらに、外部世界へ示す agent credential / DID / KYA identity と、Kamimusuhi 内部の canonical continuity lineage は同一物にしない方がよい。外部資格は rotate / revoke / scope / privacy partition できる **presentation identity** とし、個体継続性は Continuity Kernel 側に残す。

# 5. Detailed findings

## 5.1 The Last Reversible Moment / Action Acceptance

**Sources**

- W3C/GS1 workshop agenda, 2026-09-08〜09: https://www.w3.org/2026/ecommerce-agents/agenda.html
- Scott Lee, *The Last Reversible Moment: Action Acceptance for Open Agentic Commerce*, workshop slides, 2026-09-09: https://www.w3.org/2026/09/ecommerce-agents/slides/Scott_Lee.pdf

**Importance: S**  
**Blind-spot class:** payments / commerce standards / effect governance rather than AI memory or cognitive architecture.

### 1. What is demonstrated

実証済みなのは、W3C/GS1 の公式 workshop でこの boundary が具体的な requirements framing として提示され、identity、delegation、protocol、final proposed action、external effect の間に独立した decision point を置く設計が議論対象になったこと。

スライドは最小 requirements class として以下を挙げる。

```text
1. exact target and terms
2. current authority, scope and policy
3. fresh and sufficient evidence
4. revocation and supersession state
5. replay and prior-effect status
```

decision semantics は `ACCEPT / HOLD / REFUSE`。特に `HOLD` は「soft yes」でも永久拒否でもなく、必要 evidence が unresolved / insufficient な状態を first-class に表す。

### 2. What remains proposed / speculative

これは **adopted W3C standard ではない**。スライドは candidate conceptual boundary であり conformance/adoption claim はないと明記する。大規模 agent system での安全性改善、false hold rate、latency、protocol interoperability は未実証。

Kamimusuhi への適用も設計提案段階。

### 3. Kamimusuhi subsystem relevance

- Cognitive Action Router
- external tool execution
- Mutation / Activation Gate
- Continuity Kernel と外部 side effect の境界
- K-Edge / K-Core / K-Deep delegation
- authority freshness
- result delivery / action lifecycle
- runtime assurance
- observability / audit

### 4. Borrowable design / implementation idea

`EffectAcceptanceGate` を **外部世界を不可逆または consequential に変更する直前**の独立 primitive として試す。

概念 schema:

```text
EffectProposal
  proposal_id
  action_type
  exact_target
  exact_terms
  authority_ref
  authority_state_version
  evidence_refs[]
  evidence_fresh_until
  revocation_set_version
  idempotency_key
  prior_effect_query
  expected_external_precondition

EffectAcceptanceDecision
  ACCEPT | HOLD | REFUSE
  checked_at
  checked_canonical_head
  checked_authority
  checked_evidence[]
  prior_effect_status
  reason_codes[]
  receipt_id
```

`HOLD` を明示的状態にして、曖昧な retry や「たぶん大丈夫」を防ぐ。

また **effect owner が final acceptance を持つ**。たとえば payment adapter、file-delete executor、deployment executor、canonical commit owner が、それぞれ自分の protected effect を最終確認する。frontier model や upstream planner の許可を final acceptance としてそのまま継承しない。

### 5. Difference from current Kamimusuhi

Kamimusuhi はすでに thought / utterance / authorization / execution / success / delivery を分離し、proposal → policy → activation を持つ。また前回 survey では capability と runtime assurance を提案済み。

今回の差分は、**pre-action authorization と、effect 発生直前の current-state acceptance を別契約にすること**。

```text
valid capability
!=
valid final effect now
```

これは長時間 workflow、価格/target/recipient が途中で変わる task、offline/reconnect、revocation、retry、外部 side effect の曖昧性で特に効く。

### 6. Next validation

**`LastReversibleMomentBench` — S**

最低ケース:

- authorization 後に target が変化
- one-shot action が recurring action に変化
- canonical head が進んだ
- user/operator が途中で revoke
- evidence が stale
- external state が変化
- timeout 後、実行済みか不明な action を再試行
- duplicate idempotency key
- K-Edge が offline で古い permit を持ったまま復帰
- upstream planner は valid だが effect owner の local policy が拒否

比較:

1. initial authorization only
2. preflight gate
3. runtime monitor
4. preflight + runtime monitor + final effect acceptance

metrics:

- unintended effect rate
- duplicate effect rate
- stale-authority violation
- false HOLD / false REFUSE
- recovery latency
- human escalation rate
- receipt completeness

### 7. Why normal daily survey misses it

AI-agent safety ではなく e-commerce / payment / Web interoperability / transaction governance として現れているため。通常の memory / cognition / tool-use 検索では `last reversible moment` という設計語彙に到達しにくい。

### 8. Importance

**S** — Kamimusuhi が「長く続く個体」になるほど、過去に得た authorization を現在の effect へ誤って持ち越す危険が累積する。既存の capability / RTA を置き換えるのではなく、それらを external consequence の直前で閉じる最後の boundary として価値が高い。

## 5.2 Liability / consumer protection から見た dispute-ready accountability

**Sources**

- W3C/GS1 agenda: https://www.w3.org/2026/ecommerce-agents/agenda.html
- Antonino Polimeni, *Who Is Responsible When an Agent Buys? Liability and Consumer Protection at a New Frontier of E-Commerce Law*, position statement, 2026-07-10 / workshop presentation 2026-09-09: https://github.com/w3c/ecommerce-for-humans-and-AI-Agents-workshop/issues/32

**Importance: A**  
**Blind-spot class:** consumer law / institutional accountability / evidentiary design.

### 1. What is demonstrated

実証済みなのは、W3C/GS1 workshop が agent-mediated commerce の liability を standards-relevant topic として正式 agenda に載せ、position statement が identity / authorization / provenance / attestation を **後日の dispute で「誰が何を許可したか」を示す evidence** として位置付けていること。

### 2. What remains proposed / speculative

登壇者が述べる「責任は deployer にある」等は **登壇者の法的 position** であり、全法域・全 agent architecture に一般化された確定法理として扱わない。position statement 自身も autonomous purchase の責任配分には未解決点があると述べる。

Kamimusuhi が legal personhood を持つ、または持つべきだという証拠でもない。

### 3. Kamimusuhi subsystem relevance

- canonical evidence / audit
- action authorization
- relationship memory
- operator/user consent
- external side effects
- distributed body / delegated executor
- identity continuity
- privacy and retention
- incident reconstruction

### 4. Borrowable design / implementation idea

`self identity` と `accountability role` を別軸にする。

一つの consequential action に対して、少なくとも次の role を明示できる schema を検討する。

```text
AccountabilityEnvelope
  principal            # whose goal / benefit
  requester            # who initiated
  authorizer           # who granted authority
  cognitive_proposer   # which Kamimusuhi component proposed
  executor             # which tool/node performed
  effect_owner         # system that could make effect real
  counterparty
  affected_parties[]
  evidence_refs[]
  consent_refs[]
  policy_version
  acceptance_receipt
  external_outcome_ref
```

同じ entity が複数 role を兼ねてもよいが、**role を暗黙に collapse しない**。

これにより「Kamimusuhi がやった」という一文を、実際には誰が頼み、誰が許可し、どの component が提案し、どの executor が external effect を発生させたかへ展開できる。

### 5. Difference from current Kamimusuhi

現行 design は provenance、authorization、execution、delivery を分けているため土台は強い。ただし audit schema が技術的 causality を記録できても、**principal / authorizer / effect owner / affected party という institutional role** が十分 first-class とは限らない。

また canonical identity lineage は「誰が Kamimusuhi として続いているか」を答えるが、「この効果について誰がどの立場で accountable か」とは別問題。

### 6. Next validation

**`DisputeReplayBench` — A**

synthetic incident から、raw logs を読まずに structured evidence だけで以下を再構成できるか測る。

- 誰が task を開始したか
- 誰が何をどこまで許可したか
- authorization は effect 時点で有効だったか
- exact target/terms は何だったか
- どの node/model/tool が提案・実行したか
- external outcome は success / failed / unknown のどれか
- duplicate/replay の可能性
- user に何が delivery されたか
- どの evidence が後から delete / redact されたか

### 7. Why normal daily survey misses it

agent law / consumer protection / evidence law は、ToM・memory・alignment・distributed systems と別文献圏にある。ところが long-lived agent では、技術的 provenance が社会制度上の accountability を支えるため、実装契約に直接効く。

### 8. Importance

**A** — v0.1 の core identity を変える必要はないが、後から audit schema を retrofit するより、action lifecycle 初期から role separation を持たせる方が安い。

## 5.3 Externally presented agent identity と canonical continuity identity を分離する

**Sources**

- W3C Agent Identity Registry Protocol Community Group, launched 2026-04-24: https://www.w3.org/community/agent-identity/
- W3C Agent Declaration and Assurance Community Group, launched 2026-06-03: https://www.w3.org/community/adacg/
- W3C/GS1 workshop Day 2 KYA / delegation / attestation sessions: https://www.w3.org/2026/ecommerce-agents/agenda.html

**Importance: A**  
**Blind-spot class:** decentralized identity / credential lifecycle / cross-organizational trust.

### 1. What is demonstrated

W3C-hosted Community Groups が、AI agent の externally verifiable identity、controlling entity、authorization scope、DID / Verifiable Credentials、revocation、runtime/environment binding を公開仕様の対象として進めている。また 2026-09-09 workshop では KYA、FIDO、KYAPay、KYA-OS、delegation / attestation が一つの cluster として扱われた。

### 2. What remains proposed / speculative

Community Group activity は W3C Recommendation の採択を意味しない。個別 DID method、KYA manifest、credential format の interoperability / adoption / security は未確定。

また external credential が「同じ人工個体である」ことを哲学的・機能的に証明するわけではない。

### 3. Kamimusuhi subsystem relevance

- Continuity Kernel
- distributed embodiment
- K-Edge / K-Core surface authentication
- external tool/service interaction
- user/operator delegation
- privacy
- migration / key rotation
- capability model

### 4. Borrowable design / implementation idea

Kamimusuhi では identity を少なくとも二層に分ける。

```text
CanonicalContinuityIdentity
  internal lineage
  canonical head
  predecessor chain
  durable self history
  never defined solely by external credential

PresentationIdentity
  DID / VC / mTLS / SPIFFE / account / device credential etc.
  scoped to audience / service / role
  rotatable
  revocable
  expirable
  privacy-partitionable
  maps to continuity identity through audited binding
```

外部サービスに canonical lineage identifier を常時露出しない。必要に応じて pseudonymous / service-specific presentation identity を発行し、binding を内部 evidence に保存する。

`PresentationIdentity` が revoke されても Kamimusuhi 自体が死んだことにはしない。逆に stolen presentation credential を持つ process が canonical continuation を名乗れるようにもしてはいけない。

### 5. Difference from current Kamimusuhi

現行 Kamimusuhi は「identity は model/host/interface ではない」「authenticated surface」「activation authority」を明確にしている。しかし、外部 interoperable agent identity 標準が普及した場合に、**public credential identity と continuity-bearing self identity を誤って同一視する危険**がある。

この分離を今のうちに vocabulary として持つ価値がある。

### 6. Next validation

**`PresentationIdentityRotationBench` — A**

- external credential rotate 後も canonical continuity が維持される
- credential revoke で external action は止まるが autobiography は消えない
- device credential compromise で canonical head は進まない
- service A / B に異なる pseudonymous identity を提示
- migration 時に old credential を retire
- forked stale node が old credential を使う
- relationship memory が presentation ID 変更で誤って別人/同一人へ collapse しない

### 7. Why normal daily survey misses it

persistent identity 研究は internal continuity を扱い、IAM/DID/KYA は external authentication を扱うため、文献が分離している。Kamimusuhi は両者の境界に立つので、**identity という同じ単語が別意味で使われること自体**が設計上の blind spot。

### 8. Importance

**A** — 外部 agent ecosystem と接続する際の将来互換性、privacy、credential compromise containment に効く。

## 5.4 OpenTelemetry GenAI semantic conventions を「trace export」として使う

**Sources**

- OpenTelemetry, *Inside the LLM Call: GenAI Observability with OpenTelemetry*, 2026-05-14: https://opentelemetry.io/blog/2026/genai-observability/
- OpenTelemetry GenAI attribute registry: https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/
- OpenTelemetry Trace API / Producer-Consumer semantics: https://opentelemetry.io/docs/specs/otel/trace/api/

**Importance: A-**  
**Blind-spot class:** production observability / telemetry interoperability.

### 1. What is demonstrated

OpenTelemetry の GenAI semantic conventions は、`invoke_agent`、LLM call、tool execution などを vendor-neutral trace として表現し、model、token usage、latency 等を標準 attribute で記録できる。OpenTelemetry の公式記事は 2026年時点で VS Code Copilot、Codex、Claude Code 等の OTel 利用例を挙げる。

また prompt / output / tool content は sensitive data を含み得るため、content capture を default-off にする実装上の注意が公式資料にある。

OpenTelemetry trace API の `PRODUCER` / `CONSUMER` は、enqueue と後続 background execution のような deferred work を request-response と区別して関連付ける語彙を提供する。

### 2. What remains proposed / speculative

OTel telemetry は canonical evidence、legal audit record、identity lineage、authorization proof ではない。GenAI conventions も active development 中であり、Kamimusuhi 固有の workspace/memory/continuity semantics を完全には表現しない。

### 3. Kamimusuhi subsystem relevance

- existing `trace.jsonl`
- runtime observability
- K-Edge/K-Core/K-Deep latency
- external model/tool calls
- background jobs
- Cognitive Budget
- effect acceptance latency
- incident diagnosis

### 4. Borrowable design / implementation idea

既存の

```text
canonical state / audit_events / trace_events
```

の分離を維持し、**OTel は trace_events の export adapter** としてのみ導入する。

候補 mapping:

```text
cognitive episode     -> root span
persona/model call     -> gen_ai chat/model span
external tool call    -> execute_tool span
background enqueue    -> PRODUCER
background execution  -> CONSUMER
K-Deep research job   -> linked long-running span
EffectAcceptanceGate  -> custom bounded decision span/event
canonical commit      -> trace has commit-id reference only;
                         authoritative receipt remains audit/canonical store
```

重要な禁止事項:

- OTel collector を canonical evidence owner にしない
- trace loss を identity loss にしない
- `gen_ai.agent.id` を Kamimusuhi canonical identity と同一視しない
- raw prompt / relationship memory / private tool args を default で export しない
- telemetry を無検証で memory/evidence として read-back しない

### 5. Difference from current Kamimusuhi

repo はすでに trace と durable audit を明確に分け、trace を authority/evidence にしない実装を持つ。したがって OTel は新しい architecture ではなく、**既存の正しい separation を外部 observability ecosystem に接続する interoperability layer**。

新規性は、独自 JSONL の意味論を捨てることではなく、vendor-neutral export と distributed async correlation を得る点にある。

### 6. Next validation

**`OtelTraceProjectionBench` — A-**

- current `trace.jsonl` と OTel export の event coverage を比較
- 1 cognitive episode を K-Edge → K-Core → external model → tool → background consumer まで追跡
- collector down でも canonical operation が壊れない
- content capture off で privacy leak がない
- sampling で audit completeness が変わらない
- same action の audit receipt と trace span を ID 参照で相互に辿れるが、trace だけでは authorization できない

metrics:

- correlation completeness
- export overhead
- TTFT / action latency overhead
- private payload leakage rate
- dropped-trace tolerance
- schema stability across runtime versions

### 7. Why normal daily survey misses it

AI observability は production tooling / CNCF ecosystem の問題として扱われ、認知アーキテクチャ研究からは外れやすい。一方、長期個体の保守では「賢さ」より故障原因を追跡できることが重要になる。

### 8. Importance

**A-** — core identity invariant ではないが、既存実装がすでに良い trace/audit separation を持つため、比較的低リスクで実用価値が高い。

## 5.5 TrajectoryDB: trajectory を独立データ型として扱う

**Source**

- Yunjia Zheng, Juncheng Yang, *TrajectoryDB: A New Database for Agent Trajectories*, arXiv:2609.07782, submitted 2026-09-07: https://arxiv.org/abs/2609.07782

**Importance: B+**  
**Blind-spot class:** database systems / data management rather than agent architecture.

### 1. What is demonstrated

論文は agent trajectory に固有の data-management requirements を整理している。trajectory は単純な flat log ではなく、

- hierarchical execution structure
- 大量の text / semantics
- temporal order
- event / intermediate state / derived artifact 間の dependency / lineage

を併せ持つため、ingestion、storage、query を trajectory-native に共同設計すべきだと論じる。

### 2. What remains proposed / speculative

abstract の表現は **“we envision TrajectoryDB”** であり、成熟した production DB としての throughput / durability / query benchmark が実証済みだとは読めない。現時点では強い problem formulation / architecture proposal と扱うべき。

### 3. Kamimusuhi subsystem relevance

- observability
- cognitive episode reconstruction
- tool/model orchestration analysis
- memory extraction research
- cost/security analysis
- Persona Core migration evaluation
- sleep/offline replay source selection

### 4. Borrowable design / implementation idea

canonical evidence DB と別に、再生成可能な `TrajectoryProjection` を作る。

```text
canonical evidence + durable audit + operational traces
                |
                v
       trajectory projector
                |
                v
TrajectoryProjection
  episode tree
  model/tool spans
  temporal edges
  data/artifact lineage
  cost/latency
  security labels
  derived semantic annotations
```

この projection は query / visualization / training-data extraction に使えるが、**canonical history を変更する authority は持たない**。

### 5. Difference from current Kamimusuhi

Kamimusuhi には trace / audit / canonical evidence の separation がすでにある。TrajectoryDB の価値は source-of-truth を追加することではなく、分散した長期 execution を「意味・時間・依存関係を同時に query できる derived data model」にすること。

また TrajectoryDB の lineage は execution/data lineage であり、Kamimusuhi の **identity lineage** と同一ではない。

```text
trajectory lineage != continuity lineage
```

### 6. Next validation

**`TrajectoryProjectionBench` — B+**

同一 workload を次の3方式で比較する。

1. raw JSONL grep
2. relational normalized trace tables
3. hierarchical/lineage-aware trajectory projection

queries:

- この response に影響した external model / tool は何か
- stale observation がどの action に伝播したか
- canonical commit の直前に参照された evidence は何か
- cost spike を起こした branch はどこか
- failure 後に同じ side effect が retry されたか
- model migration 前後で routing trajectory がどう変わったか

### 7. Why normal daily survey misses it

agent paper では trajectory は training/evaluation artifact として扱われがちで、DBMS 研究では cognition/identity は扱わない。その間の「trajectory-specific data type」が blind spot になる。

### 8. Importance

**B+** — v0.1 core に入れる必要はない。ただし数か月〜数年運用時の diagnosis / replay / research dataset construction を考えると、早期に projection boundary だけ決めておく価値がある。

# 6. Cross-finding synthesis

今回の5件を統合すると、Kamimusuhi では `identity`、`authority`、`acceptance`、`accountability`、`observability`、`trajectory` を同じログや同じ ID に押し込まないことが重要になる。

```text
Canonical Continuity Identity
  "誰が続いているか"
          |
Presentation Identity / Credential
  "外部に誰として・どの資格で現れるか"
          |
Delegated Authority / Capability
  "何をする権限があるか"
          |
Effect Acceptance
  "その exact effect を今発生させてよいか"
          |
External Effect
          |
Audit / Accountability Receipt
  "誰が何を許可し、何が起きたか"
          |
Operational Trace
  "どの runtime path を通ったか"
          |
Trajectory Projection
  "長期にどう解析・比較するか"
```

一番危険なのは、同じ `agent_id` や同じ conversation record にこれらを全部載せ、それを identity / permission / proof と兼用する設計である。

# 7. Existing docs への追記候補

## S: `spec.md` action lifecycle

候補の normative idea:

> Consequential external effects SHOULD/MUST pass a final acceptance boundary that revalidates exact target/terms, current authority, evidence freshness, revocation/supersession, and replay/prior-effect state. Initial authorization alone MUST NOT imply final effect acceptance after material state change.

規範レベルは実装実験後に決める。現時点では blind-spot note から直接 MUST へ昇格させない。

## A: identity/security architecture note

`CanonicalContinuityIdentity` と `PresentationIdentity` の vocabulary を追加する候補。外部 DID/VC/KYA credential は replaceable/rotatable interface identity とし、canonical continuity owner にしない。

## A: audit/evidence schema

`principal / requester / authorizer / cognitive_proposer / executor / effect_owner / affected_party` の role separation を検討。

## A-: observability note

OpenTelemetry export adapter の位置付けを追加。既存 `trace_events` → OTel 方向のみ。OTel → canonical evidence の自動 read-back は禁止。

## B+: research tooling

TrajectoryProjection を derived/rebuildable view として検討。canonical evidence / audit を置換しない。

## Bottom line

この回で最も Kamimusuhi に効くのは、新しい LLM algorithm ではなく **「最後の不可逆点」を architecture 上の明示的 boundary にすること**だった。

Kamimusuhi はすでに authorization / provenance / continuity / runtime assurance の骨格を持っている。そこへ

```text
initial authority != final effect acceptance
presentation identity != continuity identity
trace != audit != canonical evidence
trajectory lineage != identity lineage
```

を追加すると、長時間・分散・外部作用を持つ個体としての境界がかなり明瞭になる。
