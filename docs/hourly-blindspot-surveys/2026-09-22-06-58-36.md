## 1. 今回狙った盲点

1. **Content identity vs custody / rollback identity**  
   byte-identicalなbackup/archive/memory artifactは、物理的に1つへdedupしてよいとしても、migration run・rollback・consent・削除 acknowledgement・provenanceのclaimまで同一とは限らない。blob identityとsemantic custodyを混同していないか。

2. **Bounded sampling geometry before summarization**  
   summaryへ渡すinputを文字数で均等sliceしたとき、serialized recordを途中で切断したり、最新recordをbudget調整で落としたりしないか。summarizer品質以前に、入力projectionが構造的に成立しているか。

3. **Machine-semantic failure facts vs human-readable diagnostics**  
   errorを人間向けの短い文へ要約した後、その文だけが次layerへ渡ることで retryability / origin / cause chain が消え、schedulerが誤判断しないか。

4. **Long-lived observabilityのalert episode identity**  
   同じ障害が数分おきに継続しているだけなのにwarningを毎回再発報してsignalを埋めないか。一方で、同じ文字列でもresource incarnation・owner・原因・severityが変わった新しいincidentを誤って抑制しないか。

固定リスト外では、**content-addressable identityとrollback custodyの分離、sampling geometry、diagnostic projection semantics、incident-keyed observability**を重点探索した。

## 4.1 A+ — Claim-Preserving Content Deduplication

**Primary source:** OpenClaw #155194  
https://github.com/openclaw/openclaw/pull/155194

### (1) 何が実証済みか

Repeated session importでbyte-identical archiveが複数生成されると、OpenClaw Doctorはそれらをconflicting historyとして扱い、repairを継続延期し得た。PRは「duplicateを消す」だけでは不十分とし、**1つのverified survivorがすべてのretained migration runのrollback claimを満たすようmanifestをredirect**する。

さらにcompleted import acknowledgementをcoalesceし、すでに削除されたhistoryを再importで復活させない。earlier successful proofでは1,307 identical pairsを1 survivorずつへ収束させ、13,154 retained referencesが解決し、4つのcontent-different pairsは保全された。

ただしsurvey時点ではdraftで、exact-headの最終proofは別の既知SQLite lock prerequisiteの統合検証中。よってproduction adoption済みとは扱わない。

### (2) 何が提案・推測段階か

Kamimusuhiへ一般化する場合、全duplicate blobを必ずdedupする必要はない。重要なのは、**content identityとcustody/rollback identityを別型にする**こと。

```text
ContentObject {
  digest
  size
  encoding
}

CustodyClaim {
  claim_id
  content_digest
  principal / memory_domain
  lineage
  migration_run
  rollback_ref
  consent_epoch
  retention_policy
  deletion_ack?
}
```

物理blobを1つへ統合しても、claimは複数残り得る。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Continuity Kernel / canonical evidence
- backup / restore / migration
- branch / merge / death-rebirth continuity
- Personal / Relationship / Library Memory
- memory ownership and consent
- multi-device embodiment
- digital legacy / archival continuity
- graceful forgetting / distributed erasure

### (4) 借りられる設計・実装アイデア

- `blob identity` と `semantic claim identity` を分離する。
- dedup transactionは `discover equal content → verify survivor → redirect all live claims → merge acknowledgements/tombstones → verify no dangling refs → retire duplicate physical artifacts` の順序にする。
- **deletion acknowledgement / tombstoneをpositive import claimより弱くしない**。同じbytesが別runに残っていても、削除済みhistoryを勝手に復活させない。
- rollback receiptは「path」ではなくsurvivor content + claim mappingへbindする。
- physical reclamation前にclaim closureを機械検証する。

### (5) Kamimusuhiとの差分

既出 `Provenance-Preserving Rollback`、`Namespace-Complete Durable References`、`Distributed Erasure Completion` は近いが、今回の差分は **「内容が完全に同じ複数artifactを1物理objectへmergeする時、各artifactが担っていたsemantic/custody claimをどう保つか」**。

content-addressable storageだけではこの問題を解かない。same digestはsame bytesを言うだけで、same owner / same deletion state / same rollback obligationを意味しない。

### (6) 次に検証すべきこと

**`ClaimPreservingDedupBench-v0`**

最低fixture:

1. migration run A/Bがbyte-identical archiveを持つ
2. Aのみcompleted / Bはinterrupted
3. Aの一部historyにはuser deletion acknowledgementがある
4. dedup途中でcrash
5. restart/recovery後に全live claimが1 survivorへ解決する
6. rollback A/Bがそれぞれ正しく動く
7. deletion済みhistoryがresurrectしない
8. 1 byteでも異なるcopyは自動mergeしない
9. consent / memory domainが異なるsame-content objectもclaimを混同しない

成功条件: dangling reference 0、unauthorized resurrection 0、rollback claim loss 0。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常のagent memory / identity continuity検索では「何を覚えるか」「どうretrieveするか」に寄りやすい。今回のfailureは**import Doctor / duplicate archive / migration manifest / rollback journal**というstorage-maintenance実装面に現れるため、高レベルmemory surveyから抜けやすい。

### (8) 重要度

**A+**。Kamimusuhiが長寿命化し、backup・migration・branch・multi-device copyが増えるほど高確率で遭遇する。content-addressingを採用するほど「same bytesだからmergeしてよい」という誤った直感が強くなる点も重要。

## 4.2 A — Record-Atomic Bounded Sampling

**Primary source:** Hermes #118564  
https://github.com/NousResearch/hermes-agent/pull/118564

### (1) 何が実証済みか

Lean summarization用inputをcharacter offsetで均等sliceすると、serialized recordを途中で切断し得る。またmarker budgetを引いた後の最終sliceがnewest regionを確実に含まず、最新状態を落とし得た。

candidate fixはcomplete record単位で複数regionをsampleし、marker spaceを先に確保し、final regionをnewest recordへanchorし、cap内へtrimする場合もrecord boundaryを守る。focused regression 2件はpass。full suiteは未実行なので評価はA止まり。

### (2) 何が提案・推測段階か

Kamimusuhiがdouble-newlineをrecord delimiterにする必要はない。一般化すべき契約は:

- bounded projectionは**semantic/structural atomを切らない**
- coverage policy（recent / stratified / priority）を明示する
- budget計算にseparator / marker / envelope overheadを含める
- giant single recordの扱いをexplicit degraded modeにする

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- context compaction
- Background Dreaming / consolidation
- self-model refresh
- memory summarization
- K-Deep handoff
- telemetry sampling / incident summarization
- scheduled survey continuity

### (4) 借りられる設計・実装アイデア

`BoundedSampleReceipt`を導入する。

```text
BoundedSampleReceipt {
  source_revision
  atom_count_total
  atom_ids_included
  coverage_policy
  newest_atom_included
  omitted_ranges
  lossy_atom_ids
  budget_used
}
```

通常modeではrecord split禁止。どうしても巨大recordを圧縮する場合は`LOSSY_ATOM_PROJECTION`として別pathにし、canonical recordとは区別する。

### (5) Kamimusuhiとの差分

既出 `Semantic Continuity Projection` は「前回runから次runへ何を意味的に渡すか」、`Compaction Continuation Closure` は圧縮後のcontinuationを扱う。今回の差分は**その前段のsampling geometry**で、summary modelへ入力するmaterial自体がhalf-recordになったりnewest stateを欠いたりする問題。

### (6) 次に検証すべきこと

**`RecordAtomicSamplingBench-v0`**

- variable-size records
- Unicode / multi-part attachment refs
- tool-call + tool-resultを不可分groupとして扱うfixture
- marker overheadがbudget境界を跨ぐcase
- oldest / middle / newestのstratified sampling
- 1 recordだけでbudget超過するcase
- newest mandatory policyとnewest non-mandatory policy
- sample → summarize → replayでsynthetic malformed recordが生まれないこと

### (7) 既存デイリーサーベイではなぜ拾いにくいか

compaction研究はsummary quality、context length、token efficiencyへ寄りやすい。serializer / delimiter / slice offset / marker accountingという**データ構造とsampling実装の境界**は通常のagent memory分類では見落としやすい。

### (8) 重要度

**A**。identity continuityを直接書き換えるわけではないが、derived summary・self-model・handoffへ壊れたmaterialを流す入口になる。実装も比較的小さくbench化しやすい。

## 4.3 A — Failure-Semantic Projection Preservation（Failure-Origin-Typed Async Outcomes の拡張）

**Primary source:** Hermes #118548  
https://github.com/NousResearch/hermes-agent/pull/118548

### (1) 何が実証済みか

raw network resolution failureは最初のlayerでは正しく認識されていたが、人間向けerror summarizerがcanonical sentenceへ変換し、その後schedulerがcause chainなしの`RuntimeError(string)`として再構成した。下流retry classifierはcause chainしか見ないため「transient provider unreachable」を認識できず、定期jobのretry ladderが消えた。

candidate fixはsummary sentenceをclassifierへ追加し、raw transport formとsummary formの両方をtransientとして認識するtestsを追加している。

### (2) 何が提案・推測段階か

文字列patternを増やす修正は局所的には有効だが、Kamimusuhiでは長期的に脆い。一般化案は**display projectionとcontrol semanticsを別fieldにする**こと。

```text
FailureEnvelope {
  failure_id
  semantic_class
  origin
  terminal
  retryability
  cause_refs
  provider / route
  display_summary
  policy_epoch
}
```

human-facing要約は`display_summary`だけを変え、semantic fieldsを消さない。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- scheduler / prospective obligations
- K-Deep delegation
- provider failover
- Cognitive Action Router
- maintenance / dream jobs
- retry / circuit breaker
- observability / UI diagnostics

### (4) 借りられる設計・実装アイデア

- exception→string→exceptionの往復をcontrol planeで禁止する。
- cross-process serializationもtyped failure envelopeで行う。
- localizationやredaction後も`semantic_class / retryability / terminal`を不変にする。
- user-visible errorとoperator diagnosticを別projectionにする。

### (5) Kamimusuhiとの差分

前回の `Failure-Origin-Typed Async Outcomes` は「同じ`TimeoutError`型でもsupervisor timeoutとworker failureは違う」という**同型異origin**問題だった。今回は逆に、**同じfailureがpresentation変換を通ることで型・cause・retry semanticsを失う**問題。

したがって独立原則ではなく、既存findingを「typed at observation」から**「typed semantics survive projection/serialization」まで閉じる拡張**として扱う。

### (6) 次に検証すべきこと

**`FailureSemanticProjectionBench-v0`**

- raw DNS / auth / quota / timeout / policy failureを生成
- human summary、localized summary、redacted summary、cross-process encode/decodeを通す
- retry / failover / terminal判定がprojection前後で不変であること
- 同じdisplay textでもsemantic classが異なるnegative control
- semantic classは同じだがdisplay languageが異なるpositive control

### (7) 既存デイリーサーベイではなぜ拾いにくいか

retryやnetwork failureを検索するとpolicy自体へ注目しやすい。今回の障害は**UX error summarizerとscheduler classifierの間**にあり、presentation layerがcontrol plane semanticsを破壊する接合事故。

### (8) 重要度

**A（既存項目の拡張）**。Background / scheduled cognitionでは人に見せるための要約層が多く、string-based controlへ落ちるとself-healingが静かに停止する。

## 4.4 B — Generation-Aware Diagnostic Suppression

**Primary source:** OpenClaw #155211  
https://github.com/openclaw/openclaw/pull/155211

**Cross-domain support:** PagerDuty Event Management / Event Orchestration  
https://support.pagerduty.com/main/docs/event-management  
https://support.pagerduty.com/main/docs/event-orchestration

### (1) 何が実証済みか

OpenClawのdurable browser-tab cleanupでは、同じunreachable conditionが5分ごとにWARNを出し続け、実環境報告で1日555行、同一tabで168 consecutive WARNsが蓄積した。candidateは最初だけWARN、同一identity/reasonのrepeatをdebugへ下げる一方、rowがretrackedされたりbrowser instanceが変わったりreasonが変わった場合は再警告する。

PagerDutyでもexplicit `dedup_key`によるalert dedupが一般化されており、同じkeyのeventは同じalertへmergeされる。つまりobservabilityでも**incident identityはmessage textとは別**に持つのが自然。

### (2) 何が提案・推測段階か

KamimusuhiでWARN→debug固定が最適とは限らない。長寿命個体では「最初だけ強く通知」すると長時間放置される可能性があるため、severity / age / user availability / repair progressに応じたrenotify policyが必要。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- K-Nerve
- Digital Interoception
- distributed body health
- maintenance / self-repair
- operator UI
- degraded-mode operation
- long-lived telemetry / observability

### (4) 借りられる設計・実装アイデア

```text
DiagnosticEpisodeKey {
  resource_incarnation
  owner_generation
  fault_class
  operation_epoch?
}
```

- first observation: visible WARN / incident open
- same episode repeat: counter + debug/trace
- severity escalation / reason change / new incarnation: re-notify
- settlement: episode close
- recurrence after settlement: new episode
- long unresolved episode: bounded renotify / escalation

message textそのものをdedup keyにしない。

### (5) Kamimusuhiとの差分

既出 `Attribution-Preserving Telemetry Batching` / `Telemetry-Policy Epochs` はtelemetryのprovenanceやpolicy versionを扱う。今回の差分は**同じ障害episodeを何回人間へinterruptすべきか**をresource generationとlifecycleへbindすること。

### (6) 次に検証すべきこと

**`GenerationAwareDiagnosticDedupeBench-v0`**

- identical faultを300回観測 → high-severity pageはbounded
- same text / new resource incarnation → 必ず新incident
- same resource / new owner generation → 必ず再評価
- same episode / severity escalation → 再通知
- settlement後のrecurrence → new episode
- dedupe map overflow / restart後もincident identityが破綻しない
- suppressionし過ぎてunresolved critical incidentが忘れられないrenotify fixture

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent observability検索は「何を計測するか」「traceをどう集めるか」に寄る。**human attentionを有限resourceとして、warning suppression自体をidentity/lifecycle問題にする**観点は抜けやすい。

### (8) 重要度

**B**。即時のidentity破壊ではないが、24/7長寿命agentではalert fatigueがoperatorの監督能力を下げ、Digital Interoceptionの実効性を損なう。実装コストは小さい。

## 9. 今回の結論

今回の最大のblind spotは、**content identityとcontinuity claim identityは別物**だという点だった。

Kamimusuhiで将来、memory archive・backup・branch snapshot・multi-device replicaをcontent hashでdedupしたとしても、

```text
same bytes
!=
same owner
!=
same consent
!=
same rollback obligation
!=
same deletion state
!=
same historical role
```

である。物理storageを縮めても、個体の履歴上のclaimを縮約してはいけない。

次点は、**bounded cognitive inputは「token budget内に収まる」だけでは不十分**で、record atomicity・coverage policy・newest anchorまでcontractにする必要があること。さらに、failure diagnosticsとobservabilityでは、人間向けprojectionがmachine control semanticsを消さず、同じincidentの反復と新しいincidentをgenerationで区別する必要がある。

**Recommended next action:** `ClaimPreservingDedupBench-v0` と `RecordAtomicSamplingBench-v0` を先に実装し、どちらも外部LLM非依存のdeterministic regression suiteとしてCIへ置く。
