## 1. 今回狙った盲点

1. **execution state を再利用できる条件を「同じsession」だけで決める問題**  
   provider/server-side response state、KV、execution continuation state等は、同じagent/sessionでも、新規user input・人間review・recovery・tool catalog変更を跨いで再利用すると意味が変わる。

2. **recovery/reconnect がretry budgetを新しくしてしまう問題**  
   retry回数をprocess-local counterとして扱うと、restartやlistener handoffのたびに「あとN回」が復活し、turn単位の有限budgetが実質無限になる。

3. **version obligationをexact equalityで判定する問題**  
   「少なくともversion Xへrestart済み」という義務は、Xの正当なdescendantで稼働していれば満たされている。byte equalityとsemantic satisfactionは別。

4. **学習済みskill / executable artifactのcanonical stateにruntime副産物が混ざる問題**  
   import cache、JIT cache、一時index等がcontent-addressed treeへ混入すると、同じ能力なのに別skillとして見えたり、正当なupdateをlocal modification扱いしたりする。

5. **長寿命identityとcredential/token寿命の混同**  
   個体identityは継続しても、access token / assertion / session credentialはrotate・revoke・再取得されるべきである。credential失効を「個体の死」と扱わず、逆に個体continuityを理由にcredentialを延命しない境界が必要。

6. **新しい経験が既存記憶を更新すべきか、別episodeとして分岐すべきかを常に同じ規則で決める問題**  
   人間記憶研究では、既存経験との不一致/prediction errorの大きさが、memory updatingとdifferentiationの競合に関与する。Kamimusuhiのreconsolidationにも「overwrite vs branch」の判定軸が必要かもしれない。

固定リスト以外の探索として、version-order semantics、artifact canonicalization、recovery budget conservation、token lifecycle standards、memory reconsolidation/update-vs-differentiation、agency-conditioned episodic encoding、日本語圏のagent運用記録を重点化した。

### 4.2 Recovery-Persistent Cumulative Retry Budget

- **重要度: A**
- **source:** Letta Code #4563

**(1) 何が実証済み / 確認済みか**  
Lettaのlistener guidanceではprovider API retry counterはturn-scoped cumulativeで、途中にsuccessful tool workを挟んでもresetせず、deployment-recovery / pre-stream retryとは別budgetとしている。PRはdocumentation changeであり、今回新たなfault-injection結果を示すものではない。

**(2) 何が提案・推測段階か**  
Kamimusuhiでどのretryを「同じbudget」に束ねるべきかは未確定。provider rate-limit、network reconnect、tool retry、embodiment action retryを全部一つにすると過度に保守的になる。

**(3) 関連サブシステム**  
Model Router、RecoveryJournal、K-Deep、tool execution、Cognitive Budget、failure-classed resource quarantine。

**(4) 借りられる設計・実装アイデア**

**(5) Kamimusuhiとの差分**  
既存のprogress-sensitive retryやfailure-classed quarantineは「いつ再試行するか」を扱う。今回の差分は、**recoveryそれ自体をbudget reset eventにしない**ことでboundednessをcontinuityの向こう側まで保存する点。

**(6) 次に検証すべきこと**  
`RetryBudgetRecoveryConservationBench-v0`: 2回failure→restart→2回failure→listener handoffを注入し、turn全体のattempt上限を超えないことと、別failure domainの独立budgetを誤消費しないことを検証。

**(7) dailyで拾いにくい理由**  
retry/backoffは通常SREまたはprovider reliabilityとして扱われ、**identity/session continuityによってretry上限が破れる**という横断failureは見落とされやすい。

**(8) 重要度**  
**A**。

### 4.6 Prediction-Error-Gated Episodic Update vs Differentiation

- **重要度: B+**
- **source:** Pronoza et al., Neural Computation 2026

**(1) 何が実証済みか**  
人間の類似conversation memory実験の再解析で、modified versionのrecognition confidenceとprediction errorにU字的関係があり、prediction errorが大きいほどoriginal/modifiedの2 versionsを想起する頻度が高かった。modified Hopfield modelは、similar new patternsでinterference/update、dissimilar patternsでseparate storageが生じ、prediction-error依存encoding strengthで傾向を説明した。

**(2) 何が提案・推測段階か**  
この機構をAI memoryへ直接転用できることは未実証。特にLLM embedding distanceを心理学的prediction errorと同一視してはいけない。

**(3) 関連サブシステム**  
Episodic Memory、Memory Reconsolidation、Narrative Self、Continuity Kernel、contradiction handling、dream/offline consolidation。

**(4) 借りられる設計・実装アイデア**  
新証拠が既存episodeに近い時でも、`expected_state vs observed_state`のprediction error / contradiction magnitudeを保持し、低〜中不一致は`revision edge`、大不一致は`branch/new episode`をdefaultにする。original evidenceは消さず、reconsolidated interpretationを別versionとして持つ。

**(5) Kamimusuhiとの差分**  
Kamimusuhiはすでにcanonical evidenceとinterpretationを分離するが、**どの時点で同じepisodeの更新とみなし、いつ別episodeへ分けるか**の認知的criteriaはまだ薄い。この研究はそのdecision variable候補を与える。

**(6) 次に検証すべきこと**  
`EpisodicUpdateDifferentiationBench-v0`: 同一人物・同一出来事への軽微修正、強い矛盾、誤情報訂正、後日再解釈を投入し、always-merge / always-branch / prediction-error-gated方式でtruth preservation、retrieval precision、narrative coherence、false overwriteを比較する。

memory researchを「retrieval精度」「long-context」「RAG」で探すと、human reconsolidationの**update-vs-differentiate competition**は心理学/計算神経科学側に埋もれる。

## 9. 今回の結論

今回の中心は、**continuityは「同じものを再利用し続けること」ではなく、再利用してよい状態・使い切ったbudget・満たされたobligation・canonical artifact・短命credential・更新/分岐すべきmemoryをそれぞれ別lifecycleで扱うこと**にある。

最も実装価値が高いのは `ContinuationEquivalentStateReuseBench-v0`。同じsession / same agent / same conversationという粗い同一性ではなく、**現在の入力が前回execution stateの正当なcontinuationか**を型として判定する設計は、Kamimusuhiが複数model・tool catalog・device・recovery generationを跨ぐほど重要になる。
