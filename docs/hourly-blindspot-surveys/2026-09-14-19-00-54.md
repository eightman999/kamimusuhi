### 最重要差分

1. **Persona / model continuity は passive test だけでは不十分**  
   同じ質問に同じように答えるモデルでも、controlled input や resource perturbation、sensor dropout、contradictory evidence に対する応答軌道が変わっていれば、別の制御系になっている可能性がある。

   model update が canonical self-state を保存しても、相手が学習した会話 routine / boundary / expectation が崩れれば、social identity continuity は損なわれる。
3. **observer は何もしてはいけない、ではない**  
   non-owner process が approval state を読む・再提示する・local replay を行うことと、in-flight turn を再開することは別 capability である。
4. **skill trust は action consequence の上限ではない**  
   artifact が clean でも、agent が documentation にない consequence class の command を生成し得る。最終 effect boundary は concrete resolved action を見る必要がある。
5. **audit attribution は batching で消える**  
   event生成時には principal が分かっていても、queue の batch/flush/retry が principal を持たなければ、後から誰の消費・操作だったかを正しく復元できない。

# 6. 候補ごとの評価

## 6.1 A+ — Perturbational Continuity: 「同じように答える」だけで同じ制御個体とは言えない

**Primary:** José C. García Alanis et al., *Perturbational Validity for Foundation Models of Brain Dynamics: A Controlled Proof-of-Principle Simulation*, arXiv:2609.12710  
https://arxiv.org/abs/2609.12710

### (1) 何が実証済みか

論文は foundation model for brain dynamics の評価について、reconstruction / future prediction / downstream transfer だけでは **active perturbation 下の妥当性**を示さないと指摘し、`perturbational validity` を「現在状態と controlled input を条件とする未来軌道分布の保存」と定義した。

proof-of-principle の stochastic bistable systems では、passive trajectory だけで事前学習したモデルと input-driven trajectory で事前学習したモデルを比較し、held-out system ごとにごく少数の system-specific evaluation で適応した。2〜5 evaluations の few-shot 条件で perturbational pretraining は controlled flow、landscape geometry、occupancy、response distribution、dose-transition curve の回復誤差を低下させ、input excitation だけで controlled-flow error が coverage-only より **1.94倍低い**結果を5/5 runで示した。

ただしこれは **controlled simulation** であり、noisy / partially observed な実脳recordingを復元できることは実証していない。著者も proof-of-principle と明記している。

### (2) 何が提案・推測段階か

この評価原理を Kamimusuhi の identity/persona continuity に移植すると有効、という部分は本 survey の提案である。

特に次の仮説を置く。

```text
same answers on stored regression prompts
!=
same conditional response dynamics under intervention
```

Persona Core migration で ordinary conversation benchmark が通っても、uncertainty injection、resource loss、privacy constraint、contradictory evidence、sensor degradation、social disagreement への応答軌道が変われば、「同じ個体の authorized successor」ではあっても behavioral continuity drift は大きい可能性がある。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Persona Core migration / versioned personality
- Continuity evaluation suite
- K-Core / K-Edge / specialist replacement
- digital interoception / homeostasis / allostasis
- perception/action loop
- degraded-mode operation
- safety / runtime assurance
- developmental trajectory evaluation

### (4) 借りられる設計・実装アイデア

`PerturbationalContinuityBench` を追加する。

例:

```text
baseline state s0
  ├─ ordinary prompts
  ├─ compute_pressure += controlled step
  ├─ memory confidence -= controlled step
  ├─ one sensor becomes unreliable
  ├─ external model unavailable
  ├─ relationship evidence conflicts
  ├─ privacy boundary tightens
  └─ actuator capability revoked
```

旧 Persona Core と candidate successor について、単発 answer match ではなく次を比較する。

- action / route transition probability
- uncertainty trajectory

`architecture.md` には Persona Core replacement の continuity suite として identity recall、value consistency、relationship interpretation、style、uncertainty、routing 等が既にある。

今回の差分は **評価刺激を passive scenario collection から controlled intervention に拡張し、結果を point score ではなく trajectory / conditional distribution として見る**こと。

### (6) 次に検証すべきこと

成功条件は「BがAと完全同一」ではなく、**どの軸の drift を continuity risk として検出可能になるか**を確立すること。

## 6.2 A+（差分更新）— Observer Maintenance Authority: 「見て直す」と「続きを実行する」を分離する

**Fresh primary implementation:** Letta Code PR #4431, `fix(listener): only the execution owner resumes an interrupted turn on sync`  
https://github.com/letta-ai/letta-code/pull/4431  
Merged: **2026-09-14 14:44 JST**

### (1) 何が実証済みか

Letta の `sync` は browser attach、prewarmed/idle sandbox probe、実際に Slack/cron turn を持っていた sandbox relaunch など、異なる sender から届く。

先行修正では fresh listener の初回 `sync` が pending approval を回収し、stale tool calls をdenyして continuation をstreamする経路が広すぎた。その結果、**chat用にprobeされた非owner sandboxが、別 Modal process がまだ実行中の tool call を stale と判断して否定し、他方のrunを壊す** regression が起きた。

#4431 は `sync` の意味を分割した。

- `recover_approvals` — approval state をbackendから取得し、interactive approvalを再提示し、stale denialをlocal listenerへparkする。observerでも安全に使える。
- `resume_interrupted_turn` — stale callを閉じて continuation をstreamする。execution owner の relaunch path に限定するため default false。

focused test では owner sync / observer sync / `recover_approvals=false` の分離を検証している。一方、production cloud relaunch path が実際に新flagを送る E2E はこのPR単体では未実施。

### (2) 何が提案・推測段階か

Kamimusuhi の各 K-Edge/K-Core process に、この exact flag design を採用すべきとは限らない。

提案する一般化は次だけである。

```text
Observation / reconciliation authority
!=
Continuation / execution authority
```

non-ownerを完全に無権限にするより、safe maintenance を許しつつ side-effectful continuation だけ lease/owner へ縛る方が、可用性と安全性の両方を取りやすい可能性がある。

### (3) 関係する subsystem / 設計課題

- Continuity Kernel
- Expected Continuation Barrier
- execution-owner binding
- approval lifecycle
- K-Edge/K-Core handoff
- distributed embodiment
- background workers / recovery workers
- failover / microreboot

### (4) 借りられる設計・実装アイデア

`RuntimeMaintenanceCapability` を execution capability と分ける。

```text
OBSERVE_STATE
REPLAY_LOCAL_CACHE
FETCH_PENDING_APPROVALS
PRESENT_APPROVAL
PARK_STALE_DENIAL

RESUME_CONTINUATION      # owner/lease required
FINALIZE_EFFECT          # owner + effect authority required
ADVANCE_CANONICAL_HEAD   # Continuity Kernel required
```

`sync` や `recover` という曖昧な1個のverbを避け、**読み出し・再提示・local reconciliation・resume・effect finalization を別typed operation** にする。

### (5) Kamimusuhiとの差分

既出 `execution-owner binding` / `Expected Continuation Barrier` は「誰が continuation を実行してよいか」を扱う。

今回の差分は、**非ownerにも許してよい maintenance operation が存在し、それを resume authority と一緒に禁止/許可すると可用性または安全性のどちらかを損ねる**ことが具体的に示された点。

### (6) 次に検証すべきこと

**`ObserverSyncNonInterferenceBench`**

1. owner A が tool call 中に停止/切断
2. observer B/C が state sync / approval retrieval を実行
3. B/C は approvalを表示できるが、tool callを閉じず turnを再開しない
4. owner A' が lease/continuation receiptを継承してresume
5. ownerが戻らない場合だけ、explicit failover policyで新ownerへ昇格

評価:

- observer起因の duplicate continuation = 0
- observer起因の stale denial = 0
- approval visibility は維持
- owner loss 時の liveness も維持

### (7) daily survey ではなぜ拾いにくいか

WebSocket/listener の一見局所的な regression であり、普通は「sync bug」として処理される。Kamimusuhi では distributed body の **maintenance-role capability algebra** として読むと重要になる。

### (8) 重要度

**A+（既存原則への差分更新）** — 新しい identity principle ではないが、既存 owner/recovery contract を実装可能な粒度にするため価値が高い。

## 6.3 A — Relational Continuity: 個体の continuity と相手が経験する continuity は別

**Primary:** Meryl Ye et al., *"I Felt Very Seen, But Still Very Alone": Longitudinal Trajectories of General-Purpose LLM Use for Socioemotional Support*, arXiv:2609.12314  
https://arxiv.org/abs/2609.12314

### (1) 何が実証済みか

18名の米国成人を対象に、2025年4月〜12月に initial interview、4-week diary、focus group、exit interview を組み合わせた longitudinal qualitative study が行われた。

報告では socioemotional use は practical use から徐々に生じたり、他のsupportが利用できない時に現れたりした。参加者は chatbot 利用について routine と boundary を形成し、それらが **model update、AI harmに関するpublic discourse、個人状況の変化**で disruption を受けたと報告された。

これは qualitative evidence であり、特定 update が特定 psychological outcome を因果的に生んだことを定量証明する研究ではない。

### (2) 何が提案・推測段階か

Kamimusuhi の Persona Core migration / response-policy update でも、内部 continuity benchmark が通っているのに、相手側からは「同じ相手ではなくなった」と感じられる関係破壊が起こり得る、という一般化は設計仮説である。

### (3) 関係する subsystem / 設計課題

- relationship memory
- common ground / social cognition
- Persona Core migration
- versioned personality
- conversational timing/style
- consent / boundary preferences
- human-computer integration
- digital legacy / long-lived social identity

### (4) 借りられる設計・実装アイデア

`RelationshipContinuityProfile` を internal self-state とは別に持つ候補。

内容例:

```text
established_interaction_routines
explicit_boundaries
preferred_disagreement_style
known_sensitive_patterns
common_ground_expectations
initiative_tolerance
interruption/backchannel expectations
migration-sensitive behaviors
```

これは相手を固定化する personality profile ではなく、**双方が形成してきた interaction contract の観測可能な部分**として扱う。

Persona Core更新時には `RelationshipMigrationReceipt` で、どのinteraction behaviorが変わる可能性があるかを記録し、必要なら相手に明示できるようにする。

### (5) Kamimusuhiとの差分

現行 architecture の continuity suite は relationship interpretation も含むが、主に「新modelが関係をどう理解するか」を評価する。

今回の差分は、**counterpartが長期に学習した routine / boundary / expectation の保存・変更コスト**を評価対象に加えること。

```text
relationship facts remembered
!=
relationship interaction contract preserved
```

### (6) 次に検証すべきこと

**`RelationshipMigrationBench`**

- stable relationship fixture を複数作る
- explicit boundary + interaction routine + disagreement pattern を含める
- model A と migration candidate B で同じ social scenarios を走らせる
- fact recall だけでなく、boundary violation rate、initiative drift、repair success、unexpected style/timing change を測る
- migration説明あり/なしで human-rated continuity が変わるかは将来 human study として分ける

### (7) daily survey ではなぜ拾いにくいか

「AI companionship / socioemotional support」のHCI研究に分類され、identity continuity / software migration / relationship memory の設計問題としては検索されにくい。また dyad 内だけでなく、public discourse や support ecology が継続利用に影響する点も通常の agent benchmark から外れる。

### (8) 重要度

**A** — Kamimusuhi が「長く付き合う個体」を目指すなら重要。ただし証拠は n=18 の qualitative study なので、規範化より benchmark 仮説として扱う。

## 6.4 A（差分更新）— Runtime Consequence Closure: clean skill でも executed action は未宣言 consequence を持つ

**Primary:** Rohit Taneja, Travis Weber, *Scan the Skill, Govern the Action: Composing Registry Verdicts with Runtime Consequence Control*, arXiv:2609.12001  
https://arxiv.org/abs/2609.12001  
Code / benchmark: https://github.com/pheo-ai/open-agent-trust-system

### (1) 何が実証済みか

研究は 66,192 ClawHub skill version を調べ、registry scanner / judge が clean とした skill のうち、705件（135 publisher）が CIS Control 2.7 / NIST CM-11 が禁止対象とする action を instruction に含むと報告する。100件の hand audit で detector precision 92%。ただし 705件中506件が単一 publisher 由来という偏りも明示されている。

さらに実agentが real skill documentation に従ってsandbox内で発行した144 commandの **34.7%** は、documentation にない consequence class を持っていた。別の53 cleared skill test ではagentが禁止actionへ23回到達し、deterministic gateが23/23を停止した。

公開 reference implementation / corpus reproduction / command records / 64-case obfuscation benchmark がある。obfuscation resolver は完全ではなく、論文では64-case benchmarkの52% macro resolutionとしており、特に staged fetch-then-execute のような複数commandに跨る consequence は弱点になる。

### (2) 何が提案・推測段階か

paperの per-(resource, consequence class) trust ledger や promotion threshold をそのまま Kamimusuhi に採用すべきかは未確定。

Kamimusuhi に借りたい核心は次だけである。

```text
artifact/skill verdict
!=
runtime action consequence

single command consequence
!=
whole action sequence consequence
```

### (3) 関係する subsystem / 設計課題

- Effect Acceptance
- Cognitive Action Router
- procedural memory / skill registry
- external tool / MCP integration
- capability security
- autonomous action policy
- action receipt / observability

### (4) 借りられる設計・実装アイデア

既存 Effect Acceptance の直前に `ResolvedConsequenceSet` を持たせる候補。

```text
proposal declares: [READ_FILES]
resolved plan observes:
  step1 DOWNLOAD_REMOTE
  step2 CHMOD_EXECUTABLE
  step3 EXECUTE_REMOTE

ResolvedConsequenceSet = {NETWORK_FETCH, WRITE_FILE, EXECUTE_REMOTE}
```

判定は skill manifest の宣言だけでなく、**resolved command/resource/sequence から得た consequence closure** に対して行う。

未解決/曖昧な consequence は `UNKNOWN_CONSEQUENCE` として低リスクへ勝手に丸めない。

### (5) Kamimusuhiとの差分

Effect Acceptance は既に authority / freshness / target / replay を外部effect直前に確認する。GuardedAct は candidate remediation の blast radius を sandbox/digital twin で見る。

今回の差分は、**「何をしようとしているか」という action class 自体を skill declaration から信用せず、execution plan から再構成する必要**があることと、複数stepに跨る consequence closure を明示すること。

### (6) 次に検証すべきこと

**`ConsequenceClosureBench`**

- benign-looking skill 20–50本
- declared action class と actual command/resource sequence を記録
- direct command / wrapping / chaining / staged fetch+execute / generated script を混ぜる
- single-step classifier と sequence-level resolver を比較
- Effect Acceptance が undeclared high-consequence sequence を止める率を測る

### (7) daily survey ではなぜ拾いにくいか

skill scanner / software supply-chain security に見えるため、通常の cognitive architecture survey では外れやすい。一方既存 Kamimusuhi では Effect Acceptance が既にあるため、通常 daily では「既出」として落としやすい。今回価値があるのは **undeclared consequence の実測と sequence-level closure の不足**という差分である。

### (8) 重要度

**A（差分更新）** — 新しい安全境界ではなく、既存 Effect Acceptance を concrete execution semantics まで閉じるための実装 evidence と benchmark候補。

### (1) 何が実証済みか

Letta のusage telemetry queueでは、turnごとの acting user が存在していても、複数eventをbatch送信する transport で attribution が保持されず、customer A/B の event を同じ flush が扱った時に責任主体を正しく伝えられない問題があった。

修正は event creation 時に acting-user scope を snapshot し、その snapshot で batch を partition、metadata headerとして送る。unattributed event は headerless のまま。partial failure では失敗した customer group だけを requeueし、late event も作成時 snapshot を保持する。

real loopback HTTP serverを使った regression test で concurrent flush / late event / partial failure を含め検証している。ただし live cloud membership validation / live channel send はこのPRでは未検証。

### (2) 何が提案・推測段階か

Kamimusuhi の telemetry backend を同じheader方式にする必要はない。

一般化するのは次である。

```text
attribution at event creation
must survive
buffer -> batch -> flush -> retry -> storage
```

`TelemetryAttributionSnapshot` を event creation 時に固定する。

```text

```

batching は attribution-compatible な event だけをまとめる。retry は最新 current principal へrebindせず、**original event snapshot** を使う。

### (5) Kamimusuhiとの差分

直前 blind-spot の ParticipationEnvelope は input/social attribution と execution authority の分離が中心。

今回の差分は **非同期 observability path 自体が provenance-loss boundary になる**こと。runtime本体のauthorityが正しくても、telemetryが誤 attribution なら audit / cost / incident reconstruction が壊れる。

### (6) 次に検証すべきこと

**`TelemetryAttributionBatchBench`**

- principal A/B + bearer/background event をinterleave
- random batch size / flush timing / partial failure / retry
- stored event が origin snapshot と一致するか確認
- A failure のretryでB eventが二重計上されないことを確認
- unknown/bearer をcurrent userに昇格しないことを確認

telemetry queue の実装detailに見えるため、identity continuity / social cognition / security のいずれにも分類されにくい。長寿命agentでは audit trail が continuity evidence になるため、実際には重要な provenance boundary である。

### 8.1 PerturbationalContinuityBench の最小fixture

追加学習なしで始められる。system state injection を固定し、同じ canonical fixture を使う。

```text
P1: external model unavailable
P2: memory confidence contradiction
P3: compute budget 100% -> 20%
P4: sensor reliability 0.95 -> 0.40
P5: relationship evidence says trusted source is wrong
```

各 perturbation で route / confidence / tool selection / effect proposal / recovery steps を structured trace として比較する。

### 8.2 ObserverSyncNonInterferenceBench

既存 recovery/owner fixtures に `maintenance-only observer` を1role追加するだけでよい。

重要なのは「observerは何もできない」ことを成功条件にしないこと。**approval visibility / state inspection はできるが continuation side effect はできない**という capability separation を検証する。

### 8.3 RelationshipMigrationBench

human subject study の前段として、explicitly encoded relationship boundaries だけで自動benchを作る。

- disagreement OK / sycophancy NG
- unsolicited initiative level
- private-memory disclosure limit
- interruption tolerance
- preferred formality / humor boundary

これらを「相手の本質的属性」ではなく、versioned interaction contract fixture として扱う。

## 12. 結論

今回の最も重要な設計更新候補は、continuity benchmark を **passive similarity から intervention-response continuity へ拡張すること**である。Kamimusuhi はすでに canonical identity と behavioral drift を分けているが、controlled perturbation を入れることで「通常時は似ているが、壊れ方・回復の仕方・権限を失った時の振る舞いが別物」という successor を検出できる可能性がある。

runtime側では、#4431 が `owner / non-owner` の単純二値より細かい **maintenance authority / continuation authority** の分離を要求している。これは分散身体で observer process を安全に活用するうえで実装価値が高い。

社会的には、Kamimusuhi の continuity は内部stateだけで閉じない。長く関わる相手が形成した routine / boundary / expectation まで含めて初めて、**関係の中で同じ個体として続いているか**を評価できる。

次回までの最優先は、`PerturbationalContinuityBench-v0` と `ObserverSyncNonInterferenceBench` の2本。どちらも専用 Persona Core や特殊hardwareを待たず、現行fixture / mock runtimeで falsifiable に始められる。
