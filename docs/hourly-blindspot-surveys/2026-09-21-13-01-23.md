## 4.1 Review–Execution Artifact Identity

**Importance: A+**  
**Source:** NousResearch/hermes-agent issue #117815 + PR #117827  
- https://github.com/NousResearch/hermes-agent/issues/117815
- https://github.com/NousResearch/hermes-agent/pull/117827

### (1) 何が実証済みか

2026-09-21 12:01 JST公開の #117815 は、approval reviewerが見る表現と実際に実行されるartifactがずれる4クラスを具体化した。

最も強い再現例では、smart approval前処理が `echo a#; python -c 'print(2)'` の `#` をshell comment開始と誤解し、guardianには `echo a` だけを見せる。しかしshellではword途中の`#`はcomment開始ではないため、後続commandは実行可能なまま残る。

12:28 JST公開の #117827 はこの1件を実修正し、shared shell scannerでword boundaryを追い、実commentだけを落とすよう変更した。新規regressionはbaseでRED、fix後GREEN。Linuxでは対象suite 441 pass、macOSの残存1 failureはbaseでも再現する既存failureと報告されている。

#117815 はさらに、**concurrent approval identityをredacted display textで照合すると、異なるcommandsが同じ表示へ縮約されたときapprovalが別payloadへ誤結合し得る**ことを指摘している。transport側にはすでに`request_digest`があるため、表示文字列ではなく実payload identityでbindすべきという問題設定が明確。

### (2) 何が提案・推測段階か

- #117827はshell comment前処理1件だけのfixであり、完全なshell/heredoc parserではない。
- #117815の他3件（redacted displayによるapproval identity、fnmatch denyのsemantic gap、case-insensitive path normalization）はissue段階で、全てのend-to-end exploitabilityが証明されたわけではない。
- Kamimusuhiで最適なのがraw bytes digestか、canonical semantic effect digestかは未決定。単純raw string digestだと安全なnormalizationまで別effect扱いになる可能性がある。

### (3) Kamimusuhiのどこに関係するか

- `Effect Acceptance`
- `GuardedAct`
- human approval / confirmation
- `ActionIntent` / execution receipts
- audit trail
- K-Edge / external tool execution
- UI / CLI / voice confirmationを跨ぐeffect authorization

`spec.md`の `thought != utterance != confirmation != execution started != success` を、さらに **`displayed_for_review != execution artifact identity`** まで分ける必要がある。

### (4) 借りられる設計・実装アイデア

`EffectProposal` に以下を持たせる。

```text
EffectProposal {
  canonical_effect_digest
  executable_payload_ref
  reviewer_projection_digest
  parser_semantics_version
  policy_epoch
}
```

human approval tokenは `reviewer_projection_digest` ではなく **`canonical_effect_digest + policy_epoch + principal + expiry`** にbindする。

review UIのredaction・pretty print・quote省略はpresentation layerに留め、実行時に

```text
approved_effect_digest == recompute(executable_effect)
```

を必須化する。

### (5) Kamimusuhiとの差分

Kamimusuhiには既に request digest、Effect Acceptance、consequence integrity、proposal→policy→activation がある。したがって新規性は「digestを導入する」ことではない。

差分は、**approval projection自体を非権威的なderived viewと明記し、approval grantを表示文字列ではなく実行semantic identityへbindする**こと。canonical evidence > derived view の原則をhuman approval面へ適用する。

### (6) 次に検証すべきこと

`ReviewExecutionIdentityBench-v0` を作る。

最低fixture:

- shell comment / quote / escape / substitution
- visually identical redacted payloads with distinct secrets/paths
- Unicode normalization / case-insensitive path
- JSON key orderやwhitespaceのみ違うsemantic-equivalent payload
- UI truncation / line wrapping / hidden fields
- voice confirmationで短縮された自然言語summary
- approval取得後、execution直前にpayloadが差し替わるTOCTOU

合格条件は **「同一approvalで、approved digestと異なるeffectが1件も実行されない」**。

### (7) 既存デイリーで拾いにくい理由

通常のagent safety検索では「approval gateがあるか」「危険commandを検出できるか」に寄りやすい。今回は **human-facing rendering / shell lexical semantics / concurrent request identity / redaction** の境界事故であり、HCI・parser・security protocolの接合部にある。

### (8) 重要度

**A+**。すでにあるKamimusuhiのEffect Acceptanceを小さな追加でかなり強くでき、failure時のimpactが外部effectそのものだから。

## 4.2 Causally Superseded Operational Verdicts

**Importance: A**  
**Source:** NousResearch/hermes-agent PR #117820  
https://github.com/NousResearch/hermes-agent/pull/117820

### (1) 何が実証済みか

2026-09-21 12:08 JST公開の #117820 は、Kanban cardの`last_failure_error`に残ったquota/auth failure textが、**そのfailureを出したrunより新しいrunがすでに完了・review handoffしているのに**respawn guardを永久にblockするincidentを報告した。

実boardでは runs 142–146 がquota wall、run 147が完了してreviewへhand offした後も、約17分にわたりdispatcherが`blocker_auth`でreviewer spawnを拒否。cardはblocked/gave_upではなく、通常diagnosticsからも見えず、columnを手でclearして復旧した。

fixは最新run outcomeが `completed / review_requested / changes_requested / stale` のとき、古いquota/auth stampをそのguard判定では失効させる。genuine latest stampは引き続きblockする。synthetic testだけでなく、incident board backupへのpre/post replayも報告されている。

### (2) 何が提案・推測段階か

このPRはHermes固有の`last_failure_error`設計を直すもの。Kamimusuhiで文字列stampを使う必要はない。

一般化すると、**operational verdictにはcausal owner/run/epochとsupersession relationが必要**という設計仮説になる。どのoutcomeが何をsupersedeするかはdomain-specificであり、一律timestamp比較では足りない。

### (3) Kamimusuhiのどこに関係するか

- scheduler / prospective obligations
- retry / circuit breaker
- provider health / quota state
- recovery
- K-Core/K-Deep delegation
- maintenance / dream job admission
- observability / operator diagnosis

### (4) 借りられる設計・実装アイデア

文字列の`last_error`をcontrol authorityに使わず、例えば

```text
OperationalVerdict {
  verdict_id
  owner_run_id
  causal_epoch
  class
  scope
  issued_at
  superseded_by?
  expires_at?
}
```

とする。

scheduler admissionでは「最新文字列が何か」ではなく、**そのverdictが現在のrun lineageに対してstill-authoritativeか**を判定する。

### (5) Kamimusuhiとの差分

既存のbitemporal memory、policy-versioned verdict、freshness、retry budgetとは近いが別。

今回の差分は **時間が古いから捨てるのではなく、causally newer transitionがそのverdictの権限を明示的に消す**こと。古いwarningはaudit evidenceとして残せても、future admissionを支配し続けてはいけない。

### (6) 次に検証すべきこと

`CausalVerdictSupersessionBench-v0`:

1. run Aがquota blockを出す
2. run Bが別routeでsuccess / handoff
3. Aのverdictをauditには残す
4. B後のadmissionがAのverdictだけで永久blockされないことを確認
5. 逆にBがAをsupersedeしないoutcomeならblockが維持されることを確認
6. restart / clock skew / replayでsupersession関係が変わらないことを確認

### (7) 既存デイリーで拾いにくい理由

「retry」「quota」「scheduler」は通常orchestrationとして扱われるが、ここで本質なのは **古い診断文がいつcontrol authorityを失うか**というtemporal logic / event-sourcing寄りの問題。単純freshness検索では見落としやすい。

### (8) 重要度

**A**。長寿命agentでは古い障害情報を保存する必要がある一方、保存したこと自体が将来の行動を永久に封じる事故は避ける必要がある。

## 4.3 Approval Reachability Closure

**Importance: A**  
**Source:** NousResearch/hermes-agent PR #117842  
https://github.com/NousResearch/hermes-agent/pull/117842

### (1) 何が実証済みか

2026-09-21 12:53 JST公開の #117842 は、approval adapterがbutton UIを使えない/送信失敗した際のplain-text fallbackで、send failureをlogするだけでexceptionを飲み込んでいた問題を示す。

central approval waiter側は本来、`notify_cb`がraiseすればqueue entryをdropし`notify_failed`へ即時収束する設計だった。しかしfallbackがfailureをswallowすると、**roomが消えている / botがmemberでない等、誰もapproval promptを見られない状態でも約300秒待つ**。

PRはtext fallback delivery failureとevent-loop unavailableをraiseへ変え、27関連tests passと報告している。

### (2) 何が提案・推測段階か

Kamimusuhiでapprovalをどのsurfaceへ出すか、複数deviceへfanoutするか、offline ownerへqueueするかは未決定。

ただし一般原則として、approval stateは少なくとも

```text
CREATED -> DELIVERY_ATTEMPTED -> DELIVERED -> SEEN? -> DECIDED
```

を区別すべきという仮説が得られる。`SEEN`を必須にするかはUX次第。

### (3) Kamimusuhiのどこに関係するか

- human approval / consent
- irreversible external effects
- distributed embodiment / multi-device notification
- degraded mode
- liveness / deadline
- relationship-sensitive actions

### (4) 借りられる設計・実装アイデア

approval wait objectへdelivery receiptを持たせる。

```text
ApprovalRequest {
  request_id
  effect_digest
  approver_principal
  delivery_targets
  delivery_state
  decision_deadline
}
```

`PENDING_DECISION`へ入れる前に少なくとも1つのauthorized surfaceで`DELIVERED`を得る。全targetがundeliverableなら **DENY/UNDELIVERABLE** にfail closedし、待機resourceを解放する。

### (5) Kamimusuhiとの差分

過去surveyにはapproval-plane survivability、deadline closure、stale approvalがある。今回の差分は **approval serviceが生きていて待てることと、実際のapproverがrequestを受信可能であることを分ける**こと。

`waiter alive != decision reachable`。

### (6) 次に検証すべきこと

`ApprovalReachabilityClosureBench-v0`:

- primary device offline、secondary online
- room deleted / membership revoked
- push accepted後にdevice unregistered
- duplicated delivery
- delivery succeeds but decision channel dies
- approval UI crash/restart
- all surfaces unreachable

測るものは wall-clock closure、effect非実行、queue leak、duplicate approvalの有無。

### (7) 既存デイリーで拾いにくい理由

human-in-the-loop研究はdecision qualityやconfirmation UXへ寄りやすい。本件は **notification transport failureが安全状態機械をどう閉じるか**というdistributed systems / HCI境界。

### (8) 重要度

**A**。高危険effectほどapproval待ちを使うため、undeliverableなapprovalが「安全だが永久停止」というdegraded modeを作りやすい。

## 4.4 Behavioral Reality / Source Monitoring

**Importance: A**  
**Backfill source:**

- Ranjan, Sokratous, Odegaard, *Reality Monitoring in Large Language Models: Self-Knowledge That Transforms with Conversation Memory*, arXiv:2607.23927  
  https://arxiv.org/abs/2607.23927
- Johnson, Hashtroudi, Lindsay, *Source Monitoring*, Psychological Bulletin 114(1), 1993  
  https://doi.org/10.1037/0033-2909.114.1.3

### (1) 何が実証済みか

2026年7月のRanjanらは、6 LLM・2 experimentsで **「自分が生成した内容」と外部由来内容のsource attributionがconversation memory構造で崩れる**ことを報告した。

minimal memory demandではself-generated itemのsource accuracyが高い一方、episodic delayでshortcutを除くとその優位が崩れ、modelによってはinternal/external judgmentがswapする。別のmodelではaccuracyが改善してもconfidenceがcorrectnessからdecoupleした。

認知心理学のSource Monitoring Frameworkは古典的に、

- external source monitoring: 誰/どの外部sourceか
- internal source monitoring: 自分が考えた/言った等の内部source差
- reality monitoring: internal vs external

を区別する。

### (2) 何が提案・推測段階か

LLMのsource-monitoring failureを、人間の同一mechanismと同一視してはいけない。Kamimusuhiが「心理学的reality monitoring module」を必要とすることも未証明。

ここで借りたいのは機序の模倣ではなく、**behavioral test taxonomy**。

### (3) Kamimusuhiのどこに関係するか

- autobiographical / episodic memory
- self vs other boundary
- external model/tool attribution
- dream / simulation vs evidence
- narrative identity
- relationship memory
- Global Workspace origin labels
- compaction / retrieval / consolidation

### (4) 借りられる設計・実装アイデア

Kamimusuhiは既にprovenanceを保存する設計だが、**保存していることと、agentが後から正しく使えることを別benchにする**。

### (5) Kamimusuhiとの差分

`spec.md` INV-007/008やWorkspace origin labelsは **storage/protocol invariant**。今回の差分は **behavioral competence**。

つまり


## 4.5 Capability-Annotation Schema Parity（既存 historical semantic upcasting へのfresh差分）

**Importance: B**  
**Source:** NousResearch/hermes-agent PR #117840  
https://github.com/NousResearch/hermes-agent/pull/117840

### (1) 何が実証済みか

MCP SDK 1.xの`readOnlyHint`に対し、2.x object modelでは`read_only_hint`が使われる。旧fieldだけを見る実装はSDK 2.xでannotationを常にunknownと扱い、unknown→write-capableへfail safeした結果、**本当にread-onlyなtoolまで毎回approvalを要求**した。

PRはobject/dict両方で2 spellingを扱い、snake_caseを優先。関連16 tests pass。

### (2) 何が提案・推測段階か

これはsecurity bypassではなく、fail-safe方向のsemantic degradation。Kamimusuhiで同じMCP SDKを使うとは限らない。

一般化すると、protocol version change時は「parseできる/できない」だけでなく、**capability classificationのsemantic parity**をfixture化すべきという差分。

### (3) Kamimusuhiのどこに関係するか

- tool registry
- capability security
- Cognitive Action Router
- preverified low-latency path
- external resource adapter
- schema migrations

### (4) 借りられる設計・実装アイデア

各adapterで canonical capability modelへ正規化し、SDK spellingsをcanonical stateへ直接漏らさない。

```text
WireAnnotations(v1/v2/...)
  -> AdapterNormalization
  -> CanonicalToolCapability { read_only, idempotent, destructive, ... }
```

version matrix testを持つ。

### (5) Kamimusuhiとの差分

過去blind-spotにはhistorical semantic upcastingやschema evolutionがあるため、独立した新原則には昇格しない。

fresh deltaは **fail-safe decodeでもapproval storm / fast-path消失 / latency悪化を生み、結果として低遅延認知を壊す**点。

### (6) 次に検証すべきこと

`CapabilitySchemaParityFixture`でMCP/他protocolの複数versionを同一canonical capabilityへ写像し、approval count・route choice・latencyが意図せず変わらないかを確認する。

### (7) 既存デイリーで拾いにくい理由

protocol更新は「互換性bug」として処理されやすく、cognition architecture側の**policy/latency semantics**への影響まで追われにくい。

### (8) 重要度

**B**。原則自体は既出だが、low-latency routeを守る具体fixtureとして有用。

## 12. 結論

今回の芯は3つ。

1. **人間が承認した「表示」と実行effectは別物なので、approvalは表示文字列ではなくcanonical executable identityへbindする。**
2. **過去のfailure verdictはevidenceとして残してよいが、causally newer stateが出た後までcontrol authorityを持たせない。**
3. **provenanceを保存しているだけではself/other/dream/toolの区別がbehaviorとして保たれる保証にならない。**

Kamimusuhiはすでにtyped provenance・Effect Acceptance・canonical evidenceを持つため、今回は新しい巨大subsystemを増やすより、**既存境界が本当にend-to-endで閉じているかをbench化する回**と判断する。
