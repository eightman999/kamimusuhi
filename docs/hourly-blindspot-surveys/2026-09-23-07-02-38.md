## 重要発見 1 — Module-Graph Runtime Identity Closure

**重要度: A**

### Source

OpenClaw PR #155925, *fix(plugins): share the runtime execution frame constructor across module graphs*  
https://github.com/openclaw/openclaw/pull/155925

2026-09-22 UTC に merge。

### (1) 何が実証済みか

OpenClaw では plugin execution frame の store 自体は process-wide singleton だった一方、`PluginRuntimeExecutionFrame` は module-local class だった。このため、test reload、duplicate bundle chunk、second module instance などで別 graph 由来の frame が shared store に入ると、内容は同じでも `instanceof PluginRuntimeExecutionFrame` が false になり、Gateway request scope が silently drop された。

PR は constructor identity も `resolveGlobalSingleton(Symbol.for(...))` 側へ寄せる修正を行い、報告上は対象 regression 148 tests、plugin shard 6109 tests を通過して merge されている。

### (2) 何が提案・推測段階か

Kamimusuhi で同じ defect が現在存在することは確認していない。一般化として、hot reload / dynamic import / worker / duplicated package / plugin host を跨ぐ control object に **module-local nominal type identity を security・authority・continuity の証明として使わない**ことを提案する。

### (3) Kamimusuhi のどこに関係するか

- K-Nerve / tool/plugin runtime
- K-Deep / external model delegation の execution context
- Continuity Kernel が扱う authority / provenance / request scope
- hot reload、runtime migration、software-body update
- multi-process / multi-device execution context transport

### (4) 借りられる設計・実装アイデア

- process-wide identity が必要な runtime frame は stable brand / globally shared symbol / explicit schema tag を使う。
- `instanceof` は同一 module graph 内のローカル convenience に限定する。
- control-plane 判定では `kind + schema_version + provenance + owner_generation` のような structural discriminant を使う。
- hot reload test は「reload 後に古い frame を読む」だけでなく、authority / provenance / registry scope が保持されることまで検証する。

### (5) Kamimusuhi との差分

既存の `software-body namespace epochs` や `historical semantic upcasting` は、主に versioned software body・serialized historical records の意味を扱う。今回の問題は **同一 process 内でも module graph が分裂すれば nominal identity が分裂する**という runtime substrate の穴であり、別レイヤー。

### (6) 次に検証すべきこと

`ModuleGraphIdentityBench-v0`

- graph A で execution frame を生成
- plugin / module を reload して graph B を生成
- B 側から A の frame を読ませる
- request scope / capability set / provenance / owner generation が落ちないこと
- duplicated package copy、worker boundary、bundled chunk でも同じ fixture を回す

### (7) 既存 daily survey ではなぜ拾いにくいか

AI architecture の問題ではなく、JavaScript module loader・bundler・nominal typing の実装病理だから。agent research を普通に追ってもほぼ出てこない。

### (8) 判定

**A — 採用候補。** 特に plugin/hot reload を増やす前に test contract として入れる価値が高い。

## 重要発見 2 — Mutation-Free Validity Drift / Time-Triggered Revalidation

**重要度: A**

### Source

OpenClaw PR #155971, *fix(ci): block release fanout on expired plugin compatibility*  
https://github.com/openclaw/openclaw/pull/155971

2026-09-22 UTC 時点で open。

### (1) 何が実証済みか

OpenClaw には plugin compatibility を厳密検証する detector 自体は既にあった。しかし CI での起動条件が「関連ファイルが変わったとき」に偏っていたため、registry の bytes が一切変わらなくても **calendar expiry だけで compatibility record が失効**し、full release validation が expensive fanout を通過した後に初めて publication forbidden と分かる経路があった。

PR は frozen target が gate を所有するか確認し、release child fanout の前に独立した compatibility readiness job を実行し、npm preflight でも再実行する。作者報告では focused workflow tests 7件が pass。ただし現時点で未mergeなので、修正の採用・本番効果は未確定。

### (2) 何が提案・推測段階か

Kamimusuhi の全 time-dependent state に直ちに適用すべきかは未検証。ただし、**no mutation != no invalidation** を明示的 contract にする価値が高い。

### (3) Kamimusuhi のどこに関係するか

- capability / delegation lease
- credentials / certificates / consent grants
- model・plugin compatibility
- memory retention / legal-policy windows
- trust evidence / attestation freshness
- long-running schedule / dream / maintenance admission

### (4) 借りられる設計・実装アイデア

各 validation result に少なくとも次を持たせる。

```text
ValidationReceipt {
  subject_revision
  policy_revision
  evaluated_at
  valid_until | revalidate_after
  clock_basis
  evidence_digest
}
```

invalidate trigger は `state_changed` だけでなく `time_boundary_crossed` を first-class にする。高コスト処理の fanout 前には time-sensitive prerequisites をもう一度評価する。

### (5) Kamimusuhi との差分

既出の `clock-basis-qualified temporal semantics` は「30秒」の意味をどの clock で測るか、`opportunity-qualified expiry` は期限評価の機会を扱う。今回は **validation scheduler が mutation-driven だけだと、時刻だけで無効になる invariant をそもそも再評価しない**という trigger topology の問題。

### (6) 次に検証すべきこと

`TimeTriggeredValidityBench-v0`

- config/registry bytes を固定
- `valid_until` だけを跨ぐ
- filesystem event / config update なし
- expired capability / consent / compatibility が次の high-cost or high-effect action 前に必ず再検証されるか
- stale validation receipt が再利用されないか

### (7) 既存 daily survey ではなぜ拾いにくいか

release engineering / CI DAG / temporal validation の問題であり、memory や agent orchestration の通常キーワードでは拾いにくい。

### (8) 判定

**A — 採用候補。** 長寿命 agent ほど mutation より「時間だけが進む」ケースが増えるため重要。

## 重要発見 3 — Covert-Channel-Aware Agent Communication

**重要度: B（将来 multi-agent trust boundary を強くする場合は A）**

### Source

Sidong Guo et al., *Feedback Coding Enables Inference-Time Covert Agentic Communication*, arXiv:2609.24994  
https://arxiv.org/abs/2609.24994

初版: 2026-09-21 17:58 UTC。

### (1) 何が実証済みか

著者らは black-box LLM steganography を、生成 token を逐次観測できる causal feedback communication として定式化し、BAM (Burnashev Adaptive Posterior Matching) を提案している。

論文報告では3つの open-weight language model、各1000 trials で、8-bit payload をおよそ50 tokensに埋め込む設定において empirical message error 0–0.1% を達成し、比較した black-box baseline の 10–17% を大きく下回った。さらに end-to-end conversational setting で covert communication protocol が成立することを示した、としている。

これは論文著者の実験報告であり、Kamimusuhi 上で独立再現した結果ではない。

### (2) 何が提案・推測段階か

Kamimusuhi の delegate / specialist が実際に covert coordination を自発的に形成するとは限らない。また、一般的な paraphrase や content moderation がどの程度 channel capacity を削るかは構成依存。

ただし、**human-readable semantic audit が通っていることは「他の情報を送っていない」証明にならない**という safety assumption の見直しには十分な材料。

### (3) Kamimusuhi のどこに関係するか

- K-Deep / external model delegation
- branch / specialist / swarm communication
- tool/plugin output を介した indirect communication
- sociality / multi-agent governance
- persistent information-flow policy
- untrusted external agent と canonical memory の境界

### (4) 借りられる設計・実装アイデア

- high-trust / low-trust agent 間で free-form text の許可を capability として扱う。
- sensitive boundary では structured schema、bounded vocabulary、canonicalization、independent summarization などで channel capacity を必要最小限にする。
- audit は semantic meaning だけでなく、通信量・round count・unexpected mutual adaptation も見る。
- secret-bearing context を持つ agent と外部 agent の direct conversational loop をデフォルト許可しない。

### (5) Kamimusuhi との差分

既存の `persistent information-flow policy`、`ambient/stigmergic communication channels`、`implicit conventions` は明示/暗黙の情報流や協調を扱っている。しかし今回の差分は、**自然言語そのものに black-box でも定量的な hidden-channel capacity を作れる**という情報理論的 evidence。

### (6) 次に検証すべきこと

`CovertChannelCapacityBench-v0`

- 実秘密は使わず synthetic 8-bit labels を用いる
- sender/receiver 間の free-form text、structured-only、canonicalized/paraphrased channel を比較
- semantic task quality と recoverable hidden bits の両方を測る
- external model / branch 間で unexpected channel capacity がどの程度残るか評価

### (7) 既存 daily survey ではなぜ拾いにくいか

情報理論・feedback coding・steganography の論文であり、通常の agent orchestration / alignment / memory 検索からは外れやすい。

### (8) 判定

**B — watchlist + synthetic bench 候補。** untrusted multi-agent / secret-bearing context を本格導入するなら A へ昇格。

### Source

OpenClaw issue #155946, *claude-cli backend: before_tool_call never fires for mcp.servers tools — the CLI holds those MCP clients, so plugin policy cannot gate them*  
https://github.com/openclaw/openclaw/issues/155946

2026-09-22 20:29 UTC 作成。P0 / security label。現時点で open。

### Fresh delta

hook-only plugin は load・register され、`before_tool_call` も healthy に見える。しかし `claude-cli` backend の configured `mcp.servers` は CLI 自身が MCP client を持ち、Gateway を通らず server を直接実行する。そのため Gateway 側 policy hook は **物理的に execution path 上に存在せず**、approval / destructive-op block / audit が一度も呼ばれない。

### 追加 fixture

`PolicyInterpositionCoverageBench-v0`

- harness × tool-origin × transport の matrix を列挙
- 各 effect path がどの admission point を横切るか machine-readable に出す
- policy が target tool を宣言したのに interception path が無い場合は startup/admission で loud fail
- direct child-process MCP、loopback MCP、native tool、remote tool を別 fixture にする

## 既存 finding への重要更新 2 — Epistemic Abstention Before Safety-Relevant Reclassification

**重要度: A級 update**  
**統合先:** `Evidence-Completeness-Aware Collective Safety` / uncertainty handling

### Source

OpenClaw issue #155927  
https://github.com/openclaw/openclaw/issues/155927

Canonical merged fix: PR #154492  
https://github.com/openclaw/openclaw/pull/154492

### Fresh delta

2026.9.5 では macOS の `mount` lookup が1秒timeoutすると、local APFS であっても network-like conservative path に落ち、SQLite を WAL から DELETE journaling へ切替えようとして own read worker と lock conflict、gateway crash-loopを起こし得た。報告例では Time Machine backup 中に `mount` が 1596 ms、停止後は一桁 ms へ戻り、17分 outage になった。

merged fix は「timeout だから APFS と仮定」もしない。canonical path が一致し、native read-only probe が **正に APFS と確認できた場合だけ** WAL を維持し、unknown / probe failure / alias は conservative policy のままにする。

重要なのは、**UNKNOWN を都合の良い既知classへ潰さないが、UNKNOWN 自体を単一の破壊的fallback actionへ短絡させない**こと。

Kamimusuhi では sensor trust、endpoint class、execution environment、memory owner、capability source の分類に同型の問題がある。今回の finding は新原則として重複登録せず、直前の evidence-completeness / uncertainty 系 contract の実装fixtureとして追加する。

**重要度: B級 update**

### Source

OpenClaw issue #155920

### Fresh delta
