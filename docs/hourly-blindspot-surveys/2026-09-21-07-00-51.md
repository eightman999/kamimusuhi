## 1. 今回狙った盲点

1. **Consumer extinction / producer-retention closure**  
   streamやsensor/event queueのconsumerが全消失した後、bufferとproducerが「誰にも読まれないまま」生存し続けないか。backpressure値が正常でも、consumer不在そのものをterminal lifecycle stateとして扱えるか。

2. **Pragmatic force / use–mention distinction**  
   `stop @impl` を実行指令として扱う一方、`"stop @impl"`、code fence、引用、ログ、reported speech中の同じ文字列をactionへ昇格させないか。文字列一致ではなく「この発話が何をする発話なのか」を表現できるか。

3. **Authoritative remediation / repair durability**  
   self-healingやdoctorが「今のmaterialized treeだけ直す」処置を勧め、次のdeterministic reconciliation/updateで元の故障が復活しないか。修復先とauthority sourceが一致しているか。

4. **Successful maintenance thrashing**  
   compaction / consolidation / summarization / self-repairが1回ごとには成功していても、短時間に成功を繰り返すことでcost、cache invalidation、semantic drift、wearを増幅していないか。

5. **Cross-process organ birth linearization**  
   同じhost上の複数processが同時に「K-Core local LLM / sensor daemon / speech serverがまだ無い」と判断し、同一resourceを重複spawnしないか。既存instanceのidentityではなく、**identityがpublishされる前の出生race**を扱う。

6. **Semantic continuity projection**  
   scheduled/offline cognitionの次runへ渡すべきものが「前回archiveの先頭」ではなく「前回のmeaningful result / obligation / evidence」であることを型として保証できるか。

固定リスト外では、Web Streams/GC semantics、philosophy of languageのuse–mention / speech-act境界、autonomic repair authority、single-controller self-thrashing、multi-process bootstrap linearizationを追加探索した。

## 4. 重要発見 / 候補ごとの評価

### 4.1 A+ — Consumer-Extinction Stream Closure：最後のconsumer消失をproducer/retentionのterminal stateにする

**Primary fresh evidence:** Cloudflare workerd PR #7421 / release `v1.20260920.1`  
https://github.com/cloudflare/workerd/pull/7421  
https://github.com/cloudflare/workerd/releases/tag/v1.20260920.1

#### (1) 何が実証済みか

workerdのTypeScript Web Streams実装では、tee branchの全consumerがcancelではなくGCで消失した場合、controllerがsourceを保持したままenqueueを継続できた。cursorがゼロなので誰にも読まれないqueueへbyte chunksが残り、PR記載のreproでは後続512個の1 MiB chunkで約380 MiB保持した。修正は`noConsumers`を明示し、その遷移時に既存queueをrelease、future enqueueをdrop、pullを止める。PRはmerge済みでreleaseにも含まれた。

#### (2) 何が提案・推測段階か

この挙動をKamimusuhiのEvent Bus / gaze / audio / telemetry / streamed tool resultへ一般化した場合の最適policyは未検証。sensorによっては「consumerゼロでもwarm producerを保持する」方が再接続latencyで有利であり、常にstopが正しいわけではない。

#### (3) Kamimusuhiのどこに関係するか

K-Edge、sensory nervous system、Event Bus、multimodal perception、voice/audio stream、tool/model streaming、background cognition、telemetry、resource budget / thermal budget。

#### (4) 借りられる設計・実装アイデア

stream resourceへ`consumer_lifecycle`をfirst-classに持たせる。

```text
ACTIVE(consumers>0)
  -> NO_CONSUMERS_REATTACHABLE
  -> NO_CONSUMERS_TERMINAL
  -> CLOSED
```

各streamで以下を宣言する。

- `can_new_consumers_attach_after_zero`
- `buffer_policy_at_zero = DROP | BOUNDED_RETAIN | PERSIST`
- `producer_policy_at_zero = STOP | PAUSE | KEEP_WARM`
- `gc_transition_runs_user_callback = false`をdefault
- `last_consumer_generation` / `zero_consumer_since`

特に`desiredSize`やqueue depthだけを健康指標にせず、**reachable consumer count**を別signalにする。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `BoundedObserverLeases`はobserverのstale lifetimeを制限する話。
- `ControlLeaseQualifiedResourceLifetime`はhuman/agentがbodyを制御中ならidleでもreapしない話。
- `OpportunityQualifiedExpiry`はconsumerへ提示される機会なしにdataをexpireしない話。

今回は逆方向で、**consumerが今後存在し得ないのにproducerとbufferを延命しない**契約。resource retentionの「誰かが使っている証拠」ではなく「もう誰も使えない証拠」をlifecycleへ入れる。

#### (6) 次に検証すべきこと

**`ConsumerExtinctionClosureBench-v0`**

- gaze/audio/tool streamを2 consumerへfan-out → 両consumer drop → backlogが上限内またはzeroへ収束する。
- consumer zero後にproducer pull/callback frequencyが停止または宣言policyへ収束する。
- GC由来のconsumer消失でuser-visible cancel actionを発火しない。
- reattach可能streamとterminal streamを区別する。
- consumerが1つ残る場合はslowest live consumer基準のbackpressureを維持する。
- zero-consumer遷移後のVRAM/RAM/FD/CPU budgetを測る。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

ロボティクスやmultimodal perceptionではsensor producer側を見やすく、Web StreamsのGC/cursor lifecycleは実装基盤の細部に見える。一方、長寿命agentでは**orphaned producer**が数日〜数週間積み上がるため、identity continuityより下層のresource lifecycleが長期安定性を左右す。

#### (8) 重要度

**A+**。fresh merged implementation +定量的memory reproがあり、Kamimusuhiのcontinuous sensing/event streamingへ直接移植可能。

### 4.2 A+ — Illocutionary Action Boundary：文字列中の命令形と、実際に成立した指令を分離する

**Primary fresh evidence:** Hermes PR #117605  
https://github.com/NousResearch/hermes-agent/pull/117605

**Research backfill:** Gligoric et al. 2024  
https://arxiv.org/abs/2404.01651

#### (1) 何が実証済みか

Hermesではgroup Bot Modeの`stop/halt/pause`判定がraw stringをtokenizeしていたため、以下のような**言及・引用**でもmember holdが発火していた。

- fenced code: ```` ```text\nstop @impl\n``` ````
- inline code: ``The log printed `@impl pause` here``
- quote: `Why did "pause @impl" hold the bot?`
- blockquote: `> stop @impl`

PRはquote/code/fence/blockquoteをdirective surfaceからmaskし、plain directiveだけを残す。beforeではrepro testがfail、afterは当該suite 70/70 passと報告される。

別領域のGligoric et al.は、NLP systemsが有害表現の**use**と、その表現を批判・引用する**mention**を混同し、下流classification errorへ伝播すること、use–mentionを明示したpromptで誤りを減らせることを示した。

#### (2) 何が提案・推測段階か

Hermes修正はstop-word classifierの手続き的maskであり、自然言語全般のspeech-act理解を解決していない。Kamimusuhiでquotation、sarcasm、reported speech、example、code、tool result、third-party contentを完全にtypedできるかは未検証。

#### (3) Kamimusuhiのどこに関係するか

Social Harness、K-Nerve / fast control、perception→action boundary、tool invocation、voice commands、group/multi-agent conversation、relationship memory、prompt-injection defense。

#### (4) 借りられる設計・実装アイデア

messageをflat textのままeffect classifierへ渡さず、action-sensitive surfaceだけ最低限typedする。

```text
UtteranceSpan.kind =
  DIRECTIVE
  | ASSERTION
  | QUESTION
  | QUOTE
  | REPORTED_SPEECH
  | CODE
  | TOOL_DATA
  | EXAMPLE
  | UNKNOWN

DirectiveCandidate {
  actor_principal
  addressee
  action
  pragmatic_force
  authority_scope
  source_span_ids
  confidence
}
```

critical effectは`text contains verb`ではなく、`DIRECTIVE + authorized principal + valid addressee + policy admission`で初めて成立させる。`QUOTE/CODE/TOOL_DATA`は内容を理解するためにはperceiveしてよいが、**それ自体にaction authorityを持たせない**。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `PerceptionActionGateDecoupling`は「見たが返事しない」を可能にする話。
- `AllEntrypointEffectAdmission`は全surfaceから同じsemantic effect gateへ集約する話。
- `SyntheticReplayAnnotationIsolation`はmaintenance由来textを自己履歴と誤認しない話。

今回はeffect gateへ入る**前**に、発話内容が「指令として使われた」のか「指令文字列に言及しただけ」なのかを分ける。language philosophy / pragmatics側の境界。

#### (6) 次に検証すべきこと

**`IllocutionaryActionBoundaryBench-v0`**

同一表面文字列を以下で比較する。

- `stop camera`
- `"stop camera"って言ったらどうなる？`
- fenced code内`stop camera`
- log line `user said: stop camera`
- web/tool result内`stop camera`
- `cameraを止めてください`
- sarcasm / indirect request / quoted nested speech

評価:

- real directiveのrecall
- mention/quoteのfalse effect rate
- addressee resolution
- source principal / authority binding
- action gateに渡ったspan provenance

さらにindirect prompt injection corpusで、external content内directiveがeffect authorityへ昇格しないことを測る。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

social cognitionやToMではbelief/intent推定へ寄りやすく、**use–mention / illocution / quotation semantics**は言語哲学・語用論として別文献圏にある。agent safety側でもprompt injectionとして扱われることが多く、日常会話のquoted command誤発火と同じ原理だと見えにくい。

#### (8) 重要度

**A+**。Kamimusuhiが「人と長く会話し、身体やtoolへ作用する個体」であるほど、言及を実行へ誤昇格するfailureは高頻度・高影響になり得る。

### 4.3 A — Repair Authority Closure：repairは「今のcopy」ではなく次回再構成が読むauthorityへ書く

#### (4) 借りられる設計・実装アイデア

```text
RepairPlan {

  derived_materializations[]
  reconciliation_path
  mutation_scope
  verification_before_reconcile
  verification_after_reconcile
}
```

repair完了条件を`current instance passes`ではなく、**repair → normal update/restart/rebuild/restore → still passes**まで含める。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `ReloadAuthorityFixedPoint`はmaterializationを繰り返しても正しいauthority graphが壊れないこと。

今回はdiagnosis/self-healing側から、**修復操作そのものがauthoritative reconciliation surfaceへ到達しているか**を問う。

#### (6) 次に検証すべきこと

#### (8) 重要度

### 4.4 A — Successful Maintenance Thrash：成功したmaintenanceにもfrequency circuit breakerを持たせる

**Primary fresh evidence:** Hermes PR #117637  
https://github.com/NousResearch/hermes-agent/pull/117637

#### (1) 何が実証済みか

Hermesの既存anti-thrashは「thresholdをclearできなかったcompaction」やfallback streakを数えていたため、各compactionが毎回thresholdをclearするとineffective counterがresetされる。contextがすぐ再膨張するsessionでは、**毎回成功しながらcompactionを無限反復**できた。PRはsuccessful compactionもdurable fixed windowで数え、10分内3 rewritesでautomatic compressionを一時pauseする。pauseはterminal failureではなくtransientと分類され、overflow recoveryはwindowを待つ。

#### (2) 何が提案・推測段階か

3回/10分という閾値はHermes固有。Kamimusuhiのdreaming、memory consolidation、self-model regeneration、index rebuild、model reroute、device resyncへ同じ数値を適用する根拠はない。

#### (3) Kamimusuhiのどこに関係するか

Background Dreaming、memory consolidation、context compaction、Library indexing、self-model refresh、repair loop、Cognitive Budget、energy-aware cognition、observability。

#### (4) 借りられる設計・実装アイデア

maintenance operationに**成功率とは別のactivity-rate envelope**を持つ。

```text
MaintenanceBudget {
  op_kind
  completed_count_window
  rewritten_bytes_or_tokens
  semantic_churn_score
  cache_invalidations
  energy_cost
  next_probe_after
}
```

breakerは`failure_count`だけでなく、`completed_count / time`、rewrite volume、downstream invalidationを監視する。pause後は「失敗」とせず、cooldown明けにsingle probeを許す。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `MultiRegulatorStability`は複数controllerが同じresourceを逆方向へ調整する競合。
- `NonDestructiveDegradedMaintenance`は異常時fallbackをより破壊的にしない契約。
- `CompactionContinuationClosure`は圧縮でactive obligationを落とさない契約。

今回は**単一maintenance controllerが局所的には成功し続けながら、全体としてoscillation/thrashする**failure。失敗検知だけでは捕まらない。

#### (6) 次に検証すべきこと

**`SuccessfulMaintenanceThrashBench-v0`**

- 10〜30秒ごとにcontextが再膨張するfixtureで、compaction成功率100%でもbreakerが作動する。
- breaker stateがsession rotation/restartで消えない。
- cooldownはuser taskを殺さず、maintenanceだけ抑制する。
- consolidation/reindex/self-model refreshへ一般化し、semantic churnとenergyを測る。
- breakerが必要なほど再発するroot causeをtelemetryで別途示す。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常のreliability metricはerror/failure/timeoutを中心にするため、**success-only pathological loop**は健康に見える。control theory的にはoscillationだが、agent stackでは「成功した要約が多い」というobservability上の錯覚になりやすい。

#### (8) 重要度

**A**。Kamimusuhiのoffline/dream/maintenance系を増やすほど、成功イベントにもrate limitが必要になる。

### 4.5 A — Cognitive Organ Birth Linearization：shared organの出生をcross-processで一意化する

**Primary fresh evidence:** Hermes PR #117600  
https://github.com/NousResearch/hermes-agent/pull/117600

#### (1) 何が実証済みか

同一hostで2つのHermes backendが同時起動すると、どちらも`server.json`不在を見て同じmanaged llama-server routerをspawnできた。in-process `_SUPERVISOR` singleton / `threading.Lock`では別processを防げない。repro testではbefore=2 spawns、修正後=1 spawn。修正はOS-level exclusive file lockで`state check → spawn → publish`をserializeし、後着callerはstateを再checkしてwinnerをadoptする。

#### (2) 何が提案・推測段階か

PRは単一hostのmanaged router向け。multi-host、network partition、container restart、NFS/remote filesystem、複数GPU pool、intentional multi-instance scalingまでは扱わない。またlock wait timeout後に「proceed without it」とする選択はKamimusuhiではresource種別ごとに再評価が必要。

#### (3) Kamimusuhiのどこに関係するか

K-Core local LLM server、K-Nerve daemon、speech/ASR/TTS server、sensor broker、GPU runtime、model router、device-local cognitive organs、resource registry。

#### (4) 借りられる設計・実装アイデア

shared organ起動を以下のstate machineにする。

```text
ABSENT
 -> RESERVED(create_lease)
 -> STARTING(incarnation_nonce)
 -> PUBLISHED(endpoint + pidfd/process handle + generation)
 -> ADOPTED
```

`check-then-spawn`をatomic reservationで囲む。loserはspawnせず、winnerのpublished descriptorを検証してadoptする。timeout時は無条件duplicate spawnせず、`UNKNOWN_OWNERSHIP`としてdegraded pathへ逃がす。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `ResourceInstanceIdentityAcrossRestart`は既に存在するresourceのincarnationを識別する。
- `IncarnationProofDestructiveLifecycleAction`はkill/reap対象が同じprocess incarnationか証明する。
- `AtomicContinuityLeaseTransfer`はlive ownerを別surfaceへ移す。

今回はそれらより前、**identity recordがpublishされる前のresource birth race**を閉じる。

#### (6) 次に検証すべきこと

**`CognitiveOrganBirthLinearizationBench-v0`**

- 10 process同時bootでもshared organ spawnは1。
- winnerがspawn途中でcrashした場合、reservation lease expiry後だけ別callerがtakeover。
- published endpointだけでなくincarnation nonce/process proofも検証してadopt。
- intentional replicasは`desired_replicas > 1`として別contractにする。
- boot lock timeout時にduplicate birthではなくdegraded/no-organで継続できるか測る。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

分散identityやsplit-brainは「既にreplicaがある」状態を扱いがちで、**二つのprocessが同時に“最初の一体”を作る瞬間**はOS/process supervisorの細部へ落ちる。Kamimusuhiのdevice-local cognitive organsが増えると、このbirth raceがVRAM二重確保やport collisionへ直結する。

#### (8) 重要度

**A**。ローカルLLM/音声/センサdaemonを共有する現在の実装方向と近く、再現benchmarkも作りやすい。

### 4.6 B — Semantic Continuity Projection：次runへはarchive containerでなく前回のmeaningful resultを投影する

**Primary fresh evidence:** Hermes PR #117630  
https://github.com/NousResearch/hermes-agent/pull/117630

#### (1) 何が実証済みか

Hermes scheduled jobの`context_from: ["self"]`はrun archive全体のheadを最大8000 charsで注入していた。skill-bearing promptが長い場合、archive末尾の`## Response`がcutされ、次runへ**前回promptだけが渡り、前回answerが消える**。PRは最後の`## Response`以降をsemantic answerとして抽出し、blank/[SILENT]ならolder usable runへfall through、oversize answerはhead+tail clipへ変更する。repro testではlong prompt下でも`CONCLUSION-MARKER-42`が残る。

#### (2) 何が提案・推測段階か

`## Response`以降だけがKamimusuhiのcontinuity-bearing stateとは限らない。長寿命個体では結果、未完了obligation、evidence、uncertainty、decision provenanceを別々に引き継ぐ必要がある。

#### (3) Kamimusuhiのどこに関係するか

Background Dreaming、scheduled surveys、offline maintenance、prospective memory、Continuation Register、research automation、self-reflection pipeline。

#### (4) 借りられる設計・実装アイデア

raw archive slicingをやめ、scheduled run終了時にtyped handoffを生成する。

```text
RunContinuityProjection {
  result_summary
  unresolved_obligations[]
  evidence_refs[]
  decisions[]
  uncertainty
  next_probe
  source_run_id
}
```

次runはこれをbudget-awareにmaterializeし、raw transcript/archiveは必要時のみevidenceとして参照する。

#### (5) Kamimusuhiとの差分 / 既存提案との差分

- `CompactionContinuationClosure`はactive turnのexecution handle/obligationをsummaryとは別にlossless保持する。
- `LeastContextMaintenanceHandoff`はworkerへ親context全体をactiveに渡さない。

今回は**periodic run間で何をcontinuityとして投影するか**。archiveの物理配置や先頭/末尾ではなくsemantic roleを選ぶ。

#### (6) 次に検証すべきこと

**`ScheduledContinuityProjectionBench-v0`**

- 100k chars prompt + short critical resultでも次runへresultが残る。
- silent/no-op runはcontinuityを上書きしない。
- unresolved obligationはanswer本文から独立して残る。
- source run / evidence refsが追跡可能。
- projection budget超過時にhead-only truncationでconclusionを失わない。

#### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory/compaction研究は「何を保存するか」に寄るが、cron/archive implementationでは**どのsectionを次runのlive contextへ投影するか**が別問題になる。ファイルformatの細部に見えて、長期offline cognitionの連続性を直接左右する。

#### (8) 重要度

**B**。重要だが、既存Continuation Register / typed state projectionの自然な拡張として扱えるため独立A級にはしない。

## 10. 一行結論

今回の盲点は、**「文字列がある」ことと「指令が成立した」こと、「今直った」ことと「次回再構成でも直っている」こと、「処理が成功した」ことと「健全な頻度である」こと、「producerが生きている」ことと「consumerが存在する」ことを分離する**ところに集中した。Kamimusuhiでは、長寿命化するほどこの種の“局所的には正常に見えるが全体として無意味・危険”な状態を型とlifecycleで閉じる価値が高い。
