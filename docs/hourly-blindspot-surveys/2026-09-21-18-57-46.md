## 2. 今回狙った盲点

通常dailyの分類だけでは見落としやすい、次の境界を重点的に探索した。

1. **request-local compatibility repair vs durable identity/memory** — あるproviderに送るためのlossy変換が、個体のcanonical historyへ逆流していないか。
2. **mutation locator vs mutation extent** — 「どこを対象にするかを見つける情報」と「どこまでを書き換えるか」が暗黙に混ざっていないか。
3. **economics/governance of cognitive escalation** — expensive / flagship / frontier cognitionへ上げるとき、理由・route・budgetを監査可能な形で残すか。
4. **graceful forgetting of working state** — live working setを小さくしても、canonical evidenceへ完全に戻れることを証明できるか。
5. **prompt/policy composition as a satisfiability problem** — 個々に正しいprompt fragmentが合成時に矛盾していないか。
6. **human oversight capability as a degrading system resource** — 長寿命agentが安全のため依存する人間の監督能力そのものが、agent利用によって劣化しないか。

今回は **有意な新規発見あり**。最重要差分は、`derived projection must not mutate canonical evidence` を「追加するな」だけでなく **「provider互換のために削るな」側まで閉じること**、およびmemory mutationで **selectorとeffect extentを別型にすること**。

# 5. 候補ごとの評価

## 5.1 A — Projection-Only Compatibility Repair: lossyな送信適応はcanonical historyを変えない

**Primary sources**

- Hermes #117891 — Unicode recovery  
  https://github.com/NousResearch/hermes-agent/pull/117891
- Hermes #118054 — image rejection recovery  
  https://github.com/NousResearch/hermes-agent/pull/118054

### (1) 何が実証済みか

#117891のreproductionでは、`UnicodeEncodeError` のexception textに `ascii` が含まれるだけでASCII-runtime fallbackへ入り、canonical `messages` をin-place sanitizeしてnon-ASCII内容を落とし、その後のflushで`state.db`までlossy内容へ書き換え得た。提案patchはruntime localeを実際に判定し、必要なsanitizationをdetached request-local copyへ限定する。focused testsはUnicode path 25件、関連send-path/history tests 68件passと報告されている。

#118054では別経路で、providerがimage contentを4xx rejectするとcanonical `messages` からimage partとimage-only messageを削除し、DBへflushしていた。automatic text-only fallbackや`/model` switchだけでも、後でvision modelへ戻したとき過去画像が永久に消える。提案patchはimage stripをsend-path copyだけへ限定し、canonical historyとDBを不変にする。

両PRともsurvey時点ではopenであり、**障害reproductionとregression testは提示されているが、upstream採用済みとは扱わない**。

### (2) 何が提案・推測段階か

Kamimusuhiの全provider adapterを「絶対immutable」にする必要はない。surrogate corruptionのようにcanonical repair自体が正しい場合はmutationしてよい。必要なのは変換の目的を型で分けること。

```text
CANONICAL_REPAIR      -> canonical mutation candidate
REQUEST_COMPATIBILITY -> derived send projection only
PRESENTATION_ADAPT    -> derived output projection only
```

### (3) 関係するサブシステム / 設計課題

- Continuity Kernel / canonical evidence
- Cognitive Action Router / model fallback
- multimodal perception/history
- K-Core / K-Deep model switch
- recovery / retry
- provenance / replay

### (4) 借りられる設計・実装アイデア

- canonical eventを直接adapterへ渡さず、`OutboundProjection`をclone/materializeしてからlossy transformする。
- transformに`purpose`を持たせ、`REQUEST_COMPATIBILITY`はpersistent writerを持たない。
- canonical hashを送信前後で比較するcanaryをdebug/test modeへ置く。
- model switch / fallback後に元capabilityへ戻したとき、以前のrich evidenceが再び利用可能であることをfixture化する。

### (5) Kamimusuhiとの差分

既出 **Semantic Transcoding Integrity** は主に「wire互換のために作ったsynthetic itemをcanonical eventとして追加しない」方向を扱った。今回の差分は逆向きで、**wire互換のためにcanonical evidenceを削除・簡略化しない**こと。`phantom insertion`だけでなく`lossy deletion`も同じprojection boundaryで閉じる。

### (6) 次に検証すべきこと

**`ProjectionOnlyCompatibilityRepairBench-v0`**

- same canonical transcriptで vision→text-only→vision、UTF-8→ASCII-only adapter→UTF-8、tool-schema downgrade→restore を実行
- outbound payloadがproviderごとに変化してよいこと
- canonical event IDs / hashes / provenance / attachment refsは不変であること
- genuine canonical corruption repairだけはexplicit receipt付きでmutation可能なこと

### (7) 既存dailyではなぜ拾いにくいか

multimodal memoryやprovider orchestrationを普通に検索すると「画像をどう保存するか」「fallback精度」に寄りやすい。今回のfailureは**互換性repair関数のownershipがdurable transcriptへ漏れた実装境界**として現れる。

### (8) 重要度

**A** — identity continuityとcanonical memoryを直接壊し、しかも通常のmodel fallbackだけで発火し得る。既存原則への明確なfresh delta。

## 5.2 A — Locator–Mutation Extent Binding: selectorと書換え範囲を同じ文字列に背負わせない

**Primary source**

- Hermes #117972 — *fail closed when approving a replace anchored inside an entry*  
  https://github.com/NousResearch/hermes-agent/pull/117972

### (1) 何が実証済みか

PR記載の実障害では、staged memory writeの`replace.old_text`がentry内部のunique substringをanchorとしていたのに、replay時のreplace semanticsはwhole-entry replacementだった。その結果、8-op batchの1操作でstanding rules約1,000 charsがprefix/suffixごと失われ、UI上は`Approved 1 memory write(s)`と成功扱いになったと報告される。

提案guardは、approval replay時に`old_text`が一意entry内部のproper substringである場合を検出し、batch全体をzero-writeでfail closedする。focused memory tests 62件 + approval周辺37件pass。survey時点ではPRはclosed/unmergedなので、**reproduction evidenceとして扱い、solution採用済みとはしない**。

### (2) 何が提案・推測段階か

Kamimusuhiでsubstring search自体を禁止する必要はない。危険なのは、**locator semanticsとeffect extent semanticsが同じfieldから推測されること**。

### (3) 関係するサブシステム / 設計課題

- Persona / Relationship / Semantic Memory mutation
- consent-bound memory promotion
- Effect Acceptance / approval UI
- rollback / provenance
- dream / consolidation writeback

### (4) 借りられる設計・実装アイデア

mutation APIを明示的に分ける。

```text
EntryReplace {
  entry_id
  expected_entry_hash
  new_full_entry
}

SpanPatch {
  entry_id
  expected_entry_hash
  span_locator
  expected_span_hash
  replacement
}
```

`selector`は対象同定、`extent`は作用範囲、`replacement_mode`は効果を表し、approval receiptはこの3つへbindする。曖昧なshort anchorからextentを推測しない。

### (5) Kamimusuhiとの差分

既出 **validated mutation-input coherence** はguardしたsnapshotと実際にwriteへ使うsnapshotが同じか、**explicit negative mutation semantics** はomitted/deleteの区別を扱う。本件は、snapshotが同じでも **「一致箇所を見つけるlocator」と「消してよい範囲」が別契約**だという差分。

### (6) 次に検証すべきこと

**`LocatorMutationExtentBench-v0`**

- exact whole-entry anchor / unique substring / duplicate substring / stale hash / Unicode-normalized match
- approval previewがactual mutation extentと一致すること
- ambiguous locatorではzero mutation
- batch中1件でもextent ambiguityがあればatomic reject
- dream/consolidation由来writeでも同じAPIを通ること

### (7) 既存dailyではなぜ拾いにくいか

memory safetyを検索するとconsent、provenance、conflict resolutionへ寄りやすい。これは**一見便利なtext APIのlocator/replace意味論の混線**で、通常は低レベルtool bugに見える。

### (8) 重要度

**A** — 人格・関係・standing ruleの静かな切断を「承認済み成功」として起こし得るため、長寿命個体では高優先。

## 5.4 B — Eviction–Rehydration Closure: working setから捨てるなら戻せる証拠を持つ

**Primary source**

- Hermes #118014 — *release paged-through transcript history from the session store*  
  https://github.com/NousResearch/hermes-agent/pull/118014

### (1) 何が実証済みか

desktop session storeは「Show earlier」で一度materializeした過去transcriptをpane lifetime中ずっと保持し、tool output / diff / preview / imageを含むpayloadがrenderer memoryを占有していた。PRのplanner benchmarkでは、2,000-row / 約100MBのtool-heavy transcriptから42 rows / 約2.1MBをliveに残し、約97.9MBをreleaseしたと報告。

重要なのは単なるLRUではなく、(a)window内rowを捨てない、(b)assistant branch groupを途中で分断しない、(c)durable `rowId`のない未persist rowは捨てない、(d)backend paging offsetをrewindして後からrehydrate可能にする、というclosureをtestしている点。

### (2) 何が提案・推測段階か

renderer向けの具体的window/slack値をKamimusuhiのworking memoryへそのまま使う根拠はない。full heap改善もplanner境界の測定であり、process-level end-to-end reductionは未確定。

### (3) 関係するサブシステム / 設計課題

- working memory / context assembly
- UI / multi-device embodiment
- long-lived session resource management
- canonical evidence / Library
- graceful forgetting / cache eviction

### (4) 借りられる設計・実装アイデア

`EvictionProof`を考える。

```text
EvictionProof {
  durable_ref
  canonical_version
  rehydrate_route
  ordering_cursor
  group_boundary
}
```

proofを作れないlive stateはevictしない。evictionはcanonical deletionではなく、**derived residencyの解除**として扱う。

### (5) Kamimusuhiとの差分

既出storage-vs-use forgettingは「保存されていること」と「現在利用可能であること」を分ける。今回のfresh deltaは逆方向で、**利用cacheから外す前に、将来の再materializationが欠落・skip・branch破壊なしにできることを証明する**実装closure。

### (6) 次に検証すべきこと

**`EvictionRehydrationClosureBench-v0`**

- persisted / unpersisted / branched / attachment-heavy / compacted eventを混在
- hot windowからevict→再scroll / restore /別device hydrate
- event ID集合と順序、branch parent、attachment refが一致
- cursor driftでもskipせず、重複はdedupe可能
- memory footprintがsession lengthではなくwindow boundへ収束

### (7) 既存dailyではなぜ拾いにくいか

agent memory研究は「何を忘れるか」をsemantic relevanceで議論しがち。本件は**canonicalは覚えたまま、live residencyだけを安全に忘れる**UI/runtime memory-management問題。

### (8) 重要度

**B** — 新原則というより既存memory hierarchyの具体化だが、長寿命UI / multi-deviceで実装価値が高い。

## 5.5 B — Prompt Constraint-Set Satisfiability: feature fragmentをappendする前に合成整合性を見る

**Primary source**

- Hermes #118068 — *swap the base platform hint for a rich variant when rich_messages is on*  
  https://github.com/NousResearch/hermes-agent/pull/118068

### (1) 何が実証済みか

`rich_messages`を有効にすると、Telegram base hintは先に「structured dataではtablesを避ける」と指示し、その直後のrich hintは「real Markdown tablesを積極的に使う」と指示していた。各fragment単体は想定featureに対して正しいが、assembled promptは自己矛盾する。提案patchはlive string surgeryではなく、rich用base variantへ切り替えてからrich blockを足し、contradictionが存在しないことをtestsで固定する。

### (2) 何が提案・推測段階か

一般prompt全体をSAT/SMT solverで形式検証できるとは限らない。自然言語constraintは曖昧で、完全自動の矛盾検出は未解決。

### (3) 関係するサブシステム / 設計課題

- Persona Core / presentation projection
- platform-specific interaction policy
- Social Cognition / relationship style
- K-Core context compiler
- runtime policy composition

### (4) 借りられる設計・実装アイデア

自然言語fragmentを直接appendする前に、最低限のtyped constraintへ落とす。

```text
FormattingPolicy {
  tables: ALLOW | PREFER | FORBID
  bullets: ALLOW | PREFER | FORBID
  code_blocks: ...
}
```

feature activationはdelta appendではなく、canonical policy objectをresolveしてから1回だけtext projectionする。`PREFER`と`FORBID`の衝突はcompile errorにする。

### (5) Kamimusuhiとの差分

既出Persona-Projection Referential Integrityはidentity presentation rewriteがURL/path等のliteral referentを壊さない話。今回の差分は**参照は正しくても、複数policy layerの要求集合が論理的に両立しない**こと。

### (6) 次に検証すべきこと

**`PromptConstraintCompositionBench-v0`**

- persona / relationship / platform / safety / accessibility / user preferenceの組合せをproperty-based生成
-同じdimensionで`FORBID + PREFER/REQUIRE`が出ないこと
- feature off/on切替でstale fragmentが残らないこと
- compiled typed policyと実promptをround-trip検査

### (7) 既存dailyではなぜ拾いにくいか

prompt engineeringの品質問題に見えるが、本質は**configuration composition / feature algebra / formal consistency**であり、agent memoryやorchestration検索から漏れやすい。

### (8) 重要度

**B** — 直接のidentity破壊ではないが、Persona Coreが多layer化するほどsilent behavior driftの原因になる。

## 5.6 B — Oversight Capability Preservation: human-in-the-loopを静的安全装置とみなさない

**Primary / supporting sources**

- Mitchell, Ghosh, Passi, *AI Agents Push Humans Out of the Loop*, arXiv:2608.23642  
  https://arxiv.org/abs/2608.23642
- Endsley & Kiris, *The Out-of-the-Loop Performance Problem and Level of Control in Automation*, Human Factors 37(2), 1995  
  https://doi.org/10.1518/001872095779064555

### (1) 何が実証済みか

Endsley & Kirisのautomation研究では、自動化下でoperatorのsituational awarenessが低下し、automation failure後のmanual takeover decision timeが悪化するout-of-the-loop performance problemが実験で示された。

2026年のMitchellらはagentic AIへこの問題を接続するposition paperで、approval fatigue、automation bias、skill atrophy、situational awareness低下により、単に「human approvalを置く」だけでは長期的な監督品質を保証できないと整理している。

### (2) 何が提案・推測段階か

Mitchellらのagent-specific処方（strategic friction、oversight canary、manual practice、role rotation等）は主に設計提案であり、Kamimusuhi型long-lived companionでの因果効果は未実証。

### (3) 関係するサブシステム / 設計課題

- Social Harness / human oversight
- Effect Acceptance
- long-lived co-adaptation
- safety / trust calibration
- observability / explanation
- relationship continuity

### (4) 借りられる設計・実装アイデア

human oversightをboolean gateではなく、時間変化するcapabilityとして扱う。

```text
OversightState {
  domain
  recent_manual_exposure
  intervention_success_rate
  review_latency_distribution
  calibration_score
  fatigue_signal?
}
```

高risk operationで、長期間rubber-stamp傾向が続く場合は「approvalがあるから安全」とは判定せず、説明粒度・review pacing・second reviewer・manual rehearsal等を変える。

### (5) Kamimusuhiとの差分

既存approval reachability / review–execution identityは、**人間へ届くか・見せたものと実行物が同じか**を守る。今回の差分は、正しく届き同じartifactを見ていても、**長期利用でreviewer自身の監督能力が変化する**こと。

### (6) 次に検証すべきこと

**`OversightCapabilityDriftBench-v0`**（human studyが必要）

- 長期automationあり/なし、review頻度、strategic frictionあり/なしを比較
- anomaly detection、takeover time、false approval、confidence calibration、fatigueを測定
- agent側task successだけでなくhuman skill retentionをsecondary objectiveにする

### (7) 既存dailyではなぜ拾いにくいか

AI safety surveyはagent policyやalignmentへ寄り、HCI surveyも単発UXへ寄りやすい。これは**agentの長寿命化がhuman overseerの能力を変えるsociotechnical feedback loop**で、両方の分類の間に落ちる。

### (8) 重要度

**B** — 長期的には重要だが、Kamimusuhi固有の実証にはhuman-subject studyが必要。watchlist価値が高い。

### Hermes #118059 — executor occupancy isolation
https://github.com/NousResearch/hermes-agent/pull/118059

`asyncio.wait_for`はawait時間をboundしても、already-running worker threadの**executor slot occupancyを解放しない**。wedged housekeepingがshared poolを食い尽くすreproに対し、housekeeping専用bounded poolへ分離し、shared poolを10→200 workersに増やしてもmutant failureが消えないことをtestしている。これは新原則ではなく、既出 **mixed-criticality cognition / maintenance isolation / deadline closure** の非常に良い実装fixture。既存benchへ「timeout != resource release」を追加する価値あり。

# 10. 今回の結論

今回の中心は、**「一時的な適応が永続的な自己を書き換えない」**ことと、**「対象を見つける方法と、変更してよい範囲を同一視しない」**こと。

Kamimusuhiはすでにcanonical/derived separation、provenance、approval、scopeをかなり持っているが、freshな実装障害はその一段下で、

```text
provider compatibility repair -> canonical deletion
substring locator            -> whole-entry destruction
expensive model override     -> reasonless resource escalation
working-set eviction         -> unprovable rehydration
feature prompt composition   -> self-contradictory policy
human approval               -> assumed-static reviewer capability
```

という形で現れている。

したがって次の最小実装は、**`ProjectionOnlyCompatibilityRepairBench-v0` と `LocatorMutationExtentBench-v0` の2本**が最も費用対効果が高い。
