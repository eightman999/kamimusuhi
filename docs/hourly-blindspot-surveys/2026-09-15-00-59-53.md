## 2. 今回狙った盲点

通常の Kamimusuhi daily survey では、分散システムは identity/fencing/replay、安全は effect authorization、neuromorphic/low-latency は learned controller、observability は agent trace という分類になりやすい。その分類の境目で、今回次の3つを狙った。

1. **故障した organ を「直ったら戻す」こと自体の危険**  
   microreboot や failure detector は「何を止めるか」「いつ怪しいとみなすか」を扱うが、いったん切り離した component を **どの条件で再接続すれば全体の安定性を壊さないか**は別問題。
2. **hot path での policy 可変性と self-modifying code の分離**  
   PNL/K-Nerve は適応可能であるべきだが、μs 級の control path で毎回 policy code を生成・検証する必要はない。**policy authoring authority と policy selection authority** を分けられる。
3. **OS kernel 内部の見えない backpressure**  
   high-level CPU/GPU/network/DB telemetry が正常でも、buffered I/O の dirty-page writeback / throttling が system call を止め、continuation / canonical commit / indexing の latency を跳ね上げ得る。これは認知資源不足や process hang と誤認しやすい。

# 6. 候補ごとの評価

## 6.1 A — Controlled Islanding & Reconnection: 回復した organ を戻す前に「再接続の安定性」を判定する

**Primary:** Shiyu Cheng, Andrew Clark, *Controlled Islanding and Reconnection with Stability Guarantees via Submodular Optimization*, arXiv:2609.12335  
https://arxiv.org/abs/2609.12335

### (1) 何が実証済みか

論文は large-scale networked dynamical system で、局所 fault / disturbance が interconnection を通じて全体へ伝播する問題を扱う。二段階で、まず network を stable / unstable island に分割し、その後 selected stable islands を **stability requirement を満たしながら再接続**する。

著者らは islanding / reconnection 双方について Lyapunov-based sufficient conditions を導出し、admissible pair を graphic matroid 上の構造として表し、nonincreasing supermodular optimization へ落とす。linear networked systems の数値実験で fault location への感度と MILP baseline との比較を行っている。

実証範囲は **線形 networked dynamical systems の数値研究**であり、agent architecture や LLM system での安定性は実証していない。

### (2) 何が提案・推測段階か

Kamimusuhi の distributed body に「controlled cognitive islanding」を導入する部分は本 survey の提案。

特に次の仮説を置く。

```text
organ/node が ping に応答する
+ local health check が通る
!=
その organ を active cognitive graph に戻しても
全体の latency / feedback / authority / control stability が保たれる
```

たとえば unstable な sensor-fusion node、oscillatory background worker、遅延した K-Edge、古い local model organ が local probe だけ回復しても、すぐ全体へ再接続すると stale feedback や oscillatory routing を再注入する可能性がある。

### (3) Kamimusuhi の関係 subsystem / 設計課題

- distributed embodiment / K-Edge ↔ K-Core ↔ K-Deep
- Organ Supervisor
- degraded-mode operation
- PNL / sensor organ / actuator organ
- failure suspicion / microreboot の**次段**
- Continuity Kernel 周辺の runtime topology（ただし canonical identity authority 自体をこの最適化へ委ねない）

### (4) 借りられる設計・実装アイデア

最初から graph optimization を実装する必要はない。まず contract を借りる。

```text
ACTIVE
  -> SUSPECT
  -> ISOLATED
  -> LOCALLY_RECOVERED
  -> RECONNECT_PROBING
  -> RECONNECT_CANDIDATE
  -> ACTIVE
       or
     DEFERRED_ISLAND
```

`LOCALLY_RECOVERED` と `ACTIVE` の間に **Reconnection Admission** を置き、少なくとも次を見る。

- generation / lease / authority freshness
- queue / state catch-up status
- observed latency / jitter
- feedback-loop gain の proxy
- dependency graph 上の simultaneous reconnection 数
- sensor disagreement / duplicate actuation risk
- replay / pending-effect state

### (5) Kamimusuhi との差分

論文は control-theoretic network stability が中心。Kamimusuhi は identity lineage、authorization、semantic correctness、privacy、resource cost まで扱う。

したがって Lyapunov stability をそのまま「人格安定性」と読み替えてはいけない。借りるのは **isolation と reconnection を別 admission problem とする構造**である。

### (6) 次に検証すべきこと

**`CognitiveIslandingBench-v0`**

Fault injection:

- K-Edge の high-jitter / delayed feedback
- sensor fusion organ の contradictory output
- background worker の oscillatory wake/escalate
- local model organ の stale capability view
- memory/index organ の intermittent timeout

比較:

1. health probe pass で即 reconnect
2. fixed cooldown 後 reconnect
3. staged reconnection admission

測定:

- canonical invariant violation
- duplicate / stale effect proposals
- oscillation / repeated wake count
- p95/p99 control latency
- time to full recovery
- degraded-mode utility
- false isolation / unnecessary defer

### (7) 既存 daily ではなぜ拾いにくいか

分類上は **電力系統・networked control / submodular optimization** に見え、通常の distributed-systems / agent / robotics 検索では外れやすい。また直近 Kamimusuhi survey は failure detection と microreboot に重点があり、**recovery 後の reintegration admission** は別概念として未収載だった。

### (8) 重要度

**A** — distributed embodiment の degraded/recovery path に直接接続するが、LLM/agent system での実証はこれから。

## 6.2 A — AKTS: hot path の適応を「事前検証済み policy の選択」に狭める

**Primary:** Mohammadali Khodabandehlou, Mahdi Alizadeh, *AKTS: Sub-Microsecond Kernel Policy Switching for Language-Model Agents*, arXiv:2609.12276  
https://arxiv.org/abs/2609.12276

Code / raw measurement data は arXiv ページから公開 repository へリンクされている。

### (1) 何が実証済みか

GPU-backed LLM server が interactive request と background batch work を同一 CPU 上で multiplex する状況で、scheduler policy を workload に応じて切り替える必要を扱う。

AKTS は runtime に eBPF policy code を生成させず、**policy library を load 時に一度 verifier へ通し、runtime agent は integer index だけを選ぶ**。in-kernel tail call が対応 policy を実行する。

Linux 6.14 の測定で、paper は以下を報告する。

- policy switch p50: **920 ns**
- attached scheduler 上で invalid index を **60,217 invocations** にわたり inert にした
- vLLM workload で throughput policy の batch work の **97%** を確保しつつ latency policy の burst response に合わせた

これは kernel scheduler policy switching の結果であり、一般的な agent reflex policy や physical actuator safety の実証ではない。

### (2) 何が提案・推測段階か

Kamimusuhi の PNL / K-Nerve へ移植する場合の核心は、eBPF そのものではなく次の分離。

```text
policy creation / training / synthesis
           !=
policy admission / verification
           !=
hot-path policy selection
```

低遅延適応のために runtime self-modifying code を許す必要はない。semantic cognition は「どの verified policy を使うか」だけを選び、policy 本体の導入は slow path で versioned / tested / admitted にできる、という設計仮説。

### (3) Kamimusuhi の関係 subsystem / 設計課題

- K-Nerve
- Peripheral Neural Layer (PNL)
- R0/R1 reflex hierarchy
- K-Edge resource control
- Cognitive Budget / background-vs-interactive scheduling
- low-latency model/tool routing
- degraded-mode policy switching

### (4) 借りられる設計・実装アイデア

**`VerifiedReflexBank`** を候補化する。

```text
policy candidate
   -> offline/slow-path tests
   -> safety-envelope compatibility
   -> version/hash/signature
   -> VERIFIED_REFLEX_BANK

runtime signal
   -> tiny selector / FSM / K-Edge hint
   -> policy_id
   -> bounds check
   -> select preverified policy
   -> R0 deterministic envelope
```

権限を分ける。

- `POLICY_AUTHOR` — 新 policy を作る
- `POLICY_ADMIT` — test / verification 後に bank へ追加する
- `POLICY_SELECT` — runtime に bank 内から選ぶ
- `POLICY_EXECUTE` — capability envelope 内で実行する

`POLICY_SELECT` を持つ K-Nerve が `POLICY_AUTHOR` を持つ必要はない。

### (5) Kamimusuhi との差分

AKTS は scheduler hot path の verifier / switching latency が主題で、identity、memory、sociality、sensorimotor safety は扱わない。

Kamimusuhi ではさらに、policy bank の各 entry に body compatibility、sensor schema、capability envelope、controller version、rollback target を結びつける必要がある。

### (6) 次に検証すべきこと

**`PreverifiedReflexSwitchBench-v0`**

比較:

1. static single policy
2. runtime policy/code generation + validation
3. preverified policy bank + index selection

workload:

- interactive burst vs background consolidation
- thermal pressure
- network degradation
- sensor-noise burst
- K-Core offline fallback

測定:

- p50/p99 switch latency
- verifier/admission failure が hot path に出る率
- invalid policy id containment
- R0 safety-envelope violations
- rollback latency
- selector accuracy / hysteresis / oscillation
- energy / CPU overhead

### (7) 既存 daily ではなぜ拾いにくいか

通常は「OS scheduler / eBPF performance paper」と分類され、AI agent survey では throughput optimization として流されやすい。一方 Kamimusuhi では **self-modifying low-latency cognition の authority 分離**という設計問題へ接続できる。

### (8) 重要度

**A** — PNL の既存方針と相性が良く、実装可能性が高い。eBPF 採用自体は未決定で、まず policy-bank pattern の比較実験が必要。

## 6.3 A — Invisible Kernel Writeback Stalls: 認知停止と storage backpressure を誤診しない

**Primary:** Mitsumasa Kondo, *Invisible Yet Dominant: Big Stalls of Kernel I/O Mechanisms in Cloud OLTP Databases*, arXiv:2609.12597  
https://arxiv.org/abs/2609.12597  
SOSP 2026 poster。SteelDB (`arXiv:2603.29052`) の companion。

### (1) 何が実証済みか

paper は PostgreSQL、RocksDB、AI KV-cache middleware などが使う buffered I/O に対し、cloud distributed block storage で各 device が **single kernel flusher thread** により drain される hidden bottleneck を調べる。

writeback が追いつかないと dirty throttling が `write()` を pause し、dirty page eviction が必要な read まで stall する。著者は、この stall が `iostat` と標準 counter では見えないと報告する。

eBPF probe で writeback / block tracepoint と throttle pause を観測し、同じ provisioned IOPS / bandwidth で 1 / 2 / 4 devices を比較。**drain を増やす**ことで throttle pause 70%減、maximum transaction latency 59%減、throughput 23%増を報告する。

数値は当該 OLTP / cloud block-storage 実験の結果であり、Kamimusuhi の SQLite / local NVMe / memory store へ一般化してはいけない。

### (2) 何が提案・推測段階か

Kamimusuhi では storage stall が次のように誤分類される可能性がある。

```text
canonical commit が遅い
  -> Continuity Kernel failure と誤認

memory/index write が詰まる
  -> background cognition hang と誤認

read eviction が止まる
  -> retrieval/model latency と誤認

commit/heartbeat が遅れる
  -> organ failure suspicion を不必要に上げる
```

したがって **`compute_pressure` だけでなく `storage_writeback_pressure` を独立観測する価値がある**、というのが本 survey の提案。

### (3) Kamimusuhi の関係 subsystem / 設計課題

- canonical evidence store
- Continuity Kernel commit path
- K-Core persistent memory
- derived index / vector store / cache
- background consolidation / sleep
- Organ Supervisor / failure suspicion
- observability / telemetry
- Cognitive Budget / backpressure

### (4) 借りられる設計・実装アイデア

`StoragePressureState` を high-level DB metrics だけで作らない。

候補信号:

- dirty page ratio / dirty bytes
- writeback duration / queueing
- throttle pause count / duration
- fsync latency distribution
- per-device drain concurrency
- read stalls associated with dirty eviction
- device saturationとは別の kernel writeback evidence

重要なのは「常に eBPF 必須」ではない。まず **storage-pressure blind spot が実環境で存在するかを測り、必要なら kernel-level probe を追加**する。

### (5) Kamimusuhi との差分

paper は cloud OLTP database の performance diagnosis。Kamimusuhi は identity / continuity semantics が主目的で、throughput 最大化だけが目的ではない。

Kamimusuhi では tail latency が高い理由を知ることが、**誤った failover / duplicate recovery / cognitive degradation diagnosis を避ける**ために重要になる。

### (6) 次に検証すべきこと

**`HiddenWritebackStallBench-v0`**

環境候補:

- local SQLite WAL / canonical event append
- vector/index build
- large sequential artifact write
- background consolidation
- same host 上の concurrent model/cache workload

fault/load:

- dirty-page burst
- slow block device / constrained IOPS
- one vs multiple backing devices
- heavy background write + interactive canonical commit

比較観測:

1. application/DB metrics のみ
2. standard OS metrics (`iostat` 等)
3. writeback/throttle-aware kernel probes

測定:

- canonical commit p99
- false φ-suspicion / false failover count
- retrieval latency
- background-job starvation
- observed cause classification accuracy
- mitigation後の utility / tail latency

### (7) 既存 daily ではなぜ拾いにくいか

通常の AI agent observability は token、trace、tool call、model latency、GPU/CPU、network を中心にしやすい。database survey でも query/index/schema へ寄り、**kernel writeback thread / dirty throttling**は OS と DB の境界に落ちる。

Kamimusuhi では、この境界が canonical commit と long-lived cognition の liveness に直結するため、独立して見る価値がある。

### (8) 重要度

**A** — 実装基盤の observability blind spot として有用。ただし現行 deployment で同じ bottleneck が起きるかは bench で確認する。

4〜8個の bounded policy を静的に用意し、selector に index だけ出させる。policy は simple scheduler / wake threshold / sensor suppression でよい。invalid id / stale bank generation / oscillating selector を fault injection する。

### 8.3 `HiddenWritebackStallBench-v0` 最小 fixture

SQLite WAL append と background large write を同居させ、dirty-page pressure を上げながら commit latency と heartbeat を測る。まず `/proc` / pressure stall / fsync latency などの低コスト signal で十分かを確認し、不十分なら eBPF probe を導入する。

## 11. この回の結論

今回の3件は、Kamimusuhi を「一つの長寿命 agent」ではなく **長く動く分散制御個体**として実装する時に効く。

短く言えば:

```text
故障から戻った器官は、すぐ繋がない。
速く適応する器官は、hot path で自分の code を書かなくてよい。
遅い cognition は、cognition 自体が遅いとは限らない。
```

次に一本だけ実装するなら **`CognitiveIslandingBench-v0`**。既存 microreboot / failure-suspicion 系の次の穴を直接叩け、mock graph だけで falsifiable にできる。
