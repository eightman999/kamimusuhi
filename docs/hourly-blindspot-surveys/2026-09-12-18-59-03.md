## 2. 今回狙った盲点

今回は、通常の AI-agent / memory / ALife survey では特に見落としやすい次の5境界を狙った。

1. **durable execution / deterministic replay / software evolution** — 長寿命の個体を、クラッシュ後や runtime upgrade 後に「再実行して同じことを考え直す」ことなく復元できるか。
2. **mixed-criticality real-time systems** — すべての cognition task を同じ優先度・同じ deadline semantics で扱わず、安全-critical な反射と低criticalityだが価値の高い認知をどう graceful degradation させるか。
3. **decision-oriented information freshness** — `新しいほど良い` ではなく、今の意思決定を変える情報だけを優先して更新する方法。
4. **training-rollout fidelity** — 将来 Persona Core / sparse model を自己改善するとき、「実際に生成した軌跡」と「学習に使った軌跡」が tokenization / routing drift で別物にならないか。
5. **recomputable authorization records** — Effect Acceptance の結論だけでなく、別実装が同じ入力から同じ判定根拠を再計算できるか。

この結果、今回は **有意な新規発見あり**。最重要は、Kamimusuhi の continuity を event log / canonical evidence だけで閉じず、**「どこまでを deterministic orchestration とし、どこからを記録済み non-deterministic cognition とするか」**を明示する必要があること。そして Cognitive Budget に **criticality と importance を分離した mode-switch semantics** を足す余地が大きいこと。

## 4. 要約 / 重要発見

### 4.1 最重要: `canonical history exists != recovery is replay-safe`

Kamimusuhi は canonical evidence、atomic activation、outbox、UNKNOWN external outcome をすでに持つ。しかし長寿命 workflow の recovery には別の問題がある。

```text
same history
+ changed runtime / clock / random source / prompt / router / model / tool schema
-> different future commands
```

Temporal の durable-execution model は、Workflow 自体を deterministic にし、LLM / tool / external API のような non-deterministic I/O を Activity へ隔離して結果を history に一度だけ記録する。回復時には LLM をもう一度呼ばず、記録済み result を replay する。さらに Worker Versioning では、長寿命 execution を開始時の worker revision に pin し、running history を新しい code で壊さないための version semantics を持つ。

この原則は Kamimusuhi にそのまま製品採用する必要はないが、**continuity-bearing orchestration と non-deterministic cognition の境界**として強い。

さらに 2026-07-29 に報告された Temporal TypeScript SDK issue #2269 は、Node 26 / ECMAScript 2026 で native `Temporal.Now` が sandbox に入った結果、従来 override されていた `Date.now()` 等と違い real wall-clock を読み、同じ history の replay が別 branch を選び得る例を示す。これは issue report であり production-wide incident の確定証拠ではないが、**runtime upgrade が「新しい global」を持ち込み、暗黙に replay contract を壊す**実例として価値が高い。

Kamimusuhi に必要なのは、`restore == re-think` を避けること。

### 4.2 Cognitive Budget には `criticality != importance` が足りない

Kamimusuhi は latency / energy / money / working-memory / tool availability を Cognitive Budget として扱い、K-Nerve〜K-Deep の役割分離もある。しかし mixed-criticality systems の知見を入れると、単一 priority では不十分になる。

- **criticality**: deadline miss / failure が安全性・continuityをどれだけ壊すか
- **importance**: その処理が今どれだけ価値を持つか

は別軸である。

たとえば「大切な長期reflection」は importance が高くても hard real-time criticality は低い。一方、actuator emergency stop や lease/fencing 更新は内容的には単純でも criticality が高い。

RTNS の graceful-degradation work は、criticality mode switch 時に low-criticality task を全部捨てるのではなく、**importance を別軸にして least-important だけを落とす**。AnTi-MiCS は low/high WCET の境界設定が utilization と不要な mode switch / QoS の trade-off を持つことを実プラットフォームで評価し、multiple low-WCET levels の価値も示す。

Kamimusuhi では、overload 時に `K-Deepを切る` だけでなく、**安全-critical task を守りながら、価値のある低criticality cognitionを圧縮版で生かす**設計へ進める。

### 4.3 `fresh enough` は時刻だけでは決まらない

現在の Kamimusuhi は freshness semantics と monotonic timeout をすでに持つ。この部分は正しい。しかし CoSMO が突いているのは別の問題である。

```text
information is old
!=
refreshing it will change the decision
```

CoSMO の edge-cloud setting では、remote service state は stale cache でしか見えない。AoI 的に「古いから更新」するのではなく、update が local / remote / reject の意思決定へどれだけ価値を持つかを task utility と結びつける。論文は評価 workload 群で best competitor に対する on-time completion の相対改善平均 18.6–21.2%、strict overload points の capacity-aware decision accuracy 改善 17.6–17.9% を報告する。

これはそのまま Kamimusuhi に転用できる数値ではない。しかし K-Edge / K-Core 間の telemetry、remote model health、sensor summary、relationship/common-ground cache などで、**refresh bandwidth を「年齢」ではなく decision regret の期待値で割り当てる**発想は有用である。

### 4.4 Self-improvement では「意味が同じ text」だけでは training lineage が閉じない

T1 は 122B-total MoE terminal agent を long-horizon shell task で RL する研究で、今回の通常 agent survey なら benchmark score に注目しがちだが、Kamimusuhiに有用なのは training fidelity の方である。

T1 は Token-In-Token-Out (TITO) で **実際に sampled した token ID** を学習へ渡し、turn boundary の drift を repair する。さらに Rollout Routing Replay (R³) で rollout 時の **per-token expert routing choice** を各 MoE layer について記録し、training 時に replay する。論文は TITO + R³ により training-to-inference log-probability gap を 0.021 → 0.013 に下げ、loss region の token drift を zero にしたと報告する。

これは Persona Core が将来 sparse / MoE になることを前提にしなくても重要で、**「経験を学習した」ことの provenance は、自然言語 transcript だけでは不十分な場合がある**ことを示す。tokenizer version、exact token IDs、sampling config、router decisions、tool observations、verifier outcome まで training episode の closure に入れる必要がある。

### 4.5 Authorization の監査ログは `ALLOW/DENY` だけより再計算可能な方が強い

IETF に 2026-09-06 公開された `draft-kroehl-agentic-trust-aae-02` は **Internet-Draft / work in progress** であり、RFCや IETF endorsement ではない。この位置づけは明示しておく。

そのうえで設計知として有用なのは、AAE の identity / DID 部分そのものより **verdict record** である。

- verdict は `PERMIT / PENDING / DENY`
- verdict は ordered predicate trace を持つ
- trace は predicate / field / observed value / required bound / PASS|FAIL を持つ
- outcome だけ返す verifier は conformant ではない
- 同一 mandate + transaction を評価する independent verifier は byte-identical core digest を出せることを要求
- `PENDING` / `DENY` を後から変える場合は prior record を編集せず、prior digest を参照する signed ratification record を append する

Kamimusuhi の Effect Acceptance / VerificationAdequacy と競合するものではなく、**effect admission の監査 receipt を「あとから人が読む説明」ではなく「別実装が再計算できる structured proof trace」にする**具体的な比較候補になる。

## 5.1 Deterministic Durable Cognition / Replay Compatibility Contract

**Importance: S**

**Sources**

- Temporal AI Agent Reference Architecture: https://go.temporal.io/platform-hub/ai-engineering/ai-reference-architecture
- Temporal Worker Versioning: https://github.com/temporalio/documentation/blob/main/docs/production-deployment/worker-deployments/worker-versioning/index.mdx
- Temporal TypeScript SDK #2269: https://github.com/temporalio/sdk-typescript/issues/2269

### (1) 何が実証・実装済みか

- Temporal は production durable-execution framework として Workflow history replay を中心に据え、Workflow に deterministic behavior を要求している。
- official AI reference architecture は LLM / tool / external API を Workflow 内で直接実行せず Activity とし、結果を一度 history に記録して replay 時に再利用する pattern を明示している。
- Worker Versioning は Workflow execution を code revision に pin する方式を提供し、running execution と新しい deployment version を分離する。
- TypeScript SDK issue #2269 は、Node 26 の native `Temporal.Now` が deterministic override の外に入り、同一 history の replay が別 branch を選んで `DeterminismViolationError` になり得る最小再現を提示している。

### (2) 何が提案・推測段階か

- Temporal の model を Kamimusuhi の Continuity Kernel に適用すれば identity continuity が改善する、という点は本稿の architectural inference。
- Kamimusuhi 全体を deterministic にすべき、という主張ではない。むしろ **orchestration nucleus と non-deterministic cognitive activity を分ける**提案である。
- issue #2269 は公開 bug report であり、広範な production failure rate や SDK 全体の安全性を示す統計ではない。

### (3) 関係する Kamimusuhi subsystem / design issue

- Continuity Kernel
- canonical evidence / lineage
- K-Core orchestration
- background jobs / scheduler / outbox
- model / prompt / runtime migration
- crash recovery
- software evolution / observability

### (4) 借りられる設計・実装アイデア

`ReplayCompatibilityContract` を導入候補にする。

```text
CognitiveOrchestrationHistory
  workflow_id
  history_schema_version
  runtime_code_revision
  policy_revision
  persona_artifact_id
  router_revision
  tool_schema_revision
  prompt/template revision refs
  clock_source
  rng_source
  recorded_activity_results[]
  explicit_version_boundaries[]
```

原則:

```text
LLM/search/tool/sensor result
  = nondeterministic Activity result
  -> record once with provenance/receipt
  -> crash recovery reuses recorded result

recovery
  != call again and pretend it was the same cognitive episode
```

upgrade は少なくとも次を選べるようにする。

- old history を old runtime revision に pin して完了
- compatibility-tested N+1 で replay
- explicit migration checkpoint / continue-as-new
- incompatible なら silent continuation ではなく lineage-visible transition

### (5) Kamimusuhiとの差分

Kamimusuhi はすでに canonical evidence、outbox、idempotency、UNKNOWN outcome、generation/fencing を持つ。しかしそれらは **外部 side effect と canonical write の安全性**を強く扱う一方、

```text
same historical inputs + upgraded cognition/runtime
-> same orchestration decisions?
```

という deterministic replay contract は明示的に収載されていない。

canonical log が存在しても、restore 時に新しいモデル・prompt・clock・routerで「もう一度考える」と、過去の未完了 episode が別人格/別policyの判断で続く可能性がある。

### (6) 次に検証すべきこと

**`ReplayEquivalenceBench`**

1. 100〜300 step の synthetic long-lived cognitive workflow を作る。
2. LLM/tool/search を nondeterministic mock Activity として record する。
3. every await / effect boundary で crash を注入する。
4. same revision replay は command sequence / canonical proposal sequence が一致することを要求。
5. N+1 runtime で replayし、互換なら一致、非互換なら明示的 `REPLAY_INCOMPATIBLE` になることを要求。
6. `wall clock`, `rng`, tokenizer, prompt, tool schema, environment variable, new language global を1つずつ変える。
7. crash recovery 時に Activity が勝手に再実行されていないかを canary で検出する。

### (7) 既存 daily で拾いにくい理由

AI agent 論文ではなく、**durable workflow / event replay / programming-language runtime determinism / deployment versioning** の実装論だから。通常の memory / continuity survey では「event sourcing がある」で止まりやすく、**history をどの code revision でどう再生するか**まで降りない。

### (8) 判定

**S**。Kamimusuhi の「モデル・端末・runtime が変わっても同じ個体が続く」という中心命題に直接関わり、既存 continuity contract の隙間を埋める。

## 5.2 Mixed-Criticality Cognitive Scheduling

**Importance: A+**

**Sources**

- Ranjbar & Kumar, *AnTi-MiCS*, arXiv:2604.27862 — https://arxiv.org/abs/2604.27862
- Sun, Sudvarg & Gill, *Elastic Scheduling for Graceful Degradation of Mixed-Criticality Systems*, DOI: https://doi.org/10.1145/3696355.3699701

### (1) 何が実証済みか

AnTi-MiCS は real embedded platform / benchmark で low-WCET 設計を評価し、既存法比で平均 QoS +30.27%、utilization waste -35.89% を報告する。複数 low-WCET level を使う MulTi-MiCS は AnTi-MiCS 比でさらに QoS +6.41%、waste -8.23% を報告する。

RTNS の elastic scheduling work は、high-criticality mode へ移る際に lower-criticality tasks を一律に捨てるのではなく、**criticality と importance を分け**、feasibility を保つために必要な範囲で least-important tasks を落とす。elastic workloads は budget compression で残存 service を増やす。

### (2) 何が提案・推測段階か

- 数値を LLM cognition scheduling へ転用できるわけではない。
- WCET をそのまま token budget に置換すればよいわけでもない。LLM / tool latency は heavy-tail で、hard WCET を持たないものも多い。
- mixed-criticality の mode-switch vocabulary を Kamimusuhi の cognitive runtime へ借りることが提案。

### (3) 関係 subsystem

- K-Nerve / K-Edge / K-Core / K-Deep
- Cognitive Budget
- emergency stop / Runtime Assurance
- turn-taking / low-latency cognition
- background cognition / sleep / dream
- degraded-mode operation
- resource health / watchdog

### (4) 借りられる設計・実装アイデア

`CognitiveTaskEnvelope` を候補化する。

```text
CognitiveTaskEnvelope
  task_id
  assurance_criticality: H | M | L
  functional_importance: 0..1
  deadline_class: HARD | FIRM | SOFT | NONE
  normal_budget
  degraded_budget
  emergency_budget
  degrade_strategy
  drop_policy
  retryability
  effect_risk
```

`criticality` と `importance` は別フィールドにする。

例:

```text
H criticality / medium importance
  actuator emergency stop
  continuity lease renewal
  split-brain/fencing check
  safety sensor alarm

M criticality / high importance
  live turn-taking
  user interruption handling
  current task control

L criticality / high importance
  autobiographical synthesis
  important relationship reflection

L criticality / low importance
  speculative dream branch
  nonurgent index compaction
  broad exploratory survey
```

runtime mode:

```text
NORMAL
  -> DEGRADED
  -> EMERGENCY
  -> RECOVERY
  -> NORMAL
```

低criticality task は全部 kill せず、`full -> compressed -> deferred -> dropped` の段階を持てる。

### (5) Kamimusuhiとの差分

Cognitive Budget と実行tierは既にあるが、現状は **resource budget / role / latency** の語彙が中心。`このtaskがdeadline missすると何を壊すか` と `内容としてどれだけ重要か` を直交軸にし、overload 時の mode switch / graceful degradation を契約化する部分は未収載。

### (6) 次に検証すべきこと

**`CognitiveCriticalityBench`**

- GPU saturation / network loss / provider throttling / sensor burst を注入。
- H-critical task の deadline-miss rate を測る。
- baseline: FIFO / simple priority / current router。
- candidate: mixed-criticality + importance-aware degradation。
- metrics:
  - H deadline misses
  - emergency-stop latency
  - turn interruption latency
  - low-criticality retained utility
  - dropped important work
  - mode-switch count
  - recovery hysteresis / flapping
  - energy / token / cost

特に **「Hを守るためにLを全部殺す」baseline と、「重要なLを圧縮して残す」candidate** を比較する。

### (7) daily で拾いにくい理由

real-time embedded systems / scheduling theory の語彙で書かれており、AI agent の orchestration 検索では `priority queue` や `latency` に還元されやすい。**criticality と importance の分離**は agent paper の一般的な routing taxonomy には出にくい。

### (8) 判定

**A+**。専用モデル不要で runtime scheduler に実装でき、K-Nerve の存在理由を安全工学の形で定式化できる。

## 5.3 Decision-Oriented Freshness / Value of Refresh

**Importance: A+**

**Source**

- Qi et al., *Update for Decisions, Not Freshness*, arXiv:2609.01082 — https://arxiv.org/abs/2609.01082

### (1) 何が実証済みか

CoSMO は edge node が remote service state を stale cache で観測する非同期 closed loop を扱い、status update と offloading decision を realized task utility で共同最適化する。論文報告値では、best competing method に対し on-time completion rate の相対改善が workload 群平均 18.6–21.2%、strict-overload points の capacity-aware decision accuracy が 17.6–17.9% 改善した。

### (2) 何が提案・推測段階か

- これは edge offloading task での結果であり、memory / relationship / sensory state に同じ数値効果が出るとは限らない。
- Kamimusuhi へ借りるのは RL algorithm 自体より、**refresh value は timestamp age ではなく downstream decision sensitivity で決まる**という contract。

### (3) 関係 subsystem

- `Freshness`
- K-Edge ↔ K-Core state propagation
- sensor / body health telemetry
- resource registry / model health
- relationship/common-ground views
- Cognitive Budget
- distributed embodiment
- low-bandwidth / energy-aware operation

### (4) 借りられる設計・実装アイデア

既存 `Freshness` を壊さず、その上に `FreshnessUsePolicy` / `ValueOfRefresh` を追加する。

```text
FreshnessUsePolicy
  source_ref
  age
  confidence_decay
  decision_sensitivity
  stale_action_loss
  refresh_cost
  max_safe_age
  hard_expiry
  refresh_trigger
```

概念的には:

```text
ValueOfRefresh
  = E[utility | refreshed]
  - E[utility | stale]
  - refresh_cost
```

同じ age でも扱いを変える。

- 10秒古い emergency-stop authority: hard expiry / high risk
- 10秒古い remote GPU load: queue near capacity なら high value、idleなら low value
- 10分古い room temperature: current taskがthermal safetyと無関係なら low value
- 1日古い casual preference: conversational decisionへ影響しないなら更新不要

### (5) Kamimusuhiとの差分

現行 repo は freshness semantics、monotonic timeout、stale background observation を遅れて適用しない原則を既に持つ。今回の差分は **「古い/新しい」の判定ではなく、更新帯域を使う価値**。

```text
freshness validity
!=
refresh priority
```

### (6) 次に検証すべきこと

**`DecisionFreshnessBench`**

- simulated K-Edge nodes 4〜16台。
- state: compute load / sensor health / battery / network RTT / capability availability。
- bandwidth / polling budget を制限。
- baseline:
  1. fixed TTL
  2. AoI / oldest-first
  3. periodic refresh
- candidate: decision-sensitivity / expected-regret based refresh。
- metrics:
  - stale-induced wrong routing
  - action regret
  - deadline miss
  - refresh bytes
  - energy
  - unnecessary updates
  - hard-expiry violations

### (7) daily で拾いにくい理由

Age of Information / semantic communications / edge offloading の研究であり、agent memory survey からは外れる。Kamimusuhi の `Freshness` が既に存在するため、通常surveyでは「既出概念」と誤って弾きやすいが、**freshness validity と refresh utility は別問題**。

### (8) 判定

**A+**。distributed embodiment と energy-aware cognition をつなぐ、実装可能な小さな拡張。

## 5.4 T1 — Exact Learning-Trajectory Fidelity

**Importance: A-**

**Source**

- Yang et al., *T1: Terminal Agent Reinforcement Learning for Long-Horizon Tasks*, arXiv:2609.11042 — https://arxiv.org/abs/2609.11042

### (1) 何が実証済みか

T1 は long-horizon terminal tasks を real shell sandbox で 300+ tool-call turns まで扱う 122B-total MoE model の RL training recipe を報告する。

本稿で重要なのは benchmark ranking ではなく:

- TITO: sampled token identifiers をそのまま training へ渡す
- turn-boundary drift repair
- R³: rollout 時の per-token expert routing choices を記録し training で replay

で training / inference mismatch を減らす点。論文は TITO + R³ で log-probability difference 0.021 → 0.013、loss region の token drift zero を報告する。

### (2) 何が提案・推測段階か

- Kamimusuhi Persona Core が MoE になるとは限らない。
- 同じ fidelity contract が personality continuity を保証するわけではない。
- ここから「学習traceは exact execution trace を持つべき」という一般化は architectural inference。

### (3) 関係 subsystem

- future Persona Core training
- self-improvement / developmental learning
- model lineage
- canonical evidence → training-data projection
- tokenizer / model artifact closure
- reproducibility / provenance

### (4) 借りられる設計・実装アイデア

`LearningEpisodeReceipt` を候補化する。

```text
LearningEpisodeReceipt
  episode_evidence_refs
  model_artifact_id
  tokenizer_hash
  exact_input_token_ids
  exact_sampled_token_ids
  sampling_config
  rng_seed_or_stream_ref
  routing_trace?          # sparse/MoE only
  tool_observation_refs
  verifier_outcomes
  reward/version
  training_projection_version
```

重要な境界:

```text
human-readable transcript equivalent
!=
training trajectory identical
```

model migration や tokenizer change の前後で、同じ自然言語 text を再tokenizeして「同じ経験」とみなさない。

### (5) Kamimusuhiとの差分

Kamimusuhi は evidence provenance と ModelArtifactClosure を強く扱うが、**経験→学習 batch への projection が exact sampled trajectory を保っているか**は別問題。特に後から transcript から再構築する dataset は、token boundary / tool observation ordering / sparse routing を失い得る。

### (6) 次に検証すべきこと

**`LearningTraceFidelityBench`**

小型 model / tiny MoE で十分。

1. exact token IDs 保存版と text-only reconstruction 版を作る。
2. tokenizer patch / chat-template update / normalization change を注入。
3. sparse routing があれば routing replay on/off を比較。
4. same episode に対する gradient / log-prob / learned behavior drift を測る。
5. receipt が不足している場合は `REPRODUCIBILITY_UNKNOWN` とする。

### (7) daily で拾いにくい理由

表面的には「terminal agent benchmark / RL post-training」の論文であり、Kamimusuhi survey では agent performance として daily 側に分類されやすい。blind spot は **学習データ lineage の byte/token-level fidelity** にある。

### (8) 判定

**A-**。今すぐ Persona Core が online learning しないなら急務ではないが、後から retrofit しにくい provenance field なので早期schema設計価値がある。

## 5.5 AAE -02 — Recomputable Effect-Admission Verdicts

**Importance: A- / standards watch**

**Source**

- IETF Internet-Draft, `draft-kroehl-agentic-trust-aae-02`, 2026-09-06 — https://www.ietf.org/ietf-ftp/internet-drafts/draft-kroehl-agentic-trust-aae-02.html

### (1) 何が実装/仕様化されているか

- AAE は `MANDATE / CONSTRAINTS / VALIDITY` を持つ structured authorization envelope を提案している。
- `-02` は verdict に ordered predicate trace を要求し、predicate / field / value / bound / PASS|FAIL を構造化する。
- verdict だけで trace がないものを non-conformant とする。
- same mandate + same transaction を評価する conforming independent verifiers が byte-identical core digest を出せることを要求する。
- verdict は `PERMIT / PENDING / DENY`。
- PENDING / DENY の後の human/authority decision は prior verdict を edit せず、prior digest を参照する ratification record を append する。

ただしこれは **Internet-Draft / work in progress**。RFC ではなく、標準として確定していない。

### (2) 何が提案・推測段階か

- AAE の DID / VC / JOSE stack を Kamimusuhi が採用すべきかは未評価。
- byte-identical verdict core が Kamimusuhi のすべての dynamic policy で可能かも未検証。
- 本稿では authorization architecture 全体を採用せず、**recomputable verdict trace と append-only ratification**だけを設計候補として抽出する。

### (3) 関係 subsystem

- Effect Acceptance
- Mutation / Activation Gate
- capability / authority lifecycle
- audit / observability
- DecisionProvenanceEnvelope
- VerificationAdequacy

### (4) 借りられる設計・実装アイデア

`EffectAdmissionReceipt`:

```text
EffectAdmissionReceipt
  policy_revision
  proposal_digest
  effect_digest
  verdict: PERMIT | PENDING | DENY
  ordered_predicates[]:
    predicate
    field
    observed_value
    required_bound
    result
  prior_receipt_digest?
  canonical_digest
```

後から authority が override / approve する場合:

```text
RatificationRecord
  ratifies_receipt_digest
  decision
  authority_ref
  authority_proof
  predicate_trace
```

prior receipt は書き換えない。

### (5) Kamimusuhiとの差分

Effect Acceptance は既に「実行直前に authority / freshness / consequence を再評価する」境界を持つ。今回の差分は decision rule そのものではなく、**判定根拠を deterministic / independently recomputable な receipt にする**こと。

また `PENDING` を「内部状態を書き換えて後から PERMIT にしたことにする」のではなく、**元の PENDING と後続 ratification を両方履歴に残す**点が canonical-history philosophy と相性がよい。

### (6) 次に検証すべきこと

**`DualVerifierAdmissionBench`**

- Rust implementation と independent Python implementation を作る。
- same proposal / policy / authority state から receipt core digest が一致するか。
- unknown predicate / malformed bound / missing field は fail-closed になるか。
- PENDING の後に approval しても prior receipt が不変か。
- ratification が別 transaction へ横展開されないか。

### (7) daily で拾いにくい理由

agent authorization の話に見えるが、Kamimusuhi で価値があるのは DID 等ではなく **deterministic audit-record semantics**。standardization draft の細部まで読まないと、既存 CapScope / Effect Acceptance と重複と判断されやすい。

### (8) 判定

**A- / watchlist**。既存原則の置換ではなく receipt format の比較対象。Internet-Draft なので normative adoption は保留。

```text

```

failure injection:

- pre-activity crash
- activity succeeded / receipt persisted前 crash
- result persisted / canonical proposal前 crash

- runtime upgrade while suspended
- wall-clock jump

成功条件:

- same revision replay: external re-call 0、command divergence 0

## 11. 結論

今回の新規性は、新しい agent framework を足すことではなく、Kamimusuhi の既存設計を **長寿命 runtime の時間軸**へ押し広げた点にある。

最優先で残すべき設計命題は次の3つ。

```text
canonical history exists
!=
recovery is replay-safe

criticality
!=
importance

freshness validity
!=
refresh priority
```

これらはそれぞれ、identity continuity、low-latency safety / degraded-mode operation、distributed embodiment / energy-aware cognition に直結する。

実装順は **`ReplayEquivalenceBench` → `CognitiveCriticalityBench` → `DecisionFreshnessBench`** を推奨する。いずれも専用 Persona Core や新規ハードウェアを待たず、現行 runtime / mock environment で falsifiable な形にできる。
