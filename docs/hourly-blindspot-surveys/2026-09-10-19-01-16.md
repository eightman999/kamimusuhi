## 4. Executive summary

今回の strongest delta は、Kamimusuhi の「外部モデルを信用しすぎない」設計をさらに一段下げ、**検証器・起動設定・評価器・cache もまた、正しさを自動的には保証しない**と明示することだった。

特に重要なのは次の二つ。

第一に、**`VERIFICATION SUCCESSFUL != specification adequate`** である。Kani 公式自身が、property は unreachable / over-constrained harness により vacuously hold し得ることを明記している。当日 Zenn の実装記録では、29機能・49 harness がすべて successful でも、認証関数を常時 Authorized にする変異が通過したケースが報告され、その後 `cover`、mutation、intended examples を別々に機械評価する設計へ進んでいる。Kamimusuhi が Continuity Kernel や authority boundary に formal verification を入れるなら、proof success と proof adequacy を別 status にしなければ「green な安全劇場」を作り得る。

第二に、**`cognition has not started yet` は安全境界の外ではない**。TrustFall の原報告は、tested coding-agent CLI で project-defined MCP server が folder trust 後に model tool-call を待たず native process として起動する経路を示した。これは CapScope や Effect Acceptance より前の層である。Kamimusuhi の organ lifecycle にある `BOOTSTRAP → VALIDATING` を実質的な trust boundary とし、未検証の config/plugin/skill/MCP を起動前に quarantine する必要がある。

その次に、memory の graceful forgetting を評価する **restore-counterfactual**、procedural skill の **trace partial-order contract**、memory correction に連動する **derived compute artifact invalidation** が実装候補として強い。

## 5.1 Green proof を信用しすぎない: verification adequacy は別成果物にする

**Sources**

- highfar, 「第3回 AIのハルシネーションとの戦い — 検証器が保証しないものを機械で炙り出す」, Zenn, 2026-09-10  
  https://zenn.dev/highfar/articles/vacuous-weak-misaligned-constraints
- highfar, 「第2回 AIのハルシネーションとの戦い — 29機能すべてが SUCCESSFUL で、認証バイパスが通った」, Zenn, 2026-09-09 / updated 2026-09-10  
  https://zenn.dev/highfar/articles/all-green-and-auth-bypass-survived
- Kani Rust Verifier, Verification results  
  https://model-checking.github.io/kani/verification-results.html
- Kani Rust Verifier Blog, *Checking Code Reachability and Sanity Checking Proof Harnesses with kani::cover*  
  https://model-checking.github.io/kani-verifier-blog/2023/01/30/reachability-and-sanity-checking-with-kani-cover.html

**Importance: S**  
**Blind-spot class:** formal-methods meta-validation / specification adequacy / assurance theater

### 1. What is demonstrated

Kani 公式は、`SUCCESS` でも property が unreachable、あるいは harness が over-constrained なため **vacuously hold** する場合があると明記している。`kani::cover` は条件/地点への到達可能性を確認でき、cover 自体が unreachable / unsatisfiable の場合は proof harness が不完全である可能性を示す。

当日更新された Zenn の実装記録では、業務アプリ29機能・49 harness がすべて `SUCCESSFUL` の状態で、認証実装を「入力を無視して常に Authorized」に変えても verification が successful のままだった例が報告された。著者はさらに、vacuous / weak / misaligned を分け、(A) reachability/cover、(B) implementation-only mutation、(C) intended accept/reject examples の評価を別々に置く方式を実装している。

これは Kani の欠陥の主張ではない。むしろ **solver が証明する命題と、人間が守りたい境界が一致しているかは別問題**という実装上の実例である。

### 2. What remains proposed / speculative

- Zenn の事例は単一開発プロジェクトの実装記録であり、Kamimusuhi の Continuity Kernel に同じ failure rate が出ることは未実証。
- mutation operator は「思いついた壊し方」に偏る。mutation coverage 自体にも coverage problem がある。
- intended examples は stakeholder intent を近似するが、仕様の完全性を証明しない。
- formal proof と runtime assurance を組み合わせても、physical/environment semantics との misalignment は別に残る。

### 3. Kamimusuhi relevance

- Continuity Kernel
- capability / authorization pure core
- Effect Acceptance Gate
- writer epoch / fencing logic
- memory revocation / supersession logic
- Runtime Assurance
- future formal verification harnesses

### 4. Borrowable design / implementation idea

`VerificationResult` と `VerificationAdequacyReport` を別成果物にする。

```text
VerificationResult
  proof_status: SUCCESS | FAILURE | UNDETERMINED
  bounded_domain
  tool/version
  assumptions

VerificationAdequacyReport
  critical_branch_cover[]
  unreachable_properties[]
  mutation_survivors[]
  mutants_truncated: bool
  intended_examples_passed
  positive_and_negative_branch_evidence
  last_reviewed_spec_revision
```

さらに、high-stakes predicate では「常に許可」「常に拒否」「freshness 無視」「epoch 無視」「revocation 無視」などの **domain-specific canary mutants** を持つ。proof が green でも canary が生存した場合は promotion を拒否する。

### 5. Difference from current Kamimusuhi

Kamimusuhi はすでに runtime assurance と deterministic authority boundary を重視している。しかし現状の docs では、**その verifier/harness 自体の判別力を別 contract として評価する**原則は明示されていない。

新しい境界は次である。

```text
proof consistency
!= harness reachability
!= specification discriminative power
!= stakeholder intent alignment
!= runtime/environment validity
```

### 6. Next validation

**`VerifierCanaryBench` — priority S**

Continuity/authority の pure functions に意図的な変異を入れる。

- authorization が常に allow
- stale predecessor を常に accept
- writer epoch comparison を削除
- revoked capability を active 扱い
- effect receipt の idempotency key を無視
- migration fencing を no-op

合格条件:

- formal proof が failure になる、または
- adequacy layer が mutation survivor として promotion を拒否する。

metrics:

- critical-mutant kill rate
- vacuous property count
- critical branch cover satisfaction
- mutation truncation visibility
- false confidence rate (`proof=green && canary survives`)

### 7. Why daily survey may miss it

「formal verification を使うか」という通常の調査では Kani / Lean / model checking の能力比較に吸収される。ここで重要なのは **検証器の外側に、検証仕様の妥当性監査を置く二階構造**であり、agent/security 文献のタイトルだけでは拾いにくい。

**Sources**

- Rony Utevsky / Adversa AI, *TrustFall: coding agent security flaw enables one-click RCE in Claude, Cursor, Gemini CLI and GitHub Copilot*, 2026-05-07  
  https://adversa.ai/blog/trustfall-coding-agent-security-flaw-rce-claude-cursor-gemini-cli-copilot/

- ちいさなソフト工房, 「Claude Code に調査だけさせる：プロンプト例と --disallowed-tools と変更検知」, Zenn, 2026-09-10  
  https://zenn.dev/chiisanasoft/articles/75b6bd6a1cf911

**Importance: S**  
**Blind-spot class:** bootstrap security / configuration-as-code / pre-cognitive execution / ambient authority

### 1. What is demonstrated

TrustFall 原報告では、2026年5月時点で著者が試験した複数の coding-agent CLI において、repository が project-defined MCP server 設定を持つ場合、folder trust 後に MCP server が native process として起動し、**model が tool call を選ぶ前**に code execution が発生する経路が示された。CI/headless 条件では human prompt がない経路も報告されている。

2026-09-09 の Zenn 記事はこの問題を「読む前に負ける」経路として再整理し、通常の repository content scan だけでは pre-cognition startup surface をカバーできないと指摘した。これは current vendor 全バージョンの独立監査ではないので、「2026年9月時点でも全製品で未修正」と本 survey が断定するものではない。

また 2026-09-10 の別 Zenn 実装記録は、read-only 調査を prompt だけに依存させず、tool prohibition と mechanical change detection を併用している。これは Kamimusuhi の read-only organ semantics と整合する。

### 2. What remains proposed / speculative

- TrustFall の product/version-specific status は時間依存であり、本 survey では各最新 release の再 exploit を実施していない。
- Kamimusuhi は現時点で同一の MCP startup path を実装しているわけではない。
- plugin manifest の署名や digest だけでは「安全な executable」であることは保証できない。

### 3. Kamimusuhi relevance

- organ lifecycle `BOOTSTRAP → VALIDATING → READ_ONLY_SAFE / ACTIVE`
- Cognitive Action Router 起動前
- MCP / plugin / skill / external executable loader
- cloned Library/code repository intake
- self-maintenance agent
- CI / unattended background jobs
- capability root

### 4. Borrowable design / implementation idea

`PreCognitionTrustGate` / `BootstrapQuarantine` を導入候補にする。

```text
untrusted repo / config / bundle
          │
          ▼
non-executing parse only
          │
          ▼
extract executable declarations
  cmd / args / cwd / env / network / files
          │
          ▼
provenance + digest + policy + capability review
          │
     ┌────┴────┐
   DENY      ACTIVATE
              │
              ▼
      registered runtime resource
              │
              ▼
     Cognitive Action Router
```

重要な invariant 候補:

> **BOOTSTRAP / VALIDATING state MUST NOT execute repository-supplied code merely because that repository is being inspected.**

read-only mode は prompt の宣言だけでなく、(a) mutation capability を物理的に与えない、(b) 終了後に canonical DB / filesystem / process tree の変化を機械的に確認する、の二層で検証する。

### 5. Difference from current Kamimusuhi

CapScope は cognition 中の tool dispatch authority を狭める。Effect Acceptance は effect 直前を守る。今回の境界はそれより前である。

```text
PRE-COGNITION STARTUP
      ↓
Cognition / routing
      ↓
Tool dispatch
      ↓
Effect acceptance
```

一番上が無防備なら、下の3層が正しくても bypass できる。

現行 organ lifecycle には `VALIDATING` があるため、conceptual fit は良い。新規性は、その state を **実行禁止を伴う trust boundary**として具体化する点にある。

## 5.3 Restore-counterfactual: memory accuracy 低下を「忘却のせい」と決めつけない

**Source**

- Chen Shen, *What Eviction Destroys: A Restore-Counterfactual Audit of Forgetting in Agent Memory*, arXiv:2609.08279, 2026-09-08  
  https://arxiv.org/abs/2609.08279

**Importance: A+**  
**Blind-spot class:** causal evaluation / memory-loss attribution / measurement methodology

### 1. What is demonstrated

この研究は fixed-budget agent memory の accuracy loss を、単なる最終正答率ではなく **restore counterfactual** で原因分解する。各質問について gold evidence を read-time context に戻して同じ reader を再実行し、evidence が eviction 後に retained されていたかと合わせて、error を recoverable / irreversible / residual に分類する。

LongMemEval-S 上で FIFO / random / redundancy-aware / LLM-importance eviction を比較し、80k-token top-k 条件では restoration で訂正された error の irreversible share が複数手法で 0.60〜0.73、8k では全手法 1.00 になったと報告する。また retrieval regime が違えば budget-accuracy は直接比較できないと明示している。

### 2. What remains proposed / speculative

- standard conversational benchmark の結果であり、Kamimusuhi の self/relationship/procedural/canonical evidence 全領域への一般化は未実証。
- gold evidence を注入できない現実運用では、counterfactual audit は offline evaluation 手法である。
- reader stochasticity / changing model version をどう固定するかは長寿命運用で別問題になる。

### 3. Kamimusuhi relevance

- graceful forgetting
- RD-Forget / MemoryEligibilityView
- lifecycle pruning
- episodic compaction
- Library cache
- sleep/offline consolidation
- memory benchmark design

### 4. Borrowable design / implementation idea

forgetting policy の評価を最低3 branch にする。

```text
A. normal retrieval
B. retained evidence forced into read context
C. evicted/suppressed gold evidence restored into read context
```

結果を以下に分ける。

- **retrieval-recoverable**: evidence は残っていたが取れなかった
- **eviction-irreversible**: evidence が消え、restore で直る
- **reader-residual**: evidence を戻しても誤る
- **policy-suppressed-by-design**: privacy/revocation/current-state rule により意図的に不可視

最後の class を入れることで、Kamimusuhi の「forgetting ≠ deletion」「revoked history may remain historically accessible」と整合できる。

### 5. Difference from current Kamimusuhi

直前 hourly survey は storage / eligibility / erasure の意味論を分離した。今回の差分は **その memory policy の失敗を causal-ish intervention で診断する評価法**である。

### 6. Next validation

**`MemoryRestoreCounterfactualBench` — priority A+**

既存 `CurrentHistoricalMemoryBench` に restore branch を足す。

metrics:

- recoverable error rate
- irreversible eviction rate
- residual reasoning rate
- intentional suppression precision
- source-class別 loss: self / relationship / episodic / procedural / library

### 7. Why daily survey may miss it

memory architecture そのものではなく **benchmark methodology** であり、より高い retention score を出す新 memory system を追う survey では落ちやすい。しかし Kamimusuhi では「何を直すべきか」を決める diagnostic value が大きい。

## 5.4 Skill は最終回答だけでなく「順序」をテストする: trace partial-order contracts

**Sources**

- taka_yayoi, 「MLflowでAgent Skillを評価する - トレースのスパン順序で、LLM judgeなしに手順の正しさを測る」, Qiita, 2026-09-10  
  https://qiita.com/taka_yayoi/items/699a92dd93d63ed12e90
- Andres David Blandon, *Evaluating and Improving Agent Skills with MLflow*, MLflow, 2026-08-02  
  https://mlflow.org/blog/evaluating-improving-agent-skills/

**Importance: A**  
**Blind-spot class:** procedural memory QA / deterministic temporal properties / AgentOps

### 1. What is demonstrated

MLflow 公式は agent skill の評価で final correctness だけでなく execution trace を scorer に渡し、`verify_identity` が `decide_and_respond` より前にあるかを deterministic に判定する例を示す。公式例では skill instruction の修正後、Correct Tool Selection scorer が 43% から 98% に改善したと報告されている。

当日 Qiita の実装記事は、`trace.search_spans()` と `start_time_ns` を使い、LLM judge なしで「本人確認 → ledger → order lookup」等の procedural ordering を検査できることを実装レベルで整理している。また「tool を呼んだか」ではなく「いつ呼んだか」が重要であると指摘する。

### 2. What remains proposed / speculative

- trace instrumentation が欠落/改ざんされれば scorer 自体が誤る。
- span ordering は semantic correctness や authority を自動的には証明しない。
- distributed organs では wall-clock ordering より causal ordering / event IDs が必要になる可能性が高い。

### 3. Kamimusuhi relevance

- procedural memory
- Code2Skill / SCAFFOLD 系 skill acquisition の QA
- Cognitive Action Router
- Effect Acceptance
- runtime-authority-learning boundary
- self-improvement / skill maintenance
- operational trace

### 4. Borrowable design / implementation idea

`SkillTraceContract` を skill artifact と分離して持つ。

```text
SkillTraceContract
  required_events[]
  forbidden_events[]
  precedence[]
  conditional_precedence[]
  max_retry?
  terminal_receipt_required
```

例:

```text
AUTHORITY_CHECK < TOOL_DISPATCH
CURRENT_EVIDENCE_CHECK < EXTERNAL_EFFECT
EFFECT_ACCEPTANCE < EFFECT_STARTED
EFFECT_STARTED < EFFECT_RECEIPT
FAILED_MUTATION -> ROLLBACK_OR_QUARANTINE
```

`trace.jsonl` は評価用 observation として利用できるが、既存設計どおり canonical authority には昇格させない。必要なら canonical receipt ID と operational span を相互参照する。

### 5. Difference from current Kamimusuhi

現行は action state の分離と operational trace / canonical audit の分離を持つ。今回の差分は、それを **skill version ごとの executable temporal contract** としてテストする点。

### 6. Next validation

**`SkillTraceContractBench` — priority A**

同じ final answer を出す二つの skill を作り、一方だけ forbidden ordering にする。final correctness が同じでも trace scorer が failure を出せるか確認する。

さらに distributed run では causal event ID / predecessor receipt に基づく scorer と wall-clock scorer を比較する。

### 7. Why daily survey may miss it

AgentOps / MLflow の observability 記事に見えるため、cognitive architecture survey では運用 tooling として捨てられやすい。しかし Kamimusuhi の procedural self-development では **「何をしたか」だけでなく「どの順にしたか」**が safety property になる。

## 5.5 PLACEMEM: memory を直したら KV/prefix/index も古くなる

**Source**

- Sukanta Ganguly, *PLACEMEM: Toward a Compute-Aware Memory Plane for Lifelong Agents*, arXiv:2607.04089, 2026-07-05  
  https://arxiv.org/abs/2607.04089

**Importance: A**  
**Blind-spot class:** serving systems / cache coherency / correction-aware reusable compute

### 1. What is demonstrated

PLACEMEM は lifelong-agent memory を versioned capsule として扱い、semantics / provenance / validity と reusable runtime state を correction-aware に関連付ける executable control-plane prototype を提示する。current prototype では persistent capsule state、concurrency-safe invalidation、OpenAI-compatible routing sidecar、typed metadata、prompt-level retrieval、KV-aware routing / cascading invalidation が実装されている。より深い layer-frontier replay は future agenda と明示され、現行 engine feature としては主張されていない。

### 2. What remains proposed / speculative

- position/prototype work であり、Kamimusuhi 規模の multi-device autobiographical memory での長期 correctness は未実証。
- model backend ごとの KV/prefix cache semantics は異なる。
- capsule の “identity” は memory/compute artifact の identity であり、人工個体の continuity identity とは別物である。

### 3. Kamimusuhi relevance

- memory supersession / revocation
- RD-Forget / MemoryEligibilityView
- local inference prompt/KV cache
- K-Edge / K-Core serving
- multi-device cache
- Library-derived embeddings/index
- latency architecture

### 4. Borrowable design / implementation idea

**`DerivedArtifactDependencyGraph`** を置く。

```text
canonical evidence revision
   ├── episodic summary rev
   ├── embedding rev
   ├── retrieval index rev
   ├── workspace rendering rev
   ├── prompt/prefix cache rev
   └── KV/reusable compute rev
```

全 derived artifact は最低限 `source_revision_set` / `eligibility_epoch` / `built_at` を持ち、source の supersession / revocation / erasure / privacy-scope change で invalidation される。

重要なルール:

> **semantic invalidation MUST propagate to any reusable compute artifact capable of reintroducing the invalidated content.**

### 5. Difference from current Kamimusuhi

Kamimusuhi は「derived memory は canonical evidence から再生成可能」としているが、**inference-time compute cache を derived representation の一種として lineage に結ぶ**点はまだ弱い。

これを入れないと、DB 上では旧住所/旧権限が revocation 済みでも、warm prompt/KV cache から stale context が復活する可能性がある。

### 6. Next validation

**`DerivedArtifactInvalidationBench` — priority A**

- fact supersession
- relationship privacy scope narrowing
- revoked procedure
- user-requested erasure

の各ケースで、DB/index/embedding/prefix/KV/warm session を跨いで古い内容が再出現しないか確認する。

metrics:

- stale artifact reuse rate
- invalidation propagation latency
- unnecessary cache invalidation rate
- warm-latency regression
- cross-device stale resurrection rate

### 7. Why daily survey may miss it

memory research と serving optimization が別コミュニティに分かれており、通常は retrieval accuracy と TTFT/KV reuse が別々に評価される。長寿命個体では **記憶の訂正 correctness と計算再利用性能が同じ dependency graph 上にある**。

## 5.6 OKF v0.2: 外部知識の portable trust envelope として借りる。ただし authority にはしない

**Sources**

- Google Cloud, *Open Knowledge Format v0.2 tackles agentic trust*, 2026-07-24  
  https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals/
- Google Cloud, *Using OKF with Knowledge Catalog to serve context for agents*, 2026-08-26  
  https://cloud.google.com/blog/products/data-analytics/scale-okf-bundles-across-an-organization-with-knowledge-catalog
- suwash, 「技術調査 - OKF (Open Knowledge Format)」, Zenn  
  https://zenn.dev/suwash/articles/okf-open-knowledge-format_20260613
- suwash, 「エージェント知識の信頼信号を記述する形式 - OKF v0.2」, Zenn  
  https://zenn.dev/suwash/articles/okf-v02-trust-signals_20260726

**Importance: B+**  
**Blind-spot class:** knowledge interoperability / machine-readable trust metadata / external cognitive extension

### 1. What is demonstrated

OKF v0.1/v0.2 は Markdown + YAML frontmatter を基本に、agent が利用する knowledge bundle を portable に表現する軽量 format を提案する。v0.2 では provenance、trust、freshness、lifecycle、attestation を frontmatter で機械的に扱える vocabulary が追加され、Google Cloud の reference implementation / sample / catalog round-trip が公開されている。

公式説明は、これらを access-control rule そのものではなく、consumer が判断できる **signals/vocabulary** として扱っている。

### 2. What remains proposed / speculative

- emerging format であり、長期的な ecosystem adoption は未確定。
- trust metadata は producer/attester の信頼性を自動的に保証しない。
- Kamimusuhi の autobiographical / relationship / canonical state を OKF で表現すべき根拠はない。

### 3. Kamimusuhi relevance

- external Library
- multi-device knowledge exchange
- agent-to-agent knowledge handoff
- provenance / freshness
- reusable runbooks / procedural references
- external cognitive extension

### 4. Borrowable design / implementation idea

`LibraryBundleAdapter` として import/export のみ行う。

```text
OKF / other external bundle
        ↓
parse + provenance preservation
        ↓
Kamimusuhi Library record
  source URI
  source digest/version
  generated/verified metadata
  freshness/lifecycle signal
  attestation reference
        ↓
local trust/retrieval policy
```

OKF の trust tier / verified metadata は retrieval ranking や review requirement に影響してよいが、**canonical self-state mutation authority や external effect authority を与えてはならない**。

### 5. Difference from current Kamimusuhi

現行は Library を self / relationship / episode と明確に分離している。この boundary はそのまま維持する。新規差分は、Library の外部交換形式として portable bundle を利用し、provenance/freshness/attestation を失わずに ingestion できる可能性。

### 6. Next validation

**`OKFImportExportBench` — priority B**

- v0.1 / v0.2 bundle import
- unknown custom keys preservation
- stale/unstable status
- conflicting sources
- attested computation receipt
- malicious frontmatter / path traversal / executable content

を確認し、round-trip 後も provenance が保持されるか測る。

### 7. Why daily survey may miss it

data governance / enterprise knowledge format に分類されるため、personal-agent memory survey には出にくい。しかし Kamimusuhi は「知識は外にあってよい」という設計なので、**外部知識を self に焼かずに持ち運ぶ標準化**は長期的には意味がある。

## 12. Bottom line

今回の blind spot は新しい「脳モジュール」ではなく、**保証の境界そのもの**だった。

Kamimusuhi はすでに model ≠ identity、derived memory ≠ evidence、tool competence ≠ authority を分離している。次に同じ分離を、以下へ拡張する価値が高い。

```text
verification success != specification adequacy
folder/repo trust != executable startup authority
memory accuracy loss != eviction damage
correct final answer != correct procedural trace
memory correction != derived cache correction
knowledge trust signal != canonical authority
```

特に `VerifierCanaryBench` と `PreCognitionBootstrapBench` は、将来 self-maintenance / plugin / MCP / formal verification を強めるほど重要になる。ここを先に固めると、「強力な仕組みを追加した結果、別の暗黙 authority root が生まれる」事故を減らせる。
