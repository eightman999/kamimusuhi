## 1. 今回狙った盲点

1. **busy/backpressure経路が操作の意味を変える問題**  
   APPEND / EDIT / REWIND / RESTORE / DELETE / REVOKE のようなtyped operationが、実行中だからという理由で単なるtext append/redirectへ劣化しないか。

2. **相互排他はあるが公平性がないturn admission**  
   live systemが壊れていなくても、fresh claimantが既存waiterを追い越し続け、social intentがstarve/dropされないか。

3. **ageと実際のservice opportunityの混同**  
   「古いから期限切れ」と「一度でも処理可能なconsumerへ提示された」を同一視して、未試行のobligationを忘れていないか。

4. **複数の正しい制御器が共有資源上で振動する問題**  
   thermal / privacy / social / task / safety / cognitive-budget regulatorが個別には正しくても、同じactuator/resourceを反対方向へ動かし続けないか。

5. **自伝的時間の不確実性**  
   timestamp / event-time / bitemporal semanticsを持っていても、「AはBの少し前」「たぶん重なっていた」「時刻は曖昧」のような不確実な時間関係をhard orderingへ潰していないか。

6. **runtime object生成前の因果帰属**  
   `run_id`等がまだ存在しないadmission/bootstrap失敗でも、どの入力・principal・runtime scopeに属する失敗かを追跡できるか。これは既出のspawn-time failure ownershipへのfresh implementation deltaとしてのみ評価する。

## 5.1 A+ — Operation-Intent Preservation Under Backpressure

**一次資料:** Hermes PR #114977  
https://github.com/NousResearch/hermes-agent/pull/114977

### (1) 何が実証済みか

PRのregressionでは、sessionが`running=True`の間に`truncate_before_user_ordinal`等を含むedit/rewind requestを送ると、従来のbusy-input pathがそのrequestを通常textとして`queued`または`redirected`できた。つまり**本文は残るが、history cutという操作意味が消える**。

- plain agent: `status=queued`だがqueued envelopeはtextだけでtruncation fieldなし
- redirect-capable agent: `agent.redirect(text)`は呼ばれるがoriginal historyは残る
- 修正案: typed rewind requestはbusy pathで意味変換せず`4009 session busy`を返し、既存clientがinterrupt後に同じtyped operationを再送する

修正案はopen/unmergedだが、baseとのA/B regression testを報告している。

### (2) 何が提案・推測段階か

Kamimusuhiの現在runtimeで同一bugがある証拠はない。また全operationを常にqueue禁止にするべきという意味でもない。重要なのは、**defer/retry/redirectする場合もoperation kindとpreconditionを失わないこと**。

### (3) Kamimusuhi関係先

- user interaction history / Episode Memory
- conversational rewind / edit / correction
- relationship evidence correction
- Continuity Kernel
- Action Router / busy policy
- future multi-device interaction surfaces

### (4) 借りられる設計・実装アイデア

text payloadとoperationを分離する。

```text

  intent_id
  operation_kind      # APPEND / EDIT / REWIND / DELETE / RESTORE / REVOKE ...
  target_revision
  precondition_digest
  payload
  principal
  source_surface
  issued_at
  deadline
  idempotency_key
```

backpressure adapterの許可変換を明示する。

```text

# forbidden without explicit reinterpretation authority
```

### (5) Kamimusuhiとの差分

既出 **explicit negative mutation semantics** はpatch/mutation境界で`omitted != delete`を守る。**semantic transcoding integrity** はprovider wire表現からphantom eventをcanonical historyへ入れない話。本件はさらに上位の**interaction control planeがbusy時にoperation typeを落とす問題**であり、別の境界。

### (6) 次に検証すべきこと

**`OperationIntentPreservationBench-v0`**

- APPEND
- EDIT previous user turn
- REWIND
- DELETE/forget request
- RESTORE checkpoint
- REVOKE consent/capability

各intentについて、busy/defer/retry/redirect後も`operation_kind + target_revision + principal`が一致することを検証。意味を保てないruntimeは**fail closed**する。

### (7) 既存dailyではなぜ拾いにくいか

agent orchestration surveyは通常「queueできるか」「interruptできるか」を見るが、**同じpayloadでもoperation semanticsが違う**UI/runtime control-plane問題はHCIとdistributed state transitionの境界にあり、分類上こぼれやすい。

### (8) 重要度

**A+** — autobiographical / relationship historyへの誤ったappendは、単なるUX bugではなくcanonical evidenceの意味を変え得る。

## 5.2 A+ — Compositional Multi-Regulator Stability Arbitration

**一次資料:** *Taming the Agentic RAN: Stability-Guaranteed Arbitration of Autonomous AI Agents in O-RAN*, arXiv:2609.18857  
https://arxiv.org/abs/2609.18857

### (1) 何が実証済みか

論文はlive O-RAN testbedで、異なる目的を持つ2つのautonomous control agentsが同一resource partitionを更新した際、**どちらを単独で動かしても発生しないrecurring opposing excursion**を観測したと報告する。

提案するAURA arbiterは、

- feasibility invariants
- per-variable dwell time
- deadband

- Cognitive Budget
- thermal-sustainable cognition
- K-Nerve / K-Edge reflex and regulation
- multi-device embodiment
- privacy/safety/task-resource regulators
- future multi-agent / branch governance

## 5.3 A — Fair Turn Admission & Intent Conservation

**一次資料:** Hermes PR #115009  
https://github.com/NousResearch/hermes-agent/pull/115009

### (1) 何が実証済みか

PRは、conversation turn leaseがstrict mutual exclusionのみでqueueを持たないため、wait中のdeliveryがtimeoutすると**何もdurableに残らずdrop**されること、さらにrelease後およそ0.2秒のwindowでfresh claimantがpolling waiterを追い越せると報告する。

修正案は:

- wait開始を`session_turn_waiters`へpublish
- oldest waiterへhandoffするFIFO fairness
- timeoutしたinbound deliveryをconversation spoolへ保存
- receiptに`status=queued / holder / waiter_age / queue_depth`
- next admitted turnでspoolをexactly once drain

focused 18 tests、stack全体258 pass / 1 skippedを報告。調査時点open/unmerged。

### (2) 何が提案・推測段階か

FIFOがKamimusuhiの全surfaceで最適とは限らない。緊急sensor/interrupt、人間発話、background reflectionはpriority classが必要。ただし**priority付きでもstarvation boundを明示する必要がある**。

### (3) Kamimusuhi関係先

- multi-surface user interaction
- social input admission
- K-Edge → K-Core event handoff
- orchestration / workspace access
- background vs foreground cognition
- distributed embodiment

### (4) 借りられる設計・実装アイデア

priority queueを使うならagingまたはbounded unfairnessを入れる。

### (5) Kamimusuhiとの差分

## 5.5 A — Probabilistic Episodic Temporal Relations

**一次資料:** Eggert et al., *PAA: The Probabilistic Allen Algebra*, arXiv:2609.20634  
https://arxiv.org/abs/2609.20634

### (1) 何が実証済みか

PAAはAllenのcrisp interval relationsを、uncertain interval boundariesの確率分布から生成する形式化を提示する。

- time point: Gaussian
- interval: Gaussian midpoint + truncated-Gaussian duration
- 13 relationsをcommon probability spaceで扱う
- contact relationsにtolerance bandを導入
- single toleranceの下でrelationsはpartitionを形成
- tolerance→0でcrisp Allen relationへ戻る
- Monte Carlo validationを実施
- tested Python packageを公開と報告

これは**agent autobiographical memoryでの有効性**を検証した研究ではない。

### (2) 何が提案・推測段階か

Kamimusuhiへの適用は推測段階。自然言語の「先週くらい」「少し前」「同じ頃」をGaussianで表せるとは限らず、multi-modal / heavy-tailed / source-dependent uncertaintyが必要かもしれない。

### (3) Kamimusuhi関係先

- Episode Memory
- autobiographical narrative
- relationship timeline
- bitemporal evidence
- event-time watermark / late evidence
- reconsolidation / reinterpretation

### (4) 借りられる設計・実装アイデア

canonical episodeへhard relationを書き込むのではなく、source evidenceとderived temporal beliefを分離する。

```text
TemporalEvidence
  source_id
  stated_time / observed_time
  uncertainty_model
  capture_time
  provenance

TemporalRelationBelief
  episode_a
  episode_b
  relation_probs   # before / overlaps / during / meets ...
  derived_from[]
  derivation_version
  confidence_epoch
```

「AがBより前」を1 bit factにせず、後から証拠が増えたらderived relationだけ再計算する。

### (5) Kamimusuhiとの差分

既存 **bitemporal memory** はvalid-time / transaction-time、**event-time watermark** はlate event completenessを扱う。どちらも基本的に「時刻/区間が与えられた後の整合性」が中心。本件は**その時間自体が不確実**なケース。

### (6) 次に検証すべきこと

**`ProbabilisticEpisodicTimeBench-v0`**

- exact sensor timestamps
- user narration: 「たぶん火曜の夜」
- conflicting calendar evidence
- late-arriving photo metadata
- overlapping uncertain intervals

を混在させ、

- premature hard ordering rate
- later correction時のcanonical rewrite数
- relation calibration
- narrative query accuracy

をcrisp timestamp baselineと比較する。

### (7) 既存dailyではなぜ拾いにくいか

AI memory surveyはretrieval/context長に寄り、temporal DB surveyはexact timestamp semanticsへ寄る。**qualitative temporal reasoning × probabilistic uncertainty × autobiographical memory**の交差点は見落とされやすい。

### (8) 重要度

**A** — 人間から得る自伝的情報はexact timestampより曖昧時間の方が多く、長期identity timelineでhard orderingを乱用しないために有用。

## 5.6 B+ delta — Pre-Run Causal Correlation

**一次資料:** Letta Code PR #4532  
https://github.com/letta-ai/letta-code/pull/4532

### (1) 何が実証済みか

APIがinputをacceptした後、**runを作る前にreject**すると、listenerは`run_id`なしterminal errorを出す。従来waiting CLIはrun-id-less eventをdiscardしdeadlineまで待った。

修正案は既存`client_message_id`をterminal eventへ載せ、CLI側で

```text
runtime scope matches
AND
owned input id matches
```

の場合だけrunless failureを受理する。real API pre-run rejectionを使ったproduct checkでは約3.2秒でnonzero exitし、run IDは0件だったと報告。focused 69 tests pass。調査時点open/unmerged。

### (2) 何が提案・推測段階か

Kamimusuhiで同じprotocolを使う必要はない。重要なのは`run_id`より前に**causal request identity**を発行すること。

### (3) Kamimusuhi関係先

- execution ownership
- subagent spawn / tool invocation
- Action Router admission
- external cognitive-resource invocation
- recovery attribution

### (4) 借りられる設計・実装アイデア

`run_id`をprimary correlation keyにしすぎない。

```text
CausalRequestId   # admission前に発行
  principal
  runtime_scope
  intent_id
  issued_at

RunId             # 作成できた場合だけ後からbind
```

terminal eventは`run_id`がなくても`causal_request_id`を必須にする。

### (5) Kamimusuhiとの差分

これは**新しい原則ではない**。2026-09-15 blind-spotで既に扱った **spawn-time failure ownership** の具体的実装delta。今回新しいのは、`run_id`が存在しない段階の帰属に **input ID + runtime scope** の組を使う実例が増えたこと。

### (6) 次に検証すべきこと

既存spawn-time failure fixtureへ以下を追加する。

- reject before run creation
- wrong-runtime terminal event
- same input id / different runtime
- duplicate pre-run terminal event
- crash between admission receipt and run allocation

**独立benchを増やさず、既存benchを拡張する。**

### (7) 既存dailyではなぜ拾いにくいか

tool executionの観測はrun/task objectが生成された後を前提にしやすい。失敗が**object生成より前**に起きるbootstrap seamは狭く、実運用incidentから出やすい。

### (8) 重要度

**B+ delta** — 既存原則のreinforcementであり、新規architecture pillarではない。

## 10. 結論

今回の最重要差分は、**「内容を保存する」より上位に「操作の意味を保存する」契約が必要**という点と、**「各regulatorが正しい」だけでは長寿命個体全体のhomeostasisは安定しない**という点。

特にKamimusuhiでは今後、

```text
user correction / rewind / revocation
multiple interaction surfaces
thermal / resource / privacy / social regulators
delayed sensor and social events
offline/online body transitions
```

が同時に存在するため、単純なmutex・TTL・last-write-wins・hard timestampでは足りない。

今回追加候補を一行でまとめると:

> **intentには型を、waitingには公平性を、expiryにはservice opportunityの証拠を、regulatorには合成安定性を、episodic timeには不確実性を持たせる。**
