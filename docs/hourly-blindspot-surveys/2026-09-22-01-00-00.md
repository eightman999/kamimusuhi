# 5. 候補ごとの評価

## 5.1 A — Failure-Origin-Typed Async Outcomes

**Primary source:** Hermes #118319  
https://github.com/NousResearch/hermes-agent/pull/118319

### (1) 何が実証済みか

Python 3.11以降では`concurrent.futures.TimeoutError`がbuiltin `TimeoutError`のaliasになっているため、`future.result(timeout=...)`が投げるpoll timeoutと、**worker自身が終了時に投げた`TimeoutError`**が同じclassになる。Hermesの複数poll loopは例外classだけで「まだworkerがrunning」と判断し、settled futureを再pollした。

PR記載では、`_await_worker_within_budget`は約2k iterations/sでceilingまでspinし、ceilingのない`_await_in_flight_commit`は永久spinし得た。修正は`except TimeoutError`内で`future.done()`を確認し、doneならworkerのactual outcomeを返す/再raiseし、poll timeoutだけをstall pathへ送る。関連testsでbase上のhang再現とfix後のprompt returnが示されている。

### (2) 何が提案・推測段階か

Kamimusuhi全体をPython例外class設計へ合わせる必要はない。一般化するのは、**failureのsemantic originをexception nameから推測しない**こと。

```text
FailureObservation {
  origin: SUPERVISOR_DEADLINE | WORKER | TRANSPORT | PROVIDER | CANCELLATION | POLICY
  operation_id
  worker_incarnation
  deadline_id?
  terminal
  retryability
  cause
}
```

### (3) 関係するサブシステム / 設計課題

- Background cognition workers
- sleep/dream/consolidation jobs
- context compression
- Cognitive Action Router / tool execution
- K-Deep delegation
- recovery / observability / telemetry

### (4) 借りられる設計・実装アイデア

- supervisor timeoutは`DeadlineExpired(deadline_id, target)`のようにoriginを持つtyped eventにする。
- childのfailureはtask completion recordから読む。catchした型だけでrunning/terminalを決めない。
- `terminal=true`のfuture/taskを同じwait pathへ戻さない。
- telemetryに`wait_timeout`と`child_timeout_error`を別metricで出す。

### (5) Kamimusuhiとの差分

既出 **Deadline Closure** は「timeoutを通知してもcleanup/joinでwall-clock budgetを超える」問題、**causal attempt trail**はretry履歴を扱う。今回の差分はもっと手前の、**同じ表面的error labelが別のcausal sourceを持つとき、lifecycle stateを誤分類する**問題。

### (6) 次に検証すべきこと

**`FailureOriginTypednessBench-v0`**

- supervisor poll timeout
- worker内部が同名`TimeoutError`
- provider HTTP timeout
- cancellation during timeout
- worker successとpoll timeoutのrace
- restart後にserialized failure originが保たれる
- same display stringでもretryability/terminal stateが異なるfixture

成功条件: worker-origin terminal failureをrunningへ戻さず、supervisor-origin wait expiryをworker failureとして記録しない。

### (7) 既存dailyではなぜ拾いにくいか

通常のfault tolerance検索では「timeout/retry policy」に集約されやすい。今回の障害はlanguage/runtimeのexception aliasとasync lifecycleの接合部に現れ、AI-agent論文や高レベルorchestration surveyからは見えにくい。

### (8) 重要度

**A**。long-lived agentのbackground/maintenance workerでは同種の待機が大量に発生し、誤分類がCPU spin、lease残留、commit待ち永久化へ波及する。

## 5.2 A — Origin-Bound Mutable Views: read provenanceをwrite targetへ運ぶ

**Primary source:** Hermes #118327  
https://github.com/NousResearch/hermes-agent/pull/118327

### (1) 何が実証済みか

Hermes Desktopではconfig GET時にはconnection + profileでrouteされる一方、save時にambient `connectionScoped()`を再解決していた。このため、connection A / profile Pから読んだrecordを編集中にprimary/ambient connectionがBへ変わると、**同じUI objectのsaveがBへ書き込まれ得た**。

修正はread originをrecordへstampし、saveは `explicit pin > captured origin > ambient` でwrite scopeを決める。derived recordsやReact Query refetch/structural sharingでもoriginを引き継ぐ。PRはread-under-A → ambient-switch-to-B → save-still-Aというinvariant testを提示し、関連451 tests greenと報告している。

### (2) 何が提案・推測段階か

Kamimusuhiで全read objectをmutable capabilityにする必要はない。ただし、**readしたstateを編集して戻す操作**には、object/revision/owner/route provenanceを一体で持つ価値が高い。

### (3) 関係するサブシステム / 設計課題

- Continuity Kernel admin/control surfaces
- distributed K-Edge / K-Core
- self/persona editor
- relationship memory / consent settings
- device registration
- model / routing / privacy policy config

### (4) 借りられる設計・実装アイデア

```text
MutableView<T> {
  value
  source_owner
  source_namespace
  source_revision
  source_route
  read_at
}
```

write時は`source_*`へbindし、current ambient ownerが変わっていればexplicit rebase/reloadを要求する。これはobject-capabilityの「designationとauthorityをambient environmentから分離する」考え方とも相性がよい。

### (5) Kamimusuhiとの差分

既出 **remediation target binding / execution-owner binding** はdiagnosis→repairやruntime effectのownerを主に扱う。今回の差分は、**長寿命UI/view object自体がread provenanceを保持し、derived viewを経てもwrite destinationがambient routingで漂流しない**こと。

### (6) 次に検証すべきこと

**`OriginBoundMutableViewBench-v0`**

- Aでself-stateをread → 編集中にactive coreをBへpromote → saveはA revisionへCAS、または明示rebase要求
- A/profile P → B/profile Qへの誤write禁止
- derived display record / translated view / cached viewでorigin保持
- refetchで新revisionへ置換時はorigin/revisionも更新
- owner消失時はambient fallbackせずfail closed

### (7) 既存dailyではなぜ拾いにくいか

distributed identityではserver-side single-writerやleaseへ注目しやすく、**人間が数秒〜数分保持するUI objectがauthority routeを跨いで生きる**問題はHCI/data-bindingの層に隠れる。

### (8) 重要度

**A**。multi-device embodimentで「Aを見ていたのにBを書いた」はidentity/config/consentの誤mutationへ直結する。

## 5.3 A — Explicit Context-Role Provenance: semantic roleをpathから推定しない

## 5.4 B — Capability-Constrained Cognitive Effort Projection

**Primary source:** Hermes #118328  
https://github.com/NousResearch/hermes-agent/pull/118328

### (1) 何が実証済みか

Hermesのmanual thinking pathではvalid reasoning effort 7段階のうち4段階しかbudget tableになく、`max`/`ultra`/`minimal`がfallback 8000 tokensへ落ちていた。そのため**より深い`max`要求が`xhigh`より少ないcompute**になる逆転が起きた。

さらにthinking budgetから`max_tokens`を持ち上げる処理がmodel output ceiling/context clampより後に走り、8192-token ceilingに対して`budget_tokens=32000, max_tokens=36096`のillegal requestを生成できた。修正は全effortをmappingし、thinking budget + visible response roomをmodel/context ceiling内へclampする。

### (2) 何が提案・推測段階か

`max/high/medium`をtoken数へ直接固定する必要はない。Kamimusuhiではproviderごとに意味が違うため、抽象Cognitive Budgetをcapability-awareに投影し、**requested と effective**を分けるべき。

### (3) 関係するサブシステム / 設計課題

- Cognitive Budget
- Cognitive Action Router
- K-Core / K-Deep
- external model delegation
- low-latency cognition
- observability / cost accounting

### (4) 借りられる設計・実装アイデア

```text
EffortProjection {
  requested_level
  provider
  model
  effective_budget
  answer_reserve
  limiting_constraint
  saturated
}
```

- capacityが許す範囲ではeffort orderingをmonotoneに保つ。
- saturateして同値になる場合は隠さずreceiptへ出す。
- reasoning budgetだけでoutput roomを食い尽くさない。

### (5) Kamimusuhiとの差分

既存Cognitive Budgetはresource量を表すが、今回の差分は**abstract intentからprovider-native knobへのprojection自体をcontract化する**こと。Reason-Carrying Escalationは「なぜ高価なrouteへ上げたか」を扱い、ここでは「上げた意図が実際にどのcomputeへ変換されたか」を扱う。

### (6) 次に検証すべきこと

**`CognitiveEffortProjectionBench-v0`**

- 全provider/modelでeffort ordinal monotonicity
- model ceiling/context limit/answer reserveとの同時制約
- saturation時のeffective effort observability
- unsupported levelをsilent medium fallbackしない
- route変更時に同一requested intentを比較可能なreceiptへ残す

### (7) 既存dailyではなぜ拾いにくいか

orchestration surveyはmodel選択やcost/latencyへ寄り、provider adapter内部で**努力レベルの意味が逆転する**ようなsemantic impedance mismatchは見落としやすい。

### (8) 重要度

**B**。identity continuityを直接壊すほどではないが、variable-depth cognitionを設計目標にするKamimusuhiでは重要な実装契約。

## 5.5 B — Clock-Basis-Qualified Temporal Semantics（systems backfill）

**Primary references**

- Python `time.monotonic()` docs: https://docs.python.org/3/library/time.html
- Linux `timerfd_create(2)`: https://man7.org/linux/man-pages/man2/timerfd_create.2.html
- Linux `clock_gettime(2)`: https://man7.org/linux/man-pages/man2/clock_gettime.2.html

### (1) 何が実証済みか

これは新規論文ではなくOS/runtimeの確立した仕様である。

- wall-clockは時刻補正によりjumpし得る。
- monotonic clockはsystem clock updateで後退しない。
- Linux `CLOCK_MONOTONIC`はsuspend中の時間を数えない。
- `CLOCK_BOOTTIME`はsuspend中も進み、suspend-aware timerに向く。

したがって、`expires_in=30s`や`lease_ttl=5m`という値だけでは意味が不足する。端末sleep中に期限が進むべきかどうかで正しいclockが変わる。

### (2) 何が提案・推測段階か

Kamimusuhiで全時間を一種類へ統一するのではなく、temporal contractごとにbasisを選ぶ。

```text
ClockBasis =
  WALL_CALENDAR
  MONOTONIC_ACTIVE
  BOOTTIME_SUSPEND_AWARE
  LOGICAL_REVISION
```

### (3) 関係するサブシステム / 設計課題

- continuity lease / fencing
- K-Edge sleep/wake
- credential/consent expiry
- retry/deadline
- social presence / typing timeout
- background job scheduling
- offline/multi-device reconciliation

### (4) 借りられる設計・実装アイデア

- duration/deadline型に`clock_basis`を必須化する。
- human calendar appointmentはwall clock、process-local deadlineはmonotonic、device lease expiryは用途に応じてBOOTTIME、canonical orderingはlogical revisionを検討。
- persisted leaseでprocess-local monotonic timestampをそのまま別hostへ移送しない。

### (5) Kamimusuhiとの差分

既出のOpportunity-Qualified Expiry、Deadline Closure、temporal obligationは「いつ期限とみなすか」のpolicyを扱うが、**その期限を測るclock自体のsemantics**は明示されていない。

### (6) 次に検証すべきこと

**`ClockBasisSemanticsBench-v0`**

- wall-clockを±1h jump
- NTP step相当
- laptop suspend 10m / resume
- VM migration / container time namespace
- restart後のpersisted deadline
- multi-device leaseで異なるwall-clock skew

成功条件: duration-based safety deadlineがclock correctionで延命/即死せず、suspend中に進むべきleaseだけが進む。

### (7) 既存dailyではなぜ拾いにくいか

AI-agent文献ではdeadline/TTLをscalarとして書くことが多く、OS timekeepingの`CLOCK_MONOTONIC` vs `CLOCK_BOOTTIME`差は実装層へ埋没しやすい。

### (8) 重要度

**B**。今すぐのmodel qualityには効かないが、multi-device / always-on / sleep-wakeを本気で扱う長寿命個体ではsplit-brainや誤expiryの原因になり得る。

## 6. 既存docsへの追記候補

### `spec.md`

採用候補は次の3つ。

1. **Failure origin invariant**
   - failure/timeout/cancellationは少なくともoriginとtarget lifecycleを失わない。
   - same display/error typeをsame semantic stateとみなさない。
2. **Mutable-view target binding**
   - source-bound mutable viewはwrite時にsource owner/namespace/revisionを保持するか、explicit rebaseする。
3. **Context role provenance**
   - self/personal/shared/relationship/library等のsemantic roleをstorage locator/pathだけからauthority-bearing classificationしてはならない。

## 10. 最終判断

今回の収穫は、long-lived cognitionの堅牢性が「何を覚えるか」「誰がauthorityを持つか」だけでは閉じず、**error・view・context role・effort・timeの意味をどこで型付けするか**に依存するという点である。

特に優先度が高いのは次の3点。

1. `TimeoutError`のような表面的labelではなく、**誰が・どの境界で発生させたfailureか**を保持する。
2. distributed UIでreadしたstateのoriginを、save時まで**ambient routingから独立して保持する**。
3. personal/shared/self/libraryというsemantic roleを、filesystem pathや名前の雰囲気ではなく**explicit provenance**から決める。

これらはKamimusuhiの既存Continuity Kernelを置き換える話ではなく、Kernelへ入る前のrepresentation/dataflow境界を硬くする補完契約である。
