# 5. 候補ごとの評価

## 5.1 A — In-flight Effector Lifetime Pinning

**一次資料:** Hermes #114624, #114506

### (1) 何が実証済みか

#114624では、`_get_backend()`で得たBot Screen backendが、display/mode変更やconcurrent releaseによりcallerのdispatch前にretireされ得る。さらにcall lockを別lookupすると、**old backend + new lock**という不整合pairも作れる。修正案はprofile-scoped call lockを先に確保し、backend/lock pair・permission mode・displayを再検証してからdispatchをadmitする。admitted callはteardownより先に完了し、retired selectionは再admissionする。旧実装で8/8 regression casesがfailし、修正後12 lifecycle/lease casesがpassと報告されている。A→B→A profile isolation、release、display/mode変更、human takeover/hand-back、unknown result時no replayも含む。

#114506は別経路の同型failureで、idle reaperが「会話側が長いprovider callで静か」な間にsandboxをreapし、callerがdead handleを保持し得る。修正案はreaped resourceをstampし、後続foreground executionを明示errorで拒否する。

両PRとも調査時点open/unmergedなので、upstream確定仕様ではない。ただしraceの再現とregression fixtureは具体的。

### (2) 何が提案・推測段階か

KamimusuhiのK-Edge/ロボット/GUI backendに同じ実装raceが存在する証拠はない。また「lockを取る」が一般解ではなく、remote actuatorやnetwork toolではlease/refcount/epoch/pin token等の別実装が必要。

### (3) 関係するKamimusuhiサブシステム/設計課題

- Action Router / effect admission
- K-Edge / Physical AI / device actuation
- computer-use / GUI control
- sandbox / tool executor
- multi-device embodiment / embodiment migration
- human takeover / authority handoff

### (4) 借りられる設計・実装アイデア

**lookup → validate → dispatch** の間をatomicなlifetime borrowとして扱う。

```text
EffectorBorrowReceipt
  effector_id
  incarnation_id
  lease_epoch
  principal / authority_epoch
  admitted_at
  permission_mode_digest
  endpoint/display binding
  release_fence
```

- effect admission時にcurrent incarnationを再検証
- active borrowがある間はdestructive teardown/rebindを待機
- takeover/revoke時はresult acceptanceも再検証
- outcome unknownのside effectは自動replayしない
- stale handleは「fresh resourceを取り直してretry可能」と「effect outcome unknown」を区別する

### (5) Kamimusuhiとの差分

既存 **capability freshness** は「まだその権限を使ってよいか」、**causal embodiment binding** は「このturnがどの身体endpointへ向かうか」を守る。本件は、その2つを通過した後の **resource lifetime race** を守る。

したがって追加すべき境界は:

> `authorized + correctly bound != alive/pinned through effect completion`

### (6) 次に検証すべきこと

**`EffectorLifetimeAdmissionBench-v0`**

- lookup直後 / lock待ち / approval待ち / dispatch中にrebind, release, human takeover, process reapを注入
- stale incarnationでeffectが発火しない
- admitted effect中はteardownが待つ
-別profile/別deviceの進行はblockしない
- A→B→Aで旧A incarnationを再利用しない
- effect result不明時は自動replayしない
- stale handle errorとauthority revoke errorを区別する

### (7) 既存デイリーサーベイではなぜ拾いにくいか

AI agent / roboticsの能力論ではなく、OS resource reclamation、concurrency、GUI backend lifecycleの交差点にあるため。単なる「stale capability」で検索するとdispatch中のlifetime pinningが落ちやすい。

### (8) 重要度

**A** — distributed embodimentとPhysical AIでは誤actuation / wrong-body effectへ直結する。

## 5.2 A — Factorized Terminal Outcome & Causal Attempt Trail

**一次資料:** Hermes #114636, #114505

### (1) 何が実証済みか

#114636ではlive profile ledgerをread-only計測し、`delivery_outcome='failed'` が10件ある一方、全10件が `status='completed'` で `error` は空だった。delivery reason自体はscheduler中で計算され、`jobs.json`のlatest fieldには存在していたが、per-attempt ledgerへ保存されず、次回成功runでlatest reasonも上書きされる。修正案はjob failure用`error`とは別の`delivery_error`を持ち、execution successと独立して永続化する。cron suite 1445 pass等が報告されている。

#114505ではfallback chainを歩いた後、terminal `api_error`が**最後に失敗したhopだけ**を表すため、primary failure、skipped candidate、そのskip理由、chain exhaustionがresult surfaceから消えていた。修正案はbounded structured `fallback_trail` に各hopの`failed/skipped/exhausted`と理由を記録し、configから推測した「backup provider」説明より実際のwalk evidenceを優先する。

両PRともopen/unmerged。#114636のlive observationはfailure reasonが消えている事実の証拠だが、修正後e2e delivery failureは未取得。#114505もfunction-boundary検証中心で、修正後live cron incidentはまだない。

### (2) 何が提案・推測段階か

Kamimusuhiで必ず同じschema bugが起きるとは限らない。また全ての内部routing detailをユーザーへ表示すべきとは限らず、privacy/security上のredaction層が必要。

### (3) 関係するKamimusuhiサブシステム/設計課題

- scheduler / prospective memory
- Cognitive Action Router / fallback providers
- observability / incident RCA
- recovery policy / degraded-mode operation
- delivery / notification / social presence
- self-modelの「何が苦手/壊れているか」更新

### (4) 借りられる設計・実装アイデア

1個の`status/error`へ圧縮せず、**Outcome Bundle**を持つ。

```text
OutcomeBundle
  execution:  {status, reason}
  delivery:   {status, reason, target}
  routing:    {selected, attempts[], skips[], terminal_reason}
  authority:  {admission_verdict, epoch}
  evidence:   {trace_refs, attempt_ids}
```

human-facing summaryはこのcanonical outcomeからderived projectionとして作る。routing trailは bounded / redacted でも、canonical ledgerではattempt単位の因果を失わない。

### (5) Kamimusuhiとの差分

既存 **completion-publication barrier** / specの実行と配信の分離は、「成功phaseが別」であることを守る。本件はさらに、**各phaseのfailure reasonとroute causal chainがdurable evidenceとして残ること**を要求する。

> `phase separation != evidence preservation`

### (6) 次に検証すべきこと

**`FactorizedOutcomeLedgerBench-v0`**

- work success + delivery failure
- primary 429 → fallback skip(unentitled) → next fallback timeout → exhaustion
- delivery failureの次runが成功
- restart / compaction / UI summary後も過去attempt reasonが消えない
- user-facing summaryをredactしてもcanonical incident evidenceは保持
- `error`一列へflattenしたlegacy readerでもexecution failureとdelivery failureを誤同一視しない

### (7) 既存デイリーサーベイではなぜ拾いにくいか

モデル/agent能力ではなく、DB schema・failure reporting・routing observabilityという運用基盤の問題。final errorだけを見る評価では、**失われた中間因果**自体を観測できない。

### (8) 重要度

**A** — 長寿命agentでは、後から「なぜ失敗したか」を再構成できることがself-repairとtrustの前提になる。

## 5.3 A — Semantic Effect Payload Health Gate

**一次資料:** Hermes #114504

### (1) 何が実証済みか

issue由来のfailureでは、モデルが退化loopに入り、同一行を約200回含む約15〜18KBのheredocをtool-call argumentとして出力した。payloadは**well-formed JSON**として正常parseされ、そのまま実行可能だった。既存visible-text repetition guardはtool callを持つturnではこの形を見ないため、防げなかった。

PRはstreaming tool-args assemblyで`is_repetition_dominated(arguments)`を適用し、反復dominantなwell-formed argsをtool dispatchせず「dropped tool call」としてpartial-stream retry/abortへ送る。長いが健全なpayloadと短いpayloadは通すcontrolも含み、同PRのfocused suiteは44/44 greenと報告。

調査時点open/unmerged。

### (2) 何が提案・推測段階か

repetition scoreが一般的なsemantic sanity判定の十分条件ではない。画像pixel array、テストfixture、データ変換等には正当な高反復payloadがあり得る。また反復でない危険な退化もある。

### (3) 関係するKamimusuhiサブシステム/設計課題

- Action Router / tool dispatch
- K-Nerve / low-latency effect path
- model orchestration / partial generation recovery
- safety / runtime assurance
- self-modifying code / shell / file-write tools

### (4) 借りられる設計・実装アイデア

Tool argument validationを段階化する。

```text
PARSE_VALID
  -> SCHEMA_VALID
  -> PAYLOAD_HEALTH_VALID
  -> POLICY_VALID
  -> AUTHORIZED
  -> EXECUTE
```

`PAYLOAD_HEALTH_VALID`ではtool-specificに、反復率、size/budget、entropy collapse、同一command streak、unexpected fan-out等を確認する。判定不能なら「実行失敗」ではなく「generation incomplete / dropped effect」として再生成・abstainへ戻す。

### (5) Kamimusuhiとの差分

既存Activation Gateやtool policyはartifact/toolの権限・安全性を扱うが、本件は**正規のtool、正規のschema、正規のauthorityを通った後でも、生成payload自体が認知退化している**ケース。

### (6) 次に検証すべきこと

**`SemanticEffectPayloadHealthBench-v0`**

- repeated heredoc / repeated file patch / repeated HTTP body / repeated actuator command
- 長いが正常なscript・表・画像的配列をfalse positiveにしない
- short payloadはfail-open
- health gate trip時にeffectが一度も発火しない
- retryで同一degenerate payloadが続く場合はbounded stop
- model-visible explanationとcanonical incident reasonを分離

### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常のagent safetyはmalicious input、policy violation、schema validationへ寄りがちで、**内部generation degenerationがstructured tool envelopeに隠れる**ケースは見落とされやすい。

### (8) 重要度

**A** — shell/file/robotic effectorでは、syntax-validな退化がそのまま外界作用になるため。

## 5.4 A — History-Conditioned Prospective Runtime Assurance (SplitLTL)

**一次資料:** Ulus, *Runtime Verification under Split Past and Future*, arXiv:2608.20783

### (1) 何が実証済みか

論文はSplitLTLを形式化し、各ruleを **PastLTL antecedent + FutureLTL consequent** に分ける。observed execution prefixでpast componentをincremental monitoringし、その時点で有効化されたfuture requirementを、外部のprediction moduleが出す複数candidate continuationへ適用するmonitoring architectureを示す。future formulaは時間反転してpast-time monitor基盤を再利用できることも説明する。

これは形式仕様・monitor architectureの提示であり、KamimusuhiやLLM agent上での安全性改善を実証したものではない。論文自身もfuture-monitoring costやprediction qualityを今後の課題としている。

### (2) 何が提案・推測段階か

LLM plan / tool sequenceを有限state trajectoryへどう落とすか、prediction branchを何本出すか、Physical AI以外の社会的/記憶的obligationへ適用可能かはKamimusuhi側の研究課題。

### (3) 関係するKamimusuhiサブシステム/設計課題

- K-Nerve / Physical AI runtime assurance
- Action Router / candidate plan filtering
- authority / human takeover
- homeostasis / degraded-mode operation
- memory ownership / consent
- prospective memory / future obligations

### (4) 借りられる設計・実装アイデア

**過去が未来のcontractをactivateする**形式を追加する。

例:

```text
PAST: authority_revoked(device_X)
FUTURE: G(no_actuation(device_X)) U reauthorized(device_X)

PAST: energy_critical
FUTURE: within H steps -> recharge OR enter_safe_degraded_mode

PAST: memory_consent_withdrawn(source_S)
FUTURE: G(no_retrieval_or_promotion_from(S))
```

Action Routerがcandidate plan/trajectoryを出した後、current history monitor stateに応じてfuture branchをfilterする。

### (5) Kamimusuhiとの差分

既出DynamicSafetyEnvelope / closed-loop verifierはstate-space safetyやcontroller dynamicsを主に扱う。SplitLTL差分は、**同じcurrent stateでも過去の出来事によって未来の義務が変わる**ことをfirst-classにする点。

### (6) 次に検証すべきこと

**`HistoryConditionedContinuationAssuranceBench-v0`**

- 同一current observationだが異なるhistory prefixを2本用意
- candidate future setは同じにする
- revoke / takeover / near-miss / energy-critical / privacy withdrawalをpast triggerにする
- historyに応じてadmissible continuation setが変わること
- future monitor latencyをK-Nerve budget内で測定
- prediction不足時は「safeと証明済み」と誤表示しない

### (7) 既存デイリーサーベイではなぜ拾いにくいか

formal runtime verification / temporal logicはAI agent検索語から外れやすく、robotics safetyでも「現在のstate envelope」へ寄せるとhistory-conditioned obligationを落としやすい。

### (8) 重要度

**A** — Kamimusuhiのcontinuityそのものを、「過去に起きたことが未来の許容行為を変える」という実行contractへ接続できる。

## 5.5 B — Human Intervention as Social Circuit-Breaker Reset Evidence

**一次資料:** Hermes #114504

### (1) 何が実証済みか

bot-to-bot loop guardがtripするとcooldown後にre-armしていたが、event budget自体が社会的にresolveされた証拠を持たないため、次のbot exchangeですぐ再tripし得た。PRは、blocked conversationに**authorized human message**が入った時だけ、そのconversationのcooldown/event budgetをresetする。regression testはguardをtrip→human message→次のbot messageをadmit、という遷移を確認する。

### (2) 何が提案・推測段階か

「人が一言話した = loopが解消した」が常に正しいとは限らない。human messageが単なる参加で、reset intentではない場合もある。したがってKamimusuhiでそのまま採用するより、human interventionをreset evidenceの一種として扱うのが妥当。

### (3) 関係するKamimusuhiサブシステム/設計課題

- Social Harness / multi-agent governance
- relationship / conversation state
- human override / supervisory control
- degraded social mode / circuit breaker

### (4) 借りられる設計・実装アイデア

```text
SocialCircuitBreaker
  TRIPPED
  -> human_intervention / explicit_review / new_epoch
  -> RESETTABLE
  -> ACTIVE
```

時間経過は`retry_eligible`にしても、`resolved`の証拠とは別にする。reset receiptにはprincipal、conversation id、reason、epochを残す。

### (5) Kamimusuhiとの差分

既存Social Harnessはagent間communicationのprevent/runtime/postmortem境界を扱うが、**trip後に何をもって再参加させるか**のreset semanticsは薄い。

### (6) 次に検証すべきこと

**`SocialCircuitBreakerResetEvidenceBench-v0`**

- bot-only loopでtrip
- cooldownだけではresolvedにしない構成と比較
- authorized human intervention / explicit reset command / moderator reset
- bot spoofingでresetされない
- conversation Aのhuman発話がconversation Bをresetしない
- reset後も短時間で再発する場合はbackoff強化

### (7) 既存デイリーサーベイではなぜ拾いにくいか

multi-agent safetyとHCI/supervisory controlの境界であり、bot-loop対策をrate limitとしてだけ見ると「人間の介入は社会的状態遷移」という観点が落ちる。

### (8) 重要度

**B** — 有用だが、human messageをreset intentとみなす条件はKamimusuhi側で追加検証が必要。

## 11. 今回の結論

今回最もKamimusuhiへ効くのは、**effectを始める直前のlifetime pinning**と、**終わった後のcausal outcome preservation**である。

Kamimusuhiはすでに「誰が」「どの身体で」「どの権限で」「何を実行したか」を分け始めているが、その間にまだ二つ穴がある。

1. 正しいbody/resourceを選んでも、dispatchまでにそのincarnationがretireされ得る。  
2. 実行後にstatusへ圧縮すると、deliveryやfallback chainの失敗因果が消え得る。

したがって今回の追加原則候補は、

> **Effect ownership is not complete until the effector lifetime is pinned through execution, and outcome ownership is not complete until phase-specific causal evidence is durably preserved.**

である。

加えて、SplitLTLはKamimusuhiのcontinuityを形式手法へ接続する良い橋になる。**過去の出来事は単なる記憶ではなく、未来に許される行為集合を変える。** これはidentity continuity / safety / consent / embodimentを同じruntime contract上で扱う方向に使える。
