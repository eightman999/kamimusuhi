## 1. A — Logical Release ≠ Physical Reclamation

Primary: Hermes Agent #131766  
https://github.com/NousResearch/hermes-agent/issues/131766

1. **実証済み**: macOSでは`trim_memory()`がglibc `malloc_trim`不在を理由に早期returnし、その後の`gc.collect()`まで実行されない。長寿命serve/gatewayで、13時間instanceが約37 GB footprint / 33.8 GB swap、別の51分instanceが11.2 GB Malloc Largeに対してwritten 8 MB / swap 11.5 GBと報告された。application上のobject解放とOSへのphysical reclaimが一致していない。
2. **提案段階**: 特定allocator APIを必須化するのではなく、runtime/platformごとにreclaim能力と結果を観測する。
3. **関係**: Computational Embodiment、homeostasis、Cognitive Budget、long-lived K-Core/K-Deep、energy-aware cognition、degraded mode。
4. **借用案**: `logical_live_bytes / allocator_retained / resident_set / swap_or_compressed / reclaim_capability / last_reclaim_result`を分離。reclaim後のRSS/footprint低下をreceiptとして観測し、効かない場合はorgan restart/microrebootもpolicy候補にする。
5. **差分**: 既出memory-pressure findingは「どのprocess treeを測るか」。今回は、正しく測ってもlogical releaseがphysical reclaimへ進まないplatform/runtime差。
6. **次**: **`PhysicalReclamationClosureBench-v0` (P0/P1)**。Linux/macOSでlarge streaming buffers、tool results、session close、context compactionを反復し、logical object countとRSS/footprint/swapのclosureを測る。
7. **拾いにくい理由**: agent researchのmemoryはepisodic/contextが中心で、allocatorはplumbing扱いされる。しかし長寿命個体ではswap/pressureが能力と継続性を直接制約する。
8. **重要度**: **A**。

Invariant候補: **logical release MUST NOT be treated as proof of physical resource reclamation.**

## 2. A update — Recovery Must Preserve Delegated Runtime Ownership

Primary: OpenClaw #163760  
https://github.com/openclaw/openclaw/issues/163760

1. **実証済み**: source conversationをexternal ACP sessionへbindした後にGatewayをrestartすると、restart recoveryがsource session keyだけを見てnative recovery対象にする。completed oneshot / live persistent / normally closed ACPの3形態で再現し、native default modelのroute/authへ入り、source transcriptへfailureをappendした。2026.9.6/9.7双方で再現。
2. **提案段階**: ownerが不在ならnative fallback、quarantine、operator decisionのどれを採るかはpolicy次第。ただしrestartだけでownerを暗黙変更しない。
3. **関係**: Continuity Kernel、external K-Deep organs、DialogueSession、ACP/A2A、execution-owner binding、restart recovery。
4. **借用案**: `ExecutionOwnershipReceipt{runtime_kind, runtime_identity, binding_generation, admitted_turn, recovery_policy}`をdurable化。owner reattach不能なら`OWNER_UNAVAILABLE`として停止し、別runtimeへ移るならfresh admissionを要求。
5. **差分**: recovery-authority revalidationは既出。fresh差分はexternal organ所有のsource conversationがcontrol-plane rebootだけでnative cognitionへ再解釈され、canonical transcriptまで変わる実証。
6. **次**: **`RecoveryRuntimeOwnershipBench-v1` (P0)**。local/remote/ACP/A2A ownerでrestart・host reboot・reconnectを交差し、owner変更には明示receiptを要求。
7. **拾いにくい理由**: recovery、interop、routingが別レイヤーに見えるが、persistent individualでは「誰がturnを続ける権限を持つか」という同一問題。
8. **重要度**: **A update**。

## 3. A update — Destructive Health Transitions Need Corroborated Evidence

Primary: Hermes Agent #131765  
https://github.com/NousResearch/hermes-agent/issues/131765

1. **実証済み**: pooled remote backendがdispatch probeの`socket hang up`でdescriptorをretireする一方、同時点でremote process、remote health endpoint、host-side SSH forwardは応答し、established socketsも存在した。independent SSH tunnelは150分安定。replacementは生成されたがconsumerにadoptされずretry loopへ入り、old forwardも長時間残留した。
2. **提案段階**: HTTP 200を絶対truthにする話ではない。operation-classごとに異なるhealth evidenceを統合する必要がある。
3. **関係**: Cognitive Resource Registry、distributed embodiment、remote organs、observer back-action、resource retirement。
4. **借用案**: `HEALTHY / SUSPECT / DEGRADED(op) / RETIRING / DEAD`を分離。単発probe failureはSUSPECTへ置き、destructive retirementは再probe・独立evidence・hysteresisを要求。replacement adoption receipt前にold generationを壊さない。
5. **差分**: Perspective-Qualified Gray Healthはobserver差を扱う。本件は、その不一致をdestructive control actionへ昇格する条件。
6. **次**: **`ProbeDrivenRetirementSafetyBench-v1` (P0/P1)**。false-negative probe、WebSocket-only failure、stale descriptor、replacement adoption failureを注入。
7. **拾いにくい理由**: health monitoringはSRE、retirementはlifecycle、remote embodimentはagent architectureとして分断される。
8. **重要度**: **A update**。

## 4. A update — Native Organ Termination Must Be Process-Contained

Primary: Hermes Agent #131776  
https://github.com/NousResearch/hermes-agent/issues/131776

1. **実証済み**: KittenTTS setupは成功するが、最初のread-aloudでbackend全体がexitする。報告のroot causeではmanaged env内のespeak data pathが162 bytes、bundled espeak-ng 1.52.0の固定長path bufferを超え、初期化失敗時にnative `exit(1)`がhost backendまで終了させる。
2. **提案段階**: TTSを必ず別process化することが唯一解ではない。safe API、no-exit option、WASM/helper process等も候補。
3. **関係**: Speech & Vocal Expression、K-Edge actuator、native runtime、organ supervision、Software Body。
4. **借用案**: organ manifestに`termination_capability / crash_domain / first_use_probe`を持つ。hostを終了し得るnative organはsupervised process境界へ置き、setup成功とは別にminimal real synthesis/open/read smoke testをActivation Gateで行う。
5. **差分**: Extension Termination-Class Containmentは既出。本件はC-level exitでspeech organがhostを実際に落とすfresh field evidenceと、installation success != first-use readinessの具体化。
6. **次**: **`NativeOrganProcessFaultContainmentBench-v1` (P0/P1)**。TTS/STT/image codec/device driverでexit/abort/crash/init failureを注入し、Continuity Kernelとunrelated organsが生存することを確認。
7. **拾いにくい理由**: voice研究は品質/latency、plugin研究はpermissions、native libraryはimplementation detailとして扱われるが、身体化agentではactuatorのcrash domainが個体の生命線になる。
8. **重要度**: **A update**。

## 5. B update — Entrypoint Bootstrap Must Preserve Profile Semantics

Primary: Hermes Agent #131764  
https://github.com/NousResearch/hermes-agent/issues/131764

1. **実証済み**: cronがrestart-safe external workerへ移った後、profile configのshell hooksがworkerで登録されなくなった。plugin hooksはdiscoverされる一方、config hook registrationがentrypointにない。報告環境で500回超のcron handoff中config shell hookは0回、同profileのTelegram/CLIでは正常。
2. **提案段階**: backgroundで全hookを無条件許可する話ではない。origin-specific denyは明示し、silent omissionをなくす。
3. **関係**: background cognition、cron/dream、worker separation、profile semantics、lifecycle hooks。
4. **借用案**: ad-hoc initializationを避け、`RuntimeComposition(profile, origin, principal, capabilities)`のcanonical builderを使う。execution modeごとのrequired subsystem/policy/hook setをmanifest化する。
5. **差分**: operational-mode coverage parityは既出。fresh差分はreliability目的のprocess splitで同じprofileのdeclared lifecycle semanticsが静かに欠落する実証。
6. **次**: **`EntrypointBootstrapParityBench-v0` (P1)**。interactive/cron/dream/recovery/delegated worker/remote organのcomposition差を検証。
7. **拾いにくい理由**: worker化はdeployment改善、hookはfeatureとして別管理され、暗黙bootstrap inheritanceの消失が見えにくい。
8. **重要度**: **B update**。

## 6. B update — Opaque Continuation Artifacts Need Byte-Preserving Transforms

Primary: OpenClaw #163778  
https://github.com/openclaw/openclaw/issues/163778

1. **実証済み**: Responses系`thinkingSignature`の`encrypted_content`がdotted suffixを含むとtranscript redactorが内容を書き換え、変形後payloadをSQLiteへpersistする。synthetic fixtureに加え、既存runtime transcript由来1,813-byte payloadでもbase redactorが変更し、修正版ではcapture/store双方のSHA-256が一致。隣接synthetic secretは修正版でもredactされた。fresh provider replay acceptanceは未検証。
2. **提案段階**: opaque fieldの永久保存を求めない。保持policyを選んだ期間だけbyte integrityを守る。
3. **関係**: Canonical Evidence、provider adapters、continuation/replay、privacy/redaction、model switching。
4. **借用案**: fieldを`TEXT_SEMANTIC / OPAQUE_PROVIDER_TOKEN / SIGNED_BLOB / SECRET / BINARY`としてtyped化。opaqueはdrop/hash/encrypt-at-rest/retain-byte-exactをpolicyで選び、generic text redactorを通さない。
5. **差分**: Semantic Transcoding Integrityのfresh concrete update。安全transformがopaque continuation stateを壊すとcanonical evidenceが将来再利用不能になる。
6. **次**: **`OpaqueContinuationArtifactIntegrityBench-v1` (P1)**。serialize→redact→DB→reloadをfuzzし、RETAIN対象はbyte-identical、SECRETは非残存を要求。
7. **拾いにくい理由**: securityはsecret removal、provider adapterはcompatibility、memoryはretentionを見て、その交点のbit-level continuityが落ちる。
8. **重要度**: **B update**。

## 結論

今回の中心は **「論理状態の終了」と「物理・制度的な後始末の完了」を分けること** だった。

`drop/free`したobjectがOSへ戻ったとは限らない。control planeが再起動しても、外部organへ委ねたturnの所有権がnative runtimeへ戻ったわけではない。health probeが1回失敗しても、healthyなremote bodyを破棄してよいとは限らない。

さらに長期では、canonical evidenceのbytesを残すだけでも不十分である。将来それを読むschema、authority vocabulary、tool semantics、migration historyが失われれば、個体は過去を「保持しているが理解できない」。

> **Long-lived continuity requires closure across semantic retirement, physical reclamation, and future interpretability.**
