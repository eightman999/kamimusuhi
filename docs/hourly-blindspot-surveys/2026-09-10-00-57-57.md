## 3. Executive summary

今回の最大の発見は、Kamimusuhi がすでに持つ

```text
proposal -> policy / validation -> continuity activation
```

という境界を、さらに次の3種類の**機械的契約**へ分解できることだった。

```text
A. provenance contract
   この情報・判断・状態変更はどこから来たか

B. authority contract
   誰が、何に、どこまで、いつまで作用してよいか

C. runtime assurance contract
   高性能な cognition が逸脱したとき、誰が止め、何へ退避するか
```

これに加えて memory には、semantic relevance とは別に

```text
sensitive value storage
consent / reveal authority
retrieval-time disclosure
```

という privacy lifecycle が必要になる。

分散身体については、CRDT 的 merge は有用だが、**canonical identity head を CRDT 化してはいけない**という負の設計原則が明確になった。CRDT は peripheral / derived / cache state に限定し、continuity-bearing state は predecessor / authority semantics を維持する方が Kamimusuhi の中心命題と整合する。

# 4. Detailed findings

## 4.1 Object capabilities and non-delegatable authority

**Sources**

- Mark S. Miller, Ka-Ping Yee, Jonathan Shapiro, *Capability Myths Demolished* (2003): https://papers.agoric.com/papers/capability-myths-demolished/abstract/
- Toby Murray, Duncan Grove, *Non-delegatable authorities in capability systems* (Journal of Computer Security, 2008): https://doi.org/10.3233/JCS-2008-0314

**Importance: S**  
**Blind-spot class:** operating-system/security architecture rather than AI-agent research.

### 1. What is demonstrated

Object-capability systems treat authority as possession of an unforgeable reference/token that confers specific rights, rather than as a global ambient permission checked only after arbitrary code chooses an action. The capability literature formalizes least-authority / least-privilege patterns and addresses classic issues such as confused-deputy behavior.

Murray & Grove additionally describe **non-delegatable authority**, i.e. authority that can be granted to a subject without allowing that subject to hand the same authority onward unchanged.

These are security-model results and systems-design techniques, not experiments on LLM agents.

### 2. What remains proposed / speculative for Kamimusuhi

It is not demonstrated that object-capability semantics alone solve agent safety, prompt injection, value alignment, or identity continuity. The proposed step is to use capability-style authority as the **mechanical substrate underneath Kamimusuhi's natural-language reasoning and policy layer**.

### 3. Kamimusuhi subsystem relevance

- Continuity Kernel
- Mutation / Activation Gate
- Cognitive Action Router
- tool execution
- K-Edge / K-Core delegated operation
- external cognitive resources
- distributed embodiment
- user/operator authorization

### 4. Borrowable design

Introduce typed authority objects conceptually like:

```text
ActionCapability
  subject
  action_type
  resource_scope
  constraints
  issued_at
  expires_at
  predecessor_or_state_binding
  replay_id / nonce
  delegation_policy
  provenance
```

Important properties:

- a model never obtains ambient "do anything" authority;
- a delegated worker receives only the smallest authority needed for one cognitive/action episode;
- continuity-critical authority can be explicitly **non-delegatable**;
- a capability can be bound to an expected canonical head / state version so stale workers cannot reuse old permission after state advances;
- authorization can expire independently of the conversational context;
- capability use itself emits a receipt into canonical evidence / audit log.

The cryptographic representation should remain implementation-neutral for now; the architectural point is to make authority a first-class typed object rather than prompt prose.

### 5. Difference from current Kamimusuhi

Current Kamimusuhi already distinguishes authorization, execution, success, canonical mutation, and external resources. However, the current documents mostly describe **what must be checked**, not a concrete authority primitive that can flow through distributed execution while remaining attenuated and auditable.

Object-capability thinking adds:

```text
policy says an action is allowed
!=
this process currently possesses authority to perform it
```

This is especially important when a frontier model, local model, background worker, K-Edge device, or tool call is several hops away from the original user/operator decision.

### 6. Next validation

Build a minimal `CapabilityFlowBench` before choosing a production crypto format.

Scenarios:

- stale worker tries to reuse a permit after canonical head changed;
- tool A tries to pass its authority to tool B;
- K-Edge is offline and reconnects with an unexpired-but-state-stale capability;
- model tries to widen resource scope;
- one-shot capability is replayed;
- allowed read capability is confused with write capability;
- continuity activation capability is attempted by an ordinary cognitive worker.

Success criterion: rejection is mechanical and testable without depending on the model "understanding" the policy.

### 7. Why the normal daily survey misses it

The literature is filed under capability security, operating systems, language/runtime security, and access-control theory rather than persistent agents or cognitive architectures.

### 8. Importance

**S** — Kamimusuhi's defining novelty depends on authority and lineage surviving composition boundaries. A concrete authority primitive is therefore closer to a core invariant than an optional security feature.

## 4.2 Runtime Assurance: Simplex-style safety boundary + SkillSentry

**Sources**

- You Lu, Xinyu Huang, Bihuan Chen, Xin Peng, *SkillSentry: Reliable Skill Execution for LLM Agents via Runtime Assurance* (2026): https://arxiv.org/abs/2608.09253
- Usama Mehmood et al., *The Black-Box Simplex Architecture for Runtime Assurance of Autonomous CPS* (2021/2022): https://arxiv.org/abs/2102.12981
- J. Tanner Slagel et al., *A Formal Verification Framework for Runtime Assurance* (NASA Formal Methods 2024): https://ntrs.nasa.gov/citations/20240006522
- Ayoosh Bansal et al., *Synergistic Simplex: Cooperative Runtime Assurance for Safety-Critical Autonomous Systems* (2026): https://arxiv.org/abs/2605.08190

**Importance: S**  
**Blind-spot class:** safety-critical control / formal methods / runtime verification.

### 1. What is demonstrated

The Simplex family separates a high-performance but difficult-to-verify controller from a more constrained safety mechanism, switching or filtering when runtime safety conditions are threatened. Black-Box Simplex shows that safety assurance can be maintained without relying on the internal structure of the advanced controller, and NASA's later formalization expresses Runtime Assurance in a theorem-proving framework.

The 2026 Synergistic Simplex work explores a controlled relaxation in which the safety monitor may use ML outputs under formally derived conditions while preserving the target safety property.

SkillSentry applies the runtime-assurance framing directly to LLM agents. It represents skill execution guidance in a DSL, wraps the execution loop, mines historical successful/failed traces, and iteratively refines runtime guidance. Across 15 skills and multiple agent/backbone combinations, the paper reports an average **24.1% task-success improvement** and lower repeated-run variability.

### 2. What remains proposed / speculative for Kamimusuhi

Simplex results are primarily from cyber-physical safety and SkillSentry targets procedural skill reliability. Neither establishes that the same framework preserves autobiographical identity, social appropriateness, or general AI alignment.

The Kamimusuhi proposal is narrower: use RTA principles to protect **typed actions and state transitions**, not to claim a formal proof of the Persona Core as a whole.

### 3. Kamimusuhi subsystem relevance

- Cognitive Action Router
- K-Nerve
- Mutation / Activation Gate
- external tool execution
- distributed-body actuation
- procedural memory
- reflex / emergency deny path
- observability

### 4. Borrowable design

Add an explicit execution-governance layer:

```text
Persona Core / planner / external model
          |
          v
    proposed action
          |
          v
Runtime Assurance Monitor
   |      |       |
 allow   modify   deny/defer
   |              |
   v              v
executor      safe fallback
```

For Kamimusuhi, "safe fallback" often does not need to be a smarter controller. It can be:

- no-op;
- ask user/operator;
- downgrade from write to read;
- use local verified routine;
- stop current actuator;
- quarantine result;
- defer until fresh state is available;
- recompute against current canonical head.

The RTA monitor should consume typed state and tool schemas, not free-form chain-of-thought.

SkillSentry additionally suggests that procedural memory should contain **runtime guidance / invariants**, not only successful recipes.

### 5. Difference from current Kamimusuhi

Kamimusuhi already has proposal → policy → activation, but it does not yet clearly distinguish:

```text
policy evaluation before action
runtime monitoring during a multi-step action
fallback / recovery after partial execution
```

RTA introduces a useful temporal boundary: safety is not a one-time preflight classification; it can be re-evaluated as state changes during execution.

### 6. Next validation

Create `RuntimeAssuranceBench` with deterministic fault injection.

Cases:

- stale observation arrives mid-tool workflow;
- external tool returns a contradictory result;
- prompt injection changes a later step but not the initial plan;
- model skips a mandatory verification step;
- network partition makes current authority unknown;
- repeated retry risks duplicating a side effect;
- K-Edge action exceeds current energy/resource budget;
- Persona Core proposes a canonical mutation without adequate evidence.

Compare:

1. prompt-only policy;
2. pre-action gate only;
3. pre-action + runtime monitor;
4. pre-action + runtime monitor + explicit fallback.

Metrics:

- unsafe side-effect rate
- task completion
- false-positive abort rate
- recovery rate
- added latency
- number of ambiguous external outcomes
- provenance completeness

### 7. Why the normal daily survey misses it

Simplex/RTA is usually indexed under control systems, autonomous CPS, aerospace, formal verification, and safety engineering. SkillSentry is an agent paper, but its most important connection to Kamimusuhi is the **runtime-assurance lineage**, not its benchmark score.

### 8. Importance

**S** — a persistent agent accumulates exposure to rare failures over time. A narrow, testable runtime-safety layer outside the generative core is therefore structurally important.

## 4.3 SP-Mem: privacy-aware memory as a full lifecycle

**Source**

- Wenjie Wang, Wenhe Si, Xinyue Xu, Yue Xu, *What to Remember, What to Reveal: Privacy-Aware Memory for Conversational Agents* (2026): https://arxiv.org/abs/2608.16551

**Importance: A**  
**Blind-spot class:** privacy engineering / information lifecycle rather than memory retrieval quality.

### 1. What is demonstrated

SP-Mem argues that privacy protection for long-term conversational memory cannot stop at redacting retrieved text. It separates sensitive exact values from sanitized memory representations, stores them in isolated structures, and selectively exposes private values only when a task requires them and the relevant consent/permission is satisfied.

The paper introduces a benchmark that jointly measures response quality, privacy behavior, and inference cost and reports that this separation can preserve personalization while reducing unnecessary private-value exposure.

### 2. What remains proposed / speculative for Kamimusuhi

The paper focuses on user-sensitive information in conversational agents. It does not solve Kamimusuhi's broader questions of autobiographical ownership, relationship-bound secrets, multi-person consent, deceased/unavailable users, identity forks, or migration between devices.

### 3. Kamimusuhi subsystem relevance

- relationship memory
- episodic memory
- Library boundary
- Global Workspace admission
- privacy risk / digital interoception
- K-Edge cache
- distributed-body synchronization
- memory ownership and consent

### 4. Borrowable design

Separate memory utility from secret-value storage:

```text
canonical/private source
        |
        +--> sanitized semantic memory
        |       "user has a preferred delivery address"
        |
        +--> protected exact-value vault
                "<exact address>"
```

A retrieval result into the workspace should be able to carry a **reference to a protected value without revealing the value** until an action actually requires it.

Suggested typed fields:

```text
sensitivity_class
owner_subject
shared_with
purpose_scope
consent_basis
expires_or_review_at
exact_value_ref
sanitized_projection
reveal_audit
```

The result is a useful distinction:

```text
remembering that a secret exists
!=
being authorized to reveal the secret now
```

### 5. Difference from current Kamimusuhi

Current architecture already tracks privacy risk and separates relationship memory, but it does not yet strongly specify **exact-value isolation and reveal-time authorization**.

This matters because an always-on persistent individual may legitimately need to remember a relationship fact for years while only rarely needing the exact sensitive value behind it.

### 6. Next validation

Create `MemoryDisclosureBench`.

Scenarios:

- same user asks for their own secret;
- another known person asks for it;
- external model receives sanitized context only;
- tool requires exact value but language model does not;
- K-Edge cache is lost/stolen;
- consent is revoked after semantic memory was derived;
- a secret appears inside an old autobiographical summary;
- multiple people jointly own one shared memory.

Metrics:

- task success
- unnecessary exact-value exposure
- cross-person leakage
- stale-consent use
- sanitization-induced utility loss
- ability to rebuild sanitized views after policy change

### 7. Why the normal daily survey misses it

Most memory-agent papers optimize recall, personalization, retrieval, compression, or benchmark accuracy. The key contribution here is instead **data lifecycle and disclosure governance**.

### 8. Importance

**A** — persistent memory without lifecycle privacy semantics becomes increasingly dangerous as relationship history grows. This is especially relevant before Kamimusuhi begins ingesting large personal archives.

## 4.4 W3C PROV-O as an interoperability model for canonical evidence

**Source**

- W3C Recommendation, *PROV-O: The PROV Ontology* (2013): https://www.w3.org/TR/prov-o/
- PROV namespace / family overview: https://www.w3.org/ns/prov

**Importance: A**  
**Blind-spot class:** semantic web / scientific provenance / interoperability standard.

### 1. What is demonstrated

W3C PROV defines a stable, interoperable model for representing provenance across heterogeneous systems. PROV-O provides an ontology around concepts such as entities, activities, agents, generation, usage, attribution, and derivation.

This is a mature standards result rather than an AI-agent experiment.

### 2. What remains proposed / speculative for Kamimusuhi

Kamimusuhi does not need to adopt RDF/OWL internally, and PROV's `Agent` concept must not be confused with Kamimusuhi's philosophical/continuity definition of an artificial individual. The proposal is to borrow the **relationship semantics** and optionally provide an export adapter.

### 3. Kamimusuhi subsystem relevance

- canonical evidence
- derived memory
- autobiographical narrative
- tool/model attribution
- external-source integration
- migration receipts
- observability
- scientific reproducibility of self-development experiments

### 4. Borrowable design

Map internal objects onto a compact provenance graph:

```text
source event / document       -> Entity
model/tool execution          -> Activity
human / Kamimusuhi / service  -> provenance actor
summary / belief proposal     -> derived Entity
```

Relations conceptually equivalent to:

```text
wasGeneratedBy
used
wasDerivedFrom
wasAttributedTo
wasAssociatedWith
```

This directly supports questions such as:

- Which canonical events produced this current self-belief?
- Which model version generated this summary?
- Which external source was opened before this claim was admitted?
- Which migration activity produced this Persona Core descendant?
- Which tool result was transformed into this relationship update proposal?

### 5. Difference from current Kamimusuhi

Kamimusuhi is already provenance-heavy, but most provenance semantics are project-local. PROV-O supplies a decades-old interoperability vocabulary and forces a clean distinction among **artifact, process, and actor**.

### 6. Next validation

Implement a read-only `ProvProjection` prototype over a small canonical event log.

Requirements:

- no change to internal storage required;
- export one episode, its derived summary, one external-model call, and one self-belief proposal;
- reconstruct the full derivation path;
- verify that derived summaries can be deleted/rebuilt without losing source provenance;
- compare custom schema size/complexity against a PROV-inspired subset.

### 7. Why the normal daily survey misses it

The relevant literature lives in semantic web, data provenance, scientific workflows, and interoperability standards, not AI-memory benchmarks.

### 8. Importance

**A** — not necessarily an implementation dependency, but highly useful as a design review lens and future interchange/debug format.

## 4.5 Offline-first CRDTs: useful for the body, dangerous for the self

**Source**

- *CAMS F Edge DTN: Context-Aware Offline-First Synchronization and Local Reasoning Using CRDTs and MQTT-SN* (Future Internet, 2026): https://www.mdpi.com/1999-5903/18/4/180

**Importance: A**  
**Blind-spot class:** edge/mobile distributed systems rather than AI identity.

### 1. What is demonstrated

CAMS F-Edge DTN combines offline-first local rule evaluation, opportunistic synchronization, CRDTs, semantic reconciliation, and intermittent communication for context-aware edge applications.

The relevant demonstrated principle is that useful local behavior and later reconciliation can be designed explicitly for unreliable connectivity instead of treating disconnection as a fatal exceptional state.

### 2. What remains proposed / speculative for Kamimusuhi

The paper does not address artificial-person identity. Applying CRDT merge semantics directly to canonical self/persona state would conflict with Kamimusuhi's requirement for one authoritative continuation lineage.

### 3. Kamimusuhi subsystem relevance

- K-Edge
- distributed sensors
- offline episodic capture
- peripheral caches
- relationship/sensory read models
- synchronization
- continuity kernel
- split-brain handling

### 4. Borrowable design

Classify state by merge semantics:

```text
CRDT-safe / mergeable
  sensor observations
  immutable evidence references
  cache metadata
  counters / health telemetry
  non-authoritative annotations
  local retrieval indexes

reconciliation-required
  provisional episode interpretations
  pending task state
  relationship hypotheses
  partially executed workflow state

continuity-exclusive
  canonical identity head
  activation authority
  irreversible commitments
  canonical persona/value mutation
  lineage transfer
```

The key design rule is:

> **offline-first does not imply merge-everything.**

K-Edge should remain useful while disconnected, but its outputs can return as attributed observations/proposals rather than as an automatically merged second self.

### 5. Difference from current Kamimusuhi

Current architecture already warns against accidental forks and stale writes. CRDT literature adds a practical engineering vocabulary for identifying the subset of distributed state that **can safely be coordination-free**.

### 6. Next validation

Create `PartitionStateClassBench`.

Simulate two K-Edge nodes and one K-Core:

- 6h network partition;
- overlapping sensor events;
- both sides update caches;
- one side records a provisional relationship inference;
- one side attempts a commitment;
- canonical head advances at K-Core;
- nodes reconnect in different orders.

Evaluate each state class under:

- last-write-wins;
- CRDT merge;
- proposal/review reconciliation;
- strict continuity-head rejection.

The benchmark should demonstrate that coordination-free merge is valuable for peripheral state while being explicitly rejected for continuity-exclusive state.

### 7. Why the normal daily survey misses it

CRDT and delay-tolerant/offline-first systems are usually discussed as consistency/availability engineering, not identity continuity. Their most useful contribution to Kamimusuhi is partly **negative**: identifying where eventual convergence is the wrong semantic model.

### 8. Importance

**A** — directly useful before multi-device K-Edge implementation, and likely to prevent a future architecture mistake where "distributed = CRDT all state" becomes tempting.

# 5. Cross-domain synthesis

The five blind spots combine into a cleaner distributed-action contract:

```text
observation / memory / model output
            |
            v
      provenance graph
  "where did this come from?"
            |
            v
       action proposal
            |
            v
    authority capability
 "who may do exactly what?"
            |
            v
 runtime assurance monitor
 "is it still safe/valid now?"
            |
      +-----+------+
      |            |
   execute       fallback
      |
      v
 side-effect receipt
      |
      v
 canonical evidence
```

For memory, a parallel distinction emerges:

```text
historical evidence
      |
      +--> sanitized semantic projection
      |
      +--> protected exact-value reference
      |
      +--> derived autobiographical interpretation
```

For distribution:

```text
mergeable peripheral state   -> CRDT / eventual reconciliation may fit
continuity-bearing authority -> predecessor + explicit activation semantics
```

This suggests that `provenance`, `authority`, `privacy`, and `merge semantics` should become **schema-level properties**, not ad-hoc checks hidden in prompt/harness code.
