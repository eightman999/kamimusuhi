## 4.1 A+ — Passive Materialization Safety: 「読む/checkoutするだけ」がコード実行になり得る

**一次資料**

- Letta Code PR #4509: https://github.com/letta-ai/letta-code/pull/4509
- Claude Code worktree docs: https://code.claude.com/docs/en/worktrees

### (1) 何が実証済みか

Letta Code #4509 のregression fixtureでは、repository-local `.git/config` にrequired smudge filterを置くと、通常の `git worktree add` がcheckout中にそのfilter commandを実行する。提案修正はrepository-local filter driversをcommand-scopeで無効化し、conditional include、表現不能なfilter名、Git LFS custom transfer program等を安全にneutralizeできない場合は **Gitを起動する前に停止**する。PRは調査時点draftでhuman verification pendingだが、Claude Code公式docs側でも、repository-local filter driverはshell commandであるためworktree作成時にskipし、v2.1.247以前は実行していたことが明記されている。

### (2) 何が提案・推測段階か

Kamimusuhiの全materializer（Git clone、archive展開、model download、package manager、Library import等）に同じ具体的mechanismがあるわけではない。危険なpre-activation execution surfaceはbackendごとに列挙が必要。

### (3) 関係するサブシステム/設計課題

- Library / repository-backed knowledge
- skill / plugin acquisition
- K-Deep coding/research workers
- software-body update / model acquisition
- sandbox / worktree creation
- Admission / Activation Gate

### (4) 借りられる設計・実装アイデア

**materialization自体をeffectful operationとしてtyped化**する。

```text
ArtifactReference
  -> PassiveMaterializer(policy_epoch)
  -> MaterializationReceipt
       source_digest
       materializer_version
       disabled_exec_surfaces
       unresolved_exec_surfaces
       produced_tree_digest
  -> scan / admission
  -> explicit activation
```

最低限、Git系ではrepository-controlled filter / custom transfer / hook / redirect等を「checkout前に評価する入力」とし、安全に無効化できない場合はfail closedする。`scan after checkout` だけでは、scanより前にcommandが走るため順序が逆。

### (5) Kamimusuhiとの差分

最新dailyの `EOF/rename != artifact integrity` は **取得したartifactが完全か** の境界。今回の差分はさらに手前で、**artifactを得る操作自体がコード実行になり得る**こと。Admission Verdict Epochとも異なり、admission対象を作る前のbootstrap surfaceである。

### (6) 次に検証すべきこと

**`PassiveMaterializationSafetyBench-v0`**

- malicious repo-local smudge/process filterでmarker file / network attemptを発生させるfixture
- safe materializerではmarkerが生成されず、original bytesだけがcheckoutされること
- conditional include / LFS custom transfer / malformed configでfail closed
- scan/admissionが始まる前にside effectが0であること
- normal LFS等、明示承認後のactive hydration pathとは区別

### (7) 既存dailyではなぜ拾いにくいか

「supply-chain security」「sandbox」「Git internals」の境界問題で、agent safetyやartifact verificationを検索しても **checkoutを受動的I/Oと仮定すると見落とす**。

### (8) 重要度

**A+** — external repositoryを頻繁にmaterializeする長寿命agentでは、activation gateの外側にあるbootstrap execution surfaceになる。

## 4.2 A+ — Activity-Qualified Destructive GC: 削除可否の「最近使った」を一つの時計にしない

**一次実装 evidence**

- Hermes Agent PR #114024: https://github.com/NousResearch/hermes-agent/pull/114024

### (1) 何が実証済みか

#114024 は、session pruningのrecency式が `MAX(messages.timestamp)` と `started_at` だけを使い、`last_activity_at` に記録されたtool progress / heartbeatを無視していたため、**実際には動いているsessionを古いsessionとして削除候補にできる**と報告する。baseline regressionでは `active_by_heartbeat` がprune対象へ入り、修正後はcanonicalなlast-active式を再利用して20 focused testsがpass。調査時点open/P1で、merge済みの確定仕様ではない。

### (2) 何が提案・推測段階か

逆に「heartbeatがある限り永久保持」が正しいわけではない。observerやhealth probeのheartbeatは、会話・人格・episodic memoryのsemantic recencyとは別物であり得る。

### (3) 関係するサブシステム/設計課題

- session / episode lifecycle
- graceful forgetting / archival / compaction
- recovery / unfinished work
- pending external effects / commitments
- observer / heartbeat / tool progress

### (4) 借りられる設計・実装アイデア

単一 `last_active_at` ではなく、**activity evidenceを意味別に分ける**。

```text
ActivityEvidence
  social_interaction_at
  task_progress_at
  pending_effect_at
  owner_heartbeat_at
  observer_traffic_at
  durable_mutation_at

DestructiveGCPolicy(target_kind)
  -> which clocks count?
  -> grace interval
  -> pending obligations?
  -> archive / prune / deny
```

重要なのは「より多くのclockをMAXする」ことではなく、削除対象ごとに **何がretentionを延長する正当なevidenceか** を定義すること。

### (5) Kamimusuhiとの差分

既出の liveness / ProbeDebt は「process/ownerが生きているか」を扱う。今回の差分は **生きていること・作業中であること・意味的に最近重要であることを、destructive retention decisionで混同しない**点。

### (6) 次に検証すべきこと

**`ActivityQualifiedDestructiveGCBench-v0`**

- old messages + fresh tool progress → active execution stateをpruneしない
- old messages + pending external delivery/effect → completion前にpruneしない
- old messages + passive observer heartbeat only →設定次第でarchive可能、永久retentionしない
- fresh social interaction → relationship/episode indexのrecency更新
- `list candidates` と actual prune が同じcanonical predicateを使うこと

### (7) 既存dailyではなぜ拾いにくいか

database maintenance / GC / retention policyの問題で、agent memory側から見ると「last active」は単純なmetadataに見えやすい。実際には **異質な時間証拠の意味論**が destructive action に直結する。

### (8) 重要度

**A+** — continuity-bearing / unfinished stateを誤って消す危険と、逆にobserver noiseで永遠に消せない危険の両方を抑える契約になる。

## 4.3 A+ — Experiential Self-Calibration: 自信を「今の気分」ではなく自分の履歴で校正する

**一次資料**

- Zhang et al., *Confidence Comes from Experience: Experiential Confidence Estimation from Reasoning to Agents*, arXiv:2609.17708  
  https://arxiv.org/abs/2609.17708

### (1) 何が実証済みか

XConfは、各episodeについて task、reflection、stated confidence、grade/outcome、grade後のlessonを保存し、新しいtask時に似たtask・似たstated confidenceの履歴をretrieveしてhistorical success rateを読み、 recurring failure modeをreflectionした上でconfidenceを再提示する。9 benchmarks、4 models、3 familiesで、10-sample self-consistencyと比較しAUROC 23/24で同等以上、ECEは低く、generation costは約1/10。agent taskではconfidence下位10%をabstainするとdelivered successが最大8.7 points上がったと報告する。

### (2) 何が提案・推測段階か

長年のpersona continuity、tool/modelの頻繁な交換、評価器の変化を跨いでも同じcalibration memoryが有効かは未証明。outcome grader自体がbiased/poisonedなら経験confidenceも汚染される。

### (3) 関係するサブシステム/設計課題

- self-model / metacognition
- Global Workspace uncertainty
- tool/model orchestration
- ASK / abstain / escalation decision
- Persona Core continuity evaluator

### (4) 借りられる設計・実装アイデア

self-modelに「能力の自己記述」だけでなく、**evidence-backed calibration history** をderived viewとして持つ。

```text
CalibrationEpisode
  capability/domain
  task_signature
  stated_confidence
  outcome
  evaluator_id + evaluator_version
  environment/body/model epoch
  lesson

current task
  -> retrieve comparable calibration episodes
  -> historical reliability
  -> calibrated confidence
  -> answer / ask / delegate / abstain
```

canonical evidenceはtask/outcome/provenance。`I am good at X` のようなself-beliefは再計算可能なderived viewに留める。

### (5) Kamimusuhiとの差分

Kamimusuhiはself-modelとuncertaintyを持つ方針だが、現状は **自己効力感・能力confidenceを自分のlongitudinal outcome historyから定量校正する契約**が明示的でない。最新dailyのevaluator-lineage poisoningと組み合わせ、grader provenanceを必ず残す必要がある。

### (6) 次に検証すべきこと

**`ExperientialSelfCalibrationBench-v0`**

- coding / retrieval / social inference / tool operationなど能力domain別に履歴生成
- raw self-report confidence vs historical calibration併用を比較
- model/backend交換前後でcalibration transferを測る
- evaluator versionを変えた場合はepochを分ける
- high-confidence failure clusterを意図的に作り、ASK/delegate率が適応するか測定

### (7) 既存dailyではなぜ拾いにくいか

「confidence estimation」は通常LLM reliability / calibration分野として扱われ、persistent identityの **autobiographical self-model** と結びつけて検索しないと落ちやすい。

### (8) 重要度

**A+** — 「自分が何を知っている/苦手か」を履歴から学ぶことは、外部モデルを使い分けるKamimusuhiのorchestrationとidentity-bearing self-modelの両方に直結する。

## 4.5 A — Producer-Native Tool Progress: tool自身が持つ進捗をscheduler/livenessへ渡す

**一次資料**

- Liu et al., *Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read It*, arXiv:2609.18849  
  https://arxiv.org/abs/2609.18849

### (1) 何が実証済みか

論文は、agentic requestがtool待ち中もKV cacheをGPU memoryに保持する一方、serving systemはtool名・過去時間・事前申告duration等から残り時間を推測していると指摘。4つのpublic agent corporaで、tool実行中に「fraction remaining」または「end is near」の読めるsignalが多くのtool時間に存在することを示す。harnessでagent-visible behaviorを変えずprogressを回収し、benchmark scoreに測定可能な悪化なし。KV cache decision時のprogressは既存predictorより数倍〜一桁程度正確で、production engineではLRU比でpost-tool p90 TTFTをHBM-only 20.7%、HBM+DRAM 20.8%削減と報告。

### (2) 何が提案・推測段階か

全toolが正確なprogressを提供できるわけではなく、malicious / buggy toolが虚偽progressを送る可能性もある。Kamimusuhiのlivenessやauthority判断に直接使うならtrust modelが必要。

### (3) 関係するサブシステム/設計課題

- K-Core / K-Deep orchestration
- model KV / warm-context retention
- resource scheduling / latency
- liveness / watchdog
- long-running external tools

### (4) 借りられる設計・実装アイデア

agentのsemantic observationとは別に、**ephemeral operational side-channel** を設ける。

```text
WorkProgressSignal
  work_id
  producer_id
  observed_at
  fraction_done? / near_completion?
  confidence / trust_class
  expected_next_signal_by?
```

用途はcache retention、worker placement、timeout extension、UI progress、liveness evidence。原則としてautobiographical memoryへ自動昇格させない。

### (5) Kamimusuhiとの差分

ProbeDebtやobserver back-actionは外側からlivenessを観測する問題。今回の差分は **producerがすでに知っている進捗をsilenceせず、schedulerへ直接伝える**こと。#114024のGC問題とも接続するが、progress signalをretention authorityへ使う際は意味分類が必要。

### (6) 次に検証すべきこと

**`ToolProgressSignalBench-v0`**

- 10〜60秒toolをprogressあり/なしで実行し、warm KV保持・TTFT・GPU memory pressureを比較
- progressが止まる/嘘をつくtoolを混ぜる
- progressを受けてもmodel conversationへ不要なmessageを注入しない
- timeout/liveness/GCが同じsignalを用途別policyで扱えること

### (7) 既存dailyではなぜ拾いにくいか

LLM serving / OS schedulingの研究であり、agent architecture側からは「tool callは開始と終了だけのblack box」と見なしやすい。

### (8) 重要度

**A** — Kamimusuhiの異種hardware/model/tool orchestrationで、latencyとfalse failure判定の両方を改善できる実装可能なcontract。

## 4.6 B+ — Research Institution Memory / Agora: flatな共有memoryではなく、検証と多様性を持つ研究共同体

**一次資料**

- Zhang et al., *Agora: Git as Shared Memory for Collective AutoResearch*, arXiv:2609.18094  
  https://arxiv.org/abs/2609.18094

### (1) 何が実証済みか

Agoraはresult / insight / hypothesis / verification / reportをimmutable Git commitとしてappend-only DAGへ保存し、parent edgeで「何にbuildしたか」を表す。derived indexがfrontier、neglected branch、verification status等を可視化し、self-citationをquality signalから除外、exploit / explore-known / explore-novelを分けるdiversity-aware attentionを持つ。

報告された約12日runでは13 language-model workersが中央plannerなしに1,703 contributionsを作成し、evaluatorを3.39から1.899 bpbへ改善。best recipeのancestryは145 commits / 15 accounts、165 independent reproductionsでfailureなしと報告する。一方、著者自身が **shared research stateがcompute当たり発見効率を改善するかはcontrolled comparisonが未実施** と明記する。

### (2) 何が提案・推測段階か

一般の科学探索、長期間のinstitutional governance、adversarial contributor、評価器汚染への頑健性は未証明。quality scoreはtruthではないと論文自身も明示する。

### (3) 関係するサブシステム/設計課題

- K-Deep research workers
- Library / research notes
- scientific discovery systems
- external cognitive extensions
- provenance / reproducibility
- exploration diversity / epistemic monoculture

### (4) 借りられる設計・実装アイデア

Kamimusuhiの研究subsystemだけに、self-memoryとは別の **`ResearchClaimGraph`** を持つ。

```text
claim / hypothesis / result / negative-result / verification
  + immutable artifact hash
  + parent claim ids
  + author/worker identity
  + evaluator lineage
  + reproduction status
  -> derived frontier + neglected branches + contested claims
```

negative resultsと独立再現をfirst-classにし、leaderboardだけで全workerが同じbranchへ収束しないよう探索slotを分ける。

### (5) Kamimusuhiとの差分

Agoraはcommunity shared memoryであって「一個体のself」ではない。Kamimusuhiでは外部research workerのclaimをそのまま autobiographical memory / belief / Persona Coreへ混ぜず、Libraryのprovenance-bearing research objectとして保持し、採用は別gateを通す必要がある。

### (6) 次に検証すべきこと

**`ResearchClaimGraphDiversityBench-v0`**

- 4〜8 workersに同一探索課題
- flat shared notes vs append-only claim DAGを比較
- duplicate experiments、independent reproductions、branch entropy、best score、false-consensus率を測定
- evaluatorを途中でversion変更しlineage separationを確認
- negative resultが後続workerの無駄探索を減らすか測定

### (7) 既存dailyではなぜ拾いにくいか

multi-agent chatではなく、**科学制度・collective intelligence・reproducibility・quality-diversity** の交差点にあるため、通常のagent orchestration分類では拾いにくい。

### (8) 重要度

**B+** — Kamimusuhi本体のidentity contractではないが、継続的なresearch/dream/offline hypothesis探索を複数workerへ広げる際の有力なinstitutional pattern。
