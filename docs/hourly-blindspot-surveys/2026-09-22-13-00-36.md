## 1. 今回狙った盲点

通常 daily の分類から外れやすい、次の境界を重点探索した。

1. **turn の存在判定と特定出力channelの存在判定を混同していないか**  
   text が空でも、音声・gesture・structured response・tool/action result・その他の公開payloadが存在し得る。逆に private thought だけを user-visible completion と見なしてもいけない。

2. **科学的発見の生成速度と独立検証能力の非対称性**  
   discovery engine の throughput が verifier / reviewer / attribution / exposition の capacity を上回ると、個々のclaimが正しくても epistemic pipeline 全体が不健全にならないか。

3. **宣言済み依存関係と retention / archival / GC の接続**  
   まだ一度も直接使われていない skill / organ / model / service でも、enabled role・cron・procedure・fallback topologyから到達可能なら「未使用」ではなく将来実行可能性の一部ではないか。

4. **effective execution route と nominal route の差分**  
   relay / router / aggregator 経由では、requested provider / endpoint / model と実際に応答した downstream provider が一致しない場合がある。既存 route receipt をどこまで実観測へ閉じるべきか。

5. **capability の変化と derived availability cache の整合**  
   device/driver/toolを取得・修復しても、長寿命processのnegative cacheが残れば self-model / schema projection は古いままになる。既存 capability freshness を実装上どこでinvalidateするか。

6. **cleanup の「成功表示」と実postcondition**  
   symlink等で API が no-op しても `ignore_errors` と counter increment により「削除済み」と見えるケースを、既存 failure-atomic teardown / TypedObjectRef にどう追加するか。

固定リスト外では、**semantic payload existence、verification capacity as a bounded resource、declared dependency as retention root** を主な blind spot とした。

## 4.1 A — Channel-Aware Turn Settlement

**Primary evidence:** Hermes #118758  
https://github.com/NousResearch/hermes-agent/pull/118758

### (1) 何が実証済みか

Hermes Desktopのstream settlementで、reasoning payloadを既に受け取っているturnでも、最後の`message.complete.text`が空なら「出力欠落」とみなしてstored sessionをrehydrateできた。PRのregressionでは、`reasoning.delta` → empty `message.complete` の順で、修正前はhydrationが呼ばれ、修正後はreasoning partを保持してhydrationしない。focused suiteは17 tests passと報告されている。

ここで実証されているのはHermes固有のDesktop stream bugであり、**reasoning contentを一般に保存/表示すべきことではない**。

### (2) 何が提案・推測段階か

Kamimusuhiへ一般化する場合、turnの「payloadあり」を単一booleanにせず、channel / visibility / durabilityごとに判定する設計が有効と推測する。

```text
TurnContribution {
  channel: TEXT | AUDIO | GESTURE | STRUCTURED | TOOL_EFFECT | PRIVATE_COGNITION | ...
  visibility: PRIVATE | USER_VISIBLE | PEER_VISIBLE | AUDIT_ONLY
  durable_class
  payload_ref
}

TurnSettlement {
  semantic_payload_seen
  user_visible_payload_seen
  durable_payload_seen
  effect_receipt_seen
  terminal_frame_seen
}
```

### (3) Kamimusuhiの関連サブシステム / 設計課題

- Persona Core / expression
- Global Workspace
- multimodal output / social signals
- session hydration / restore
- canonical event store
- delivery ledger
- tool/action receipt
- INV-012 `thought != utterance != confirmation != execution != success/delivery`

### (4) 借りられる設計・実装アイデア

- `final_text.empty()` をturn欠落判定へ直接使わない。
- publication classごとのpayload presenceを持つ。
- private thoughtしかない場合は**user-deliverable completionではない**ため、必要ならpublic expression生成へ進む。
- audio/gesture/structured/tool-only turnはtext無しでも正当なturnとしてsettle可能にする。
- restore/hydrationは「どのchannelが欠けているか」を比較して実行し、既存のnewer channelをblank snapshotで上書きしない。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでにthought/utterance/action/deliveryを分離している。今回の新規差分は、その**同一turn内の複数payload channelをsettlement / hydration predicateへ落とす具体契約**である。現状の原則だけでは、text-centric adapterが別channelを「出力なし」と誤判定する余地が残る。

### (6) 次に検証すべきこと

**`ChannelAwareTurnSettlementBench-v0`**

最低fixture:

1. textあり / audioなし
2. textなし / audioあり
3. textなし / user-visible gestureあり
4. textなし / structured cardあり
5. textなし / external action receiptあり
6. private cognitionのみ（user-visible completionとしてはfalse）
7. public payload後にempty terminal frame
8. stale stored snapshotがnewer non-text payloadを消そうとするrace
9. restart / reconnect / multi-device rehydration後もchannel provenanceが保持される

合格条件: **公開済みの意味payloadをtext absenceだけで消さず、private cognitionだけを公開済み回答と誤認しない**。

### (7) 既存dailyではなぜ拾いにくいか

multimodal researchは通常「入力sensor」やmodel modality能力に寄り、stream protocol / UI hydration / transcript settlementのpredicateまでは見ない。一方agent runtime調査はtext responseを暗黙の主channelとして扱いがちで、**semantic turn existence と channel-specific projection**の境界が埋もれる。

### (8) 重要度

**A**。multi-device / multimodal / long-lived transcriptを本格化すると、誤った「出力なし」判定はcanonical/derived stateの巻き戻し、duplicate reply、duplicate effectへつながるため。

### (6) 次に検証すべきこと

**`EpistemicVerificationBackpressureSim-v0`**

- claim impact / novelty / uncertaintyを混在
- verifier backlog増加時のroute変更
- duplicate claim / rediscovery / contradictory claim
- external independent verifierが一時offline
- attribution searchが未完了
- formal checker successだがsemantic statement match未確認

比較:

1. unlimited generation
2. FIFO review only
3. impact-aware backpressure
4. verification-budget-aware exploration/exposition switching

評価指標は raw claim count ではなく、**verified useful claims / reviewer-hour、unverified high-impact debt、time-to-retraction、attribution completeness** とする。

### (7) 既存dailyではなぜ拾いにくいか

scientific discovery surveyはproblem-solving score / theorem proving / agent collaborationへ寄り、組織論・出版・査読・community capacityを「runtime resource」として扱いにくい。これはAI capabilityよりも **science governance + queueing / capacity planning + epistemology** の接合部にある。

### (8) 重要度

**B**。Kamimusuhiの現在段階で即時P0ではないが、長寿命K-Deepが自律的に大量研究を回す段階では、research institutionとしての健全性を左右する。

```text
historically_inactive
AND not reachable_from_any_active_retention_root
AND no pending obligation requires it
AND no recovery/fallback lease pins it
```

のときだけ生成する。

### (5) Kamimusuhiとの差分

これは新しい `transitive dependency closure` の再提案ではない。2026-09-11のClosureBoundは主に**authority / activationをdependency closureへbind**する。2026-09-17のActivity-Qualified Destructive GCは**複数のrecent activity clock**を削除判断へ入れる。

今回の差分は、**activityが一度もなくても、enabled declarative topologyからreachableならlive**という第三の軸を追加すること。`recently active` と `prospectively required` は別である。

### (6) 次に検証すべきこと

既存GC benchへのfixture追加、または **`DeclaredDependencyRetentionBench-v0`**:

- roleがskillを宣言、まだ一度もlaunchされていない
- usage=0 / age>archive thresholdでも保持
- roleをdisableし最後のrootを外すと次回GCでeligible
- cron paused / rare / scheduled-future-only
- fallback-only model/organ
- exact dependency versionをupgradeしたときold version rootが外れる
- recovery中だけ一時pin
- cyclic dependency graph
- invalid/missing referenceは「使用済み」と偽装せずdiagnosticへ出す

### (7) 既存dailyではなぜ拾いにくいか

agent memoryのforgetting調査はrecord age / salience / access frequencyに寄りやすい。package managerのGCはreachabilityを扱うが、**future cognitive role topologyをGC rootとして扱う**話はprocedural memory / package GC / schedulerの境界にあり、通常分類では分断される。

### (8) 重要度

**A（既存finding更新）**。新原則ではないが、Kamimusuhiがskill evolution / rare fallback / scheduled cognitionを持つほど、usage-only pruningは「最初に必要になった瞬間だけ壊れる」潜伏障害になる。

を追加する。

## 10. 今回の結論

今回は「大きな新理論」より、**長寿命・multi-modal・self-maintaining systemで、単一のproxyを実在そのものと取り違える実装穴**が中心だった。

最も直接的な新規候補は **Channel-Aware Turn Settlement** である。`final_text`、`semantic payload`、`user-visible delivery`、`private cognition` を別状態にすると、Kamimusuhiの既存 `thought != utterance` 原則をstream / restore / multimodal runtimeまで一貫して落とせる。

次に、scientific discoveryが強くなるほど **verification capacityそのものをCognitive Budgetに近い有限資源として扱う必要**がある。生成数ではなく、独立に検証され、帰属・説明が整い、必要なら撤回できる知識のthroughputを測るべきである。

一方 Hermes #118753/#118756 は、一見新規に見えたが repositoryにはすでに ClosureBound と Activity-Qualified Destructive GC があるため、独立提案せず **「declared dependency closureをretention liveness rootにも使う」更新候補**に留めた。今回の重複排除で最も重要な判断点である。
