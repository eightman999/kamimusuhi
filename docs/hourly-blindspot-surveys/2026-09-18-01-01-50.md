# 5. 候補ごとの評価

## 5.1 A — Poison-record containment: parseできる壊れrecordを「健康な兄弟を止める毒」にしない

**一次資料**

- Hermes Agent PR #114241  
  https://github.com/NousResearch/hermes-agent/pull/114241

### (1) 何が実証済みか

Hermes #114241 は、durable JSON-file scanの多くが `OSError / ValueError` を捕捉して「parseできたか」は確認する一方、parse結果がobject/dictであることを確認せず `.get()` や `record["sequence"]` を呼んでいた問題をlive reproしている。

特に `cron/bot_chat_pending` では、`[1,2,3]` のような合法JSONが一つあるだけで `sorted()` が毎tick `TypeError` になり、deferred Bot Chat drain全体がwedgedする。PRは15 sitesをauditし、scan系ではnon-dictを既存のunreadable-item skip pathへ流し、exact-id readではfail closedする。E2Eではbad receiptを残したままhealthy deferred messageがdeliveryされること、約330 focused testsのpassを報告している。

ただし調査時点では **open / P1で未merge**。したがって「upstreamで採用済みの確定仕様」ではなく、再現付き実装証拠として扱う。

### (2) 何が提案・推測段階か

- JSON file以外のSQLite row、protobuf、message bus、vector-store metadataにも同じfailure modeが同頻度で存在するとは未証明。
- corruption policyはdomainごとに異なる。receipt evidenceはpreserve、ephemeral cacheはdelete、canonical evidenceはquarantineが妥当かもしれず、一律skipは危険。
- schema-validでもsemantic-invalidなrecordをどう扱うかは別問題。

### (3) 関係するサブシステム/設計課題

- delivery ledger / outbox / inbox
- RecoveryJournal / pending work
- cron / sleep / consolidation queue
- Library import / research result spool
- background cognition result queue
- continuity receipts / lineage-adjacent non-canonical artifacts
- observability / operator diagnostics

### (4) 借りられる設計・実装アイデア

persistent item ingestionを最低3段に分ける。

```text
bytes
  -> syntax parse
  -> shape/schema validation
  -> semantic/domain validation
  -> process
```

さらにcollection scanでは、item-level failure containmentをcontractにする。

```text
DurableItemDisposition =
  ACCEPT
  QUARANTINE_PRESERVE
  SKIP_PRESERVE
  DELETE_EPHEMERAL
  FAIL_CLOSED_EXACT_ID
```

重要なのは、**collection-wide livenessを一つのbad siblingへ与えない**ことと、exact-id readでは「別recordとして解釈して上書き」しないこと。

### (5) Kamimusuhiとの差分

Kamimusuhiは既に recovery / delivery / provenanceを明示状態にしているが、そこへ入るpersistent itemの**shape failure containment**は独立した契約として明記されていない。Completion Publication Barrierは「完了をpublishし忘れない」問題であり、今回は「publish済みqueueに毒itemが混じった後も健康な仕事を進める」問題。

### (6) 次に検証すべきこと

**`PoisonRecordContainmentBench-v0`**

- pending delivery dir / recovery dir / consolidation queueに scalar、array、wrong-version object、missing-key objectを混入
- bad itemより後ろにhealthy siblingを置く
- healthy itemのprogress / deliveryが継続すること
- canonical/receipt系bad itemは勝手に削除せずquarantine + operator-visible evidenceにする
- exact-id lookupはwrong shapeを別payloadとして上書きしない
- 10k item中1〜10 bad itemでscan latency / starvationを測定

### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory / agent / recoveryを検索するとtransactionやretryは見つかるが、これは**serialization boundaryとdirectory-level fault containment**の地味な実装穴で、queue/storage internalsを見ないと出にくい。

### (8) 重要度

**A** — 長寿命agentではdurable spoolが増え、数か月に一度の部分corruptionでも「一個のbad fileが全future workを止める」形は深刻。

## 5.2 A — Validated mutation-input coherence: guardしたsnapshotと書込みに使うsnapshotを同一にする

**一次資料**

- Hermes Agent PR #114227  
  https://github.com/NousResearch/hermes-agent/pull/114227

### (1) 何が実証済みか

#114227 は、`save_config` がまず `require_readable_config_before_write(config_path)` でfresh / fail-closed parseを行うものの、その返り値を捨て、explicit-path判定のために別のcached `read_raw_config()` を再読していた問題を修正した。

cached readは一部error pathで `{}` を返すため、guardは「正常」と判断した直後でもmutation計算側だけexplicit-path evidenceを失い、default-valued sectionsを大量にdropできた。PRのlive reproでは30-section fileが `_config_version` だけへ縮退。修正は**guardに使った同じfresh readをmutation inputへそのまま渡す**。2026-09-18 00:49 JSTごろmerge済みで、194 focused tests passを報告している。

### (2) 何が提案・推測段階か

- Kamimusuhiのcanonical DB mutationはconfig YAMLとは異なるため、同一のcache bugがあるとは限らない。
- すべてのwriteにfull snapshotを持つべきとは限らず、version/CAS/hashで同じ保証を作る方法もある。
- external DBやdistributed storeでは「同じread object」よりtransaction snapshot / version bindingが適切。

### (3) 関係するサブシステム/設計課題

- Continuity Kernel / canonical activation
- config / policy / authority metadata
- Persona / memory schema migrations
- device registry / embodiment state
- derived-view rebuild / writeback
- rollback / repair tooling

### (4) 借りられる設計・実装アイデア

write admission evidenceとmutation inputをreceiptで結ぶ。

```text
ValidatedMutationInput
  object_id
  read_version / digest
  read_at
  validation_policy_epoch
  validated_snapshot_ref

MutationProposal
  predecessor = read_version
  computed_from = validated_snapshot_ref
```

同じ保証は以下でもよい。

- DB transaction snapshot
- CAS / ETag / generation
- content digest
- MVCC revision

原則は **「readabilityを確認したstate A」と「mutationを計算したstate B」を暗黙に混ぜない**。

### (5) Kamimusuhiとの差分

既存の `expected predecessor` や provenance-preserving rollbackは「どのversionへcommitするか」を守る。一方今回の穴は、その前の**mutation計算が本当に検証済みの同一stateから導かれたか**。predecessorだけ一致しても、cache層が別viewを返すと意味的に誤ったpatchを作り得る。

### (6) 次に検証すべきこと

**`ValidatedMutationInputCoherenceBench-v0`**

- fresh canonical readは正常、secondary cache readだけempty/stale/corruptにするfault injection
- self-state/profile/config migrationが大量field dropを起こさないこと
- `validated_digest == mutation_input_digest` または同一transaction revisionをassert
- guard後・commit前にconcurrent writerを入れCAS conflictへ落ちること
- repair/rollback pathでも同じinvariantを使う

### (7) 既存デイリーサーベイではなぜ拾いにくいか

これはtransaction一般論より細い **TOCTOU + cache provenance** 問題。write gateを持っているだけで安全に見えるため、guard後の「二度目のread」を追わないと見つからない。

### (8) 重要度

**A** — canonical self / policy / device registryで起これば、正常fileが「成功扱いのsave」で静かに縮退するため高リスク。

## 5.3 A — Configuration Authority Precedence: ambient environmentをprofile-local intentより強くしない

**一次資料**

- Hermes Agent PR #114244  
  https://github.com/NousResearch/hermes-agent/pull/114244

### (1) 何が実証済みか

#114244 は email adapter が `env first, extra second` でsettingを解決していたため、secondary profileが `config.yaml` に明示したaddress / SMTP host / SMTP security / TLS verify等が、process environmentに存在する `EMAIL_*` 値でsilent overrideされる問題を示している。

shared/multiplex processでdefault profile由来のenvがbridgedされた場合だけでなく、単にambient environmentに値があるだけでも起こり得る。提案修正はexplicit profile configを先に採用し、scoped envをfallbackにする。mutation verificationを含む70 tests passを報告。ただし調査時点 **open / 未merge**。

### (2) 何が提案・推測段階か

- 「常にfile config > env」が普遍的に正しいわけではない。deployment overrideを意図してenvを最上位にするsystemもある。
- 重要なのは固定順位そのものではなく、**source authorityがschemaで明示され、profile boundaryを跨ぐambient値が勝手に上位へ昇格しないこと**。
- secretとnon-secret configでは適切なprecedenceが異なる可能性がある。

### (3) 関係するサブシステム/設計課題

- K-Edge / K-Core multi-profile / multi-organ runtime
- communication surfaces / email / Slack / sensor adapters
- credential / secret resolution
- network endpoint / routing configuration
- Embodiment State
- identity-bound connector configuration

### (4) 借りられる設計・実装アイデア

各config fieldにsourceとauthority classを残す。

```text
EffectiveConfigValue
  key
  value
  source = PROFILE_EXPLICIT | ORGAN_LOCAL | DEPLOYMENT_ENV | DEFAULT
  source_principal
  source_scope
  precedence_rule_id
  resolved_at
```

さらに `EffectiveEnvironmentManifest` と組み合わせ、**「値が存在する」ことと「その値がこのprofileをoverrideする権限を持つ」ことを分ける**。

### (5) Kamimusuhiとの差分

9/11の EffectiveEnvironmentManifest は「実際のnetwork/filesystem能力がprose/configと一致するか」を扱った。今回の差分は、複数の**正しく観測されたconfig sources同士のauthority precedence**。Credential Non-Inheritanceとも違い、credentialそのものを継承していなくても、ambient non-secret endpoint/security modeで誤routingし得る。

### (6) 次に検証すべきこと

**`ConfigurationAuthorityPrecedenceBench-v0`**

- profile A/Bを同processで起動
- Aのambient envにendpoint/security設定を入れ、Bにexplicit local設定を持たせる
- BがAの値へsilent driftしない
- deployment-wide overrideを許すfieldは明示schemaでのみ上書き可能
- effective configの各fieldにsource/scope/precedence provenanceを表示
- restart / subprocess / executor境界でもprecedenceが変化しない

### (7) 既存デイリーサーベイではなぜ拾いにくいか

security調査はsecret leakageに寄りやすく、**正当な値どうしのprecedence inversion**は見落とされやすい。multi-profile adapter実装の細部に潜るため通常のagent surveyでは拾いにくい。

### (8) 重要度

**A** — multi-device / multi-surface Kamimusuhiで、別身体のendpointやsecurity modeを使う誤結合はidentity/embodiment contaminationへ直結する。

## 5.4 A — Failure-Classed Cognitive Resource Quarantine: provider lane単位で劣化し、理由ごとに復帰時間を変える

**一次資料**

- Hermes Agent PR #113965  
  https://github.com/NousResearch/hermes-agent/pull/113965

### (1) 何が実証済みか

#113965 は auxiliary `provider:auto` のfallbackで、primary failureをfallback chainへ入れるclassifierは存在する一方、**fallback candidate自身**が429 / quota / connection等で失敗すると即raiseしてしまい、次のconfigured laneへ進まない非対称性を修正している。

local stand-in live reproでは A=429, B=429, C=200 のとき、修正前はA→Bで停止しCへ到達しない。修正後はA→B→Cで成功。Cも429なら各laneを一度だけ試しcontrolled exhaustionする。またtransient 429/connection/invalid responseは約60秒、payment/quota/dead credentialは長いholdと、failure classでquarantine TTLを分ける。

調査時点 **open / 未merge**。したがって設計証拠として評価し、確定upstream behaviorとはみなさない。

### (2) 何が提案・推測段階か

- provider fallbackが増えれば必ず成功率が上がるわけではない。correlated outageや同一upstream依存では多段walkが無駄になる。
- latency / cost / privacy / model-quality差を無視して「全部試す」のは不適切。
- error classifierが誤ると、永久failureを短時間でretryしたり、transient failureを長くbanしたりする。

### (3) 関係するサブシステム/設計課題

- Cognitive Action Router
- K-Core / K-Deep external model routing
- local model server failover
- search / code / retrieval backends
- Cognitive Budget / degraded mode
- provider health telemetry

### (4) 借りられる設計・実装アイデア

resource healthをbooleanにしない。

```text
ResourceLaneHealth
  lane_id
  failure_class
  observed_at
  quarantine_until
  retry_budget
  correlated_failure_domain
  privacy_class
  capability_profile
```

失敗class例:

```text
RATE_LIMIT_TRANSIENT
CONNECTION_TRANSIENT
CAPACITY_TRANSIENT
PAYMENT_EXHAUSTED
CREDENTIAL_DEAD
MODEL_ROUTE_INCOMPATIBLE
MALFORMED_RESPONSE
POLICY_BLOCKED
```

同じfailure fingerprintのlaneを何度も回らず、**laneごとに一度、failure-domain全体が同じなら早期停止**する。

### (5) Kamimusuhiとの差分

既存 `Progress-Sensitive Retry` は「同じ条件を再送するretryをprogressとみなさない」原則。今回はretryではなく、**異なるcognitive resource lane間のhealth/quarantine semantics**。`Dependency-Scoped Hydration retry taxonomy`とも対象が異なる。

### (6) 次に検証すべきこと

**`FailureClassedResourceQuarantineBench-v0`**

- 3 local model/API stand-insで429 / timeout / 402 / auth dead / malformed responseを注入
- transient laneを短期hold、dead credentialを長期hold
- privacy policyで許されないfallbackへは進まない
- same failure-domain laneを無限walkしない
- success率だけでなく added latency / token cost / information exposureを測る
- all lanes exhausted時は最もoperator-actionableなroot causeを返す

### (7) 既存デイリーサーベイではなぜ拾いにくいか

orchestration研究はmodel selection精度やcost最適化を見がちで、**failure class別のquarantine lifecycle**はproduction reliability実装に埋もれやすい。

### (8) 重要度

**A** — Kamimusuhiが外部モデルを「交換可能な認知資源」とするなら、故障時にselfまで停止せず、安全な範囲で別organ/resourceへ縮退する契約が必要。

## 5.5 A — Cognitive Event-Time Watermarks: 「もう来ないだろう」を明示的completeness estimateにする

**一次資料 / 公式資料**

- Akidau et al., *The Dataflow Model*, VLDB 2015  
  https://research.google/pubs/the-dataflow-model-a-practical-approach-to-balancing-correctness-latency-and-cost-in-massive-scale-unbounded-out-of-order-data-processing/
- Apache Beam Programming Guide  
  https://beam.apache.org/documentation/programming-guide/
- Apache Flink, *Timely Stream Processing*  
  https://nightlies.apache.org/flink/flink-docs-release-1.15/docs/concepts/time/

### (1) 何が実証済みか

stream-processing systemsでは、eventが起きた時刻（event time）とsystemが処理した時刻（processing time）は別であり、network / queue / multi-source skewによりout-of-order arrivalが通常に起こる。Dataflow/Beam/Flinkはwatermarkを「あるevent-time以前のdataは概ね/保証上もう到着しない」というprogress/completeness boundaryとして扱い、late data、allowed lateness、early/late triggerを明示する。

これは大規模data processingで長年実運用されている設計概念であり、Kamimusuhi固有の実証ではない。

### (2) 何が提案・推測段階か

- cognitionのepisode boundaryへwatermarkをそのまま移植すると有効かは未実証。
- human/social inputには「永遠にlate replyが来る可能性」があり、strict completeness watermarkを作れない場合がある。
- sensor stream、tool result、delivery、memory consolidationで必要なallowed latenessは異なる。
- watermarkは真実ではなくheuristicの場合があり、late evidence correction contractが必要。

### (3) 関係するサブシステム/設計課題

- multimodal perception / sensor fusion
- distributed embodiment / K-Edge→K-Core event transport
- Global Workspace episode closure
- episodic memory capture / consolidation
- deferred tool results / social delivery
- sleep/offline summarization
- bitemporal memory / reinterpretation

### (4) 借りられる設計・実装アイデア

observation streamごとにprocessing-timeとevent-time progressを分ける。

```text
ObservationStreamState
  source_id
  max_event_time_seen
  processing_time_now
  watermark
  watermark_kind = STRICT | HEURISTIC
  allowed_lateness
  late_event_policy
```

episode summary / consolidationを一発finalizeせず、例えば:

```text
EARLY_VIEW
  -> WATERMARK_CLOSED
  -> LATE_CORRECTION_ALLOWED
  -> FINALIZED / REOPENED
```

とする。特に「5秒何も来なかった」だけでsensor/social episodeを完全とみなさない。

### (5) Kamimusuhiとの差分

Kamimusuhi specにはbackground resultのfreshness、bitemporal memory、historical truth vs interpretationがある。一方、**out-of-order source群から『どこまで到着済みと考えてよいか』というcompleteness progress**は明示されていない。bitemporalはrecord後の時間軸、watermarkはrecordを閉じる前のarrival completenessを扱う。

### (6) 次に検証すべきこと

**`CognitiveEventTimeWatermarkBench-v0`**

- K-Edge A/B、tool server、social channelからtimestamped eventsをout-of-order送信
- processing-time timeoutのみのbaselineとwatermark-aware closureを比較
- late gaze/sensor eventで誤ったepisode summaryが修正されるか
- late tool resultが既にcanonicalizedされた「失敗」eventをどう補正するか
- completeness / latency / recomputation cost / false-finalization rateを測る
- source offline時のwatermark stallとdegraded-mode policyを検証

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent memoryでは「timestampを保存する」話に寄り、stream-processingではidentityやautobiographyを扱わない。**distributed cognitionをunbounded out-of-order streamとして見る**発想が分類境界を跨ぐため拾いにくい。

### (8) 重要度

**A** — multi-device embodimentとcontinuous perceptionが進むほど、「arrival silenceをcompletenessと誤認する」問題がepisodic truth / sensor fusion / social causalityへ波及する。

## 11. 結論

今回の補完サーベイでは、memory algorithmやagent reasoningそのものより、**長寿命個体の周縁にある「入力shape」「read snapshot」「config source」「resource health」「event-time completeness」**に新しい穴が見つかった。

とくに重要なのは次の二つ。

> **検証に使ったstateと、実際にmutationを計算したstateが同じでなければ、write gateがあっても安全ではない。**

> **何も届いていない時間が続いたことは、過去のeventがもう届かないことの証明ではない。**

前者はcanonical mutation / config / migrationのsilent collapseを防ぎ、後者はmulti-device perception / episodic memory / delayed social or tool evidenceのfalse finalizationを防ぐ。どちらもKamimusuhiが「session-level agent」から「長寿命・分散型の人工個体」へ進むほど重要になる。
