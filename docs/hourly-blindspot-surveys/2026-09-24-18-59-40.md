## 3. 要約

今回の中心は、**「長寿命AIの継続性には、本人の記憶でも model hidden state でもない protocol-level continuation artifact が存在する」**ことだった。

Kamimusuhi は identity を model/provider/session から切り離す設計なので、provider の signed reasoning block を Persona や autobiography へ入れるべきではない。一方で、同じ provider conversation を cold resume する契約を提供するなら、その provider が replay に要求する opaque/signed ordered block を失った状態で「同じ session を復元した」と主張することもできない。

したがって少なくとも次を分離する必要がある。

```text
canonical semantic evidence / durable self state
!=
provider-protocol replay envelope
!=
active inference hidden/cache state
```

さらに orchestration 側では、single-flight が duplicate work を1本へまとめた瞬間、caller の cancel token を physical request の owner にしてはいけない。**logical interest と physical acquisition lifetime を別管理**し、最後の consumer が去るまで shared work を生かし、誰も待っていない completion は cache/semantic state を勝手に更新させない必要がある。

memory/sociality 側では、protocol event や control input を USER/ASSISTANT role へ押し込めると、単なる表示バグではなく、将来の model context・fanout cache・autobiographical interpretation が変わる。Kamimusuhi の `thought / utterance / execution / delivery` 分離を、**`conversation act / control event / protocol event / maintenance metadata`** まで明示的な event type として拡張する価値がある。

設計圧縮:

```text
provider-required replay artifact
!=
identity or autobiographical memory

one logical caller canceled
!=
shared physical acquisition should abort

protocol/control event
!=
user or assistant social utterance

same command payload redelivered on another adapter
!=
new authorization to perform the effect again

capability probe failed
!=
capability is supported
```

# 5. 候補ごとの評価

## 5.1 A — Provider-Protocol Replay Envelope Completeness

### (1) 何が実証済みか

Hermes #121293 の hermetic E2E では、同一 process 内では Bedrock `reasoningContent` の text/signature がそのまま次 request に含まれるが、session を別 process で `--resume` すると ordered sidecar がDBにないため消失し、同じ session の wire representation が restart 前後で変わる。

AWS 公式 Converse schema も、multi-turn で reasoning block を再投入する場合に text と signature を unmodified のまま含める必要を明記している。

### (2) 何が提案・推測段階か

- すべての provider が reasoning/signature 永続化を必要とするわけではない。
- provider-specific replay artifact を long-term identity state に含める必要はない。
- raw reasoning text を無期限保存することが privacy / policy 上妥当とは限らない。
- Kamimusuhi が provider-switch を跨いで byte-identical wire replay を保証すべき、という主張でもない。

提案は **「同provider/sessionを protocol-faithful に resume すると約束するなら、必要 artifact をdurableにするか、resume不可と明示する」** に限定する。

### (3) Kamimusuhi のどの subsystem / 設計課題に関係するか

- provider adapter / model routing
- K-Core / K-Deep session runtime
- active cognitive episode resume
- migration / restart
- privacy-preserving memory
- provenance / observability
- graceful degradation / provider switch

### (4) 借りられる設計・実装アイデア

canonical transcript と別に `ProviderReplayEnvelope` を置く。

```text
ProviderReplayEnvelope {
  session_id,
  turn_id,
  provider_id,
  api_mode,
  provider_revision?,
  ordered_blocks,
  integrity_metadata,
  created_at,
  replay_scope,
  retention_policy,
  export_policy,
  encryption_policy,
  replayable: bool
}
```

重要な契約:

- canonical autobiography / self belief へ自動昇格しない。
- same-provider cold resume に必要な opaque block は原順序・原値を保持する。
- privacy/export では canonical chat と別policyを適用する。
- provider switch 時は opaque envelope を無理にtranslateせず、canonical semantic evidence から fresh session を開始する。
- envelope が欠落している場合は `protocol-faithful resume` ではなく `semantic rehydrate` と明示する。

### (5) Kamimusuhiとの差分

既出 `Hybrid Cognitive-State Resume Alignment` は KV / scheduler cursor / hidden cache の alignment を扱う。今回の artifact は tensor/cache state ではなく **provider API が将来 request の妥当性のために要求する protocol object**。

また canonical evidence / Persona state とも異なり、本人性を構成しない。Kamimusuhi の model-independent identity を守るためにも、むしろ別レイヤに隔離する必要がある。

### (6) 次に検証すべきこと

**`ProviderReplayEnvelopeBench-v0`**

- in-process turn N+1 と cold-resume turn N+1 の provider request semantic/wire-required block が一致するか。
- signed / encrypted / opaque block の欠落・並べ替え・改変を検出できるか。
- provider swap では raw envelope を使用せず semantic rehydrate へ落ちるか。
- export / telemetry / long-term memory へ opaque reasoning が accidental leak しないか。
- retention expiry 後は「同provider exact resume不可」を正しく返せるか。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

「persistent memory」「identity continuity」「provider routing」で検索すると、意味記憶や session state、KV cache は拾えるが、**特定providerの request schemaにだけ存在する signed/opaque continuation sidecar** は API adapter の plumbing に見えて落ちやすい。

### (8) 重要度

**A**

理由: model/provider independent identity と provider-faithful session resume を両立するための状態分類として重要。直接 identity を変えるものではないので S にはしないが、実装初期に型を分けないと後から privacy / migration / replay を壊しやすい。

## 5.2 A update — Shared Acquisition Cancellation Ownership

### (1) 何が実証済みか

OpenClaw #157189 は、shared promise が個別 caller の signal を捕まえることで、1 caller の cancel が他 caller の必要な request までabortし得る source-level defect を示す。同issueは source review はcompleteだが exact baseline/candidate runtime qualificationはpendingと明記しているため、現時点では実装構造に基づく強いevidenceとして扱う。

### (2) 何が提案・推測段階か

Kamimusuhi の全shared readで reference-counted cancellation が最適とは限らない。高コストGPU inference、sensor snapshot、network fetchでは cancellation cost / provider billing / completion valueが異なるため policy 化が必要。

### (3) 関係 subsystem

- model/tool orchestration
- shared retrieval / provider catalog
- K-Edge/K-Core sensor reads
- deduplicated background cognition
- cache / admission / quota accounting
- cancellation / liveness observability

### (4) 借りられる設計・実装アイデア

```text
LogicalWaiter { waiter_id, deadline, cancel_reason, authority_epoch }
SharedAcquisition { key, physical_owner, waiters[], state, abort_policy }
```

- caller cancel はその waiter だけをdetach。
- surviving waiterが1つでもあればphysical acquisition継続。
- 最終 waiter が去った時に physical abort policy を評価。
- no-waiter completion は cache-warm / durable mutation を自動許可しない。
- logical cancellation 後も physical request が未settledなら resource accounting 上は消さない。

### (5) Kamimusuhiとの差分

`Keyed Single-Flight Read Ownership with Revalidation` は **duplicate workのcoalescingとjoin後のcurrentness revalidation** が中心だった。今回の差分は **logical consumerとphysical acquisitionのcancel authority / settlement lifetime**。

### (6) 次に検証すべきこと

**`SharedAcquisitionCancellationBench-v0`**

- waiter A/B が同一keyにjoin。
- AだけcancelしてもBは成功する。
- A/B両方cancelでphysical abort。
- abort不可providerではphysical settleまでin-flight countを保持。
- abandonment後の結果がcacheをwarmしないモードを検証。
- authority epochが変わったwaiterだけresult適用を拒否できるか。

### (7) なぜ拾いにくいか

single-flight は通常 performance optimization として扱われ、cancel token の authority model、physical settlement、cache admissionまで一緒に調べないとこの失敗は見えない。

### (8) 重要度

**A update**

独立原則ではなく 06:59 finding の重要なlifetime拡張。

## 5.3 A update — Semantic Transcript Role Closure

### (1) 何が実証済みか

Hermes #121301 は `contextCompaction` protocol item が raw JSON assistant messageとしてdurable化され、resume/export/thread fallbackでassistant発話として再利用される hermetic repro を持つ。

加えて AWS AgentCore Memory は conversational payload と non-conversational JSON event をAPI型として分離し、system event / activity logを疑似会話に変換せず保存できる。これはKamimusuhi固有の正解ではないが、実装可能なschema precedentになる。

### (2) 何が提案・推測段階か

すべてのcontrol eventを durable化すべきとは限らない。compaction boundaryは provenanceに必要な場合がある一方、provider-specific noiseはdrop可能。何をcanonical evidenceへ残すかは別policyが必要。

### (3) 関係 subsystem

- canonical evidence / episodic transcript
- social cognition / relationship history
- compaction / replay
- model/tool orchestration
- MoA / specialist fanout
- export / audit

### (4) 借りられる設計・実装アイデア

`role` だけでevent意味を表さない。

```text
Event {
  event_kind: UTTERANCE | CONTROL | PROTOCOL | MAINTENANCE | TOOL | OBSERVATION,
  actor,
  social_role?,
  illocutionary_act?,
  visibility,
  persistence_class,
  payload,
  provenance
}
```

conversation renderer は `UTTERANCE` だけを通常のUSER/ASSISTANT historyへ投影し、CONTROL/PROTOCOLは必要に応じたtyped instruction / metadataとして明示的にrenderする。

### (5) Kamimusuhiとの差分

2026-09-20 `Synthetic Replay Annotation Isolation` では **synthetic markerが過去のtool contentに見える**ことを扱った。今回の差分は、**protocol/control object自体がsocial actor roleを獲得する**こと。

2026-09-21 `Illocutionary Action Boundary` とも接続するが、今回の対象は人間の発話行為だけでなく machine protocol / maintenance event まで広がる。

### (6) 次に検証すべきこと

**`SemanticTranscriptRoleBench-v0`**

- compaction / retry / steer / handoff / provider marker を混ぜたevent streamを作る。
- exportされたsocial transcriptにprotocol JSONがassistant utteranceとして出ない。
- model replayでcontrol eventが自己発話として模倣されない。
- fanout cache keyが`control event`を`new user turn`と誤認しない。
- canonical event logには必要なcontrol provenanceを失わず残せる。

### (7) なぜ拾いにくいか

provider adapter / compressor / transport projector の fallback behaviorに潜み、表面的には「message serialization bug」に見えるため、social cognitionやautobiographical identityの調査からは拾いにくい。

### (8) 重要度

**A update**

新原則にはしないが、Kamimusuhiのevent schemaを早期にtyped化する強い追加証拠。

## 5.4 A update — Cross-Surface Effect Replay Identity

### (1) 何が実証済みか

Hermes #121325 のE2E報告では、同一 `/restart` redeliveryが Telegram では stale guard される一方、Discord / Slack では `platform_update_id` が存在しないため再度gateway restartを発火する。

### (2) 何が提案・推測段階か

platform message ID が必ずglobal uniqueとは限らず、編集・thread・bridge・forward等の意味論も異なる。単純な `message_id` 一本化だけで全surfaceのexactly-once effectを保証できるとは限らない。

### (3) 関係 subsystem

- multi-surface input
- K-Edge / gateway
- restart / shutdown / emergency control
- action admission / effect receipt
- distributed embodiment

### (4) 借りられる設計・実装アイデア

adapterごとのraw idから normalized `SourceEventIdentity` を作る。

```text
SourceEventIdentity {
  surface,
  account_or_binding,
  conversation,
  platform_event_id,
  event_incarnation?,
  edit_revision?
}
```

restart/delete/payment等のeffectful commandは `SourceEventIdentity + effect_class` へreceiptをbindし、platform固有のfield欠落時は「dedupできないのでfresh」と楽観しない。

### (5) Kamimusuhiとの差分

既出 replay-dedup horizon / transition-qualified effects は replay generally を扱う。今回の差分は **surface adapterごとに replay identity のfieldが違う時、共通effect contractまでidentityを運ぶこと**。

### (6) 次に検証すべきこと

**`CrossSurfaceEffectReplayIdentityBench-v0`**

Telegram / Discord / Slack / Webhook mockで同じlogical redeliveryを作り、restart/delete/side-effect commandが各surfaceで1回だけ実行されることを確認する。edit/reaction/forwardは別eventとして扱うfixtureも入れる。

### (7) なぜ拾いにくいか

exactly-onceやdedupを抽象レイヤだけで見ていると、adapterがそもそもidentity fieldを埋めていない問題が見えない。multi-device embodimentの「入口の異質性」に属する。

### (8) 重要度

**A update**

control commandの再実行はblast radiusが大きいが、原則自体は既出のためupdate扱い。

## 5.5 B update — Proof-Before-Detach Capability Polarity

### (1) 何が実証済みか

Hermes #121048 は、`async_delivery_supported()` probeの例外時にpush targetを返し、delivery-capableと扱うsource pathを特定している。同じ形がcron dispatchにもあると報告する。到達条件はimport/binding failure等でnarrowであり、live loss-rateの実証はない。

### (2) 何が提案・推測段階か

すべてのprobe failureをhard denyすべきとは限らない。read-only optimizationならfallback可能だが、**detached workのresult delivery** のようにconsumer existenceがliveness条件ならfail-closedが合理的、という範囲に限定する。

### (3) 関係 subsystem

- background cognition
- delegate / subagent
- cron / scheduler
- result delivery
- degraded-mode operation
- liveness / capability telemetry

### (4) 借りられる設計・実装アイデア

boolean capabilityではなく三値以上を使う。

```text
CapabilityEvidence = SUPPORTED | UNSUPPORTED | UNKNOWN | STALE
```

`detach` は `SUPPORTED` のみ許可し、`UNKNOWN/STALE` は synchronous execution / durable outbox / explicit defer のいずれかへ落とす。

### (5) Kamimusuhiとの差分

既出 capability readiness / freshness は広い。今回の差分は **delivery consumerを証明できないのにbackgroundへdetachするerror-polarity** を具体的にtestableにする点。

### (6) 次に検証すべきこと

**`CapabilityProbePolarityBench-v0`**

- capability readがtrue / false / exception / timeout / staleの5条件。
- detached childが許可されるのはproven supportedだけ。
- unknown時のfallbackで結果が失われない。
- telemetryに`unsupported`と`probe_failed`を別表示する。

### (7) なぜ拾いにくいか

正常系ではprobeがほぼ失敗せず、コードレビューでも`except: fallback`に見える。background result-deliveryのconsumer proofと結びつけて初めて危険性が見える。

### (8) 重要度

**B update**

重要だが到達条件が狭く、既存capability contractのfixture強化で十分。

## 10. 結論

**有意な新規発見あり。**

今回の独立新規は **Provider-Protocol Replay Envelope Completeness (A)** の1件。ほかは既存 finding を無意味に増やさず、single-flight cancellation、synthetic/control transcript typing、cross-surface replay identity、capability probe polarity の具体的な更新として整理した。

最も重要な設計判断は次の3層分離:

```text
1. canonical semantic/self state
2. provider-protocol replay envelope
3. active inference/cache state
```

この区別を持つと、provider固有のsigned/opaque artifactを「本人の記憶」にしてしまう誤りと、逆にresumeに必要なprotocol artifactを単なる一時データとして捨ててしまう誤りの両方を避けられる。

次の実装優先順位は **`ProviderReplayEnvelopeBench-v0` → `SharedAcquisitionCancellationBench-v0` → `SemanticTranscriptRoleBench-v0`**。いずれもLLM品質評価に依存せず、小さなdeterministic fixtureから始められる。
