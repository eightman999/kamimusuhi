## 4. 要約

今回の最重要発見は、Kamimusuhi の「誰が言ったか」「誰の権限で動いているか」「何がその入力を生んだか」を、単一の `principal` フィールドに押し込んではいけないということだ。

Letta Code #4423 は、**一つの active continuation が principal A の request / billing / authorization context を維持したまま、human B、別 human C、bearer-authored notification、tool result を同じ continuation 内で受け取れる**ように修正した。修正前は acting user が変わると queue 消費を止めたり、複数入力を一つの user message にまとめたりしていた。修正後は request actor を維持し、各 message の author / ID / content を別々に保存する。

これは Kamimusuhi にとって、既存の AsyncCausalContext より一段細かい。

```text
execution principal      = この continuation が誰の委任・権限で動くか
message author           = この意味内容を誰の発話として扱うか
causal producer          = background job / tool / organ のどこから生じたか
delivery/transport actor = どの component が運んだか
```

これらは一致することもあるが、**一致を仮定してはいけない**。

さらに Goffman の production format / footing は、会話上の「speaker」を animator / author / principal へ分解する。agent runtime の attribution 問題をそのまま Goffman 用語へ写像するべきではないが、「発話を物理的に運ぶもの」「語を構成したもの」「その発話に社会的責任を持つ主体」を分解する発想は、Kamimusuhi の social memory / quotation / relay / generated notification に非常に相性がよい。

第二の重要発見は、**human approval UI 自体が safety-critical runtime component** だということ。#4422 では malformed `AskUserQuestion` payload が tool implementation の validation より先に specialized approval UI を crash させ得た。Effect Acceptance が正しくても、approval surface が落ちれば人間は承認も拒否もできない。

第三は self-invocation topology。#4425 は current conversation への agent message を普通の inter-agent message として扱うことを拒否し、Monitor / schedule を self-invocation の別経路として使う。これは「自己刺激」を一般 message queue に混ぜず、**内因性 trigger の意味・予算・再入可能性を型で分離する**設計へ接続できる。

## 6.1 S — Participation-role separation: 「誰が言ったか」と「誰の権限で動くか」を分離する

**Fresh primary implementation:** Letta Code PR #4423  
https://github.com/letta-ai/letta-code/pull/4423  
Merged: **2026-09-14 12:14:50 JST**

**Related standards context:**

- WIMSE Applicability for AI Agents (`draft-ni-wimse-ai-agent-identity`)  
  https://datatracker.ietf.org/doc/draft-ni-wimse-ai-agent-identity/
- AI Agent Authentication and Authorization (`draft-klrc-aiagent-auth`)  
  https://datatracker.ietf.org/doc/draft-klrc-aiagent-auth/

**Humanities / social-science backfill:**

- Erving Goffman, *Forms of Talk* (1981), production format / footing
- HAU review of animator / author / principal distinction  
  https://www.journals.uchicago.edu/doi/full/10.14318/hau3.3.006

### (1) 何が実証済みか

#4423 の regression では、以前の listener は queue 内で acting user が変わると入力消費を止め、複数入力を一つの user message にまとめる挙動を持っていた。

修正後は:

- active continuation の request header / billing identity は維持する
- queued human message は message ごとに `acting_user_id` attribution を保持する
- generated notification は bearer-authored として空 attribution を保持できる
- explicit attribution は上書きしない
- message content / ID / authorship を個別に保持する
- recovery / pre-stream conflict handling で queued sender を request actor に昇格させない

focused suite は 196 tests を通し、実 HTTP fixture で「tool result + bearer reminder + human input」を一つの continuation に入れながら request actor が変わらないことを確認している。ただし server 側の per-message attribution 対応との hosted E2E は未実施で、release 前 validation が残っている。

IETF の agent identity / authorization drafts も、agent workload identity と delegated user/system context を分け、call context と delegation context を audit 可能に保持する方向を示している。これは RFC ではなく work in progress である。

### (2) 何が提案・推測段階か

Kamimusuhi で以下の4軸が常に必要だ、という部分は今回の設計仮説である。

```text
ExecutionPrincipal
MessageAuthor
CausalProducer
DeliveryActor
```

Goffman の animator / author / principal とこれらは**同型ではない**。社会科学概念は、speaker を一個の identity に潰さないための設計語彙として借りる。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Global Workspace / input normalization
- relationship memory / social cognition
- autobiographical memory
- provenance / evidence graph
- Effect Acceptance
- multi-user interaction
- background notifications / K-Edge events
- quotation / relay / summarization
- Persona Core が「誰から学んだか」を記録する learning episode provenance

### (4) 借りられる設計・実装アイデア

`ParticipationEnvelope` を durable input item に持たせる。

```text
ParticipationEnvelope
  event_id
  content_ref
  message_author: KNOWN(id) | BEARER | UNKNOWN
  causal_producer_id?: id
  delivery_actor_id?: id
  transport_sender_id?: id
  active_execution_principal_ref
  authorization_context_ref
  quoted_source_ref?: evidence-id
  received_at
```

利用規則:

- relationship memory の「誰が言ったか」は `message_author`
- tool/effect 実行権限は `active_execution_principal_ref`
- background job の責任追跡は `causal_producer_id`
- relay / quotation は `quoted_source_ref`
- `UNKNOWN` や `BEARER` を current user に暗黙昇格しない
- message を coalesce する場合も author boundary を失わない

### (5) Kamimusuhiとの差分

既存 `AsyncCausalContext` は「background completion が誰から始まったか」と current authorization を分離した。今回の差分は、**一つの continuation の最中に複数 origin / author の message が同時に入ること**、そして queue 消費時に request principal を sender へ rebinding してはいけないこと。

既存 provenance も source chain は持てるが、social participant role と execution authority を明示的に別 field へ固定してはいない。

### (6) 次に検証すべきこと

**`MixedPrincipalContinuationBench`**

シナリオ:

1. principal A の authorization で tool-running continuation を開始
2. tool await 中に human B、human C、bearer notification、K-Edge event を queue
3. continuation 時に全 item を取り込む
4. 次 effect を生成

検証:

- request / execution principal が勝手に B/C へ変わらない
- message は author ごとに分離されたまま
- B の発言を A の発言として relationship memory に保存しない
- bearer / unknown notification を human statement にしない
- B が書いた命令文だけで B の capability が continuation へ付与されない
- coalescing / summarization 後も participation metadata が追跡可能
- restart / replay 後も同一 attribution が再構築される

### (7) 既存 daily survey ではなぜ拾いにくいか

- security survey では delegation / authorization に吸収される
- social cognition survey では発話者認識の問題に吸収される
- distributed systems survey では message metadata に見える
- HCI survey では multi-user UI の話に見える

実際にはこれら4分野の境界にあるため、単一カテゴリ検索では落ちやすい。

### (8) 重要度

**S** — Kamimusuhi の「同じ個体が複数人・複数organ・background process から入力を受けても、権限と社会的記憶を混同しない」ための中心 contract になり得る。

## 6.2 A+ — Approval-plane survivability: 承認画面も safety boundary の一部

**Fresh primary implementation:** Letta Code PR #4422  
https://github.com/letta-ai/letta-code/pull/4422  
Merged: **2026-09-14 09:10:10 JST**

**Related HCI / safety context:**

- NASA Crew Interfaces: crew interface は safety / human performance に重要な system boundary として扱われる  
  https://www.nasa.gov/reference/10-0-crew-interfaces-vol-2/
- NASA graceful-degradation work: safety-critical complex systems では failure 時の graceful degradation と human-system integration が重要  
  https://ntrs.nasa.gov/citations/20190002752

### (1) 何が実証済みか

#4422 では malformed `AskUserQuestion` arguments が、tool implementation 側の validation より前に specialized approval UI を crash させ得た。

修正は:

- specialized UI の描画前に question payload を parse / validate
- answer submission 時も同じ parser を使う
- malformed payload は generic approval UI へ fallback
- option array 等が壊れていても renderer が落ちないよう defense in depth

focused approval-parser / renderer / tool tests 25件と isolated Node host で検証されている。ただし full conversation fork/resume E2E ではない。

### (2) 何が提案・推測段階か

Kamimusuhi で approval surface を独立した safety-critical subsystem として SLO / degraded mode の対象にすべき、というのは設計提案。

### (3) 関係する subsystem / 課題

- Effect Acceptance
- explicit confirmation
- human override / refusal
- runtime assurance
- UI / mobile / voice approval
- degraded-mode operation
- accessibility
- observability

### (4) 借りられる設計・実装アイデア

`ApprovalPresentation` と `ApprovalDecision` を分離する。

```text
CanonicalPendingEffect
   |
   +-> rich approval renderer
   |      malformed / unsupported
   v
 generic safe renderer
   |
   +-> alternate surface / CLI / web / mobile
   v
 explicit approve | deny | defer
```

規則:

- rich UI parse failure で canonical pending effect を失わない
- UI crash を `approval denied` と勝手に解釈しない
- effect は承認なしに実行しない
- unknown schema は generic representation へ degraded-mode fallback
- user が何を承認するか確認できない場合は fail-closed
- approval payload と effect payload の digest binding を維持

### (5) Kamimusuhiとの差分

既存 Effect Acceptance は「何を承認すべきか」は強いが、**承認を提示する UI が壊れたときに安全 contract をどう維持するか**は薄い。

### (6) 次に検証すべきこと

**`ApprovalSurfaceFailSafeBench`**

fuzz input:

- null / missing fields
- wrong scalar/list type
- unknown schema version
- oversized option list
- invalid Unicode
- partial/corrupt serialized state
- stale approval after restart
- renderer plugin unavailable

合格条件:

- UI process が落ちない
- pending effect が canonical store に残る
- generic fallback が表示可能
- user が target/effect/risk を特定できなければ approve 不可
- alternate surface から同一 effect digest を approve/deny できる
- timeout と deny を区別する

### (7) daily survey で拾いにくい理由

human-in-the-loop は policy / alignment として扱われがちで、**approval UI の parser / renderer が安全機構そのもの**という software-HCI 境界は検索語から漏れやすい。

### (8) 重要度

**A+** — Effect Acceptance が強くなるほど、approval plane の単一点故障は相対的に重要になる。

## 6.3 A — Typed self-invocation & scoped reentrancy

**Fresh primary implementation:** Letta Code PR #4425  
https://github.com/letta-ai/letta-code/pull/4425  
Merged: **2026-09-14 10:02:40 JST**

**Systems backfill:** Microsoft Orleans request scheduling / call-chain reentrancy  
https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling

### (1) 何が実証済みか

#4425 は agent が **現在自分が実行中の conversation へ ordinary message を送る**経路を拒否した。比較は caller agent + current conversation の runtime context で行い、`--from-agent` 等の見かけの sender を偽装しても回避できない。同一 agent の別 conversation / fork への message は許可される。

PR は self-invocation が必要なら Monitor / schedule を使うよう明示し、6 rejection regressions、82 focused tests、built CLI で zero enqueue を確認している。

Orleans の official documentation では actor/grain 間 call chain が元の grain へ戻る cycle は、reentrancy を明示的に許可しなければ deadlock し得る。一方、広い reentrancy は race / state corruption の危険があるため、call-chain scope で細かく許可する仕組みを持つ。

### (2) 何が提案・推測段階か

Letta の fix 自体は「self-message が runaway loop を起こした」と実証していない。Kamimusuhi で direct self-message が endogenous event amplification、duplicate cognition、effect duplication、billing runaway を生み得るという部分は**検証すべき仮説**。

### (3) 関係する subsystem / 課題

- default cognition / spontaneous cognition
- scheduler / reminders / monitor
- Global Workspace event injection
- internal reflection
- multi-conversation / branching identity
- cognitive budget
- liveness / reentrancy
- observability / causal trace

### (4) 借りられる設計・実装アイデア

自己起動を message という一種類に潰さず型を分ける。

```text
SelfInvocationKind
  INTERNAL_CONTINUATION
  SCHEDULED_WAKE
  MONITOR_TRIGGER
  OFFLINE_CONSOLIDATION
  CROSS_CONVERSATION_MESSAGE
  DIRECT_CURRENT_CONVERSATION_MESSAGE  -> deny by default
```

さらに `EndogenousTriggerLineage` を持つ。

```text
trigger_id
parent_trigger_id?
root_external_event_id?
kind
hop_count
spawn_budget
expires_at
```

reentrancy が本当に必要な場合だけ、scope / operation / lifetime を限定した `ReentrancyPermit` を発行する。

### (5) Kamimusuhiとの差分

Kamimusuhi は sleep/dream、default cognition、background processing を構想しているが、**「自分から自分への刺激」を inbound social/message channel と同じ queue semantics で扱ってよいか**は明確でない。

### (6) 次に検証すべきこと

**`SelfInvocationTopologyBench`**

比較:

- direct current-conversation enqueue
- internal continuation
- scheduled wake
- monitor trigger
- same-agent other-conversation message

計測:

- 1 root event あたり生成 turn 数

- stop / cancel の効きやすさ
- token / latency / energy amplification
- restart 後の trigger duplication

### (7) daily survey で拾いにくい理由

AI agent の「autonomy」は planning や scheduler として検索される一方、actor-model の reentrancy / event-cycle と長寿命 agent の自発 cognition を同じ問題として見る検索は少ない。

### (8) 重要度

**A** — すぐ必須ではないが、default cognition や永続的 background process を増やす段階で重要度が上がる。

## 6.4 A（既出項目への差分更新）— Recovery authority must be revalidated, not memoized

**Fresh primary implementation:** Letta Code PR #4426  
https://github.com/letta-ai/letta-code/pull/4426  
Merged: **2026-09-14 11:52:20 JST**

### (1) 何が実証済みか

直前の #4410 / Expected Continuation Barrier は incoming destination 側の ordinary recovery を抑止したが、**teleport を終えて yield した source listener** や、in-memory teleport marker を持たない freshly prepared listener が stale approval を crash recovery として再構築し、既に成功した tool を deny して competing continuation を始める余地が残った。

#4426 は recovery entry で:

- local handoff state
- Cloud runtime-status owner
- conflicting listener
- pending delivery / live work

を確認し、別 owner がいる・lookup に失敗した等の場合は recovery を defer する。さらに backend await 後にも ownership を再確認し、**以前得た recovery permission を cache しない**。

controlled regression では shipped v0.32.7 が期待0 continuation に対して2 continuation を開始したケースが、fix 後は0になった。unreleased bundle による full Cloud teleport E2E は未検証。

### (2) 提案・推測

Kamimusuhi のすべての migration / recovery decision を lease-style revalidation にすべきかは今後の検証対象。

### (3) 関係先

- Continuity Kernel
- Expected Continuation Barrier
- K-Edge/K-Core migration
- pending effect recovery
- active episode lease

### (4) 借りる差分

既存 `HandoffRecoveryRaceBench` に **TOCTOU injection** を加える。

```text
check owner -> await network/storage -> owner changes -> resume
```

合格条件は、await 前の `RECOVER_OK` を capability として保存せず、commit/recovery-start 直前に current owner / handoff state を再確認すること。

### (5) Kamimusuhiとの差分

新原則ではない。前回 survey の `recoverable state != recovery authorized now` を、**permission is not stable across await** まで具体化する差分。

### (6) 次に検証

`RecoveryOwnershipTOCTOUBench`:

- lookup 中に migration 開始
- lookup failure
- source yield → delayed sync
- owner changes twice
- duplicate sync
- partition recovery

### (7) daily で拾いにくい理由

#4410 を既に採用候補にすると「問題は解決済み」に見えやすく、その後の source-side counterexample は同一テーマとして重複除外されやすい。

### (8) 重要度

**A（差分更新）** — 新規設計項目として数えず、既存 bench / contract の strengthening として扱う。

# 13. 結論

今回の中心 invariant 候補は次の3つ。

```text
message author != execution principal != causal producer

approval policy exists != approval surface remains operable

self-directed event != ordinary inbound message
```

Kamimusuhi の次の実験として最も情報量が大きいのは **`MixedPrincipalContinuationBench`**。これは新しいモデルや hardware を必要とせず、既存 provenance / Effect Acceptance / relationship-memory fixture の上で、multi-user + background event を混ぜるだけで試せる。

ここで失敗するなら、memory や sociality を増やす前に ingress representation を直すべきである。特に、発話者の違う message を一つの user turn に潰したり、最後に届いた sender を active execution principal にしてしまう実装は、**identity continuity と authority safety の両方を同時に壊し得る**ため優先度が高い。
