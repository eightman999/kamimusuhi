## 4.1 Completion Publication Barrier — 「finished set が空」でも episode は終わっていない

**Importance: A**  
**Blind-spot class:** distributed termination detection / process registry internals / asynchronous publication boundary

### Sources

- NousResearch/hermes-agent PR #111430, merged **2026-09-15 12:44:57 JST**  
  https://github.com/NousResearch/hermes-agent/pull/111430
- Edsger W. Dijkstra & C. S. Scholten, *Termination detection for diffusing computations* (1979 manuscript / 1980 IPL)  
  https://www.cs.utexas.edu/~EWD/transcriptions/EWD06xx/EWD687a.html  
  DOI: https://doi.org/10.1016/0020-0190(80)90021-6

### (1) 何が実証済みか

Hermes Agent #111430 の concrete regression は非常に小さいが、長寿命 agent には重要である。

`ProcessRegistry._move_to_finished` は child session を `_running` から外した後、receipt保存、handle解放、checkpoint書込みを行い、その**後**で completion を queue へ publish して `_completion_event` を立てていた。quiet one-shot parent がこの数msの窓で `wait_for_pending_completions` を実行すると、`_running` は空、completion queue もまだ空なので「待つものなし」と判断し、follow-up notification を失った。

PRでは `_finished` に移動済みでも `_completion_event` が未setの session を pending とみなす。強制race E2Eでは main が2/2 fail、fixが2/2 pass。関連focused suiteは139 tests pass と報告されている。

Dijkstra–Scholten の古典的 termination detection は、分散計算で各nodeが受動状態に見えるだけでは termination を宣言できず、まだ伝播中の計算message / engagement を会計する必要がある、という一般形を与える。

### (2) 何が提案・推測段階か

Hermes の bug は process-registry 内の completion publication race を実証したものであり、Kamimusuhi 全体に Dijkstra–Scholten をそのまま実装すべきことは示していない。

Kamimusuhi で「cognitive episode の終了」を global quiescence problem として扱い、publication debt / causal debt を明示状態にする案は設計提案段階。

### (3) Kamimusuhi のどのサブシステム/設計課題に関係するか

- background cognition / background jobs
- external tool / subagent completion
- Global Workspace への結果publish
- task / action lifecycle
- dream / offline consolidation へ移行する境界
- session close / episode close / shutdown
- Continuity Kernel へ receipt を確定する境界
- output delivery / notification

### (4) 借りられる設計・実装アイデア

`CompletionPublicationState` を worker の実行状態と分離する。

```text
RUNNING
  -> COMPUTE_FINISHED
  -> RECEIPT_DURABLE
  -> COMPLETION_PUBLISHED
  -> COMPLETION_CONSUMED
  -> CLOSED
```

episode の `QUIESCENT` 判定は少なくとも、

```text
no active work
AND no unpublished completion
AND no unacknowledged causal child
AND no required delivery still in-flight
```

とする。

必要なら background spawn 時に `causal_debt += 1`、completion が親/ownerへ publish され durable acknowledgement を得た時点で `causal_debt -= 1` とする軽量な termination-credit 方式を試せる。これは tool execution 自体の再実行権限とは別物にする。

### (5) Kamimusuhiとの差分

既存の deterministic replay / in-flight continuation / Expected Continuation Barrier は主に、**途中で失われた・再開待ちの仕事をどう復旧するか**を扱う。

今回の差分は、

```text
recoverable work exists?
```

ではなく、

```text
may the system safely assert that no causally relevant work remains?
```

を独立した contract にすること。

`RUNNING set == empty` を `episode complete` と同一視しない。

### (6) 次に検証すべきこと

**`EpisodeQuiescencePublicationRaceBench-v0`**

fault injection:

- child を running registry から外した直後に parent close
- receipt fsync 後・completion publish 前に crash
- completion publish 後・consumer ack 前に reconnect
- child completion が duplicate delivery
- nested subagent が孫taskを残して親だけ finished
- dream/consolidation 開始直前に late completion

比較:

1. active registry empty のみ
2. queue empty 追加
3. publication-state + causal-debt barrier

metrics:

- lost completion rate
- premature episode close rate
- duplicate follow-up rate
- shutdown latency
- false non-quiescent rate
- replay後の canonical result equivalence

### (7) 既存デイリーサーベイではなぜ拾いにくいか

AI-agent memory / orchestration のキーワードではなく、**distributed termination detection と process-registry の数ms race**として現れるため。通常の benchmark では最終task成功率に埋もれやすく、CI負荷や shutdown/quiet mode の timing でのみ露出する。

### (8) 重要度

**A** — identityそのものを直接変える機構ではないが、background cognition を持つ長寿命個体で「もう考えていない」「episodeが閉じた」という事実を誤判定すると、記憶・通知・consolidation・shutdownの境界が壊れる。

## 4.2 Dependency-Scoped Memory Hydration — memory topology を一個の READY bit に潰さない

**Importance: A**  
**Blind-spot class:** startup critical path / partial initialization / Git-backed memory / dependency-local readiness

### Source

- letta-ai/letta-code PR #4438, merged **2026-09-15 12:17:12 JST**  
  https://github.com/letta-ai/letta-code/pull/4438

### (1) 何が実証済みか

Letta #4438 は、primary MemFS と attached/shared repository の同期を分離した。

- primary memory を必要とする mods は primary readiness を待つ
- shared/attached repositories は background clone
- それらを必要とする Shell / Skill / mod tools だけが checkout readiness を待つ
- unrelated external tools / unrelated explicit file paths は block しない
- fresh clone は Git setup 完了後に atomic publish
- refresh failure 時、既存 checkout はアクセス可能なまま残せる
- new clone failure は後続 access で retry
- repository discovery failure は unrelated local tools を disable しない

focused tests は144 pass、Node smokeも実施。ただし PR 自身が **hosted production latency improvement は未検証**と明記している。

### (2) 何が提案・推測段階か

Kamimusuhi の memory hierarchy を同じ readiness topology へ写像し、各 tool/controller が必要memory domainを宣言する設計は未実証。

特に Persona Core / Relationship / Library / shared workspace のどこまでを startup critical にするべきかは、benchmarkで決める必要がある。

### (3) Kamimusuhi のどのサブシステム/設計課題に関係するか

- Continuity Kernel / canonical identity state
- Persona Core / Relationship state
- Library / externalized knowledge
- shared workspace / multi-device embodiment
- tool/model orchestration
- startup / restart latency
- degraded-mode operation
- background sync / freshness

### (4) 借りられる設計・実装アイデア

一個の `agent_ready: bool` ではなく、`MemoryReadiness` と dependency requirement を分ける。

```text
MemoryDomainState
  domain_id
  readiness = ABSENT | HYDRATING | READY | DEGRADED_EXISTING | FAILED
  freshness = CURRENT | STALE | UNKNOWN
  authority = CANONICAL | DERIVED | REPLICA | EXTERNAL
  generation
  last_successful_sync
  failure_reason
```

各 executable surface は、

```text
requires:
  - domain: canonical_identity
    min_readiness: READY
    min_freshness: CURRENT
  - domain: shared_library
    min_readiness: DEGRADED_EXISTING
    min_freshness: UNKNOWN_ALLOWED
```

のような `ReadinessRequirement` を持つ。

重要なのは **readiness と freshness を同じ軸にしない**こと。既存 checkout が使えることと、最新であることは別である。

newly hydrated replica は staging で検証してから atomic publish し、未完成treeを tool から見せない。

### (5) Kamimusuhiとの差分

Kamimusuhi はすでに freshness semantics、degraded mode、capability membership freshness、distributed embodiment を持つ。

今回の差分は、**initialization / restart 中の memory dependency graph を first-class にし、optional memory の readiness を global startup barrier にしない**こと。

```text
whole agent ready
```

という単一状態ではなく、

```text
this operation is ready with respect to its actual dependencies
```

へ変える。

### (6) 次に検証すべきこと

**`PartialHydrationStartupBench-v0`**

setup:

- local canonical identity store: fast
- relationship store: medium delay
- shared Library replica: 10〜60s delay
- optional remote skill repo: timeout / corrupted clone / stale existing checkout

比較:

1. global all-memory startup barrier
2. optimistic no-gate
3. dependency-scoped readiness gate

metrics:

- time-to-first-safe-response
- time-to-first-local-action
- unready-memory illegal access
- stale-as-current confusion
- unrelated tool blockage time
- false capability presentation
- recovery after background hydration failure

### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory research は通常 retrieval quality / forgetting / consolidation / persistence を測る。一方この問題は **Git checkout、startup critical path、partial initialization、tool path resolution**として発生するため、memory algorithm survey から抜けやすい。

### (8) 重要度

**A** — multi-device / shared-memory 化するほど、全同期待ちは可用性を落とし、無待機は安全性を落とす。dependency-scoped readiness はその中間を機械的に表現できる。

## 4.4 既存 finding への fresh 差分: Local Recovery Journal

**Importance: A（新原則ではなく既存 recovery finding の実装更新）**

### Source

- letta-ai/letta-code PR #4444, merged **2026-09-15 07:58:40 JST**  
  https://github.com/letta-ai/letta-code/pull/4444

### (1) 何が実証済みか

listener が process restart を跨いで **自分自身が所有していた unfinished turn だけ**を続行するため、active run、pending tool IDs、completed results、request OTID、working directory、initiating user を local disk に記録する実装がmergeされた。

reconnect時はその local record に属する workだけを対象にし、保存済み結果は再利用、保存されていない tool は二重実行せず interruption denial とする。結果POSTが crash直前にserverでacceptedされたケースも original OTID で解決する。

### (2) 何が提案・推測段階か

PR本文では exact-build managed-sandbox verification が進行中とされており、全production failure modeが実証済みとは扱わない。

### (3) Kamimusuhi との関係

- Expected Continuation Barrier
- deterministic replay
- execution-owner binding
- process incarnation / resource ownership
- external effect duplicate suppression

### (4) 借りられる設計・実装アイデア

既存 recovery bench に `RecoveryJournal` を足す。

```text
RecoveryJournal
  episode_id
  execution_owner_generation
  initiating_principal
  run_id
  request_operation_id
  pending_effect_ids[]
  completed_result_receipts[]
  workspace_binding
  suspended_for_handoff
```

local journal は continuation authority そのものではなく、**「この incarnation が自分の未完了workを主張するためのevidence」**とする。restart後も current lease / generation / handoff state を再検証する。

### (5) 既存 Kamimusuhiとの差分

新しい原則ではない。過去 survey の recovery ownership / Expected Continuation Barrier を、process-local durable evidence で具体化する差分。

### (6) 次に検証すべきこと

既存 `HandoffRecoveryRaceBench` / restart fixture に追加:

- result accepted → local ack前 crash
- model output生成 → run ID受領前 crash
- owner lookup await中に新しいturn到着
- independent 2 conversations 同時restart
- handoff開始直後restart
- old journal + new owner generation

### (7) なぜ拾いにくいか

recovery paper ではなく、listener process の local persistence / OTID reconciliation の実装修正として出ているため。

### (8) 重要度

**A（更新）** — 既存設計を変えるより、benchを現実的な crash boundary へ強化する材料として価値が高い。

## 11. Bottom line

今回の中心は、**長寿命agentの「終わった」と「使える」を単純なboolにしない**こと。

```text
finished computation
!= published completion
!= consumed completion
!= globally quiescent episode

process started
!= all memory ready
!= this operation's dependencies ready
```

Kamimusuhi へ最も先に落とすなら `EpisodeQuiescencePublicationRaceBench-v0`。次点で `PartialHydrationStartupBench-v0`。どちらもモデル性能ではなく runtime invariant を壊しに行くため、現行fixtureで低コストに検証できる。
