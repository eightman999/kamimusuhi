## 4.1 A — Challenge-Bound Continuity Attach Proof

**Primary source**

- NousResearch/hermes-agent PR #120605, *fix(cli): prove lease ownership in the session-attach handshake instead of echoing it*, 2026-09-23 19:58 UTC  
  https://github.com/NousResearch/hermes-agent/pull/120605

**Relevant standard**

- RFC 9449, *OAuth 2.0 Demonstrating Proof of Possession (DPoP)*  
  https://www.rfc-editor.org/rfc/rfc9449.html

### (1) 何が実証済みか

Hermesの`discover_attach_url`は、`/api/session-attach` reply中の `session_id`, `lease_id`, `profile_home` がclient自身がqueryで送った値と一致することを確認していた。しかしrogue loopback listenerは、そのrequestを見れば同じ値をechoできるため、正しいsession ownerでなくても自分の`ws://` URLを返してTUIをattachさせられた。

さらに、ownerを区別するsecretである`lease_id`自体がrequestへ載っていたため、偽listenerはverificationに必要なsecretをrequestから学習できた。

修正は `lease_id` をregistryから外へ出さず、nonceに対して

```text
client_proof = HMAC(lease_id, "...request:<session>:<nonce>")
attach_proof = HMAC(lease_id, "...attach:<session>:<nonce>")
```

を作るmutual proofに変える。PRのregression testは、**全request parameterをechoして同一originの偽WebSocketを返すlistenerが修正前にはaccepted、修正後にはrefused**になることを確認している。forged/non-ASCII proof、wrong profile、off-origin URLもfail closedし、`lease_id`がrequestへ出ないことを確認している。

RFC 9449 DPoPも一般原則として、token/identifierの提示だけでなく、requestごとにkey possessionをproofへbindし、method/URI/nonce/freshnessを検証してreplayを制約する。DPoP自体は認証・authorizationの全部ではないが、「bearer valueを知っている」と「authorized presenterがkeyを所持している」を分ける標準的な先例になる。

### (2) 何が提案・推測段階か

- Hermes PRはopenであり、upstream contractが最終形とは限らない。
- HMAC方式をKamimusuhiへそのまま採用する必要はない。device間ではasymmetric key / mTLS / secure enclave-backed keyの方が適する可能性がある。
- proof-of-possessionだけで「同一個体」の形而上学的identityを証明できるわけではない。証明できるのは、**特定continuity lease / device authority credentialを保持するprincipal**である。
- compromised ownerがvalid proofを返すケース、stolen key、rollback済みgenerationのkey所持までは別問題。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Continuity Kernel / canonical writer handoff
- migration / resume / recovery attach
- K-Edge / K-Core device registration
- session / turn continuation
- distributed embodiment endpoint binding
- authority lineage / lease ownership
- zero-trust internal network

### (4) 借りられる設計・実装アイデア

continuation attachを次のようなchallenge-bound contractにする。

```text
AttachChallenge {
  challenge_id,
  target_individual_id,
  target_runtime_generation,
  expected_session_or_lease_id,
  endpoint_binding,
  nonce,
  expires_at,
  verifier_context
}

AttachProof {
  challenge_id,
  principal_id,
  generation,
  proof,
  algorithm,
  key_id
}
```

原則:

- verifierが既に送ったidentifierを相手が返しただけではproofとしない。
- secret / private keyそのものはverification requestへ送らない。
- proofはsession/leaseだけでなく**generation + endpoint + role + challenge**へbindする。
- nonce / expiry / one-shot receiptでreplayを抑える。
- old runtimeがまだ旧keyを持つ場合でも、current canonical head/generationからretiredならattach拒否する。
- `localhost`, same machine, same profile pathをauthority proofとして使わない。

### (5) Kamimusuhiとの差分

既出の **Authenticated Discovery Probe** は「discovery traffic自身をauthenticated / protocol-boundedにする」話、**Endpoint-Qualified Protocol Binding** は「stateをどのendpoint/protocolへbindするか」、最新dailyの **Local Device Bootstrap Authority Ceiling** は「localityをadmin grantにしない」話である。

今回の差分はさらに具体的に、**“そのendpointが正しいcontinuity ownerだ”というclaimを、相手が秘密/鍵を所持しているchallenge proofで確かめる**こと。

```text
identifier matches
!=
responder possesses current continuity authority
```

### (6) 次に検証すべきこと

`ContinuityAttachPossessionBench-v0`:

1. rogue loopback listenerが全public fieldをechoする。
2. 正常ownerのみattachできること。
3. retired generationのownerがold keyを持つ。
4. valid proofを別session / endpoint / roleへreplayする。
5. challenge reuse / nonce reuse / reordered responseを注入する。
6. client clock skewが大きい条件ではserver nonceで成立すること。
7. network partition後のhandoffでold writerがcurrent proofを作れないこと。
8. proof失敗が「network unavailable」と混同されず、identity refusalとしてobservabilityへ出ること。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent securityでは通常tool authorizationやprompt injectionを見る。これは **local IPC / discovery / cryptographic handshake / continuity lease** の境界にあり、セッションresumeの実装詳細に見えやすい。一方Kamimusuhiではresume endpointの偽装が「誰の続きを起動したか」に直結するため独立重要度が高い。

### (8) 重要度

**A** — distributed embodiment / migrationを本格化する前に閉じるべきP0候補。特に「secretを送ってからechoを検証する」はcontinuity authorityには不適切。

## 4.2 A — Keyed Single-Flight Read Ownership with Revalidation

**Primary source**

- OpenClaw PR #156791, *fix(gateway): sessions.describe stalls while the session list refreshes the same row*, 2026-09-23 21:52 UTC  
  https://github.com/openclaw/openclaw/pull/156791

**Related systems primitive**

- Go `singleflight` — duplicate function call suppression  
  https://pkg.go.dev/golang.org/x/sync/singleflight  
  （同概念のdocumented implementation: https://pkg.go.dev/go4.org/syncutil/singleflight ）

### (1) 何が実証済みか

OpenClawのresident session-row projectionでは、dirty rowに対し

- background bulk refresh
- foreground exact preparation (`sessions.describe`)

の2経路が同じrowを同時にreadできた。両者が互いのin-flight workを知らず、同じlogical rowの2つ目のworker readを発生させ、その2つ目がcold shared-state readerを起動すると1秒超stallすることがあった。

修正はrow ownerが**1 row = 1 in-flight worker read**を保持し、

- bulkはexact readがownedするrowをskip
- exactはbulkがownedするreadへjoin
- join後にaccepted fact / archive / materialization状態を再確認
- 全dirty rowが他callerにownedならdrainはspinせず待つ
- settle後にyieldしてforegroundがplacement snapshotをinstallしてから次のdrainへ進む

とする。

新regression testはworker readを明示holdし、bulk-first / exact-firstの両順序で同じrowが**exactly once**読まれることを確認し、mainではfail、修正後pass。macOS上で約40–50% flakeしていたrecap testはfinal codeで10/10 passと報告されている。

一般的なsingleflightも「同じkeyの同時呼び出しを1回のworkへ束ねる」primitiveを提供する。ただしOpenClawの修正が重要なのは、joinerが既存resultを盲目的に正解扱いせず、settle後に現在stateを再確認している点である。

### (2) 何が提案・推測段階か

- OpenClawの1秒stallがKamimusuhiで同じ形で起きる証拠はない。
- すべてのreadをsingleflight化すればよいわけではない。distinct consistency level、different authority snapshot、different privacy scopeのreadを同一keyへcoalesceすると逆に誤る。
- slow ownerへ高priority foreground requestをjoinさせるとpriority inversionになり得る。
- cancellation propagationを共有すると1 callerのcancelが全waiterを落とす危険がある。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- K-Core low-latency cognition
- memory retrieval / derived view hydration
- relationship/self projection refresh
- Global Workspace materialization
- background cognition vs foreground turn
- resource health / capability refresh
- DB/cache / continual database
- energy-aware cognition / API monetary budget

### (4) 借りられる設計・実装アイデア

単純なmemoizationではなく、**logical resource ownerによるin-flight work registry**を置く。

```text
InFlightReadKey = (
  object_id,
  owner_namespace,
  consistency_class,
  authority_epoch,
  projection_kind
)

InFlightRead {
  key,
  producer_id,
  started_at,
  waiters,
  cancellation_policy,
  result_epoch
}
```

ルール:

1. 同じsemantic keyのworkだけをcoalesceする。
2. worker poolではなく**object/projection owner**がdedup責任を持つ。
3. joinerはproducerのresultを受けたあと、current revision / accepted fact / authorizationを再検証する。
4. producer failureはwaiterごとにretryabilityを再評価する。
5. foreground priorityがbackground ownerにjoinするときはdeadline / promotion / duplicate-read escape hatchを持つ。
6. distinct keyは並列性を失わない。

Kamimusuhiでは、同じepisodic pageをbackground consolidationとactive turnが同時hydrateする、同じrelationship projectionを複数processorが同時再構築する、といった場面で特に効く。

### (5) Kamimusuhiとの差分

既出 **Observer Back-Action** は「観測が対象へ副作用・負荷を与える」問題、**Admission-Wait Snapshot Release** は「scheduler待ちをDB snapshot保持のまま跨がない」問題、**Fair Turn Admission** は優先制御の問題。

今回の差分は、**同じlogical observation/materializationを複数callerが同時に要求したとき、workそのもののownershipを1つへ束ねる**こと。そのうえで、wait中のstate変化を考慮し、singleflight resultをcurrent truthとはみなさない。

```text
same requested read
=> share work where safe

shared work result
!= automatically current/authorized result for every waiter
```

### (6) 次に検証すべきこと

`SingleFlightCognitiveReadBench-v0`:

- background refreshとforeground turnが同じepisodic objectを同時request。
- underlying DB/API/model readが1回だけになること。
- foreground側はjoin後にrevision/currentnessを再確認すること。
- producer failure / cancellation / timeoutを注入し、waiterごとに正しくsettleすること。
- different principal / relationship / privacy scopeはcoalesceされないこと。
- different consistency class (`eventual` vs `canonical-head`)はcoalesceされないこと。
- 1 hot keyで10/100/1000 concurrent requestを入れ、TTFT、CPU、DB reads、energy、queue debtを測る。
- slow background ownerにhigh-priority turnがjoinする場合のpriority inversionを計測する。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent研究ではcache hit率やretrieval qualityを測ることが多いが、**同一stateの並行materialization ownership**はDB/cache internals、actor model、thundering-herd対策に寄る。長寿命agentでbackground/foregroundが常時並行になると初めて重要になる。

### (8) 重要度

**A** — K-Coreの低遅延化・energy/cost削減・DB安定性へ横断的に効き、実装も局所benchで検証しやすい。特に今後background cognitionを増やす前に価値が高い。

## 4.3 A — Authoritative-Consumer Roundtrip Closure

**Primary sources**

- NousResearch/hermes-agent issue #120682, *config writer folds long scalars at width 80 ... backend refuses to start*, 2026-09-23 21:54 UTC  
  https://github.com/NousResearch/hermes-agent/issues/120682
- NousResearch/hermes-agent PR #120685, *fix(config): preserve long YAML mapping keys*, 2026-09-23 21:57 UTC  
  https://github.com/NousResearch/hermes-agent/pull/120685

### (1) 何が実証済みか

Hermesの`config.yaml` writerはruamel round-trip modeを使うが、`yaml_rt.width`を設定せずdefault 80 columnsのままだった。spaceを含む長いplain scalarの**mapping key**（例: 長いGGUF pathをmodel idとして使う）がwrite時にfoldされ、continuation lineへ`: value`が来ることで、もともとvalidだったYAMLがPyYAMLでは`mapping values are not allowed here`になる。

issueのreproは:

1. 元fileは`yaml.safe_load`でvalid、`hermes config check`もclean。
2. `hermes config set logging.level INFO`など無関係のwriteを1回行う。
3. writerが同fileをunreadableへ変換し、次回check/startupが失敗。

reporterは2回on-demandで再現し、手で行を直しても次のwriteで再発するためrepair loopになると報告している。

PR #120685はwriter widthを4096へ広げ、**real full-state save pathで長いspace-containing keyを保存後、PyYAMLが再parseできる**regressionを追加し、focused 12 tests passを報告している。

ここで重要なのはYAML固有の80桁ではなく、

```text
input parses
write returns success
output persisted
```

だけではdurable mutation completionにならず、**そのstateを次に実際に読むconsumerが再解釈できること**まで必要という点。

### (2) 何が提案・推測段階か

- Kamimusuhiのcanonical stateがYAMLで同じbugを持つ証拠はない。
- すべてのwriteで全旧version parserを再実行するのは高コストであり、compatibility envelopeを定義する必要がある。
- parse可能性だけではsemantic equivalenceを保証しない。型coercion、timestamp precision、Unicode normalization、unknown field loss、enum downgrade等も別途必要。
- comments/order等のpresentation fidelityをcanonical semantic correctnessと同一視しない方がよい。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Continuity Kernel durable commit
- self/persona configuration
- software-body / provider/resource registry
- plugin / skill manifests
- migration / backup / restore
- event sourcing / schema evolution
- multi-device old/new runtime compatibility
- self-modifying/autonomic computing

### (4) 借りられる設計・実装アイデア

`serialize`成功ではなく、**consumer roundtrip**をactivation gateへ入れる。

```text
candidate typed state
   -> encode
   -> atomic temp write
   -> authoritative consumer decode
   -> schema validate
   -> semantic-equivalence check
   -> fsync / replace / commit receipt
```

receipt候補:

```text
DurableEncodingReceipt {
  object_id,
  schema_version,
  encoder_id/version,
  consumer_parser_id/version,
  encoded_hash,
  decoded_semantic_hash,
  compatibility_targets[],
  verified_at
}
```

multi-deviceでは、current writerだけでなく**まだactiveなreader generation**のcompatibility targetをmanifest化する。古いreaderが未知fieldをdropして書き戻すようなケースはseparate migration fenceを要求する。

### (5) Kamimusuhiとの差分

既出 **Semantic Transcoding Integrity / Projection-Only Compatibility Repair** はprovider wire formatへの変換がcanonical evidenceを足したり削ったりしないことを扱う。最新dailyの **Activation Artifact Closure** は正しいcommit由来でも必要artifactが欠けていないかを見る。

今回の差分は、**canonical/durable stateそのものを書いたあと、そのstateがauthoritative consumerにとって有効な意味表現であり続けるか**。

```text
producer accepted encoding
!=
consumer can recover intended semantic state
```

### (6) 次に検証すべきこと

`ConsumerRoundtripClosureBench-v0`:

- long key / Unicode / combining forms / very long scalar / enum / timestamp / float / null / empty collection
- current writer→current reader
- new writer→old still-active reader
- old writer→new reader
- unknown fields保持 / loss
- parser successだがsemantic hashが変わるcase
- partial write / crash before rename / crash after rename
- config / plugin manifest / lineage metadata / relationship state snapshotで共通contract化できるか

pass条件:

1. accepted candidateがauthoritative consumerでdecode可能。
2. semantic fieldsが意図通り。
3. compatibility target未達ならcommit前にreject/quarantine。
4. write failureでold valid stateを破壊しない。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agentのself-modification研究は「何を変更するか」に寄りやすく、**serializerとconsumer parserの生態系差**はconfig management / data format / migration engineeringの問題に見える。しかし長寿命個体では、正しい自己変更が次回boot不能なbodyを作ること自体がcontinuity failureになる。

### (8) 重要度

**A** — canonical stateで同じbugが起きればrestart後に自分を読めなくなる。YAML固有修正ではなく、durable mutation completion条件としてbench化する価値が高い。

- Huang et al., *Gray Failure: The Achilles' Heel of Cloud-Scale Systems*, HotOS 2017  
  https://www.microsoft.com/en-us/research/publication/gray-failure-achilles-heel-cloud-scale-systems/

### (1) 何が実証済みか

OpenClaw #156789では、synthetic transcript検索中にnative macOS appが約100% CPUでunresponsiveになり、accessibility readと`openclaw-mac status`がtimeout、SIGTERMでも終了せずSIGKILLが必要になった。一方、remote Gatewayは全6 synthetic messagesを保持し、conversation dataは失われていなかった。

ただしこれは**1 verified hang**で、deterministic reproductionや単一root causeは確立していない。sampleはSwiftUI/AttributeGraph main-thread hot pathを示すが、inline-math parserが原因だとは証明していない。

HotOS 2017のGray Failure研究は、system内部observerがhealthyと判断している一方で少なくとも1つのapplication/user pathがunhealthyと観測する状態を**differential observability**として整理した。fail-stopではないため、自動reactorが発火しないまま利用者だけが被害を受け得る。

### (2) 何が提案・推測段階か

- #156789をGray Failureの厳密な実例と断定はしない。GatewayとUIは別componentであり、単なるUI hangでも説明できる。
- Kamimusuhiのhealth subsystemが同様にfalse-healthyになる証拠はまだない。
- 1 surfaceの失敗を個体全体のfailureへ即昇格させると、逆に過剰failoverやsplit-brainを招く。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- distributed embodiment
- K-Edge / K-Core / surface health
- Resource Registry / routing
- degraded-mode operation
- observability / telemetry
- speech/audio/vision surface liveness
- human-facing availability
- failover / replacement-route serviceability

### (4) 借りられる設計・実装アイデア

healthを1bitのcomponent propertyではなく、**observer-qualified evidence**として持つ。

```text
HealthObservation {
  target_resource,
  observer_id,
  path_id,
  operation_class,
  observed_at,
  latency,
  error_class,
  success_ratio,
  generation,
  evidence_ref
}

HealthAssessment {
  target_resource,
  dimensions: {
    control_plane,
    data_plane,
    user_surface,
    cognitive_operation,
    persistence,
    actuation
  },
  disagreement_state,
  confidence
}
```

`/healthz`が200でも、実tool call / memory read / TTS / UI delivery / sensor pathが失敗するならgray-degradedとみなす余地を持つ。逆にsurfaceだけwedgedでcanonical coreがhealthyなら、個体全停止ではなくsurface isolation/restartへ落とす。

### (5) Kamimusuhiとの差分

既出のresource health、tri-state capability evidence、observer back-actionはそれぞれ重要だが、今回の差分は **「誰から見たhealthか」が一致しないこと自体をsignalにする**こと。

```text
internal monitor healthy
AND
consumer path unhealthy
=> gray state, not simply HEALTHY
```

Behavioral Reality/Source Monitoringはmemory provenanceのbehavioral attributionであり、本件はruntime health observer間のdisagreementなので別。

### (6) 次に検証すべきこと

`GrayOrganFailureBench-v0`:

- health endpointは正常だが、特定RPCだけtimeout。
- K-Coreから成功、K-Edgeからpacket loss。
- text generation成功、stream deliveryだけstall。
- DB read成功、large-history readだけevent-loop stall。
- camera process alive、frames stale。
- TTS process alive、audio device detached。
- UI surface hang、Gateway/canonical core healthy。

測定:

- false-healthy time
- consumer-observer disagreement duration
- failover/isolation latency
- unnecessary whole-body restart率
- split-brain発生有無

### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常のagent observabilityはtrace/log/metricsを集めること自体に注目しやすい。Gray Failureは「monitorが存在しているのに、**monitorの観測世界と利用者の観測世界が違う**」という分散systems/reliability engineeringの問題で、AI agent分類からは外れやすい。

### (8) 重要度

**B** — 概念は非常に重要だが、今回のfresh implementation evidenceは1 verified hangでroot cause未確定。まずwatch + fault-injection benchに留め、複数organで実再現したらA昇格を検討。

# 5. 既存findingへのfresh update（独立再提案しない）

## 5.1 Recoverable closeはbackground effectorsをreapしてはいけない

- Hermes PR #120648  
  https://github.com/NousResearch/hermes-agent/pull/120648

`AIAgent.close()`がsession layer上はrecoverableな`agent_close`でもtracked background processをSIGTERMし、観測事例ではbackground reviewとchild `hermes chat`が消え、completion notificationも届かなかった。修正はrecoverable/handed-forward closeならprocessを保持し、deliberate close/sessionless teardownだけkillする。

これは独立新規ではなく、既出 **Continuation-Equivalent Execution-State Reuse / Effector Lifetime Pinning / Recovery Artifact Lifetime** の強いfixtureに追加する。

追加すべきassertion:

```text
semantic session continuity preserved
=> live background obligations/effectors are not destroyed by wrapper close
```

ただし`/quit`, `/new`等のdeliberate boundaryでprocessを残すかは別policy。

## 5.2 Outbound policyは全egress pathをcomplete-mediateする

- Hermes PR #120663  
  https://github.com/NousResearch/hermes-agent/pull/120663

Signalのadapter経由sendだけでなく、typing / stop-typing / file / multi-image / reactionと、adapterを迂回していたstandalone `hermes send` / cron pathまで共通egress helperへ集約する提案。これは既出 **All-Entrypoint Effect Admission / Policy Interposition Coverage Attestation** のfresh evidence。

新規原則にはせず、entrypoint inventory testへ

```text
send / typing / reaction / media / cron / standalone
```

を加える候補とする。

## 5.3 Stored-history readをinteractive control-plane threadへ置かない

- OpenClaw PR #156772  
  https://github.com/openclaw/openclaw/pull/156772

stored-message lookup/countのSQLite workをGateway main threadからhistory workerへ移し、8MiB fixtureでmax observed event-loop gapを14.7ms→8.8msへ減らしたと報告。request medianは8.9→17.8msへ増えており、throughput/latency tradeoffも明示されている。

これは既出 **Observer Back-Action / mixed-criticality cognition / event-loop stall attribution** のupdateとして、`large-history read` fixtureを追加するに留める。

## 5.4 Security propertyをdependency defaultへ暗黙委譲しない

- OpenHands PR #17655  
  https://github.com/OpenHands/OpenHands/pull/17655

Electron renderer sandboxがdefault依存だったため` sandbox: true`を明示し、security propertyをartifactへ固定する提案。runtime確認はheadless環境のため未実施で、unit/static verificationのみ。

これは独立findingにはせず、既出 **Operational-Mode Coverage / Activation Artifact Closure / software-body versioning** のwatch fixtureとして、security-critical defaultをmanifest/attestationへ明示する候補とする。

### `docs/persistent-agent-implementation-pitfalls.md`

追記候補:

1. **Echoed identifiers are not possession proof**  
   - client自身が送ったsession/lease IDのechoはauthenticationにならない。
   - secret itselfをrequestへ送ってから照合しない。
2. **A valid write must survive authoritative reparse**  
   - serializer成功だけでcommit完了にしない。
   - boot時consumer/schemaでroundtripする。
3. **Duplicate read ownership belongs to the logical resource owner**  
   - generic worker poolは同一logical requestか判定できない。
   - join後のrevalidationが必要。

### `docs/technology-watchlist.md`

即時追記までは不要だが、次回reviewで以下をwatch候補にできる。

- proof-of-possession / sender-constrained token patterns (DPoP, mTLS, enclave-backed device keys)
- keyed single-flight + priority-aware cancellation for cognition/memory hydration
- gray-failure / differential-observability fault injection for distributed embodiment

### `architecture.md` / `spec.md`

採用判断後の候補のみ:

- attach/handoff authorityをidentifier equalityではなくcurrent possession witnessで検証するSHOULD/MUST。
- durable state mutationのcompletionにauthoritative-consumer decode/schema checkを含める。

# 12. 今回の結論

今回の4候補は共通して、**見えているidentifier/state/health/resultを、そのまま実在するauthorityやcurrent truthへ昇格させない**問題だった。

特に重要なのは次の4式。

```text
echoed identifier
!= proof that the responder holds continuity authority

same logical read requested twice
!= two physical reads are necessary

write succeeded
!= the next authoritative consumer can still reconstruct the state

one observer says healthy
!= every cognitive/surface path is healthy
```

Kamimusuhiの直近実装へ落とすなら、まず `ContinuityAttachPossessionBench-v0` と `ConsumerRoundtripClosureBench-v0` はLLMなしで小さく閉じられる。次に`SingleFlightCognitiveReadBench-v0`をbackground cognition増設前のlatency/resource baselineへ入れ、`GrayOrganFailureBench-v0`をdistributed embodiment fault injectionへ追加するのがよい。
