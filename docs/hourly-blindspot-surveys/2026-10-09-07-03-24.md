## 3. 候補別評価

### 3.1 A — Route-decision metadata leaks private cognitive topics

**一次資料:** Teng-Ruei Chen, *Sensitive-Topic Leakage Through LLM Routing Metadata: Measurement and Mitigation*, arXiv:2610.09981。2026-10-08 regular announcement（v1 submissionは2026-10-07 12:47 UTC）。
https://arxiv.org/abs/2610.09981

1. **実証済み:** 著者は実リクエスト約**170万件**（WildChat-1M / LMSYS-Chat-1M）を用い、2種類のcost/quality routerとdomain router、11システムのloggingを調査。本文を記録しなくてもモデル選択比率などのroute metadataが内容の機微分類と統計的に関連する。RouteLLMの20回の決定から医療相談頻度の高い利用者を識別する評価は **AUC 0.71**（探索的）で、事前登録した主エンドポイント **0.75は未達**。domain router の **0.92は上界的な探索結果**。カテゴリごとのlength-matched parityの後処理でgapを減らす検証も示す。
2. **提案・推測:** 一般的なKamimusuhiのルータが同じ leakage を持つかは未検証。集計秘匿、sticky route、privacy-aware decision等は品質・費用・可観測性とトレードオフ。AUC 0.71を「既に実害を確定」と表現しない。
3. **関連:** Cognitive Action Router、Resource Registry、Embodiment State、外部model delegation、privacy-preserving memory、relationship/self data、observability telemetry。
4. **借りる案:** inference bodyが保存されなくても `model_choice`, `route_reason`, `fallback`, `tool_category`, `timing` 等を機微な派生情報として分類する `RoutingDecisionDisclosurePolicy`。raw per-user route traceの公開・高粒度保持を抑制し、必要なら個体内ローカル集計へ切り替える。
5. **Kamimusuhiとの差分:** 従来はexternal modelへ渡すpayload自体のprivacyとtrajectory-level unnecessary accessが重点。今回の差分は **payloadなしのルーティングログ自体がprivate mental/relationship stateの代理指標になる**という測定。
6. **次の検証:** `CognitiveRouteMetadataLeakageBench-v0`（P1）。同じtoken長/費用帯でsensitive topicを差し替え、route/logから属性を推測する攻撃のAUC、utility、費用、監査可能性を比較。未ログ・aggregated・category-parity・session-stickinessをablation。
7. **通常dailyで拾いにくい理由:** orchestrationはコスト最適化、privacyはprompt/logの直接漏えいを見がち。*モデル選択の観測可能性*はside-channel securityであり両者の境界。
8. **重要度:** **A（独立）**。サーベイ対象のprivacy/socialityとCognitive Budget双方に接続。

### 3.2 A update — Consolidation completion must retire only snapshot-covered writes

**一次資料:** Microsoft Agent Framework #9218, *Automatic memory consolidation clears sessions still extracting memories*。issue created **2026-10-09 01:38:55 JST**。
https://github.com/microsoft/agent-framework/issues/9218

1. **実証済み:** `MemoryContextProvider` のdeterministic offline reproduction。あるconsolidationが古いtopicのsnapshotを処理中に、別sessionが新しいmemoryを抽出すると、consolidation終了時のsession maintenance markerの掃除がその未収載の新抽出も「処理済み」にしてしまう。serialでは後続consolidationに `Old` と `New` が入り、interleavedでは `Old` しか入らない。**新しいmemory fact自体は保存済みで、消失していない**。問題は処理/整理のcadence。
2. **提案・推測:** 恒久修正未実装。同一sessionの重複run、multi-process・partial failuresには別検証が要る。「model request中ずっと排他ロック」は既存concurrency目的を壊す可能性。
3. **関連:** Sleep/Dream consolidation、Memory Extraction、semantic/episodic promotion、background cognition、snapshot/epoch bookkeeping。
4. **借りる案:** `ConsolidationPass{snapshot_seq, covered_event_set, topic_versions, completion_epoch}` を記録し、clear/retireできるのは **そのpassが実際に観測・処理したwriteの集合のみ**。遅れて完了した抽出はpendingに残す。処理対象のevent-idとsession-idを混同しない。
5. **差分:** 既存のconsolidation freshness、WAL generation fencing、mutation policyと近接するが、**正しいfactが残ったままbackground housekeepingだけが進行を誤ってcreditする**という新しいfailure。user-visible correctnessだけで検知できない。
6. **次の検証:** `SnapshotCoveredConsolidationRetirementBench-v0`（P0/P1）。A consolidation snapshot→B extraction start→A finish→B finish、同一session再run、別owner、partial retryを組合せ、未収載writeのpending保持、event coverage、consolidation latency、重複学習量を計測。
7. **拾いにくい理由:** database snapshot semantics / background-job bookkeeping / cognitive memory consolidation の三領域。memory QAが成功するので生成評価では見えない。
8. **重要度:** **A update**。

### 3.3 B — Silence is an event: event-triggered + time-triggered runtime verification

**一次資料:** Kekatos et al., *Hybrid Hierarchical Runtime Verification for Edge-IoT Security: Combining MonPoly and RTLola*, arXiv:2610.09825。2026-10-08 regular announcement。
https://arxiv.org/abs/2610.09825

1. **実証済み:** edge→gateway→cloudの3層runtime verificationを、**15 actor Docker testbed**、8 attack profiles とsilent-bypass scenarioで評価。MonPolyはcross-device temporal correlation、RTLolaはeventが止まっても一定時間後にfailureを検出するtime-triggered predicateを担当。controlled testbedではsilent-bypassをevent-only tierが見逃し、time-triggered tierが検知。edge/gatewayのper-event処理はmicrosecond級と報告。
2. **提案・推測:** これはIoT-security testbedでありKamimusuhiの意識/生理機構の証明ではない。実世界のnetwork partitionや任意のsensor omission下で同じ検知率になるとは限らない。
3. **関連:** K-Nerve、Edge sensory organs、Embodiment State、homeostasis、fault tolerance、degraded-mode、runtime assurance。
4. **借りる案:** `EventMonitor`とは別に `AbsenceMonitor` を持ち、`expected_heartbeat_interval / max_silence / source_generation / deadline / risk_level`を監視。**何も到着しないこと自体**を時間ベースのstate transitionとして発火させる。故障と正常な休止はleaseやscheduler状態で区別する。
5. **差分:** stale sensor/organ healthは既知だが、event-streamだけの監視では「攻撃・障害でstreamが丸ごと止まる」時にpredicate評価すら走らない点をformal RVの設計として補強。
6. **次の検証:** `SilenceAwareCognitiveOrganMonitorBench-v0`（P1）。active nodeの無音化、network partition、planned sleep、sensor maintenance、compromised node、delayed heartbeatをinjectし、detection bound、false alarms、CPU/energy、低遅延K-Nerveへの干渉を測る。
7. **拾いにくい理由:** runtime assuranceはevent trace、OS monitoringはwatchdog、認知アーキテクチャはsalience inputを扱うため、**無入力を認知入力として扱う義務**が見落とされやすい。
8. **重要度:** **B（独立）**。

### 3.4 B update — Transport reconnect cannot silently inherit protocol initialization

**一次資料:** OpenClaw #167371, *MCP SSE transport silently switches to an uninitialized server session after auto-reconnect*。created **2026-10-09 03:04:08 JST**。
https://github.com/openclaw/openclaw/issues/167371

1. **実証済み:** SSE stream自動reconnectで新しい`session_id`/endpointが配布されるのに、clientの`initialize`済みstateが引き継がれ、後続`tools/call`が `202 Accepted` の後 `-32602: request before initialization` で失敗し続ける。reportはshipped bundle sourceとserver logsを突き合わせ、消耗したruntimeが破棄されるまで長時間tool lossを観測。ただしGET→session ID対応は時間相関からの推定と明記されている。
2. **提案・推測:** 修正は「endpoint世代変更時再handshake」か「transportを閉じruntime再生成」など。すべてのMCP transportに同じ挙動とは限らない。
3. **関連:** MCP/Tool organs、distributed embodiment、capability health、protocol lifecycle、K-Core delegation。
4. **借りる案:** `TransportGeneration` と `ProtocolSessionGeneration` を分離し、`initialized_for_session_id`を証明できない場合はtool admissionしない。HTTP 202をtool successと扱わずRPCのprotocol outcomeを確認する。
5. **差分:** 既出のconnection-generation **authorization freshness** に加え、今回は **authorizationが一致してもprotocol initialization stateが別sessionに属すれば機能しない**という新しいliveness/handshake dimension。
6. **次の検証:** `MCPReconnectInitializationParityBench-v0`（P1）。SSE/streamable HTTP、server restart、transparent reconnect、endpoint rotation、旧/新session ID、202+RPC-errorを交差し、bounded recoveryとsession-bound handshake parityを検証。
7. **拾いにくい理由:** transportはTCP/SSE再接続、authはcredential、MCPはinitialize handshakeとして別管理される。**再接続成功 != protocol session initialized**が境界。
8. **重要度:** **B update**。

### 3.5 B update — Live heartbeat does not imply monotone progress delivery

**一次資料:** Hermes #135295, *background-process heartbeats are delivered out of emission order*。created **2026-10-09 05:27:12 JST**。
https://github.com/NousResearch/hermes-agent/issues/135295

1. **実証済み:** 1つのbackground processから順に生成された8 heartbeatsがsessionに `[3,6,5,7,8,2,1,4]` の順で到着。seq#1と#4はseq#8より約15分遅い。重複・lossなし、単純なstale-liveness checkでは通る。**root causeは未確認**で、複数drainerのrequeueは候補にとどまる。
2. **提案・推測:** source-level raceの確定には追加interleaving reproductionが必要。completion eventとprogress heartbeatはdrop許容度が異なる。
3. **関連:** background cognition、K-Deep task supervision、observability、Expected Continuation、progress state。
4. **借りる案:** `ProgressEnvelope{task_id, process_generation, emission_seq, emitted_at, observed_at}`。同一sourceのprogressはhighest-accepted-seqを超える場合のみ状態へ適用。late heartbeatはarchive/metricsへ送るが現行stateへ巻き戻さない。completion/effect receiptは捨てず別のdurable semantics。
5. **差分:** replay order・timestamp vs presentation orderは既知。fresh差分は、**liveなprogress通知がすべて届いていても、modelのprogress worldviewを逆行させ得る**実測例。
6. **次の検証:** `MonotoneProgressProjectionBench-v0`（P1）。two drainers、busy/idle、requeue、process restart、out-of-order seq、duplicate、late completionを交差し、progress regressions、incorrect replanning、turn/compute浪費を測る。
7. **拾いにくい理由:** distributed queuesはdelivery、agent evaluationはtask completion、observabilityはlivenessを測る。**stateful progress projection**を別契約としないとordering故障が埋もれる。
8. **重要度:** **B update**。

### 3.6 B update — User delivery policy must mediate synthetic internal events

**一次資料:** Hermes #135327, *let pre_gateway_dispatch see internal events and defer them*。created **2026-10-09 06:46:28 JST**。
https://github.com/NousResearch/hermes-agent/issues/135327

1. **実証済み:** issueの現行実装分析では、`pre_gateway_dispatch` が外部inboundだけに適用され、kanban完了等の`admit_internal_event`起因wakeが通らない。quiet hours実装者はadapter monkeypatchで回避しているという一次実装記録。**正式なdefer APIは未実装の提案**。
2. **提案・推測:** 全internal eventを抑止してよいわけではない。safety escalation、明示のinterrupt、高優先度operator alertは別policyが要る。再開期限切れ時の扱いも設計未確定。
3. **関連:** proactive cognition、sociality、notification governance、operator consent、background work、sleep/wake behavior。
4. **借りる案:** ingress sourceがhuman/automated/agent-internalでも、外部に出すnotificationには同じ`DeliveryPolicy`を再適用。提案された`defer(until, reason)`をdurable custody stateとして扱い、defer receiptとend-user delivery receiptを混同しない。
5. **差分:** 既知の「機械生成通知はhuman intentではない」とは別方向。今回は **内部処理で正当に生成された通知も、外部へ出す時はユーザーのquiet hours等に従う**というsocial-boundary。
6. **次の検証:** `SyntheticWakeDeliveryPolicyBench-v0`（P1/P2）。scheduled report、internal task completion、human inbound、emergency alert、quiet hours、restart、defer/releaseで通知頻度、drop、重複、false wake、deadlineの遵守を測る。
7. **拾いにくい理由:** event busはwakeをdelivery、HCIはquiet hours、task systemはcompletionを扱う。内部生成イベントがUI/人間へ到達する境界のガバナンスが抜ける。
8. **重要度:** **B update**。

## 6. 既存docsへの追記候補（採用前レビュー）

**`architecture.md`**
- Cognitive Action Router telemetryをprivate derived signalとして扱う。
- `ConsolidationPass`はsnapshot-covered event IDsを持ち、完了で未カバーwriteを処理済みにしない。
- K-Nerve/organ healthへevent-driven + deadline-driven absence detectionを分離導入。
- `ProtocolSessionGeneration`をconnection/credential generationと分離。
- Background Task Progressをper-source monotone projectionとして扱い、completionと別にする。
- internal wakeとhuman-visible deliveryのpolicy boundariesを明記する。

**`spec.md`候補（未採用）**
1. Private routing decisions SHOULD be protected from per-user topic inference through logs and external telemetry, even if prompt contents are not logged.
2. Memory consolidation MUST NOT retire extraction writes that were not included in the consolidation pass's captured coverage.
3. Safety-critical organ monitoring SHOULD evaluate required *absence-of-event* predicates on time triggers independent of event arrival.
4. A reconnected transport MUST NOT use a new protocol session for tool execution before that session's required initialization succeeds.
5. Model-visible progress SHOULD NOT regress merely because live notifications were delivered out of emission order.
6. Synthetic/internal notifications SHOULD respect operator delivery preferences at the human-facing boundary, subject to explicit emergency exceptions.

## 10. 今回の結論

**「観測可能なもの」「処理済みと数えるもの」「到着しなかったもの」「今つながっているもの」「順序」「通知の出し時刻」を、個体の真実と直接同一視しない。**

- route metadataは本文なしでも機微情報を漏らしうる。
- consolidation成功は開始後の全抽出を統合した証拠ではない。
- 無入力も故障信号になりうる。
- reconnectはhandshake完了と同義ではない。
- 生きたheartbeatも進行順とは限らない。
- 内部処理の完了は夜中のユーザー通知を自動正当化しない。

いずれも**Kamimusuhi未実装・未採用の研究候補**として扱い、provenanceと実験合否を残す。
