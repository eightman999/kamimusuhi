## 1. A — Order-Bearing Configuration Must Not Be Canonicalized as an Unordered Map

Primary:
- https://github.com/openclaw/openclaw/issues/165055

### (1) 何が実証済みか

OpenClaw 2026.9.8のmacOS appが `openclaw.json` のobject keyをalphabetical orderへ並べ替えて保存した結果、`agents.entries` の先頭agentが変わり、Gatewayの実挙動も変わったproduction reportがある。報告環境ではexplicit ownership下で先頭agentのworkspaceが変わり、automatic iMessage replyが失敗した。値集合は同一でも、serialization上のkey orderがruntime selection semanticsを持っていた。

### (2) 何が提案・推測段階か

JSON object orderへ依存する設計自体を全面禁止すべき、という結論までは未確定。既存互換性のため順序保存が必要なsystemもある。ただし、順序が意味を持つならschema上で明示する方が安全。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Software Body configuration
- organ/resource registry
- K-Edge / K-Core / K-Deep routing
- default/fallback selection
- migration / normalization / backup
- reproducibility

### (4) 借りられる設計・実装アイデア

順序に意味があるconfigurationはunordered mapではなく、明示的なlistまたは`priority`を使う。

```text
ordered_agents:
  - id: main
    priority: 0
  - id: research
    priority: 10
```

さらにconfig rewrite / formatter / migrationへsemantic round-trip testを入れ、`parse -> rewrite -> parse`後のeffective resolver outputが不変であることを確認する。

### (5) Kamimusuhiとの差分

既出のConfig Normalization Semantic Equivalenceはmigration前後のdefault principal/route変化を扱った。本件はさらに下層で、**syntax normalizationそのものがimplicit ordering semanticsを壊す**。値やschemaが変わっていなくてもbehaviorが変わる。

### (6) 次に検証すべきこと

**`OrderSemanticConfigRoundTripBench-v0` — P0**

- JSON/YAML/TOML
- key sort / pretty-print / parse-reserialize
- map→map migration
- explicit list / explicit priority
- duplicate priority / missing priority

を交差し、effective routing/default ownerが無意識に変わらないことを確認する。

### (7) 既存dailyではなぜ拾いにくいか

serializationは通常「表現の違い」、orchestrationは「runtime policy」として別々に扱われる。**表現上の順序が実行意味を持つ**境界は、config tooling・language semantics・agent ownershipの隙間に落ちやすい。

### (8) 重要度

## 2. A update — Semantic Ordering Must Survive Debounce / Partition Keys

Primary:
- https://github.com/openclaw/openclaw/issues/165067

### (1) 何が実証済みか

同一channel内でSender Aのmessageがdebouncer/preflight中にlaneをreleaseし、Sender Bが別debounce keyを持つ場合、BがAより先にreply admissionへ到達できる構造的reorderingがOpenClawで報告された。A/Bは同じchannelに属し、Aが先に到着しているが、partition keyの違いがadmission順序を変える。

### (2) 何が提案・推測段階か

すべてのmulti-sender channelでglobal FIFOが正しいとは限らない。独立thread/topic間では並列化できる。必要なのは、**どのsemantic ordering domainで順序を保存するか**を明示すること。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Event Bus / ingress
- multi-surface sociality
- turn-taking
- relationship context
- debounce/coalescing
- K-Nerve / K-Edge pre-processing

### (4) 借りられる設計・実装アイデア

`debounce_key` と `ordering_domain` を分離する。

```text
event_id
arrival_seq
ordering_domain
coalescing_key
admitted_seq
```

batch optimizationはordering authorityを持たず、同一ordering domainでは「earlier batch admitted downstream」等のexplicit handoff witnessを使って後続admissionをfenceする。

### (5) Kamimusuhiとの差分

2026-09-18のFair Turn Admissionはwaiter starvation / FIFO handoffを扱った。本件のfresh差分は、**公平性問題がなくても、optimization partitionがcausal/social orderを再定義してしまう**点。

### (6) 次に検証すべきこと

**`SemanticOrderDomainPartitionBench-v1` — P0/P1**

- same sender / different sender
- same channel / different topic
- different debounce keys
- defer / release / reconnect
- coalescingあり/なし

を交差し、指定したordering domain内のcausal order conservationを測る。

### (7) 既存dailyではなぜ拾いにくいか

queue fairness、UI debouncing、stream processing、conversation turn-takingが別分野として扱われるため、**partition keyとsocial orderの不一致**が見落とされやすい。

### (8) 重要度

**A update**

## 3. A update — Synthetic Control Frames Need Typed Out-of-Band Provenance Across Replay

Primary:
- https://github.com/NousResearch/hermes-agent/issues/132934
- https://github.com/NousResearch/hermes-agent/issues/132949

### (1) 何が実証済みか

Hermes #132934ではcontext-compaction handoffがmodelによってparaphraseされ、byte-exact prefix classifierを回避してordinary assistant replyとして公開された。#132949では、過去のinterrupt時にhidden assistant rowの`api_content`へ入れられた`[response interrupted]` placeholderが後のreplayでmodel-visible assistant textへ変換され、何turnも後にmodel自身がそれだけを正常replyとして生成した。後者では`finish_reason=stop`、6 output tokens、reply length 22がplaceholderと一致する実ログがある。

### (2) 何が提案・推測段階か

すべてのcontrol textをprovider wireから完全排除できるとは限らない。role alternation等のためwire-only scaffoldingが必要なproviderはあり得る。しかし、そのscaffoldをcanonical social utteranceと同じ型で保存・再注入すべきではない。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Canonical Evidence / transcript
- context compaction
- replay / recovery
- synthetic memory / system context
- social utterance boundary
- generated-cognition recirculation

### (4) 借りられる設計・実装アイデア

control artifactsをtext prefixから推定せず、typed provenanceを保持する。

```text
semantic_role =
  USER_UTTERANCE
  ASSISTANT_UTTERANCE
  CONTROL_FRAME
  COMPACTION_HANDOFF
  WIRE_SCAFFOLD
  INTERRUPT_PLACEHOLDER
```

provider projectionで必要な場合も、canonical rowへassistant utteranceとして昇格させず、projection終了後にsemantic roleを復元する。text classifierは防御の補助に留める。

### (5) Kamimusuhiとの差分

### (6) 次に検証すべきこと

**`SyntheticControlFrameQuarantineBench-v2` — P0**

- compaction
- interrupt / redirect
- provider role-repair
- hidden/display-only row
- restart後 replay

を組み合わせ、control artifactがassistant utterance / autobiographical memoryへpromotionされないことを確認する。

### (7) 既存dailyではなぜ拾いにくいか

memory surveyはsummary fidelity、provider integrationはwire compatibility、social cognitionはutterance roleを見る。**wire scaffold→replay→model imitation→社会的発話**という多段自己汚染は単一分類では追いにくい。

## 4. B — Security Evidence Must Be Operation-Scoped, Not Sampled from Shared Transient State

Primary:
- https://github.com/NousResearch/hermes-agent/issues/132905

### (1) 何が実証済みか

HermesのmacOS Bedrock経路で、shared `SSLContext`を複数threadが同時利用すると`InsecureRequestWarning`が断続的に出るreproductionが報告された。報告ではsequential shared contextは0/10、concurrent per-thread contextは0/24、concurrent shared contextでは6/24 warnings。expired/self-signed証明書は同stackで拒否されており、実接続の検証失敗ではなく、truststoreがhandshake中にshared contextの`verify_mode`を一時的に変えるwindowを別threadが観測した可能性が示されている。

### (2) 何が提案・推測段階か

root causeはissue reporterのsource-level analysisであり、upstream truststore側での確定診断ではない。また「warningを抑制する」だけでは安全ではない。重要なのはsecurity verdictが正しいoperation instanceへbindされること。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- provider transport
- secure channel / zero trust
- observability
- self-diagnosis
- execution evidence
- distributed embodiment health

### (4) 借りられる設計・実装アイデア

security postureをshared mutable objectの瞬間snapshotから推定せず、**operation-scoped receipt**として記録する。

```text
TransportSecurityReceipt
  connection_id
  handshake_id
  peer_identity
  verification_result
  verifier
  policy_epoch
  completed_at
```

global/shared context stateはconfiguration evidenceに留め、個別connectionのsecurity verdictとは分離する。

### (5) Kamimusuhiとの差分

既出のPerspective-Qualified Gray Healthやstable semantic telemetryは観測の視点/型を扱った。本件は、**同じshared objectの一時的内部状態を別operationのsecurity truthとして読んではいけない**というconcurrency-specific差分。

### (6) 次に検証すべきこと

**`ConcurrentSecurityEvidenceIsolationBench-v0` — P1**

- shared/per-connection TLS context
- concurrent handshake
- policy reload
- verifier failure
- real bad certificate
- diagnostic sampler

を交差し、false insecure / false secureの両方を測る。

### (7) 既存dailyではなぜ拾いにくいか

TLS/security surveyは最終verification結果、concurrency surveyはrace safety、observability surveyはmetric correctnessを見る。**security evidence生成そのもののlinearizability**は境界領域。

### (8) 重要度

**B**

## 5. B — Downstream Authorization Hops Need Explicit Resource-Bound Token Semantics

Fresh standards discussion:
- https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3413

Normative specification:
- https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations

### (1) 何が実証済みか

MCP 2026-07-28 authorization security considerationsは、MCP serverがclientから受け取ったtokenをそのままupstream APIへpass throughしてはならず、MCP server自身をintended recipientとして検証することを要求している。2026-10-04作成のspec issue #3413では、同一authorization server / 同一project内のthin MCP adapterが同じuser tokenを自projectのData APIへ渡すvendor patternと、この規定の関係が不明確だと指摘されている。issueはclarification requestであり、規範解釈は未解決。

### (2) 何が提案・推測段階か

same-AS / same-protected-resource domainならreuse可能か、常にseparate downstream grant / token exchangeが必要かはspec maintainerによる解決待ち。Kamimusuhi側で独自に「same projectだから安全」と緩和すべきではない。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- capability security
- MCP / tool adapters
- delegation
- principal propagation
- external memory/data APIs
- privacy-preserving memory

### (4) 借りられる設計・実装アイデア

inbound grantとdownstream credentialを別artifactとして表現する。

```text
InboundGrant
  principal
  audience/resource
  scopes
  issuer
  grant_epoch

DownstreamGrant
  target_resource
  derived_from
  scopes
  exchange/consent evidence
```

specがclarifyされるまで、resource boundaryを跨ぐtoken reuseはexplicit exceptionとして監査し、implicit passthroughにしない。

### (5) Kamimusuhiとの差分

既出のrequest-scoped authorityやdelegation context separationは「誰の権限か」を扱う。本件は**同じprincipalのtokenでも、どのresourceへ向けて発行されたかというaudience/resource boundary**を別軸として保持する点。

### (6) 次に検証すべきこと

**`DownstreamTokenAudienceSeparationBench-v0` — P1**

- MCP server intended token
- separate downstream API token
- token exchange
- same AS / different resource
- missing/ignored RFC8707 `resource`
- over-broad audience
- cached downstream grant

を交差し、confused-deputy / token-forwardingを検出する。

### (7) 既存dailyではなぜ拾いにくいか

authorization surveyはprincipal/scopeを中心に見がちで、MCP adapterはtool transportとして扱われる。**principal continuityとresource-audience continuityは別問題**。

### (8) 重要度

**B**

## 結論

今回の中心は **「意味のある軸を、便利なrepresentation / optimization / shared implementation stateへ暗黙に押し込まない」**こと。

- map key orderが意味を持つなら、それは単なるserialization detailではない。
- debounce keyはordering authorityではない。
- control frameはtext prefixではなくsemantic roleを持つ。
- shared TLS objectの一瞬の状態は、別connectionのsecurity truthではない。
- 同じprincipalのtokenでも、target resourceが違えば同じauthority artifactとは限らない。

Kamimusuhiでは、**order / role / resource audience / operation-scoped evidence**をfirst-class metadataとして表現し、representation layerから推測しない方が長寿命個体のcontinuity・safety・observabilityを強くできる。
