## A — Artifact Availability Horizon Closure
Primary: Hermes #122240 — https://github.com/NousResearch/hermes-agent/issues/122240

1. **実証済み**: lockされたffmpeg daily autobuildがupstream retention後に404となり、fallback mirrorも使えずinstall/updateが停止した。artifact identityが正しくても将来availabilityは保証されない。
2. **提案・推測**: boot/restore critical artifactにはmirror、escrow、rebuild recipe、十分なretention SLAの少なくとも1つが必要。
3. **関係**: software body、self-maintenance、migration/rebirth、restore、degraded-mode。
4. **借りる案**: dependency recordへ digest / mirrors / retention / availability_checked_at / rebuild_recipe / recovery_critical を追加し、`availability_horizon >= recovery_horizon`を検査。
5. **差分**: Kamimusuhiはprovenance/version/integrityには強いが、正常なupstream retentionによる将来取得不能は独立contractになっていない。
6. **次に検証**: `ArtifactAvailabilityHorizonBench-v0`。upstream prune、cache/mirror/rebuild有無、cold restoreをfault injection。
7. **dailyで拾いにくい理由**: supply-chain調査は署名・悪性dependencyへ寄り、善意のretention expiryは見落とされやすい。
8. **重要度**: **A**。

## A — Consent-Qualified Replication Scope
Primary: Hermes #122151 — https://github.com/NousResearch/hermes-agent/issues/122151

1. **実証済み**: local + shared remote gatewayへ接続したDesktopで、local bot group chatのroom名・members・recent messagesがreachable gatewayへ同期され、shared gateway側の別Desktopにも見えたとのrepro。per-room sharing choiceがない。
2. **提案・推測**: `reachable(surface)` と `replication_authorized(object,surface,audience)` を分離する。
3. **関係**: distributed embodiment、relationship memory、social transcript、lifelog、memory ownership/consent。
4. **借りる案**: objectごとに owner / allowed_surfaces / allowed_audiences / purpose / revocation_epoch を持つReplicationScope。新surfaceはdefaultでreplication grant無し。
5. **差分**: same individualのorganであることとsame privacy domainであることは同義ではない。
6. **次に検証**: `ReplicationConsentScopeBench-v0`。private episodic/relationship/social transcriptを複数surfaceでgrant/revoke/resync。
7. **dailyで拾いにくい理由**: distributed systemsは「複製できること」を追いやすく、「複製しないこと」をcontinuity/trust要件として扱いにくい。
8. **重要度**: **A**。

## A update — Last-Surviving-Copy Recovery Barrier
Primary: Hermes #122210 / #122209  
https://github.com/NousResearch/hermes-agent/issues/122210  
https://github.com/NousResearch/hermes-agent/issues/122209

1. **実証済み**: #122210ではrollback stagingからmetadataを戻すmoveが失敗してもstaging cleanupが進み、唯一のcopyが消え得た。#122209ではSQLite restore pathのURI解釈で別/空DBを開き、成功風restoreがlive DBを壊し得た。
2. **提案・推測**: cleanupは別のrecoverable copyが存在し到達可能と確認できるまで許可しない。
3. **関係**: continuity recovery、backup/restore、skills、canonical memory、software update。
4. **借りる案**: failed stagingをtemporary continuity authorityとして保持し、cleanup receiptにretained stagingとverificationを残す。
5. **差分**: 既出non-destructive degraded maintenanceをcopy custody proofまで具体化するupdate。
6. **次に検証**: `LastSurvivingCopyRecoveryBench-v0`。stage成功/unstage失敗、archive除外、特殊path、I/O fault。
7. **dailyで拾いにくい理由**: backup/restoreはsnapshot存在やcommand成否で見られ、staging cleanup semanticsは低レベルに埋もれる。
8. **重要度**: **A update**。

## A update — Online Budget Observability & Enforcement Closure
Primary: OpenHands #17691 — https://github.com/OpenHands/OpenHands/issues/17691  
Supporting: OpenClaw #157794 — https://github.com/openclaw/openclaw/issues/157794

1. **実証済み**: OpenHands V1の報告ではconversation running中はaccumulated_costが0のままで、終了時に初めて実コストが出る。settable per-conversation budgetもなく、外部watchdogはhard ceilingを実際にenforceできなかった。
2. **提案・推測**: Cognitive Budgetをhomeostatic controlにするならpost-hoc accountingだけでは不十分。
3. **関係**: Cognitive Budget、digital interoception、router、background cognition、cloud/local routing。
4. **借りる案**: spendを estimated / committed / settled に分離し、provider/tool dispatch前でenforce。pendingを0扱いしない。
5. **差分**: 既出principal-wide budgetへ timing contract を追加。**visible eventually != observable while controllable != enforceable at spender**。
6. **次に検証**: `OnlineBudgetClosureBench-v0`。settlement遅延、streaming、fanout、cache pricing、cancel race、unknown price。
7. **dailyで拾いにくい理由**: agent economicsは平均costへ寄り、signalが停止可能時間内に届くかはcontrol/runtime境界になる。
8. **重要度**: **A update**。

## B update — Embodiment-Qualified Resource References
Primary: Hermes #120730 — https://github.com/NousResearch/hermes-agent/issues/120730

1. **実証済み**: macOS clientのabsolute image pathをremote Linux backendへ送り、backend側でobjectを解決できなかった。same POSIX path形状なのでheuristicでは所在差を検出できない。
2. **提案・推測**: locatorだけでなく locator scope / owning surface / materialization mode を持つ。
3. **関係**: multimodal perception、K-Edge、multi-device embodiment、external files/tools。
4. **借りる案**: ResourceRefを object_id / locator / locator_scope / owning_surface / digest / transport(BY_REFERENCE|BY_VALUE) にする。
5. **差分**: 既出referential identity / materialization contractの具体fixture。
6. **次に検証**: `CrossEmbodimentResourceRefBench-v0`。macOS→Linux、Windows→Linux、container、shared CAS。
7. **dailyで拾いにくい理由**: multimodal surveyはmodel性能へ寄り、locatorのembodiment semanticsはRPC detailに見えやすい。
8. **重要度**: **B update**。

## B update — Capability-Flap / Resume-Identity Separation
Primary: OpenClaw #157823 — https://github.com/openclaw/openclaw/issues/157823

1. **実証済み**: configured MCP serverの一時start失敗でbundle config hashが変わりCLI sessionがreset、復帰時にも再度hashが変化する。
2. **提案・推測**: resume identityにはdurable definition / grant / semantic protocol versionだけを入れ、一時availabilityはruntime healthへ分離。
3. **関係**: tool orchestration、MCP、session continuity、degraded operation。
4. **借りる案**: `resume_identity_hash` と `runtime_capability_health` を別stateにする。
5. **差分**: 既出capability readinessのupdate。一時欠落をidentity mutationへ昇格させない。
6. **次に検証**: `CapabilityFlapContinuityBench-v0`。fail→recover、URL変更、grant変更を分ける。
7. **dailyで拾いにくい理由**: MCP調査はdiscovery/securityへ寄り、availabilityがresume hashへ混入する境界は見えにくい。
8. **重要度**: **B update**。
