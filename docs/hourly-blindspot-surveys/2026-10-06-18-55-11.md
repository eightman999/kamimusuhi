## 1. A update — World Models Need Applied-Action Attribution, Not Merely Issued-Action History

Primary: *Mind the Execution Gap: Action-Semantic Mismatch in World-Model Control*  
https://arxiv.org/abs/2610.06582

Submitted: **2026-10-05 15:59 UTC / 2026-10-06 00:59 JST**

### (1) 何が実証済みか

論文は、通信delay、packet loss、reordering、actuator bufferingによって、controllerが「出したcommand」とworldが実際に受けたactionのtimelineがずれる問題を、単なる外乱ではなく **action semantics mismatch** として評価した。

architectureごとにfailure modeが異なり、TD-MPC2型 planning controllerでは imagined future action sequence と actual execution sequence のずれ、DreamerV3型 recurrent world modelでは observed transition を「実際には適用されなかったcommand」に誤帰属するfailureをcontrolled interventionで示した。

対策として Future-Sequence と Applied-Action Feedback を導入し、pretrained world model本体を変更せず、delay / loss / reorder / measured network trace / process-separated stackで改善を確認している。

### (2) 何が提案・推測段階か

Kamimusuhiの言語tool、GUI、robotics、distributed actuatorで同じinterfaceがそのまま最適とは限らない。physical actuatorだけでなく、remote APIやbrowser operationでは「applied」の観測方法自体が異なる。

### (3) 関係

perception/action loop、Computational Embodiment、world/body model、K-Nerve/K-Edge、Effect Acceptance、actuator/tool receipt、causal self-history、MOVI等のphysical embodiment。

### (4) 借りる案

```text
IssuedAction
  action_id
  intended_command
  issued_at
        │
        ▼
AppliedActionReceipt
  action_id
  actually_applied_command
  applied_at
  actuator_generation
  execution_order
        │
        ▼
ObservedTransition
  caused_by_applied_action_id
  observation_window
```

planning / learning / causal self-historyは、可能な限り `IssuedAction` ではなく `AppliedActionReceipt` にtransitionを帰属する。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでに `REQUESTED → EXECUTING → SUCCEEDED/FAILED/UNKNOWN`、action receipt、own-action historyを持つ。fresh差分は、**receiptを監査・安全確認だけでなく、world modelのdynamics attributionそのものへ戻す必要がある**こと。「実行結果を後から記録する」だけでは、学習器がcommandを誤ったcauseとして学習する可能性が残る。

### (6) 次

**`AppliedActionCausalAttributionBench-v0` — P0/P1**

fixed delay / jitter、dropped action、reordered actions、actuator buffer、command replacement/coalescing、remote tool timeout with later completion、physical/API actuatorを交差し、transition attribution accuracy、prediction error、unsafe replanning、self-caused vs external-change識別、recovery後のcausal-history fidelityを測る。

### (7) 既存dailyではなぜ拾いにくいか

roboticsではnetworked control、world-model研究ではlatent dynamics、agent設計ではeffect receiptとして別々に扱われる。**「監査上のexecuted action」と「学習モデルがcauseとして使うaction」を同じtimelineへbindする問題**が境界に落ちやすい。

## 2. A update — Adopted Capability Authorization Must Be Revalidated on Connection-Generation Change

Primary: Hermes Agent #133722  
https://github.com/NousResearch/hermes-agent/issues/133722

Created: **2026-10-06 15:49 JST**

### (1) 何が実証済みか

Hermesのmultiplexed gatewayでは、profile Aがprofile B所有のlive MCP connectionを、resolved identityが一致する場合にadoptできる。#133722では、そのidentity matchが **adoption時にしか確認されない**ため、owner Bがcredential変更等で同じtaskを別resolved identityへreconnectしても、A側のregistry overlay / scope membershipが残り、Aのtool callがBの **new connection generation** へdispatchされ続ける構造が示された。そのnew generationはAのidentityとのmatchを一度も確認されていない。

### (2) 何が提案・推測段階か

すべてのdispatchで高価なfull identity recomputationが必要とは限らない。generation-bound digestやepochを比較するだけでよい可能性がある。

### (3) 関係

capability security、MCP/tool organs、distributed embodiment、principal/credential lineage、shared resource adoption、delegation、Resource Registry。

### (4) 借りる案

```text
AdoptedCapabilityGrant
  adopter_principal
  owner_principal
  resource_id
  admitted_identity_digest
  admitted_connection_generation
  scopes
  policy_epoch
```

foreign/adopted dispatch時には `current_generation.identity_digest == admitted_identity_digest` を確認する。generation change時はgrantを自動継承せず、`REVALIDATE_REQUIRED`へ落とす。

### (5) 差分

credential non-inheritance、route-generation freshness、capability membership freshnessは既出。fresh差分は、**resourceを共有/adoptした後にowner側だけがreconnect・credential rotationした場合、adopterの過去のadmission verdictがnew generationへ暗黙移植される**こと。

### (6) 次

**`AdoptedCapabilityGenerationRevalidationBench-v0` — P0**

owner credential rotation、endpoint rotation、same logical server/new process、same identity/new generation、different identity/new generation、secret source change without visible config change、reconnect during in-flight callを交差し、unauthorized generation dispatch = 0を要求する。

### (7) 拾いにくい理由

authorizationはgrant時点、connection lifecycleはtransport層、credential rotationはsecret managementで評価されるため、**共有接続のauthorization freshness**が抜けやすい。

### (8) 重要度

**A update**

## 3. A update — A Valid Durable Anchor Is Not Proof of Current Destructive Intent

Primary: Hermes Agent #133716  
https://github.com/NousResearch/hermes-agent/issues/133716

Created: **2026-10-06 15:36 JST**

### (1) 何が実証済みか

Hermes Desktopのlong-lived sessionで、userがcurrent tail上でregenerate操作を行ったにもかかわらず、client-side message runtimeのstale bindingが **4時間前の有効なrow** をtargetとして送信した。gateway側から見るとmessage id、row id、ordinal、original textはすべて実在し整合していたため、既存のstale-anchor guardを通過した。その結果gatewayはhistoryを **430 → 323** へtruncateし、107 live messagesをarchiveした。データ自体はDBに残ったが、visible transcriptとmodel contextは4時間前へsilent rollbackした。

### (2) 何が提案・推測段階か

「N message以上のtruncateは常に確認」という固定閾値が最適とは限らない。明示的に過去turnへ戻るUIではdeep rewriteが正当な場合もある。

### (3) 関係

HCI/UI action semantics、canonical transcript、memory/history mutation、destructive effect admission、current-view identity、undo/regenerate/branch、user intent continuity。

### (4) 借りる案

```text
TargetIdentity
CurrentViewWitness
ExpectedTipOrFrontier
DestructiveExtent
UserGestureOrigin
```

`target exists`だけでなく、このgestureが現在どのvisible messageへbindされていたか、current tipから何turn巻き戻すか、expected transcript generation、destructive extentが通常rangeを超えるかをserver側で検証する。

### (5) 差分

既出のLocator–Mutation Extent Bindingは「selectorと作用範囲を分離する」。今回のfresh差分は、**selectorが完全に正しく、targetが実在していても、そのtargetが「いまuserが操作した対象」ではない**場合があること。identity validityだけでは **interaction-currentness** を証明しない。

### (6) 次

**`CurrentIntentBoundHistoricalRewriteBench-v0` — P0**

index-scoped vs ID-scoped binding、history insertion/replacement、long-lived renderer、edit/regenerate/restore/fork、1-turn/10-turn/100-turn rewind、concurrent incoming rowsを交差し、wrong-current-target destructive commit = 0を要求する。

### (7) 拾いにくい理由

database integrityは「anchorが存在するか」、HCIは「buttonが何を指すか」、effect safetyは「どれだけ消すか」を別々に見る。**valid object identity と current user intention のずれ**はその境界にある。

### (8) 重要度

## 4. B update — Optimistic Validation Tokens Must Match the Predicate's Semantic Scope

Primary: OpenClaw #165994  
https://github.com/openclaw/openclaw/issues/165994

Created: **2026-10-06 16:41 JST**

### (1) 何が実証済みか

OpenClawのsession-entry currentness guardはSQLite `PRAGMA data_version` を使い、predicate評価の前後で別connectionのcommitがあればrevision conflictとして失敗する。しかし `data_version` は **同じDB fileへの任意のforeign commit** で変わるため、別session transcript appendやunrelated plugin-state writeでもguardが `invalid_state` を返す。deterministic two-connection reproがあり、productionではCodex subagent spawnやsubagent registry finalizationが失われたと報告されている。

### (2) 提案・推測段階か

最適解がfine-grained per-row revisionか、coarse token change時のbounded predicate re-evaluationかはworkload次第。

### (3) 関係

Continuity Kernel、optimistic concurrency、task/session admission、shared durable state、multi-agent orchestration、database/transactional semantics。

### (4) 借りる案

**invalidation domainとsemantic predicate domainを一致**させる。coarse revision tokenしか得られない場合は、predicateを評価し、coarse token changeを検出しても `predicate false` と同一視せずbounded re-evaluationし、stable windowでpredicateがtrueならacceptする。

### (5) 差分

Kamimusuhiはpredecessor check、revision、lease、atomic commitを重視するが、**revisionが細かいほど安全とは限らない**。無関係なstate変化まで「対象predicateが壊れた」と扱うと、安全機構そのものがavailability failureやwork lossを起こす。

### (6) 次

**`SemanticScopeOptimisticValidationBench-v0` — P1**

same-row relevant write、different-row same table、unrelated table、high write concurrency、predicate changes/unchanged、retry cap、starvationを評価し、false conflict率とstale accept率を同時測定する。

### (7) 拾いにくい理由

database concurrencyではserialization safety、agent runtimeではsession currentnessを別々に評価し、**validation tokenのgranularityがsemantic invariantより広すぎる問題**は見えにくい。

### (8) 重要度

**B update**

## 6. B — Harness–Inference Coordination Needs a Bidirectional Resource Contract

Primary: *Can Agent Harnesses and Inference Engines Hear Each Other? The HEAR Protocol for Agentic LLM Serving*  
https://arxiv.org/abs/2610.06597

Submitted: **2026-10-05 16:07 UTC / 2026-10-06 01:07 JST**

### (1) 何が実証済みか

HEARはagent harnessとinference engineが別々の情報を持つことを問題設定する。harness側はworkflow dependencies、context lifecycle、execution objectives、engine側はrequest queue、KV-cache state、resource pressure、execution capabilitiesを持つ。これをbidirectional protocolで交換し、protocol semanticsとoptimization policyを分離する。

報告ではSCBenchで **1.61× batch speedup**、median TTFT **2.23×改善**、BrowseComp-Plus **1.23× end-to-end speedup**、DeepResearchBench **2.45×**、observed task-quality degradationなしとしている。

### (2) 提案・推測段階か

Kamimusuhiのheterogeneous local/remote models、複数node、privacy boundary、monetary budgetを含む環境で同じ利得になるとは限らない。

### (3) 関係

Cognitive Budget、Cognitive Action Router、K-Core/K-Deep、local inference runtime、multi-agent orchestration、energy/latency-aware cognition、computational embodiment。

### (4) 借りる案

```text
HarnessIntent
  role
  deadline
  dependency frontier
  context reuse hint
  quality floor
  privacy/placement constraint

EngineState
  queue pressure
  KV-cache affinity
  memory pressure
  supported mode
  expected latency
  admission outcome
```

という**typed bidirectional contract**として扱う。重要なのはHEARの具体policyを採用することではなく、workflow semanticsとengine optimizationをprotocol境界で分離すること。

### (5) 差分

KamimusuhiにはCognitive Budget、runtime telemetry、resource routingがある。fresh差分は、**runtime healthを上へ報告するだけでなく、harness側のworkflow dependency/context lifecycleもengine側へ安全に渡し、両側の情報を組み合わせてexecution modeを決める**双方向interface。

### (6) 次

**`BidirectionalCognitiveRuntimeContractBench-v0` — P1**

serial/parallel delegation、shared-prefix/KV reuse、memory pressure、deadline-sensitive K-Edge vs throughput-sensitive K-Deep、local/remote placement、privacy constraint、engine overloadでtask quality、p50/p95 TTFT、end-to-end latency、energy/cost、cache reuse、semantic-policy violationを測る。

### (7) 拾いにくい理由

agent orchestrationはworkflow semantics、serving研究はqueue/cache/GPU efficiencyを見る。**認知スケジューラとmodel runtimeのcontrol planeを一つのcontractとして扱う設計**は両領域の境界。

### (8) 重要度

**B**

### spec.md candidate

1. Observed world transitions MUST NOT be attributed solely to issued commands when the actually-applied action can differ; applied-action evidence SHOULD be preserved and used by action-conditioned models.
2. Authorization to use an adopted/shared connection MUST NOT automatically transfer to a new connection generation whose effective identity was not revalidated.
3. A valid historical object anchor MUST NOT alone authorize a destructive rewrite when current interaction binding or destructive extent may have changed.
4. A coarse revision-token change SHOULD NOT be treated as proof that a narrower semantic predicate became false; scoped validation or bounded re-evaluation is required.
5. Privacy evaluation SHOULD include unnecessary intermediate data access, not only final-output disclosure.
6. Cognitive scheduling interfaces SHOULD distinguish workflow intent from runtime resource state and preserve both across bidirectional coordination.

## 結論

今回の中心は、**agentが「そうしたつもり」「前に許された」「そのIDは実在する」「DBが変わった」「最終出力に秘密はない」「GPUは空いている」といった代理信号を、そのまま現在のsemantic truthへ昇格しないこと**。

- commandを発行したことと、worldへ適用されたactionは違う。
- connectionを一度adoptできたことと、その後のnew generationも使ってよいことは違う。
- row IDがvalidであることと、userが今そのrowを巻き戻そうとしたことは違う。
- DB全体のrevisionが変わったことと、対象predicateがfalseになったことは違う。
- final responseがprivate dataを漏らさないことと、execution中に不要なprivate dataへ触れなかったことは違う。
- workflowを知るharnessとresource pressureを知るengineは、片側だけのtelemetryでは最適に協調できない。

Kamimusuhiの長寿命性には、**実際に適用された作用、current generation、current interaction intent、semantic invariant scope、trajectory-level data access、runtimeとの双方向契約**をfirst-classに扱う設計が有効である。
