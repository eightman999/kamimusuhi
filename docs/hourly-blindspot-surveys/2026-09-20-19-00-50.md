## 1. 今回狙った盲点

通常の agent / memory / identity survey では「設定バグ」「queue cleanup」「KV cache 最適化」「PID file の細部」「plugin format」に見えて落ちやすい、以下の境界を重点化した。

1. **Destructive maintenance parameter semantics**  
   retention / TTL / age / grace / percentage / quota のような数値が、異常値・単位違い・符号反転で「削除しない」から「全部消す」へ意味反転しないか。

2. **Recovery latch / gate ownership**  
   startup restore / migration / replay / reconnect の間だけ閉じる admission gate が、途中例外で永久に閉じたままにならないか。また1件の poison replay が後続eventまで停止させないか。

3. **History-dependent inference state**  
   long-lived local recurrent/attention modelで、同じ memory text を持っていても、差分更新をどのsequence位置へ入れたかによって hidden/recurrent/KV state と意味応答が変わらないか。

4. **Runtime incarnation identity**  
   PID / process name / command line / path / logical slot が一致しただけで「自分が起動した同じprocess」とみなし、kill/reapしてよいか。

5. **Portability vs trust**  
   plugin package が標準にconformして読み込めることと、そのcode/tool/serverへどの権限を渡してよいかを混同していないか。

固定リスト外では、OS process handles / pidfd、destructive configuration monotonicity、failure containment latch、incremental recurrent inference maintenance、portable extension standardのtrust gapを追加探索した。

- https://github.com/NousResearch/hermes-agent/pull/116654

## 5.1 A+ — Retention Policy Domain Safety

**Primary fresh evidence:** Hermes #116735  
https://github.com/NousResearch/hermes-agent/pull/116735

### (1) 何が実証済みか

負のretention dayが未来cutoffへ変換され、ended session全件がselection対象になるproduction pathが再現され、DB boundaryでの値域拒否 + config callerのskipにより回避された。PRはreal SessionDB probeと292 focused testsを報告し、merge済み。

### (2) 何が提案・推測段階か

Kamimusuhi全体のforgetting/retention APIをtyped policyへ統一すること、destructive maintenance前に対象件数・scopeをpreviewすることは提案段階。

### (3) 関係する subsystem / 設計課題

- episodic / session / relationship memory retention
- Canonical Evidenceのarchive / GC
- dream/reflection artifact cleanup
- K-Edge spool / trace retention
- privacy-driven deletion
- digital legacy / death / rebirth policy

### (4) 借りられる設計・実装アイデア

数値sentinelをやめ、例として:

```text
RetentionPolicy =
  KEEP_FOREVER
  AGE_DAYS(non_negative_duration)
  KEEP_LAST_N(non_negative_count)
  QUOTA(bytes)
  LEGAL_HOLD(reason, authority)
  EXPLICIT_DELETE_ONLY
```

を使う。さらに destructive operation では:

```text
policy parse
→ semantic domain validation
→ candidate set preview
→ blast-radius cap
→ authority/consent validation
→ delete/tombstone
→ audit receipt
```

とする。

### (5) Kamimusuhiとの差分

既存には explicit destructive scope、opportunity-qualified expiry、endogenous retention feedback、distributed erasure がある。しかし今回の差分は、**policy valueそのものが選択集合の意味を反転させる場合に、destructive boundaryで値域をfail closedすること**。`scope=None != ALL` とも別で、`duration=-1`のような「一見型は合っている値」が危険。

### (6) 次に検証すべきこと

`RetentionPolicyDomainSafetyBench-v0`:

- `-1`, `-0`, `NaN`, `inf`, overflow, unit mismatch, 0, huge values
- timezone / DST / clock rollback
- empty scope / all scope
- `keep N` のN<0
- byte quotaのsigned/unsigned変換
- policy reload前後

を注入し、**invalid policyが削除対象を広げない**ことを確認する。mass-deletion thresholdを越えたらsecond authorizationを要求する案も比較。

### (7) なぜ既存dailyでは拾いにくいか

AI agent / memory研究ではretention policyの高水準アルゴリズムに注目しやすく、数値domain errorが「forgetting authorityの全件化」へつながるmaintenance APIの細部は落ちやすい。

### (8) 重要度

**A+** — identity continuityに直結するdurable memoryを一括破壊できるため。merge済みproduction evidenceも強い。

### (2) 何が提案・推測段階か

Kamimusuhiのmigration / restore / resync / memory rebuild / body reconnectで、gate/lease/latch ownershipを共通primitiveへ抽象化し、exception pathまで静的・動的に検査することは提案。

### (3) 関係する subsystem / 設計課題

- Continuity Kernel recovery
- K-Edge reconnect
- session restoration
- pending input replay
- migration publication barrier
- approval / effect gate
- Global Workspace ingress

### (4) 借りられる設計・実装アイデア

```text
GateLease
  acquire_reason
  owner_operation_id
  acquired_at
  release_mode = FINALLY_BOUND
  max_hold / watchdog
  queue_depth
  failed_items[]
```

とし、replay queueは **poison item containment** を持つ。

```text

→ mark that item failed/unknown

```

### (5) Kamimusuhiとの差分

## 5.5 B — Portable Plugin Trust Projection

**Official specification:**  
https://agent-plugins.org/specification

**Official future considerations:**  
https://github.com/agentplugins/agent-plugins-spec/blob/main/FUTURE_CONSIDERATIONS.md

### (1) 何が実証済みか

Agent Plugins 1.0.0はportable package layout、manifest validation、path containment、component failure boundaries等をnormativeに定義する。一方、公式文書はtrust model、permission system、sandboxing、origin/integrity verification、portable secret handling等をv1.0.0のscope外と明記する。

### (2) 何が提案・推測段階か

KamimusuhiがAgent Pluginsを採用するかは未定。採用する場合にlocal trust manifest / capability profileを別layerで結合する設計は提案。

### (3) 関係する subsystem / 設計課題

- Skill Registry
- MCP / external tools
- cognitive extension loading
- provenance / capability security
- multi-device portability
- software-body migration

### (4) 借りられる設計・実装アイデア

packageのportable identityとlocal activation authorityを分ける。

```text
PortablePluginDescriptor
  spec_version
  package_digest
  declared_components

LocalPluginTrustProjection
  verified_origin?
  signer / attestation
  granted_capabilities
  filesystem/network/tool scopes
  secret scopes
  sandbox class
  approval epoch
  audit policy
```

`conformant package → enabled` を禁止し、`conformant → inspected/resolved → locally authorized → activated` とする。

### (5) Kamimusuhiとの差分

extension security-envelope inheritance、capability security、skill dependency closureは既存。今回の差分は **今後現実に流通し得るportable package standard自体がsecurity/trustを意図的に扱わないため、portability metadataをauthority metadataとして誤用しない** というstandard-specific watch。

### (6) 次に検証すべきこと

`PortablePluginTrustProjectionBench-v0`:

- same packageを2 devicesで異なるcapability grantにする
- package update時にgrantを自動継承する/しない比較
- MCP server command変更
- symlink/path containment passだがnetwork authority過大なcase
- unsigned / unknown-origin package
- secret request
- extension namespaceのclient-specific behavior

### (7) なぜ既存dailyでは拾いにくいか

plugin standardは「agent tooling / interoperability」ニュースに見えやすく、identity continuity surveyではsecurity non-goalsまで読まれにくい。また日本語紹介記事だけではportable conformanceとtrust保証の差が埋もれやすい。

### (8) 重要度

**B** — 直ちに採用する必要はないが、Skill Registry / cognitive extension portabilityを進めるなら早期に境界を固定する価値がある。

## 10. 今回の結論

今回もっとも重要なのは、**「forgetting policyが壊れた時に忘れすぎない」ことを第一級invariantにする**ことである。Kamimusuhiの長寿命性では、保存できることだけでなく、maintenance設定の異常がcanonical historyを一括破壊しないことが必要になる。

次に、recoveryについては「復元できるか」だけでは不十分で、**復元処理が失敗しても外界への入口を必ず返却する**必要がある。

さらにlocal cognitionを長寿命化するなら、canonical memoryとwarm model stateの間にもう一層の契約が必要になる。memory textが正しいだけでは、履歴依存のrecurrent/KV stateが正しいとは限らない。

圧縮すると今回の4行は以下。

```text
invalid forgetting policy must fail closed
recovery must release its gates even when recovery fails
warm inference state is derived history-dependent state, not canonical memory
reusable runtime identifiers are not incarnation identity
```
