## 3. Executive summary

今回は **有意な新規発見あり**。

最も強い差分は、Kamimusuhi がすでに持つ `canonical evidence != interpretation`、`tool result != belief`、`runtime assurance != cognition` という原則を、**監査・外部認知資源・個人化・プライバシー・実行証明の各境界で機械的な contract にできる資料**がまとまって見つかったことである。

特に重要なのは次の三つ。

1. **Audit Without Verification** は、各 agent の報告に「観測」と「その agent 自身の結論」を同梱すると、後段 auditor が独立に検証するのではなく結論を relay しやすいことを大規模な controlled study で示す。Kamimusuhi の canonical evidence / interpretation 分離を、postmortem と inter-organ audit の UI/API まで徹底する根拠になる。
2. **Agents Trust Tools Too Much** は、14 LLM・web search / sub-agent / code execution の3 tool で、壊した tool return の採用率が全設定平均で1/3を超え、web search では68.0%に達したと報告する。単に `[tool-result]` と provenance を付けるだけでは epistemic safety にならず、belief admission 前の conflict handling と tool reliability calibration が必要になる。
3. **DP-MemView** は、「内部 memory を読む権限」と「その memory と相関した情報を何ターンにもわたり外へ漏らしてよい権限」を分離する。長寿命 personal agent では、read ACL だけでなく **attribute-level cumulative disclosure budget** を持つべきという未収載の強い示唆になる。

さらに、個人化で demographic group centroid へ引っ張られる **Alignment by Stereotyping**、portable runtime evidence の **TRACE v0.2**、安全 monitor を target model の実際の compliance に条件付けて評価すべきとする **Recall Is Not Protection** を採用した。

# 4. Detailed findings

## 4.1 Audit Without Verification — 「観測」と「告発/結論」を同じ report に載せない

**Source:** Paul-Peter Arslan, *Audit Without Verification: When LLM Accountability Layers Relay Rather Than Check*, arXiv:2609.07680  
**Primary:** https://arxiv.org/abs/2609.07680  
**Submitted:** 2026-09-07  
**Importance:** **S**  
**Blind-spot class:** organisational accountability / audit science / information dependency

### (1) 何が実証済みか

論文は、組織境界を模した6-agent pipeline、process-level information boundary、balanced defect injection と matched clean twins を使い、2種類の chain model について各345,600 requests を評価している。

pre-registered hypothesis だった「collective responsibility framing が chain length とともに escalation を悪化させる」は支持されなかった。一方で、より重要な failure が観測された。

- 全 agent が silent な clean episode 7,996件では auditor は allegation を新規生成しなかった。
- upstream agent が false alarm を出した clean episode では、auditor が innocent party を名指しする率が34.4% / 62.6%だった。
- true origin を upstream agent が誰も提案していない条件では、auditor が report から true origin を回復できたのは4.1%だったのに対し、同じ episode の raw documentation からは60.3%だった。
- report 中の agent 自身の conclusion field を削除し、観測を一定に保つと、該当条件で accuracy が45.2%へ上がり、upstream suggestion への adherence が94.4%から3.4%へ低下した。

したがって「audit agent を置いた」だけでは independent verification にならず、**auditor の evidence が upstream conclusion と十分独立している必要がある**という結果である。

### (2) 何が提案・推測段階か

- synthetic / controlled pipeline であり、Kamimusuhi の実運用で同じ数値になるとは限らない。
- conclusion-blind audit が常に最良ではない。upstream conclusion が正しい条件では、削除が accuracy を70.5%から55.7%へ下げたと報告されている。
- したがって「結論を永久に隠す」より、独立検証フェーズと advisory conclusion 利用フェーズを分ける設計が妥当かを検証する必要がある。

### (3) Kamimusuhi の関連サブシステム

- Canonical Evidence / Self History
- operational trace / canonical audit
- Continuity Kernel incident reconstruction
- K-Edge / K-Core / K-Deep handoff
- external model / tool result integration
- Effect Acceptance / dispute replay

### (4) 借りられる設計・実装アイデア

`AuditRecord` で observation と conclusion を別 field / 別 view にする。

```text
AuditRecord
  observation_refs[]      # raw/canonical evidenceへの参照
  local_observations[]    # そのorganが直接観測したもの
  hypothesis[]            # 推測
  conclusion              # 誰が原因だと思うか
  conclusion_source
  confidence

AuditView.INDEPENDENT
  -> observation_refs + local_observations only

AuditView.ADVISORY
  -> hypothesis + conclusion も開示
```

事故解析ではまず `INDEPENDENT` view で auditor に原因候補を出させ、その後 upstream conclusion を開示して差分を比較する。`conclusion agreement` は evidence quality と別 metric にする。

### (5) Kamimusuhiとの差分

Kamimusuhi はすでに canonical evidence と interpretation を概念上分けているが、**audit consumer がどの derived conclusion を見るか**までは強い runtime contract になっていない。保存時の分離だけでなく、監査時の information-flow separation が必要。

### (6) 次に検証すべきこと

`ConclusionContaminationBench`:

- K-Edge→K-Core→K-Deep の3段 handoff を模擬。
- upstream に false cause / correct cause / no conclusion を注入。
- auditor を `raw evidence only` / `observation+conclusion` / `two-stage reveal` で比較。
- true-cause accuracy、false accusation、calibration、latency を測る。

### (7) 既存 daily で拾いにくい理由

multi-agent reliability の論文に見えるが、核心は reasoning 能力より **組織監査・報告書の情報構造**にある。agent benchmark として読むだけだと「audit layer の精度」で終わり、canonical evidence API の read-view 設計まで接続しにくい。

## 4.2 Agents Trust Tools Too Much — provenance だけでは tool overtrust を防げない

**Source:** Hoyeol Yang et al., *Agents Trust Tools Too Much: Measuring Reliance on Unreliable Tools*, arXiv:2609.05587  
**Primary:** https://arxiv.org/abs/2609.05587  
**Submitted:** 2026-09-04 / recent feed で再確認  
**Importance:** **S**  
**Blind-spot class:** epistemic trust / external cognitive resource reliability

### (1) 何が実証済みか

14 LLM を web search、LLM sub-agent delegation、code execution の3 tool で評価し、tool return を plausible だが誤った内容へ corrupt して最終回答への採用を測定した。

- mean adoption rate は3 tool すべてで1/3を超えた。
- web search では68.0%に達した。
- reasoning trace の分析では、agent が conflict を認識し内部では正しい答えを回復しているのに、最終出力では corrupt tool answer だけを提示して warning を出さない failure も観測された。
- user prompting、tool-provider metadata、agent-builder post-training の3レベルの mitigation を試したが、特定 model/tool では効いても全 tool に一貫して効くものはなかった。

### (2) 何が提案・推測段階か

- corruption は controlled injection であり、実Webや実コード実行の自然故障分布とは異なる。
- どの tool/domain にどれだけ redundancy を要求すべきかは未確立。
- 「必ず複数 tool で再検証」が latency / cost / correlated failure を考えると最適とは限らない。

### (3) Kamimusuhi の関連サブシステム

- Cognitive Action Router
- Global Workspace origin tagging
- Persona Core の external-result integration
- Library ingestion / Web search
- K-Deep research
- belief / self / relationship proposal generation

### (4) 借りられる設計・実装アイデア

既存の `external result != belief` を runtime gate にする。

```text
tool return
  ↓
ToolClaim
  source/tool/version
  domain
  reliability prior
  freshness
  conflict_with_internal_or_other_sources[]
  ↓
EpistemicAdmissionGate
  ACCEPT_AS_EVIDENCE
  REQUIRE_CORROBORATION
  HOLD_CONFLICT
  REJECT
  ↓
workspace / belief proposal
```

特に「内部推論と tool result が衝突しているのに tool を採用した」状態を silent overwrite にせず `HOLD_CONFLICT` として一級状態にする。tool trust は単一 global score ではなく domain × operation × freshness × failure history で持つ。

### (5) Kamimusuhiとの差分

現行 architecture は provenance を保持し external model/tool を self から分離するが、**由来が分かっていることと、その由来を信用すべきことは別**。provenance は必要条件だが reliability calibration ではない。

### (6) 次に検証すべきこと

`CorruptToolReturnBench`:

- Search / local specialist LLM / frontier LLM / code runner / sensor adapter を対象。
- correct / stale / plausible-wrong / adversarial-wrong を注入。
- origin tag のみ、confidence metadata、cross-check、EpistemicAdmissionGate を比較。
- wrong-adoption、conflict disclosure、追加cost/latency、false distrust を測る。

### (7) 既存 daily で拾いにくい理由

通常の tool-use benchmark は「正しい tool を呼べるか」を測り、tool 自体を oracle と仮定しがち。この研究は **外部認知器官が嘘を返す場合の認識論**を測っており、orchestration の一段上ではなく一段下の信頼境界である。

## 4.3 Alignment by Stereotyping — person model を demographic prototype へ潰さない

**Source:** Qishuai Zhong et al., *Alignment by Stereotyping: How LLMs Sacrifice Individual Distinctiveness for Cultural Adaptation*, arXiv:2609.05993, EMNLP 2026 Findings  
**Primary:** https://arxiv.org/abs/2609.05993  
**Submitted:** 2026-09-05  
**Importance:** **A+**  
**Blind-spot class:** personalization / social psychology / individuality preservation

### (1) 何が実証済みか

World Values Survey を用い、GPT-5.1 を含む7モデルで demographic profile conditioning を評価した。

- 多くの model で group-level value alignment accuracy は改善した。
- 同時に response が demographic group centroid へ引き寄せられ、individual differences が圧縮された。
- 10,000 permutation tests、6 demographic attributes、7 models で top-performing models の individual compression が human baseline より強いことを報告。
- model family 内の scaling でこの tradeoff が強まる傾向も報告。
- compact demographic label ではなく、情報を multi-turn dialogue に分散させると prototype retrieval が部分的に抑えられた。これは synthetic dialogue と PRISM の real conversation で確認されたが、大規模 replication は未実施。

### (2) 何が提案・推測段階か

- WVS/value question が長期 relationship modeling 全般を代表するわけではない。
- Kamimusuhi の person model が同じ centroid collapse を起こすかは未検証。
- demographic signal を完全に使わないことが最適とも限らない。弱い prior として有益な場面はあり得る。

### (3) Kamimusuhi の関連サブシステム

- relationship/person model
- social cognition / Theory of Mind
- common ground
- self/other separation
- long-term personalization
- Persona Core training/evaluation

### (4) 借りられる設計・実装アイデア

person model を次のように優先順位付きにする。

```text
individual direct evidence
  > individual repeated pattern
  > current interaction evidence
  > weak population/group prior
```

人口統計・属性ラベルは `relationship/stable` の「本人について確定した性格・価値観」へ直接展開しない。使う場合は `population_prior` として provenance・低confidence・expiry を持たせ、個人 evidence と衝突したら即座に個人側を優先する。

### (5) Kamimusuhiとの差分

Kamimusuhi は self/other separation を強く持つが、**other model 内部で「個人」と「所属集団の prototype」を分離する invariant**はまだ明示的でない。

### (6) 次に検証すべきこと

`IndividualityPreservationBench`:

- 同じ demographic profile を持つが preference/value が異なる synthetic personas を作る。
- label-only / dialogue-history / atomic individual memory / hybrid prior の4条件を比較。
- individual recall、group-centroid attraction、false inference、recovery after contradictory personal evidence を測る。

### (7) 既存 daily で拾いにくい理由

fairness/cultural adaptation の研究として分類されやすく、persistent-agent memory の論文検索では出にくい。しかし Kamimusuhi では「人ごとに分離された relationship model」を長期間育てるため、**個人化の名の下で個体差を消す failure**は直接的な continuity/sociality 問題になる。

## 4.4 DP-MemView — memory ACL と transcript leakage budget を分ける

**Source:** Jong Wook Kim et al., *DP-MemView: A Memory Interface for Attribute-Level Transcript Privacy in Long-Term LLM Agents*, arXiv:2608.03130  
**Primary:** https://arxiv.org/abs/2608.03130  
**Submitted:** 2026-08-04  
**Importance:** **A+**  
**Blind-spot class:** differential privacy / cumulative information leakage / memory interface  
**Backfill:** primary 24h window 外だが、現行 Kamimusuhi に未収載で privacy contract の穴を直接埋めるため採用。

### (1) 何が実証済みか

研究は、long-term memory を使う agent が protected attribute を直接発話しなくても、**何ターンもの personalized response の相関から属性が累積推定される**脅威を adaptive transcript privacy として定式化する。

DP-MemView は response LLM に raw memory を渡さず、private selection によって public response-conditioning view を選ぶ。各 selection は、その read set と交差する protected memory group ごとに attribute ledger へ charge され、cap を超える selection は fixed generic view に置換される。

明示した interface contract の下で adaptive transcript 全体に対する pure differential-privacy guarantee を示し、3 response LLM を使った controlled adjacent-store benchmark と public-corpus transfer で、transcript distinguishability を near-chance に保ちながら personalization utility を維持したと報告する。safeguard を外す ablation では side channel や long-horizon leakage が増える。

### (2) 何が提案・推測段階か

- DP の隣接関係・protected attribute grouping を実ユーザーにどう設計するかは domain-specific。
- privacy budget を消費すると personalization utility が低下するため、UX / consent / reset semantics が必要。
- relationship memory 全般に formal DP を強制することが実用的とは限らない。

### (3) Kamimusuhi の関連サブシステム

- Memory Access Kernel
- relationship/self memory
- Global Workspace rendering
- response/action generation
- privacy policy
- multi-surface / third-party app interaction

### (4) 借りられる設計・実装アイデア

重要な新 invariant 候補:

```text
internal_read_authority != external_disclosure_authority
single_turn_safe != adaptive_transcript_safe
```

`DisclosureBudgetLedger` を memory ACL の外側に置く。

```text
protected_attribute
  memory_groups[]
  disclosure_budget
  spent_budget
  audience/surface scope
  reset/expiry policy
```

response rendering 前に「この output-conditioning view は、どの protected attributes の budget をどれだけ使うか」を評価する。

### (5) Kamimusuhiとの差分

直近 survey の SP-Mem / privacy-aware memory lifecycle は sensitive exact value と sanitized semantic memory の分離を扱う。一方 DP-MemView の差分は、**値を直接出さなくても repeated outputs から漏れる**ことを transcript 全体で扱う点。これは別レイヤーである。

### (6) 次に検証すべきこと

`AdaptiveLeakageBench`:

- protected attribute を持つ/持たない adjacent person-memory store を作る。
- 16〜64 turn の benign personalization query を生成。
- raw retrieval / redaction / per-turn policy / attribute ledger 付き memory-view を比較。
- attacker AUC、task utility、budget exhaustion rate、false genericization を測る。

### (7) 既存 daily で拾いにくい理由

privacy は通常「保存時暗号化」「ACL」「PII redaction」として扱われる。ここで問題になっているのは **合法な内部アクセスから生まれる合法そうな複数出力の統計的合成**であり、memory architecture と会話 privacy の境界に落ちる。

## 4.5 Recall Is Not Protection — monitor は「危険ラベル」を拾う率ではなく「実際に危険になるケース」を止める率で測る

**Source:** Sripad Karne, *Recall Is Not Protection: Evaluating Safety Monitors Against Model Compliance*, arXiv:2609.05797  
**Primary:** https://arxiv.org/abs/2609.05797  
**Submitted:** 2026-09-05 / NeurIPS 2026 JUDGe Workshop submission  
**Importance:** **A**  
**Blind-spot class:** safety metric design / counterfactual effect-conditioned evaluation

### (1) 何が実証済みか

研究は harmfulness label に対する通常 recall と、「その prompt を target model が実際に少なくとも一度 comply するか」で条件付けた monitor recall を分離した。

6 monitor configurations、3 model families（activation probe、fine-tuned text guard、120B policy-conditioned reasoning classifier を含む）で、固定 false-positive rate において elicitable harmful prompts に対する recall が non-elicitable prompts より **0.22〜0.38低い**と報告する。また monitor が miss する prompt は、catch する prompt より target model に comply される確率が **2.8〜5.6倍高い**。text-only monitor でも gap が見られた。

### (2) 何が提案・推測段階か

- harmful prompt screening の設定であり、Kamimusuhi の effect acceptance / memory mutation / K-Nerve reflex へ同じ gap がそのまま移るとは限らない。
- elicitable の定義は sampling budget に依存する。
- rare catastrophic effect の評価には別の importance weighting が必要。

### (3) Kamimusuhi の関連サブシステム

- Runtime Assurance
- K-Nerve deny/interrupt
- Cognitive Action Router
- external-effect safety
- mutation/effect gates
- evaluation harness

### (4) 借りられる設計・実装アイデア

monitor の metric を `label_recall` だけにしない。

```text
protection_recall = P(monitor_blocks | target_would_violate)
missed_effect_risk = P(target_would_violate | monitor_misses)
```

Kamimusuhi では「gate が policy violation candidate を分類できるか」だけでなく、**gate がなければ下流 component が本当に effect / commit まで進むケース**を counterfactual に測る。

### (5) Kamimusuhiとの差分

直前 hourly の verification adequacy は「proof/harness が intended property を測っているか」を扱った。本項はさらに **安全 component の評価母集団を downstream susceptibility に条件付ける**という deployment-side metric の問題であり、別の failure mode。

### (6) 次に検証すべきこと

`EffectConditionedMonitorBench`:

- risky proposal corpus を用意。
- gate 無しで downstream actor が effect を起こす頻度を反復 sampling で推定。
- monitor recall を all-risk-label / actually-elicitable に分解。
- severity × elicitation probability を加味した expected prevented harm も出す。

### (7) 既存 daily で拾いにくい理由

safety paper として読むと guard model の比較に見えるが、Kamimusuhi に重要なのは **評価指標の causal target が実際の side effect か**という systems-evaluation の論点。

## 4.6 TRACE v0.2 — canonical identity とは別に、portable な「何が実行されたか」の署名済み evidence receipt を持つ

**Sources:**

- TRACE project: https://trace.agentrust-io.com/
- Specification repository: https://github.com/agentrust-io/trace-spec
- v0.2 spec: https://github.com/agentrust-io/trace-spec/blob/main/spec/trace-v0.2.md

**Status:** Developer Preview / TRACE Specification is hosted as an LF Project  
**Importance:** **A**  
**Blind-spot class:** runtime attestation / confidential computing / portable compliance evidence  
**Backfill:** 2026-08-25 に Linux Foundation governance へ移行した標準化動向。未収載のため watchlist 候補として採用。

### (1) 何が実証・公開済みか

TRACE v0.2 は portable signed runtime evidence の open specification と conformance test suite を公開している。Trust Record は workload identity、model/runtime、policy、data classification、tool-transcript commitment 等を一つの record に結び、verifier が signature と required evidence を検査する。

仕様は既存標準を profile/composition する方向で、RATS (RFC 9334)、EAT (RFC 9711)、SLSA、SCITT、SPIFFE 等と接続する。software-only synthetic example から hardware provenance を伴う trust level まで段階を持つ。

### (2) 何が提案・推測段階か

- v0.2 は **Developer Preview** であり、production-stable / regulatory acceptance を意味しない。
- signed record は「その policy hash が active だった」等を証明し得ても、**policy 自体が正しい、model decision が正しい、tool action が安全**とは証明しない。
- hardware/issuer/verifier trust chain 自体の運用設計が必要。

### (3) Kamimusuhi の関連サブシステム

- distributed embodiment / organ registry
- K-Edge / K-Core / K-Deep attestation
- operational trace / canonical audit
- external model/tool execution receipts
- migration / recovery
- capability / runtime principal boundary

### (4) 借りられる設計・実装アイデア

Kamimusuhi 内部の canonical evidence schema を TRACE に従属させず、**adapter/projection** として `ExecutionEvidenceReceipt` を出す。

```text
canonical execution event
  + organ/runtime identity
  + code/model digest
  + policy revision
  + data class
  + tool-call commitments
  + attestation evidence
      ↓ projection
TRACE-compatible Trust Record
```

これにより external verifier に「どのorgan/環境/方針で実行されたか」を提示できる一方、TRACE record を continuity head や self identity の source of truth にはしない。

### (5) Kamimusuhiとの差分

Kamimusuhi は「誰が同じ個体として続くか」を扱う。TRACE は主に **どの workload/runtime が、どの条件下で実行されたか**の evidence。したがって、`CanonicalContinuityIdentity != WorkloadAttestedIdentity` を維持する必要がある。

### (6) 次に検証すべきこと

`RuntimeEvidenceProjectionBench`:

- K-Edge/Core の synthetic execution event から minimal TRACE record を生成。
- signature tamper、policy revision mismatch、stale attestation、tool transcript mismatch を検出できるか。
- canonical replay から同じ semantic receipt を再生成できるか。
- TRACE schema upgrade で canonical history が壊れないか。

### (7) 既存 daily で拾いにくい理由

AI agent framework ではなく confidential-computing / attestation / compliance-evidence 標準として出てくるため、agent cognition 検索から漏れやすい。しかし distributed embodiment を実機・複数hostへ広げるほど、**runtime self-report ではなく第三者検証可能な execution evidence** が重要になる。

## 5. Cross-cutting design implications

今回の6件は、異なる分野ながら一つの共通原則へ収束する。

```text
誰かがそう言った       != 観測事実
Toolが返した            != 真である
個人化できた            != 個人を理解した
Memoryを読める          != 出力から漏らしてよい
Monitorが高recall        != 実害をよく防ぐ
Runtime recordが署名済み != policy/decisionが正しい
```

Kamimusuhi はすでにこの種の分離を多く持つが、次の三層を明示するとさらに強い。

### 5.1 Evidence plane

- canonical event / raw observation
- tool return as observed artifact
- cryptographic/runtime evidence
- immutable provenance links

### 5.2 Interpretation / epistemic plane

- hypothesis
- conclusion
- confidence
- tool reliability
- conflict state
- population prior vs individual evidence

### 5.3 Admission / disclosure / effect plane

- belief admission
- memory disclosure budget
- durable mutation
- external effect acceptance
- safety monitor / runtime assurance

この3層を型として分けると、「記録されている」「信じている」「外へ出してよい」「実行してよい」が同じ boolean に潰れにくい。

## 11. Bottom line

今回の設計上の最重要メッセージは、**Kamimusuhi の境界は provenance を付けるだけでは完成しない**ということ。

- provenance があっても upstream conclusion に auditor が引っ張られる。
- provenance があっても tool を過信する。
- person profile があっても group prototype に個人を潰す。
- memory ACL があっても transcript から累積漏洩する。
- monitor が高recallでも実際に危険なケースを取り逃がす。
- attestation receipt があっても policy/decision の正しさは別問題。

次の実装優先候補は **`CorruptToolReturnBench` と `ConclusionContaminationBench`**。どちらも現行アーキテクチャの大改造なしで先に failure を測定でき、その結果から `EpistemicAdmissionGate` / independent audit view を normative contract に昇格すべきか判断できる。
