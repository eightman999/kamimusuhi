## 5.1 A — Closed-World Tool Resolution Before Causal Gating

**一次資料:** Iyer, *Closed-World Resolution Against Tool Hallucination in LLM Agents*, arXiv:2609.19425  
https://arxiv.org/abs/2609.19425

### (1) 何が実証済みか

著者は10 hosted models × 2 invocation surfacesで322件のgenuine tool hallucinationを測定し、MCP live surfaceでも154件を観測したと報告する。fabricated-tool callはunconstrained raw-JSON surfaceに34件、より制約されたsurfaceに3件と偏り、675B modelでも7–8B model相当のstructural failureが残った。また複数MCP serverを1 namespaceへmergeするとcollision / shadowing等の別taxonomy M1–M5が現れ、single-registryではcleanだったfrontier modelにもfailureが生じた。

論文の中心的な形式化は、tool-selection / safety gateが「このcallがどのreal toolを指すか」を前提にするため、存在しないtool callは**causal gateが下したdecisionではない**という点。closed-world registry membership + signature checkを行う`Resolution Rung`をgateより前に置く必要性を示す。

### (2) 何が提案・推測段階か

- benchmark / resolverはpreprint段階で独立追試はまだ薄い。
- registry membership + signature checkだけでは、**実在tool + valid schemaだが意味的に誤ったargument**は防げない。論文自身もschema-indistinguishable borrowed argumentsをirreducible residueとして残す。
- KamimusuhiのAction Routerに同一failureが現在存在する証拠はない。

### (3) Kamimusuhi関係先

- Cognitive Action Router
- tool/model registry
- MCP / plugin / connector surfaces
- capability freshness
- Effect Acceptance / last reversible moment
- semantic effect-payload health
- audit / provenance

### (4) 借りられる設計・実装アイデア

Action lifecycleの先頭へ明示的な**resolution phase**を置く。

```text
ModelToolIntent
  tool_name_raw
  args_raw
  registry_epoch_seen
  source_model
  turn_id

        ↓

ClosedWorldResolution
  exact_registry_member
  exact_signature_version
  namespace_owner
  collision_status
  resolution_receipt

        ↓ only if RESOLVED

Policy / Capability / Authority / EffectAcceptance
        ↓
Execution
```

重要なのは `DENY` と `UNRESOLVABLE` を同じにしないこと。

- `UNRESOLVABLE`: canonical action候補になっていない
- `DENIED`: canonical action候補だがpolicy/authorityで拒否
- `AUTHORIZED`: canonical action候補として実行可能

MCP merge時は単純なflat tool nameではなく `(server_identity, tool_identity, schema_epoch)` をcanonical keyとし、collision/shadowingを明示状態にする。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでにcapability freshness、tool discovery、semantic payload health、Effect Acceptance等を持つ/候補化している。しかしそれらは基本的に**実在resourceへのcandidate action**を扱う。

今回の差分は、その前に

> 「model出力をcanonical action candidateと呼んでよいか」

を決める層を置くこと。特に `stale tool` と `never-existing tool` を別failure classにする。

### (6) 次に検証すべきこと

**`ClosedWorldToolResolutionBench-v0`**

fixture:

- real tool name / exact schema
- nonexistent tool
- typo / near-neighbor name
- stale-but-formerly-real tool
- real tool + undeclared arg
- real tool + wrong schema epoch
- two MCP servers with same tool name
- shadowed server/tool after reconnect
- valid schemaだがwrong semantic value

- unresolved callがpolicy/effect gateへ到達した割合 = 0であること
- collision時にguessしないこと
- valid callのfalse rejection
- registry update後のlatency
- audit上 `UNRESOLVABLE` と `DENIED` が区別されること

### (7) 既存デイリーサーベイではなぜ拾いにくいか

普通のtool-use / alignment surveyは「どのtoolを選ぶか」「選んだtoolを安全に使うか」を扱いやすい。今回の穴は**selection以前のsymbol resolution / linker / namespace semantics**であり、compiler/linker・closed-world resolutionに近い。

### (8) 重要度

## 5.2 A — Least-Context Maintenance Handoff

**一次資料:** Letta Code PR #4539  
https://github.com/letta-ai/letta-code/pull/4539

### (1) 何が実証済みか

PRのcontrolled live evaluationでは、parent conversationをforkしたmemory workerはmemory correctnessが高い一方、**15 trials中11回でunrelated parent questionまで答えた**。task-ownership instructionを追加しても15/15 memory correctnessへ改善しただけで、unrelated answersは11/15のままだった。

一方:

- fresh worker + explicit complete handoff: 15/15 correct、unrelated answer 0/15
- fresh worker + transcript as reference: 15/15 correct、0/15
- 追加21 trialsのon-demand transcript path方式: 21/21 correct、unrelated answer 0/21

という差が報告されている。history factsを渡さないfresh workerは9/15まで落ちるため、単に「contextを切る」だけでも不十分。

### (2) 何が提案・推測段階か

- short constructed transcript、Claude Sonnet 4.6、memory taskという限定条件。
- explicit handoffはevaluator-writtenで、自動handoff生成の品質は未検証。
- long-history retrieval、relationship memory、dream/consolidationに同じ数字が出る保証はない。
- PR自体はdraftでproductはまだfork-based。

### (3) Kamimusuhi関係先

- background memory writer
- dream / consolidation / maintenance cognition
- Relationship / Persona contamination prevention
- K-Deep task delegation
- Continuity Kernel proposal generation
- transcript / episode access policy

### (4) 借りられる設計・実装アイデア

既存 `MaintenanceCognitionIsolation` を「表示隔離」から**context activation isolation**まで強化する。

```text
MaintenanceHandoff
  maintenance_task_id
  explicit_goal
  allowed_mutation_domain
  required_facts[]
  provenance_refs[]
  read_only_context_handles[]
  forbidden_goal_classes[]
  completion_sink = maintenance-only
```

原則:

1. worker launch promptへparent conversation全体をactive contextとしてforkしない。
2. 必要なfactsはexplicit handoffへmaterialize。
3. 足りなければexact read-only transcript / evidence handleをon-demand retrieval。
4. retrieved contextは**reference evidence**であり、そこに含まれる未完了goalをworker taskへ自動昇格しない。
5. maintenance workerのfinal reportはsocial episodeへ自動投稿しない。

## 5.3 A — Privacy Propagation Mediation at Information-Moving Events

**一次資料:** Huang et al., *PAPC: Platform Mediation for Privacy-Propagation Externalities in AI-Mediated Workflows*, arXiv:2609.19226  
https://arxiv.org/abs/2609.19226

### (1) 何が実証済みか

論文はprivacy lossをfinal responseだけでなく、memory write / shared workspace / inter-agent message / tool eventという**information-moving event**で測る。retrieval-memory / multi-agent workflow benchmark上で、PAPCがdeterministic task completionを維持しつつ、測定したexact raw-valueおよびexternal raw-value exposureを除去したと報告する。

また、同じcontentでもfanout/topologyによってdownstream exposure costが変わるというmodelを採用し、高fanout objectを独立のrisk factorとして扱う。

### (2) 何が提案・推測段階か

- preprintであり、現実のheterogeneous agent ecosystemでのlatency / false quarantine / utility lossは未確定。
- exact raw-value exposureが消えることと、semantic inference / reconstruction attackまで防げることは同義でない。
- topology/fanout riskの最適な定量化はKamimusuhi向けに再設計が必要。

### (3) Kamimusuhi関係先

- memory ownership and consent
- Episodic / Relationship / Library promotion
- Workspace
- Social Harness / multi-agent delegation
- provenance graph
- external tool/event delivery
- distributed embodiment

### (4) 借りられる設計・実装アイデア

privacy gateを`final answer filter`ではなく、shared stateへ情報が**移動する直前**へ置く。

```text
InformationMoveProposal
  source_object
  source_principal
  target_surface
  target_principals[]
  data_class
  provenance
  current_fanout
  projected_fanout
  onward_rights
  purpose

PrivacyMoveDecision
  ALLOW
  ABSTRACT
  QUARANTINE
  BLOCK
  ALLOW_WITH_ATTENUATED_ONWARD_RIGHTS
```

特に`raw fact`と`policy-safe abstraction`を別objectにし、後者からraw sourceへ逆流しないようlineageを保持する。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでにconsent-bound memory promotion、persistent information-flow policy、distributed erasure、privacy-aware memoryを扱っている。

今回の差分は、privacyを**state categoryだけでなくgraph topology / fanoutを持つtransition cost**として扱うこと。

```text
same fact + private episode
!=
same fact copied into high-fanout shared workspace
```

というrisk差をfirst-classにする。

### (6) 次に検証すべきこと

**`PrivacyPropagationFanoutBench-v0`**

同一secretを:

- private episodeのみ
- one-to-one subagent handoff
- shared workspace
- N-agent broadcast
- external tool/log
- derived abstractionのみ

へ流し、raw exposure / semantic leakage / fanout / task utility / deletion costを計測する。

さらにconsent withdrawal後に、raw object・abstraction・downstream copiesのrights attenuationが正しくpropagateするか確認。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常のprivacy / memory surveyは「何を保存するか」「最終出力に何を出すか」を中心にしやすい。PAPCはplatform economics / externality / topologyとして中間transitionを扱うため分類をまたぐ。

### (8) 重要度

**A** — distributed/social Kamimusuhiで個人情報・relationship dataを扱うなら、memory write時点のownershipだけでなくfanoutを評価する必要がある。

## 5.4 A — Durable Delegation Ownership Across Session-ID Rotation

**一次資料:** Hermes PR #115189  
https://github.com/NousResearch/hermes-agent/pull/115189

### (1) 何が実証済みか

PRは、reconnect/resumeでUI session idがrotationすると、still-running subagentがstatus panelから消える一方workerは走り続けるbugを修正する。修正案はspawn時のdurable `owner_session_key`、reminted UI sidへのreclaim、compression rotation時のmapping rewriteを追加し、foreign-key isolationを含むregression coverageを報告している。

### (2) 何が提案・推測段階か

- PRはopen/unmerged。
- Kamimusuhiの現在のmulti-device UI / subagent controlで同型bugが存在する証拠はない。
- `owner_session_key`という具体形がKamimusuhiの最適解とは限らず、canonical actor/task lineage IDでもよい。

### (3) Kamimusuhi関係先

- K-Deep delegation
- multi-device embodiment
- interaction surfaces
- cancellation / steer / interrupt
- task observability
- session resume / compression / migration

### (4) 借りられる設計・実装アイデア

`owner`をpresentation session IDから分離する。

```text
DelegationOwnership
  delegation_id
  durable_owner_key
  canonical_task_id
  current_surface_bindings[]
  control_capability
  spawned_at_head
  child_ids[]

SurfaceBinding
  ephemeral_session_id
  device_id
  binding_epoch
  bound_at
```

session remint時はchildをrecreateせず、**control projectionだけをrebind**する。

### (5) Kamimusuhiとの差分

actor-native identity、execution-owner binding、namespace-complete durable referencesは既収載。

今回のfresh差分は、**owner identityは維持されていても、control-plane projectionがephemeral UI handle rotationで切れる**というfailure。identity correctnessとoperability/steerabilityを別に測る。

### (6) 次に検証すべきこと

**`DelegationOwnerRebindBench-v0`**

running child中に:

- UI reconnect
- session ID remint
- context compression / episode rotation
- device A→B handoff
- parent surface closed/reopened

を注入し、list / steer / cancel / status / completion routingが同じdurable childへ到達することを検証。foreign ownerへの誤rebindは必ず0。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

identity continuityはcanonical IDの継続に注目しやすいが、これは**GUI/session handleとruntime control authorityのprojection**というcontrol-planeの問題。

### (8) 重要度

**A** — distributed embodimentを本格化する前に固定したい。走っているtaskが「見えないが生きている」状態は取消不能・ghost workにつながる。

## 5.5 A — Persona-Projection Referential Integrity

**一次資料:** Hermes PR #115294  
https://github.com/NousResearch/hermes-agent/pull/115294

### (1) 何が実証済みか

単純なglobal string replacementでidentity presentationを変換した結果、URL、filesystem path、repo slug、mailbox、quoted skill identifierまで壊れる具体的production-class bugが示され、context-aware rewriteへ変更後333 related tests passと報告されてmerge済み。

これは「prompt textが自然言語だけで構成されている」という仮定が崩れる例。system promptはproseに加え、code/resource identifiersを内包するmixed-language artifactになっている。

### (2) 何が提案・推測段階か

- regex fix自体をKamimusuhiへコピーすべきという意味ではない。
- identifier class全般を正確に判定するにはregexよりtyped prompt AST / template compilerが望ましい可能性がある。
- Kamimusuhi J系/provider adapterで現在global rewriteをしている証拠はない。

### (3) Kamimusuhi関係先

- Persona Core / J系language organ
- model/provider-specific prompt projection
- versioned personality
- self/other naming
- tool/resource references
- Library / source URL injection
- multi-model orchestration

### (4) 借りられる設計・実装アイデア

promptをflat stringとしてpost-processせず、最低限segment typeを持つ。

```text
PromptSegment =
  PersonaProse
  InstructionProse
  LiteralIdentifier
  URL
  FilePath
  ToolName
  Code
  QuotedUserText
  EvidenceQuote
```

identity/persona projectionは`PersonaProse`等、明示許可されたsegmentにだけ適用する。

もしflat stringしかないadapter境界では、rewrite前後でreferential integrity checkを行う。

```text
all(literal_ref_before == literal_ref_after)
```

### (5) Kamimusuhiとの差分

2026-09-10には `external presentation identity != canonical continuity identity` を収載済み。あちらはcredential / DID / KYA等、外部へ見せるidentityと内部continuityの分離。

今回は別物で、**presentation wordingを変える処理が同じtext artifact内のliteral referentを破壊しないこと**。言語哲学のuse/mention distinction、compiler hygiene、template typingに近い。

### (6) 次に検証すべきこと

**`PersonaProjectionReferentialIntegrityBench-v0`**

同じidentity tokenを:

- ordinary prose
- URL host/path
- filesystem path
- git repo slug
- email address
- tool name
- JSON key/value
- quoted user text
- code block
- citation/evidence text

に埋め、provider/persona projection後に**proseのみが期待通り変わり、literal refsはbyte-equivalentまたはcanonical-equivalentのまま**かを検証。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

persona / identity研究では「何を名乗るか」を扱うが、prompt compiler研究では「文字列置換でresource referentを壊すか」を扱う。両者の隙間にある実装基盤問題。

### (8) 重要度

**A** — Kamimusuhiが複数J器官・provider adapter・versioned personalityを持つほど事故面が増える。benchは非常に安価。

## 5.6 B — Endpoint-Qualified Protocol Binding

**一次資料:** Hermes PR #115401  
https://github.com/NousResearch/hermes-agent/pull/115401

### (1) 何が実証済みか

PRは、semantic providerが`minimax`でもcustom `base_url`がOpenAI-compatible relayならwire protocolは別物になり得ることをlive E2Eとparameterized testsで示す。従来はprovider-declared `anthropic_messages`をforeign relayへ持ち込み、Messages-shaped request + `x-api-key`で401またはsilent fallbackが発生した。修正案はendpoint host/pathとcatalog defaultを照合してprotocolを決める。

### (2) 何が提案・推測段階か

- PRはopen/unmerged。
- endpoint shapeからprotocolを推測する方式にも曖昧さが残り、標準的capability negotiationがあるならそちらを優先すべき。
- Kamimusuhi resource routerに同型bugがある証拠はない。

### (3) Kamimusuhi関係先

- external model router
- local LLM / OpenAI-compatible APIs
- provider adapter
- auth scheme selection
- fallback routing
- model identity / lineage

### (4) 借りられる設計・実装アイデア

ResourceDescriptorを分解する。

```text
ExternalModelEndpoint
  semantic_provider_id
  model_id
  endpoint_origin
  endpoint_path
  wire_protocol
  auth_scheme
  capability_schema
  resolution_evidence
  protocol_epoch
```

`provider_id`から`wire_protocol`/`auth_scheme`を暗黙継承しない。custom endpoint設定時はprotocol bindingを再解決し、resolution resultをtraceへ残す。

### (5) Kamimusuhiとの差分

configuration authority precedence、authenticated discovery、redirect capability attenuationは既収載。

今回の差分は「どの設定sourceが勝つか」ではなく、**semantic resource identityとtransport identityを別軸にすること**。同じmodel/providerでもrelayによってwire contractが変わる。

### (6) 次に検証すべきこと

**`EndpointQualifiedProtocolBindingBench-v0`**

- native provider endpoint
- same provider host / alternate native path
- local OpenAI-compatible relay
- corporate proxy
- scheme-less URL
- endpoint with misleading provider-like path
- redirect to different protocol/origin
- offline/no catalog state

について、protocol/auth/header/body shapeが意図通り解決されるか、secretがforeign protocolへ漏れないか測定。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

tool/model orchestrationはmodel能力・fallback・cost・latencyへ寄りやすく、**application-layer protocol identity**はadapter実装詳細として落ちやすい。

### (8) 重要度

**B** — Kamimusuhiはlocal/remote model endpointを多用するため実用価値は高いが、現時点では1プロジェクトのopen PR証拠が中心。

## 11. 結論

今回もっとも重要なblind spotは、**安全gateの前に「それは本当に実在するactionか」を解決する層が必要**という点と、**background cognitionを隠すだけではcontext由来のgoal contaminationは止まらない**という点だった。

Kamimusuhi向けに一行へ圧縮すると:

```text
resolve before authorize,
activate only the context the worker actually owns,
mediate privacy at every information move,
keep durable ownership above ephemeral session handles,
and treat identity/protocol projection as typed transforms rather than string inheritance.
```

この5つは、既存のcanonical evidence / Continuity Kernel / capability / Effect Acceptance / memory separationの思想を壊さず、むしろ**境界のさらに手前**を埋める補強として実装できる。
