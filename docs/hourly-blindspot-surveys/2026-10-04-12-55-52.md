## 1. A — Retention Utility Must Be Identifiable Under the Retrieval Policy

Primary: https://arxiv.org/abs/2610.02070

1. **実証済み**: Causal Memory Policyは、retrievalされたmemoryだけからretention utilityを推定すると、never-retrieved memoryの価値が識別不能になるretrieval-level positivity violationを示す。LongMemEvalでrequired memoriesの54%、LoCoMoで67%がunidentifiedで、CMPによりrequired/non-required discriminationがAUC 0.54→0.66。per-query utilityが同queryで0.78 AUCでもunseen queryの将来価値を予測するaggregationは得られなかった。
2. **提案・推測**: Kamimusuhiで常時randomized retrievalを使う必要はない。privacy、latency、context pollutionとのtrade-offがある。
3. **関係**: episodic/relationship/semantic memory、graceful forgetting、sleep/offline consolidation、Memory View Service、Cognitive Budget。
4. **借用案**: destructive forgetting前のutility estimateへ RETRIEVAL_EXPOSED / CENSORED_BY_POLICY / EXPERIMENTALLY_PROBED / UNIDENTIFIED を持たせる。限定exploration laneではretrieval propensityを記録する。
5. **差分**: storage-vs-use forgetting、bounded recall、retention policyは既存だが、**retrieval policy自体がretention utilityの観測可能性を決める**因果契約は弱い。
6. **次の検証**: **MemoryRetentionPositivityBench-v0 — P0/P1**。rare-but-critical memoryを含む長期corpusでgreedy/recency/learned router/small explorationを比較し、critical false-delete、identifiability、context cost、privacy exposureを測る。
7. **dailyで拾いにくい理由**: retrieval qualityとforgetting policyが別々に評価され、selection biasが両者の境界に落ちる。
8. **重要度**: **A**。

## 2. A — Human Principal Deprovisioning Must Close Relationship & Memory References

Fresh evidence: OpenClaw #164580  
https://github.com/openclaw/openclaw/issues/164580  
created 2026-10-04 07:19 JST

1. **実証済み**: issue記載のfield/source evidenceでは、一時的なexternal sign-inでpersonal user profileが生成され、後にその認証経路を無効化してもsupportedなretire/merge pathがない。残存profileにはpreferences、email alias、historical actor reference、session membershipが残る。
2. **提案・推測**: retired principalを物理削除すべきとは限らない。audit用tombstoneとfuture-active identityは分ける必要がある。
3. **関係**: Relationship Model、human principal registry、memory ownership/consent、cross-surface identity、session membership、delivery preferences。
4. **借用案**: HumanPrincipalLifecycleを ACTIVE / MERGE_PENDING / RETIRED / TOMBSTONED とし、retirement receiptへ alias transfer、relationship-memory disposition、session membership、preference ownership、historical reference policyを記録する。
5. **差分**: same-person cross-surface mergeやconsent-bound memoryは既存。fresh差分は **human principalの生成・linkだけでなく退役のclosure**。
6. **次の検証**: **PrincipalDeprovisioningClosureBench-v0 — P0/P1**。複数surface/profileをretire/mergeし、historical provenance preservation、future cross-profile retrieval=0、stale delivery=0、preference ambiguity=0を確認。
7. **dailyで拾いにくい理由**: identity研究はmerge、privacy研究はdata deletionへ寄り、identity namespace自体のretirementはIAM・relationship memory・temporal DBの間に落ちる。
8. **重要度**: **A**。

## 3. A update — Uncertain External Reconciliation Must Not Default to Irreversible Creation

Fresh evidence: Hermes Agent #132522  
https://github.com/NousResearch/hermes-agent/issues/132522  
created 2026-10-04 10:53 JST

1. **実証済み**: network incident後のadapter rebuildで、設定には既存external topic IDsが残るのに、degraded reconnect直後のsetupが新規topicを追加し、設定は旧IDsのままというdivergenceが報告された。clean restartでは既存IDsを再利用できる。
2. **提案・推測**: verification failure時に常にskipすべきとは限らない。本当にremote側で消えた場合は再作成が必要。
3. **関係**: distributed embodiment、social surface adapters、external resource registry、recovery/reconciliation、delivery routing。
4. **借用案**: ExternalResourceStateを PRESENT / ABSENT_CONFIRMED / EXISTENCE_UNKNOWN / REPLACED とする。externally visibleなcreateはABSENT_CONFIRMEDかfresh intentでのみ許可し、EXISTENCE_UNKNOWNではlocator保持とverification retry/deferへ進む。
5. **差分**: idempotency/reconciliationは既出。fresh差分は **既存resourceを確認できないことをabsenceとして扱い、不可逆なduplicate createへ進む** asymmetric failure。
6. **次の検証**: **ExternalResourceReconciliationUncertaintyBench-v0 — P0**。timeout、authorization failure、stale locator、confirmed absence、partial listingを交差し、duplicate creation、orphan messages、config/remote divergenceを測る。
7. **dailyで拾いにくい理由**: idempotency、network recovery、social resource lifecycleが別分野に分かれる。
8. **重要度**: **A update**。

## 4. A update — Shared Blocking Executors Need Saturation Admission and Worker-Failure Isolation

Fresh evidence: Hermes Agent #132546  
https://github.com/NousResearch/hermes-agent/issues/132546  
created 2026-10-04 11:40 JST

1. **実証済み**: fixed-size LONG-handler executorでworker-level deadline/saturation handlingがなく、stuck handlerがworker capacityを占有し続けると後続slow RPC全体がqueueで待つ一方、fast RPCは生存するfailure modeが報告された。
2. **提案・推測**: executor再作成やthread leakを一般解にはできない。operation classによってprocess isolationやasync deadlineが適切。
3. **関係**: K-Core/K-Deep orchestration、RPC/control plane、background jobs、observability、Organ Supervisor、degraded mode。
4. **借用案**: criticality/operation classごとのbulkhead、bounded queue、saturation fail-fast、in-flight age telemetryを持つ。caller timeoutとworker occupationを別状態にし、stuck capacityをcapacity debtとして観測する。
5. **差分**: 既存bulkheadとblocking-reclamation isolationに対し、fresh差分は **finite executor capacity自体がfailure-domain amplifierになり、caller timeoutだけではcapacityが戻らない**こと。
6. **次の検証**: **ExecutorBulkheadSaturationBench-v1 — P0/P1**。hang 1/4/全workers、slow-valid work、burst trafficを注入し、critical RPC p99、fail-fast latency、capacity recoveryを測る。
7. **dailyで拾いにくい理由**: timeoutはcall単位、bulkheadはservice単位、thread poolはruntime detailとして別々に扱われる。
8. **重要度**: **A update**。

## 5. B — Natural-Rate Memory Evaluation Must Condition on Actual Memory Need

Primary: https://arxiv.org/abs/2610.01780

1. **実証済み**: RealCompanionは10 real relationships、27,218 messages、最大120日を含む。recency windowは全probeではrequired messageを95.9%見つけるように見えるが、実際にmemoryが必要なprobeでは2.2%。natural rateではrecorded evidenceによるgainの96%がmemory不要message由来。試したdetectorはreal messagesでmemory needを識別できず、同じmessageを「memory」とlabelするだけで利用率が10〜14 points上がった。
2. **提案・推測**: 10 relationshipsを全user分布へ一般化できず、日本語対話やKamimusuhi固有taxonomyでも再検証が必要。
3. **関係**: relationship memory、episodic retrieval、social cognition、HCI、K-Edge↔K-Core routing、Cognitive Budget。
4. **借用案**: benchmarkへ自然会話base rateを入れ、memory-need detection、retrieval correctness、evidence use、不要時non-useを別metricにする。memory labelのframing effectもnegative control化。
5. **差分**: bounded recallやmemory routingは既存。fresh差分は **memoryが必要かの判定自体が難しく、benchmark framingがその判定を簡単にし得る** evaluation validity問題。
6. **次の検証**: **NaturalRateMemoryNeedBench-v0 — P1**。memory-needed/unneeded、遠距離evidence、label/no-labelを交差し、need-detection AUC、unnecessary recall、cost、relationship inferenceを測る。
7. **dailyで拾いにくい理由**: benchmark自体がmemory利用をcueするためnatural base rateが隠れる。
8. **重要度**: **B**。

## 6. B update — Property Evidence Requires Namespace-Bound Existence Evidence

Fresh evidence: Hermes Agent #132565  
https://github.com/NousResearch/hermes-agent/issues/132565  
created 2026-10-04 12:41 JST

1. **実証済み**: system-level serviceを観測すべきdiagnosticが、別namespaceに存在しない同名unitのqueryからdefault propertyを受け取り、plausibleだが誤った値として採用するsource-level reproductionが報告された。
2. **提案・推測**: systemd固有fixだけでなく、一般にはresource existenceとproperty observationを別evidenceにする必要がある。
3. **関係**: Computational Embodiment、Organ Supervisor、observability、service-manager integration、runtime assurance。
4. **借用案**: ResourceWitnessへ namespace、canonical_id、existence、property_source、generationを持たせる。APIがdefault/synthetic valueを返し得る場合はexistence witnessを別途要求する。
5. **差分**: namespace-qualified embodiment identityやcapability evidenceは既出。fresh差分は **API success + plausible property valueでもentity existenceの証明にはならない**こと。
6. **次の検証**: **ScopedExistenceEvidenceBench-v0 — P1**。service namespace、cgroup、device alias、container namespace、missing process defaultsを横断する。
7. **dailyで拾いにくい理由**: observabilityは値、identityは名前解決を別々に見るため、synthetic/default property trapが境界に落ちる。
8. **重要度**: **B update**。

## 7. B update — Missing Supply-Chain Metadata Is UNKNOWN, Not Evidence of Policy Violation

Fresh evidence: Hermes Agent #132558  
https://github.com/NousResearch/hermes-agent/issues/132558  
created 2026-10-04 12:20 JST

1. **実証済み**: package-index metadataでupload timeが欠けるmirrorに対し、age-based admission policyがmissing timestampを「新しすぎる」側へ倒し、実際には古いexact-pinned dependencyまでresolution不能にするreproductionが報告された。
2. **提案・推測**: metadata欠落を常にallowすべきではない。UNKNOWNとKNOWN_NEWを分離し、exact pin、digest、trusted sourceなど追加evidenceで解決すべき。
3. **関係**: Software Body update、reproducibility、dependency provenance、offline/region-constrained deployment、maintenance liveness。
4. **借用案**: package admissionに provenance completenessを持たせ、publish_time=UNKNOWNをnewへ写像しない。policy assumptionには機械的conformance testを置く。
5. **差分**: Observation Omission Provenanceはsensor/tool側。fresh差分は **software supply-chain metadata absenceを悪性事実へ変換すると、計算身体の再構築不能につながる**点。
6. **次の検証**: **SupplyChainMetadataUnknownBench-v0 — P1/P2**。missing timestamp、mirror lag、exact pin、digest present/absentを交差し、unsafe allowとfalse blockを測る。
7. **dailyで拾いにくい理由**: agent runtimeとbuild/reproducibility toolingが別分野に分かれる。
8. **重要度**: **B update**。

## 結論

今回の中心は **「見えていない」を「価値がない / 存在しない / 新しい / 消してよい」へ変換しないこと**。

retrievalされないmemoryは低utilityとは限らず、使わなくなったhuman principalも参照閉包が終わったとは限らず、degraded networkでremote resourceを確認できないことはabsenceではない。worker capacity、resource property、package metadataも同様に、unknown / unobserved / censoredをfirst-class stateとして残すことがKamimusuhiの長寿命性に重要である。
