3. **関係するKamimusuhiサブシステム**：Episodic Memory / Cognitive Budget / retrieval-source admission / observability。
4. **借りられる設計・実装アイデア**：indexed corpus集合をruntime capabilityとして公開し、未index源は初手で型付き`NOT_INDEXED`を返す。重いcatch-upは背景ジョブへ切り離し、問い合わせの15秒予算を尊重。
5. **Kamimusuhiとの差分**：前回のEmbedding障害によるFTS-only degradationとは異なり、**embeddingに到達する前のデータ源初期化と可用性宣言**の不整合。
6. **次に検証すべきこと**：`MemoryCorpusReadinessAndBudgetBench`：未index/partial/fullの各状態でTool schema、失敗診断、CPU/IO予算、index task重複起動を比較。
7. **既存デイリーで拾いにくい理由**：認知記憶ではなく検索DBのsource completeness・index運用SLOの問題。
8. **重要度**：**A**。将来の不変条件・運用健全性の有力候補。

### F09【A】更新プロセスをkillしても子孫のgit pack writerが残り、ストレージ・OSを枯渇

- **一次資料・初出**：Hermes #144439、2026-10-25 20:31 JST。https://github.com/NousResearch/hermes-agent/issues/144439
1. **何が実証済みか**：macOSでupdaterのkill対象が単一PIDで、`git-remote-https`、`index-pack`など孫が残ると報告。実機では`.git`45.6GiB・一時pack多数、macOS panicまで発展した相関事例と、親kill後の孫生存を確認するshell再現を提示。
2. **何が提案・推測か**：kernel panicの直接原因は因果分離済みでない。すべてのmacOS更新で同問題が出るとは限らない。
3. **関係するKamimusuhiサブシステム**：Software Body / autonomic maintenance / energy/storage budget / failure containment。
4. **借りられる設計・実装アイデア**：OSごとのプロセスgroup/Job Object/cgroupで**副作用を持つ子孫を単位として所有**。updateキャンセル後はwriter静止確認と残留artifact掃除を分けて扱う。
5. **Kamimusuhiとの差分**：既報の旧agent workerが書込権限を持ち続ける問題からの差分は、**Gitの補助子プロセスがowner終了後も生成物を書き続ける**保守系固有の現象。
6. **次に検証すべきこと**：`UpdaterProcessTreeCustodyBench`：spawn treeをcancel/timeout/owner crashし、孫が新規ファイルを書けないことと正常時完了までの資源を確認。
7. **既存デイリーで拾いにくい理由**：OS job control・Git内部helperと人工認知個体のライフサイクル保守の交差領域。
8. **重要度**：**A**。将来の不変条件・運用健全性の有力候補。

### F10【A】要約fallbackで元モデル専用harnessが残り、代替モデルを実行できない

- **一次資料・初出**：OpenClaw #183273、2026-10-25 14:10 JST。https://github.com/openclaw/openclaw/issues/183273
1. **何が実証済みか**：native harness付きprimaryが認証失敗した際、compaction fallbackが別provider/modelへ切替を試みても`agentHarnessId`をprimaryのまま継承し、fallbackが拒否される。報告者はcredential不要のsynthetic-provider回帰でreproduce。
2. **何が提案・推測か**：長期会話での一般的な発生率や修正済みリリースは未確認。代替モデルへの自由な切替が常に安全とは限らない。
3. **関係するKamimusuhiサブシステム**：Cognitive Action Router / Sleep-compaction / Organ Registry。
4. **借りられる設計・実装アイデア**：modelだけでなくruntime/harness/auth adapterの互換性tupleを検証してからfallbackを確定。session lock policyとcompaction-only routeを分ける。
5. **Kamimusuhiとの差分**：既報のfallback wire-format欠落に対し、こちらは**fallbackに保持されたnative harness拘束の残留**が破綻点。
6. **次に検証すべきこと**：`CompactionFallbackRuntimeCompatibilityBench`：primary harness-specific→secondary generic routeのケースで、契約適合とcontinuity維持をチェック。
7. **既存デイリーで拾いにくい理由**：モデル比較の多くは推論結果のみ評価し、要約パスの実行器選択を検証しない。
8. **重要度**：**A**。将来の不変条件・運用健全性の有力候補。

### F11【A】background操作の承認待ちが通知器の消滅後に発生し『回答不可能な待ち状態』になる

- **一次資料・初出**：Hermes #144440、2026-10-25 20:32 JST。https://github.com/NousResearch/hermes-agent/issues/144440
1. **何が実証済みか**：ゲートウェイが承認通知callbackをターン開始時に登録・終了時に解除し、turn終了後も生存するterminal background処理が承認を要求すると`pending_approval`になるがカードが送信されないと報告。危険コマンド自体は実行されていない。
2. **何が提案・推測か**：報告者ログ3例とソース解析。全種のadapterに必ず生じるという推測は避ける。
3. **関係するKamimusuhiサブシステム**：Human Oversight / Mutation Gate / Task Ledger / sociality。
4. **借りられる設計・実装アイデア**：`PENDING_APPROVAL`へ遷移する条件を`reachable_approver`証拠へ束縛。ターン寿命と異なるsession通知器または明示不能状態へfail closed。
5. **Kamimusuhiとの差分**：従来の承認可達性問題への**新しい実装差分**は、ターン終了後のbackground effectのcallback所有権寿命。
6. **次に検証すべきこと**：`PostTurnApprovalReachabilityBench`：turn終了→background承認要求でcard配送有無と期限切れ状態遷移をassert。
7. **既存デイリーで拾いにくい理由**：組織の承認ワークフローと非同期call lifecycleの組合せが通常のエージェント評価から抜ける。
8. **重要度**：**A**。将来の不変条件・運用健全性の有力候補。

### F12【B】会話履歴の構造検証失敗が特定スレッドだけ再開不能にする

### F13【B】非同期Toolの生ログが最終返答後に一般会話へ表示される
