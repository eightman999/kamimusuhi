## 6.1 A+ — Admission Verdict Epoch: artifact が同じでも安全判定 cache は policy epoch を跨げない

**Primary implementation:** NousResearch/hermes-agent PR #108811, *fix(plugin-guard): require confirmation for ambiguous JS capability references*  
Merged: **2026-09-15 06:49:25 JST**  
https://github.com/NousResearch/hermes-agent/pull/108811  
https://github.com/NousResearch/hermes-agent/commit/7d7ba4ba35f15bf78f5e4daad583adf036ef61ce

### (1) 何が実証済みか

Hermes の plugin scanner では、共有 text rule が JavaScript/TypeScript UI コード中の `dig` / `host` template や `authorized_keys` という表示文言まで critical と解釈し、RSS / SSH plugin の実際の catalog install を hard-block していた。

修正では JS/TS に限り、この2種の **単独では意図を確定できない capability reference** を `high/caution` に落とし、silent allow ではなく **明示 confirmation を要求**する。一方で:

- shell の DNS exfil payload
- documentation 上の SSH backdoor instruction
- JS が literal private-key path を読んだ後 DNS に埋め込むケース

は hard dangerous のまま残り、`--force` でも bypass できない回帰テストが追加された。

さらに scanner version を進め、**古い scanner version で cache された verdict を再scan**させている。follow-up test では version を特定の `v2` に固定するのではなく、「v1より先である」契約へ変更し、rule change ごとの将来 bump を許している。

### (2) 何が提案・推測段階か

Kamimusuhi で skill/tool/model artifact の admission receipt を scanner/policy epoch と結びつける部分は本 survey の提案。

特に:

```text
sha256(artifact) が同一
!=
ALLOW / CONFIRM / DENY の意味が将来も同じ
```

とする。

### (3) Kamimusuhi の関係 subsystem / 設計課題

- Effect Acceptance / runtime assurance
- tool / skill / plugin / model / policy artifact admission
- K-Edge / K-Core の executable extension loading
- long-lived agent maintenance / upgrade
- capability security
- provenance / audit receipt

### (4) 借りられる設計・実装アイデア

候補:

```text
AdmissionVerdictReceipt {
  artifact_digest,
  scanner_id,
  scanner_policy_epoch,
  execution_context_class,
  findings_digest,
  disposition: ALLOW | CONFIRM | DENY,
  confirmation_scope?,
  confirmer?,
  evaluated_at
}
```

再利用キーを `artifact_digest` 単独にしない。scanner / policy epoch が変われば原則再評価する。

また binary verdict に潰さず:

- `ALLOW` — 十分に低risk
- `CONFIRM` — ambiguity が残るため人間判断が必要
- `DENY` — high-confidence hard block、confirmationでも overrideしない

を分ける。

### (5) Kamimusuhi との差分

Hermes は plugin static scanner の具体的 policy。Kamimusuhi は tool/skill/model/policy/organ の activation や Effect Acceptance まで含む。

したがって文字列ルールや JS 特例をそのまま移植するのではなく、**verdict provenance + policy epoch + contextual disposition** だけを借りる。

既出の `dynamic capability freshness` とも別である。前者は「今どの capability が存在するか」、今回は **「その capability を許した安全判断がまだ有効か」**を扱う。

### (6) 次に検証すべきこと

**`AdmissionVerdictEpochBench-v0`**

- 同一 plugin/skill bytes を scanner v1 → v2 → v3 で評価
- v1 cached `ALLOW` が存在する状態で policy update
- benign ambiguous JS reference → `CONFIRM`
- credential read + exfil chain → `DENY`
- `force=true` でも hard deny は通らない
- confirmation は artifact digest + policy epoch + narrow scope に bound
- policy update 後の stale confirmation reuse を拒否

測定:

- stale-verdict reuse rate
- false allow / false hard-deny
- human confirmation burden
- rescan cost
- cache hit rate

### (7) 既存 daily ではなぜ拾いにくいか

通常は「static-analysis false positive を直した plugin bug」に見える。Kamimusuhi の分類では tool safety / capability security に入り得るが、**安全判定 cache 自身の versioning** は capability freshness や Effect Acceptance の shadow に隠れやすい。

### (8) 重要度

**A+** — 長寿命 agent では policy が artifact より速く変わる。古い `ALLOW` を永続事実のように扱うと、更新した安全境界が実際の runtime に反映されない。

## 6.2 A+ — Control-Plane Operation Isolation: renderer は会話を偽造せず explicit operation を進める

**Primary implementation:** NousResearch/hermes-agent PR #110574, *Desktop connect runs on the connection operation: one card, no link to the model, no renderer polling*  
Merged: **2026-09-15 04:11:19 JST**  
https://github.com/NousResearch/hermes-agent/pull/110574

### (1) 何が実証済みか

旧 Hermes connector flow では、接続 link が model に返り、model が `wait` を呼び、renderer も2秒 pollingし、さらに hidden composer message が user の代わりに model の `wait` を開始していた。PR記載では2 targetで約 **3 Composio calls/sec** に達する重複 loop があった。

新 flow では:

- backend が1つの `ConnectionOperation` を持つ
- target state / deadline / settle reason を operation が所有
- backend watcher が gateway をまとめて監視
- renderer は operation update を表示する
- tool turn は operation settle まで blocking
- model には bearer/connect URL を返さず、settled outcome のみ返す
- `Not now` 等の UI action は hidden chat message を生成しない
- state transition は actor (`user | renderer_flow | backend_watcher | clock`) ごとの許可表を通る
- **renderer は `connected` を自称できず、backend watcher のみが外部接続成功を確定**できる

という設計へ移った。

### (2) 何が提案・推測段階か

Kamimusuhi の UI / approval / connector / device-control surface 全般を explicit control operation に統一する部分は提案。

中心原則は:

```text
UI action
!= user utterance

workflow progress event
!= conversational cognition

renderer displays external state
!= renderer owns truth of that state
```

### (3) Kamimusuhi の関係 subsystem / 設計課題

- multi-surface HCI
- Cognitive Action Router
- tool / connector orchestration
- ParticipationEnvelope / authorship
- PendingHumanDecision
- result delivery
- external credential / bearer-token containment
- canonical evidence / transcript integrity

### (4) 借りられる設計・実装アイデア

```text
ControlOperation {
  operation_id,
  kind,
  principal,
  targets[],
  state,
  revision,
  deadline_at,
  allowed_actor_transitions,
  settle_reason,
  conversation_visibility
}
```

重要なのは、surface の click / reconnect / retry を **typed control event** として扱い、「user がそう発話した」ことにしないこと。

また secrets / OAuth URL / transient credentials は、認知 model が必要としないなら control plane 内に留め、model へ exposure しない。

### (5) Kamimusuhi との差分

Hermes の対象は connector UI。Kamimusuhi では approval、sensor pairing、device migration、credential setup、actuator grant、human clarification などへ一般化できる。

直前 daily の `PendingHumanDecision` は「人間返答待ちを durable obligation にする」もの。今回はさらに **その obligation を進める UI/control state を conversation transcript へ偽装しない**という差分。

### (6) 次に検証すべきこと

**`ControlPlaneOperationIsolationBench-v0`**

シナリオ:

- desktop / TUI / phone で connector or approval operation を開始
- skip / retry / continue / navigate away / reconnect
- user surface と backend watcher の update を競合
- late snapshot / reordered update を注入

確認:

- hidden/synthetic user message = 0
- duplicate polling / duplicate side-effect = 0
- model exposure が不要な bearer link = 0
- actor table 外 transition = 0
- settled operation が late snapshot で復活しない
- revision により out-of-order update を reject
- transcript は genuine utterance と typed control event を区別できる

### (7) 既存 daily ではなぜ拾いにくいか

見た目は「connector card の UX / polling 最適化」。しかし実際には **誰が何をしたか**、**model が何を見たか**、**external success を誰が確定できるか**という agency/provenance contract を含む。HCI と distributed state machine の境界にあり、通常の agent survey では落ちやすい。

### (8) 重要度

**A+** — Kamimusuhi の identity continuity は transcript の意味論にも依存する。hidden UI automation を user turn に偽装すると、将来の autobiography / relationship memory / authorization audit まで汚染する。

## 6.3 A — Immediate Failure Ownership: optional failure policy は task spawn と同時に付ける

**Primary implementation:** letta-ai/letta-code PR #4443, *fix(tui): handle secrets rejection during startup*  
Merged: **2026-09-15 06:47:27 JST**  
https://github.com/letta-ai/letta-code/pull/4443

**Runtime semantics:** Node.js Process documentation, `unhandledRejection`  
https://nodejs.org/api/process.html

### (1) 何が実証済みか

Letta Code の startup は secrets fetch と他の初期化を並列化しており、secrets access は失敗しても TUI startup を妨げない設計だった。しかし nonfatal rejection handler が **他の startup work の後**に付いていたため、`/secrets` が先に即時404すると Node が unhandled rejection として process を exit させた。

修正は、Promise を開始した時点で nonfatal handler を付け、並列性と後段の synchronization は維持する。

回帰テストは実 TUI PTY + mock API で、secrets request を即404、message-history request を pending にして race を再現する。修正前の built Node CLI は code 1 で終了、修正後は Bun source / built Node とも process が生き、pending-approval startup まで到達した。

Node.js docs でも、Promise が reject されて **event-loop 1 turn 内に handler がない**場合 `unhandledRejection` が発生し、現在の default behavior では条件により process termination へ至り得る。

### (2) 何が提案・推測段階か

Kamimusuhi の background / organ startup へ `SpawnContract` を導入するのは提案。

```text
failure is allowed
!=
we can attach the failure policy later
```

### (3) Kamimusuhi の関係 subsystem / 設計課題

- K-Edge / K-Core organ startup
- background cognition
- optional external model / secret store / telemetry / index service
- degraded mode
- Organ Supervisor
- async runtime / actor/future/task orchestration

### (4) 借りられる設計・実装アイデア

```text
SpawnContract {
  task_id,
  owner,
  criticality,
  failure_policy: FATAL | DEGRADE | RETRY | IGNORE_WITH_EVIDENCE,
  timeout,
  cancellation_scope,
  fallback,
  attach_time
}
```

task/future を spawn した直後から failure ownership を持たせる。`DEGRADE` の意味は「例外を捨てる」ではなく、explicit degraded-state evidence を残し、上位へ capability loss を伝えること。

### (5) Kamimusuhi との差分

Letta は Node/Bun TUI startup の Promise timing bug。Kamimusuhi は複数runtime/複数nodeの organ lifecycle を扱う。

既出の microreboot / failure suspicion は「動作中 component が壊れたらどうするか」。今回は **component が spawn された瞬間から最初の failure までの時間窓を誰が所有するか**という別境界。

### (6) 次に検証すべきこと

**`FastFailureStartupRaceBench-v0`**

- optional service が synchronous/0ms/1ms/10ms で失敗
- required service が slow / pending
- handler registration を意図的に遅延させる mutant
- retryable / nonretryable / fatal service を混在

測定:

- whole-process death
- unhandled failure count
- degraded-mode entry latency
- leaked task / zombie future
- correct critical service fail-closed rate
- failure evidence completeness

### (7) 既存 daily ではなぜ拾いにくいか

「Promise の `.catch()` を早く付けた」という言語ランタイムの小さな bug に見える。通常の failure detector / fault tolerance survey は steady-state 故障を扱いやすく、**spawn-to-handler の micro-temporal race** は拾いにくい。

### (8) 重要度

**A** — Kamimusuhi が optional organ を増やすほど、非critical component 1個の早すぎる失敗で全個体が落ちる事故は現実的になる。

## 6.4 A- — Namespace-Complete Durable References: live state の暗黙scopeに依存しない

**Primary implementation:** letta-ai/letta-code PR #4440, *fix(tools): include Conversation ID in background Task return*  
Merged: **2026-09-15 04:15:52 JST**  
https://github.com/letta-ai/letta-code/pull/4440

**Reference model:** Akka — Actor References, Paths and Addresses  
https://doc.akka.io/libraries/akka-core/current/general/addressing.html

### (1) 何が実証済みか

Letta Code の background `Task` return は `Task ID / Agent ID / Output file` を含み、web chat の inline subagent card が page reload 後や live snapshot 消失後も subagent へ link するために使っていた。

しかし `Agent ID` はあっても `Conversation ID` がなく、live snapshot が消えると consumer は `conversation=default` へ fallback し、**non-default conversation で動いた subagent の wrong thread** を開いた。修正は同じ linked snapshot から `Conversation ID` を durable return に追加する。

Akka でも actor path は address + hierarchy を含む一方、同じ path に actor を再生成しても新しい incarnation であり、古い `ActorRef` は新しい actor を意味しない、と明示される。

### (2) 何が提案・推測段階か

Kamimusuhi の durable reference を scope-complete typed address にする部分は提案。

```text
object_id is known
!=
object is durably resolvable to the same semantic instance
```

### (3) Kamimusuhi の関係 subsystem / 設計課題

- background task / subagent / cognitive organ
- conversation / episode / run / relationship scope
- result delivery / UI deep link
- distributed embodiment / migration
- observability / provenance
- restore / replay

### (4) 借りられる設計・実装アイデア

object 種類ごとに必要 scope を型へ含める。

```text
CognitiveObjectRef {
  principal_or_profile_id,
  agent_or_organ_id,
  conversation_id?,
  episode_or_run_id?,
  object_id,
  incarnation_or_generation?
}
```

persistent reference で `default` scope を暗黙補完しない。missing scope は `UNKNOWN/UNRESOLVABLE` として fail closed / ask caller to re-resolve する。

### (5) Kamimusuhi との差分

Letta は web card deep-link の参照 bug。Kamimusuhi は canonical history、multiple surfaces、organ restart、intentional migration を含むため、単なる URL 修正ではなく **referential integrity across time** の問題になる。

既出の causal provenance / ParticipationEnvelope は「誰が生んだか」を扱う。今回は **後で同じ対象を指せるか**であり別軸。

### (6) 次に検証すべきこと

**`ScopedReferenceSurvivalBench-v0`**

- non-default conversation で background task/subagent を生成
- live snapshot/cache を削除
- UI reload / process restart / device migration
-同一 logical name で新 incarnation を生成
- durable receipt から対象を再解決

成功条件:

- original conversation / run / incarnation へ正しく到達
- stale incarnation を新 actor と誤同一視しない
- missing scope を `default` で勝手に補わない
- canonical evidence link も同一 target を保持

### (7) 既存 daily ではなぜ拾いにくいか

frontend deep-link / serialization の小bugとして処理されやすい。だが長寿命 distributed cognition では、live state に隠れていた namespace が restart 後に消えるため、**reference durability** は identity continuity の下位基盤になる。

### (8) 重要度

**A-** — 今すぐ Persona Core を変える finding ではないが、multi-surface / migration / background cognition が増えると確実に効く。

3. async task / organ lifecycle で、**failure policy は spawn と同時またはそれ以前に ownership が確立される**。
4. durable external/internal reference は、restart 後に同一 semantic object を再解決するのに必要な scope/generation を失わない。

## 11. 本回の短い結論

今回の重要点は、Kamimusuhi の長寿命性を守る対象が「memory / identity / capability 本体」だけではなく、**それを許可した verdict、UIが進める operation、spawnした task の failure ownership、後で対象を指し直す reference** にまで広がること。

特に次の2本はすぐ bench 化する価値が高い。

```text
artifact unchanged
!= safety judgment unchanged

UI progressed a workflow
!= user said something
```

この2境界を explicit にすると、policy update 後の stale allow、hidden synthetic user turn、credential exposure、audit transcript 汚染を同じ control-artifact layer でかなり機械的に潰せる可能性がある。
