### 3.1 A — Shared Mutable Cache Non-Interference

Fresh evidence:
- Hermes Agent #125007: https://github.com/NousResearch/hermes-agent/issues/125007
- Fix PR #125008: https://github.com/NousResearch/hermes-agent/pull/125008

1. **何が実証済みか**  
   MoA runtime cache が resolved runtime object を複数callで共有し、あるcallerのrequest-local mutationによってcache本体が変化し、同じentryを使う後続callのeffective requestまで変わるreproductionが報告された。PR #125008はcaller-owned copyを返す修正とregression testを追加し、修正前に再現、修正後に関連test群が通ると報告している。

2. **何が提案・推測段階か**  
   全cacheをdeep copyに統一する必要はない。immutable value object、copy-on-write、structural sharingでもよい。必要なのはcanonical cached stateとcaller-owned working stateの分離。

3. **関係subsystem**  
   Cognitive Resource Registry、provider/model routing、K-Core/K-Deep orchestration、runtime policy、long-lived processのbehavior stability。

4. **借りられる設計・実装アイデア**  
   cached runtime/config/policy objectはimmutable snapshotとして公開する。mutable APIが必要ならcaller-owned copyを返す。cache valueにrevision/digestを持たせ、同一input+revision間のunexpected driftを観測する。

5. **Kamimusuhiとの差分**  
   configuration authority precedence、runtime identity、policy epochは既出だが、object aliasingにより一度の局所処理が未来のturnや別consumerの挙動までrewriteするshared-mutable-state failureは独立収載されていない。

6. **次に検証すべきこと**  
   **`SharedRuntimeCacheIsolationBench-v0` — P0**。複数consumerが同じcache entryを共有する状況でrequest-local mutationを交互に注入し、canonical digest不変、consumer間leakage=0、concurrency下のrevision driftなしを要求する。

7. **既存dailyではなぜ拾いにくいか**  
   model routing surveyではprovider/model選択を見るが、cache object ownershipは実装詳細に見える。長寿命agentでは数turn後だけbehavior driftが出るため単発評価でも見落としやすい。

8. **重要度**: **A**

**Invariant候補:** `cached canonical runtime state SHALL NOT be caller-mutable by alias`

### 3.2 A update — Lifecycle-State Currentness Over Creation-Time Ordering

Fresh evidence:
- Hermes Agent #125001: https://github.com/NousResearch/hermes-agent/issues/125001
- Fix PR #125002: https://github.com/NousResearch/hermes-agent/pull/125002

1. **何が実証済みか**  
   routing keyごとに「最も新しく作られたsession row」を選んでからactive判定する実装では、古いsessionをresumeした後も新しい終了済みrowが選ばれ、live mappingが消える/誤るreproductionが報告された。PR #125002はlive rowを優先するqueryへ修正し、修正前に失敗するregression testを示した。

2. **何が提案・推測段階か**  
   live-firstが全temporal queryの正解ではない。history/auditではevent timeやtransaction timeが必要。current routing viewと履歴queryを分けるべきという話。

3. **関係subsystem**  
   DialogueSession、routing directory、temporal DB、current embodiment/session projection、continuity view。

4. **借りられる設計・実装アイデア**  
   creation timestampからcurrentnessを推論しない。current pointer / lifecycle state / generation / activation receiptをfirst-classにし、履歴順序と現在有効性を別queryにする。

5. **Kamimusuhiとの差分**  
   late-bound currentness、generation fencing、bitemporal reconciliationは既出。今回の差分は、古く作られたobjectがresumeにより正当にcurrentへ戻るとcreation-time orderとcurrentnessが逆転することを実DB queryのred/green fixで具体化した点。

6. **次に検証すべきこと**  
   **`LifecycleCurrentnessProjectionBench-v0` — P0/P1**。old A active → new B active → B end → A reopen、同時刻tie、migration/handoff、crash recoveryを作り、current viewとhistory viewを別々に検証する。

7. **既存dailyではなぜ拾いにくいか**  
   temporal DBでは「最新row」を時刻で選ぶのが自然に見えるが、identity continuityではresume/reactivationがあるため、時間順序と現在性が別関係になる。

8. **重要度**: **A update**

**更新原則:** `latest-created object != currently-authoritative object`

### 3.3 A update — Recovery-Fallback Continuity Fencing

Fresh evidence:
- OpenClaw #159531: https://github.com/openclaw/openclaw/issues/159531

1. **何が実証済みか**  
   long-lived requester sessionへのchild completion handoffでwriter-claim conflictが起きた後、fallback deliveryが同じrouting keyに新しい空transcriptを作り、completion turnをそこへ配送したfield reportがある。old transcriptは残るがrequesterは新sessionを向き、explicit resetなしで作業文脈を失った。logsとbefore/after session metadataが提示されている。

2. **何が提案・推測段階か**  
   recovery時のsession rotationを絶対禁止するものではない。corruptionやexplicit resetでは新generationが必要なこともある。ただしcontinuity-changing recoveryは暗黙fallbackではなくexplicit transitionであるべき。

3. **関係subsystem**  
   DialogueSession、Continuity Kernel、subagent completion handoff、active-turn recovery、transcript writer ownership。

4. **借りられる設計・実装アイデア**  
   delivery/retry/fallbackにexpected session identityとexpected generationをfenceとして持たせる。target continuityを維持できなければretry/quarantine/typed failure。新transcriptへ移行するならtransition reason、source lineage、carried context receiptを必須にする。

5. **Kamimusuhiとの差分**  
   in-flight continuation、continuity durability、active-turn recovery dependency、handoff authorityは既出。fresh差分はdelivery fallbackがtransport-level workaroundに見えながら、実際にはsession continuity mutationになったこと。

6. **次に検証すべきこと**  
   **`RecoveryFallbackContinuityFenceBench-v0` — P0**。writer claim change、target generation change、wake failure、fallback deliveryをfault-injectionし、implicit rotate=0、explicit rotateではreason/lineage/context receiptを要求する。

7. **既存dailyではなぜ拾いにくいか**  
   child completionはorchestrationの配送問題に見えるが、fallback targetがsession identityを所有するとcontinuity mutationに変わる。

8. **重要度**: **A update**

**更新原則:** `delivery fallback SHALL NOT silently become an identity/session transition`

### 3.4 A update — Off-Turn Principal Context Transport

Fresh evidence:
- Hermes Agent #125032: https://github.com/NousResearch/hermes-agent/issues/125032
- Fix PR #125038: https://github.com/NousResearch/hermes-agent/pull/125038

1. **何が実証済みか**  
   multiplex gatewayのbackground reviewで、deterministic halfはprofile scope内なのに、LLM halfがraw threadへ移った時点でcaller contextを継承せず、profile-specific execution scopeを失うreproductionが報告された。その結果default側artifactを参照・更新し得る状態になった。PR #125038はcaller contextを明示搬送し、修正前後のscope behaviorをtestで確認している。

2. **何が提案・推測段階か**  
   language runtimeのcontext機構をcontinuity identityの唯一のcarrierにする必要はない。durable jobではexplicit execution envelopeの方が適切な場合がある。

3. **関係subsystem**  
   K-Core background cognition、Sleep/Dream/Curator相当、multi-principal runtime、executor/thread work、maintenance cognition isolation。

4. **借りられる設計・実装アイデア**  
   off-turn work spawn APIを集約し、principal / individual_id / execution home / capability set / policy revision / causal parentをexplicit ExecutionContextとして渡す。scope不明時のglobal fallbackを禁止する。

5. **Kamimusuhiとの差分**  
   async causal principal propagationとexecutor context transportは既出。今回はscope lossが単なるlookup errorではなく、別scopeのstate read/writeへ到達するred/green evidenceが追加された更新。

6. **次に検証すべきこと**  
   **`OffTurnExecutionContextCoverageBench-v1` — P0**。thread/executor/async task/callback/timer/cron/reconnect hookを横断し、owner一致、cross-scope read/write=0、missing context fail-closedを確認する。

7. **既存dailyではなぜ拾いにくいか**  
   concurrency implementationの話に見えるが、長寿命分散agentではbackground cognitionが別identityのstateへ触れるprincipal-confusion bugになる。

8. **重要度**: **A update**

### 3.5 B update — Resource-Centric Classification Parity

- Hermes Agent #124999: https://github.com/NousResearch/hermes-agent/issues/124999
- Fix PR #125000: https://github.com/NousResearch/hermes-agent/pull/125000

1. **何が実証済みか**

2. **何が提案・推測段階か**

3. **関係subsystem**  
   privacy-preserving tooling、Library/file access、information-flow policy、tool observation projection。
4. **借りられる設計・実装アイデア**  
   ResourceClassをread/write/export/logの共通authorityとし、resource classとparser/decoder typeを分離する。
5. **Kamimusuhiとの差分**  
   persistent information-flow policyは既出。fresh差分はoperation間でclassification tableがdriftする具体的failure。
6. **次に検証すべきこと**  
   **`ResourceClassificationParityBench-v0` — P1**。複数representationを各tool surfaceへ通し、classification mismatch=0、decoder failure時のunsafe passthrough=0を確認する。
7. **既存dailyではなぜ拾いにくいか**  
   toolごとのsecurity reviewではresource分類の横断整合性が落ちる。

## 10. 今回の結論

今回もっとも新しい blind spot は **shared mutable cache**。長寿命agentでruntime configurationをcacheするのは自然だが、そのcache objectをconsumerが直接変更できると、一度の局所処理が未来のturn・別organ・別roleの挙動までsilently rewriteする。canonical memory mutationとは別に、**runtime cognitive policyがhidden mutable stateになる**問題である。

同時に、currentnessとcontinuity transitionの明示化も重要。古いsessionでもresumeされればcurrentになり得る。recovery fallbackが新しいsessionを作るなら、それは配送上の小変更ではなくcontinuity transition。background workがscopeを失えば別principalのstateを触り得る。

Kamimusuhiでは runtime cache / session currentness / recovery fallback / off-turn execution を **owner・generation・revision・immutability** の共通語彙で閉じる価値が高い。
