## 2. 今回狙った盲点

今回は、通常の AI agent / memory / ALife survey では「ただのネットワーク再試行」「DB運用」「CLI既定値」「メトリクス形式」に見えて落ちやすい次の境界を狙った。

1. **in-flight continuation liveness** — control-plane / WebSocket が落ちた時、接続復旧と「途中の認知runが継続したこと」を同一視していないか。
2. **post-commit durability / visibility** — canonical commit が成功しても、host failure domain を越えて残るか、別surfaceから直後に読めるか。
3. **execution placement as authority** — 保存先deviceがofflineだからといって、cloud等の別substrateへ暗黙移行してよいか。
4. **resource-accounting semantics** — Cognitive Budget を「上限」だけでなく、長寿命runで実際に何を何回再送・委譲・消費したかとして比較可能にできるか。
5. **日本語圏 discovery** — Zenn / note / Qiita の直近 long-running agent / restart / memory sync / observability に独立した新規 contract があるか。

今回の結論は **有意な新規発見あり**。特に重要なのは、distributed continuity において、

```text
connection recovered
!= in-flight run recovered

canonical commit acknowledged
!= failure-domain durable
!= every embodiment can immediately observe it

preferred device unavailable
!= migration to another substrate authorized
```

を別契約として扱うこと。

# 5. 候補ごとの評価

## 5.1 A+ — Layered In-Flight Continuation Liveness

**Primary fresh evidence:** Letta Code #4401  
https://github.com/letta-ai/letta-code/pull/4401

### (1) 何が実証済みか

Letta Code の cloud-api restart E2E では、listener が LLM step の途中で WebSocket を失った際、従来は `drainStreamWithResume` が default の **1回・遅延なし**再開だけを試した。

PR に記録された failure trace では、socket close 後約5msで resume を1回試し、cloud-api がまだ停止中のため約32ms後に失敗。その後 listener 自体は数秒後に新しい cloud-api へ再接続したにもかかわらず、active run は失われて `WAITING_ON_INPUT` となり、**turn が途中で放棄**された。

修正では listener 用に `initialDelayMs=500`, `maxAttempts=60`, `maxDelayMs=5000` の resume policy を設け、message-turn と approval-recovery の両方に適用した。総待機は約287.5秒で、rolling restart に加えて server-side producer heartbeat の 90秒 window を跨げるようにしている。

PR はさらに、listener-side retry だけでは run finality を解けず、paired cloud-api 側で producer heartbeat expiry 後に orphaned run を finalization する必要がある、と明記する。

つまり実装上、少なくとも以下は別である。

```text
transport connected
consumer/listener alive
stream resume cursor valid
producer still alive
run still authoritative/in-flight
run finalized
```

### (2) 何が提案・推測段階か

- Letta の5分 retry / 90秒 heartbeat が Kamimusuhi に適切という意味ではない。
- WebSocket stream を使わない runtime でも同じ具体的障害が起こるとは限らない。
- Kamimusuhi の canonical mutation はより狭い Continuity Kernel に集約されているため、run abandonment が直ちに identity corruption を意味するわけではない。

一般化して借りるべきなのは **「接続層・実行producer・run lifecycle の livenessを一つのboolへ潰さない」**こと。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- K-Core / K-Deep long-running cognition
- background cognition / asynchronous worker
- external model streaming
- approval / confirmation wait
- tool execution / result integration
- Runtime observability
- StopLifecycle / recovery
- distributed embodiment の control plane restart

### (4) 借りられる設計・実装アイデア

候補 schema:

```text
InFlightContinuationState
  continuation_id
  causal_principal
  execution_owner
  transport_state
  consumer_state
  producer_state
  run_state
  last_accepted_seq
  resume_token_or_cursor
  producer_last_heartbeat
  retry_deadline_monotonic
  finalization_authority
  effect_state
```

重要なルール候補:

```text
transport reconnected
  != run resumed

resume exhausted
  != producer definitely dead

producer suspected dead
  != external effect definitely absent

new user turn accepted
  SHOULD NOT silently erase unresolved prior-run finality
```

### (5) Kamimusuhiとの差分

既存 Kamimusuhi には:

- abort liveness
- φ accrual failure suspicion
- deterministic replay
- async causal principal
- ambiguous external outcome

がある。

しかし今回の差分は、**control-plane restart 中に進行中の cognition stream をどの cursor から、どの producer/run identity に再接続し、いつ orphan と確定するか**という中間層。`organ alive/dead` や `restore/replay` より細かい。

### (6) 次に検証すべきこと

**`ControlPlaneRestartContinuationBench`**

fault injection:

1. LLM streaming 中に router/API process restart
2. tool result の途中で transport cut
3. human approval 待ち中に listener restart
4. producer は生存 / consumerのみ死亡
5. consumer は再接続 / producerは死亡
6. duplicate frame / reordered replay frame
7. resume token stale
8. external effect outcome `UNKNOWN`

metrics:

- abandoned continuation rate
- duplicate effect rate
- wrong finalization rate

- false producer-death rate
- stale principal / wrong owner continuation rate
- unresolved run が新turnに隠される率

### (7) 既存デイリーサーベイではなぜ拾いにくいか

AI研究としては「再試行の実装バグ」にしか見えず、distributed systems では普通の stream-resume 問題に見える。しかし長寿命agentでは、**途中runが自己の継続中の認知・承認・effectを持つ**ため、単なる networking retry より continuity semantics が重い。

### (8) 重要度

**A+** — 現行 runtime で再現しやすく、既存 abort/replay/failure-detector の間にある未定義層を埋める。

## 5.2 A+ — Continuity Commit = Authority Commit × Durability × Session Visibility

**Fresh implementation evidence:** Letta Code #4336  
https://github.com/letta-ai/letta-code/pull/4336

**Classic / official references:**

- Terry et al., *Session Guarantees for Weakly Consistent Replicated Data*, PDIS 1994  
  https://doi.org/10.1109/PDIS.1994.331722
- PostgreSQL 18 WAL / synchronous replication  
  https://www.postgresql.org/docs/18/runtime-config-wal.html  
  https://www.postgresql.org/docs/current/warm-standby.html

### (1) 何が実証済みか

Kamimusuhi 自身の phase-1 store は SQLite WAL + `synchronous=FULL` を選び、local durability を correctness 優先で扱っている。一方、repository 内の comment も **WALを完全なpower-loss durabilityの主張とはしない**と明示している。

Letta #4336 は別の実務的な gap を示す。shared-memory の Git synchronizer 自体には test があったが、**completed turn の cleanup が本当に synchronizer まで到達し、remote bare repository の SHA を進めるか**という lifecycle-level E2E が無かった。追加 test は finalized listener cleanup → post-turn coordinator → attached repository discovery → real Git push を通し、remote SHA が turn-produced commit へ進むことと local checkout に unpushed commit が残らないことを確認する。production code変更ではなく、欠けていた end-to-end durability/replication gate の追加である。

分散DB側では PostgreSQL が commit acknowledgement を複数段階へ分けている。`synchronous_commit=off` は success を返した後でも直近transactionが crash で失われ得る。`local`、standby への flush を待つモード、`remote_apply` では **standbyでreplayされ query から見えるところまで**待つ。

また Terry et al. の古典は、弱整合 replica を移動して使う application に対し、

- read-your-writes
- monotonic reads
- monotonic writes
- writes-follow-reads

という per-session guarantees を定義した。

ここから Kamimusuhi に重要なのは、

```text
canonical head advanced
!= commit survives loss of current host
!= another embodiment can already read that revision
```

という三分離である。

### (2) 何が提案・推測段階か

- Kamimusuhi が PostgreSQL の sync replication や Git remote push を採用すべき、という結論ではない。
- すべての episode/event を failure-domain replicated にしてから応答する必要もない。latency / energy / offline availability と衝突する。
- 1994年の session guarantees は replicated database の概念であり、AI identity continuity への直接実証ではない。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Continuity Kernel / lineage receipt
- Canonical Evidence Store
- K-Edge ↔ K-Core cache / replica
- multi-device embodiment
- migration / failover / backup / restore
- relationship/self-state projection
- offline device rejoin
- observability / user-visible acknowledgement

### (4) 借りられる設計・実装アイデア

`LineageReceipt` / canonical commit receipt に、authority だけでなく **durability と visibility の保証水準**を明示する。

候補:

```text
ContinuityCommitReceipt
  revision
  predecessor
  authority_commit = ACCEPTED

  durability:
    LOCAL_VOLATILE
    LOCAL_DURABLE
    FAILURE_DOMAIN_REPLICATED
    MULTI_FAILURE_DOMAIN_REPLICATED

  visibility:
    AUTHORITATIVE_ONLY
    REPLICA_RECEIVED
    REPLICA_APPLIED

  acknowledged_surfaces[]
  min_visible_revision
  replication_witnesses[]
  policy_id
```

さらに各 authenticated surface は、同一個体の session 内で `minimum_seen_revision` を保持する。

```text
surface has observed revision r
→ 以後「現在の自己」として r より古い state を無警告で提示しない
```

stale K-Edge しか使えない場合は availability を優先して動いてよいが、`CURRENT_SELF` ではなく **stale/degraded projection** であることを明示する。

### (5) Kamimusuhiとの差分

`read-your-writes` という語自体は 9/10 の KMSM 評価 metric に一度現れているため、本稿はそれを「初出」と主張しない。

今回の差分は、**Bayou型 session guarantees を multi-device identity continuity の read contract として独立昇格し、local durability / replicated durability / replica visibility と統合して canonical commit receipt に接続すること**。

現行 Continuity Kernel は「どの branch/head が authoritative か」に強い。しかし **正しい head が決まった後、その head を失わないか／別surfaceが直後に古いselfを見ないか**は別問題である。

### (6) 次に検証すべきこと

**`CrossDeviceContinuityCommitBench`**

scenario:

1. K-Core で self/commitment mutation を commit
2. success acknowledgement 直後に process kill
3. OS crash 相当 / host loss 相当
4. replica propagation 前後で K-Edge へ surface switch
5. K-Edge が一度 revision `r` を見た後に古い replicaへroute
6. offline K-Edge が旧revisionで再接続
7. asynchronous / synchronous replication policyを比較

metrics:

- acknowledged-but-lost mutation rate
- read-your-writes violation
- monotonic-read violation
- stale-self response rate
- replication-induced latency
- offline availability
- false claim of `CURRENT` state

### (7) 既存デイリーサーベイではなぜ拾いにくいか

AI memory survey は「保存できたか」に寄り、continuity survey は head/fork detection に寄りやすい。DB研究では単なる consistency / durability の古典であるため、**「別deviceへ移った自分が数秒前の自分より古くならない」ことを identity invariant として読む**とき初めて Kamimusuhi へ直接効く。

### (8) 重要度

**A+** — 今後 K-Edge/K-Core を実際に分散配置する前に、`authoritative` と `durable/visible` を分けないと continuity の成功判定を誤る。

## 5.3 A — Execution Placement Intent: `offline != fallback authorized`

**Primary fresh evidence:** Letta Code #4409  
https://github.com/letta-ai/letta-code/pull/4409

### (1) 何が実証済みか

Letta #4409 は agent message の optional `computer` 指定について、CLI と `SendAgentMessage` の挙動を統一した。

- omitted / `null` / whitespace-only は **overrideなし**として扱う。
- explicit device / Cloud alias は引き続き指定可能。
- override が無ければ recipient の active computer または saved destination を使う。
- **saved computer が offline でも Cloud sandbox へ暗黙 fallback しない。**
- tests では unset `computer` が request から省略され、2 concurrent senders が各自の identity を保持することを確認している。

これは単なる `null` normalization の修正だが、設計的には重要な境界を露出している。

```text
destination unavailable
!= permission to execute elsewhere
```

### (2) 何が提案・推測段階か

- Letta が Cloud fallback をしないこと自体が universal best practice という意味ではない。
- stateless public web search 等では自動fallbackが妥当な場合もある。
- Kamimusuhi でどの organ/resource を「身体」とみなし、どこまで placement-sensitive にするかは未決定。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- K-Edge / K-Core / K-Deep distributed embodiment
- Cognitive Action Router
- external/local model delegation
- privacy / data residency
- sensor / actuator affinity
- trusted owned compute vs external other
- energy / monetary budget
- degraded-mode operation

### (4) 借りられる設計・実装アイデア

resource selection に `available=true` だけでなく **placement intent / fallback authority** を持たせる。

```text
ExecutionPlacementIntent
  preferred_target
  inherited_target?
  allowed_fallback_targets[]
  fallback_authority_ref?
  trust_boundary_max
  data_residency_scope
  sensor_affinity[]
  actuator_affinity[]
  state_locality_requirements[]
  max_added_latency
  max_added_cost
  migration_allowed
```

unavailable時の状態も:

```text
READY
PREFERRED_UNAVAILABLE
FALLBACK_REQUIRES_AUTH
DEFERRED_FOR_PLACEMENT
DEGRADED_LOCAL
```

のように区別する。

特に private memory、local-only sensor、actuator control、credential-bound task は「Cloudが空いているから移す」を禁止できるようにする。

### (5) Kamimusuhiとの差分

直近 survey には:

- capability membership freshness
- execution-owner binding
- EffectiveEnvironmentManifest
- resource health

がある。

しかし、**実行可能な別resourceが存在することと、そのresourceへ cognition/effect を移す権限があること**は同じではない。今回の差分は availability/ownership ではなく **placement migration authority**。

- local-only private evidenceを含むtask

### (7) 既存デイリーサーベイではなぜ拾いにくいか

表面上は optional CLI argument の validation bug であり、AI論文にも distributed-system theorem にも見えない。しかし distributed artificial individual では **「どこで考える／動かすか」は privacy・身体性・権限の一部**なので、fallback policy が identity-adjacent contract になる。

## 5.4 B+ watch — Agent Run Metrics / Context Amplification Accounting

**Source:** `draft-arsentev-agent-run-metrics-00`, 2026-09-10  
https://datatracker.ietf.org/doc/draft-arsentev-agent-run-metrics/

### (1) 何が実証済みか

これは実験論文ではなく **Internet-Draft**。したがって「性能が実証された」ものではない。

公開仕様は、LLM agent の1 runと constituent steps の resource consumption を vendor-neutral JSON で記述する案を具体化している。特に:

- 1 reported model step = 1 completed model invocation と定義し、streaming block や複数内部recordを invocation 多重計上しない。
- delegated child/sub-run の resource attribution を持ち、親子で **double counting しない**ためのルールを置く。
- repeated input / output / timing / cost を run 単位で集計する。
- prompt / completion content 自体を metrics format に含めない。

という点は設計済みの仕様として確認できる。

### (2) 何が提案・推測段階か

- RFC ではない。
- IETF WG consensus や interoperable implementations が確立したとはいえない。
- energy、GPU memory、network bytes、local sensor cost 等、Kamimusuhi の Cognitive Budget 全体を覆う仕様ではない。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Cognitive Budget
- K-Edge/K-Core/K-Deep routing
- observability / telemetry
- economics of long-lived AI
- energy-aware cognition
- context / memory admission
- external model delegation
- high-fanout subagent / research runs

### (4) 借りられる設計・実装アイデア

Cognitive Budget を **capacity/planning** と **realized accounting** に分ける。

```text
CognitiveBudget
  allowed / available capacity

CognitiveRunResourceReceipt
  root_run_id
  run_id
  parent_run_id?
  step_id
  invocation_id?
  input_tokens
  cached_input_tokens
  output_tokens
  latency
  monetary_cost
  local_energy_estimate?
  network_bytes?
  delegated_cost_exclusive
```

追加で Kamimusuhi 独自に、

```text
context_amplification
  = total transmitted input / newly admitted information
```

のような指標を検討する価値がある。長い history / workspace item を早い段階で入れると、その後の各 model step で繰り返し送信されるため、単発prompt長より **run全体の再送量**が重要になる。

### (5) Kamimusuhiとの差分

現行 Cognitive Budget は resident capacity、latency、energy、money、tool availability 等を **意思決定時の予算/状態**として持つ。一方、run終了後に vendor横断で **実際にどこへどれだけ消費したか、delegated child を重複なく集計する contract** は watchlist 上で十分明示されていない。

### (6) 次に検証すべきこと

**`ContextAmplificationAccountingBench`**

同一taskで:

- full history
- compact workspace
- retrieval-on-demand
- delegated sub-run あり/なし
- prompt cache あり/なし

を比較し、

- total input tokens
- unique newly admitted tokens
- repeated-input ratio
- child-run double-count error
- latency / cost / energy proxy
- task quality

を測る。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

「メトリクスJSONの仕様」に見えるため、agent intelligence / memory / safety の研究検索では落ちやすい。しかし長寿命agentでは、**同じcontextを何度再送するか**が経済性・energy・latencyを決め、Cognitive Budget の実測閉ループに直結する。

### (8) 重要度

**B+ / watch** — 仕様は work in progress。考え方は有用だが、標準採用ではなく内部 telemetry schema と比較する対象。
