1. **安全上「反応しない」ことと「知覚しない」ことの混同**  
   bot-loop breaker、moderation、rate limit、social circuit breakerなどが、出力/actionだけでなく入力観測・context形成まで消していないか。

   「このendpointにcredentialを送ってよい」ことを、redirect targetやpreflight probeにも暗黙継承していないか。

   server truthによるresyncが、serverにまだ届いていない唯一のuser intentを「存在しない」と解釈して消さないか。

   path / user-facing name / external identifierをbyte/string identityで比較し、同じresourceを別物と判定しないか。

   command / credential / principalを運んでも、どのdurable state rootに属するprocessかを運ばず別個体のstateへfallbackしないか。これは既出 executor-context / effective-environment 系への差分としてのみ扱う。

# 5. 候補ごとの評価

## 5.1 A+ — Perception–Action Gate Decoupling

**一次資料:** Hermes PR #115156  
https://github.com/NousResearch/hermes-agent/pull/115156

### (1) 何が実証済みか

HermesのTelegram adapterでは、`bots_require_mention`により sibling bot からのmessageをreply dispatchしないloop breakerが存在する。ところが、wake-wordで宛先を示したmessageやquote-replyについて、dispatch gateは`False`を返し、別のobservation gateは「wake-word matchならdispatchされるはず」と仮定して観測もしなかった。その結果、**安全のためreplyしないことは意図通りなのに、受信したsocial evidenceそのものまで消失**した。

PRでは、bot-sender suppression predicateを共有し、loop breaker由来でdispatchしなかったmessageは、既存のchat allowlist / observation enable / topic gate等を満たす場合に`observed=True`でcontextへ残す。explicit `@mention`は従来通りdispatchされ、二重記録しない。

新規2 regression rowsはunpatched mainでRED、修正後30/30、Telegram関連collateralは738 pass / 2 skippedと報告されている。調査時点open/unmerged。

### (2) 何が提案・推測段階か

Kamimusuhi全体で「action gateとperception gateを常に別契約にすべき」という一般化は設計提案である。platformごとに、privacy上そもそも観測してはいけないeventもあるため、**observe always**ではなく、独立に判定できることが重要。

### (3) Kamimusuhiのどこに関係するか

- Social Harness
- Global Workspace input admission
- relationship / social episodic memory
- group conversation / multi-agent interaction
- K-Edge social event ingestion
- loop prevention / rate limiting / moderation
- self-modelの「なぜ反応しなかったか」provenance

### (4) 借りられる設計・実装アイデア

単一`should_process: bool`を避け、入力eventに独立したdispositionを持たせる。

```text
IngressDisposition
  perceive: ALLOW | DROP_PRIVACY | DROP_INVALID
  observe_context: ALLOW | REDACT | DROP
  reply_eligible: yes/no
  action_eligible: yes/no
  memory_class: none | transient | episodic | relationship
  suppression_reason?: loop_breaker | policy | rate_limit | moderation | ...
```

loop breakerは`reply_eligible=false`を設定しても、`observe_context`を自動でfalseにしない。

### (5) Kamimusuhiとの差分

既存Kamimusuhiは `thought != utterance != execution`、Social Harness、typed self-invocation等を持つが、今回の差分は**入力側**である。output/effectの抑制とsensory/social evidenceの保持を別々に扱う明示contractはまだ弱い。

### (6) 次に検証すべきこと

**`PerceptionActionGateDecouplingBench-v0`**

ケース:

1. sibling agent loop-risk message: observe=yes / reply=no
2. explicit allowed mention: observe=yes / reply=yes
3. privacy-denied source: observe=no / reply=no
4. moderation-denied harmful content: raw保存なし、metadata-only observation
5. rate-limited human message: observe=yes / immediate reply=no / deferred intent=yes
6. duplicate transport delivery: semantic observation exactly-once

評価: loss rate、double-observation、unwanted response rate、relationship-memory contamination。

### (7) なぜ既存dailyで拾いにくいか

一見するとTelegram adapterのmention条件というplatform固有bugであり、social cognitionやperception-action theoryの検索では出にくい。実際には **inhibitionがperceptionを消してはいけない**というcognitive architecture境界。

### (8) 重要度

**A+**。Social Harnessとepisodic/social continuityの境界に直結し、実装も小さい。

## 5.2 A+ — Namespace-Qualified Embodiment Identity

**一次資料:** Hermes PR #115162  
https://github.com/NousResearch/hermes-agent/pull/115162

**fresh research:** Song Zhang et al., *A Scalable Trust Discovery Architecture for the Internet of Agents*, arXiv:2609.20095  
https://arxiv.org/abs/2609.20095

### (1) 何が実証済みか

Hermes #115162では、各Desktopが自分のregistry内で自身を`local`と呼ぶ。二つのDesktopが一つのgatewayへ接続すると、共有roster/outboxが「どのDesktopのlocalか」を持たず、後から同期したDesktopが先のrosterを消したり、`hermes@local`宛 envelopeを別Desktopがclaimして**自分のlocalへ誤配送**できた。つまり各namespace内では正しい識別子が、集約境界を越えた瞬間にcollisionした。

修正案はDesktop installation由来のscoped owner idを追加し、rosterを`(desktop owner, connection, profile)`でkeyし、envelopeにもownerをstampする。曖昧な名前はguessせず`ambiguous`で拒否する。Python 165 tests、Desktop 743 tests、mainでREDになるmulti-Desktop regressionを報告。調査時点open/unmerged。

arXiv:2609.20095は独立に、agent native identifierだけではglobal discoveryに不十分として、trusted registry suffixと結合したcomposite identityを提案する。著者らのprototypeではregistration/discovery latencyとthroughputを評価しているが、これはpreprint内の報告であり独立再現済みではない。

### (2) 何が提案・推測段階か

Kamimusuhiのdevice / body / branch / peer identityを、DNS風global hierarchyへそのまま寄せる必要はない。重要なのは **aliasの有効範囲をidentityの一部として明示すること**。trusted registry suffix方式は参考候補の一つ。

### (3) Kamimusuhiのどこに関係するか

- distributed embodiment / multi-device body
- K-Edge / Action Router routing
- branch / clone / collective identity
- peer-to-peer agent communication
- relationship memoryのcounterparty identity
- restore / migration後のresource addressing
- local device aliases (`local`, `home`, `phone`, `lab`, etc.)

### (4) 借りられる設計・実装アイデア

```text
EmbodimentScopedName
  local_alias
  namespace_owner_id
  registry_id?: id
  profile_id?: id
  body_incarnation_id?: id
  verified_binding_ref?: evidence-id
```

表示は`local`のままでよいが、wire / durable refs / queue ownershipではqualified identityを使う。collision時はguessせずfail closed。alias解決結果はresolver epoch / registry provenanceとbindする。

### (5) Kamimusuhiとの差分

既出の`CausalEmbodimentBinding`は、**既に選ばれた正しいcontroller/end-pointをturnへbindする**問題だった。今回の差分はその前段で、**同じ文字列のlocal aliasが複数の正しいbodyを指す**問題。namespaceをglobal identityへ誤昇格しないことが新しい。

### (6) 次に検証すべきこと

**`NamespaceCollisionEmbodimentResolutionBench-v0`**

### (7) なぜ既存dailyで拾いにくいか

agent identity一般では「誰か」を扱うが、今回の故障はDNS / naming / distributed namespace / desktop registry実装に現れる。multi-device embodimentの研究検索だけではlocal alias collisionまで落ちにくい。

### (8) 重要度

## 5.3 A — Redirect-Bound Capability Attenuation

**一次資料:** Hermes PR #115158  
https://github.com/NousResearch/hermes-agent/pull/115158

### (1) 何が実証済みか

HermesのMCP HTTP transportでは`strict_redirect_headers`が存在したが、httpx response hookで`response.next_request`を読む実装だったため、実redirectではfollow-up request構築前にhookが走り、保護が実質機能していなかった。さらにcontent-type preflightが別clientでredirectをfollowし、strict policy自体が伝播していなかった。

PR作者はcross-origin 302のlive pairでconfigured `X-API-Key`がpre-fix時にtargetへ到達することを再現。修正案ではredirect request construction seamでcross-origin credential strippingを行い、probeと本transportへ同じpolicyを適用する。multi-hop redirectも含め768 MCP tests + 40 agent-plugin tests greenを報告。調査時点open/unmerged。

### (2) 何が提案・推測段階か

Kamimusuhiで全redirectを拒否すべき、という話ではない。same-origin / explicitly allowlisted cross-origin / OAuth authorization serverなど、credentialごとに正当な移送先が違う。**redirect hopを新しいauthority decisionとして扱う**のが提案。

### (3) Kamimusuhiのどこに関係するか

- Action Router
- MCP / external tools / model endpoints
- capability security / zero trust
- K-Deep web/network integration
- plugin network clients
- discovery/probe layer

### (4) 借りられる設計・実装アイデア

```text
EndpointAuthorityEnvelope
  origin_authority
  credential_class
  allowed_origin_set
  redirect_policy
  preflight_policy
  max_redirect_hops
  decision_policy_epoch
```

各redirect hopでauthorityを再計算する。preflight / metadata discovery / health checkにもprimary requestと同じcredential policyを使う。testはmocked `next_request`だけでなくreal redirect serverで行う。

### (5) Kamimusuhiとの差分

object capability / capability attenuation自体は既出。2026-09-18 06:58のAuthenticatedDiscoveryProbeも「probeはeffect」を収載済み。今回の差分は **origin authorityをredirect destinationへ自動転送しないこと**と、**policy enforcement hookの時系列が本当にfollow-up requestへ作用するかをlive protocol fixtureで検証すること**。

### (6) 次に検証すべきこと

**`RedirectCapabilityAttenuationBench-v0`**

- same-origin 301/302/307/308
- cross-origin one-hop / multi-hop
- Authorization / API key / cookie / custom signed header
- preflight vs primary request
- OAuth authorization endpoint exception
- DNS rebinding / host aliasing
- redirect policy change mid-chain

success条件: unauthorized credential egress = **0**。

### (7) なぜ既存dailyで拾いにくいか

capability securityの理論ではなく、HTTP client libraryのredirect lifecycleとpreflight client分岐に埋まるため。mock testが通っていても実transportではfailする種類の盲点。

### (8) 重要度

**A**。既存原則への具体化だが、credential leakageへ直結するため優先度は高い。

## 5.4 A — Provisional Intent Reconciliation

**一次資料:** Hermes PR #115085  
https://github.com/NousResearch/hermes-agent/pull/115085

### (1) 何が実証済みか

Desktopのoptimistic user rowはclient-local IDを持ち、serverはそのIDを返さない。composer draftはsend時にclearされ、ack前はrenderer memoryが**唯一のuser-written copy**だった。ところがbackground refresh / post-turn rehydrateのmerge pathがserver transcriptでlocal tailを置換し、ack window中のuser messageをsilent dropできた。flaky networkではreconnect自体がrehydrateを起こすため、raceが日常的failureへなる。

修正案はauthoritative chat mergeで既に使われていたpending-message preservation helperを3 merge pathへ適用し、serverに未出現のlocal pending rowを保持する。新testはmainでfail、修正後該当file 41 tests pass。調査時点open/unmerged。

### (2) 何が提案・推測段階か

KamimusuhiでUI optimistic rowをcanonical memoryへ格上げすべきではない。provisional intentは**canonical evidence前の別状態**として守り、ack/reject/cancelで明示的にterminalizeする必要がある。

### (3) Kamimusuhiのどこに関係するか

- conversational input / Global Workspace ingress
- multi-device UI / reconnect
- social intent continuity
- episode creation前のpending event
- offline-first clients
- user consent / correction / edit operations

### (4) 借りられる設計・実装アイデア

```text
PendingIntent
  client_intent_id
  content_hash
  created_at
  source_surface_id
  status: PROVISIONAL | SENT | ACKED | REJECTED | CANCELLED
  server_event_id?: id
```

server snapshot mergeは`ACKED/REJECTED/CANCELLED`でないlocal intentを消さない。server eventとclient intentのdedup correlationを持つ。provisional intentはautobiographical factやrelationship memoryへpromoteしない。

### (5) Kamimusuhiとの差分

直前の`OperationIntentPreservationBench-v0`はbusy/backpressure中でもEDIT/REWIND等の**操作型**を保持する話。今回は**canonical ack前の人間の意図そのものをresyncで失わない**話で、state reconciliationの別問題。

### (6) 次に検証すべきこと

**`ProvisionalIntentReconciliationBench-v0`**

- send直後にdisconnect→authoritative refresh
- ack arrives after refresh
- duplicate ack
- server reject
- user cancel/edit during reconnect
- same user intent from two devices
- crash between local write and network send

評価: lost-intent = 0、duplicate canonical event = 0、unacked intentのmemory promotion = 0。

### (7) なぜ既存dailyで拾いにくいか

frontend optimistic UI / state hydration bugに見えるため、persistent memory / identity continuity surveyでは拾いにくい。しかし長寿命agentでは**人間が実際に発したintentを消す**continuity failureになる。

### (8) 重要度

**A**。

## 5.5 A — Security-Envelope Inheritance for Extension Surfaces

**一次資料:** Hermes PR #115181  
https://github.com/NousResearch/hermes-agent/pull/115181

### (1) 何が実証済みか

Hermes-i3 pluginは従来、独自aiohttp server、独自port、Unix socket、Tailscale share、token checkを持っていた。PR作者はlive installで、secondary service未起動なのに外部proxyだけ生きてwhite pageになった事例、独自token checkがnon-ASCII `compare_digest`やforged Tailscale headerを別途学び直す必要があった事例を報告する。

PR #115181はplugin pageをhost dashboardの`/p/<slug>`へmountし、既存auth gate / Host-Origin guard / lifecycleを継承させる。HTTP/WS両方をhost gateへ通し、headlessではmountしない。unloadはidentity-conditionalでold generationがnew registrationを消せない。49 unit testsとreal dashboard + real plugin discovery + PTY/WebSocketのE2Eを報告。調査時点open/unmerged。

### (2) 何が提案・推測段階か

「全部host processへ同居」が常に安全ではない。untrusted plugin routerをhostへ入れるとblast radiusは広がる。借りるべきなのは、**security perimeterの重複実装を減らしつつ、plugin側capabilityを限定すること**。

### (3) Kamimusuhiのどこに関係するか

- operator / observability dashboard
- plugin / cognitive extension UI
- HCI / human approval surfaces
- local web surfaces
- lifecycle / generation fencing
- capability security

### (4) 借りられる設計・実装アイデア

`ExtensionSurfaceRegistration`に以下を必須化:

```text
slug / route namespace
required host auth class
origin/host policy
headless visibility
lifecycle owner
registration_generation
capability set
static/resource limits
```

host authを自動継承し、pluginが独自auth bypassを追加できない。WebSocketも同じgate。plugin unloadはgeneration check付き。高リスクpluginはprocess isolationしつつhost security proxyを利用する。

### (5) Kamimusuhiとの差分

既存のcapability securityやapproval-plane survivabilityはあるが、「extensionごとにsecurity perimeterをforkするとsecurity/liveness driftが増える」という**deployment topology**の観点は薄い。

### (6) 次に検証すべきこと

**`ExtensionSurfaceSecurityInheritanceBench-v0`**

- HTTP / WS auth parity
- Host/Origin spoof
- headless late-env flip
- old-generation unload race
- plugin crash / host survival
- plugin path collision/traversal
- plugin attempts auth bypass / cookie extraction

standalone server方式とhost-mediated方式でattack surface / lifecycle failure数も比較する。

### (7) なぜ既存dailyで拾いにくいか

AI agentそのものではなくplugin web hosting / dashboard architectureの問題。HCIやsecurityの分類を跨ぐため見落としやすい。

### (8) 重要度

**A**。Kamimusuhiのoperator surfacesが増えるほど効くが、hostへの同居blast radiusもあるため採用時はisolation設計とセット。

## 5.6 B+ — Canonical-Equivalent Resource Identity

**一次実装:** Hermes PR #115103  
https://github.com/NousResearch/hermes-agent/pull/115103

**標準:** Unicode Standard Annex #15, Unicode 18.0.0  
https://www.unicode.org/reports/tr15/

### (1) 何が実証済みか

macOS / FileProvider pathで、DB rowはNFC、filesystem/git側はNFDという同一ディレクトリの異表現が生じ、raw `Path` equalityがfalseになった。その結果worktree resolutionが失敗し、繰り返しspawn失敗後にcircuit breakerがtaskを止めた。PRではpath文字列自体を書き換えず、**identity comparison用keyだけNFC化**して4箇所のcomparisonへ適用する。3 regression testsはbaseでRED、fix後GREEN、関連117 tests pass / 2 skippedを報告。

Unicode UAX #15はcanonical-equivalent sequencesを同じnormalization formへ変換できることをnormativeに定義している。

### (2) 何が提案・推測段階か

NFCをKamimusuhiのあらゆるidentifierへ無条件適用するのは危険。opaque token、hash、case-sensitive remote identifiers等は別。**identity domainごとにcanonicalization ruleを定義する**べき。

### (3) Kamimusuhiのどこに関係するか

- workspace / project / file identity
- durable references
- cross-OS migration
- Library / external resource refs
- restore / backup manifests
- user/device display namesとwire identifiersの分離

### (4) 借りられる設計・実装アイデア

```text
ResourceIdentityKey
  raw_representation
  identity_domain
  canonical_form
  canonicalization_rule_version
```

比較・indexにはcanonical key、実際のfilesystem callやpresentationにはraw pathを保持。canonicalization前後のprovenanceをdebug可能にする。

### (5) Kamimusuhiとの差分

`NamespaceCompleteDurableReference`やresource-instance identityは「どのnamespace / instanceか」を強くする。今回の差分は、**同じnamespace・同じinstanceでも表現がcanonical-equivalentで異なる**ケース。

### (6) 次に検証すべきこと

**`EquivalentResourceRepresentationBench-v0`**

- NFC/NFD path
- macOS ↔ Linux sync
- case-sensitive / case-insensitive FS
- symlink / realpath（Unicode canonicalizationとは別軸として分離）
- percent-encoding / URL normalization
- opaque IDsに誤normalizationを掛けないnegative test

### (7) なぜ既存dailyで拾いにくいか

Unicode text normalization / filesystem portabilityという低層互換性問題であり、agent memoryやdistributed identity検索ではまず現れない。

### (8) 重要度

**B+**。原則は小さいが、cross-device / cross-OSの長寿命個体では「同じ場所を別物と誤認」する地味なcontinuity faultを防ぐ。

## 5.7 B+ delta — State-Namespace Context Transport over Remote Spawn

**一次資料:** Hermes PR #115183  
https://github.com/NousResearch/hermes-agent/pull/115183

### (1) 何が実証済みか

named profileをSSHでremote spawnする際、`HERMES_HOME`が渡されずremote CLIがdefault `~/.hermes`へfallbackした。backend lockにはwrong state rootが記録され、reconnect時に期待するprofile homeと一致せずbackend reuseに失敗した。修正案はprofile-specific homeをPOSIX / Windows remote spawnへ明示輸送し、live named-profile backendでreconnect成功を確認。103 + 16 + 3 targeted tests passを報告。調査時点open/unmerged。

### (2) 何が提案・推測段階か

Kamimusuhiでは単一path環境変数ではなく、state namespaceをtyped contextとして持つべきという一般化が提案。

### (3) Kamimusuhiのどこに関係するか

- remote K-Edge / K-Deep process spawn
- multi-device embodiment
- state root / identity root selection
- restore / reconnect
- ExecutorContextContinuity
- EffectiveEnvironmentManifest

### (4) 借りられる設計・実装アイデア

既存`ExecutionContextReceipt` / effective-environment系へ次を追加:

```text
state_namespace_id
state_root_ref
profile/identity_domain
spawn_host_id
runtime_incarnation
```

remote processはstate rootを再推論しない。spawn receiptとlock/leaseのstate namespaceを照合する。

### (5) Kamimusuhiとの差分

これは独立した新原則ではない。2026-09-17のexecutor context transportと2026-09-11のeffective environment attestationの**fresh concrete extension**であり、principal / privacy / policyに加えて **durable-state namespaceも輸送対象**とする差分。

### (6) 次に検証すべきこと

既存benchへSSH rowを追加:

- named identity Aをremote hostへspawn
- env fallbackを故意に除去
- wrong default state rootを用意
- reconnect / lock reuse
- A/B profile concurrent spawn
- stale remote process

success条件: cross-profile state-root access = 0、reconnect correctly reuses only same namespace/incarnation。

### (7) なぜ既存dailyで拾いにくいか

SSH launcher / env propagationの小さな運用bugに見えるが、長寿命agentでは「どの自己stateを開いたか」というidentity continuity問題。

### (8) 重要度

**B+差分**。既存契約の拡張として採用候補。

## 10. 今回の結論

今回の最重要差分は **「抑制」と「忘却」を同じbooleanにしないこと** と **「local」をidentityにしないこと**。

Kamimusuhiのような長寿命・社会的・multi-deviceな個体では、

- 返答してはいけないが、起きたことは知っているべきevent
- 自分の端末では`local`だが、共有世界ではqualifyしなければならないbody
- serverにはまだ見えていないが、人間が確かに送ったprovisional intent
- originには許されたがredirect先には許されていないcredential

が必ず発生する。

これらを一つの「processing」「identity」「truth」「authorization」に潰すと、silent loss / wrong-body actuation / credential leak / continuity breakになる。今回のfresh implementation evidenceは、Kamimusuhiの設計原則をさらに **「境界を型で分離する」**方向へ押す具体例として価値が高い。
