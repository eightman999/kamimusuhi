## 1. 今回狙った盲点

1. **maintenance が自分で消した operational state を、後から restore inventory の根拠にしてしまう問題**  
   update / migration / reboot のために daemon / gateway / body organ を先に止め、その後で「何を復帰すべきだったか」を live state から推定すると、復元対象の証拠そのものが消えていないか。

2. **意味の異なる policy axis を一つの boolean / enum に押し込む問題**  
   `internal`、`silent`、`trusted`、`continuation`、`safety-exempt` のような概念が混ざり、UI上の静音化が emergency-stop bypass に化けないか。

3. **receipt / provenance を作る query API の selector semantics**  
   `[]` が「全件」「0件」「filterなし」のどれかを caller の思い込みに任せ、実行は成功しているのに completion receipt が永続的に空になるような観測欠落がないか。

4. **active sensing / uncertainty reduction の privacy externality**  
   認識が不確かなために行う corrective action 自体が外部観測者へ情報を漏らす場合、情報取得の時刻・順序を control state として扱う必要がないか。

5. **clone / rename / migration 後の relative resource rebinding**  
   durable config に materialized absolute path が残り、clone が親のmemory DBを共有したり rename後にghost DBを作らないか。

補助探索として、long-lived diagnostics resource ownership、multi-session live-state retirement、OAuth refresh continuity、monotonic timing、A2A実装、Zenn / note / Qiita の当日記事を走査した。

## 5.1 A — Pre-maintenance operational intent capture

**Primary source**: Hermes Agent #119815  
https://github.com/NousResearch/hermes-agent/pull/119815

### (1) 何が実証済みか

- Windows Desktop update pathでは、installation lock回避のため全profile gatewayを先にstopする。
- `hermes update` のresume inventory captureはその後に走るため、successful hand-off時点では元のactive fleet情報が失われていた。
- 修正案はverified update後のlocal pathで`gateway start --all`を行い、restoration failureを「update完了」と偽らない。
- remote `-NoGateway` pathはlocal gatewayを復帰しない。
- ただしWindows実機/full suiteは未実施で、source-level assertions中心の証拠である。

### (2) 何が提案・推測段階か

- Kamimusuhiで常に`start --all`相当が正しいわけではない。必要なのはall-startではなく、**maintenance開始前のdesired operational set / owner / generation / exemptionをdurableにcapturedすること**。
- sensor / model server / speech / body actuator / social bridgeごとに復帰条件は異なる。

### (3) 関係する Kamimusuhi subsystem / design issue

- K-Nerve lifecycle
- K-Observe / maintenance agent
- distributed embodiment / multi-device surfaces
- model / ASR / TTS / sensor daemon lifecycle
- Continuity Kernel restore / migration / software-body update

### (4) 借りられる設計・実装アイデア

maintenanceの最初に次を作る。

```text
MaintenanceIntentReceipt
  maintenance_id
  pre_generation
  desired_active_resources[]
    logical_resource_id
    incarnation/generation
    desired_post_state
    owner/principal
    restore_policy
  intentionally_disabled[]
  remote/local exemptions
  captured_before_quiesce = true
```

その後 `quiesce -> mutate/update -> verify -> restore -> verify restored set` と進める。**restore inventoryをpost-quiescence live scanから逆算しない。**

### (5) Kamimusuhiとの差分

既存のFailure-Atomic Lifecycle Teardown、Repair Authority Closure、Live-Postcondition Migration Completionは「cleanup/repair後の整合性」「修復後も再構成でGREEN」「migration完了条件」を主に扱う。本件はさらに前段で、**maintenance actionそのものが復帰判断に必要な観測証拠を消す**というtemporal-order bugである。

### (6) 次に検証すべきこと

`PreMaintenanceIntentSnapshotBench-v0`:

1. K-Edge / local LLM / TTS / social bridgeを一部active、一部intentionally stoppedにする。
2. update開始後、active resourcesをquiesce。
3. crashを `after intent capture / after quiesce / after update commit / during restore` に注入。
4. recovery後、**pre-maintenance desired setだけ**が復帰し、元々停止中だったresourceを勝手に起動しないことを確認。
5. restore failure時はmaintenanceを`COMPLETE`にしない。

### (7) 既存デイリーではなぜ拾いにくいか

AI agent / identity / memory研究ではなく、updaterの**operation orderingとobservational self-erasure**の問題。通常surveyはupdate成功/rollbackを見るが、「stopした後にresume inventoryを取る」という数行のchoreographyを見落としやすい。

### (8) 重要度

**A**

- Kamimusuhiに同じempty-list bugが存在する証拠はない。

### (3) 関係する Kamimusuhi subsystem / design issue

- tool effect receipts
- provenance graph / file-artifact lineage
- maintenance / experiment output inventory

### (4) 借りられる設計・実装アイデア

query modeをdata構造で明示する。

```text
EvidenceScope =
  | AllByOwner(owner_id, since)
  | ExplicitObjects(NonEmptyVec<ObjectRef>)
```

`[]`、`null`、`""` のようなsentinelに`ALL`を割り当てない。receiptには `query_mode`, `coverage`, `source_generation` を残し、**empty result と evidence-not-queried を区別**する。

### (6) 次に検証すべきこと

`ExplicitEvidenceQueryModeBench-v0`:

- owner writes 0/1/N objects
- explicit path filter 0/1/N
- last-writer takeover
- timestamp boundary
- empty explicit setのconstructor拒否
- restart/replay後も同じcoverage

をproperty-based testし、`actual effects != receipt effects` を検出する。

### (7) 既存デイリーではなぜ拾いにくいか

memory qualityやagent reasoningではなく、registry helperの引数semanticsという地味なAPI契約。end-to-end successだけでは見えず、**observabilityが嘘をつくがtask自体は成功する**ため通常benchmarkから漏れる。

## 5.4 B — Path-dependent active-sensing leakage / early uncertainty has irreversible externality

**Primary source**: Hu, Jin, Yang, arXiv:2609.24225  
https://arxiv.org/abs/2609.24225

### (1) 何が実証済みか

この論文内の理論モデル・数値実験として:

- estimation error varianceをroute-dependent information stateとして導入。
- 推定誤差がcorrective maneuverを生み、その補正がdetectability rateを増やすleading-order項を導出。
- HJBでdeadline / leakage tradeoffを定式化。
- sensing qualityへのsensitivityから、**early informationはfuture leakageを減らせるがlate informationはpast leakageを取り消せない**ことを示す。
- numerical examplesでlearning detour、spatial ordering、randomized sensing allocationを示す。

これはKamimusuhiや人間社会でのprivacyを直接実証した研究ではない。

### (2) 何が提案・推測段階か

Kamimusuhiへの転用は仮説:

- perception uncertaintyにより増える確認動作、視線、再質問、探索、network probe、device handoffが、observerへ「何を知らないか / 何を気にしているか」を漏らす可能性。
- 後で高精度modelへescalateしても、先行するprobe/actionが生んだprivacy leakageは消せない。

### (3) 関係する Kamimusuhi subsystem / design issue

- K-Perception / K-Edge
- active perception / clarification
- distributed embodiment
- privacy / social cognition
- cognitive escalation routing
- physical action safety / observability

### (4) 借りられる設計・実装アイデア

- control stateへ `belief_uncertainty` だけでなく `cumulative_external_leakage_budget` を持つ。
- sensing/action planで `task value + uncertainty reduction - privacy/detectability cost` を評価。
- low-cost/private sensingを早期に使い、public correctionを後段へ追いやる。
- privacy costを最終出力だけでなく**trajectory-level**に測る。

### (5) Kamimusuhiとの差分

論文はadversarially sensed vehicle navigationであり、LLM assistant / social agentのprivacyモデルではない。Kamimusuhiでは漏洩channelが言語、tool call、network access、physical movement、gaze、timingなど多様で、KL detectabilityをそのまま適用できない。

### (6) 次に検証すべきこと

`PathDependentSensingLeakageSim-v0`:

- hidden goal / private preferenceを持つagentがuncertain observation下でactive probeするtoy worldを作る。
- observer classifierにtrajectoryからhidden stateを推定させる。
- `early private sensing / late private sensing / public corrective probing` を比較。
- task success、uncertainty、cumulative observer inference accuracy、latency/costを測る。

**「最終回答に秘密を書かなかった」だけではprivacy successとしない。**

### (7) 既存デイリーではなぜ拾いにくいか

robotics surveyではnavigation/control論文として、privacy surveyでは言語/データ漏洩として分断されやすい。今回の価値は **uncertainty → corrective action → detectability** というcontrol-theoretic couplingとtemporal irreversibilityにある。

## 11. 今回の結論

今回もっともKamimusuhiへ直接効くのは、**maintenance開始前の自己状態を「現在観測できるもの」ではなく「復帰すべきdesired state」として先に記録すること**、そして **eventの静音性・由来・continuation性・安全例外を一つの`internal`概念に潰さないこと** の2点。

特に後者は、便利な分類がpolicy planeを跨いだ瞬間に、HCI上の小さな要求（通知を静かにする）がe-stop bypassへ化けた実例である。Kamimusuhiの長寿命化・ambient化・multi-device化が進むほど、意味的に直交するfieldを直交したまま保つ価値が上がる。

また、`files_written`の事例は、**agentが正しく行動していても、その自己観測receiptが恒常的に空なら、後から見たKamimusuhiは自分が何をしたかを誤認する**という小さいが重要な警告になる。
