## 1. A — Suspend-Aware Clock-Domain Semantics

Primary: https://github.com/NousResearch/hermes-agent/issues/131523  
OS reference: https://www.man7.org/linux/man-pages/man2/timerfd_settime.2.html

1. **実証済み**: cron / turn watchdog が wall-clock elapsed を inactivity として扱い、host suspend 中の時間まで idle と数える実例が報告された。9月29日〜10月2日に12回、sleep gap直後に処理停止。具体例では wall-clock 約940秒に対して実行側 monotonic elapsed は約16秒だった。
2. **提案段階**: timer を一律に同じ clock へ移すのではなく、calendar、active-runtime、suspend-aware age、CPU budget、source event time を分ける。
3. **関係**: K-Core/K-Deep liveness、cron、prospective memory、homeostasis、lease、retry、sleep/wake。
4. **借りる案**: ClockDomain を明示し、WALL_CALENDAR / ACTIVE_MONOTONIC / SUSPEND_AWARE / PROCESS_CPU / EVENT_TIME を区別。
5. **差分**: clock-basis-qualified temporal semantics は既出だが、host sleep を「認知の無活動」と誤認する field evidence は新しい。
6. **次**: **ClockDomainSemanticsBench-v0 (P0)**。
7. **拾いにくい理由**: AI survey は時間を単一timestampとして扱い、OS timekeepingを実装詳細と見なしやすい。
8. **重要度**: **A**。

## 2. A — Capture-Before-Admission for Inbound Resource Events

Primary: https://github.com/openclaw/openclaw/issues/163509

1. **実証済み**: native resource port は既に存在するのに、ownership admission 後までlistenerを付けないため、admission window に届いたinputがsilently lostする reproduction が示された。
2. **提案段階**: admission 前のeffect実行を許す必要はない。capture と authorized consumption を分離すればよい。
3. **関係**: Sensory Event Bus、K-Nerve、native worker、device attach、resource ownership。
4. **借りる案**: resource surface が可視になった時点で最小captureを開始し、PENDING_OWNERSHIP bufferへ保持。admission後にgeneration/ownerを検証してordered drainする。
5. **差分**: accepted-input durability と ownership fencing は既出だが、安全なadmission待ちが観測blind windowを作る点が新しい。
6. **次**: **PreAdmissionInputCaptureBench-v0 (P0)**。
7. **拾いにくい理由**: security、reactive systems、perceptionで責務が分かれる。
8. **重要度**: **A**。

## 3. A update — Maintenance Promotion Must Respect Active Cognitive Occupancy

Primary: https://github.com/NousResearch/hermes-agent/issues/131624

1. **実証済み**: unattended update のstage-and-swapがlive Desktopを停止し、active sessionを失う事例が3日間で14回報告された。既存保護はprocess ancestry依存のため、別process treeから始まったmaintenanceではlive surfaceが保護されない。
2. **提案段階**: maintenanceを禁止する話ではなく、quiescence / graceful handoff / deferred activationが候補。
3. **関係**: Software Body、self-maintenance、session continuity、delegated work、migration。
4. **借りる案**: artifact_ready → occupancy_check → quiesce/handoff → activation → verified_resume のphaseを持つ。process ancestryではなくlive cognitive ownershipを参照する。
5. **差分**: maintenance-cognition isolation / atomic activation は既出。fresh差分はactivation権限が起動元process topologyに左右されること。
6. **次**: **MaintenanceOccupancyHandoffBench-v1 (P0)**。
7. **拾いにくい理由**: deployment、UX、agent orchestrationが別分野。
8. **重要度**: **A update**。

## 4. A update — Capability Statements Must Be Mechanically Grounded

Primary: https://github.com/NousResearch/hermes-agent/issues/131568

1. **実証済み**: vision-capable modelへuser imageが実際に届いているのに、browser tool descriptionがmodel全体をtext-onlyと誤って説明し、modelが画像を利用しなかった。原因は「tool-result screenshotを運べるか」と「user imageを見られるか」を同一視したこと。
2. **提案段階**: capability説明自体をなくす必要はない。能力軸を分解してlive evidenceから生成する。
3. **関係**: Computational Embodiment、self-model、multimodal perception、tool projection。
4. **借りる案**: USER_IMAGE_INPUT / TOOL_RESULT_IMAGE / AUDIO_INPUT / FILE_ATTACH 等を独立axisにし、説明文も同じ CapabilityEvidence から生成する。
5. **差分**: mechanically grounded present state / capability evidenceは既出。fresh差分は誤った自己能力説明が実在する感覚器を使わせなくする実例。
6. **次**: **CapabilitySelfDescriptionConsistencyBench-v1 (P0/P1)**。
7. **拾いにくい理由**: adapter metadata、self-model、prompt engineeringの境界。
8. **重要度**: **A update**。

## 5. B update — Schedule Revision Must Fence Obsolete Temporal Obligations

Primary: https://github.com/NousResearch/hermes-agent/issues/131592

1. **実証済み**: paused jobのscheduleを変更後にresumeすると、旧scheduleで生成された経過済みslotが残り、新policyに変えた直後でも旧cadenceのcatch-upが発火する。
2. **提案段階**: schedule未変更時のcatch-up自体は有効。
3. **関係**: prospective memory、standing duties、temporal database、reminder。
4. **借りる案**: scheduled occurrenceへ schedule_revision をbindし、resume時にcurrent revisionと違うoccurrenceをobsoleteとしてretireする。
5. **差分**: temporal obligation projectionは既出。fresh差分はpauseが旧policy由来のfuture obligationを凍結し、edit後に蘇生すること。
6. **次**: **TemporalObligationRevisionFenceBench-v0 (P1)**。
7. **拾いにくい理由**: scheduler側ではtimestamp、agent側ではintentとして扱われる。
8. **重要度**: **B update**。

## 6. B update — Known Terminal Evidence Must Dominate Derived Unknown

Primary: https://github.com/openclaw/openclaw/issues/163543

1. **実証済み**: live runではRunning、native terminal itemではcompleted/failedと判明しているtool callでも、status-less history projection由来の Outcome unknown がUIで優先されるdeterministic regressionが報告された。
2. **提案段階**: UIが全runtime detailを表示する必要はないが、evidence precedenceは必要。
3. **関係**: observability、Canonical Evidence、task outcome、operator trust。
4. **借りる案**: native terminal / live owner > durable terminal > incomplete projection > unknown のauthority orderingを持たせる。
5. **差分**: Canonical Evidence outranks summariesは既出。fresh差分はUNKNOWNが単なる情報不足でなくknown evidenceを覆うprojection valueとして振る舞うこと。
6. **次**: **OutcomeEvidencePrecedenceBench-v1 (P1)**。
7. **拾いにくい理由**: presentation detailに見えるがoperatorのrepair判断へ直結する。
8. **重要度**: **B update**。

## 7. B update — Configured Offline Cognition Must Prove Pipeline Advancement

Primary:
- https://github.com/openclaw/openclaw/issues/163607
- https://github.com/openclaw/openclaw/issues/163599

1. **実証済み**: Dreaming がdefault-enabledでnightly cronも走るのに、数週間recall store / dream corpus / ingestion stateが進まず、manual backfillは正常に候補抽出できる事例が報告された。別件ではself-learning autoがdefaultでもCLI runtimeではexperience reviewが設計上skipされ、その非稼働状態をdoctor/statusが表示しない。
2. **提案段階**: 全runtimeで同じoffline cognitionを必須化する話ではない。
3. **関係**: sleep/dream、memory consolidation、self-improvement、observability。
4. **借りる案**: CONFIGURED / ELIGIBLE / SCHEDULED / STARTED / ADVANCED_STATE / COMMITTED / LAST_SUCCESS を別stateとして機械的に出す。
5. **差分**: IMPLEMENTED/WIRED/OBSERVED/SOAKED は既出。fresh差分はdream/self-learningでscheduled runの存在自体が「発達している」という錯覚を作ること。
6. **次**: **OfflineCognitionPipelineAdvancementBench-v1 (P1)**。
7. **拾いにくい理由**: memory quality研究とscheduler healthの間にend-to-end advancement確認が落ちる。
8. **重要度**: **B update**。

## 異分野 / 古典 backfill

Linux timekeepingは CLOCK_MONOTONIC がsystem suspendを数えず、CLOCK_BOOTTIME はsuspendを含むことを明示している。KamimusuhiではAPI選択そのものより、clockをsemantic typeとして扱う抽象を借りるべき。

- inactivity / active cognition → active monotonic
- calendar appointment → wall/calendar
- maintenance age → suspend-aware elapsed
- compute budget → CPU/process time
- sensory freshness → source event time + ingestion time

OS suspend、Kamimusuhiのsleep phase、外界のwall timeを同じ「経過時間」にしない。
