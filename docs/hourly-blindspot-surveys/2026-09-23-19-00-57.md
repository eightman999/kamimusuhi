# 4. 候補ごとの評価

## 4.1 A — Rotation-Domain Key Separation

**Primary fresh evidence:** OpenHands #17640  
https://github.com/OpenHands/OpenHands/pull/17640

### (1) 何が実証済みか

OpenHandsのself-hosted automation stackでは、rotatableな`LOCAL_BACKEND_API_KEY`をdefaultで`AUTOMATION_KV_SECRET`にも流用していた。KV stateとrepository-sync secretsはその値でat-rest encryptionされるため、authentication credentialをrotationしただけで旧ciphertextの復号keyが変わった。

PRのreal-backend reproでは、key AでKVを書き、API keyだけBへrotateしてrestartすると従来実装はGET 500 `Failed to decrypt value`。persisted KV secretを導入した変更後はGET 200で`page-42`を回収できた。

つまり、**credential rotationという正常maintenanceがdurable memory loss相当の障害を作り得る**ことが具体的に実証された。

### (2) 何が提案・推測段階か

- Kamimusuhiが現時点で同じkey reuseをしているという証拠ではない。
- `persisted secret file`がKamimusuhiの最終解とは限らない。OS keychain / TPM / KMS / envelope encryptionの方が適切なdeploymentもある。
- keyのpurpose separation、KEK/DEK分離、multi-device key escrow、cryptographic erasureとの整合は別途設計が必要。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Continuity Kernel / canonical evidence store
- K-Core / K-Deep durable state
- memory ownership / consent
- backup / restore / migration
- multi-device embodiment
- death / rebirth / host replacement
- credential management / zero trust
- cryptographic erasure

### (4) 借りられる設計・実装アイデア

`KeyPurpose` / `KeyLifetimeDomain`をcredentialとは別型で持つ。

```text
AUTH_SESSION_CREDENTIAL
API_ACCESS_TOKEN
DATA_AT_REST_DEK
KEY_ENCRYPTION_KEY
SIGNING_KEY
DEVICE_ATTESTATION_KEY
ERASURE_DOMAIN_KEY
```

少なくとも、**「rotate頻度・失効理由・復旧手順が異なるartifactを同一secretへ暗黙束縛しない」**。

upgrade migrationでは、新しいkeyをいきなり生成して旧ciphertextを孤児化せず、旧keyのcustodyを確認してからrewrap/migrateする。key identity/versionをciphertext metadataへ明示し、復号不能をgeneric corruptionとして扱わない。

### (5) Kamimusuhiとの差分

Kamimusuhiにはcredential non-inheritance、credential-token lifecycle separation、encryption key granularityのwatch question、cryptographic erasureが既にある。一方、**rotatable authentication credentialとdurable encrypted stateのlifetime coupling**を明示的に壊すcontractは確認できなかった。

したがってこれは「tokenはidentityではない」の再提案ではなく、**memory continuityを守るためのkey-lifecycle domain separation**である。

### (6) 次に検証すべきこと

`KeyRotationContinuityBench-v0`:

1. canonical/episodic stateを暗号化してwrite
2. authentication/session credentialのみrotate
3. process restart / host restart
4. old durable stateがread可能であること
5. explicit data-encryption-key rotation時はversioned migration/rewrapを要求すること
6. old key欠損時は「memory missing」ではなく`CRYPTOGRAPHIC_CUSTODY_UNAVAILABLE`等のtyped failureになること
7. backup restore / second deviceでもkey version bindingを検証

### (7) 既存dailyではなぜ拾いにくいか

security surveyはcredential theft/least privilegeへ、memory surveyはretrieval/durabilityへ、identity surveyはprincipal continuityへ寄りやすい。今回の穴は**正常なcredential rotationがmemory availabilityを破壊するcross-lifecycle coupling**で、key-managementとpersistent-agent maintenanceの境界にある。

### (8) 重要度

**A**。長寿命個体でcredential rotationは避けられず、誤couplingはsilent data lossではなく「保存されているのに本人が読めない」というcontinuity failureを起こす。

## 4.2 A — Admission-Wait Snapshot Release & Revalidation

**Primary fresh evidence:** OpenClaw #156390  
https://github.com/openclaw/openclaw/pull/156390

### (1) 何が実証済みか

worker lease verificationがSQLite read transaction/snapshotを開いたままhost admissionを約1秒待つことで、WAL truncationを妨げる実測が出た。修正前はsnapshot hold 1,051〜1,055ms、修正後はadmission中transactionなし。さらに、snapshotをreleaseするだけでなく**host grant後にcurrent committed ownershipを再読**している。

これは一つのsnapshotを長く持つ問題が、

1. storage maintenanceをpinするresource-lifetime問題
2. admission待ち中にauthorityが変わるstaleness問題

の両方を持つことを示す。

### (2) 何が提案・推測段階か

- KamimusuhiのSQLite access pathに同じ長期read transactionがあるとは未確認。
- すべてのtransactionを短くすればよいわけではない。atomic read-modify-writeやwrite/renewalのauthority checkはtransaction内に残す必要がある。
- snapshot isolationが必要な処理まで分割すると逆にcorrectnessを壊すため、operation classごとの設計が必要。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- `kamimusuhi-store-sqlite`
- Continuity Kernel state reads
- execution owner / lease validation
- Cognitive Action Router admission
- maintenance / checkpoint / vacuum
- low-latency cognition
- long-lived agent observability

### (4) 借りられる設計・実装アイデア

待ちを跨ぐ処理を次の2-phaseへ分ける。

```text
read minimal precondition
close snapshot
await scheduler / host / network admission
re-read current authoritative state
validate generation/owner/revision
perform effect or fail stale
```

`DBSnapshotLease`に`opened_at`, `operation`, `await_crossings`, `max_hold_ms`を記録し、**await boundaryを跨いだread snapshot**をtrace上で直接検出できるとよい。

### (5) Kamimusuhiとの差分

既出のmaintenance-cognition isolationやlate-bound dispatch currentnessは近いが、前者はbackground maintenanceがforeground cognitionを塞ぐ方向、後者はawait後のauthorization再確認が中心。今回の差分は**foreground側の「読むだけ」のsnapshotがmaintenanceを逆にpinし、そのsnapshot自体もawait後にはauthority evidenceとして古い**という双方向の問題。

### (6) 次に検証すべきこと

`SnapshotAdmissionLeaseBench-v0`:

## 4.3 B — Ownership-Qualified Concurrent Scope Finalization

**Primary fresh evidence:** Hermes #119904  
https://github.com/NousResearch/hermes-agent/pull/119904

### (1) 何が実証済みか

concurrent turnが同じphysical relay scope stackへ重なると、先に完了したlogical turn Aが自分のscopeをcloseしようとした時、stack topはまだ生きているturn Bのscopeになり得る。unguarded popはRuntimeErrorになりcleanupをskip。PRは当日14件、日次8〜19件、累積95件の観測を報告している。

修正は「自分のhandleがtopならpop、違えばpopしない」。後続のsession-close drainが残scopeを回収する。

### (2) 何が提案・推測段階か

- Kamimusuhiがrelay scopeを同じstack表現で実装しているわけではない。
- `if_top`だけではarbitrary overlap全般を解決しない。長寿命resourceではowner-scoped set / reference counting / structured concurrencyの方が適切な場合もある。
- deferred cleanupがauthority/cost accountingを残し続ける危険もあり、drain livenessが別途必要。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- provider routing / logical model calls
- concurrent dialogue turns
- K-Core/K-Deep delegation
- external model scopes
- tracing / accounting context
- cancellation / finalization

### (4) 借りられる設計・実装アイデア

finalizationを「stackを1つpop」ではなく、owner/handle/generationでqualifyする。

```text
ScopeHandle {
  scope_id,
  owner_turn,
  generation,
  opened_at,
  finalizer_authority,
  state
}
```

`close(scope_id)`は別scopeを絶対にremoveしない。順序制約により今すぐcloseできない場合は`DEFERRED_CLOSE`へ移し、bounded drainで回収する。`deferred_scope_age`もobservability対象にする。

### (5) Kamimusuhiとの差分

Kamimusuhiにはexecution-owner binding、resource incarnation、cancellation closureがあるが、**concurrent logical scopesのfinalizationをLIFO container mutationからowner-qualified operationへ変える**具体契約は確認できなかった。

### (6) 次に検証すべきこと

`ConcurrentScopeFinalizationBench-v0`:

- A open → B open → A complete → B complete
- A open → B open → A cancel → C open → B complete
- provider fallback / nested delegationを混ぜる
- wrong-scope pop = 0
- leaked scope after drain = 0
- route/accounting attribution cross-contamination = 0
- deferred cleanupに上限時間を置く

### (7) 既存dailyではなぜ拾いにくいか

agent orchestrationでは「task owner」、systemsでは「stack/RAII」、distributed tracingでは「span context」と別々に扱われる。穴は**concurrent async lifetimeが単純LIFO disciplineを壊す**境界にあり、通常のagent taxonomyではただのcleanup bugに見えやすい。

### (8) 重要度

**B**。直ちにidentity破壊へ直結するとは限らないが、routing、cost accounting、authority、cleanupのcross-turn contamination源になる。

## 5.1 A update — P30へ Replay–Dedup Horizon Dominanceを追加

**Source:** Hermes #119899  
https://github.com/NousResearch/hermes-agent/pull/119899

Kamimusuhiには既に`Dedup and idempotency are not synonyms`があり、local state loss後にdedupだけではexactly-onceを証明できないことも収載済み。したがって「durable dedupが必要」を新規原則としては再提案しない。

fresh差分は**時間幅の包含関係**。

```text
dedup_retention_horizon
>= upstream_replay_horizon
 + reconnect/jitter margin
```

かつ、restartがdedup horizonを0へresetしてはならない。

候補fixture `ReplayWindowDominanceBench-v0`:

- provider replay window = 10min
- local dedup TTL = 5min / 15min / 60min
- reconnect + process restartを挟む
- same upstream message IDのeffect countを測る
- horizon不足をstartup/config validationで検出できるか確認

これはK-Nerve adapter contractへ入れる価値がある。

## 5.2 A update — Layered In-Flight Continuation Livenessへ Incarnation-Qualified Replay Cursorを追加

`ReplayCursorIncarnationBench-v0`ではsession reap / runtime-id再生成 / old watermark / empty new ringを組み合わせ、`events=[]`が「nothing missed」と誤解されないことを確認する。

## 5.3 A update — privacy policyはcapture/export境界より前でenforce

**Sources:**

- OpenClaw #156420: https://github.com/openclaw/openclaw/pull/156420


## 10. 今回の結論

今回のfresh差分は、Kamimusuhiの長寿命性を壊すものが必ずしも「LLMの記憶忘れ」ではなく、**周辺lifecycleの時間尺度の不一致**であることをかなり強く示した。

最も重要なのは次の3点。

1. **短寿命authentication credentialのrotationを、長寿命memoryの復号能力へ伝播させない。**
2. **待ち時間を跨ぐsnapshot/authority evidenceは、resourceをpinしないよう解放し、effect直前にcurrent stateを取り直す。**
3. **concurrent cognitionのscopeはstack positionではなくowner identityでcloseする。**

既存契約への更新としては、`dedup_window >= upstream_replay_window` と `replay_cursor=(incarnation, sequence)` の2つが特に実装価値が高い。

今回の日本語圏探索については、**Zenn / note / Qiita由来の独立した有意な新規発見なし**。ただしfresh OSS一次実装側では十分に有意な差分が得られたため、本runは「有意な新規発見あり」とする。
