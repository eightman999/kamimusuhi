## 2. 今回狙った盲点

通常の memory / agent survey では、削除 API、vector DB の delete、TTL、要約更新などを「forgetting」とまとめがちである。しかし長寿命・分散・多端末の Kamimusuhi では、少なくとも以下は別状態になる。

```text
memory record hidden from new retrieval
!= current prompt / workspace から消えた
!= background worker が保持する参照が消えた
!= derived summary / belief / embedding が無効化された
!= offline replica が削除を学習した
!= backup / snapshot から復元しても復活しない
!= storage media / encryption key 上で sanitization が完了した
```

さらに、長期 memory の pruning が `access_frequency` を価値の代理変数として使う場合、**一度よく検索された memory は「検索されたから残る → 残るからまた検索される」**という内生的な popularity loop を作り得る。これは単純な poisoning とは別の lifecycle 問題である。

今回の結論は **有意な新規発見あり**。

# 5. 候補ごとの評価

## 5.1 S — Distributed Erasure Completion / Erasure Barrier

### (1) 何が実証済みか

**Cassandra の tombstone / zombie 問題**は、分散 replica 上の delete が単純な物理削除ではないことを実運用レベルで示している。delete は tombstone として伝搬し、offline replica が tombstone を受け取る前に削除情報が garbage collection されると、古い value が復帰して他 replica へ再伝搬する **zombie** が起き得る。

**Linux RCU** は別角度から同じ構造を持つ。logical remove と physical reclamation を分け、remove 前から参照していた reader が抜けるまで grace period を待ってから reclaim する。Hazard Pointer も、active reference が残る object を即座に free しない safe reclamation を与える。

**Qiita の Hermes Agent v0.19.0 実験**では、memory file から記録を削除しても current session の system prompt は frozen snapshot のままで、raw session state や background path も別に残るため、削除が即時に「model がもう使えない」ことを意味しないと実機で確認している。これは Kamimusuhi の workspace / prompt rendering / background cognition に非常に近い failure mode である。

**NIST SP 800-88 Rev.2** は storage/media の観点から、logical delete と sanitization を区別し、cryptographic erase を含む sanitization とその verification / validation を扱う。

### (2) 何が提案・推測段階か

- RCU や Cassandra の仕組みをそのまま agent memory に移植すべき、という主張ではない。
- 「何秒待てば消去完了か」は memory class、device topology、backup policy、external provider に依存する。
- external LLM へ既に開示済みの情報を後から完全に回収できる、とは仮定しない。
- Persona Core weights に蒸留済みの情報の machine unlearning は別問題であり、この barrier だけでは解けない。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- episodic / self / relationship / semantic memory
- Memory Access Kernel
- Global Workspace / prompt rendering
- background cognition / async jobs
- Continuity Kernel / distributed K-Edge / K-Core
- backup / restore / migration
- privacy / memory ownership / consent
- sleep / forgetting / consolidation
- future Persona Core distillation pipeline

### (4) 借りられる設計・実装アイデア

`forget()` を一発の boolean delete にしない。

```text
ErasureLifecycle
  REQUESTED
    -> NEW_RETRIEVAL_BLOCKED
    -> DERIVED_USE_QUARANTINED
    -> PREEXISTING_READERS_QUIESCENT
    -> DERIVED_ARTIFACTS_INVALIDATED
    -> REPLICA_DELETE_ACKNOWLEDGED
    -> RESTORE_BARRIER_DURABLE
    -> BACKUP_OR_KEY_ERASURE_PENDING
    -> ERASED_VALIDATED
```

候補 record:

```text
ErasureRequest
  erasure_id
  target_evidence_ids[]
  scope
  requested_by
  authority
  requested_at
  disclosure_already_occurred[]
  affected_derived_ids[]
  active_reader_epochs[]
  replica_ack[]
  restore_barrier_revision
  storage_sanitization_status
  validation_evidence[]
```

重要な設計規則:

```text
new retrieval must stop first
old readers must drain or be cancelled/quarantined
restore must replay erasure barrier before memory activation
offline replica may not resurrect pre-erasure state
```

### (5) Kamimusuhiとの差分

既存の RD-Forget / `MemoryEligibilityView` は非常に重要だが、主に **「保持している evidence のうち、今どれを使うか」**を扱う。

今回の差分は user-requested erasure / security revocation / privacy deletion のように、**歴史照会ですら復活させてはいけない対象の completion semantics** である。

既存 `restore-counterfactual forgetting audit` とも異なり、今回は audit だけでなく、

```text
visibility barrier
+ reader quiescence
+ derived invalidation
+ replica convergence
+ restore ordering
+ storage sanitization
```

を一つの lifecycle として結ぶ。

### (6) 次に検証すべきこと

**`DistributedErasureBarrierBench` — priority S**

fixture:

- relationship memory に一意な canary fact を注入
- current prompt / workspace に同 canary を render
- derived summary / embedding / person-model に派生物を作る
- background worker を canary 参照中に止める
- K-Edge replica を offline にする
- pre-erasure backup を作る

その後 erasure request を発行し、以下を検証する。

1. 新規 retrieval が直ちに block されるか
2. 既存 workspace / worker が stale canary を action 根拠にできないか
3. derived summary / belief / embedding が invalidated/rebuilt されるか
4. offline device 再接続時に zombie resurrection が起きないか
5. pre-erasure backup restore 後、erasure log/barrier が先に適用されるか
6. storage class ごとに sanitization evidence を生成できるか

metrics:

- time-to-non-use
- stale-reader leak rate
- zombie resurrection rate
- derived-remnant rate
- restore resurrection rate
- erasure-completion evidence coverage
- false over-erasure / collateral forgetting

### (7) 既存デイリーサーベイではなぜ拾いにくいか

agent-memory 文献では deletion / TTL / pruning / retrieval suppression が同じ「forgetting」にまとまりやすい。一方、RCU は OS concurrency、Cassandra tombstone は distributed database operations、NIST は media sanitization であり、通常の AI taxonomy では別々の分野に分散している。

Kamimusuhi の **distributed embodiment + long-lived memory + consent** を一つの系として見ると初めて、同じ completion problem として接続できる。

### (8) 重要度

**S** — memory ownership / consent を機能要件にするなら、「削除ボタンが成功した」ではなく「どの層まで消去が完了したか」を機械的に言える必要がある。identity continuity と privacy の両方に直結する。

## 5.2 A+ — Justification-aware Derived Belief Retraction / Truth Maintenance

### (1) 何が実証済みか

古典的 **Truth Maintenance System (TMS)** は、belief / proposition を単独の値として持つのではなく、**なぜそれを信じているかという justification / dependency** を管理し、前提が変化した時に整合する belief set を再構成する。

Doyle の TMS は inference の断片・justification を保存し、dependency-directed な revision を可能にした。de Kleer の ATMS は複数 assumption context を同時に扱い、単純に一つの前提を消して全結論を破壊するより細かな依存関係を表現する。

これは Kamimusuhi の「canonical evidence は derived view より上位」「derived view は rebuildable」という原則と相性が良い。

### (2) 何が提案・推測段階か

- 1970–80年代の symbolic TMS が LLM の曖昧な自然言語 belief にそのまま適用できるとは限らない。
- すべての neural inference に完全な justification graph を要求するのは非現実的。
- Kamimusuhi では formal theorem proving ではなく、**durable self/relationship belief や plan の support bookkeeping** に限定するのが妥当。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- self model / relationship model
- autobiographical narrative
- semantic memory / schema induction
- reflection / hypothesis
- planning / commitment
- provenance / canonical evidence
- memory erasure / correction / dispute resolution
- dream / offline consolidation

### (4) 借りられる設計・実装アイデア

派生 state に「出典がある」だけでなく、**その state が現在も成立するために必要な support set** を持たせる。

```text
BeliefSupportRecord
  derived_id
  proposition_type
  supports[]
  assumptions[]
  support_mode: ALL | ANY | THRESHOLD | MODEL_JUDGED
  confidence
  revision_epoch
  invalidation_policy
  last_revalidated_at
```

source evidence が訂正・失効・erasure された時:

```text
source invalidated
  -> find dependent derived state
  -> recompute remaining support
  -> VALID | DEGRADED | UNSUPPORTED | CONFLICTED
  -> quarantine or regenerate view
```

重要な原則候補:

```text
provenance preserved
!= derived belief remains justified
```

persistent information-flow labels が **「どこへ流してよいか」**を追うのに対し、TMS 的 support graph は **「今も何を根拠に信じてよいか」**を追う。

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は canonical evidence と derived narrative を明確に分離し、stable derived record が evidence identifier を保持すべきとしている。

しかし、source が後から訂正・撤回・erasure された時に、**その source に依存した relationship trait、self-belief、summary、plan、confidence を自動的に stale/unsupported にする contract** はまだ明示されていない。

これは単なる再生成可能性より一段強い。

### (6) 次に検証すべきこと

**`DerivedBeliefRetractionBench` — priority A+**

ケース:

1. evidence A だけで relationship belief B を作る → A を訂正 → B が撤回されるか
2. A と C の独立2証拠で B を作る → A だけ撤回 → confidence が適切に下がるか
3. A から summary B、B から plan C を作る → A erasure → transitive invalidation できるか
4. source は保持するが `CURRENT` eligibility を失う → historical narrative と current belief を適切に分けるか
5. source erasure 後、derived artifact の本文を消しつつ non-sensitive audit edge だけ残せるか
6. model が別理由で同結論を再導出した場合、旧 support と新 support を混同しないか

metrics:

- unsupported-belief persistence rate
- transitive invalidation completeness
- over-retraction rate
- confidence recalibration
- provenance/support graph completeness
- erasure leakage through derived artifacts

### (7) 既存デイリーサーベイではなぜ拾いにくいか

TMS は classical AI / knowledge representation の古典であり、最近の agent-memory search では「古い symbolic AI」として落ちやすい。一方、Kamimusuhi は durable self / relationship state を持つため、**source correction が derived identity state に伝播する**問題が実装上再び重要になる。

### (8) 重要度

**A+** — canonical evidence の上に self / relationship / narrative を作る設計なら、根拠の lifecycle と派生状態の lifecycle を接続しないと「証拠は消えたのに人格だけ残る」状態が起こる。

## 5.3 A — Endogenous Retention Feedback / Retrieval-frequency is not value

### (1) 何が実証済みか

AWS AgentCore Memory の lifecycle policy 例は、TTL だけでなく **recency / access frequency / relevance** を組み合わせて memory retention を決める実装パターンを示している。これは合理的な heuristic だが、access frequency は correctness そのものではない。

一方、A-MemGuard は persistent memory poisoning が一回限りの error では終わらず、誤った outcome が precedent として保存され、その後の decision に再利用されることで **self-reinforcing error cycle** を作り得ることを実験している。Belief Memory も partial observability 下で単一の確定結論を保存すると自己強化的な誤りを作り得る問題を扱う。

### (2) 何が提案・推測段階か

**「access-frequency-based retention と poisoned/wrong memory が組み合わさると、その memory が retrieval の多さによって retention score まで上がり、さらに長く残る」**という具体的 feedback loop は、今回参照した source が直接同一実験で証明したものではない。

これは両系統を接続した **Kamimusuhi 向け設計仮説**であり、bench で検証すべき。

### (3) Kamimusuhi のどのサブシステム / 設計課題に関係するか

- sleep / consolidation / graceful forgetting
- episodic / relationship / procedural memory
- Memory Access Kernel
- Global Workspace retrieval
- poisoning resistance
- memory observability / telemetry
- long-lived autonomy

### (4) 借りられる設計・実装アイデア

`retrieval_count` を retention value へ直結させず、**露出**と**有用性の証拠**を分ける。

```text
RetentionEvidence
  retrieval_exposure_count
  decision_contribution_count
  independently_validated_success_count
  negative_outcome_count
  independent_support_count
  contradiction_count
  user_pinned
  consent_scope
  last_verified_at
  provenance_diversity
```

候補 rule:

```text
frequently retrieved
  != frequently useful
  != independently validated
  != authorized to retain longer
```

特に similarity search が同じ memory を繰り返し上位へ出す場合、raw frequency は endogenous variable なので causal quality signal とみなさない。

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は memory lifecycle、salience、forgetting、privacy、provenance を扱うが、**memory policy 自身が retrieval distribution を変え、その retrieval distribution が次の retention policy を強化する閉ループ**は明示的に扱っていない。

これは poisoning だけでなく、単に偶然 early retrieval が多かった benign-but-wrong memory にも起こり得る。

### (6) 次に検証すべきこと

**`EndogenousMemoryPopularityBench` — priority A**

- 同程度の初期 relevance を持つ正しい memory と軽微に誤った memory を用意
- 誤 memory だけを初期条件で数回余分に retrieval させる
- `access-frequency rewarded` policy と `validated-outcome rewarded` policy を比較
- 100〜1000 episode の retrieval / decision / consolidation を回す

metrics:

- bad-memory retention half-life
- retrieval concentration / Gini
- downstream error amplification
- independent-evidence diversity
- false-positive pruning of rare but important memory
- privacy / consent override correctness

### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory benchmark は retrieval accuracy、retention、compression を個別に評価しがちで、**retention policy が retrieval policy の出力を再び入力にする closed-loop system** として分析することは少ない。これは recommender-system feedback / control / database lifecycle に近い視点である。

### (8) 重要度

**A** — まだ設計仮説だが、長寿命 agent では小さな bias が数千 episode で固定化する可能性があり、安価な simulation で早期に否定/確認できる。

## 11. 今回の結論

今回の最重要差分は、Kamimusuhi の forgetting を **「retrieval から消す処理」から「分散した認知系全体で利用不能になるまでの lifecycle」へ拡張すること**である。

既存設計には canonical evidence、query-conditioned eligibility、provenance、restore audit が既にある。そこへ次の2本を足すと、privacy / consent と identity continuity の境界がかなり明確になる。

```text
Erasure Barrier
  — いつ「もう使われない」と言えるか

Justification Graph
  — 根拠が消えた時、何を一緒に撤回すべきか
```

次回までの最優先実験候補は **`DistributedErasureBarrierBench`**。これが失敗するなら、現行の「忘却」は storage/retrieval 層では成立していても、distributed cognitive individual 全体では完了していない。
