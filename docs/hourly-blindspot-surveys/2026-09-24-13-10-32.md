## 5.1 A — Lossy Projection Non-Writeback: 読むための表現を「本物の値」として書き戻さない

**一次資料**

- Hermes Agent PR #121011  
  https://github.com/NousResearch/hermes-agent/pull/121011

### (1) 何が実証済みか

Hermes #121011 は、dashboard API が credential を redacted preview として返し、その preview をユーザーが変更せず保存した場合に、preview文字列そのものが live secret へ書き戻される回帰を再現している。

PR記載の before evidence では `PUT /api/env` 後に `sk-env-secret-1234567890` が `sk-e...7890` へ変わった。修正後は Env / messaging channel / custom endpoint の各save flowで preview submissionをpreserveとして扱い、explicit replacement と explicit clear は維持する focused regression が通ったと報告されている。

調査時点では **open / 未merge**。したがって upstream確定仕様ではなく、再現付きimplementation evidenceとして扱う。

### (2) 何が提案・推測段階か

Kamimusuhiへ一般化する次の契約は提案段階。

```text
Projection<T> is readable
!=
Projection<T> is a valid MutationValue<T>
```

特に secret だけでなく、summary、privacy-filtered memory、relationship view、Persona edit preview、consent status のような **lossy / redacted / derived representation** を canonical write input として扱わない方がよい。

Hermesのcompatibility fixは「submitted stringが現在のredacted previewと一致したらpreserve」と推定する方式であり、最終形としては operationを明示する方が強い。

```text
SecretEdit = Preserve | Replace(Secret) | Clear
```

### (3) 関係するサブシステム / 設計課題

- K-Nerve settings / control UI
- secret / provider credential store
- memory ownership and consent UI
- relationship / Persona / self-model のeditable projection
- multi-device embodiment の設定同期
- canonical evidence vs derived views
- privacy-preserving memory

### (4) 借りられる設計・実装アイデア

1. read responseに projection metadata を持つ。

```text
ProjectionMeta {
  source_object_id,
  source_revision,
  representation: Redacted | Summarized | Filtered | Canonical,
  lossy: bool,
  roundtrip_safe: bool,
}
```

2. write APIでは `value` のoverloadではなく intention を明示する。

```text
MutationIntent = Preserve | Replace(value) | Clear
```

3. derived/lossy projectionからcanonical mutationを開始する場合、source revisionへbindし、server側でfresh canonical ownerを再確認する。

4. compatibility目的で masked-string detection を残す場合も、それをcanonical valueへ昇格させない。

### (5) Kamimusuhiとの差分

Kamimusuhiはすでに **canonical evidence > derived view**、Persona / episode / relationship / library の分離を強く持つ。しかし現在の原則は主に「何を真実として読むか」であり、**derived/lossy representationをmutation requestへ再投入した時のwrite authority** は独立contractとして弱い。

既出 `Origin-Bound Mutable Views` は「どのowner/revisionのviewか」を扱う。今回はownerが正しくても、**表現そのものが不可逆でwrite値として不適格**という別軸。

### (6) 次に検証すべきこと

**`LossyProjectionMutationBench-v0`**

- secretをGET→redacted previewをそのままSAVE → original secretを保持
- explicit replace → new secretへ変更
- explicit clear → clear
- GET後にsource revisionが変わったpreview → preserve/replaceをstaleに扱えるか
- privacy-filtered memory viewをsaveしても、非表示部分を暗黙削除しない
- Persona summary viewを保存しても、summary textをcanonical self-stateへ丸ごと上書きしない

### (7) 既存デイリーサーベイではなぜ拾いにくいか

LLM memory / HCI / privacy / config API / secret handling の境界にある。memory研究では「derived summary」、security研究では「secret masking」、UI研究では「settings form」と別々に見え、**read representationの意味論がwrite contractへ漏れる問題**として統合されにくい。

### (8) 重要度

**A** — credential破壊だけでなく、長寿命agentではmemory/consent/selfのderived viewがcanonical stateを破壊する同型事故になり得る。

## 5.2 A — Transition-Qualified External Effects under Replay: 状態を復元することと出来事を再び起こすことを分ける

**一次資料**

- OpenClaw PR #156989  
  https://github.com/openclaw/openclaw/pull/156989
- Akka Event Sourcing 公式 docs  
  https://doc.akka.io/libraries/akka-core/current/typed/persistence.html
- Akka Replicated Event Sourcing 公式 docs  
  https://doc.akka.io/libraries/akka-core/current/typed/replicated-eventsourcing.html

### (1) 何が実証済みか

OpenClaw #156989では、数日前にfailure済みの retained subagent taskをrestart時にregistryへ復元すると、`previous=failed, next=failed` のunchanged upsertがbroadcastされ、Web Pushへ「background task failed」が再発火した。

報告されたdeterministic reproductionでは、restartごとに1 pushが出る一方、実際にはそのrestart時点で新規failureはない。さらに `notify_policy: silent` の taskも初回のreal failureでpushされる問題が併存していた。修正後 evidenceでは genuine transition は1回pushし、restart re-projectionは0回になる。

Akka公式docsも、event handlerはreplayに使われるためside effectをそこから直接出すとundesired re-executionになる、と明示している。

### (2) 何が提案・推測段階か

Kamimusuhiの全external effectへ以下を一般化するのは提案。

```text
current_state == FAILED
!=
a failure transition just happened

projection/recovery
!=
effect authorization
```

通知だけでなく、message送信、tool call、billing、relationship signal、wake-up、robot actionまで同じcontractが必要かは要検証。

### (3) 関係するサブシステム / 設計課題

- K-Nerve event routing / notification
- social delivery / relationship signals
- background task / delegation completion
- RecoveryJournal / cold replay
- dream/offline processing
- migration / backup / restore
- distributed embodiment
- observability / incident surfacing

### (4) 借りられる設計・実装アイデア

state projection と external effect emission を分離する。

```text
CommittedTransitionEvent {
  event_id,
  entity_id,
  from_state,
  to_state,
  cause_id,
  policy_epoch,
}

EffectReceipt {
  event_id,
  effect_kind,
  destination,
  disposition,
}
```

- recovery/replay handlerはstateを再構成するだけ
- external effectは **new committed transition event** に対してのみ評価
- effect policy (`silent`, privacy, destination) もevent/receiptへbind
- replay時にreceiptを再利用し、同じeventから新しいeffect attemptを生成しない
- compensation/retryが必要なら「同一effect attemptの再送」と「新規semantic effect」を別IDにする

### (5) Kamimusuhiとの差分

Kamimusuhiには replay dedup horizon、cursor incarnation、attempt-scoped acknowledgement、completion-publication 等が既にある。しかしこれらは主に「同じdeliveryを重複処理しない」「replay streamを正しく読む」契約。

今回は **delivery replay以前に、同じhistorical stateを再投影しただけで新しいexternal effect eventを生成してしまう** ことが問題。transport dedupだけでは根治しない。

### (6) 次に検証すべきこと

**`ReplayTransitionEffectBench-v0`**

1. `RUNNING -> FAILED` の実transition → user notification 1回
2. process restart × N → reconstructed `FAILED`、notification 0回
3. `notify_policy=silent` → 実transitionでも0回
4. 別generationで新しいfailure event → 1回
5. effect送信中のcrash → same effect attemptのretryは許可、semantic eventの二重新規作成は禁止
6. backup/restore先でも既通知historical eventを再pushしない

### (7) 既存デイリーサーベイではなぜ拾いにくいか

event sourcing / recovery semantics / push notification lifecycle の交点。agent研究では「persistent memory」は調べても、**replayが外部世界への作用を再演しない条件**はsystems side-effect disciplineとして埋もれやすい。

### (8) 重要度

**A** — restart/recoveryを高頻度に使う長寿命agentほど、古い感情・failure・social actionを「再体験」ではなく「再実行」してしまう危険が増える。

## 5.3 A — Semantic-Sentinel-Safe Resource Accounting: `unknown` を数値に押し込めてhomeostasisを壊さない

**一次資料**

- Hermes Agent PR #121012  
  https://github.com/NousResearch/hermes-agent/pull/121012
- OpenRouter Auto Router 公式  
  https://openrouter.ai/openrouter/auto
- OpenRouter routing説明  
  https://openrouter.ai/blog/insights/model-routing/

### (1) 何が実証済みか

Hermes #121012は、pricing catalogue由来の負値を実rateとして計算し、session accountingへnegative `estimated_cost_usd`を永続化するreproを示した。

PRのlive-install報告では、1週間・6 profiles・125 sessionsで、OpenRouter dashboard約 `$39.88` に対しlocal aggregateが約 `-$31.4M`。tokens自体は正しく、pricing interpretationだけが壊れていたとされる。

修正はnegative rateを「pricing unavailable / unknown」へ落とし、最終computed amountが負ならstoreしない。`0`はfree routeとして維持する。

OpenRouter公式説明ではAuto Routerはroute先model相当で課金されるため、負の金額をusage creditとして解釈する設計ではない。

調査時点PRはopenなので、数値はPR作者のlive evidenceとして扱い、外部独立再現済みとはしない。

### (2) 何が提案・推測段階か

Kamimusuhiでは monetary costだけでなく、次のresource signalsへ同じ原則を広げる案。

- energy / power
- latency / deadline slack
- token quota
- VRAM / memory pressure
- confidence / quality score
- network health
- privacy/risk budget

`-1`, `NaN`, `∞`, missing, stale は「数値」ではなく epistemic / validity state として型を分けるべき、という一般化は提案段階。

### (3) 関係するサブシステム / 設計課題

- Cognitive Action Router
- Cognitive Budget
- provider selection / local-vs-cloud routing
- K-Nerve telemetry
- homeostasis / active inference系regulator
- economics of long-lived AI
- energy-aware cognition

### (4) 借りられる設計・実装アイデア

```text
Measured<T> =
  Known { value: T, source, observed_at, schema_version }
  | Unknown { reason, source, observed_at }
  | Stale { last_known, age, source }
  | Invalid { raw, reason, source }

Money = NonNegativeDecimal
Energy = NonNegativeQuantity
Probability = Bounded[0,1]
```

重要なのは:

- `Known(0)` と `Unknown` を分ける
- impossible valueを「便利なsentinel」として arithmeticへ通さない
- regulator入力前にdomain validation
- source/versionを保持し、catalogue corruptionをquarantine可能にする
- Unknown時のrouting policyを明示する（conservative fallback / probe / human review 等）

### (5) Kamimusuhiとの差分

Kamimusuhiは cognitive budget / degraded mode / provider routing を持ちつつあるが、**budget signal自体のsemantic validity lattice**は明示が弱い。

homeostasisは入力値が正しいことを前提にすると、negative costが「使うほど予算が増える」という正のfeedbackへ変わり、regulator全体を逆向きにできる。

### (6) 次に検証すべきこと

**`ResourceSentinelAccountingBench-v0`**

各provider/resource sourceへ以下をinjectする。

- `-1`
- `0`
- `None / missing`
- `NaN`
- `+inf`
- unit mismatch
- stale price / stale energy sample
- extreme but valid positive value

assert:

- invalid/unknownがnegative creditにならない
- known zeroはunknownと混同しない
- budget regulatorがinvalid sourceだけをquarantineできる
- provider routerがunknown costを「最安」と誤認しない
- telemetryにraw/source/reasonを残す

### (7) 既存デイリーサーベイではなぜ拾いにくいか

billing catalogue / type systems / control theory / AI routing economics の境界にある。AI surveyではcostを「最適化対象のscalar」として置きがちで、そのscalarが **meaningful quantityか sentinelか** を検証するデータ契約まで掘りにくい。

### (8) 重要度

## 5.4 A級更新 — Guard–Executor Language Inclusion: policy parserがexecutorより狭ければguardは存在しないのと同じ

**一次資料**

- Hermes Agent PR #121009  
  https://github.com/NousResearch/hermes-agent/pull/121009
- LangSec  
  https://langsec.org/

### (1) 何が実証済みか

Hermes #121009は、approval側regexが `***` 後のspaceを必須にする一方、実executor parserはspaceなしも受理するため、guardから不可視なeffectful syntaxが存在したことを再現している。

`***Update File: /repo/.env` や `.ssh/` へのmove targetがapproval path-setに入らず、workspace-session policyでsilent auto-approveされ得た。

### (2) 何が提案・推測段階か

新規原則として増やさず、既出 **Review–Execution Artifact Identity / Semantic Transcoding Integrity / All-Entrypoint Effect Admission** を次のformal contractへ強化する。

```text
For all x accepted by executor:
  semantic_effects(guard_parse(x)) == semantic_effects(exec_parse(x))
```

最低限の弱い条件なら:

```text
L_executor ⊆ L_guard_recognized
```

しかし本命は「二つのparserを同期」ではなく、**一つのcanonical ASTをparseし、そのASTをreviewして、その同じASTをexecuteする**こと。

### (3) 関係するサブシステム / 設計課題

- tool admission / approval
- patch / file / shell effectors
- sensitive path guard
- plugin protocol adapters
- capability security
- runtime assurance

### (4) 借りられる設計・実装アイデア

- parserを一つにする
- `EffectAST` をcanonicalizeしてhash-bind approval
- policyはraw textでなくASTのtarget set / operation kindを見る
- property/fuzz testで executor accepted corpus 全体をguardへ流す
- alternative syntax, whitespace, Unicode, alias, nested path, move targetをgrammar-levelで生成

### (5) Kamimusuhiとの差分

既存のreview–execution artifact identityは「reviewしたものとexecuteするものが同じ」を要求するが、その前段で **review parserがeffectを見落とす** と、同じraw artifactをbindしても安全ではない。

今回の差分はartifact identityから一歩下げて、**semantic interpretation identity**をcontractにする点。

### (6) 次に検証すべきこと

**`GuardExecutorLanguageParityBench-v0`**

- executor grammarからvalid syntaxを生成
- guardが抽出したeffect setとexecutor AST effect setを比較
- path alias / whitespace / Unicode / move source+destination / multi-fileを含める
- fuzz corpusで `exec_effect - guarded_effect` が常にemptyであることをassert

### (7) 既存デイリーサーベイではなぜ拾いにくいか

AI safetyというよりLangSec / compiler front-end / input-language securityの問題。tool authorizationをpolicy問題として検索していると、parser grammarのsubset relationは見落としやすい。

### (8) 重要度

**A級更新** — 新規findingとしては重複だが、security invariantをproperty-test可能な形まで具体化する価値が高い。

## 5.5 A級更新 — Causal-Cut Scoped Destructive Mutation: 遅延Clear/Deleteは「未来に生まれた状態」まで所有しない

**一次資料**

- OpenClaw PR #156990  
  https://github.com/openclaw/openclaw/pull/156990

### (1) 何が実証済みか

OpenClaw #156990では、Side chatのClear requestを送った後、response待ち中に新しいdraft/question/imageを追加すると、遅れて届いたsuccessful Clearが新しいstateまでretireし得た。

merged fixは、Clear click時点でそのoperationが所有していたturns / attachment reads / image payloadsだけを消し、post-click stateを残す。failed Clearでは既存threadを保持する。

### (2) 何が提案・推測段階か

Kamimusuhiのforget / revoke / branch cleanup / relationship resetへ、destructive intentを `causal_cut` とbindする案。

```text
DestructiveIntent {
  target_predicate,
  owner,
  causal_cut / revision,
  requested_at,
  mode: OneShot | StandingPolicy,
}
```

one-shot deleteと「今後も保存するな」というstanding policyを別物にするべき、という一般化は提案。

### (3) 関係するサブシステム / 設計課題

- graceful forgetting / memory deletion
- consent revocation
- relationship reset
- session clear / branch retirement
- multi-device sync
- UI-control plane
- attachment / sensory buffer cleanup

### (4) 借りられる設計・実装アイデア

- destructive request時に対象object IDsまたはrevision cutoffをfreeze
- completion時にcurrent namespace全体を再scanして削除しない
- post-cut writesはone-shot deleteから除外
- 「以後も禁止」は別のretention/admission policyとして表現
- async completionはrequest token / generationへbind

### (5) Kamimusuhiとの差分

`explicit destructive scope` と `operation-intent preservation` は既出なので独立原則にはしない。

差分は **space scopeだけでなくtime/causal scopeも destructive authorityの一部** とすること。`delete(memory/*)` のような名前空間scopeだけでは、response待ち中に追加された新しいmemoryまで巻き込める。

### (6) 次に検証すべきこと

**`CausalCutDestructiveActionBench-v0`**

1. revision RでClear要求
2. Clear pending中にR+1, R+2を書込
3. Clear成功
4. ≤Rのtargetだけ消え、R+1/R+2は残る
5. failure時は何も消えない
6. standing forget policyを明示した場合だけpost-cut writeをadmissionで拒否

### (7) 既存デイリーサーベイではなぜ拾いにくいか

memory deletion / UI async race / temporal databases / consent semanticsの境界。削除を「対象名」の問題として見ると、**いつまでの世界を削除する権限なのか**が抜ける。

### (8) 重要度

**A級更新** — identity continuityとmemory ownershipを両立するには、forgettingが未来の本人の新しい行為を巻き込まないことが重要。

# 10. 今回の結論

今回の中心は、長寿命agentのidentity continuityを「memoryの保存」だけでなく、**representation・event・resource signal・policy parser・destructive intentの意味論を時間を跨いで壊さないこと**として見る点にある。

特に次の3つは独立に追加する価値が高い。

1. **読むための表現は、書くための値ではない。**
2. **過去の状態を再構築することは、過去の作用を再実行することではない。**
3. **unknownは数値ではない。homeostasisへ入れる前に意味論を型にする。**

Guard–executor parser parity と causal-cut destructive mutation は既出原則の強化として取り込み、独立概念の水増しは避ける。
