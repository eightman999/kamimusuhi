## 1. 今回狙った盲点

今回は、通常の agent / memory / identity survey では「ただの入力サイズ制限」「プラグイン hook」「queue bug」「Git の細部」「reactive programming」「API rate limit」に見えて落ちやすい次の境界を重点化した。

1. **budget を materialization 後にだけ検査する問題** — 小さな参照文字列が巨大な file / diff / URL / directory 展開へ化け、Global Workspaceへ入る前に memory / CPU / I/O を使い切る。
2. **effect policy が agent-tool surface にしか存在しない問題** — 同じ semantic action が CLI / dashboard / cron / plugin / remote surface から実行できると、tool gateだけでは system-wide policy にならない。
3. **continuation を queue へ保存しただけで「継続する」とみなす問題** — idle 状態で次の wake source がなければ、durable intent が runnable work に変わらない。
4. **opaque digest / 40-hex をそのまま object identity とみなす問題** — 同じ「SHAらしいもの」でも commit / tag object / tree / blob 等の型が違えば意味が違う。
5. **分散 derived state の transient impossibility** — 各sourceは正しくても非同期伝播の途中で、self-model / body state / authority view が現実には同時成立しない組合せを一瞬公開し得る。
6. **外部 quota の cost unit と cognitive action unit の不一致** — 1 secret = 1 cost と仮定すると、実際には process invocation 単位のaccount-wide quotaをcold startごとに増幅し得る。

### 4.3 A — Continuation Wakeup Closure

**Primary fresh evidence:** Hermes #116619  
https://github.com/NousResearch/hermes-agent/pull/116619

**(1) 何が実証済みか**  
`should_continue=true` のgoal continuationはFIFOに保存されるが、enqueue timingがcurrent-turn drain後だったためidle sessionにconsumer wakeupが存在せず、別messageが来るまで開始されなかった。修正branchはidleならcontinuationを能動dispatchし、busyなら既存turn-drainへ委ね、FIFO orderを保つtestsを通す。

**(2) 何が提案・推測段階か**  
PRはopen。Kamimusuhiで同じFIFO実装を使うわけではない。能動dispatchとstanding watcherのどちらが最適かも未決定。

**(3) 関係するサブシステム / 設計課題**  
background/default cognition、prospective memory、goal continuation、dream/offline processing、deliberation continuation、scheduler、Global Workspace wakeup、K-Core/K-Deep task liveness。

**(4) 借りられる設計・実装アイデア**  
continuation recordを作成するtransactionは、同時に **`runnable` state + wake source / scheduler ownership** を確立する。`PERSISTED_PENDING` と `SCHEDULED/RUNNABLE` を分離し、pending itemに `next_wakeup_owner`, `wake_generation`, `last_wakeup_attempt`, `runnable_since` を持たせる。

**(5) Kamimusuhiとの差分**  
9/13収載の in-flight continuation liveness は「既に走っているrunのtransport/restart後resume」が中心。今回はその前段、**まだ走っていないcontinuationをqueueへ置いた後、誰が次の認知cycleを起こすか**というactivation edgeである。

**(6) 次に検証すべきこと**  
**`ContinuationWakeupClosureBench-v0`**: enqueue直後にproducer turn終了、consumer idle、scheduler restart、duplicate wake、real user inputとの競合をfault-injectし、bounded start latency、exactly-once claim、priority/FIFO preservation、stale continuation suppressionを測る。

**(7) 既存デイリーではなぜ拾いにくいか**  
「永続goal」「scheduler」「prospective memory」を調べても、**保存とwake activationの間にある1 event-loop ordering bug**は実運用差分からしか見えにくい。

**(8) 重要度**  
**A** — request/response外で自発的に継続するKamimusuhiでは、intent persistenceだけでなくwake closureが生命線になる。

### 4.4 A — Object-Kind-Qualified Referential Identity

**Primary fresh evidence:** Hermes #116618 + Git official docs  
https://github.com/NousResearch/hermes-agent/pull/116618  
https://git-scm.com/docs/git-rev-parse  
https://git-scm.com/docs/git-tag

**(1) 何が実証済みか**  
annotated tagはtag object自身のSHAを持ち、commitへdereferenceできる。Hermesでは40-hex形式だけを見て「commit SHA」と解釈したため、正しいtag pinが実checkout時のcommit SHAと不一致になった。`^{commit}` でexpected object kindへpeelすると正しいcheckoutを受理し、異なるcommitは拒否できる。

**(2) 何が提案・推測段階か**  
Kamimusuhiのartifact storeで同じGit-specific failureがあるとは限らない。すべてのcontent-addressed objectへ同じ型体系が必要かは未設計。

**(3) 関係するサブシステム / 設計課題**  
Persona Core model lineage、skill/artifact registry、checkpoint/backup、policy bundle、memory snapshot、software-body update、provenance receipts。

**(4) 借りられる設計・実装アイデア**  
referenceを単なる `digest:string` でなく `TypedObjectRef{scheme, object_kind, digest, resolution_rule}` として扱う。検証では `syntax valid` → `object exists` → `object kind valid` → `resolution/peel valid` → `content/lineage policy valid` を分ける。

**(5) Kamimusuhiとの差分**  
Gitではtag→commitの明確なpeel ruleがある。Kamimusuhiでは `snapshot`, `manifest`, `model weights`, `index`, `derived cache`, `policy` の関係を独自に型付けする必要がある。型を間違えたdigestを「同じidentity」として受理しないことが重要。

**(6) 次に検証すべきこと**  
**`TypedReferentialIdentityBench-v0`**: 同じhash syntaxで異なるobject kind、alias→artifact、manifest→payload、snapshot→derived indexを混在させ、kind mismatch / wrong peel / missing resolution / stale aliasをfail-closedできるか測る。

**(7) 既存デイリーではなぜ拾いにくいか**  
identity continuityではcryptographic hashやprovenanceを重視しやすい一方、**hashが何を指すかというtype system**はSCM/packagingの細部に見えて落ちる。

**(8) 重要度**  
**A** — digestを持つだけではtyped provenanceにならない。誤ったobject kindへの強い検証はcontinuity artifactで特に重要。

### 4.5 A — Derived-State Glitch Freedom

**Backfill sources:** DREAM / distributed FRP / reactive programming literature.

**(1) 何が実証済みか**  
reactive systems研究では、依存入力が非同期に伝播する際に一時的な不整合値（glitch）がderived computationへ見える問題が古くから扱われている。DREAMは causal / glitch-free / atomic propagation を異なるconsistency guaranteeとして整理し、2022年のdistributed FRP研究はsingle-source/complete glitch freedomを狙うpropagation algorithmをsimulated distributed settingで評価している。

**(2) 何が提案・推測段階か**  
これらはAI self-modelやidentity systemを対象にした研究ではない。Kamimusuhiの全derived stateへatomic propagationを要求するのは高コストで、過剰同期になる可能性が高い。

**(3) 関係するサブシステム / 設計課題**  
Embodiment State、self-model derived views、Global Workspace、resource health、permission/consent view、relationship/common-ground projection、multi-device status、observability。

**(4) 借りられる設計・実装アイデア**  
全stateをstrongly consistentにするのではなく、derived viewごとに consistency class を宣言する。

```text
EVENTUAL_OK
CAUSAL
SINGLE_SOURCE_GLITCH_FREE
MULTISOURCE_GLITCH_FREE
ATOMIC_CUT_REQUIRED
```

たとえば「body owner=Device-B」と「actuation credential=Device-A epoch」を同一derived snapshotへ混ぜてはいけないcritical viewでは、dependency epoch/cutが揃うまでpublicationを待つ。

**(5) Kamimusuhiとの差分**  
Kamimusuhiはcanonical writesをContinuity Kernelで守るが、**derived self-description / health / authority projection**は複数ownerから非同期に更新され得る。canonical consistencyだけでは、読み手に一瞬不可能な自己状態を見せる問題を防げない。

**(6) 次に検証すべきこと**  
**`DerivedStateGlitchFreedomBench-v0`**: body migration、credential rotation、consent revoke、model route switch、relationship updateを異なるlatency/orderで注入し、derived self/world viewが禁止組合せを一度でも公開するか測る。eventual / causal / glitch-free方式のlatency costも比較する。

**(7) 既存デイリーではなぜ拾いにくいか**  
distributed systems surveyでも「consistency」はDB/CRDTへ寄り、HCI/self-model側では「最新状態を表示する」議論へ寄る。**reactive dependency graph上のtransient impossible state**という概念は両方の隙間に落ちる。

**(8) 重要度**  
**A** — multi-device embodimentとmechanically grounded self-modelを本気で行うなら、stalenessだけでなくcross-field temporal coherenceが必要。

resource accountingに `logical_items` だけでなく `provider_cost_unit`, `account_scope`, `cold_start_cost`, `batchability`, `shared_daily_budget`, `cache_lifetime` を持つ。budget managerは「1件いくら」ではなく実provider単位でrate-limit debtを観測する。

**(5) Kamimusuhiとの差分**  
Kamimusuhiは長寿命だがmulti-process/multi-deviceなので、個々のnodeが安価でも**同一account quotaを共有**していれば全bodyの合計で枯渇する。これは単なるbilling問題ではなくcognitive organ availabilityの問題になる。

**(6) 次に検証すべきこと**  
**`SharedQuotaAmplificationBench-v0`**: N devices × M cold starts × R resourcesで実request countとquota depletionを計測し、batch/cache/coordinator導入時のavailability・latency・privacy trade-offを比較する。

**(7) 既存デイリーではなぜ拾いにくいか**  
AI economicsではtoken costが中心で、secret managerやconnector APIの**非token・account-wide shared quota**は周辺運用コストとして見落とされやすい。

**(8) 重要度**  
**B** — continuity coreそのものではないが、長寿命・多body化したときの認知資源枯渇とdegraded-mode設計に効く。

## 9. 今回の結論

今回の共通テーマは **「意味的な境界より前に起きることを、free preprocessing / mere plumbing とみなさない」** ことだった。

- referenceを読む前にも resource authority が要る。
- effectを実行する全surfaceに同じpolicy authorityが要る。
- continuationを保存した後にも wake authority が要る。
- digestを比較する前にも object type が要る。
- derived self-stateを公開する前にも cross-source temporal coherence が要る。
- external resourceを使う前にも provider-native cost unit を知る必要がある。

Kamimusuhiのcontinuityを壊すのはcanonical commitだけではない。**canonical boundaryへ到達する前のmaterialization、activation、projection、resource accountingにも、明示的な契約が必要**というのが今回の主要差分である。
