# 3. 要約

今回の中心は、**「正しかった」という事実には有効期限と証拠範囲がある**という点だった。

OpenClawの2件のfresh fixは、requestを準備した時点ではcurrentでも、transport準備やprovider reviewをawaitしている間にcancel・resource retirement・native thread / owner / model / provider変更が起きれば、そのprepared requestはもう実行権限を持たないことを具体的に示した。これは「stale resultを後から適用しない」だけでは足りない。**外部cost/effectを開始する直前に、start-authorityそのものを再検証する**必要がある。

HermesのDiscord修正は別の層を示す。reply先のmessage IDだけが残り、誰の発話か、どのchannelか、bot自身か他者か、何のattachmentを指すかが落ちると、agentは近傍historyから誤って意味を再構成し得る。Kamimusuhiでは会話をmessage node列としてだけでなく、**provenanceを持つdiscourse relation graph**として扱う価値がある。

最後にruntime-assurance研究をbackfillした。各platform単位では規約違反がなくても、複数platformへ禁止目的を分割したりcollective budgetを越えたりすればmission-levelでは違反になる。またmonitoring evidenceが欠けた時、`SAFE`ではなく`UNKNOWN`へ落とす必要がある。これはKamimusuhiのmulti-device embodimentやbranch/specialist cognitionにも直接対応し、**安全判定にはstatusだけでなくevidence completenessが必要**という設計差分になる。

## 4.1 A — Late-Bound Dispatch Currentness Closure: prepare時にcurrentでも、dispatch直前には失効している

**Primary sources**

- OpenClaw PR #155817 — `fix: reject stale Codex turn selections`  
  created: 2026-09-23 01:06:02 JST 頃  
  https://github.com/openclaw/openclaw/pull/155817
- OpenClaw PR #155819 — `fix: stop cancelled completions before provider dispatch`  
  created: 2026-09-23 01:07:15 JST 頃  
  https://github.com/openclaw/openclaw/pull/155819

### (1) 何が実証済みか

#155817では、prepared Codex turnが、準備対象だったnative thread selectionより長生きできた。provider reviewやnative turn acceptanceの途中でhost connectionは再確認されても、**selected thread、live subscription owner、model、provider**は再確認されていなかったため、selectionが入れ替わった後でもstale continuationが進めた。

修正では各`startCodexTurn`ごとにbinding / thread id / live owner / model / providerをcaptureし、provider-review preparation、pre-write dispatch、accepted response、host acknowledgmentまで同じcurrentness判定を運ぶ。11件のstale-selection regressionがmainで失敗し、修正後suiteでは対象24 testsがpassしたと報告されている。またproviderが既にacceptした後は、cleanupを**新しいbindingへ付け替えず、実際にrequestを受け取った元client/threadへ残す**。

#155819では、completionがtransport host準備中にcancelされてもprovider requestが開始できた。PDF extraction pathでもretained resourceの確認とasync facadeの間にwindowがあり、resource retirement後にproviderを呼べた。修正はtransport initializationをawaitした**後、provider invocation直前**にcurrentnessとabort signalを再確認し、PDF側も既存resource claimを同じ境界へ渡す。mainではcancelled/retired caseでもsynthetic provider resultが返ったが、修正後は23 focused casesでcancel/retire後のprovider dispatchが0になると報告されている。

### (2) 何が提案・推測段階か

これをKamimusuhiの全tool / actuator / model delegationへ一律適用することは本surveyの提案である。

すべてのawait後に重いglobal validationを行うべきとは限らない。何をrevalidateするかはeffect severity、resource ownership、dispatch cost、replayabilityで変える必要がある。

## 4.2 A — Referential Conversation-Edge Completeness: reply先IDだけでは社会的意味を復元できない

**Primary source**

- Hermes Agent PR #119257 — `fix(discord): retain reply/forward context for the agent turn`  
  created: 2026-09-23 01:07:39 JST 頃  
  https://github.com/NousResearch/hermes-agent/pull/119257

**Supporting official docs**

- Microsoft Teams SDK / reply-to-message documentation  
  https://microsoft.github.io/teams-sdk/typescript/essentials/sending-messages/  
  https://github.com/MicrosoftDocs/msteams-docs/blob/main/msteams-platform/bots/build-conversational-capability.md

### (1) 何が実証済みか

Hermesの問題では、Discord reply / forwardがagent turnへ`reply_to_id`だけで届き、referenced messageの**author、channel、attachment metadata**が落ちていた。そのためagentが、実際のreply targetではなく近傍history中の無関係な過去bot messageへanchorし得た。

修正はreferenceから以下を抽出して既存event contractへ載せる。

- author id / name
- `is_own`（bot自身か）
- referenced channel id
- text
- attachment filenames
- unresolved referenceでも保持できるchannel情報

relay側もstructured author / channel / message / attachmentを受けつつlegacy形式を維持する。PR記載では新規11 testsのうちmainで7件がRED、修正後GREENとなり、周辺463 testsもpassした。

Teamsの公式SDK/ドキュメントでもquoted replyは元messageとの構造的linkとsender情報を保持するものとして扱われており、単なる文字列再掲ではない。

### (2) 何が提案・推測段階か

Kamimusuhiが全会話を恒久的graph DBへ保存すべき、という主張ではない。

ただしaction判断、relationship memory、common ground、self/other attributionへ使うreply/quote/forwardについては、relation edgeをderived proseへ潰さず構造化して保持する価値が高い、というのが本surveyの提案である。

- common ground
- multi-surface interaction
- self/other distinction
- conversation provenance
- tool/action grounding
- deferred / asynchronous interaction

### (4) 借りられる設計・実装アイデア

message nodeとは別にreference edgeをtyped recordにする。

```text
ConversationReferenceEdge
  edge_id
  source_message_id
  target_message_id
  relation = REPLY | QUOTE | FORWARD | THREAD_PARENT | MENTIONED_ARTIFACT
```

```text

```

成功条件:

- relationship memoryへpromotionする場合はedge provenanceを維持

## 4.3 A — Evidence-Completeness-Aware Collective Safety: local SAFEの集合はglobal SAFEを保証しない

**Primary source / backfill**

  arXiv:2607.23532, 2026-07-26  
  https://arxiv.org/abs/2607.23532
- project/publication page  
  https://www.max-robotics.com/en/research/publications/cms5weves005xrw4smaztxwm5

### (1) 何が実証済みか

報告されたsimulationでは、indirect prompt injectionにより禁止されたcollection taskを**4 platformへ分割**すると、各per-platform monitorでは個別制限を破らないため検出できないが、mission-level compositionではfull provenance付きで検出できた。

ここで実証されているのはsimulation / 当該fabric内の結果であり、一般のAI swarmやKamimusuhiへそのまま性能保証できるわけではない。

# 11. 結論

今回の3つのblind spotは、共通して**「局所的に正しい情報だけでは、実行時の意味や安全性を確定できない」**ことを示す。

```text
prepare時にauthorized
!= dispatch時にもauthorized

message target idがある
!= social referentが十分に復元できる

observed local agentsが全部SAFE
!= collective systemがSAFE
```

Kamimusuhiで最初に実装価値が高いのは **`LateBoundDispatchCurrentnessBench-v0`**。外部model / tool / actuatorを多用するほど、cancel・owner handoff・route change・resource retirementの直後に「古いprepared work」が飛ぶ危険が増える。

次が **`ConversationReferenceEdgeBench-v0`**。長寿命なrelationship / common-groundを扱うなら、発話nodeだけでなくreply/quote/forward edgeの由来を保存する方が、後からLLMに推測させるより安全である。

分散身体を本格化する段階では **`EvidenceCompletenessCollectiveSafetyBench-v0`** を入れ、global verdictの根拠が欠けている時にKamimusuhiが自信満々に`SAFE`を出さないことを機械的に保証したい。
