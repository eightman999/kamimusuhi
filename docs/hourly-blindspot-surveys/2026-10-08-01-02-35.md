## 1. A — Capability Projection Must Be Monotone Through Final Tool Assembly

Primary:

- OpenClaw #166644 — *File-backed memory flush regains ring-zero execution tools after projection*  
  https://github.com/openclaw/openclaw/issues/166644  
  created 2026-10-08 00:37:52 JST

### (1) 何が実証済みか

OpenClaw 2026.9.8 の hidden file-backed memory flush では、いったん tool surface を「read + memory path限定write」へ projection した後、最終 tool assembly で ring-zero discovery/execution controls が再 merge され、restricted maintenance run が unrelated MCP modeling tools を呼べる状態になっていた。

報告された実環境では hidden memory flush が foreground user request の待機中に CAD revision の保存やrenderを実行した。通常の project-file `write` は memory-only guard に拒否された一方、MCP経由の `save_scad` は同じ project 領域へ実際に書き込めた。

つまり個々の guard は局所的には働いていても、**後段の tool merge が authority projection を逆転させた**。

### (2) 何が提案・推測段階か

全 tool assembly を完全に静的にする必要があるとは限らない。動的 tool discovery 自体は有用である。ただし restricted run の capability envelope が決まった後に、別レイヤーが ambient authority を再導入しないことを機械的に保証する必要がある。

### (3) Kamimusuhiのどのサブシステム/設計課題に関係するか

- Background Cognition / Sleep-Dream
- memory consolidation / maintenance
- Cognitive Action Router
- capability security
- runtime-authority-learning boundary
- K-Deep / hidden maintenance runs
- self-improvement / procedural mutation

### (4) 借りられる設計・実装アイデア

tool assembly を「和集合」中心ではなく **capability attenuation の単調性**として表現する。

```text
BaseCapabilities
    -> task projection
    -> policy attenuation
    -> maintenance attenuation
    -> final executable set

invariant:
  final_capabilities ⊆ every authority-bearing upstream envelope
```

各 tool に provenance を付与し、finalization 時に

- origin
- capability class
- effect scope
- required authority
- projection step
- final admission reason

を確認する。

特に hidden maintenance / memory flush / dream run では、**後段 merge による privilege resurrection を禁止**する。

### (5) Kamimusuhiとの差分

Kamimusuhiには least-context maintenance、extension security-envelope inheritance、capability attenuation、layered policy composition が既にある。

fresh 差分は、**projection自体が正しくても、その後の tool registry merge / discovery helper が権限を復活させ得る**ことを実環境で示した点。したがって「projectionされた」ことではなく、**最終 executable tool graph まで attenuation が保たれたこと**が必要。

### (6) 次に検証すべきこと

**`MonotoneCapabilityProjectionAssemblyBench-v0` — P0**

- foreground turn
- memory flush
- dream/offline consolidation
- background review
- delegated subagent
- dynamic MCP discovery
- ring-zero/bootstrap tools
- plugin reload後のtool graph

を交差し、restricted runで後段 merge が capability を増やさないことをassertする。

特に

```text
project -> merge -> normalize -> dynamic discover -> final dispatch
```

の各段階で capability set を記録する。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

capability security は「誰に何を許すか」、memory maintenance は「どう保存するか」、tool registry は「どう発見・組み立てるか」と別々に扱われる。**一度削った権限が assembly pipeline の後半で復活する** failure は境界に落ちやすい。

## 2. A — Destructive Process Ownership Needs Positive Spawn Lineage, Not Temporal Coincidence

Primary:

- Hermes #134611 — *MCP child snapshot attribution can claim and SIGTERM unrelated cron workers*  
  https://github.com/NousResearch/hermes-agent/issues/134611  
  created 2026-10-08 00:29:41 JST

### (1) 何が実証済みか

Hermes の stdio MCP process tracking は spawn 前後の **global child PID snapshot差分**から「このMCPがspawnした子」を推定していた。

別gateway threadが同じ時間窓でcron workerをspawnすると、その unrelated child も差分へ入る。filterには一部 negative exclusion はあるが positive transport ownership proof がなく、そのcron PIDがMCP-ownedとしてledgerへ登録され得る。

報告者は actual source function を抽出した deterministic mechanism replay で、unrelated cron PIDがMCP childとして受理され、transport teardown後に orphan とみなされて **SIGTERM → SIGKILL 対象になる**ことを再現した。

重要なのは、PID / PGID / start-time fingerprint が正しくても防げない点である。fingerprint は「同じprocessか」は証明するが、**そもそも誰がspawnしたか**の誤帰属は直せない。

### (2) 何が提案・推測段階か

過去の production cron `exit -15` がこの機構で実際に殺されたことまでは証明されていない。またOS/APIによって利用可能な parentage primitive は異なる。

### (3) Kamimusuhi関連

- Software Body
- tool/MCP organ lifecycle
- Background Cognition / cron
- process supervision
- cancellation / cleanup
- distributed embodiment
- destructive authority
- fault containment

### (4) 借りられる設計・実装アイデア

destructive cleanup 対象は **positive ownership lineage** で登録する。

```text
spawn_operation_id
owner_organ_id
parent_process_incarnation
child_process_incarnation
creation_receipt
process_group/container/job identity
cleanup_authority
```

「spawn window中に増えたPID」や「名前が似ているprocess」を ownership 証拠にしない。

platform別には、spawn直後の returned handle / pidfd / Job Object / container ID / explicit wrapper token 等を使い、**発生元が確定しないprocessは cleanup対象へpromotionしない**。

### (5) Kamimusuhiとの差分

2026-09-20 surveyでは process incarnation proof を destructive termination に要求した。

今回は一段手前の問題である。

```text
incarnation proof:
  このPIDは、以前見た同じprocessか？

spawn-lineage proof:
  このprocessを、そもそも私のorgan/taskが作ったのか？
```

前者だけでは後者を保証しない。

### (6) 次に検証すべきこと

**`PositiveSpawnLineageCleanupBench-v0` — P0**

- MCP spawn と cron spawn の同時発生
- sibling thread/process
- fast exit / PID reuse
- wrapper → exec
- detached process group
- Windows Job Object
- containerized child
- remote worker

を交差し、destructive cleanup が positive lineage を持つdescendantだけに作用することを確認する。

### (7) なぜ拾いにくいか

OS/process survey は PID identity、agent survey は task ownership、MCP runtime は stdio lifecycle を見る。**時間的に近く生まれたことと因果的に所有していることの違い**は distributed/causal provenance の視点がないと抜けやすい。

### (8) 重要度

**A**

## 3. A update — Accepted Queued Intent Must Outlive the Sender's Wait Budget

Primary:

- OpenClaw #166647 — *queued input is withdrawn when CLI timeout elapses*  
  https://github.com/openclaw/openclaw/issues/166647  
  created 2026-10-08 00:44:30 JST

### (1) 何が実証済みか

busy sessionへ `openclaw agent --session-id ... --message ... --timeout 60` を送ると、inputはいったん `session_pending_inputs` に `state=queued` として入り、UIにも見える。

しかし active turn が caller timeout を超えると、その input が `cancelled` へ変更され、receiver agentへ一度も届かない。報告環境では work-pump 10件中8件がこの形で失われた。

同じcommandを `--timeout 900` にすると、active turn終了後に queued input がconsumeされ正常応答した。

したがって **senderが「待つのをやめた」ことが、すでにaccepted/queuedされたsemantic intentの取消しへ暗黙変換**されている。

### (2) 何が提案・推測段階か

caller abortが必ずintent custodyを維持すべきとは限らない。明示的な「送信もキャンセル」APIは必要である。問題は wait timeout と semantic cancellation が同じsignalになっていること。

### (3) Kamimusuhi関連

- Event Bus / ingress
- Expected Continuation
- standing steering / work pump
- sociality
- durable intent
- orchestration
- delivery acknowledgement
- retry/recovery

### (4) 借りられる設計・実装アイデア

最低限、

```text
enqueue acceptance
sender wait lifetime
delivery/consumption lifetime
semantic cancellation authority
```

を分ける。

accepted queue itemには

```text
intent_id
accepted_at
custody_owner
delivery_state
expiry_policy
cancel_authority
cancel_reason
```

を持たせ、caller-side timeoutは `WAIT_EXPIRED` にだけ作用する。

semantic withdrawal は別の explicit `CancelIntent(intent_id)` として処理する。

### (5) Kamimusuhiとの差分

AcceptedRequestReplaySafety、ContinuationWakeupClosure、retry/deadline closure は既出。

fresh 差分は **execution前のaccepted intentそのものが、producerの待機budgetに引きずられて消える**こと。retry権限やwake path以前に、custody ownershipの問題である。

### (6) 次に検証すべきこと

**`AcceptedIntentCustodyVsCallerWaitBench-v0` — P0**

- busy receiver
- sender timeout
- sender process exit
- network disconnect
- explicit cancel
- receiver restart
- queue expiry
- duplicate resend

を交差し、waiter disappearanceだけでaccepted intentが消えないこと、取消し時にはexplicit receiptが残ることを確認する。

### (7) なぜ拾いにくいか

CLI timeoutはUX、queueはruntime、conversation steeringはsocial semanticsとして別々に設計されるため、**wait lifetimeがintent lifetimeを支配する**結合が見落とされやすい。

### (8) 重要度

**A update**

## 4. B update — Effective Cognitive-Organ Selection Must Be Persisted Even When It Was Only the Default

Primary:

- Hermes #134626 — *gateway session resume inherits warmup model instead of session's prior model*  
  https://github.com/NousResearch/hermes-agent/issues/134626  
  created 2026-10-08 00:44:46 JST

### (1) 何が実証済みか

Hermes では session中に明示 `/model` override を行った場合はmodel選択がpersistされる一方、ambient/config defaultとして実際にmodel Aがturnを担当していても、そのeffective serving modelはsession stateへ保存されない。

gateway restart後は warmup/config state のmodel Bがsessionへ入り、stored promptを「stale runtime identity」と判定してB向けにrebuildし、そのまま別modelで応答した。

報告例では prior turn を `upstage/solar-pro4:free` が担当していたsessionが、restart後に `z-ai/glm-5.3-flash` へsilent switchした。

### (2) 何が提案・推測段階か

全 session が常に同じmodelへ固定されるべきではない。model消失、quota、policy、hardware failure等ではrebindが必要。ただし rebind は continuity event として明示されるべき。

### (3) Kamimusuhi関連

- Models are organs, not owners
- K-Core / K-Edge / K-Deep resource binding
- Computational Embodiment
- session continuity
- provider/model lineage
- Persona projection
- restart / migration

### (4) 借りられる設計・実装アイデア

explicit overrideの有無ではなく、各turnで **effective serving identity** を記録する。

```text
logical_role
effective_provider
effective_model
runtime_generation
selection_reason = EXPLICIT | DEFAULT | FALLBACK | POLICY | RECOVERY
valid_from / valid_until
```

resume時には last-effective organ をcontinuity inputとして扱い、利用不能なら visible/traceableな `OrganRebind` eventを作る。

### (5) Kamimusuhiとの差分

model switch projection、runtime identity reuse、embodiment stateは既出。

fresh 差分は **「defaultだから永続化しない」という実装上の省略が、restart後には意味のあるcognitive-organ changeになる**点。implicit effective stateもcontinuity上重要ならmaterializeする必要がある。

### (6) 次に検証すべきこと

**`ImplicitEffectiveOrganContinuityBench-v0` — P1**

- explicit model
- ambient default
- policy-routed model
- fallback model
- restart
- quota exhaustion
- model removed
- local↔remote rebind

を交差し、silent organ driftを検出する。

### (7) なぜ拾いにくいか

config systemではdefaultは「保存不要」、LLM servingではmodelは「交換可能」、identity architectureではmodelは「ownerではない」。しかし**ownerではないことと、どのorganが直前まで認知を担ったかを忘れてよいことは別**。

### (8) 重要度

## 5. B update — Cognitive Budget Needs Attempt-Level Accounting Across Auxiliary Inference Paths

Primary:

- Hermes #134621 — *proxy inference lacks request/usage accounting*  
  https://github.com/NousResearch/hermes-agent/issues/134621  
  created 2026-10-08 00:39:23 JST
- OpenClaw #166623 — *model_call_ended carries no per-call token usage*  
  https://github.com/openclaw/openclaw/issues/166623  
  created 2026-10-07 23:19:18 JST

### (1) 何が実証済みか

Hermesではtool-launched workflowがbuilt-in `hermes proxy` を通して main conversationとは別providerへ推論requestを送れるが、parent chatのusage recordsにはそのrequestが残らない。loopback reproductionではupstream responseにrequest ID / token usage / costが含まれていても、session usage tableへ保存された行は0だった。

OpenClawでは逆に real model callごとのstart/end hookは存在するものの、`model_call_ended`にusageがなく、token/costはturn集約値しか得られない。1 turn内で5 real model callsが起きても、pluginからは各callへcostを配賦できないことが実traceで確認されている。

### (2) 何が提案・推測段階か

provider側が常に正確なper-request costを返すとは限らない。またprivacy上、prompt/response本文をaccounting journalへ保存すべきではない。

### (3) Kamimusuhi関連

- Cognitive Budget
- K-Deep / external frontier models
- tool-launched inference
- proxy / auxiliary models
- self-improvement
- observability / telemetry
- economics of long-lived AI
- retry / ambiguous billing

### (4) 借りられる設計・実装アイデア

budget ledger の最小単位をturnだけでなく **inference attempt** にする。

```text
attempt_id
parent_cognitive_episode
origin = MAIN | TOOL_PROXY | AUXILIARY | JUDGE | MEMORY | DREAM
provider / endpoint / model
start/end
outcome
request/generation id
tokens/cache/reasoning usage
provider-reported cost
estimated cost
usage_status = CONFIRMED | PARTIAL | UNKNOWN
predecessor/retry relation
```

同じprovider requestを複数layerが観測した場合はcorrelationして二重計上しない。

### (5) Kamimusuhiとの差分

Composite Cognitive Resource Accountingやrun resource accountingは既出。

fresh 差分は、**turn集約だけでは tool-loop 内部のcall分布が見えず、auxiliary/proxy inferenceは親session ledgerから完全に消え得る**こと。長寿命agentでは「見えない外部認知」がcost、quota、privacy、failure attributionを歪める。

### (6) 次に検証すべきこと

**`InferenceAttemptBudgetClosureBench-v1` — P1**

- 1 turn / N model calls
- tool-launched proxy
- judge/evaluator call
- memory summarizer
- retry after stream interruption
- provider fallback
- missing final usage
- duplicate telemetry

を交差し、総costとattempt graphのreconciliation、UNKNOWN扱い、double-count preventionを測る。

### (7) なぜ拾いにくいか

LLM observabilityはturn/session集計、billingはprovider request、agent runtimeはtool invocationを単位にするため、**cognitive work graphのどの辺で実推論costが発生したか**が分断される。

### (8) 重要度

## 結論

今回の最重要差分は、**補助機構のlifetimeやassembly orderをsemantic authorityへ漏らさないこと**である。
