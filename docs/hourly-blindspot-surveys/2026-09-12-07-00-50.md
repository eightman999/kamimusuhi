## 2. 今回狙った盲点

今回は、通常の agent / memory / ALife survey の分類からさらに一段外側にある次の境界を優先した。

1. **formal specification と実 runtime の間の conformance gap** — verifier が正しくても、実装が検証済みモデルと違えば保証は抜ける。
2. **attestation と source-level reproducibility の間の gap** — enclave measurement が正しくても、その measurement がどの source/build 由来か追えなければ「何を信頼したか」を説明できない。
3. **weights と deployed model state の間の gap** — bit-identical weights でも inference 時の state が変われば、公開評価や削除監査の verdict が動く場合がある。
4. **sensor packet identity uncertainty** — sensor provenance field 自体が壊れたり入れ替わった場合、hard binding ではなく source attribution を推定問題として扱う必要がある。
5. **inference substrate を安全 telemetry に再利用する可能性** — speculative decoding の draft/target disagreement を性能最適化以外の integrity signal として使えるか。
6. **multi-agent coordination の recurrent safety** — best outcome や平均 reward ではなく、長期反復で「悪い領域に再帰的に留まらない」ことを評価できるか。
7. **日本語圏 discovery** — Zenn / note / Qiita で、一次資料へ遡って今回の新規 invariant を上回る実装知がないか。

## 4. 要約

今回は **有意な新規発見あり**。

最大の差分は、Kamimusuhi がすでに持つ **verification adequacy** の次に、もう一段別の境界が必要だと分かったことである。

`From Specs to Apps` は Signal / WhatsApp の実装を instrument し、formal protocol model と observed runtime execution の conformance を SpecMon で監視する。formal model 側で authentication / secrecy を検証できても、実アプリが同じ model に従っている保証は自動ではない。実際、monitoring は original libsignal と WhatsApp fork の未文書化差分を発見し、故意に注入した security fault も検出した。Kamimusuhi では、**`property verified != runtime implementation conforms to the verified model`** を明示し、Continuity Kernel / Effect Acceptance / StopLifecycle / capability state machine について、実行 trace を検証済み transition system と照合する `RuntimeConformanceMonitor` を候補にする価値が高い。重要度 **S**。

第二に、TEE の remote attestation には source-level の別の穴がある。115 deployment を調べた研究では **91% が reproducible build ではなく、80% が source と reference build の両方を提供していなかった**。attestation は「この measurement の binary が走っている」を強く言えても、verifier がその measurement を review 可能な source へ再現可能に結び付けられなければ、identity / authority critical code の trust anchor として不十分である。Kamimusuhi が secure enclave を Continuity Kernel や key owner に使う場合、**`attested measurement != source-identifiable implementation`** を hard boundary とし、`AttestationProvenanceChain` を要求する候補を **A+** とした。

第三に、model migration / unlearning / Persona Core distillation では **weights だけを artifact identity とみなすと足りない**可能性がある。`Published Unlearning Numbers...` は 263 released checkpoint を監査し、trainable weights を byte-identical に保ったまま batch-normalization の deployed state を retained data で refit すると、221 checkpoint 中47が自身の seed spread を越えて動き、公開 pass/fail verdict も一部反転した。一方、removed data がその state に残っていることが主因ではないという control も示している。Kamimusuhi では `model_hash == same` を behavioral sameness とせず、**weights + buffers + adapters + quantization/calibration + tokenizer/template + preprocessing/runtime state** を `ModelArtifactClosure` として versioning する案を **A+** とした。論文が直接実証するのは BN-bearing vision model の deployed normalization state であり、他 state への一般化は設計仮説として区別する。

第四に、distributed embodiment の sensor provenance そのものが壊れる場合を扱う研究があった。`Fusion Estimation ... Disrupted Identities` は device identity allocation の混乱、protocol defect、識別子不足により packet component が permutation される問題を明示し、posterior arrangement probability による Bayesian fusion と greedy arrangement 推定を示す。Kamimusuhi の sensory event は source ID を持つだけでは足りず、**`claimed source != authenticated transport != inferred physical source`** を区別し、曖昧な attribution は probability / quarantine を維持する設計が有用である。重要度 **A**。

第五に、SpecGuard は speculative decoding の draft-token acceptance shift を backdoor trigger の runtime signal に転用する。Kamimusuhi ではこれを security proof にはせず、K-Core / local Persona Core の **non-canonical InferenceIntegrityTelemetry** として利用する余地がある。重要度 **A-**。最後に TNBR は multi-agent submodular coordination について recurrent class の Performance / Safety bound と両者の waterbed trade-off を与える。Kamimusuhi への直接適用は遠いが、internal multi-agent / organ orchestration を平均 reward だけでなく **bad recurrent region を避ける性質**で見る設計語彙として **B+** とした。

## 5.1 From Specs to Apps — formal proof と production execution の間を監視する

**Source:** Moustafa Said, Aurora Naska, Kevin Morio, Robert Künnemann, *From Specs to Apps: Verifying and Monitoring Models of Signal and WhatsApp*, arXiv:2609.11882, 2026-09-10, full version of ACM CCS 2026 paper  
**Primary:** https://arxiv.org/abs/2609.11882  
**Importance:** **S**  
**Blind-spot class:** runtime verification / implementation conformance / formal-methods deployment gap

### (1) 何が実証済みか

研究は WhatsApp Web と Signal Desktop を instrument し、network / cryptographic component との interaction を capture して Tamarin 互換の multiset-rewrite model を構築した。Signal protocol の core component について authentication / secrecy property を formal に検証したうえで、SpecMon を使って **observed execution が formal model に conform するか**を runtime monitoring している。

報告上の重要点は次の通り。

- WhatsApp Web 実装についての model と、Signal original protocol の詳細 model を構築。
- monitoring は trusted event extraction / symbolic abstraction に相対して observed execution の conformance を確認。
- original `libsignal` と WhatsApp fork の **previously undocumented differences** を発見。
- deliberately injected security faults を runtime monitoring で検出。
- measured setting では low overhead を報告。
- WhatsApp Web model 作成、instrumentation、fuzzing、experiment まで約3 person-weeks。

### (2) 何が提案・推測段階か

- Kamimusuhi の Continuity Kernel state machine に SpecMon / Tamarin をそのまま採用すべきとは示されていない。
- event extractor / abstraction layer が誤っていれば monitoring の保証も崩れる。論文自身も conformance は trusted event extraction と symbolic abstraction に相対する。
- neural policy / LLM internal reasoning を formal model 化できるという話ではない。
- monitor が通ったことは policy 自体が正しいこと、epistemic output が正しいこと、identity continuity が保たれたことを自動的には意味しない。

### (3) Kamimusuhi のどこに関係するか

- Continuity Kernel
- Mutation / Activation Gate
- Effect Acceptance / ActionRiskEnvelope
- StopLifecycle
- capability / authority lifecycle
- background worker / outbox / delivery state machine
- formal verification / runtime assurance / observability

### (4) 借りられる設計・実装アイデア

**VerificationAdequacyReport と RuntimeConformanceReceipt を別物にする。**

```text
VerifiedModel
  model_id
  model_version
  properties[]
  proof_artifact
  proof_tool_version
  adequacy_report_ref

RuntimeConformanceReceipt
  runtime_component_id
  implementation_digest
  model_id
  event_extractor_version
  abstraction_version
  trace_window
  observed_transition_count
  conformance: PASS | VIOLATION | UNKNOWN
  violations[]
  monitor_version
  generated_at
```

特に次を hard distinction とする。

```text
formal property verified
!= verification harness adequate
!= deployed implementation conforms
!= current effect authorized
!= final effect safe
```

### (5) Kamimusuhiとの差分

Kamimusuhi はすでに verification adequacy、Runtime Assurance、Effect Acceptance を扱っている。しかし現行 docs では **「証明した state machine と実 runtime adapter / fork / implementation が同じ transition semantics を守っているか」**を継続監視する contract はまだ薄い。

これは verification adequacy の再掲ではない。前者は「正しい性質を正しく検証しているか」、本候補は「検証対象モデルと deployment が実際に一致しているか」を扱う。

### (6) 次に検証すべきこと

`ImplementationDriftBench`:

1. Continuity / Effect / Stop の小さな executable reference state machine を作る。
2. reference model へ property test / model check を行う。
3. runtime adapter に意図的な drift を注入する。
   - transition skip
   - stale authority epoch accepted
   - `STOP_ACK` だけ出して effect path を残す
   - success-before-side-effect-confirmation
   - retry で duplicate effect
4. event extractor で trace を作り、offline/online monitor が drift を検出できるか比較する。
5. false positive、detection latency、trace overhead、extractor failure を測る。

### (7) 既存 daily ではなぜ拾いにくいか

「formal verification」「agent safety」を普通に検索すると proof / verifier の話へ寄りやすく、**verified model と shipped implementation の間の deployment conformance** は protocol-security / runtime-verification の文脈に埋もれるため。

### (8) 重要度

**S** — Continuity Kernel のような narrow trusted core を形式化する場合、proof と runtime の binding がないと「正しく証明した別物」が動く危険が残る。

## 5.2 TEE build reproducibility — attestation は source provenance ではない

**Source:** Annika Wilde et al., *“They don't care about this”: A Systematic Study of TEE Build Reproducibility in the Wild*, arXiv:2609.11411, ACM CCS 2026  
**Primary:** https://arxiv.org/abs/2609.11411  
**Importance:** **A+**  
**Blind-spot class:** secure enclaves / reproducible builds / attestation provenance / supply-chain trust

### (1) 何が実証済みか

Intel SGX / Intel TDX / AMD SEV を含む **115 TEE deployment** を技術調査し、次を報告している。

- **91% が reproducible ではなかった。**
- **80% が source code と reference build の両方を提供していなかった。**
- SGX project 50件の maintainer に連絡し、12 developer へ interview。reproducibility を priority と答えたのは1人。
- timestamp のような比較的直しやすい問題だけでなく、multi-stakeholder project で build environment を control できない ecosystem-level problem を確認。

論文の中心命題は、remote attestation が返す cryptographic measurement を original source code へ trace するには reproducible build が不可欠だというもの。

### (2) 何が提案・推測段階か

- 91% という値を全 confidential-computing ecosystem へ一般化はできない。
- reproducible build が成立しても source code 自体が安全・正しいとは限らない。
- TEE 自体の side-channel / microarchitectural risk を解決する研究ではない。
- Kamimusuhi が TEE を必須採用すべき根拠ではない。

### (3) Kamimusuhi のどこに関係するか

- Continuity Kernel の将来 trusted deployment
- key / credential owner
- canonical-head signing / lineage receipt
- K-Core secure execution
- remote organ attestation
- supply-chain provenance
- zero-trust / secure enclave watchlist

### (4) 借りられる設計・実装アイデア

`attestation_verified=true` だけを trust signal にしない。

```text
AttestationProvenanceChain
  component_id
  source_repo
  source_commit
  source_tree_digest
  build_recipe_digest
  toolchain_digest
  dependency_lock_digest
  build_environment_digest
  reference_binary_digest
  reference_measurement
  observed_measurement
  reproducible_build_status
  reproducer_count
  builder_attestations[]
  enclave_type
  attestation_epoch
```

境界:

```text
measurement matches
!= binary corresponds to reviewed source
!= source is correct
!= runtime policy is correct
!= canonical identity authority is justified
```

### (5) Kamimusuhiとの差分

既出の partial-TEE finding は **どの node が trusted か / quorum topology** の問題、TRACE は **execution evidence** の portable projection を主に扱った。本候補はそのさらに下で、**「measurement と source の対応そのものが再現可能か」**を扱うため独立した差分である。

### (6) 次に検証すべきこと

`RebuildAttestationBench`:

- deterministic container / Nix 等で tiny Continuity-Kernel-like binary を build。
- timestamp、dependency update、compiler version、generated file、link order を意図的に揺らす。
- source commit → reproducible binary → reference measurement → runtime measurement の chain がどこで切れるか記録。
- `measurement-only` trust policy と `reproducible-source-bound` policy を比較。

現時点で TEE hardware を用意しなくても、まず build closure / reference measurement の mock で contract を検証できる。

### (7) 既存 daily ではなぜ拾いにくいか

secure enclave を「trusted hardware」「remote attestation」の一語でまとめると、**attested binary を人間が読める source へ戻す build-system の問題**が supply-chain / reproducibility 研究側へ埋もれるため。

### (8) 重要度

**A+** — 今すぐ mandatory ではないが、continuity authority を enclave 化するなら採用前に解かなければならない trust-chain の穴。

## 5.3 Published Unlearning Numbers... — model identity は weights だけでは閉じない

**Source:** Junlong Shen, Xingyu Li, *Published Unlearning Numbers Move Per Checkpoint, and Not Because the Removed Data Survives: An Audit of 263 Released Batch-Normalized Checkpoints*, arXiv:2609.11490, 2026-09-10  
**Primary:** https://arxiv.org/abs/2609.11490  
**HTML:** https://arxiv.org/html/2609.11490v1  
**Importance:** **A+**  
**Blind-spot class:** deployed model state / unlearning audit / model lineage / non-parameter state

### (1) 何が実証済みか

論文は released batch-normalized checkpoint の trainable parameter tensor `θ` と、inference 時に使う deployed normalization state `φ` を分離して監査した。

主要結果:

- 263 checkpoint はまず shipped state のまま自身の published number を再現できるものだけを対象化。
- 221 checkpoint を10回の refit で検査し、**47 checkpoint が forget accuracy で ±1.2pp margin を越えて displacement**。retain 39、test 40も displacement。
- **12 published verdict が threshold を crossing**、うち4は measured recalibration budget を越え、2は replicate 全てで越えた。
- 20 checkpoint の control では removed record を fitting pool に混ぜても published cell の shift は小さく、主因は removed data の残存ではなく shipped state の staleness と整合。
- self-trained population では **90/90 の pair が trainable weights bit-identical で buffer state だけ異なる** intervention を構成し、deployed state が weights だけでは決まらない behavior を担えることを示した。
- quantization scale を扱った別 deployed-state channel では同じ種類の verdict displacement は観測されず、すべての non-parameter state が同様に危険だとは主張していない。

### (2) 何が提案・推測段階か

- 直接の対象は主に BN-bearing vision model。Transformer LLM の KV cache、RoPE scaling、tokenizer、adapter、quantization metadata 等へ同じ magnitude の effect があるとは未実証。
- この結果は「unlearning が失敗して removed data が残った」という主張ではない。むしろ removed-data provenance が主因ではない control を含む。
- Persona Core の identity を全 runtime bit で固定すべき、という結論ではない。

### (3) Kamimusuhi のどこに関係するか

- Persona Core model lineage
- model migration / upgrade continuity test
- future offline weight consolidation
- forgetting / unlearning / deletion audit
- rollback checkpoint
- local inference backend switching
- reproducibility / evaluation provenance

### (4) 借りられる設計・実装アイデア

model version を `weights_hash` 一個で表さない。

```text
ModelArtifactClosure
  trainable_weights_digest
  non_trainable_buffers_digest
  adapters[]
  quantization_manifest
  calibration_state_digest
  tokenizer_digest
  chat_template_digest
  preprocessing_digest
  inference_config_digest
  runtime_backend_version
  architecture_config_digest
  closure_digest
```

そして:

```text
same weights
!= same deployed model state
!= same measured behavior
!= same continuity evaluation result
```

`PersonaCoreLineageReceipt` は weights と deployment closure の両方を参照できるようにする。

### (5) Kamimusuhiとの差分

既出の weight-level privacy は「経験を weights に蒸留すると DB deletion だけで消去を保証できない」という privacy 問題だった。本候補は **同じ weights でも auxiliary deployed state により behavior / audit verdict が動く**という evaluation / lineage 問題であり別レイヤー。

### (6) 次に検証すべきこと

`DeploymentStateClosureBench`:

- 小型 local model / classifier で weights を固定し、behavior-affecting auxiliary state を一つずつ変える。
- Transformer 系では tokenizer/template、adapter、quant config、generation defaults、runtime kernel/version、cache warm-state などを分類。
- `weights-only identity` と `closure identity` のどちらが behavioral regression を説明できるか測る。
- future unlearning/distillation では pre/post artifact closure を必ず保存し、評価器がどの closure を読んだかを receipt 化する。

### (7) 既存 daily ではなぜ拾いにくいか

unlearning survey は通常「忘れた情報が weights に残るか」に焦点が当たり、**parameter ではない deployed state が audit verdict を動かす** release-engineering / model-artifact 問題は落ちやすい。

### (8) 重要度

**A+** — Persona Core を将来学習・蒸留・移行するなら、model lineage と continuity benchmark の artifact boundary を誤ると再現性が壊れる。

## 5.4 Disrupted Identities in Multi-sensor Fusion — sensor provenance 自体を疑う

**Source:** Haoyuan Xu, Yuzhe Li, *Fusion Estimation in Multi-sensor Systems for Data Packets with Disrupted Identities*, arXiv:2609.11062, 2026-09-10  
**Primary:** https://arxiv.org/abs/2609.11062  
**Importance:** **A**  
**Blind-spot class:** sensor identity / multi-device embodiment / uncertain provenance / control theory

### (1) 何が実証済みか

研究は、multi-sensor system で受信 packet の identity が device allocation confusion、communication protocol defect、identifier 不足などにより誤ると、data component が random shuffle / permutation され fusion performance が劣化する問題を扱う。

- permutation / symmetry group で packet arrangement uncertainty をモデル化。
- posterior arrangement probability を使う Bayesian fusion algorithm を提示。
- likely arrangement を推測する greedy algorithm を提示。
- 両 algorithm が expectation error-bounded であることを示す。
- prior arrangement 情報が乏しい場合に EM を使って補う方法と convergence proof を提示。
- numerical simulation で評価。

### (2) 何が提案・推測段階か

- Kamimusuhi の sensor event stream で同じ probability model が最適とは限らない。
- malicious spoofing / credential theft / Byzantine sensor を直接扱う研究ではない。
- identity continuity の研究ではなく、measurement fusion の attribution problem である。
- numerical simulation から実世界の multi-device setup への一般化には追加実験が必要。

### (3) Kamimusuhi のどこに関係するか

- K-Edge / K-Nerve sensory event pipeline
- distributed embodiment
- multimodal fusion
- sensor registration / hot-swap
- device reconnect / migration
- canonical sensory evidence provenance
- body state / sensor health

### (4) 借りられる設計・実装アイデア

sensor source を単一 string field として確定させすぎない。

```text
ObservationAttribution
  event_id
  claimed_sensor_id
  authenticated_transport_id
  registered_surface_id
  candidate_physical_sources[]
  source_probability[]
  attribution_method
  sequence_context
  calibration_epoch
  confidence
  disposition:
    BOUND | AMBIGUOUS | QUARANTINED | REJECTED
```

```text
packet arrived on channel X
!= packet was produced by sensor X
!= observation is safe to fuse as sensor X
```

### (5) Kamimusuhiとの差分

現行 sensory-event 方針は time / provenance を重視するが、provenance field が **正しく bind されていること自体**を不確実量として扱う設計は薄い。Bio-Memory / person binding や SoulAuth の主体認証とも異なり、これは物理 sensor packet の source attribution。

### (6) 次に検証すべきこと

`SensorPermutationBench`:

- camera / mic / IMU 相当の synthetic multi-sensor streams を作る。
- source ID swap、packet reorder、reconnect 後の stale ID、duplicate ID、missing ID を注入。
- hard-ID fusion / posterior attribution / quarantine-first を比較。
- metric: state-estimation error、wrong-source canonicalization、recovery latency、false quarantine。

将来、実カメラ/マイクを複数端末へ置く前に simulation だけで開始できる。

### (7) 既存 daily ではなぜ拾いにくいか

multimodal perception は modality fusion / representation alignment へ寄りやすく、**device identity metadata の破損を推定対象にする control-theory 問題**は agent / robotics keyword では見落とされやすい。

### (8) 重要度

**A** — network-native body を持つ Kamimusuhi では、「何を観測したか」以前に「どの器官が観測したか」が canonical evidence の意味を変える。

## 5.5 SpecGuard — speculative decoding を integrity telemetry にする

**Source:** Rui Wen, Ahmed Salem, Andrew Paverd, Mark Russinovich, Zheng Li, *SpecGuard: Inference-Time Backdoor Detection For Free*, arXiv:2609.11799, 2026-09-10  
**Primary:** https://arxiv.org/abs/2609.11799  
**Importance:** **A-**  
**Blind-spot class:** inference runtime security / speculative decoding / model health telemetry

### (1) 何が実証済みか

SpecGuard は speculative decoding の target verification が元から計算している signal を backdoor detector に転用する。

- clean draft model が token を提案し、target model が verify する通常の speculative decoding を利用。
- backdoor trigger で target が attacker behavior へ shift する一方、clean draft はその shift を予測しないため、draft-token acceptance rate が変化することを利用。
- diverse backdoor types / model families で triggered behavior を検出し、input-level filter が見逃す stealthy case も扱うと報告。
- attacker がこの signal を抑えるには backdoor 自体を弱める必要がある条件を形式化。
- **zero added model-computation cost** と主張する。これは「追加 generation pass を不要にする」という意味であり、monitoring 全体の overhead が物理的にゼロという意味には読み替えない。

### (2) 何が提案・推測段階か

- speculative decoding を使わない backend では signal が存在しない。
- draft model が clean / sufficiently independent であるという assumption が重要。
- all backdoors / model compromise を検出する security proof ではない。
- ordinary hallucination、policy drift、memory poisoning を一般に検出するものではない。

### (3) Kamimusuhi のどこに関係するか

- local Persona Core / K-Core inference
- llama.cpp / vLLM speculative path
- model upgrade health
- runtime assurance
- Cognitive Action Router escalation
- observability / anomaly detection

### (4) 借りられる設計・実装アイデア

performance counter を security/cognition telemetry として reuse する発想。

```text
InferenceIntegrityTelemetry
  target_model_id
  draft_model_id
  target_lineage
  draft_lineage
  acceptance_rate
  baseline_distribution_ref
  anomaly_score
  detector_version
  window
  disposition:
    NORMAL | SUSPECT | QUARANTINE_RECOMMENDED
```

これは canonical belief ではなく **operational health sensor** とする。

### (5) Kamimusuhiとの差分

既存 Runtime Assurance / EpistemicAdmissionGate は action/result の境界を主に見る。本候補は **inference serving path 内にすでに存在する draft-target disagreement** を低追加コストの integrity signal にする点が異なる。

### (6) 次に検証すべきこと

`BackdoorPhysiologyBench`:

- speculative decoding baseline を local open-weight model で構成。
- benign distribution で acceptance-rate baseline を取得。
- 公開 backdoor benchmark / controlled trigger を使い anomaly detection を測る。
- model update / quantization / domain shift による false positive を測る。
- compromised draft / correlated model lineage 条件も含める。

### (7) 既存 daily ではなぜ拾いにくいか

speculative decoding は通常 throughput / latency 最適化として追われ、**推論高速化の内部 disagreement signal を model integrity sensor にする**安全研究は performance survey と security survey の境界に落ちるため。

### (8) 重要度

**A-** — backend 条件付きだが、Kamimusuhi の「実 runtime state から self/health を grounded に取る」方針と相性が良い。

## 5.6 TNBR — multi-agent coordination を「最良状態」ではなく recurrent safety で見る

**Source:** Vartika Singh, Philip N. Brown, *Truncated Noisy Best-Response Algorithms: Toward Game Theoretic Learning with Safety Guarantees*, arXiv:2609.11863, 2026-09-10  
**Primary:** https://arxiv.org/abs/2609.11863  
**Importance:** **B+**  
**Blind-spot class:** game theory / recurrent dynamics / multi-agent safety / coordination

### (1) 何が実証済みか

submodular maximization objective の game に対し、agent が asynchronous / stochastic に best-response payoff の近傍から action を選ぶ TNBR family を定義し、対応する Markov chain の recurrent class に bound を与える。

- **Performance bound:** high-value recurrent state が存在することを保証。
- **Safety bound:** arbitrarily bad recurrent state を含まないことを保証。
- 両者に **waterbed-like trade-off** があり、poor Safety guarantee の game は favorable Performance guarantee を持つという関係を導く。

### (2) 何が提案・推測段階か

- LLM multi-agent system / Kamimusuhi organ orchestration に直接適用された研究ではない。
- submodular objective と discrete action game の仮定が Kamimusuhi の cognition にそのまま当てはまるわけではない。
- safety の意味はこの game class 内の objective bound であり、alignment / security / physical safety 全般を意味しない。

### (3) Kamimusuhi のどこに関係するか

- K-Edge / K-Core / K-Deep resource coordination
- optional multi-agent / branch-based cognition
- distributed organ scheduling
- collective / branching identity experiments
- degraded-mode strategy selection
- compute / tool budget allocation

### (4) 借りられる設計・実装アイデア

multi-agent controller の評価を average reward / best episode だけにしない。

```text
CoordinationRecurrenceProfile
  state_partition
  recurrent_regions[]
  worst_recurrent_utility
  best_recurrent_utility
  unsafe_region_recurrence_rate
  recovery_probability
  convergence_or_cycle_signature
  perturbation_condition
```

### (5) Kamimusuhiとの差分

既出の successful strategy coverage は「複数の成功方略を持つ」procedural robustness、本候補は **複数主体の反復 dynamics がどの recurrent region に留まるか**という coordination-level property。functional degeneracy とも異なる。

### (6) 次に検証すべきこと

`CoordinationRecurrenceBench`:

- 3〜5 organ が compute / memory / external-model budget を共有する toy environment。
- greedy、deterministic best-response、noisy bounded response を比較。
- transient peak performance と long-run recurrent safety を別 metric で測る。
- correlated failure / stale information を注入。

### (7) 既存 daily ではなぜ拾いにくいか

multi-agent survey は communication / role specialization / task success へ偏りやすく、**Markov-chain recurrent class の安全 bound**は game theory / control theory 側に埋もれるため。

### (8) 重要度

**B+** — 現段階では直接採用より、将来の multi-organ / branching cognition 実験の評価語彙として保持する価値がある。

## 11. 結論

今回の中心的な設計差分は、Kamimusuhi の trust / continuity をさらに **「何を検証したか」から「実際に何が動いているか」へ寄せること**である。

```text
spec is correct
!= verifier is adequate
!= implementation conforms
!= binary is source-identifiable
!= model artifact closure is identical
!= sensor source attribution is certain
```

このうち最も即座に実験可能で、既存 Kamimusuhi の方針を壊さずに強化できるのは `ImplementationDriftBench`。次に `DeploymentStateClosureBench` と `SensorPermutationBench` を行うと、将来の Persona Core migration と distributed embodiment の両方で「同一性・由来・現在状態」をより機械的に扱える。
