## 2. 今回狙った盲点

今回は通常の AI agent / memory / distributed-runtime survey では落ちやすい以下を狙った。

1. **dynamic capability topology** — MCP server / tool / organ の attach / detach が実行中に変わる時、能力一覧の「所属」と説明・schema の「metadata freshness」を分離できるか。

## 4. 要約

今回は **有意な新規発見あり**。

最も fresh な実装差分は Letta Code #4398 である。MCP attachment の discovery を5分キャッシュしていた結果、server を attach / detach しても次の user turn が古い tool topology を見る問題があり、修正では **各 user turn の前に attachment membership を再取得しつつ、tool count metadata は5分 cache のまま**にしている。つまり、

```text
capability membership freshness
!=
capability metadata freshness
```

である。これは Kamimusuhi の `freshness` 一般論より具体的で、**何が存在するか／接続されているかという topology 自体に freshness と negative evidence が必要**という差分になる。

設計上さらに大きい backfill は **persistent information-flow control (IFC)** だった。Kamimusuhi は provenance と privacy-aware memory を強く持つが、今後 summary / embedding / reflection / relationship synthesis / distillation が増えると、

```text
source provenance preserved
!=
source disclosure policy / authority ceiling preserved
```

になる。NeuroTaint は semantic transformation と cross-session memory を跨ぐ taint propagation を監査対象にし、LLMbda は dynamic IFC を含む agent calculus 上で noninterference を machine-checked に扱い、GAAP / SPA は persistent store や cross-query artifact に flow policy を持たせる方向を示している。TMA-NM はさらに summarization、trusted-tool echo、manufactured corroboration による authority laundering を問題化する。

したがって Kamimusuhi では provenance graph に加えて、**derived artifact が親データより自由な disclosure / act authority を暗黙に獲得しない** `FlowPolicyLabel` / `DeclassificationReceipt` が必要になる可能性が高い。

もう一つの未収載な systems/PL 境界は **Multiparty Session Types (MPST)** である。現行 Kamimusuhi は component state、authority、replay、coordination を細かく分けているが、複数 participant 間のプロトコル全体を `global type → local projection` として検査する層はない。

```text
valid message schema
!=
valid conversation protocol

local state-machine conformance
!=
distributed choreography liveness
```

Effect Acceptance、StopLifecycle、migration、branch reconciliation のような高リスクな interaction だけを MPST 的に記述すると、全 runtime を形式化せずとも message order / branch / termination / unexpected participant replacement を試験できる。

標準化では W3C の AI Agent Memory Interoperability Community Group と IETF の memory-format drafts を未収載 watch とした。ただし **W3C Community Group は W3C Recommendation を作る Working Group ではなく、現在の SAIHM も Internet-Draft で work in progress** である。採用候補というより、Kamimusuhi の memory export / sharing / erasure contract を他実装と比較する interoperability test surface として見るのが妥当である。

最後に、9月12日公開の MI-BCI longitudinal study は single-participant の限定結果だが、将来の wearables / BCI / sensory substitution に重要な警告を与える。interface performance の変化は decoder の性能変化だけではなく **利用者側の学習軌道**を含む。Kamimusuhi が人間と共適応する interface を持つ場合、`interface changed` と `human adaptation changed` を一つの performance score に畳み込まない方がよい。

## 6.1 S — Persistent Information-Flow Contract: 派生しても disclosure / authority を勝手に軽くしない

**Primary references**

- NeuroTaint — https://arxiv.org/abs/2604.23374
- LLMbda — https://arxiv.org/abs/2602.20064
- SPA — https://arxiv.org/abs/2608.27234
- GAAP — https://arxiv.org/abs/2604.19657
- TMA-NM — https://arxiv.org/abs/2606.24322

### (1) 何が実証済みか

複数の独立した2026年研究が、agent の情報流を **文字列コピーだけでは追えない**という同じ方向を示している。

- **NeuroTaint** は semantic transformation、decision への causal influence、memory を跨ぐ cross-session persistence を扱う offline provenance auditor を提案し、20 real-world agent frameworks・400 scenarios の TaintBench で IFC-style baseline より高い source-to-sink propagation detection を報告している。
- **LLMbda** は agent planner loop / prompt-response conversation / code generation を calculus に含め、dynamic IFC において every value の label propagation と explicit reclassification を表現し、termination-insensitive probabilistic noninterference を machine-checked に示す。公開 harness は AgentDojo banking benchmark で 1296 attacked runs 中2件を除き攻撃を防いだと報告している。
- **GAAP** は private data の disclosure permission を agent/model provider を信頼せず execution environment 側で追跡し、persistent stores を含む複数task間の情報流を IFC で扱う。評価では対象 attack を block し、大きな utility loss がないと報告している。
- **SPA** は confidentiality / integrity の dual-lattice を explicit data flow と control dependency に適用し、cross-query persistent artifact に label を保持する。AgentDojo では対象 attack success 0、multi-query extension では0.2%を報告している。
- **TMA-NM** は memory authority が summarization、trusted-tool echo、manufactured corroboration で laundering され得ることを形式化し、write-time origin binding と non-malleable propagation を要求する。報告 benchmark では既存 defense が最大68% laundering ASR を示し、提案方式は定義した threat model 内で0%としている。

これらは Kamimusuhi 自体を検証した結果ではないが、**persistent data transformation と privileged sink の間に、provenance とは別の flow policy が必要**という工学的根拠はかなり強い。

### (2) 何が提案・推測段階か

Kamimusuhi に適した label lattice は未確定である。

特に以下を一つのラベルへ雑に詰めるべきではない。

- confidentiality / 誰に見せてよいか
- integrity / どの程度 trusted source か
- epistemic confidence / 真である確率
- action authority / consequential effect の根拠にできるか
- retention / expiry
- purpose limitation / 何の用途に使ってよいか

IFC が成立しても「情報が真である」ことは保証しない。また、厳しい label propagation は utility を落とし、label explosion や過剰 quarantine を起こし得る。

### (4) 借りられる設計・実装アイデア

既存 `provenance` を置換せず、**別軸として flow policy を付ける**。

```text
FlowPolicyLabel
  confidentiality_scope
  owner_subjects
  allowed_principals
  allowed_sink_classes
  purpose_scope
  retention_state
  integrity_floor
  action_authority_ceiling
  source_policy_ids[]
  declassification_rule
  endorsement_rule
```

派生時の default rule は、まず保守的に次を置く。

```text
summary / embedding / reflection / schema / tool-derived result

confidentiality:
  親より緩くしない

action authority:
  親より強くしない

provenance:
  親 source を失わない

declassification / authority elevation:
  暗黙に行わず explicit receipt を必要とする
```

重要なのは、次を禁止すること。

```text
private exact value
  -> sanitized summary
  -> "summaryだからpublic"

untrusted web text
  -> internal reflection
  -> "自分で考えたからtrusted"

relationship secret
  -> embedding
  -> external vector/model API へ送信

untrusted memory
  -> trusted tool echo
  -> consequential action authority
```

`SP-Mem` の exact-value vault はこの仕組みの一部として使えるが、今回の差分は **exact value 以外の派生情報と provider/tool sink まで policy を持続させること**である。

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は provenance、canonical evidence、self/other separation、SP-Mem 的 disclosure governance をすでに強く持つ。しかし repository には、

- derived summary / embedding / schema / reflection が親データの disclosure 制約を継承すること
- external model prompt 自体を privacy sink とみなすこと
- tool echo や self-summary による authority elevation を禁止すること
- declassification / endorsement を explicit event とすること

を横断的にまとめた **persistent information-flow contract** は確認できなかった。

したがってこれは SP-Mem / PROV-O / DP-MemView の再提案ではない。

## 6.2 A+ — Dynamic Capability Inventory Freshness: 「tool の説明」より先に「まだ接続されているか」を更新する

**Primary:** Letta Code PR #4398  
https://github.com/letta-ai/letta-code/pull/4398

**Merged:** 2026-09-13 12:41:17 JST

### (1) 何が実証済みか

#4398 の報告では、MCP attachment discovery が5分 interval に依存していたため、server を attach して直後に user message を送ると old attachment list が model に提示される問題があった。

修正後は **各 user turn の前に attachment membership を refresh**し、更新された reminder を user message より前に提示する。一方で tool counts は5分 cache を継続する。

実環境検証として、同一 persistent bidirectional session で最初は `None`、外部から DeepWiki を attach した後、同じ prompt に対して **2.5秒後の次 turn で `DeepWiki`** と認識したと報告している。restart、cache reset、tool call は不要だった。

さらに attach → next-turn reminder → count cache reuse/refresh → detach → next-turn `None` を interactive / one-shot / bidirectional / listener mode で確認し、discovery failure 時は last sent list を保持して次 turn で retry する設計である。

### (2) 何が提案・推測段階か

Letta の reminder list は UI/context freshness の問題であり、PR 自体は Kamimusuhi の authority safety を証明していない。

特に `discovery failure -> last-known listを表示` は usability 上は合理的でも、その last-known list を **現在の execution authority** と同一視すると危険である。

Kamimusuhi で必要なのは、

```text
last known attached
!=
currently verified attached
!=
currently authorized
!=
currently healthy
```

という分離である。

- Effective Environment Manifest

### (4) 借りられる設計・実装アイデア

capability inventory を一枚の cache とせず、**membership と metadata を別freshnessにする**。

```text
CapabilityInventorySnapshot
  snapshot_id
  owner_runtime
  observed_at
  discovery_status
  membership_generation
  capabilities[]

CapabilityPresence
  capability_id
  status: PRESENT | ABSENT | UNKNOWN | STALE_LAST_KNOWN
  observed_at
  attachment_epoch

CapabilityMetadata
  schema_hash
  description_hash
  tool_count
  metadata_observed_at
  metadata_ttl
```

運用原則候補:

```text
next-turn admission:
  membership は可能なら refresh

metadata:
  高価なら TTL cache 可

discovery failure:
  UI 上は last-known を示してよい
  ただし effect authorization は UNKNOWN として再検証

detach:
  stale-positive capability を新規 effect の根拠にしない
```

また invocation receipt に `inventory_snapshot_id / attachment_epoch` を結び、同名 server が差し替わった場合に generation fencing と接続できる。

### (5) Kamimusuhiとの差分

現行設計は present state を real owner から導出する `INV-013`、freshness、revocation、generation fencing を持つ。しかし **capability topology の membership freshness と schema/metadata freshness を別々に扱う contract** は明示されていない。

これは一般的な `stale data` の再提案ではなく、**negative topology event（detach / disappear）が positive cached list に負ける**問題を独立して扱うもの。

- next-turn availability latency
- cross-node inventory divergence

### (7) 既存デイリーサーベイではなぜ拾いにくいか

通常の tool/model orchestration は「どの tool を選ぶか」「schema をどう使うか」に寄り、**service discovery / topology cache / negative membership freshness** は configuration-management や distributed service discovery 側に埋もれやすい。

### (8) 重要度

**A+** — distributed body と hot-pluggable tools を増やすほど、存在しない organ/tool を「まだある」と思う stale-positive が side effect と recovery の両方を壊す。実装コストも比較的小さい。

## 6.3 A+ — Multiparty Protocol Choreography: local state machine だけでなく interaction 全体を型付けする

**Primary references**

- https://arxiv.org/abs/2602.23927
- https://arxiv.org/abs/2605.23633
- https://arxiv.org/abs/2604.06878

### (1) 何が実証済みか

**Multiparty Session Types (MPST)** は複数 participant の communication protocol を global type として記述し、各 participant の local type へ projection する枠組みである。

2026年の関連研究では:

- *Mixed Choice in Asynchronous Multiparty Session Types* が asynchronous mixed choice を扱い、分散 participant 間に一時的不整合があっても mutually consistent state へ到達できる progress property と global/local operational correspondence を示し、Erlang/OTP `gen_statem` 用 toolchain で RabbitMQ `amqp_client` の一部を再実装している。
- *Formally Verified Liveness with Multiparty Session Types in Rocq* は synchronous MPST の liveness を Rocq 上で mechanize し、safety / liveness を証明する。約14K LOC の Rocq artifact を報告している。
- *Towards MPST for Highly-Concurrent and Fault-Tolerant Web Applications* は標準 MPST が state evolution / dynamic workflow / failure semantics を十分扱わないことを明示し、failure と dynamic participation を global type に入れる方向を示す。

つまり「すべての分散 runtime が自動的に安全になる」わけではないが、**message choreography を局所handlerの集合より高いレベルで検査する理論・実装系は成熟している**。

### (2) 何が提案・推測段階か

Kamimusuhi の LLM / tool / human interaction をそのまま MPST 化できるわけではない。

特に:

- participant が動的に増減する
- timeout 後の external effect outcome が UNKNOWN
- LLM が protocol 外の提案を生成する
- branch / migration / human approval が長時間継続する
- recovery と replay がある

ため、classical MPST だけでは不足する。

採用するとしても、まず **高リスクで participant が比較的明確な protocol** に限定すべきである。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- Effect Acceptance
- Continuity Kernel
- StopLifecycle
- migration / backup / restore
- K-Edge ↔ K-Core delegation
- actuator ownership transfer
- branch reconciliation
- async tool execution / result delivery
- human approval
- runtime assurance

### (4) 借りられる設計・実装アイデア

`ProtocolContract` を global choreography として置き、local runtime monitor を生成する実験。

例: effect lifecycle

```text
roles:
  Cognition
  AdmissionGate
  Executor
  EvidenceLog
  Delivery

Cognition -> AdmissionGate: Propose(effect, evidence)
AdmissionGate -> Cognition: Deny(reason)
  or
AdmissionGate -> Executor: Permit(grant, effect_hash)
Executor -> EvidenceLog: Started(execution_id)
Executor -> EvidenceLog: Succeeded(receipt)
  or Failed(reason)
  or Unknown(observation)
EvidenceLog -> Delivery: DeliverableResult(receipt_ref)
Delivery -> EvidenceLog: Delivered | DeliveryFailed
```

protocol monitor は、例えば次を違反として扱える。

- Permit 前の `Started`
- 同じ single-use grant の2回目 `Started`
- `Succeeded` 前の success delivery
- `Unknown` 後の無条件 automatic retry
- migration 中の旧ownerからの effect
- stop finalized 後の new tool dispatch

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は component ごとの state machine、authority、runtime conformance、CALM、replay を持つ。

しかし、

```text
participant A は local spec に適合
participant B も local spec に適合
participant C も local spec に適合

それでも組み合わせた message sequence が deadlock / orphan / wrong branch
```

という問題を **global choreography** として検査する層は確認できなかった。

`RuntimeConformanceReceipt` は「実装が自分の仕様通りか」を見る。一方 MPST は「複数 participant の仕様同士が protocol 全体として噛み合うか」を見るため、役割が異なる。

### (6) 次に検証すべきこと

**`ProtocolChoreographyBench`**

まず3 protocolだけ対象にする。

1. `EffectAdmissionProtocol`
2. `StopLifecycleProtocol`
3. `PersonaMigrationProtocol`

fault injection:

- message delay / reorder
- duplicate
- dropped acknowledgment
- timeout after effect
- participant crash
- participant replacement
- stale generation
- human approval arriving after cancellation

比較:

- current ad-hoc event handlers
- local state-machine assertions only
- global protocol monitor + local projection

指標:

- protocol violation detection before effect
- deadlock / orphan message rate
- false-positive block
- recovery completion
- monitor overhead
- number of protocol states / maintenance cost

### (7) 既存デイリーサーベイではなぜ拾いにくいか

主要文献が programming languages、concurrency theory、session types、formal verification にある。agent survey は tool schema / A2A protocol / orchestration API を見ても、**global choreography の型安全性・deadlock freedom・liveness**までは掘らないことが多い。

### (8) 重要度

**A+** — Continuity Kernel を含む高リスク path が増えると、個別 component の正しさだけでは interaction bug を防げない。ただし全面導入は複雑なので、effect / stop / migration の3本で価値を測るべき。

## 6.4 B+ — AI Agent Memory Interoperability: portable memory と portable authority を分ける

**Primary / official sources**

- W3C Community Group: https://www.w3.org/community/ai-agent-memory-interop/
- Charter v1.0: https://www.w3.org/community/ai-agent-memory-interop/2026/07/16/charter-ai-agent-memory-interoperability-community-group-v1-0/
- SAIHM draft: https://datatracker.ietf.org/doc/draft-saihm-memory-protocol/
- ApertoMemory: https://datatracker.ietf.org/doc/html/draft-ferro-apertomemory-01
- IETF 126 agentproto minutes: https://datatracker.ietf.org/doc/minutes-126-agentproto-202607230700/

### (1) 何が実証済みか

これは performance 研究ではなく **標準化・interop activity が実際に存在する**ことが確認できる、という種類の evidence である。

W3C AI Agent Memory Interoperability Community Group は2026年6月19日に charter v1.0を採択し、vendor / model / framework 間で memory を portable / verifiable にする interoperability profile、use-case catalogue、conformance test surface を目的としている。scope には memory cell shape、identity binding、encryption envelope、audit anchor、sharing contract、cryptographic erasure が含まれる。

一方で重要な制約がある。

- **W3C Community Group は W3C Recommendation を作る Working Group ではない**。
- charter 自身も normative protocol を外部 draft に依存する形を明記している。
- `draft-saihm-memory-protocol-01` は Internet-Draft であり、RFC ではない。
- 2026年7月の group update では Independent Submission の扱いが終了し、IETF 本体側の agent protocol work を追跡する姿勢を示している。
- 別系統として `draft-ferro-apertomemory-01` も portable / client-side-encrypted memory format を提案しており、現時点で単一の settled standard があるわけではない。

### (2) 何が提案・推測段階か

SAIHM の cryptographic architecture、public-chain audit、wallet binding、specific algorithm choices を Kamimusuhi が採用すべきとは言えない。

また、`cryptographic erasure` を実装しても、summary、embedding、backup、provider logs、Persona weights まで消えたことを自動的に意味しない。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- memory ownership / consent
- backup / restore
- device migration
- external memory store
- Library / relationship export
- intentional fork / successor handoff
- deleted / revoked memory semantics
- interoperability test

### (4) 借りられる設計・実装アイデア

規格を採用するのではなく、まず **interop profile test** を作る。

```text
PortableMemoryEnvelope
  payload_or_reference
  content_hash
  memory_domain
  subject_scope
  source_provenance_ref
  owner / controller
  sharing_policy_ref
  retention / tombstone state
  continuity_source_lineage
  format_version
```

守る境界:

```text
memory portable
!= identity portable

memory copied
!= disclosure authority copied

recipient can decrypt
!= recipient may re-share

cryptographic erasure receipt
!= all derived artifacts erased

exported self-memory
!= new runtime becomes canonical self
```

### (5) Kamimusuhiとの差分

Kamimusuhi は migration / lineage / provenance を中心に置くが、**第三者実装との memory portability / conformance** は現在の中核研究ではない。

そのため今すぐ規範へ入れるより、将来の backup/export format が独自仕様へ閉じないよう watchlist / test-vector comparison として持つのが妥当。

### (6) 次に検証すべきこと

**`MemoryPortabilityRoundTripBench`**

- canonical evidence / episodic / relationship / semantic の4 domain を小さな export bundle にする。
- export → import → re-export で provenance / owner / policy / tombstone が失われないか比較。
- foreign memory を import しても canonical self lineage が自動継承されないことを確認。
- revoked share / expired share / deleted cell を含める。
- SAIHM / ApertoMemory の field mapping を read-only adapter で試す。

指標:

- semantic round-trip loss
- provenance loss
- policy loss
- accidental authority gain
- identity contamination
- crypto / storage overhead

### (7) 既存デイリーサーベイではなぜ拾いにくいか

W3C Community Group、IETF Internet-Draft、interop profile、conformance test といった **standards-process / governance** に散在しており、memory benchmark / agent architecture の検索では拾いにくい。

### (8) 重要度

**B+ / watch** — 今すぐ architecture を変える必要はないが、long-lived personal AI が vendor / runtime を越えるなら memory portability は将来避けられない。未成熟な標準化なので watch と実験 adapter に留める。

## 6.5 B — Co-adaptive Interface State: machine performance と human learning を同じ数字にしない

**Primary:** Palatella et al., Journal of NeuroEngineering and Rehabilitation, published 2026-09-12  
https://link.springer.com/article/10.1186/s12984-026-02127-y

### (1) 何が実証済みか

本研究は Cybathlon pilot の longitudinal MI-BCI EEG data を Riemannian geometry で分析し、geodesic distance と tangent-space direction の指標から、training に伴う structured longitudinal change と、異なる organization / consistency を表す2つの dominant geometric configuration と整合的な pattern を報告している。

重要な制約として、公開ページの記述は **participant / individual が単数**であり、single-participant longitudinal study とみなすべきである。したがって一般的な「人間の BCI learning law」を確立した結果ではない。

### (2) 何が提案・推測段階か

この EEG geometry を Kamimusuhi の sensor adaptation 指標へ直接移植する根拠はない。

借りる価値があるのは測定哲学だけである。

```text
interface task success changed
!=
decoder alone improved
```

人間が interface に適応し、interface も人間に適応する co-adaptive system では、joint performance だけで変化の主体を推定してはいけない。

### (3) 関係する Kamimusuhi subsystem / 設計課題

- future BCI
- wearables
- sensory substitution
- multimodal input personalization
- speech / turn-taking adaptation
- human-computer integration
- relationship-specific interface adaptation
- developmental / plasticity evaluation

### (4) 借りられる設計・実装アイデア

`CoAdaptiveInterfaceRecord` を候補化する。

```text
interface_version
calibration_version
user_session_index
machine_policy_change
observed_performance
human_adaptation_proxy
confidence
context
```

interface adaptation を評価するとき、少なくとも:

- fixed machine / repeated human training
- updated machine / same human stage
- new human / same machine
- no-feedback control

を区別する。

### (5) Kamimusuhiとの差分

現行 Kamimusuhi は sensor health / body state / learning lineage を持つが、**human-side adaptation と machine-side adaptation を longitudinal に分解する interface contract** は未収載。

### (6) 次に検証すべきこと

実 BCI を待たず、まず speech / gesture / gaze interface で **`CoAdaptationAttributionBench`** を作る。

- interface model を固定してユーザー習熟だけ進める条件
- user behavior を固定した replay に対して interface model だけ更新する条件
- 両方変化する条件

を比較し、joint task score の改善をどこまで attribution できるかを見る。

### (7) 既存デイリーサーベイではなぜ拾いにくいか

BCI / neurorehabilitation / longitudinal skill acquisition にあり、agent architecture や AI memory の検索語から遠い。しかも価値は BCI model 自体ではなく **co-adaptation の評価設計**にある。

### (8) 重要度

**B** — 現時点の Kamimusuhi に BCI は必須ではなく、研究も single-participant であるため昇格しない。ただし将来の wearable / embodied HCI では評価上の重要な注意になる。
