## 候補評価

### 1. A — Observation Completeness / Omission Provenance

Primary: Hermes #131174  
https://github.com/NousResearch/hermes-agent/issues/131174  
Backfill: Conformal Fusion Under Missing Modalities, arXiv:2608.07183  
https://arxiv.org/abs/2608.07183

1. **実証済み**: Feishu adapterで大容量添付の取得に失敗した際、agent inputからattachment自体が消え、約171MB ZIPの実例ではmedia=0となった。MCCFはmodality-presence maskを明示し、欠落subsetごとのuncertainty calibrationを評価している。
2. **提案段階**: 特定fusion方式の採用ではなく、「sourceが存在を知らせたが取得できなかったcomponent」をtyped missing evidenceとして残す。
3. **関係**: Sensory Nervous System、Canonical Evidence、episodic memory、multimodal ingestion。
4. **借りる案**: componentに PRESENT / ACQUISITION_FAILED / TOO_LARGE / PERMISSION_DENIED / UNSUPPORTED / TIMED_OUT / CORRUPT / UNKNOWN を持たせ、confidenceとavailabilityを分離。
5. **差分**: 既存sensory docsはmissing/conflicting modalityを評価するが、ingressで「何が落ちたか」をcanonical evidence化する契約が弱い。
6. **次**: **ObservationOmissionProvenanceBench-v0 (P0)**。text成功+image失敗、limit、timeout、sensor offline、privacy exclusionを交差しsilent absence=0を要求。
7. **拾いにくい理由**: multimodal研究は欠落後の推論、adapter研究はdownload成否を扱い、その間のepistemic provenanceが抜ける。
8. **重要度**: **A**。

### 2. A — Code–State Ownership Closure Across Organ Replacement

Primary: Hermes #131126  
https://github.com/NousResearch/hermes-agent/issues/131126

1. **実証済み**: pinned pluginを新revisionへ移すdocumented replacement pathで、plugin directory内のuser state/local settingsが失われるreal reproduction。通常update pathにはstate carry/backupがあり、入口で保存契約が異なる。
2. **提案段階**: 全file保存ではない。code、operator config、durable organ state、cache、temp、local patchのlifecycle分類が必要。
3. **関係**: Software Body、plugin/organ update、procedural state、migration/rollback。
4. **借りる案**: replacement receiptにold/new generation、state schema、retained/migrated/discarded class、backup locatorを記録。
5. **差分**: generation/activation/rollbackは既出だが、code generationとdurable state ownershipをinstallation namespaceから独立させるcontractが弱い。
6. **次**: **OrganCodeStateReplacementBench-v0 (P0)**。update/replacement/rollback、state migration、publish途中failureを検証。
7. **拾いにくい理由**: software updateとmemory/storageが別領域で調査され、同じdirectoryへ同居する時の境界が落ちる。
8. **重要度**: **A**。

### 3. A update — Shared Retention Latches Need Acquisition Ownership

Primary: OpenClaw #163213  
https://github.com/openclaw/openclaw/issues/163213

1. **実証済み**: source inspectionではsession pinが単一状態で、automationとhumanの独立pinを区別できず、一方だけ安全にreleaseする契約がない。live competing-pin incidentではなくsource-derived gap。
2. **提案段階**: pinだけでなくkeepalive/no-GC/wake lockへの一般化。
3. **関係**: session retention、async delegation、result custody、GC。
4. **借りる案**: booleanでなく hold_id × owner × purpose × target_generation × expiry のacquisition set。
5. **差分**: shared-acquisition cancellation ownershipのpositive-retention版。保持意図も複数ownerの合成状態。
6. **次**: **SharedRetentionHoldOwnershipBench-v0 (P0/P1)**。human/automation/background owner、reset、expiryを交差。
7. **拾いにくい理由**: pin/keepaliveはUI flagに見え、ownership研究から外れやすい。
8. **重要度**: **A update**。

### 4. A update — Readiness Must Close Over the First Real Cognition Path

Primary: Hermes #131145  
https://github.com/NousResearch/hermes-agent/issues/131145

1. **実証済み**: turn-machinery warm-up未完了でもinbound gateが開き、Gateway/platform healthはgreenのままfirst turnがprovider call前で永久停止するfield report。restartで回復。
2. **提案段階**: 全organ warm-up強制ではなく、lazy/degraded startupなら未ready dependencyにdeadline/fail-fast/fallbackが必要。
3. **関係**: K-Core startup、Resource Registry、DialogueSession、degraded mode、observability。
4. **借りる案**: readinessをtransport、cognition core、tool registry、model route、memory等のdependency-qualified stateにする。
5. **差分**: end-to-end readinessのfresh具体例。gateを早く開く設計で外形healthとfirst-turn serviceabilityが分裂する。
6. **次**: **FirstTurnReadinessClosureBench-v1 (P0)**。warm-up/probe/tool-registry/memory cold-start hangを注入、永久wait=0を要求。
7. **拾いにくい理由**: SREはprocess/socket、agent評価はturn結果を見てstartup dependency closureが間に落ちる。
8. **重要度**: **A update**。

### 5. B update — Discovery Materialization Must Respect Principal Scope

Primary: OpenClaw #163206  
https://github.com/openclaw/openclaw/issues/163206

1. **実証済み**: 3 agents中1 agentだけが使うMCP serverへ全agentがconnect/spawnし、別cleanup defectと重なって約2.5日で24 process trees、約400MBの回収が報告された。
2. **提案段階**: 全discoveryの完全lazy化は不要だがmaterialization scopeはprincipal/tool policyと一致させる。
3. **関係**: Cognitive Resource Registry、MCP discovery、principal scope、Cognitive Budget。
4. **借りる案**: may_discover_metadata / may_connect / may_spawn_server / may_call_tool を別capabilityにする。
5. **差分**: discovery-action principal parity / pre-materialization admissionのfresh実運用evidence。
6. **次**: **PrincipalScopedDiscoveryMaterializationBench-v1 (P1)**。N agents×M serversで禁止agentのspawn=0を要求。
7. **拾いにくい理由**: discoveryを副作用なしmetadata readとみなしやすいがstdio MCPではprocess creationを伴う。
8. **重要度**: **B update**。

### 6. B update — Logical Sensor Roles Need Incarnation-Aware Rebinding

Primary: Hermes #131177  
https://github.com/NousResearch/hermes-agent/issues/131177

1. **実証済み**: macOSでinput device hot-plug後、PortAudioが古いdevice IDを保持し、system default指定でもreopenに失敗し続けた。報告sessionで122連続failure、restartまで回復しなかった。
2. **提案段階**: backendごとのre-enumeration方式は異なる。
3. **関係**: K-Edge、Sensory Nervous System、distributed embodiment、wake word。
4. **借りる案**: logical role DEFAULT_MIC と physical device_identity + enumeration_generation を分け、topology changeでrebind。
5. **差分**: resource-instance/attachment incarnationのsensory-body側具体化。
6. **次**: **SensorHotplugIncarnationBench-v0 (P1)**。mic/camera/USBのunplug/replug、default変更、permission changeを検証。
7. **拾いにくい理由**: multimodal研究は認識精度、device runtimeはdriver/APIを見てsensor handleのidentity continuityが抜ける。
8. **重要度**: **B update**。

## 結論

今回の中心は **「欠けたものにもprovenanceが必要」** だった。「添付が無かった」と「添付はあったが取得できなかった」、「sensor eventが無かった」と「sensorがofflineで観測できなかった」は異なる世界状態である。ingressでこれを潰すとmemory/self-model/safetyは正しく不確実性を表現できない。

software bodyでも同様に、code generationの交換と、そのcodeが解釈するdurable stateの所有権は別である。
