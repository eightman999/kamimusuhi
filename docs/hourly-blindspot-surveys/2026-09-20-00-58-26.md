## 1. 今回狙った盲点

1. **maintenance annotation が agent 自身の過去出力へ混ざり、次の生成で自己模倣される問題**
   - summary / truncation / redaction marker は単なる表示 metadata ではなく、モデルから見ると「自分が以前書いた文字列」に見え得る。

2. **observation の detection と consumption/acknowledgement を同一commitにする問題**
   - change detector が新状態を見た時点で cursor/hash をadvanceすると、その後 admission gate で拒否された場合に「見たが処理していない変化」が消える。

3. **working cognition に必要だが durable history へ残してはいけない sensitive context**
   - verified file bytes / native image / credential-adjacent payload 等を live model context には入れたいが、transcript / snapshot / replay / diagnostic export には残したくない。

4. **deferred intent が成功後も残り、後続の明示変更を再上書きする問題**
   - retryable intent は failure 時には残るべきだが、成功後には「使い切った一回性命令」として退休しなければならない。

5. **turn atomicity が compaction liveness を破る問題**
   - in-progress turn を絶対分割不可とすると、長い tool chain 1 turn だけで protected tail budget を越えた場合に compaction が永遠にno-opになり得る。

6. **canonicalization が operational identity provenance を落とす問題**
   - `named provider → custom` のような normalization は equality/dispatchには便利でも、affinity/security/protocol判断に必要だった configured identity を消し得る。

固定リスト以外の探索として、stream-processing の acknowledgement boundary、information-flow/persistence boundary、linear/one-shot state transitions、normalization/provenance loss、context compaction の control-plane metadata contamination を重点化した。

# 5. 候補ごとの評価

## 5.1 A+ — Synthetic replay annotation isolation

### (1) 何が実証済みか

Hermes #116169では、compressorがtool-call argumentへ入れた普通の`...[truncated]`文字列がモデルの過去出力としてreplayされ、後続turnでモデルに模倣されて**新しいtool callの実payloadへ混入し、disk writeまで到達**したfailureが報告されている。修正は明示的なnon-original marker、個別counts、二重適用防止、byte-identical no-opを導入し、186 tests passと報告される。PRはmerge済み。

### (2) 何が提案・推測段階か

marker文言を目立たせるだけで、全モデル・全transformに対して imitation が防げる保証はない。summary、redaction、OCR placeholder、missing-field marker、policy-injected noteでも同種の問題が起こるかは未検証。

### (3) Kamimusuhiの関係箇所

- Global Workspace / prompt rendering
- context compaction / sleep-derived summaries
- tool-call replay / K-Deep handoff
- `INV-007` provenance separation
- `INV-008` generated cognition is not fact
- `INV-011` canonical evidence > derived view

### (4) 借りられる設計・実装アイデア

自然言語markerだけに頼らず、rendered context segmentへtyped provenanceを持たせる。

```text
ContextSegment {
  payload,
  origin: USER | AGENT | TOOL | CANONICAL_EVIDENCE | MAINTENANCE_SYNTHETIC,
  transform: NONE | SUMMARY | TRUNCATION | REDACTION | REPLAY_NOTE,
  imitable: bool,
  source_refs,
  transform_epoch
}
```

model APIがflat textしか受けない場合も、synthetic markerはagent-authored proseと衝突しにくいdelimiterにし、tool/action生成前にはmarker残留を検査する。

### (5) Kamimusuhiとの差分

Kamimusuhiは canonical evidence と derived representation を概念上分離しているが、**derived metadataがprompt/replay内で一度flat textへ落ちた後、モデルがそれを自己履歴として再利用する経路**は明示的contractになっていない。

### (6) 次に検証すべきこと

**`ReplayAnnotationIsolationBench-v0` — P0 candidate**

- tool args / tool results / user text / summaryにsynthetic markerを挿入
- compactionを2〜5 cycle実施
- modelへedit/write/code toolを再生成させる
- synthetic markerがnew action payloadへ移る率を測定
- plain marker / explicit marker / structured sidecar / pre-action scrubを比較
- `transform(transform(x)) == transform(x)` fixed-pointも検証

成功条件: derived maintenance artifactが新しいeffect payloadへ「original intent/content」として昇格しない。

### (7) 既存dailyで拾いにくい理由

通常のmemory/compaction surveyは「何を残すか」「continuationを守れるか」を見るが、**圧縮器が足した記号をmodelが行動様式として学習・模倣する**問題は、prompt renderingとcompiler hygieneとbehavioral imitationの境界にある。

### (8) 重要度

**A+** — canonical/derived separationを、実際のprompt surfaceで破るfresh merged failure。tool effectまで到達しており実装優先度が高い。

## 5.2 A+ — Observation Consumption Barrier

### (1) 何が実証済みか

Hermes #116140ではmonitor changeを検出直後にhash/snapshotへcommitしていたため、provider/config gateでrunが拒否されると、agentが一度もそのchangeを処理していないのに次回は`unchanged`となるlost wakeが再現された。修正案はchangeをpending outcomeとして持ち、pre-inference gates通過時にcommitする。focused 22/22、cron suite 1461 passと報告される。

### (2) 何が提案・推測段階か

どこを「consume point」とすべきかはevent classごとに異なる。high-value alertではinference successまでackを遅らせたい場合があり、cheap monitorではadmission時consumeが適切な場合がある。単一ルールではない。

### (3) Kamimusuhiの関係箇所

- K-Edge/K-Nerve perception
- background monitors / schedulers
- prospective memory / reminders
- salience/event bus
- degraded/offline cognition
- event-time/watermark processing

### (4) 借りられる設計・実装アイデア

観測に lifecycle を持たせる。

```text
DETECTED
  -> STAGED
  -> ADMITTED_TO_COGNITION
  -> ACKED_CONSUMED
  -> PROCESSED / FAILED_AFTER_ACK
```

`detector cursor/hash`更新を、source observationとagent processing opportunityのどちらにbindするかをevent classで定義する。ack前failureはreplayable、ack後inference failureはduplicate policyに従う。

### (5) Kamimusuhiとの差分

`CognitiveEventTimeWatermark`はevent completenessを、`OpportunityQualifiedExpiry`はservice opportunityを扱う。今回はさらに手前の**「変化を観測したという事実」と「その変化を認知系がconsumeしたという事実」のcommit separation**である。

### (6) 次に検証すべきこと

**`ObservationConsumptionBarrierBench-v0` — P0 candidate**

- source A→B change検出
- config refusal / provider unavailable / privacy gate / overload / inference errorを各段階へ注入
- changeがlost / duplicate / exactly-once-equivalentになるか測定
- high-priority alertとlow-priority monitorでack policyを比較
- restart前後でpending observationをdurable replay

### (7) 既存dailyで拾いにくい理由

perception研究はsensor accuracyやsalience、distributed systems surveyはqueue semanticsを見ることが多く、**「認知個体がいつ“見たことにするか”」をdurable cursor commitとして設計する問題**は両者の境界にある。

### (8) 重要度

**A+** — continuous autonomous cognitionでsilent lost wakeを直接防ぐ。prospective memory / environment monitoringへ広く効く。

## 5.4 A — One-shot deferred intent retirement

### (1) 何が実証済みか

Hermes #116135ではsession初期化時の`pending_hidden`が成功後もmemoryに残り、後から明示unhideされた状態を次回materializationで再びhideへ戻すreproがある。成功時だけpending flagをconsumeし、failure/no-row時はretry用に残す修正でtarget tests 3 passと報告される。

### (2) 何が提案・推測段階か

hidden flag以外のbootstrap/migration/consent/recovery intentでも同じpatternが一般化するかは未検証。distributed copyがある場合、local flag削除だけでglobal retirementを保証できない。

### (3) Kamimusuhiの関係箇所

- Continuity Kernel mutation
- migration/restore bootstrap
- one-time consent/revocation actions
- device registration
- deferred configuration / repair

### (4) 借りられる設計・実装アイデア

intent lifecycleを明示する。

```text
PENDING
 -> APPLYING
 -> APPLIED(receipt)
 -> RETIRED

failure/no-target
 -> PENDING_RETRY
```

後続mutationは`APPLIED/RETIRED` intentから上書きされない。retryable intentには`intent_id`, `target_generation`, `success_receipt`, `retired_at`を持たせる。

### (5) Kamimusuhiとの差分

`OperationIntentPreservation`はbackpressure下でintent typeを保つ問題、`ProvisionalIntentReconciliation`はack前intentの生存問題。今回はその後段の**成功済みintentをいつ無効化するか**である。

### (6) 次に検証すべきこと

**`OneShotIntentRetirementBench-v0` — P1 candidate**

- initial hidden/visible, consent, device bind, migration repair等のone-shot intent
- success→後続explicit opposite mutation→rematerialization
- transient failure→retry→success
- crash between effect success and retirement receipt
- stale replicaがretired intentを再注入するcase

### (7) 既存dailyで拾いにくい理由

agent surveyではintent保持やretryに注目しやすいが、**成功後もintentが生き続けること自体がbugになる**というlinear-resource的なlifecycleはUI/bootstrap/runtime境界に埋もれやすい。

### (8) 重要度

**A** — continuity systemのmigration/restore/consentで古い命令が蘇る事故を防ぐ基本契約になり得る。

## 5.5 B+ — Elastic active-turn compaction boundary

### (1) 何が実証済みか

Hermes #116181では、active turnを必ずwhole-tailに残す既存invariantが、turnそのものがbudgetを越えた時にcompactionを永久no-op化した。bounded条件でtool-group-aligned mid-turn splitを許可し、active requestはhandoff経由でactionableに保つ。real path 24→8 messages、base 24→24と報告され、PRはmerge済み。

### (2) 何が提案・推測段階か

どのboundaryならsemantic continuityを壊さずsplitできるかはtool protocol依存。tool-call/result pair、human approval、multi-agent delegationを跨ぐsplitは危険。

### (3) Kamimusuhiの関係箇所

- long-running K-Deep tool loops
- compaction / continuation register
- bounded working memory
- resource pressure / degraded mode

### (4) 借りられる設計・実装アイデア

`atomic semantic unit` と `UI turn` を分ける。通常はturn boundaryを保護するが、budget超過時はverified atomic group boundaryまでsplit可能にし、active goal/obligationはlossless continuation registerへ残す。

### (5) Kamimusuhiとの差分

既出`CompactionContinuationClosure`の原則を変更するものではない。**continuationを守るためにturn全体をverbatim保持することが、逆にcontinuation livenessを壊す場合の例外条件**を追加する差分。

### (6) 次に検証すべきこと

既存 `CompactionContinuationClosureBench-v0` へ:

- 100〜500 tool eventsのsingle active turn
- protected tail budget 0.5x/1x/2x
- tool-group-aligned split / turn-whole / arbitrary split比較
- goal recall、tool pair integrity、next-action correctness、recompression fixed-pointを測定

### (7) 既存dailyで拾いにくい理由

「active turnを守る」は直観的安全策で、resource pressure下でそれ自体がliveness bugになる逆説はcompactor実装詳細に埋もれる。

### (8) 重要度

## 5.6 B — Pre-canonicalization operational identity provenance

### (1) 何が実証済みか

Hermes #116203ではnamed custom providerがruntimeで`custom`へcanonicalizeされると、OpenCode-family判定に必要なconfigured identityが失われ、session-affinity headerが欠落した。real gatewayでは一日で305 main-turn requestsがheaderなし、269がheaderあり。fresh/restarted sessionだけ壊れ、model switchで復旧するresolution-path dependencyが報告される。

### (2) 何が提案・推測段階か

PRはopenでfull suite未実施。provider identity以外のresource canonicalizationで同じ問題がどの程度一般化するかは未検証。

### (3) Kamimusuhiの関係箇所

- Cognitive Action Router
- model/tool endpoint descriptors
- warm-cache/session affinity
- resource provenance / routing policy

### (4) 借りられる設計・実装アイデア

resolved resource descriptorにcanonical valueだけでなく、判断に必要なprovenanceを残す。

```text
ResolvedResource {
  requested_identity,
  canonical_family,
  resolved_endpoint,
  transport,
  auth_scheme,
  resolution_path,
  policy_epoch
}
```

ただしaux/fallbackへrequested identityを無条件伝播せず、resolved routeがsame endpoint/familyの時だけ利用する。

### (5) Kamimusuhiとの差分

`EndpointQualifiedProtocolBinding`はsemantic provider名とactual wire protocolを分ける。今回は**canonicalizationで捨てたpre-resolution identityが、後段のaffinity/capability判断に必要**というprovenance retentionの差分。

### (6) 次に検証すべきこと

独立benchより `EndpointQualifiedProtocolBindingBench-v0` へ追加:

- alias→canonical family
- custom endpoint→generic family
- fallback route
- restart / restore / model switch
- requested identityがunrelated routeへleakしないこと

### (7) 既存dailyで拾いにくい理由

通常のprovider surveyはendpoint/schema互換性を見るが、normalization工程で落ちたidentity provenanceがwarm-session behaviorへ影響する問題はresolver/affinity境界に埋もれる。

### (8) 重要度

**B** — fresh実装証拠は強いが、既出endpoint/provenance contractへの差分であり独立原則にはしない。

## 10. 今回の結論

今回の最大の収穫は、**「認知系へ入った文字列は、その由来を失うと次の行動の“自己模倣用教師データ”になり得る」**ことと、**「環境変化を検出しただけでは、それを認知個体が処理したことにはならない」**ことの二点。

Kamimusuhi向けには次の4契約を強く推す。

```text
synthetic maintenance metadata must stay typed as synthetic
observation cursor advances only at an explicit consumption boundary
working context can be usable without being persistable
retryable intent becomes inert after verified successful application
```

直前runまでのcontinuity設計は主に「何を失わず持ち越すか」を強化してきた。今回の差分は逆に、**何を“自分の過去”として扱ってはいけないか、何をまだ“処理済み”として扱ってはいけないか、何を成功後まで生かしてはいけないか**を明確にする方向である。
