## A — Assurance-Claim Qualification

Sources:
- Hermes #121583: https://github.com/NousResearch/hermes-agent/issues/121583
- Silent Failures in Agent-Tool Interaction, arXiv:2609.26836: https://arxiv.org/abs/2609.26836
- Certified Against Which Oracle?, arXiv:2609.25938: https://arxiv.org/abs/2609.25938

### (1) 何が実証済みか

Hermes #121583 は実運用上、tool/verifier自体の実行成功と、検査対象の良否、retryability、検査coverageを一つのtask statusでは区別できないと報告する。具体例として利用可能168 checksのうち78だけをassertしたrunが完全passと同じ形で記録され得た。

arXiv:2609.26836 は15 scientific toolsを監査し、LLM候補抽出・自動test・manual validation後に91件のsilent failureを確認したと報告する。51件はAPI layer、25件はwrapper layerで、missing fieldsやsearch/filter/ranking条件の不一致が下流へvalid-looking outputとして伝播し得る。

arXiv:2609.25938 はText-to-SQL conformal abstentionでcorrectness oracleを差し替えると、certificateのheld-out riskが自己ラベル上のriskより2.73–10.23 points高くなり、expert labelsではnominal 0.10 certificateに20.0 / 17.2 pointsのriskが観測されたと報告する。またscore constructionに使ったoracle自身のlabelsで評価するとscoreが有利に見える系統差も示した。

### (2) 何が提案・推測段階か

Kamimusuhi共通のAssuranceRecordへ統合することは設計提案。open-world taskではcoverage denominator自体が完全には定義できないため、COMPLETEだけでなくPARTIAL / OPEN_WORLD / UNKNOWNを持たせる必要がある。

### (3) 関係subsystem

K-Deep research、self-improvement promotion、Mutation/Activation Gate、runtime assurance、tool result integration、Canonical Evidence、observability。

### (4) 借りられる案

verification resultを少なくとも以下へ分離する。

- execution_status
- subject_verdict
- retryability
- coverage basis / examined / unexamined
- oracle_id / version
- evaluator provenance
- evidence refs
- limitations

COMPLETE実行をPASSと同一視せず、PASSをcoverage completeとも同一視しない。

### (5) Kamimusuhiとの差分

verification adequacy、claim-safe evaluation、Epistemic Verification Backpressure、Operational-Mode Coverageは既出。今回の差分は **1件のassurance claim内部にcoverageとoracle identityを保持する**点。

### (6) 次に検証

**AssuranceQualificationBench-v0**

- verifier成功だがsubject fail
- 一部だけ検査して全pass
- prerequisite不足でほぼ未検査
- oracle A/Bで結論不一致
- plain PASSとqualified recordをdownstreamへ渡した時の誤promotion率比較

### (7) dailyで拾いにくい理由

scientific tool reliability、workflow record semantics、conformal prediction、epistemology of incomplete observationの交点であり、通常のagent/safety分類では「verifier精度」に縮約されやすい。

### (8) 重要度

**A — 独立新規**

## A update — Presentation-Frontier Qualified Utterance Memory

Sources:
- Hermes #121594: https://github.com/NousResearch/hermes-agent/issues/121594
- Hermes #121613: https://github.com/NousResearch/hermes-agent/issues/121613

### (1) 実証済み

#121594ではstreaming replyをinterruptしたとき、screen上のpartial replyよりstate.dbのassistant rowが少し長くなり、次turnではmodelがuserに見えていないsuffixまで以前の自発話として受け取るraceが報告された。例ではscreen 432 chars、persisted 436 chars。loaded hostで約1/16 runs。

#121613ではbackendでcompleteかつDBに457 chars保存されたreplyがDesktop上で一度見えた後に消える現象が報告された。具体root causeはissue時点ではsource-level hypothesisであり未確定。

### (2) 提案段階

userが実際に読んだことはUIでは証明できない。記録できるのはsurfaceへ提示されたextentまで。

### (3) 関係subsystem

Dialogue、relationship/autobiographical memory、multi-surface embodiment、interruption、voice/text streaming、Channel-Aware Turn Settlement。

### (4) 借りる案

assistant utteranceについて generated_extent / persisted_extent / presentation_frontier_by_surface / delivery_certainty / interruption_cut を分離する。

### (5) 差分

2026-09-22のChannel-Aware Turn Settlementはsemantic payloadとuser-visible deliveryを既に分ける。今回の新情報は **deliveryがmessage単位のboolではなく、同一stream内のpartial extentになり得る**こと。

### (6) 次に検証

**InterruptedUtterancePresentationFrontierBench-v0**: interrupt jitter、surface A/B差、UI retention、restartを組み合わせ、unseen suffixが「相手へ言った記憶」へ昇格しないことを確認する。

### (7) dailyで拾いにくい理由

## A update — Batch-Scoped Control-Transfer Settlement

Source:
- OpenClaw #157364: https://github.com/openclaw/openclaw/issues/157364

### (1) 実証済み

同一assistant messageにsessions_yieldとsibling tool callが含まれると、yieldのturn handoffでsiblingが実行開始前にabortされてもrun全体がsuccessになるケースが報告された。issueのproduction/source evidenceでは、siblingは333msでpreflight abort、同じcommandを単独turnで実行すると574msで成功した。

### (2) 提案段階

Kamimusuhiでdrain・pre-admission reject・明示cancelのどれを採るかはeffect class依存で未決。

### (3) 関係subsystem

Cognitive Action Router、K-Core↔K-Deep handoff、tool orchestration、external effects、completion-publication barrier。

### (4) 借りる案

control transferをbatch settlement barrierとして扱い、既にadmitされたsiblingsはterminal / explicit cancelled / unknown outcomeのいずれかへ必ずsettleさせる。

### (5) 差分

abort liveness、pre-commit handoff abortability、cancellation closureは既出。今回の差分は **一つのturnの中に複数effectとcontrol-transferが同居する場合のsibling fate**。

### (6) 次に検証

**BatchControlTransferSettlementBench-v0**: read-only / idempotent write / non-idempotent effect / approval-waiting siblingをpreflight・executing・provider-accepted各phaseでyieldと競合させる。

### (7) dailyで拾いにくい理由

handoffとtool executionを別領域として見ると、同一batchの局所lifecycleが抜ける。

### (8) 重要度

**A update**

## B update — Policy-Invalidation Fallback Intent Preservation

Source:
- OpenClaw #157377: https://github.com/openclaw/openclaw/issues/157377

### (1) 実証済み

sessionのmodel overrideがpolicy変更でdisallowedになると、configured primaryではなくcatalogの最初のallowed modelへfallbackするreproductionが報告された。provider declaration orderを変えるとfallback先も変わる。

### (2) 提案段階

primary自体がdenyされた時の完全なfallback policyは別途必要。

### (3) 関係subsystem

Cognitive Action Router、degraded mode、configuration authority、model/provider policy。

### (4) 借りる案

invalidated override → admissible configured primary → configured fallback chain → explicit unavailable、の順をsemantic contractにし、collection orderをfallback意味論にしない。

### (5) 差分

Configuration Authority Precedence / execution-placement fallback authorityへの具体update。

### (6) 次に検証

**PolicyInvalidationFallbackIntentBench-v0**: provider orderをpermutationし、policy mutation後も選択がconfigured intentだけで決まることを確認。

### (7) dailyで拾いにくい理由

model routing surveyは品質/価格/速度を追いやすく、collection order由来の意味論は見落とされやすい。

### (8) 重要度

## B watch — Device-Custodied Private Memory Continuity

Primary source:
- Google DeepMind, 2026-09-23: https://deepmind.google/blog/advancing-private-ai-compute-with-secure-server-side-memory/
- Trail of Bits publications listing: https://github.com/trailofbits/publications

GoogleはPrivate AI Compute向けに、dedicated encrypted storage、personal-device-held keys、authenticated E2E channel、secure enclave内での一時復号、per-user database、server software authenticityを端末側で検証するpublic recordを組み合わせたpersistent cross-device memory architectureを公開した。

これはactual long-term product deploymentの実証ではなくtechnical architecture。KamimusuhiにはPartial-TEE Trust、Rotation-Domain Key Separation、cryptographic custody unavailable、multi-device recovery metadataが既出なので独立promotionしない。

借りるなら、memory ciphertext location / decryption-key custody / execution attestation / canonical identity authorityを別domainにする。device loss、device追加/削除、key rotation、consent withdrawal、deletion verification、backup/restoreをwatchする。
