## 3. 要約

今回もっとも直接的な blind spot は、**「scope がない」ことを「全scopeに作用してよい」と読まない**ことである。Hermes Agent #112885 では、launch profile の MCP server `x` を config から削除しただけなのに、`scope=None` が wildcard と解釈され、同じ名前の server `x` を持つ profile B の接続まで shutdown された。修正後は、引数なしの bare call だけを process-wide wildcard とし、`scope=None` + `names={x}` は明示的な unscoped owner の `x` だけに作用する。これは Kamimusuhi で memory organ / tool / sensor / model endpoint を複数principalが共有する際、**absence-of-scope を destructive authority に昇格させない**契約へ一般化できる。

第二は rollback。#112882 では agent-write ledger の key と restore planner の key が別の path normalization を使っていたため、ledger が空に見え、`safe=True` なのに full `git checkout` へfall throughして人間の手編集まで上書きした。rollback は「過去checkpointへ戻す」操作ではなく、**誰が何を書いたかという provenance を保った selective compensation**であるべきだと分かる。Kamimusuhi の self-modification / code-writing organ では、canonical checkpoint と agent-write ledger の scope identity を一つの関数・IDに統一する必要がある。

第三は software-body hot update。#112753 は updater 自身が pre-pull interpreter 上で動き続けるため、`sys.modules` から旧submoduleを除去しても parent package の属性に旧module objectが残り、`from package import child` が新sourceを読まず旧objectを返す実障害を示した。つまり **disk revision / git head / package version が新しくても、実行中 software body は旧・新の混合epochになり得る**。Kamimusuhi の software-body lineage は artifact revision だけでなく、live loaded-code epoch / process epoch / handler epoch を観測対象にする必要がある。

第四は runtime context の輸送。#112837 では boot-time warmup が bare executor threadへ移ったことで profile secret scope を失い、non-production routing override が見えずproduction endpointへhealし、refresh tokenを誤ったendpointへ送る経路が生じた。Pythonの `contextvars` 自体も thread ごとに独立した current context stack を持ち、別threadで同じcontextを使うには明示的な context entry が必要である。Kamimusuhiでは principal / relationship / privacy / embodiment / authority / causal-turn context を「呼び出しstackの雰囲気」に任せず、async/thread/executor境界で明示的に輸送・検証すべきである。

第五は multi-agent causality。Barbaraci & Cachin は、Byzantine process が dependency を偽造・省略できるため、古典的 happened-before を各processの自己申告eventsだけから作っても causal broadcast を保証できないと示し、十分なcorrect process群のjoint observationに基づく causal ordering を定式化・証明した。Kamimusuhi の external peers / branch identities / social harness にそのまま同protocolを入れる必要はないが、**「peerがこのevidenceを見てから発話した」という主張を peer自身のmetadataだけで canonical social history にしない**という設計圧になる。

最後に #112883 は、fault説明が profile A のstoreを指していても、copy-paste remediation commandが sticky active profile B に作用し得た問題を修正した。これは telemetry attribution の再提案ではなく、**診断 provenance から remediation target まで binding を切らさない**具体的差分として扱う。

# 5. 候補ごとの評価

## 5.1 A+ — Explicit Destructive Scope: `None` / missing scope を `ALL` にしない

**Primary source**

- NousResearch/hermes-agent PR #112885 — *Launch profile pruning an MCP server no longer tears down served profiles' same-named connections*  
  merged **2026-09-17 00:45:38 JST**  
  https://github.com/NousResearch/hermes-agent/pull/112885

### (1) 何が実証済みか

Hermes Agent の multi-profile backend で、launch profile が MCP server `x` を削除/disableしたとき、`shutdown_mcp_servers(scope=None, names={'x'})` が `scope is None` を「全owner」と解釈し、profile B の `(B, 'x')` connectionまでshutdownしていた。

修正後は意味を分けた。

```text
shutdown_mcp_servers()                     -> process-wide wildcard
shutdown_mcp_servers(scope=None, names={x}) -> explicit unscoped owner の x
shutdown_mcp_servers(scope=B, names={x})    -> B の x
```

PRの検証では、修正前の新規 invariant test は profile B の接続が消えて `KeyError`、修正後は関連13ファイルで177 tests green。live probe でも `scope=None, names={'x'}` は launch owner の `x` だけ閉じ、`(B,x)` は残った。

### (2) 何が提案・推測段階か

Kamimusuhi の全APIで `None` を禁止すべき、という主張ではない。提案するのは、**destructive / revocation / teardown operation において wildcard authority を absence や falsy value で表現しない**こと。

### (3) 関係するサブシステム / 設計課題

- Cognitive Action Router
- tool / MCP / external model registry
- K-Edge / K-Core organ lifecycle
- shared sensor / actuator endpoints
- multi-principal / multi-body resource ownership
- capability security
- maintenance / shutdown / revoke
- INV-006 / INV-013 / INV-014

### (4) 借りられる設計・実装アイデア

破壊的操作には explicit selector を要求する。

```text
ResourceScope =
  | Owner(principal_id, owner_epoch)
  | Organ(organ_id, generation)
  | Resource(resource_id, instance_epoch)
  | AllOwners(GlobalMaintenanceCapability)
```

API例:

```text
teardown(scope=Owner(...), names={...})
teardown(scope=AllOwners(global_maintenance_cap), names={...})
```

`None`, missing field, parse failure, unknown owner は fail-closed。`AllOwners` は typed token + capability receipt + audit reason を必須にする。

### (5) Kamimusuhiとの差分

Kamimusuhi は task-scoped capability、execution owner、causal embodiment binding を強く意識しているが、**maintenance API の selector encoding 自体が ambient/global authority を作る**問題は未収載。権限が正しくても selector の sentinel semantics が弱いと別body/organへ破壊作用が広がる。

### (6) 次に検証すべきこと

**`ExplicitDestructiveScopeBench-v0`**

- owner A/B が同名 `memory-index`, `MCP:x`, `speech`, `local-model` を持つ。
- Aのresourceだけを disable / restart / revoke / prune。
- `None`, empty string, unknown owner, stale owner epoch, omitted field を fault-inject。
- 成功条件:
  - A以外へ作用しない。
  - wildcardは explicit `AllOwners` + global maintenance capability なしでは生成不能。
  - stale owner generation は current resource を壊せない。
  - audit log が selector provenance を保持する。

### (7) 既存dailyではなぜ拾いにくいか

通常は「MCP teardown bug」「multi-profile bug」と分類される。重要なのはMCPではなく、**API sentinel value が capability semantics を暗黙に拡大する**という capability-security / language-API design の境界である。

### (8) 重要度

**A+** — distributed embodiment / multiple organ ownership を実装すると再発しやすく、cross-principal destructive effect に直結する。

## 5.2 A+ — Rollback Provenance-Key Coherence: rollback は selective compensation である

**Primary source**

- NousResearch/hermes-agent PR #112882 — *Safe rollback no longer overwrites hand-edits when the restore dir is not a project root*  
  merged **2026-09-17 00:45:10 JST**  
  https://github.com/NousResearch/hermes-agent/pull/112882

### (1) 何が実証済みか

Hermesの `record_agent_write` は agent-write ledger を marker-walk した project root でkey化していた一方、`safe_restore_plan` は exact restore dir のhashで読むという非対称があった。

そのため、restore dirそのものにmarkerがなく、ancestorに `.git` / `package.json` 等がある場合、plannerからledgerが空に見え、`restore(safe=True)` が full `git checkout <hash> -- .` へfall throughし、agentが変更していない人間の `README` まで上書きした。

修正では writer / reader が一つの `_ledger_key` を使う。新規testは修正前1 fail、修正後56 pass。live probeでも hand-edited README を保持しながら agent-written `main.py` だけrestoreした。

### (2) 何が提案・推測段階か

Git checkpointをKamimusuhiの唯一の rollback substrate にする提案ではない。一般化するのは、**safe rollback の安全性は snapshot の存在ではなく、mutation provenance と restore-domain identity の一致に依存する**こと。

### (3) 関係するサブシステム / 設計課題

- self-modifying software body
- code-writing / coding-agent organ
- checkpoint / rollback
- candidate Persona Core training artifacts
- generated config / skill evolution
- human-in-the-loop co-editing
- external repository / working tree ownership

### (4) 借りられる設計・実装アイデア

`RollbackDomainId` をcanonicalizeし、checkpoint・write ledger・restore plannerが同じIDを使う。

```text
RollbackReceipt
  domain_id
  checkpoint_id
  base_revision
  agent_written_paths[]
  external_written_paths[] | unknown
  writer_principals[]
  write_epoch
  restore_plan_digest
  conflict_policy
```

原則:

```text
rollback target = agent-attributable delta
not = entire directory at historical commit
```

人間/他agentの変更と重なる場合は silent overwrite ではなく conflict / ask / quarantine。

### (5) Kamimusuhiとの差分

現行設計は canonical evidence と derived state の rollback / lineage を重視しているが、**software-body working treeの co-ownership** は別問題。checkpointが正しくても、`who changed what after checkpoint` を失うと rollback が他principalの現在を破壊する。

### (6) 次に検証すべきこと

**`ProvenancePreservingRollbackBench-v0`**

- agent A、human、agent B が同一repoの別path/同一pathを交互編集。
- checkpoint後に cwd/path alias、symlink、subdir、nested repo、marker-in-ancestor を変化させる。
- Aだけを rollback。
- 成功条件:
  - A-only deltaは戻る。
  - human/B-only deltaは保持。
  - overlapping deltaは自動全消去せずconflict化。
  - ledger key normalizationを変えても same `domain_id` にresolve。
  - ledger missing時は destructive full restoreへ自動fallthroughしない。

### (7) 既存dailyではなぜ拾いにくいか

「checkpoint」「recovery」「self-modification」は拾えても、問題の本体は **provenance-key normalization と co-owned filesystem semantics**。Git/IDE/backup研究の境界にあり、agent memory surveyから外れやすい。

### (8) 重要度

**A+** — 長寿命agentが自分のsoftware bodyやユーザーrepoを編集し続けるなら、誤rollbackは外部データ破壊と自己更新失敗の両方を起こす。

## 5.3 A — Software-Body Namespace Epoch Coherence: source更新とlive code更新を分ける

**Primary source**

- NousResearch/hermes-agent PR #112753 — *post-update cleanup no longer crashes on a pre-pull hermes_cli submodule*  
  merged **2026-09-16 19:34:28 JST**  
  https://github.com/NousResearch/hermes-agent/pull/112753

**Supporting runtime semantics**

- Python `importlib` documentation / approximate import implementation  
  https://docs.python.org/3/library/importlib.html

### (1) 何が実証済みか

`hermes update` は **pre-pull interpreter** のまま source treeを更新し、その後 cleanup を続ける。旧 `hermes_cli.main_dashboard` を `sys.modules` からevictしても、purge対象外のparent package `hermes_cli` が旧submodule objectを属性として保持していた。

その結果、`from hermes_cli import main_dashboard` は新sourceをimportせず旧objectを返し、新版にしかないsymbolを参照して `AttributeError` になった。PR説明ではこの形の in-tree call site が約200ある。

修正は `sys.modules` entryだけでなく **parent package bindingも object identity を確認して除去**する。regression 2件はmainでred、branchでgreen、focused 102 tests pass。live field pathも crashせず返った。

Python import machineryの説明でも、submodule import時に parent moduleへ child module attribute を設定する構造が示されている。

### (2) 何が提案・推測段階か

Pythonだけの問題ではない。Node module cache、JVM classloader、plugin registry、model/tokenizer cache、schema handler tableでも類似の mixed epoch は起こり得る。Kamimusuhiで「hot updateを禁止」すべきかは未決定。

### (3) 関係するサブシステム / 設計課題

- software-body lineage
- self-update / autonomic maintenance
- live process upgrade
- tool/plugin/skill reload
- K-Core/K-Edge runtime migration
- deterministic replay
- observability / version attestation

### (4) 借りられる設計・実装アイデア

`SoftwareBodyEpoch` を artifact version と live loaded state に分ける。

```text
SoftwareBodyState
  artifact_revision
  process_epoch
  loaded_module_epoch
  schema_epoch
  plugin_registry_epoch
  model_runtime_epoch
  mixed_epoch_detected
```

self-update後は少なくとも:

1. live namespace invalidationを検証する、または
2. 新processへhandoffして旧processをdrainする。

**「git HEADが新しい」だけで migration success にしない。**

### (5) Kamimusuhiとの差分

既出 deterministic replay / software-version continuity は「どのversionで実行したか」を保存する契約が中心。今回の差分は、**一つのprocess内に複数versionのcode objectが同時残存し得る**ため、単一 `software_version` field が嘘になること。

### (6) 次に検証すべきこと

**`MixedSoftwareBodyEpochBench-v0`**

- long-running processで v1 module / tool schema / callbackをload。
- diskをv2へ更新。
- cache evictionを部分的に行い、旧closure / parent binding / background callbackを残す。
- 成功条件:
  - mixed epochを検出できる、または新work admissionを停止する。
  - v1 callbackがv2 canonical mutation contractを破らない。
  - self-update completionは live attestation 後のみcommit。
  - replay logに artifact + process/module epoch が残る。

### (7) 既存dailyではなぜ拾いにくいか

「self-improvement」「software evolution」はモデルやcode diffに寄りやすく、**language runtime の import/cache object graph** は下位実装詳細として落ちる。しかし長寿命processではここが software-body continuity の実体になる。

### (8) 重要度

**A** — immediate identity lossではないが、自己更新個体で旧/新policy・schemaが混ざると再現不能な行動と安全境界破壊を生む。

## 5.4 A — Causal Context Transport Across Executor Boundaries

**Primary source**

- NousResearch/hermes-agent PR #112837 — *boot warm-up and free-tier bootstrap run inside the launch profile's scope under multiplex*  
  merged **2026-09-16 19:46:26 JST**  
  https://github.com/NousResearch/hermes-agent/pull/112837

**Supporting runtime semantics**

- Python `contextvars` documentation  
  https://docs.python.org/3/library/contextvars.html

### (1) 何が実証済みか

Hermesのboot warmupは `_warm_turn_machinery_sync` を bare executor thread 上で実行した。multiplex環境では profile secret scope が context-local だったため、executor側で routing override を読めず、non-production endpoint設定が消え、production endpointへhealする経路が発生した。PR説明では non-production refresh token がproduction Portalへ送られ `invalid_grant` / OAuth quarantine へ至るfield pathが示されている。

修正では launch profile の runtime scopeへ入り、`copy_context().run` で executor に current context を輸送する。focused 41 files / 391 tests pass。live probeではmainが16 schemas / 17 `check_fn` で fail-closed pathに入りcache 0だったのに対し、修正版は24 schemas、fail-closed 0、cache populationあり、終了後context leakなし。

Python docsでも各threadは別のtop-level `Context` stackを持ち、`copy_context()` と `Context.run()` が明示的なcontext管理機構として定義される。

### (2) 何が提案・推測段階か

KamimusuhiがPython `contextvars` を必須採用する提案ではない。一般化は、**principal / policy / privacy / embodiment / causal-turn state が ambient context にあるなら concurrency boundary は security boundaryでもある**こと。

### (3) 関係するサブシステム / 設計課題

- K-Edge/K-Core background workers
- external model/tool orchestration
- relationship / privacy scope
- secret / credential resolution
- per-device embodiment
- background cognition
- telemetry attribution
- async → thread / executor / process delegation

### (4) 借りられる設計・実装アイデア

`ExecutionContextReceipt` を明示化する。

```text
ExecutionContextReceipt

```

- explicit copy / serialization
- receiver-side validation

### (5) Kamimusuhiとの差分

既出 `AsyncCausalContext` / Delegation Envelope は「誰の依頼か」「子に何を渡すか」が中心。今回の差分は、**同一logical operationの内部実装で thread/executorへhopしただけでも ambient authority が消える**こと。delegationしていないつもりでも security/identity boundary が生まれる。

### (6) 次に検証すべきこと

**`ExecutorContextContinuityBench-v0`**

- same operationを direct / asyncio task / thread pool / process / delayed callback で実行。
- principal A/B、private relationship scope、device-local credentialを交差。
- 成功条件:
  - expected scope digestが全boundaryで一致。
  - missing contextはA/B/defaultへ推測fallbackしない。
  - callback完了後contextが次taskへleakしない。
  - stale principal epochはeffectを起こせない。

### (7) 既存dailyではなぜ拾いにくいか

orchestration surveyはagent-to-agent delegationを見がちで、**同一process内部の executor hop** は言語runtime detailとして見落とされる。しかし長寿命background cognitionでは頻出する。

### (8) 重要度

**A** — credential leakだけでなく、別person/別bodyのmemory・tool authorityを誤解決する原因になる。

## 5.5 A — Byzantine Causal Provenance: peer自己申告の causality を canonical にしない

**Primary source**

- Mariarosaria Barbaraci, Christian Cachin, *Byzantine Reliable Broadcast with Causal Ordering*, arXiv:2609.17074, submitted 2026-09-15  
  https://arxiv.org/abs/2609.17074

### (1) 何が実証済みか

論文は Byzantine process を含む reliable broadcast で、古典的 happened-before を individual process のlocal event relationとして使うだけでは broadcast message間の causal ordering を保証できないことを示す。Byzantine processは dependency information を lie / omit / forge でき、その操作がsingle observerにはcorrect behaviorと区別できない場合がある。著者らは front-running attack で問題を示し、local potential knowledgeをexternalizeし、十分なcorrect process群のjoint observationsに基づく causal orderingを定式化する。

さらに最適耐障害数 `f < n/3` にresilientなprotocolを提示し、そのcausal reliable broadcast propertyを証明する。これは形式的protocol結果であり、LLM agent社会での empirical study ではない。

### (2) 何が提案・推測段階か

Kamimusuhiのexternal agents / branchesに Byzantine broadcast protocolをそのまま実装する必要性は未証明。特に通常のpersonal agent networkで `n/3` adversary modelが妥当とは限らない。

借りるべきなのは **causal claimとcausal evidenceを分ける**原則。

### (3) 関係するサブシステム / 設計課題

- Social Harness
- branching / collective identity
- external agent federation
- common ground
- distributed autobiographical evidence
- provenance / causal graph
- multi-device observation reconciliation

### (4) 借りられる設計・実装アイデア

外部peer由来の causal metadataを段階化する。

```text
CausalClaim
  claimed_predecessors[]
  claimant
  signature

CausalEvidence
  observed_by[]
  receipt_ids[]
  quorum_or_trust_policy
  verified_relation
```

`peer says seen(X)` は library/social claim にはなれても、canonical `X -> Y` edgeへ自動昇格しない。重要な shared commitment / lineage / effect ordering は independent receipt / trusted observer / local witness で補強する。

### (5) Kamimusuhiとの差分

既出 Social Harness は inter-agent communication の admission / validation / accountability を要求するが、**message内容ではなく causal metadataそのものを adversarial object として扱う**点は未収載。ParticipationEnvelopeが正しく署名されても、そのsenderがdependencyを嘘申告する可能性は残る。

### (6) 次に検証すべきこと

**`AdversarialCausalClaimBench-v0`**

- 3〜7 simulated peersで shared task / common-ground updateを行う。
- one peerが predecessor omission、forged dependency、front-run、late replayを行う。
- self-reported metadata-only と independent receipt-backed causal graph を比較。
- 成功条件:
  - unverified causal edgeが canonical commitment orderを変更しない。
  - false dependencyでrelationship/shared factが上書きされない。
  - evidence不足は `unknown/contested` として残る。

### (7) 既存dailyではなぜ拾いにくいか

multi-agent surveyは「通信内容」「protocol」「trust」を見るが、**causality relation自体のtruthfulness** は distributed-computing の Byzantine broadcast literatureに埋もれやすい。

### (8) 重要度

**A** — external peersやbranching identitiesを本格導入する段階で重要。現状単体Kamimusuhiのv0.1には即必須ではないためS/A+にはしない。

## 5.6 B+ — Remediation Target Binding: fault provenance を repair command まで保持する

**Primary source**

- NousResearch/hermes-agent PR #112883 — *Persistence-failure `hermes` commands name the failing profile on every surface*  
  merged **2026-09-17 00:45:33 JST**  
  https://github.com/NousResearch/hermes-agent/pull/112883

### (1) 何が実証済みか

multi-profile backendで profile A の `state.db` が失敗しても、説明文内の bare `hermes doctor`, `hermes gateway stop`, `hermes sessions recover` は sticky `active_profile` に従うため、operatorがcopy-pasteすると別profile Bを診断・停止・recoverし得た。

修正後は failing store/profile に対応した `-p <profile>` selectorを説明・warning・fallbackの各surfaceへ埋め込む。mainで新規testsはred、branchでは82 focused tests + 127 consumer tests green。live probeでも `profiles/research` のfailureから `hermes -p research ...` が出る。

### (2) 何が提案・推測段階か

Kamimusuhiで人間向け remediation command を必ずshell commandにする必要はない。一般化するのは **diagnosis origin と repair target の binding**。

### (3) 関係するサブシステム / 設計課題

- observability / incident response
- operator UI
- multi-device / multi-profile recovery
- memory store repair
- organ restart
- distributed embodiment maintenance

### (4) 借りられる設計・実装アイデア

```text
RemediationProposal
  incident_id
  faulting_resource_id
  faulting_owner_epoch
  diagnosis_evidence[]
  proposed_action
  target_selector
  capability_required
  generated_at
```

UIがactive bodyを切り替えても `target_selector` は incident にpinする。operatorが明示的に retarget した場合は別proposalとしてauditする。

### (5) Kamimusuhiとの差分

telemetry attribution / causal embodiment binding は「誰/どこで起きたか」の記録。今回の差分は、**その情報を人間が実行する修復actionまでcarryする**こと。

### (6) 次に検証すべきこと

**`IncidentScopedRemediationBench-v0`**

- Aでstorage fault、BをUIでactiveにする。
- diagnosis後に active body/profileを何度も切替。
- stop/recover/rebuild proposalsがAへpinされたままか確認。
- stale generationのAが既にreplacedされた場合は再validationを要求。

### (7) 既存dailyではなぜ拾いにくいか

observability surveyでは diagnosis accuracyまで、authorization surveyでは action executionから見始めやすい。**診断→人間向け指示→実行のUI seam** が中間で抜ける。

### (8) 重要度

**B+** — immediate architecture pillarではないが、multi-device運用時の operator-induced incident amplification を防ぐ実装契約として有用。

- Zenn / note / Qiita の当日AIエージェント紹介・ニュースまとめ — discovery sourceとして確認したが、今回の一次実装 finding を更新する独立した実証なし。
