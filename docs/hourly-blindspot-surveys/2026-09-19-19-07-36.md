## 1. 今回狙った盲点

1. **snapshot / restore が ephemeral state を複製する問題**  
   起動時に作った random ID、credential、timestamp、PRNG state、tool inventory、hostname/PID由来 identity が、snapshot復元個体へそのまま複製されないか。

2. **layered configuration の再読込が一回目と二回目で意味を変える問題**  
   source precedence が正しくても、一回限りのsource passと繰返しdotenv loadの組合せで authoritative secret が低優先sourceへ戻らないか。

3. **API timeout と caller wall-clock bound の混同**  
   future が deadline で timeout しても、cleanup/finalizer/executor shutdown が hung child を join して caller を拘束し続けないか。

4. **degraded-mode maintenance が通常時より destructive になる問題**  
   summary/consolidation/repair subsystem が過負荷・不調な時に、品質の低いfallbackを authoritative stateへ書き戻して不可逆に情報を減らさないか。

5. **delivery timeout の結果が曖昧な時の retry semantics**  
   timeout時点で「相手に全く届かなかった」のか「commit直後にackだけ失った」のか不明なのに、full payload replayで二重実行したり、何も通知せずsilent lossにしたりしないか。

6. **capabilityを独立した環境変数の集合として扱う問題**  
   tokenと対象URLのように意味的に結合した capability がconfig layerごとに片側だけ上書きされ、別home/profileへreplayされないか。

補助探索として、OS/RTOS priority inversion、snapshot-based serverless runtime、spatial/semantic uncertainty decomposition、formal/runtime assurance、Zenn / note / Qiita の当日 agent 運用記事を走査した。priority inversion は Kamimusuhi 内に直接の収載を確認できなかったが、今回は fresh implementation evidence が十分強いため backfill finding への昇格は見送った。

# 5. 候補ごとの評価

## 5.1 A — Snapshot restore では ephemeral state をsnapshot-safe stateから分離する

**Primary sources**

- AWS, *The new AgentCore Runtime is now available*, 2026-09-18  
  https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/
- AWS, *Optimize your agent for Amazon Bedrock AgentCore Runtime V2*  
  https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-v2-optimize.html

### (1) 何が実証済みか

AgentCore Runtime V2は、startup完了後のprocess stateをsnapshotに取り、複数instanceをそのsnapshotからrestoreする公式runtimeである。AWS公式ガイドは、startupで生成したrandom value / token / timestamp / monotonic reference / credential / hostname/PID由来ID / tool inventoryがrestore後もfreshではないことを具体的に列挙している。crypto libraryについてもrestore後reseed可能なsnapshot-safe buildを要求する。

これは「LLMの推測」ではなく、実運用runtimeの明示的なservice contractである。

### (2) 何が提案・推測段階か

KamimusuhiがAgentCore V2を使う予定である、あるいは現行K系runtimeに同じbugがある、という証拠はない。提案はVM snapshot、fork、hibernation、checkpoint/restore、warm pool等に一般化できると推測するもの。

### (3) Kamimusuhiのどこに関係するか

- distributed embodiment / multi-device embodiment
- K-Edge / K-Nerve process incarnation
- credential freshness / capability validity
- Continuity Kernel のbody/runtime incarnation
- observability / lock owner / telemetry identity
- recovery / backup / restore / migration

### (4) 借りられる設計・実装アイデア

stateをrestore semanticsで型分けする。

```text
SnapshotStateClass
  VERSION_IMMUTABLE       # model weights, static schema, bundled config
  RESTORE_REFRESH         # credentials, tool catalog, external capability map
  INSTANCE_UNIQUE         # worker/body incarnation id, lock-owner id
  REQUEST_UNIQUE          # request id, nonce, trace id
  TIME_REBASE_REQUIRED    # monotonic reference, leases, deadline origin
  ENTROPY_RESEED_REQUIRED # PRNG / crypto state
```

restore hookは`restore_epoch`を発行し、`RESTORE_REFRESH`以下が完了するまでexternal effectを許可しない。

### (5) Kamimusuhiとの差分

既存のsoftware-body epoch、capability freshness、state-transfer closureは「version / authority / transfer対象」を扱うが、**同一snapshotを複数bodyへ復元したとき、ephemeral identityやentropyまで同一になる問題**は明示していない。identity continuityのために同じものを残す領域と、continuityを守るために必ず変えなければならない領域を分ける必要がある。

### (6) 次に検証すべきこと

**`SnapshotEphemeralStateSeparationBench-v0` — P0 candidate**

- 同一checkpointからN=16〜64 instanceを復元
- startup UUID / PRNG sequence / nonce / `time.monotonic()`基準 / credential / tool catalog / lock-owner / telemetry worker IDを観測
- restore前後でcredential expiry、tool catalog change、policy epoch changeを注入
- `restore_epoch`前のeffectをblock
- 成功条件:
  - instance/request IDs collision 0
  - expired credential reuse 0
  - mutable catalog stale-use 0
  - monotonic deadline誤判定 0
  - snapshot-safe static stateの再初期化コストは最小

### (7) なぜ既存dailyでは拾いにくいか

AI agent論文ではなく**serverless microVM snapshotのruntime contract**に埋まる問題だから。今回Qiitaをdiscovery sourceとして拾い、AWS一次資料へ辿った。

### (8) 重要度

**A** — long-lived/distributed selfでsnapshot/hibernate/warm restoreを採用すると、identity・security・timing・observabilityへ同時に効く。

## 5.2 A — Layered config reload は authority-respecting fixed point であるべき

**Primary source**

- Hermes PR #115984  
  https://github.com/NousResearch/hermes-agent/pull/115984

### (1) 何が実証済みか

external secret sourceでplaceholderを実値へ解決した後、二回目のdotenv loadがraw placeholderを`override=True`で復活させるlive failureが報告されている。external source passはhomeごと一回のみなので再解決されず、その後gatewayがplaceholderやrotated-away tokenを使い続ける。修正案はauthority provenanceを保存し、authoritative sourceが所有するnameだけreload後に再assertする。targeted suitesは167件（78+89）passと報告。

### (2) 何が提案・推測段階か

PRはopen/unmergedであり、Kamimusuhiに同じdotenv構成がある証拠はない。一般化は「同じ入力・同じauthority graphならre-materialization後のeffective stateが同じ」というfixed-point性を設計契約にする提案。

### (3) Kamimusuhiのどこに関係するか

- external resources / credentials
- configuration authority
- profile / body / environment isolation
- long-running process reload
- K-Edge / tool/model routing config

### (4) 借りられる設計・実装アイデア

各effective valueに`source + authority + scope + source_epoch`を付与し、reloadを純粋なrecompositionとして扱う。

```text
EffectiveValue
  value
  source_id
  authority_rank
  scope_id
  source_epoch
  materialized_at
```

入力が変わっていなければ `materialize(materialize(S)) == materialize(S)` を満たす。source変更時のみ対応fieldを更新し、低authority placeholderが高authority resolved valueを復活させない。

### (5) Kamimusuhiとの差分

既出`Configuration Authority Precedence`は「複数sourceが同時にある時どれが勝つか」。今回は**時間方向**の差分で、最初は正しいのにreload順序・one-shot source処理で後からauthorityが逆転する問題。

### (6) 次に検証すべきこと

**`ReloadAuthorityFixedPointBench-v0` — P1 candidate**

- env / vault / managed config / runtime override / per-profile configを5層程度用意
- N=100回reload、順序変更、secret rotation、profile switchを注入
- unchanged inputではeffective digest不変
- higher-authority source変更時のみ該当fieldが更新
- profile A materializationがBへ漏れない
- placeholder/token tombstoneが復活しない

### (7) なぜ既存dailyでは拾いにくいか

config precedence一般論ではなく、**再読込という時間軸を跨いだcomposition algebra**の失敗だから。通常のagent/memory surveyからは見えにくい。

### (8) 重要度

**A** — 永続agentはprocessを長期間生かしてreloadを繰り返すため、一回限りのCLIより露出が大きい。

## 5.3 A — Timeout contract は cleanup/finalizer まで含む wall-clock deadline closure にする

**Primary source**

- Hermes PR #115993  
  https://github.com/NousResearch/hermes-agent/pull/115993

### (1) 何が実証済みか

`.result(timeout=...)`は期限通りtimeoutしたが、その後の`Executor.__exit__ → shutdown(wait=True)`がhung workerをjoinしたためcallerは30秒以上拘束された。PRのA/B regressionでは修正前30.31秒、修正後は要求した約0.5秒でcallerをreleaseし、targeted tests 7件passと報告。

### (2) 何が提案・推測段階か

daemon workerを残すことが常に安全という意味ではない。read-only fetchならcaller livenessを優先しやすいが、side-effectful workではtimeout後もeffectが継続する可能性があるため、cancel/reconcile/outcome-unknown契約が必要。

### (3) Kamimusuhiのどこに関係するか

- tool/model orchestration
- K-Nerve low-latency cognition
- external resource health
- liveness / degraded-mode operation
- action router / cancellation / outcome ledger

### (4) 借りられる設計・実装アイデア

`DeadlineBudget`をchild callだけでなくcleanupまでpropagateする。

```text
DeadlineBudget
  absolute_deadline
  remaining()
  effect_class = READ_ONLY | IDEMPOTENT | AMBIGUOUS_EFFECT
  timeout_outcome = CANCELLED | DETACHED_READ | RECONCILE_REQUIRED
```

cleanup/finalizerに無制限waitを許さず、期限超過時は「caller released」と「child quiesced」を別eventとして記録する。

### (5) Kamimusuhiとの差分

既出Cancellation Closureは「止めた後にdescendant effectが生き残らないか」を扱う。今回は**停止/timeoutのsignalが発生した後もcleanupがcallerを拘束し、latency contractを破る**問題。逆にdetachを選ぶとchild quiescenceは未達なので、二つのcontractを同時に管理する必要がある。

### (6) 次に検証すべきこと

**`DeadlineClosureBench-v0` — P0/P1 candidate**

- provider never-responds / cleanup hangs / log flush hangs / nested executor / subprocessを注入
- 50ms〜5s budgetでcaller release timeを測定
- READ_ONLYはdetach可、effectfulはkill/reconcileへ分岐
- metric:
  - wall-clock overrun p99
  - orphan work count
  - unresolved effect count
  - false-cancel / duplicate effect

### (7) なぜ既存dailyでは拾いにくいか

API timeout設定の有無ではなく、**language runtimeのcontext-manager/finalizer semantics**に潜むliveness bugだから。

### (8) 重要度

**A** — K-Nerveやinteractive/social loopでは数百ms〜秒のdeadline contractそのものが機能境界になる。

## 5.4 A — Degraded maintenance は正常時より destructive になってはいけない

**Primary source**

- Hermes PR #115906  
  https://github.com/NousResearch/hermes-agent/pull/115906

### (1) 何が実証済みか

summary provider overload + main fallback failure時、従来pathはgeneric fallback summaryをcommitし、live reproで13 messages→7 messages、7件drop。修正案はoverload classをterminal summary failureとして扱い、13→13のままabortする。

### (2) 何が提案・推測段階か

全fallbackを禁止する提案ではない。fallback artifactに十分な品質/evidence/continuation保証があるならcommit可能。問題は**maintenance subsystemの信頼度が落ちた時に、通常時より不可逆性が増える**こと。

### (3) Kamimusuhiのどこに関係するか

- context compaction
- sleep / dream / reflection
- memory consolidation / summarization
- Persona/self derived summaries
- Continuity Kernel commit gate

### (4) 借りられる設計・実装アイデア

maintenance transformに`loss_budget`と`source_retention_required`を付ける。

```text
MaintenanceTransform
  source_digest
  transform_quality
  failure_class
  loss_budget
  reversible
  source_retained_until_verified
```

`failure_class in {overload, auth, network, truncated, empty}`ではdestructive commitを原則禁止。low-quality fallbackはderived viewとして保存してもcanonical evidenceを削らない。

### (5) Kamimusuhiとの差分

直前の`CompactionContinuationClosureBench`はtask handle / agent id / verification stateの保持が中心。今回は**summary generation failure時のfallback policyそのものがcanonical evidenceを削る**という別の境界。

### (6) 次に検証すべきこと

**`DegradedMaintenanceNonDestructiveBench-v0` — P0 candidate**

- summarizer overload / timeout / truncation / low-confidence / malformed outputを注入
- canonical episode 100件 + active obligations + relationship evidenceを用意
- fail-open destructive fallback / fail-closed abort / derived-only fallbackを比較
- metric:
  - irreversible evidence loss
  - continuation correctness
  - storage growth
  - later recovery quality
  - false-abort rate

### (7) なぜ既存dailyでは拾いにくいか

memory qualityやcompression benchmarkではなく、**maintenance failure ladderのerror semantics**に現れる。通常成功pathだけを見るsurveyでは落ちやすい。

### (8) 重要度

**A** — Kamimusuhiはsleep/offline processingを積極的に使う構想なので、maintenance failureがidentity evidenceを壊す経路は早期に閉じる価値が高い。

## 5.5 A — Delivery timeout は ambiguous outcome として degraded marker へ落とす

**Primary source**

- Hermes PR #115977  
  https://github.com/NousResearch/hermes-agent/pull/115977

### (1) 何が実証済みか

cron bot-chat deliveryがtimeoutすると、実運用でdeadman alertのfindingsがjob outputにだけ残り、consumerには届かなかった。さらにkill直前にchildがsessionへpersist済みの可能性があり、full payload retryはduplicateを作り得る。修正案は280-char excerpt + durable run参照を持つdegraded markerをstable keyでqueueし、kill-window reportを再読してdelivered/lost polarityを再判定する。6 regression testsを追加。

### (2) 何が提案・推測段階か

degraded markerがあらゆるdelivery surfaceで最適とは限らない。human-facing alert、tool command、financial/physical effectでは必要なreconciliation手段が異なる。

### (3) Kamimusuhiのどこに関係するか

- reminders / prospective memory
- social replies / relationship continuity
- background work completion
- notification / multi-device delivery
- Factorized Outcome Ledger

### (4) 借りられる設計・実装アイデア

`DELIVERY_TIMEOUT`を`NOT_DELIVERED`に潰さず、次の状態を持つ。

```text
DeliveryOutcome
  CONFIRMED_DELIVERED
  CONFIRMED_NOT_DELIVERED
  AMBIGUOUS_AFTER_TIMEOUT
  DEGRADED_NOTICE_DELIVERED
```

ambiguous時はoriginal effectを再送せず、durable sourceへのpointerを持つidempotent markerを送る。後からreceiptが見つかれば状態をreconcileする。

### (5) Kamimusuhiとの差分

既出のexecution/delivery separationやdeferred reply anchorは「実行成功と配信成功を分ける」「何への返答かを保存する」。今回は**timeoutが配信のnegative proofにならない**ことと、duplicate riskを避けつつ人間へ「結果がある」ことだけ知らせる縮退protocolが差分。

### (6) 次に検証すべきこと

**`AmbiguousDeliveryDegradationBench-v0` — P1 candidate**

- persist-before-ack / ack-before-kill / network partition / late receipt / duplicate retryをfault inject
- full replay / drop / degraded marker / receipt reconciliationを比較
- success metric:
  - silent loss 0
  - duplicate side effect 0
  - user-visible unresolved outcome rate
  - marker recursion 0

### (7) なぜ既存dailyでは拾いにくいか

distributed messagingの「exactly-onceは難しい」という一般論ではなく、**agent notification UXとdurable execution recordを接続するdegraded protocol**だから。

### (8) 重要度

**A** — 長寿命agentでは「仕事は終わったが誰にも知られなかった」がcontinuity failureになり得る。

## 5.6 B — Capability は bound tuple としてatomicに扱う

**Primary source**

- Hermes PR #115976  
  https://github.com/NousResearch/hermes-agent/pull/115976

### (1) 何が実証済みか

Dashboard session tokenとloopback URLを独立env値としてlayeringすると、parent-injected launch capabilityがdotenv等で壊れ得る。別PR案の単純restoreは逆に別homeへlaunch capabilityをreplayし得た。#115976はpairでcapture/restoreし、process homeへscopeする。targeted tests 61件passと報告。

### (2) 何が提案・推測段階か

Kamimusuhiのcapability representationが同じenv構成で壊れる証拠はない。一般化はcredentialだけでなく`(authority token, target, scope, constraints)`を不可分なsemantic objectとして扱う提案。

### (3) Kamimusuhiのどこに関係するか

- local control surfaces
- credentials / capability security
- multi-profile / multi-device embodiment
- resource router

### (4) 借りられる設計・実装アイデア

```text
BoundCapability
  capability_id
  bearer_or_handle
  target_origin
  scope_id
  issued_for_body
  constraints
  expiry
  provenance
```

config layerは個々のfieldを上書きせず、capability object全体をreplace/revokeする。target変更時はtoken再bindingまたはreissueを要求。

### (5) Kamimusuhiとの差分

既出capability attenuationは「delegate時に権限を狭める」、config authority precedenceは「どのsourceが勝つか」。今回は**authorityの意味が複数fieldの結合関係に宿るため、片側だけの正しい値でも全体として誤権限になる**問題。

### (6) 次に検証すべきこと

**`CompoundCapabilityAtomicityBench-v0` — P2 candidate**

- token A + URL A、token B + URL Bを複数layerへ配置
- partial reload / profile switch / child spawn / home overrideを注入
- A-token/B-targetのchimera組合せが一度もeffect pathへ出ないことを確認
- stale pair / cross-home replayはfail closed

### (7) なぜ既存dailyでは拾いにくいか

credential managementでは通常「secret value」単体を見るが、これは**複合capabilityのreferential integrity**の問題だから。

### (8) 重要度

**B** — 現時点でKamimusuhi固有のfailure証拠はないが、実装コストが低くsecurity benefitが明確。

## 10. 今回の結論

今回の最も重要な盲点は、**「継続性のために残すstate」と「継続性を守るためにrestore後必ず更新しなければならないstate」は逆方向の性質を持つ**ことだった。snapshotはmodel/configを高速に復元できる一方、entropy、time base、credential、instance identity、mutable discoveryまで凍結すると別bodyが同一ephemeral identityを共有してしまう。

もう一つの軸は **degraded pathの設計**。timeoutした、summary modelが落ちた、delivery ackが来なかった、configをreloadした、という異常時ほど「とりあえずfallback」で不可逆変換やfull replayを行わず、canonical evidenceを残し、ambiguous stateをambiguousなまま記録し、callerのdeadlineとdescendant quiescenceを分離する方がKamimusuhiのidentity continuityに合う。

次回はこの流れから、**restore後のentropy/lease fencing、priority inversion、snapshot-aware provenance、late receipt reconciliation**を重点的に追う価値がある。
